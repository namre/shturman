# Изменения

## 0.0.4 — 2026-10-07

Всё новое в этой версии по умолчанию выключено: экземпляр, который просто обновили, ведёт себя как раньше. Исключения названы в конце раздела.

**Свой бот согласований и своя модель сервиса**

- У сервиса переписки может быть свой бот — «бот согласований» (`SHTURMAN_BOT_TOKEN`). Его токен есть только в контейнере сервиса. Карточки с кнопками приходят в этого бота, а нажатие владельца сервис получает от Telegram напрямую, мимо Hermes. Владелец привязывается к боту одноразовой ссылкой: `./ops/bot-bind.sh`.
- Своя модель сервиса (`SHTURMAN_LLM_API_KEY`, `SHTURMAN_LLM_MODEL`, API, совместимый с OpenAI): сервис сам спрашивает модель при ночной обработке, сборке страниц, автоответе и в наблюдателе.
- Со своим ботом бизнес-режим Telegram подключается к нему, а не к боту Hermes; отправка от имени владельца идёт через него же.
- Со своим ботом плагину закрыты маршруты, через которые можно было подделать владельца: `/api/owner`, `/api/callbacks/telegram`, `/api/ingest/business/*` отвечают 403 с кодом `own_bot`. Задания, которые сервис выполняет сам, по HTTP закрыть нельзя: `/api/jobs/{id}/complete` и `/fail` трогают только задания плагина.
- Плагин в Hermes при своём боте уходит в спокойный режим: не привязывает владельца, не передаёт нажатия, не пересылает бизнес-сообщения. О режиме он узнаёт из `GET /api/status` и из отказа `own_bot`, переспрашивает раз в 5 минут. На старую кнопку в чате Hermes владелец получает ответ «Теперь согласования приходят в отдельного бота».
- Команды `shturman bot-bind` и `shturman bot-status`, маршрут `GET /api/executor/status`. Миграции `0013_executor.sql` и `0015_executor_bot.sql`.
- Бот и модель ходят в сеть через `EGRESS_PROXY_URL`, в том числе через прокси SOCKS (`httpx[socks]`, пакет `socksio`).

**Подтверждения владельца**

- Со своим ботом изменения, которые расширяют права ассистента или необратимо стирают данные, по HTTP не применяются: маршрут отвечает 202 `pending_confirmation`, владелец получает карточку «Подтвердите действие» и решает кнопкой. На решение час. Ужесточения применяются сразу. Что именно ждёт — таблица в `docs/service.md`.
- Маршруты `GET /api/confirmations`, `GET /api/confirmations/{id}`, `POST /api/confirmations/{id}/cancel`. Подтвердить действие по HTTP нельзя.
- `shturman call` на ответ 202 печатает «ЖДЁТ ПОДТВЕРЖДЕНИЯ В БОТЕ». `./ops/tg-login.sh` при своём боте сначала ждёт разрешения владельца в боте и только потом показывает QR-код.
- Без своего бота всё это применяется сразу, как в 0.0.3.

**Защита от внедрённых инструкций**

- Каждое входящее текстовое сообщение при записи в архив оценивает модель-классификатор `Horizon-Labs/prompt-injection-guard-small` в отдельном контейнере без выхода в интернет. Подозрительное скрывается от ассистента; владелец получает одно уведомление с кнопками «Показать ассистенту» и «Оставить скрытым» (`docs/guard.md`).
- По умолчанию выключено. Включается командой `./ops/guard.sh on`: около 0,3 ГБ скачивания, около 0,6 ГБ памяти.
- Измерено на синтетическом русском наборе, порог 0,9: модель находит 79 % попыток на своём наборе и 56 % на независимом; ложных срабатываний 8 % и 2 %. Просьбы переслать данные, сказанные как обычная просьба, ловятся редко. Это снижение риска, а не гарантия.
- Все пути, которые отдают переписку ассистенту и модели, учитывают новый признак `messages.agent_visible`. Текст скрытого сообщения через внутренний API не отдаётся, выключателя защиты в API нет.
- `/api/status`: счётчики `guard_*`. Маршрут `GET /api/guard/status`. Миграция `0014_guard.sql`.

**Режим установки без Hermes**

- Второй режим — «только архив и согласования»: `SHTURMAN_MODE=standalone`. Работают сервис переписки и база; у сервиса свой бот и своя модель; архив подключается к Codex CLI или Claude Code владельца (`docs/standalone.md`, `docs/runbooks/deploy-standalone.md`, `prompts/deploy-standalone.md`). Режим по умолчанию прежний, с Hermes.
- Чего в этом режиме нет: разговора с ассистентом в Telegram, сводок, веб-мастера и **готовых черновиков ответов** — создавать их без Hermes некому.
- `compose.yaml`: контейнер Hermes описан профилем `hermes`; сервису передаются `SHTURMAN_BOT_TOKEN` и `SHTURMAN_LLM_*`, контейнеру Hermes — нет.
- Новые скрипты: `ops/mode.sh`, `ops/bot-bind.sh`, `ops/connect.sh`, `ops/mcp-token.sh` (запускает только человек), `ops/guard.sh`, общий `ops/lib.sh`. `ops/init-env.sh` получил ключ `--mode` и вопросы о токене бота согласований и ключе модели.
- `ops/up.sh` и `ops/doctor.sh` работают в обоих режимах. `ops/doctor.sh` показывает режим, состояние бота согласований, своей модели и защиты, а в режиме с Hermes — знает ли плагин о своём боте сервиса (`plugin-own-bot`).

**Прочее**

- `ops/backup.sh` кладёт в копию и файл `.env`; каталог модели защиты в копию не входит.
- Тексты бота согласований и команды `shturman bot-status` больше не отсылают к Hermes там, где его может не быть.
- Исправлено: `ops/up.sh` при каждом запуске переписывал запись об архиве в настройках Hermes и лишний раз перезапускал Hermes. Hermes отдаёт настройки с подставленными переменными окружения, и сравнение с образцом не сходилось.
- Исправлено: `ops/doctor.sh` показывал `FAIL embeddings` при выключенном поиске по смыслу; без программы `ss` проверка «порт не слушает наружу» молча проходила.
- Исправлено: `ops/embeddings.sh` затирал чужие профили в `COMPOSE_PROFILES`. Теперь `ops/embeddings.sh` и `ops/guard.sh` меняют только свой профиль одной общей функцией.
- Исправлены три теста, которые изредка падали из-за гонки с фоновой работой.
- Решения Р-44–Р-50. Изменены правила для агента (`AGENTS.md`): режимы установки, ввод токена бота и ключа модели, ссылка привязки, токен архива, смена режима, защита.

**Что меняется без включения нового**

- `SHTURMAN_SENDING=on` теперь действует только вместе со своим ботом согласований. Без него отправка остаётся выключенной при любом значении.
- `SHTURMAN_GUARD` по умолчанию `off`. В коде 0.0.3 значилось `on`, но ничего не включало.

**Не проверено**

- Настоящий бот Telegram: связь, привязка по ссылке, карточки, кнопки, бизнес-режим через своего бота. Всё проверено на подставном Telegram.
- Настоящая модель по ключу сервиса.
- Защита на настоящей переписке; полный путь `./ops/guard.sh on` → `./ops/up.sh` → `./ops/doctor.sh`.
- Совместная работа Hermes и бота согласований на живом боте.
- Эталонный сервер. Под Docker стек запускался только на стенде разработки, с образом сервиса, собранным из изменённого `Dockerfile` (`docs/deployment.md`).
- Новые строки `ops/doctor.sh` про защиту и `plugin-own-bot` под Docker не исполнялись.

Автоматические тесты: сервис — 1389, плагин — 428 без Hermes (3 пропущены) и 535 с Hermes 0.21.5.

**Требует действий при обновлении** — `UPGRADING.md`.

## 0.0.3 — 2026-10-06

- Сервис переписки стал одним работающим процессом: `shturman serve` на локальном адресе, порт 8765 — `/health`, внутренний API `/api/*` для плагина и архив `/mcp` для агента Hermes, у каждого свой токен.
- Общий путь записи в архив для экспорта, бизнес-бота и сессий; служебные чаты Telegram и диалог «Коды подтверждения» в архив не принимаются.
- Приём сообщений бизнес-бота из плагина; загрузка экспорта через внутренний API; исключение чата из архива с удалением сохранённого.
- Сессии аккаунтов Telegram на Telethon: вход по QR, основной аккаунт владельца — только чтение, аккаунт-помощник, выбор чатов владельцем, загрузка истории на 12 месяцев по умолчанию, приём новых, изменённых и удалённых сообщений, сверка.
- MCP-сервер архива для агента: девять инструментов только на чтение, чужой текст — в рамке.
- Поиск по смыслу: эмбеддинги `intfloat/multilingual-e5-small` в отдельном контейнере без выхода в интернет, гибридный поиск. По умолчанию выключено; `ops/embeddings.sh on|off|status`.
- Обработка: реестр людей, разбор сроков кодом, извлечение обязательств с одобрением владельца, ночной прогон.
- Страницы памяти о людях: файлы Markdown и история в git в каталоге данных сервиса.
- Шлюз отправки: черновики с согласованием кнопкой, автоответ доверенным, наблюдатель групп. **Отправка выключена по умолчанию** и включается только в `.env` на сервере: `SHTURMAN_SENDING`, потолок `SHTURMAN_SEND_DAILY_CAP`.
- Плагин `shturman`: мост к сервису — исполнитель заданий (модель, сообщение владельцу, отправка через бизнес-бота), пересылка бизнес-сообщений в архив, кнопки согласования; инструменты агента `shturman_draft_message`, `shturman_commitments`, `shturman_commitment_update`, `shturman_people`; скиллы `shturman:morning-brief` и `shturman:weekly-review`; проход дашборда к сервису. Экранов для этого в кабинете пока нет.
- `compose.yaml`: сервис переписки, Postgres 16 с pgvector в закрытой сети, профиль эмбеддингов. Образ сервиса собирается на сервере, зависимости — из списка с контрольными суммами (`service/requirements.lock`).
- `ops/up.sh` собирает и запускает сервис, подключает архив к Hermes; `ops/doctor.sh` проверяет сервис, базу, очередь заданий и эмбеддинги; `ops/backup.sh` дополнительно выгружает базу.
- `ops/import-export.sh` — импорт экспорта без веб-интерфейса; `ops/tg-login.sh` — вход в аккаунт Telegram, запускает человек.
- Известное ограничение: токен внутреннего API доступен агенту Hermes, поэтому отправку включать не следует (`docs/architecture.md`).
- Не проверено: настоящий Telegram, настоящая модель, запуск под Docker, эталонный сервер (`docs/service.md`, `docs/deployment.md`).
- Решения Р-29–Р-42. Изменены правила для агента: включение отправки, вход в аккаунт Telegram, команды `shturman call`, данные сервиса (`AGENTS.md`).
- **Требует действий при обновлении** — `UPGRADING.md`.

## 0.0.2 — 2026-10-06

- Плагин Hermes `shturman` (`plugins/shturman/`): вход в дашборд по одноразовой ссылке активации и по коду от собственного бота владельца; привязка владельца кнопкой «Запустить»; мастер первой настройки из шести шагов со схемами «куда нажать и что ввести»; перехват сообщений бизнес-режима, пока не включён плагин бизнес-режима.
