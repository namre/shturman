## 0.0.7 — 2026-10-08

### Ограниченные ответы и повседневные решения

- Сохраняемые задачи ответа: модель предлагает ответ, запрос определённого источника, вопрос владельцу или отказ. После решения владельца задача продолжается с прежними адресатом и целью; отказ, отмена, истечение и ошибка имеют явные состояния.
- Раздельные разрешения чтения и раскрытия для чатов, памяти и зарегистрированного внешнего источника. Сервисные свидетельства связывают фрагменты с точной задачей, запросом и версией; перед доставкой проверяются отзыв, видимость и актуальность. Готовый текст без права автоматического раскрытия ждёт точного просмотра владельца.
- Карточка источника в Telegram показывает название, получателя и тему, точный запрос, даты и пределы; кнопка «Этот поиск — на 30 дней» сохраняет только точное разрешение чтения для той же области без повторного вопроса. Однократное чтение и отказ остаются отдельными кнопками.
- Ограниченный внешний MCP-посредник поиска/чтения. Реестр и credentials — только у сервиса; модель не выбирает URL, headers или произвольный tool. Публичный HTTPS, проверка адресов, ограничение ответа и времени. Это контракт подключения, не готовая универсальная интеграция любой почты (`docs/external-sources.md`).
- Независимый бот сервиса принимает меню и команды текущего привязанного владельца только в личном чате: задачи, источники, отзыв, правила и группы. Поддельное поручение через HTTP не получает owner authority. Свободный разговор остаётся в полном штатном Hermes.
- Подготовка без доставки: режим `prepare_only` и явное решение владельца `/prepare on|off`. Начальная отправка остаётся выключенной; репетиционный черновик не становится доставляемым от последующего включения отправки.
- Групповые кандидаты — только аккаунт-помощник, достоверное новое входящее сообщение обычного пользователя, точная область аккаунта/чата/темы либо проверенное прямое обращение. Цитаты, код, пересылки, правки, боты и неизвестные признаки не создают обращения. Источники и право отправки проверяются отдельно; наблюдатель групп остаётся уведомлением владельцу.
- Исключение служебного собеседника очищает связанные копии контекста задач, задания модели и черновики; производная память помещается в карантин. Уже переданные наружу данные этим не отзываются.
- Внешний MCP одинаково проверяет эквивалентные записи Host (регистр, завершающая точка и стандартный HTTPS-порт); неоднозначные повторные заголовки отклоняются.
- Успешная доставка имеет конечный статус `completed`. Позднее подтверждение прежней неизвестной доставки исправляет связанную запись результата, не создаёт повторную отправку.
- Решение проверенного владельца может продолжить точную задачу в пределах её срока; пятиминутная свежесть сохраняется для автоматической работы без такого решения.
- Усиление привязки черновика: неизменяемые текст, получатель, тема, исходное сообщение, задача, источники и версия политики. Неизвестная доставка не повторяется автоматически.

- Необязательный внешний OAuth-вход к архиву на чтение на отдельном HTTPS-origin: PKCE S256, точные адрес возврата и ресурс, согласие владельца в независимом Telegram-боте, одноразовые коды, ротация и отзыв токенов. `archive:read` открывает весь доступный архив; путь по умолчанию выключен. Код реализован, конкретный облачный клиент требует живого пилота (`docs/remote-mcp.md`).

- Актуализированы архитектура, установка, самостоятельный режим, документы сервиса, правила агента и стартовые промпты. Исторические результаты 0.0.6 сохранены с датами; поддержка новых провайдеров и клиентов не придумана.
- Добавлены целевая модель и критерии приёмки, отдельный документ подключения источников, runbook изолированных проверок и личного пилота, русский сценарий CEO-видео на 3–4 минуты. На видео непроверенные внешние сценарии обозначаются макетами.

**Границы проверки.** Новые функции проходят локальную приёмку на искусственных данных и подставных внешних системах. Это не свидетельство настоящего Telegram, качества ответа выбранной модели, подключения конкретной почты или облачного клиента. ## 0.0.6 — 2026-10-07

**Страница настройки переписки**

- Сервис переписки сам отдаёт владельцу страницу `/shturman-setup/` — мимо Hermes, со своим входом. На ней три шага: ключи приложения Telegram, вход в свой аккаунт Telegram по QR-коду (на чтение), выбор чатов. По желанию — выгрузка из Telegram Desktop. В блоке «Дополнительно» — то, что понадобится позже: бот согласований, бизнес-режим, аккаунт-помощник, своя модель сервиса; там же счётчики архива и журнал действий. Терминал владельцу для этого больше не нужен; команды остались запасным путём. Решение Р-55.

Ссылку создаёт только команда на сервере; маршрута для неё во внутреннем API нет. Завершить все входы — `./ops/logout-all.sh`. Вход по коду от бота согласований (8 цифр, 5 минут) есть, только когда бот настроен и владелец привязан.

Миграция одна — `0016_setup_page.sql`: таблицы `setup_links`, `setup_sessions`, `setup_state`, `setup_audit`.

**Отдельный адрес страницы — находка проверки безопасности**

- Независимая проверка безопасности 2026-10-07 нашла критичную дыру в первой редакции: страницу отдавали с адреса дашборда Hermes, а ассистент может ставить расширения дашборда — его скрипт на том же адресе действовал бы на странице от имени вошедшего владельца и перехватывал бы вводимое. Теперь у страницы свой адрес: по умолчанию то же имя, порт 8443. Решение Р-56.
- `.env`: новая несекретная строка `SHTURMAN_SETUP_URL`. `./ops/set-public-url.sh` записывает её вместе с адресом дашборда, `./ops/up.sh` дописывает экземпляру, у которого её ещё нет. Новый `./ops/set-setup-url.sh` показывает, меняет и убирает адрес и отказывает, если он совпал с адресом дашборда.
- `compose.yaml`: сервис получает адрес страницы (`SHTURMAN_SETUP_ORIGIN`) и адрес дашборда (`SHTURMAN_DASHBOARD_ORIGIN`); при совпадении страницу снаружи не отдаёт — по локальному адресу она остаётся доступной. Адреса сравниваются как схема, имя и порт; неразборчивый адрес сервис не принимает и не запускается, поэтому `./ops/up.sh` останавливается на такой записи в `.env` до перезапуска.
- `config/Caddyfile.example`: два блока сайта. В блоке дашборда на путь страницы стоит отказ; страница — в своём блоке на порту 8443, и до порта сервиса доходят только простые пути под `/shturman-setup/`.
- Сессия страницы — без cookie: cookie по портам не разделяются. Ключ сессии лежит в хранилище браузера для адреса страницы и приходит в заголовке; сессия живёт ровно 7 дней от входа. Запросы к API страницы сервис принимает только от самой страницы — запрос с адреса дашборда или с чужого сайта получает отказ и с верным ключом. Решение Р-57.
- Вторая находка той же проверки: сохранённый ключ своей модели мог уйти на адрес, заданный позже. Теперь адрес, введённый на странице, — только https и не во внутренние сети (проверяется по записи и заново при каждом запросе), а при смене адреса ключ вводится заново. Оговорка: за исходящим прокси HTTP имя второй раз разрешает сам прокси. Адрес из `.env` не фильтруется и со страницы не меняется.
- `./ops/doctor.sh`: строки `setup-page`, `setup-origin`, `setup-page-public`, `setup-isolation`, `setup-state`. Кто ответил, проверка узнаёт по заголовку-метке `X-Shturman-Setup-Page`, которую сервис ставит на ответ с самой страницей, а не по телу ответа.

Сервис считает непустую переменную «заданной на сервере», поэтому поле адреса своей модели на странице под Docker было закрыто, и ввести адрес другого провайдера было нельзя. У мастера не было шага «Переписка», а проход дашборда к сервису по-прежнему пропускал вход в Telegram и импорт. Теперь `./ops/up.sh` перезапускает Hermes, когда файлы плагина изменились (отпечаток — `local/plugin.sha256`), а `./ops/doctor.sh` показывает `WARN plugin-code`, если этого ещё не сделали.

- `./ops/doctor.sh` при адресе дашборда с путём проверял, закрыта ли страница, под этим путём, а не в корне адреса. Теперь запрос идёт в корень.
- `./ops/doctor.sh` и `./ops/set-setup-url.sh` говорили «страница отключена», когда её адрес совпал с адресом дашборда; на самом деле сервис не отдаёт её только по внешнему адресу. Тексты приведены к поведению.
- `./ops/up.sh` в режиме без Hermes напоминал про «кнопку в мастере»; теперь — про туннель SSH.
- `.gitignore`: каталог `node_modules`, подключённый символической ссылкой для браузерного сценария, больше не попадает в git.
- CI: проверяется, что адрес модели не подставляется по умолчанию, что `./ops/up.sh` останавливается на неразборчивом адресе до обращения к Docker и что файлы страницы настройки и миграции есть в собранном образе.
- Текст отказа сервиса «сначала привяжите себя к боту… в мастере настройки» при подключении помощника называет теперь основной путь — подключить основной аккаунт на странице — и не упоминает мастер.

## 0.0.5 — 2026-10-07

Экземпляр, который просто обновили, ведёт себя как раньше: схема базы не меняется, модель поиска по смыслу остаётся прежней. Исключения названы в конце раздела.

**Вторая модель поиска по смыслу**

- К `intfloat/multilingual-e5-small` добавлена вторая поддерживаемая модель — русскоязычная `deepvk/USER2-small` (Apache-2.0, 384 измерения, схема базы та же). Модель по умолчанию прежняя. Выбирает владелец: `./ops/embeddings.sh on --model e5-small|user2-small`; `./ops/embeddings.sh status` показывает модель. Решение Р-51.
- `ops/embeddings.sh` скачивает выбранную модель по закреплённой ревизии и сверяет контрольную сумму каждого файла — раньше сверялись только веса и токенизатор. У каждой модели свой каталог: смена туда и обратно ничего не перекачивает.
- `compose.yaml`: контейнер эмбеддингов берёт модель и её имя из `.env`, а без этих строк запускает прежнюю модель из прежнего каталога; добавлен `--max-batch-tokens 2048` — без него `USER2-small` не запускается в отведённой памяти. Имя модели сервису теперь передаёт `compose.yaml`, той же строкой, что и контейнеру.
- Смена модели — пересчёт всех векторов. Векторы двух моделей в выдаче не смешиваются: до конца пересчёта поиск по смыслу видит только уже пересчитанные сообщения, поиск по словам — весь архив. Прежние векторы не стираются, пока контейнер не подтвердил, что отдаёт новую модель.
- `GET /api/status` и `./ops/doctor.sh` показывают модель, сколько сообщений посчитано и сколько осталось; `GET /api/embeddings/status` — ещё и сколько посчитано прежней моделью. Доступность сервера эмбеддингов сервис проверяет обращением к нему, а `ops/doctor.sh` даёт контейнеру до полуминуты на прогрев, прежде чем сообщить о неполадке.
- Пачка для сервера эмбеддингов ограничена по объёму текста (`SHTURMAN_EMBEDDINGS_BATCH_CHARS`, по умолчанию 8000 знаков): пачка из длинных сообщений больше не может считаться дольше срока ожидания и застревать в очереди.
- Исправлено: `./ops/embeddings.sh off` оставлял контейнер эмбеддингов работать и занимать память — Compose не останавливает контейнер выключенного профиля сам. Теперь скрипт убирает его явно; файлы моделей и посчитанные векторы остаются. `ops/doctor.sh` раньше судил о поиске по смыслу по одному состоянию контейнера и после `off` показывал его включённым; теперь он спрашивает сервис.
- Набор и скрипт измерения поиска перенесены в репозиторий: `service/tests/search/data/`, `service/tools/search_eval.py`. Скрипт меряет и «только модель», и настоящий путь сервиса — запись в архив, фоновый счётчик, гибридный поиск. Числа и оговорки — новый документ `docs/search.md`.
- Смена модели — стоп-точка в `AGENTS.md`: только по явной просьбе владельца.

**Выбор варианта установки**

- При установке владелец выбирает из двух вариантов: «Ассистент в Telegram (Hermes)» и «Только архив и согласования». Агент спрашивает об этом до первого шага и сам не выбирает: вопрос добавлен в стартовые промпты, в оба runbook-а, в `README.md` и `docs/setup.md`. Решение Р-53.

## 0.0.4 — 2026-10-07

Всё новое в этой версии по умолчанию выключено: экземпляр, который просто обновили, ведёт себя как раньше. Исключения названы в конце раздела.

**Свой бот согласований и своя модель сервиса**

- У сервиса переписки может быть свой бот — «бот согласований» (`SHTURMAN_BOT_TOKEN`). Его токен есть только в контейнере сервиса. Карточки с кнопками приходят в этого бота, а нажатие владельца сервис получает от Telegram напрямую, мимо Hermes. Владелец привязывается к боту одноразовой ссылкой: `./ops/bot-bind.sh`.
- Своя модель сервиса (`SHTURMAN_LLM_API_KEY`, `SHTURMAN_LLM_MODEL`, API, совместимый с OpenAI): сервис сам спрашивает модель при ночной обработке, сборке страниц, автоответе и в наблюдателе.
- Со своим ботом бизнес-режим Telegram подключается к нему, а не к боту Hermes; отправка от имени владельца идёт через него же.
- Со своим ботом плагину закрыты маршруты, через которые можно было подделать владельца: `/api/owner`, `/api/callbacks/telegram`, `/api/ingest/business/*` отвечают 403 с кодом `own_bot`. Задания, которые сервис выполняет сам, по HTTP закрыть нельзя: `/api/jobs/{id}/complete` и `/fail` трогают только задания плагина.
- Плагин в Hermes при своём боте уходит в спокойный режим: не привязывает владельца, не передаёт нажатия, не пересылает бизнес-сообщения. О режиме он узнаёт из `GET /api/status` и из отказа `own_bot`, переспрашивает раз в 5 минут. На старую кнопку в чате Hermes владелец получает ответ «Теперь согласования приходят в отдельного бота».
- Команды `shturman bot-bind` и `shturman bot-status`, маршрут `GET /api/executor/status`. Миграции `0013_executor.sql` и `0015_executor_bot.sql`.
- Бот и модель ходят в сеть через `EGRESS_PROXY_URL`, в том числе через прокси SOCKS (`httpx[socks]`, пакет `socksio`).

**Подтверждения владельца**

- Со своим ботом изменения, которые расширяют права ассистента или необратимо стирают данные, по HTTP не применяются: маршрут отвечает 202 `pending_confirmation`, владелец получает карточку «Подтвердите действие» и решает кнопкой. На решение час. Ужесточения применяются сразу. Что именно ждёт — таблица в `docs/service.md`.
- Маршруты `GET /api/confirmations`, `GET /api/confirmations/{id}`, `POST /api/confirmations/{id}/cancel`. Подтвердить действие по HTTP нельзя.
- `shturman call` на ответ 202 печатает «ЖДЁТ ПОДТВЕРЖДЕНИЯ В БОТЕ». `./ops/tg-login.sh` при своём боте сначала ждёт разрешения владельца в боте и только потом показывает QR-код.
- Без своего бота всё это применяется сразу, как в 0.0.3.

**Защита от внедрённых инструкций**

- Каждое входящее текстовое сообщение при записи в архив оценивает модель-классификатор `Horizon-Labs/prompt-injection-guard-small` в отдельном контейнере без выхода в интернет. Подозрительное скрывается от ассистента; владелец получает одно уведомление с кнопками «Показать ассистенту» и «Оставить скрытым» (`docs/guard.md`).
- По умолчанию выключено. Включается командой `./ops/guard.sh on`: около 0,3 ГБ скачивания, около 0,6 ГБ памяти.
- Измерено на синтетическом русском наборе, порог 0,9: модель находит 79 % попыток на своём наборе и 56 % на независимом; ложных срабатываний 8 % и 2 %. Просьбы переслать данные, сказанные как обычная просьба, ловятся редко. Это снижение риска, а не гарантия.
- Все пути, которые отдают переписку ассистенту и модели, учитывают новый признак `messages.agent_visible`. Текст скрытого сообщения через внутренний API не отдаётся, выключателя защиты в API нет.
- `/api/status`: счётчики `guard_*`. Маршрут `GET /api/guard/status`. Миграция `0014_guard.sql`.

**Режим установки без Hermes**

- Второй режим — «только архив и согласования»: `SHTURMAN_MODE=standalone`. Работают сервис переписки и база; у сервиса свой бот и своя модель; архив подключается к Codex CLI или Claude Code владельца (`docs/standalone.md`, `docs/runbooks/deploy-standalone.md`, `prompts/deploy-standalone.md`). Режим по умолчанию прежний, с Hermes.
- Чего в этом режиме нет: разговора с ассистентом в Telegram, сводок, веб-мастера и **готовых черновиков ответов** — создавать их без Hermes некому.
- `compose.yaml`: контейнер Hermes описан профилем `hermes`; сервису передаются `SHTURMAN_BOT_TOKEN` и `SHTURMAN_LLM_*`, контейнеру Hermes — нет.
- Новые скрипты: `ops/mode.sh`, `ops/bot-bind.sh`, `ops/connect.sh`, `ops/mcp-token.sh` (запускает только человек), `ops/guard.sh`, общий `ops/lib.sh`. `ops/init-env.sh` получил ключ `--mode` и вопросы о токене бота согласований и ключе модели.
- `ops/up.sh` и `ops/doctor.sh` работают в обоих режимах. `ops/doctor.sh` показывает режим, состояние бота согласований, своей модели и защиты, а в режиме с Hermes — знает ли плагин о своём боте сервиса (`plugin-own-bot`).

**Прочее**

- `ops/backup.sh` кладёт в копию и файл `.env`; каталог модели защиты в копию не входит.
- Тексты бота согласований и команды `shturman bot-status` больше не отсылают к Hermes там, где его может не быть.
- Исправлено: `ops/up.sh` при каждом запуске переписывал запись об архиве в настройках Hermes и лишний раз перезапускал Hermes. Hermes отдаёт настройки с подставленными переменными окружения, и сравнение с образцом не сходилось.
- Исправлено: `ops/doctor.sh` показывал `FAIL embeddings` при выключенном поиске по смыслу; без программы `ss` проверка «порт не слушает наружу» молча проходила.
- Исправлено: `ops/embeddings.sh` затирал чужие профили в `COMPOSE_PROFILES`. Теперь `ops/embeddings.sh` и `ops/guard.sh` меняют только свой профиль одной общей функцией.
- Исправлены три теста, которые изредка падали из-за гонки с фоновой работой.
- Решения Р-44–Р-50. Изменены правила для агента (`AGENTS.md`): режимы установки, ввод токена бота и ключа модели, ссылка привязки, токен архива, смена режима, защита.

**Что меняется без включения нового**

- `SHTURMAN_SENDING=on` теперь действует только вместе со своим ботом согласований. Без него отправка остаётся выключенной при любом значении.
- `SHTURMAN_GUARD` по умолчанию `off`. В коде 0.0.3 значилось `on`, но ничего не включало.

**Не проверено**

- Настоящий бот Telegram: связь, привязка по ссылке, карточки, кнопки, бизнес-режим через своего бота. Всё проверено на подставном Telegram.

- Защита на настоящей переписке; полный путь `./ops/guard.sh on` → `./ops/up.sh` → `./ops/doctor.sh`.
- Совместная работа Hermes и бота согласований на живом боте.
- Эталонный сервер. Под Docker стек запускался только на стенде разработки, с образом сервиса, собранным из изменённого `Dockerfile` (`docs/deployment.md`).
- Новые строки `ops/doctor.sh` про защиту и `plugin-own-bot` под Docker не исполнялись.
