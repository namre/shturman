# Развёртывание: как устроен экземпляр на сервере

Состояние на версию 0.0.6: Hermes с плагином `shturman` поднимался на живом сервере; сервис переписки и его база под Docker запускались **только на стенде разработки** (2026-10-07). Контейнеры защиты и эмбеддингов запускались на стенде из `compose.yaml`. Образец обратного прокси с отдельным блоком страницы настройки переписки проверен настоящим Caddy с подставными сервисами; на сервере с настоящим сертификатом и открытым портом — нет. Что проверено, а что нет, сказано в конце.

## Два режима установки

Вариантов установки два, и выбирает из них владелец — до первого шага установки агент спрашивает его, какой он ставит (решение Р-53). Режим записан в `.env` строкой `SHTURMAN_MODE` и задаётся при первой установке: `./ops/init-env.sh --mode hermes|standalone`. Без ключа `--mode` на новой установке скрипт спрашивает человека сам, а с `--auto` останавливается и просит назвать вариант. Показать и сменить — `./ops/mode.sh`.

| Режим | Что запускается | Документ |
|---|---|---|
| `hermes` — «Ассистент в Telegram (Hermes)» | Hermes, сервис переписки, база | Этот документ, `docs/runbooks/deploy.md` |
| `standalone` — «только архив и согласования» | Сервис переписки и база; у сервиса свой бот согласований и свой доступ к модели | `docs/standalone.md`, `docs/runbooks/deploy-standalone.md` |

Устроено это профилями Compose: контейнер Hermes описан с профилем `hermes`, эмбеддинги — с профилем `embeddings`, модель защиты — с профилем `guard`. Скрипты `ops/` сами выставляют профили по режиму и ведут строку `COMPOSE_PROFILES` в `.env`; `./ops/embeddings.sh` и `./ops/guard.sh` добавляют и убирают только свой профиль. Экземпляр, развёрнутый до появления режимов, строки режима не имеет: первый же `./ops/up.sh` записывает ему `SHTURMAN_MODE=hermes` и профиль `hermes`, сохраняя включённый поиск по смыслу. Голая команда `docker compose up` без профилей Hermes не запустит — стек поднимается только через `./ops/up.sh`.

Всё ниже описывает режим с Hermes.

## Принцип

**Hermes — стоковый.** Он ставится и обновляется своим штатным способом, его образ и код мы не меняем и возможности не урезаем. «Штурман» — это набор расширений к нему и один сервис рядом. Весь интеллект живёт в Hermes; сервис отвечает только за данные и сессии Telegram.

## Что чем сделано

| Что нужно | Чем делаем | Механизм Hermes |
|---|---|---|
| Вход владельца в дашборд | Плагин `shturman`: ссылка активации и код от собственного бота | Свой способ входа (`register_dashboard_auth_provider`) |
| Привязка владельца к боту, защита от сообщений бизнес-режима | Плагин `shturman` | Обработчики Telegram (`register_telegram_handler`) |
| Мастер первой настройки | Плагин `shturman`: вкладка «Штурман», пять шагов | Вкладка и маршруты в дашборде Hermes |
| Настройка переписки: ключи приложения Telegram, вход в аккаунт, выбор чатов, выгрузка | **Страница сервиса переписки** `/shturman-setup/`, на отдельном адресе, со своим входом. Мастер только ведёт на неё | — (мимо Hermes) |
| Бизнес-режим Telegram | В первую настройку не входит. Когда понадобится — подключается к боту согласований сервиса; бота Hermes в бизнес-режиме не подключают (Р-59) | — |
| Кнопки согласования; на экземпляре прежней схемы — запись бизнес-сообщений в архив | Плагин `shturman`: пересылка в сервис переписки | Обработчики Telegram, отдельная группа раньше остальных |
| Поиск по переписке, обязательства, страницы о людях — для агента | MCP-сервер сервиса переписки, только чтение | Штатный MCP-клиент |
| Черновик сообщения, правка обязательств и людей — для агента | Плагин `shturman`: четыре инструмента поверх внутреннего API сервиса | `register_tool` |
| Обращения сервиса к модели | Плагин `shturman`: исполнитель заданий. По желанию — сам сервис по своему ключу | Доступ плагина к модели (`ctx.llm`), вспомогательные задачи (`register_auxiliary_task`) |
| Карточки владельцу и нажатия кнопок | Плагин `shturman` в управляющем чате. Позже, когда владелец решит включать отправку, — свой бот согласований сервиса, мимо Hermes | Обработчики Telegram; у своего бота механизма Hermes нет |
| Защита от внедрённых инструкций | Сервис переписки и контейнер с моделью-классификатором; по умолчанию выключена | — |
| Утренняя сводка, обзор недели | Два скилла плагина и задачи по расписанию | `register_skill`, cron Hermes |
| Имя и характер | Блок в файле личности | `SOUL.md` |
| Сессии аккаунтов, архив, импорт, индексация, обработка, шлюз отправки | **Сервис переписки** — единственное, что вне Hermes | Для агента это обычный MCP-сервер; для плагина — внутренний API |
| Экраны кабинета: архив, память, правила, согласования | **Не сделаны.** Проход дашборда к сервису есть (`/api/plugins/shturman/service/...`), страниц нет. Входа в аккаунт Telegram, управления аккаунтами и импорта выгрузки в этом проходе нет: они только на странице сервиса | Вкладка и маршруты в дашборде Hermes |
| Гейт отправки хуком Hermes (`pre_tool_call`), подготовка ко встрече | Запланированы | — |

Почему сервис нельзя сделать плагином: плагины исполняются в процессе агента, а сессия пользовательского аккаунта — это полный доступ к аккаунту. Она должна лежать там, куда агент и его инструменты не дотягиваются.

Следствие: **по умолчанию модель одна — та, что настроена в Hermes.** Сервису переписки ключ модели не нужен: он ставит задание, плагин спрашивает модель (`docs/service.md`).

Позже, по желанию владельца, у сервиса могут быть свой бот согласований и свой доступ к модели: значения вводятся на странице настройки переписки, в разделе «Дополнительно», либо строками `SHTURMAN_BOT_TOKEN`, `SHTURMAN_LLM_API_KEY` и `SHTURMAN_LLM_MODEL` в `.env`. Они достаются только сервису. Тогда карточки с кнопками и нажатия идут мимо Hermes, бизнес-режим подключается к боту сервиса, а плагин уходит в спокойный режим (`docs/service.md`, «Свой бот согласований и своя модель»). В первую настройку это не входит.

## Эталонный вариант: один файл Compose

| Контейнер | Что это | Сеть | Данные |
|---|---|---|---|
| `shturman-hermes` | Официальный образ `nousresearch/hermes-agent` без изменений. Плагин `shturman` подключён из репозитория только для чтения | Сеть хоста — как в официальном compose Hermes | `data/hermes` |
| `shturman-service` | Сервис переписки. Образ собирается на сервере из каталога `service/` | `backend` и `egress`; порт 8765 опубликован только на `127.0.0.1`. Обратный прокси отдаёт наружу один его префикс — `/shturman-setup/` | `data/shturman` |
| `shturman-postgres` | Postgres 16 с pgvector (`pgvector/pgvector:0.8.7-pg16-bookworm`) | Только `backend`; порт не публикуется | `data/postgres` |
| `shturman-embeddings` | Сервер эмбеддингов TEI 1.9.4 с моделью, которую выбрал владелец: `intfloat/multilingual-e5-small` (по умолчанию) или `deepvk/USER2-small` (`docs/search.md`). Отдельный профиль Compose, по умолчанию выключен | Только `backend` | `data/embeddings`, только чтение |
| `shturman-guard` | Сервер TEI 1.9.4 с моделью-классификатором `Horizon-Labs/prompt-injection-guard-small` для защиты от внедрённых инструкций. Отдельный профиль Compose, по умолчанию выключен; лимит памяти 1 ГБ | Только `backend` | `data/guard`, только чтение |

Сети:

| Сеть | Что это | Кто в ней |
|---|---|---|
| `backend` | Закрытая: контейнеры видят друг друга, но не интернет | База, эмбеддинги, защита, сервис |
| `egress` | Обычная, с выходом в интернет | Только сервис: ему нужен Telegram для сессий аккаунтов и своего бота, а со своей моделью — и её провайдер |

У базы, у контейнера эмбеддингов и у контейнера защиты выхода в интернет нет вовсе. Через контейнер эмбеддингов проходит текст всех сообщений, через контейнер защиты — текст всех входящих, поэтому модели скачиваются заранее, на хосте, скриптами `./ops/embeddings.sh` и `./ops/guard.sh` с проверкой контрольных сумм.

Сервис переписки работает под владельцем каталога данных, без дополнительных прав (`cap_drop: ALL`, `no-new-privileges`). Hermes обращается к нему по адресу `127.0.0.1:8765`: он сам работает в сети хоста.

Hermes в официальном образе остаётся стоковым, а его терминал ограничен контейнером — без каких-либо наших правок. Доступ к Docker контейнеру `hermes` не даётся. Каталог `data/shturman` ему не подключён. При этом контейнер Hermes работает в сети хоста: из него достижим порт сервиса `127.0.0.1:8765`, а значит и страница настройки по локальному адресу. Войти на неё оттуда нечем — ссылку входа создаёт только команда в контейнере сервиса (`docs/security-review.md`).

## Что отдаётся наружу

Три вещи, все через обратный прокси на хосте (образец — `config/Caddyfile.example`, два блока сайта):

| Что | Адрес | Кто отвечает | Вход |
|---|---|---|---|
| Дашборд Hermes с мастером | `https://имя` (порт 443), всё, кроме двух путей ниже | Hermes, `127.0.0.1:9119` | Свой способ входа «Штурмана»: ссылка активации, код от бота |
| Страницы входа «Штурмана» | `https://имя/shturman-auth/` | Сам прокси, статические файлы из `plugins/shturman/public` | Не нужен: данных в них нет |
| Страница настройки переписки | `https://имя:8443/shturman-setup/` — то же имя, **другой порт** | Сервис переписки, `127.0.0.1:8765`, только пути под `/shturman-setup/` | Свой: одноразовая ссылка из `./ops/setup-link.sh` |

По адресу дашборда путь `/shturman-setup*` закрыт: прокси сам отвечает 404, запрос не уходит ни сервису, ни Hermes. Остальные пути сервиса переписки — внутренний API `/api/*` и архив `/mcp` — наружу не выходят ни по одному адресу. Порт сервиса и порт базы слушают только локальный адрес сервера; `./ops/doctor.sh` это проверяет.

**Почему у страницы настройки другой порт.** Ассистент в Hermes может ставить расширения дашборда, то есть исполнять свой JavaScript на адресе дашборда. Для браузера адрес — это схема, имя и порт вместе; на общем адресе такой скрипт действовал бы на странице настройки от имени вошедшего владельца. Другой порт — уже другой адрес. Подробно — `docs/architecture.md`, «Почему у страницы настройки свой адрес»; решение — Р-56.

Адреса лежат в `.env` двумя несекретными строками:

| Строка | Кто записывает | Куда идёт |
|---|---|---|
| `SHTURMAN_PUBLIC_URL` — адрес дашборда | `./ops/set-public-url.sh https://имя` | Hermes — как `HERMES_DASHBOARD_PUBLIC_URL`; сервису — как `SHTURMAN_DASHBOARD_ORIGIN`, только чтобы сверить, что адреса разные |
| `SHTURMAN_SETUP_URL` — адрес страницы настройки | По умолчанию (то же имя, порт 8443) — `./ops/set-public-url.sh`, а экземпляру, у которого строки ещё нет, — `./ops/up.sh`. Другой порт или отдельное имя — `./ops/set-setup-url.sh`; убрать — `./ops/set-setup-url.sh --clear` | Сервису — как `SHTURMAN_SETUP_ORIGIN` |

`./ops/set-setup-url.sh` не принимает адрес, совпадающий с адресом дашборда, и объясняет почему. Если адреса всё же совпали (строку вписали вручную), сервис запускается, но страницу снаружи не отдаёт; `./ops/doctor.sh` показывает `FAIL setup-origin`, мастер — «странице нужен отдельный адрес». Если адрес страницы не задан или убран, она открывается только с самого сервера и через туннель SSH: `./ops/setup-link.sh` в этом случае даёт локальную ссылку и подсказку про туннель.

Что нужно на сервере для адреса по умолчанию:

- второй блок сайта в обратном прокси и отказ на `/shturman-setup*` в блоке дашборда — правка прокси, стоп-точка;
- порт 8443 открыт в firewall сервера и в правилах хостинга — стоп-точка;
- сертификат отдельный не нужен: Caddy получает один на имя и отдаёт его на обоих портах (проверка владения именем идёт через порты 80 и 443);
- если перед сервером стоит Cloudflare в режиме прокси, HTTPS на порту 8443 он пропускает (документация Cloudflare «Network ports», сверено 2026-10-07). Cloudflare Access и подобные сервисы единого входа номер порта из адреса убирают: если нужен единый вход перед страницей настройки — странице дают отдельное имя.

Вариант с отдельным именем (`https://setup.example.com` на обычном порту) допустим: нужна запись DNS, а заголовок второго блока в образце прокси меняется на это имя. По умолчанию он не предлагается: владелец счёл отдельное имя слишком сложным (Р-56).

Прокси не должен подменять заголовок `Host` ни в одном блоке: Hermes сверяет с адресом дашборда и `Host`, и `Origin`, и при подмене отказывает в соединении чату дашборда; сервис переписки сверяет `Host` с адресом страницы настройки — именем вместе с портом — и на любой другой отвечает отказом. Журнал запросов в образце не включён.

Перед адресом дашборда можно поставить ещё и сервис единого входа с портом 443, открытым только для его адресов: входу «Штурмана» это не мешает. Пока адрес дашборда не задан, дашборд доступен только с самого сервера и входа не требует.

### Проверка маршрутизации образца прокси

Проверено 2026-10-07 настоящим Caddy 2.10.2 с настройкой из `config/Caddyfile.example` (имя и порты заменены на стендовые, сертификат — внутренний, на обоих портах один и тот же) и двумя подставными сервисами на местах Hermes и сервиса переписки. «Прокси» в столбцах значит: ответил сам прокси, до сервисов запрос не дошёл.

| Путь запроса | По адресу дашборда | По адресу страницы настройки |
|---|---|---|
| `/` | Hermes | прокси: перенаправление на `/shturman-setup/` |
| `/shturman-setup` | прокси: 404 | прокси: перенаправление на `/shturman-setup/` |
| `/shturman-setup/`, `/shturman-setup/static/setup.js`, `/shturman-setup/api/session`, запросы с параметрами после `?` | прокси: 404 | **сервис переписки**, путь как есть |
| `/SHTURMAN-SETUP/`, `/%73hturman-setup/`, `//shturman-setup/`, `/x/../shturman-setup/`, `/x/%2e%2e/shturman-setup/`, `/api/../shturman-setup/` | прокси: 404 | прокси: 404 |
| `/shturman-setup/../api/status`, `/shturman-setup/%2e%2e/api/status`, `/shturman-setup/..%2fapi/status`, `/shturman-setup/%2e%2e%2fmcp`, `/shturman-setup/x/../../mcp` | Hermes (после разбора пути это его `/api/status` и `/mcp`; до сервиса переписки не доходит) | прокси: 404 |
| `/shturman-setup//api/status`, `/shturman-setup/..;/api/status`, `/shturman-setup/%5c..%5capi/status`, `/shturman-setup/.hidden`, `/shturman-setup/a%00b` | прокси: 404 | прокси: 404 |
| `/api/status`, `/mcp`, `/health`, `/auth/callback`, `/sessions` | Hermes | прокси: 404 |
| `/shturman-auth/login.html` | прокси: статический файл | прокси: 404 |

До порта сервиса переписки по адресу дашборда не дошёл ни один запрос; по адресу страницы настройки — только простые пути под `/shturman-setup/`. Заголовок `Host` до сервиса доходит с портом. Запрос с чужим именем узла не проходит дальше установления соединения: сертификата для него нет. Тело запроса в 300 МБ прошло к сервису потоком, память прокси при этом не выросла; тело больше заданного предела с заголовком длины прокси отклоняет кодом 413. Предел на тело, переданное без заголовка длины, не проверен: подставной сервис такое тело не читает.

## Каталоги данных

Все данные лежат в каталоге `data/` рядом с клоном репозитория.

| Каталог | Что в нём | Кто читает |
|---|---|---|
| `data/hermes` | Настройки, ключи и состояние Hermes; состояние плагина — `data/hermes/plugin-data/shturman` | Hermes |
| `data/shturman/sessions` | Файлы сессий Telegram: `owner.session`, `assistant.session`. Это полный доступ к аккаунту | Сервис |
| `data/shturman/pages` | Страницы памяти о людях (Markdown) и их история в git | Сервис |
| `data/shturman/setup` | Значения, введённые на странице настройки переписки (`secrets.json`, права 600), и ключ подписи кодов входа | Сервис |
| `data/shturman/uploads` | Выгрузка, загруженная на странице настройки переписки; временные файлы, удаляются сами | Сервис |
| `data/postgres` | База архива | Postgres |
| `data/embeddings/model`, `data/embeddings/user2-small` | Файлы моделей эмбеддингов: первой — `e5-small` (каталог назван так с тех пор, когда модель была одна), второй — `user2-small`. Скачивает `./ops/embeddings.sh`; при смене модели файлы прежней остаются | Контейнер эмбеддингов, только чтение |
| `data/guard/model` | Файлы модели-классификатора защиты | Контейнер защиты, только чтение |

ИИ-агент оператора каталоги `data/` не читает (`AGENTS.md`).

## Что делает `ops/up.sh`

Повторный запуск безопасен. В режиме без Hermes выполняются шаги 1–5, затем сразу `./ops/doctor.sh`; про шаги 6–9 скрипт пишет «пропущено: режим без Hermes». Если от прежнего режима остался контейнер Hermes, скрипт останавливает и убирает его; каталог `data/hermes` не трогает. По шагам:

1. Вызывает `./ops/init-env.sh --auto`: служебные значения, появившиеся в новой версии (токены сервиса, режим установки и профили Compose), дописываются в `.env`. Заданные значения не меняются, ничего не печатается. Затем, в режиме с Hermes: если адрес дашборда задан, а строки `SHTURMAN_SETUP_URL` в `.env` ещё нет, дописывает адрес страницы настройки по умолчанию — то же имя, порт 8443 — и говорит об этом одной строкой. Строку, которая уже есть (в том числе пустую после `--clear`), не трогает. Прокси и firewall скрипт не меняет.
2. Создаёт каталоги `data/hermes/plugins/shturman`, `data/shturman`, `data/embeddings/model` от имени того, кто запускает стек; закрывает `data` и `data/shturman` для остальных пользователей.
3. С ключом `--pull` — обновляет образы указанных версий.
4. Проверяет файл Compose, собирает образ сервиса переписки из `service/`, запускает контейнеры. Первая сборка идёт несколько минут и скачивает пакеты из интернета; зависимости ставятся из `service/requirements.lock` — списка с точными версиями и контрольными суммами.
5. Ждёт до 90 секунд ответа сервиса на `http://127.0.0.1:8765/health`. При старте сервис сам приводит схему базы к текущей версии.
6. Включает плагин `shturman` в Hermes, если он не включён.
7. Записывает в настройки Hermes MCP-сервер `shturman` (см. ниже), если записи нет или она отличается от образца.
8. Если шаг 6 или 7 что-то изменил — перезапускает контейнер Hermes.
9. Ждёт до 90 секунд ответа дашборда и запускает `./ops/doctor.sh`. Если проверка прошла — одной строкой напоминает, что дальше настройка переписки и что ссылку входа выдаёт `./ops/setup-link.sh` только по просьбе владельца.

Строки `./ops/doctor.sh` про страницу настройки переписки:

| Строка | Что значит |
|---|---|
| `PASS setup-page` | Страница отвечает на локальном адресе, и отвечает именно сервис: в ответе есть заголовок-метка `X-Shturman-Setup-Page` |
| `WARN setup-page: …сервис прежней версии` | Сервис ещё не обновлён: страницы или метки у него нет |
| `PASS setup-origin` | У страницы свой адрес, не совпадающий с адресом дашборда |
| `FAIL setup-origin` | Адрес страницы совпал с адресом дашборда — страница отключена: `./ops/set-setup-url.sh` |
| `WARN setup-origin` | Адрес не задан (страница только через туннель) либо записан в `.env`, а сервис ещё не перезапущен |
| `PASS setup-page-public` | По своему адресу страницу отдаёт сервис: код 200 и метка |
| `WARN setup-page-public` | По своему адресу страница не открывается; причина названа простыми словами: порт закрыт, у прокси нет блока, нет сертификата, перед адресом внешняя защита |
| `PASS setup-isolation` | По адресу дашборда путь `/shturman-setup/` страницу сервиса не отдаёт |
| `FAIL setup-isolation` | По адресу дашборда отдаётся страница настройки — так было в прежней схеме прокси: блок дашборда нужно поправить |
| `PASS setup-state` / `WARN setup-state` | Что настроено: ключи приложения Telegram, сколько аккаунтов, сколько сообщений в архиве |

По внешним адресам проверка делает по одному запросу к самой странице и смотрит только на код ответа и метку; на адреса её API не ходит. Строки про бота согласований (`approvals-*`, `plugin-own-bot`) в режиме с Hermes появляются, только когда он настроен.

## Как архив подключён к Hermes

`ops/up.sh` записывает в настройки Hermes запись `mcp_servers.shturman`:

| Поле | Значение |
|---|---|
| Адрес | `http://127.0.0.1:8765/mcp` |
| Токен | Заголовок `Authorization: Bearer ${MCP_SHTURMAN_API_KEY}` — в настройках лежит имя переменной, а не значение. Саму переменную контейнеру Hermes передаёт `compose.yaml` из `SHTURMAN_MCP_TOKEN` |
| Инструменты | Явный перечень из девяти инструментов чтения (`docs/service.md`); ресурсы и промпты выключены |

Плагин `shturman` получает свой адрес и токен отдельно: `SHTURMAN_SERVICE_URL` и `SHTURMAN_API_TOKEN`.

Запись сравнивается с образцом в том виде, в каком она лежит в файле настроек. Hermes отдаёт настройки с уже подставленными переменными окружения, и до версии 0.0.4 сравнение не сходилось никогда: `ops/up.sh` переписывал запись и перезапускал Hermes при каждом запуске. Исправление проверено на коде настроек Hermes 0.21.5 вне Docker; в контейнере — нет.

## Резервные копии

`./ops/backup.sh` складывает в `local/backups` (вне git, доступ только владельцу):

| Файл | Что в нём | Что не входит |
|---|---|---|
| `data-<время>.tar.gz` | Архив каталога `data/` (настройки и ключи Hermes, сессии Telegram, страницы памяти) и файл `.env` (режим установки, служебные токены, значения, введённые владельцем в терминале: токен бота согласований, ключ модели сервиса, ключи приложения Telegram) | Журналы Hermes, файлы базы, модели эмбеддингов и защиты, загруженные экспорты |
| `db-<время>.dump` | Выгрузка базы архива средствами Postgres (`pg_dump`) | — |

Базу копирует именно выгрузка, а не архив файлов: она согласованная, в отличие от копии файлов на ходу. Скрипт проверяет, что архив не пустой, а выгрузка читается и содержит таблицу сообщений. Хранятся пять последних копий каждого вида. `./ops/backup.sh --list` показывает имеющиеся копии.

В копии ключи, сессии и вся переписка владельца. Агент её не открывает и никуда не передаёт. Восстановление поверх данных — стоп-точка; отдельной процедуры и скрипта для него пока нет.

## Вариант «пристройка»: Hermes уже есть

Если у владельца Hermes уже работает — в образе или прямо в системе, — Compose поднимает только сервис и базу, а расширения ставятся в существующий Hermes. Интерфейс между частями тот же: внутренний API и MCP на локальном адресе. Вариант не проверялся.

Если Hermes установлен в систему и его пользователь имеет права администратора, инъекция через входящее сообщение может дотянуться до сессии Telegram. Это выбор владельца; безопасные настройки описываются, но не навязываются.

| 0. Хост | Docker, файрвол, SSH по ключу, обновления безопасности, клон репозитория | Один раз при подготовке |

| 2а. Секреты и личные настройки | Ключ модели, токен бота-ассистента — в мастере; ключи приложения Telegram, вход в аккаунт, выбор чатов — на странице настройки переписки; позже, по желанию, — бот согласований и ключ модели сервиса | Владелец — `docs/setup.md` |

## Обновления

- **Обновление «Штурмана»** — по `UPGRADING.md`: копия, `git pull`, `./ops/up.sh`. Скрипта обновления одной командой пока нет.
- **Hermes обновляется штатно** — новой версией официального образа (`HERMES_VERSION` в `.env`). Мы этого не запрещаем.
- **Совместимость — совет, а не замок.** Расширения проверены с Hermes 0.21.5 (образ `v2026.9.24`); это единственная проверенная версия. Перед сменой версии оператор говорит владельцу, что целевая не проверена.
- **После каждого старта** `ops/doctor.sh` проверяет страницу настройки переписки (строки `setup-*`) и сообщает, подключён ли бот-ассистент в бизнес-режиме (строка `business-hermes` — только на экземпляре прежней схемы). От сообщений собеседников ядро Hermes в любом случае закрывает плагин `shturman`.
- **Версии названы явно**: образы — по версии, зависимости сервиса — по списку с контрольными суммами, модели эмбеддингов и защиты — по ревизии и контрольным суммам.

## Что остаётся за сервисом, а не за плагинами

Отправку решает сервис переписки, а не плагин и не модель: главный выключатель и суточный потолок он читает из своего окружения, правила проверяет сам, отправляет только согласованную строку черновика. Без своего бота нажатие владельца сервис получает через плагин, а токен плагина доступен агенту — такое нажатие агент может подделать, поэтому без своего бота отправка не включается вовсе. Свой бот согласований даёт способ подтверждения мимо Hermes; он написан, но с настоящим ботом не проверен, и отправка по-прежнему выключена. Что свой бот закрывает и что остаётся — `docs/architecture.md`, «Открытое ограничение».

## Проверено и не проверено

Проверено по документации Hermes на 2026-10-06: виды плагинов и хуков, установка плагинов из подкаталога репозитория с закреплением по коммиту, MCP-клиент, плагины дашборда, официальный образ с томом данных.

Проверено на стенде разработки 2026-10-07 для версии 0.0.6, без Docker (демона Docker на этом стенде не было): образец прокси настоящим Caddy 2.10.2 — `caddy validate` и таблица маршрутизации выше; `ops/set-public-url.sh`, `ops/set-setup-url.sh`, `ops/setup-link.sh`, `ops/doctor.sh` и `ops/preflight.sh` — в песочнице с подставными `docker` и `curl`, где адреса экземпляра вели на тот же Caddy: все строки `setup-*` в положениях «всё в порядке», «адрес совпал», «адрес не задан», «сервис не перезапущен», «сервис прежней сборки», «порт закрыт», «нет сертификата», «прокси прежней схемы»; `docker compose config` с новыми переменными; шаги CI для скриптов и образца прокси. Сервис переписки в этих проверках подставной.

**Не проверено** — первый запуск на эталонном сервере и есть проверка:

1. Сборка образа из неизменённого `service/Dockerfile` на сервере. Образ собирает CI; на стенде он собирался в изменённом виде.
2. Сети Compose: что сервис видит Telegram и провайдера модели, а база и эмбеддинги не видят интернет. Что сервис видит базу, проверено на стенде.
3. `ops/up.sh`, `ops/doctor.sh`, `ops/backup.sh` на эталонном сервере: на стенде они пройдены, сборка образа внутри `ops/up.sh` — нет.
4. Контейнер эмбеддингов на эталонном сервере: на стенде он читает заранее скачанную модель из каталога, подключённого только для чтения; время пересчёта векторов на архиве настоящего размера не измерялось.
5. Хватает ли 4 ГБ памяти на Hermes, сервис, базу, эмбеддинги и защиту вместе.
6. Плагины, установленные в том официального образа, переживают его обновление.
7. Экземпляр прежней схемы: официальный плагин бизнес-режима уживается с обработчиками плагина `shturman` на живом боте. Новые экземпляры этот плагин не ставят.
8. Полный путь `./ops/guard.sh on` → `./ops/up.sh` → `./ops/doctor.sh`; строки `guard` и `plugin-own-bot` в `ops/doctor.sh` под Docker не исполнялись.
9. Свой бот согласований с настоящим Telegram, в том числе рядом с Hermes.
10. Страница настройки переписки за настоящим прокси: второй блок сайта на порту 8443 с настоящим сертификатом, открытие порта в firewall, работа за Cloudflare. Что Caddy получает один сертификат на имя и отдаёт его на обоих портах, проверено только с внутренним сертификатом стенда.
11. `ops/up.sh` с настоящим Docker после этих правок: дописывание адреса по умолчанию проверено в песочнице и шагом CI, сам запуск стека версии 0.0.6 — нет. Шаг CI, который проверяет образец прокси образом `caddy:2.10.2`, локально не запускался (на стенде проверка шла тем же Caddy без Docker).
12. `ops/doctor.sh` против настоящего сервиса версии 0.0.6: строки `setup-*` проверены с подставным сервисом, который ставит метку так, как договорено.

Наблюдение стенда: запуск стека от root не работает — `hermes plugins enable` падает с ошибкой прав при `HERMES_UID=0`. Стек запускает обычный пользователь с правом на Docker.
