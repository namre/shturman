# Развёртывание: как устроен экземпляр на сервере

Состояние на версию 0.0.3: Hermes с плагином `shturman` поднимался на живом сервере; сервис переписки и его база под Docker запускались **только на стенде разработки** (2026-10-07), контейнер эмбеддингов — не запускался. Что проверено, а что нет, сказано в конце.

## Два режима установки

Режим записан в `.env` строкой `SHTURMAN_MODE` и выбирается при первой установке: `./ops/init-env.sh --mode hermes|standalone`. Показать и сменить — `./ops/mode.sh`.

| Режим | Что запускается | Документ |
|---|---|---|
| `hermes` — по умолчанию | Hermes, сервис переписки, база | Этот документ, `docs/runbooks/deploy.md` |
| `standalone` — «только архив и согласования» | Сервис переписки и база; у сервиса свой бот согласований и свой доступ к модели | `docs/standalone.md`, `docs/runbooks/deploy-standalone.md` |

Устроено это профилями Compose: контейнер Hermes описан с профилем `hermes`, эмбеддинги — с профилем `embeddings`. Скрипты `ops/` сами выставляют профили по режиму и ведут строку `COMPOSE_PROFILES` в `.env`. Экземпляр, развёрнутый до появления режимов, строки режима не имеет: первый же `./ops/up.sh` записывает ему `SHTURMAN_MODE=hermes` и профиль `hermes`, сохраняя включённый поиск по смыслу. Голая команда `docker compose up` без профилей Hermes не запустит — стек поднимается только через `./ops/up.sh`.

Всё ниже описывает режим с Hermes.

## Принцип

**Hermes — стоковый.** Он ставится и обновляется своим штатным способом, его образ и код мы не меняем и возможности не урезаем. «Штурман» — это набор расширений к нему и один сервис рядом. Весь интеллект живёт в Hermes; сервис отвечает только за данные и сессии Telegram.

## Что чем сделано

| Что нужно | Чем делаем | Механизм Hermes |
|---|---|---|
| Вход владельца в дашборд | Плагин `shturman`: ссылка активации и код от собственного бота | Свой способ входа (`register_dashboard_auth_provider`) |
| Привязка владельца к боту, защита от сообщений бизнес-режима | Плагин `shturman` | Обработчики Telegram (`register_telegram_handler`) |
| Мастер первой настройки | Плагин `shturman`: вкладка «Штурман» | Вкладка и маршруты в дашборде Hermes |
| Бизнес-режим Telegram | Официальный плагин `hermes-telegram-business`, закреплённый по SHA; ставится из мастера | Обработчик обновлений Telegram |
| Запись бизнес-сообщений в архив, кнопки согласования | Плагин `shturman`: пересылка в сервис переписки | Обработчики Telegram, отдельная группа раньше остальных |
| Поиск по переписке, обязательства, страницы о людях — для агента | MCP-сервер сервиса переписки, только чтение | Штатный MCP-клиент |
| Черновик сообщения, правка обязательств и людей — для агента | Плагин `shturman`: четыре инструмента поверх внутреннего API сервиса | `register_tool` |
| Обращения сервиса к модели | Плагин `shturman`: исполнитель заданий | Доступ плагина к модели (`ctx.llm`), вспомогательные задачи (`register_auxiliary_task`) |
| Утренняя сводка, обзор недели | Два скилла плагина и задачи по расписанию | `register_skill`, cron Hermes |
| Имя и характер | Блок в файле личности | `SOUL.md` |
| Сессии аккаунтов, архив, импорт, индексация, обработка, шлюз отправки | **Сервис переписки** — единственное, что вне Hermes | Для агента это обычный MCP-сервер; для плагина — внутренний API |
| Экраны кабинета: переписка, память, согласования | **Не сделаны.** Проход дашборда к сервису есть (`/api/plugins/shturman/service/...`), страниц нет | Вкладка и маршруты в дашборде Hermes |
| Гейт отправки хуком Hermes (`pre_tool_call`), подготовка ко встрече | Запланированы | — |

Почему сервис нельзя сделать плагином: плагины исполняются в процессе агента, а сессия пользовательского аккаунта — это полный доступ к аккаунту. Она должна лежать там, куда агент и его инструменты не дотягиваются.

Следствие: **модель одна — та, что настроена в Hermes.** Сервису переписки ключ модели не нужен: он ставит задание, плагин спрашивает модель (`docs/service.md`).

## Эталонный вариант: один файл Compose

| Контейнер | Что это | Сеть | Данные |
|---|---|---|---|
| `shturman-hermes` | Официальный образ `nousresearch/hermes-agent` без изменений. Плагин `shturman` подключён из репозитория только для чтения | Сеть хоста — как в официальном compose Hermes | `data/hermes` |
| `shturman-service` | Сервис переписки. Образ собирается на сервере из каталога `service/` | `backend` и `egress`; порт 8765 опубликован только на `127.0.0.1` | `data/shturman` |
| `shturman-postgres` | Postgres 16 с pgvector (`pgvector/pgvector:0.8.7-pg16-bookworm`) | Только `backend`; порт не публикуется | `data/postgres` |
| `shturman-embeddings` | Сервер эмбеддингов TEI 1.9.4 с моделью `intfloat/multilingual-e5-small`. Отдельный профиль Compose, по умолчанию выключен | Только `backend` | `data/embeddings`, только чтение |

Сети:

| Сеть | Что это | Кто в ней |
|---|---|---|
| `backend` | Закрытая: контейнеры видят друг друга, но не интернет | База, эмбеддинги, сервис |
| `egress` | Обычная, с выходом в интернет | Только сервис: ему нужен Telegram для сессий аккаунтов |

У базы и у контейнера эмбеддингов выхода в интернет нет вовсе. Через контейнер эмбеддингов проходит текст всех сообщений, поэтому модель скачивается заранее, на хосте, скриптом `./ops/embeddings.sh` с проверкой контрольных сумм.

Сервис переписки работает под владельцем каталога данных, без дополнительных прав (`cap_drop: ALL`, `no-new-privileges`). Hermes обращается к нему по адресу `127.0.0.1:8765`: он сам работает в сети хоста.

Наружу открыты две вещи, обе через прокси на хосте: дашборд Hermes, который сам требует входа, и статические страницы входа «Штурмана» (`/shturman-auth/`, данных в них нет). Образец настройки прокси — `config/Caddyfile.example`. Порт сервиса переписки и порт базы наружу не открываются; `./ops/doctor.sh` это проверяет. Перед прокси можно поставить ещё и сервис единого входа с портом 443, открытым только для его адресов: входу «Штурмана» это не мешает.

Внешний адрес задаётся один раз командой `ops/set-public-url.sh` и передаётся Hermes как `HERMES_DASHBOARD_PUBLIC_URL`. Прокси не должен подменять заголовок `Host`: Hermes сверяет с этим адресом и `Host`, и `Origin`, и при подмене отказывает в соединении чату дашборда. Пока адрес не задан, дашборд доступен только с самого сервера и входа не требует.

Hermes в официальном образе остаётся стоковым, а его терминал ограничен контейнером — без каких-либо наших правок. Доступ к Docker контейнеру `hermes` не даётся. Каталог `data/shturman` ему не подключён.

## Каталоги данных

Все данные лежат в каталоге `data/` рядом с клоном репозитория.

| Каталог | Что в нём | Кто читает |
|---|---|---|
| `data/hermes` | Настройки, ключи и состояние Hermes; состояние плагина — `data/hermes/plugin-data/shturman` | Hermes |
| `data/shturman/sessions` | Файлы сессий Telegram: `owner.session`, `assistant.session`. Это полный доступ к аккаунту | Сервис |
| `data/shturman/pages` | Страницы памяти о людях (Markdown) и их история в git | Сервис |
| `data/shturman/uploads` | Экспорт, загруженный через дашборд; временные файлы, удаляются сами | Сервис |
| `data/postgres` | База архива | Postgres |
| `data/embeddings/model` | Файлы модели эмбеддингов | Контейнер эмбеддингов, только чтение |

ИИ-агент оператора каталоги `data/` не читает (`AGENTS.md`).

## Что делает `ops/up.sh`

Повторный запуск безопасен. В режиме без Hermes выполняются шаги 1–5, затем сразу `./ops/doctor.sh`; про шаги 6–9 скрипт пишет «пропущено: режим без Hermes». Если от прежнего режима остался контейнер Hermes, скрипт останавливает и убирает его; каталог `data/hermes` не трогает. По шагам:

1. Вызывает `./ops/init-env.sh --auto`: служебные значения, появившиеся в новой версии (токены сервиса, режим установки и профили Compose), дописываются в `.env`. Заданные значения не меняются, ничего не печатается.
2. Создаёт каталоги `data/hermes/plugins/shturman`, `data/shturman`, `data/embeddings/model` от имени того, кто запускает стек; закрывает `data` и `data/shturman` для остальных пользователей.
3. С ключом `--pull` — обновляет образы указанных версий.
4. Проверяет файл Compose, собирает образ сервиса переписки из `service/`, запускает контейнеры. Первая сборка идёт несколько минут и скачивает пакеты из интернета; зависимости ставятся из `service/requirements.lock` — списка с точными версиями и контрольными суммами.
5. Ждёт до 90 секунд ответа сервиса на `http://127.0.0.1:8765/health`. При старте сервис сам приводит схему базы к текущей версии.
6. Включает плагин `shturman` в Hermes, если он не включён.
7. Записывает в настройки Hermes MCP-сервер `shturman` (см. ниже).
8. Если шаг 6 или 7 что-то изменил — перезапускает контейнер Hermes.
9. Ждёт до 90 секунд ответа дашборда и запускает `./ops/doctor.sh`.

## Как архив подключён к Hermes

`ops/up.sh` записывает в настройки Hermes запись `mcp_servers.shturman`:

| Поле | Значение |
|---|---|
| Адрес | `http://127.0.0.1:8765/mcp` |
| Токен | Заголовок `Authorization: Bearer ${MCP_SHTURMAN_API_KEY}` — в настройках лежит имя переменной, а не значение. Саму переменную контейнеру Hermes передаёт `compose.yaml` из `SHTURMAN_MCP_TOKEN` |
| Инструменты | Явный перечень из девяти инструментов чтения (`docs/service.md`); ресурсы и промпты выключены |

Плагин `shturman` получает свой адрес и токен отдельно: `SHTURMAN_SERVICE_URL` и `SHTURMAN_API_TOKEN`.

## Резервные копии

`./ops/backup.sh` складывает в `local/backups` (вне git, доступ только владельцу):

| Файл | Что в нём | Что не входит |
|---|---|---|
| `data-<время>.tar.gz` | Архив каталога `data/` (настройки и ключи Hermes, сессии Telegram, страницы памяти) и файл `.env` (режим установки, служебные токены, значения, введённые владельцем в терминале) | Журналы Hermes, файлы базы, модель эмбеддингов, загруженные экспорты |
| `db-<время>.dump` | Выгрузка базы архива средствами Postgres (`pg_dump`) | — |

Базу копирует именно выгрузка, а не архив файлов: она согласованная, в отличие от копии файлов на ходу. Скрипт проверяет, что архив не пустой, а выгрузка читается и содержит таблицу сообщений. Хранятся пять последних копий каждого вида. `./ops/backup.sh --list` показывает имеющиеся копии.

В копии ключи, сессии и вся переписка владельца. Агент её не открывает и никуда не передаёт. Восстановление поверх данных — стоп-точка; отдельной процедуры и скрипта для него пока нет.

## Вариант «пристройка»: Hermes уже есть

Если у владельца Hermes уже работает — в образе или прямо в системе, — Compose поднимает только сервис и базу, а расширения ставятся в существующий Hermes. Интерфейс между частями тот же: внутренний API и MCP на локальном адресе. Вариант не проверялся.

Если Hermes установлен в систему и его пользователь имеет права администратора, инъекция через входящее сообщение может дотянуться до сессии Telegram. Это выбор владельца; безопасные настройки описываются, но не навязываются.

## Слои

| Слой | Что в нём | Кто меняет |
|---|---|---|
| 0. Хост | Docker, файрвол, SSH по ключу, обновления безопасности, клон репозитория | Один раз при подготовке |
| 1. Стек | Контейнеры из Compose | `ops/up.sh` |
| 2. Расширения | Плагин `shturman`, запись MCP-сервера в настройках Hermes — `ops/up.sh`; плагин бизнес-режима и блок в `SOUL.md` — мастер настройки | Штатными командами и вызовами Hermes |
| 2а. Секреты и личные настройки | Ключ модели, токен бота, вход в аккаунты, правила | Владелец — `docs/setup.md` |
| 3. Обслуживание | Резервные копии, проверка здоровья | Сейчас вручную: `ops/backup.sh`, `ops/doctor.sh`. Таймеры и сторож запланированы |
| 4. ИИ-оператор | Первое развёртывание, обновление версии, разбор поломки | Человек с агентом, по runbook |

Сторож и ИИ-оператор живут на хосте, вне контейнеров: иначе они не смогут ни сообщить, что стек упал, ни починить его.

## Обновления

- **Обновление «Штурмана»** — по `UPGRADING.md`: копия, `git pull`, `./ops/up.sh`. Скрипта обновления одной командой пока нет.
- **Hermes обновляется штатно** — новой версией официального образа (`HERMES_VERSION` в `.env`). Мы этого не запрещаем.
- **Совместимость — совет, а не замок.** Расширения проверены с Hermes 0.21.5 (образ `v2026.9.24`); это единственная проверенная версия. Перед сменой версии оператор говорит владельцу, что целевая не проверена.
- **После каждого старта** `ops/doctor.sh` проверяет, что плагин бизнес-режима установлен и включён. Если нет — Hermes принимает личные чаты владельца за команды (issue NousResearch/hermes-agent #127430), и владелец должен узнать об этом немедленно.
- **Версии названы явно**: образы — по версии, плагин бизнес-режима — по полному SHA, зависимости сервиса — по списку с контрольными суммами, модель эмбеддингов — по ревизии и контрольным суммам.

## Что остаётся за сервисом, а не за плагинами

Отправку решает сервис переписки, а не плагин и не модель: главный выключатель и суточный потолок он читает из своего окружения, правила проверяет сам, отправляет только согласованную строку черновика. Но нажатие владельца сервис получает через плагин, а токен плагина доступен агенту — поэтому способа подтверждения, который агент не может подделать, пока нет. Это открытое ограничение (`docs/architecture.md`), и из-за него отправка выключена.

## Проверено и не проверено

Проверено по документации Hermes на 2026-10-06: виды плагинов и хуков, установка плагинов из подкаталога репозитория с закреплением по коммиту, MCP-клиент, плагины дашборда, официальный образ с томом данных.

Проверено на стенде 2026-10-06 (Hermes 0.21.5 из исходников тега `v2026.9.24` за Caddy 2.10.2): плагин из каталога пользователя регистрирует способ входа до проверки «есть ли вход» при старте дашборда; дашборд с заданным внешним адресом без включённого плагина не стартует; маршруты плагина монтируются только при старте дашборда; обработчики плагина подключаются раньше обработчиков ядра и получают сообщения бизнес-режима. Подробности и то, что не проверено на живом боте, — `docs/setup.md`.

Проверено на живом стенде 2026-10-06, до появления сервиса переписки в Compose: `compose.yaml` с официальным образом `v2026.9.24` (Hermes 0.21.5) поднимается одной командой `ops/up.sh`; шлюз работает и без настроенных каналов; данные ложатся в `data/hermes` под владельцем каталога; контейнер занимает около 0,4 ГБ памяти; образ — около 4 ГБ на диске.

Проверено на стенде разработки для версии 0.0.3, без Docker: сервис целиком запущен на Postgres; стоковая команда `hermes mcp test shturman` подключилась к архиву с токеном из окружения и нашла 9 инструментов; настоящий сервер TEI 1.9.4 с настоящей моделью отдаёт векторы. Подробно — `docs/service.md`.

Проверено на стенде разработки 2026-10-07 под Docker 29.8.2 и Compose 5.5.1 (оба режима; образ сервиса собран из того же `Dockerfile` без пакета git и с сертификатом прокси стенда; у контейнеров не было выхода в интернет; бот и модель не настоящие): `ops/up.sh` с официальным образом Hermes `v2026.9.24` включает плагин, записывает MCP-сервер и поднимает дашборд; стоковая команда `hermes mcp test shturman` в контейнере видит инструменты архива; `ops/doctor.sh` даёт `ИТОГ: OK`; `ops/backup.sh` делает архив и читаемую выгрузку базы; экземпляр без строки режима остаётся режимом с Hermes; переход между режимами в обе стороны. Наблюдение: после возврата в режим с Hermes `ops/up.sh` записал MCP-сервер заново и ещё раз перезапустил Hermes, хотя запись в его настройках оставалась; причина не разбиралась.

**Не проверено** — первый запуск на эталонном сервере и есть проверка:

1. Сборка образа из неизменённого `service/Dockerfile` на сервере. Образ собирает CI; на стенде он собирался в изменённом виде.
2. Сети Compose: что сервис видит Telegram и провайдера модели, а база и эмбеддинги не видят интернет. Что сервис видит базу, проверено на стенде.
3. `ops/up.sh`, `ops/doctor.sh`, `ops/backup.sh` на эталонном сервере: на стенде они пройдены, сборка образа внутри `ops/up.sh` — нет.
4. Контейнер эмбеддингов читает заранее скачанную модель из каталога, подключённого только для чтения.
5. Хватает ли 4 ГБ памяти на Hermes, сервис, базу и эмбеддинги вместе.
6. Плагины, установленные в том официального образа, переживают его обновление.
7. Официальный плагин бизнес-режима уживается с обработчиками плагина `shturman` на живом боте.
