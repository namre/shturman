## Два слоя под два объёма

| | Архив | Курируемый слой |
|---|---|---|
| Объём | Сотни тысяч сообщений | Сотни–тысячи страниц |
| Что это | Переписка дословно | Страницы о людях, проектах, решениях; обязательства; профиль и правила владельца |
| Кто пишет | Приём сообщений, без LLM | LLM ночной сборкой + владелец |
| Где лежит | Postgres | Markdown в git + таблицы Postgres |
| Как ищется | Полнотекстовый поиск с русской морфологией + векторный | Тот же индекс Postgres + чтение файлов агентом |

Память самого Hermes (`MEMORY.md`, `USER.md`) используется только под короткий профиль и постоянные правила: она ограничена парой тысяч символов и всегда находится в системном промпте.

## Кто чему хозяин

У каждого вида данных один источник истины, синхронизация только в одну сторону.

| Данные | Источник истины | Производное |
|---|---|---|
| Сообщения | Postgres, неизменяемо | Индексы |
| Люди: идентификаторы, имена, алиасы | Postgres | Шапка страницы человека |
| Обязательства: кто, кому, что, срок, статус | Postgres | Блок на страницах людей и проектов |
| Датированные факты с периодом действия, извлечение произвольных фактов | Сделано: тем же запросом на эпизод, с дословной цитатой; новый факт с тем же ключом закрывает прежний датой. Ключи — закрытый перечень (должность, компания, телефон, почта, адрес, город, цена, бюджет, срок, статус, площадь, подрядчик, ответственный) |
| Проза: кто этот человек, контекст проекта, как принято общаться | Markdown-файл | Индекс в Postgres |
| Заметки владельца | Markdown-файл, блок владельца | Индекс в Postgres |

Обязательство меняется командой («закрой», «перенеси срок»), а не правкой таблицы в тексте страницы: блок с таблицей перерисовывается из базы при каждой сборке.

## Страница

```markdown
---
entity_id: person:123456789
type: person
aliases: [Иван Петров, Петров, Ваня]
updated: 2026-10-06
---
# Иван Петров

<!-- summary: пересобирается ассистентом из хронологии и таблиц -->
Руководитель подрядчика по фасадам. Отвечает медленно, сроки называет с запасом…

<!-- owner: ассистент этот блок не трогает -->
Не писать ему после 19:00.

<!-- commitments: перерисовывается из базы -->
| Что | Срок | Статус | Источник |
|---|---|---|---|
| Прислать смету | 2026-10-10 | ждём | [сообщение](msg:…) |

<!-- facts: перерисовывается из базы -->
- должность: руководитель отдела фасадов в «Альфе» (с 2026-10-01) [сообщение](msg:…) (сказал собеседник)

<!-- timeline: только дописывается -->
- 2026-09-12 — согласовали перенос монтажа на октябрь [сообщение](msg:…)
```

Между таблицей обязательств и хронологией — необязательные блоки `decisions` (только у проекта) и `facts`, в этом порядке; страницы версии 0.0.7 их не имеют и читаются как раньше, блок `facts` у человека появляется при первой сборке. Блок владельца — по-прежнему всё между меткой `owner` и последней меткой `commitments`, байт в байт.

Страница проекта — `projects/<название>-<id>.md`, `entity_id: project:<id>`, `type: project`; в шапке ещё два списка, оба пишет код: `chats` (чаты проекта, исключённые не показываются) и `participants` (люди с сообщениями в этих чатах). Блоки: сводка, блок владельца, обязательства проекта, решения по датам, действующие факты (цена, бюджет, срок, статус…), хронология. Сводку модель собирает по тем же правилам, что у людей; входы — решения, факты, обязательства, хронология и последние 40 видимых сообщений чатов проекта за 90 дней.

Профиль владельца — `owner/profile.md`, `entity_id: owner:profile`, `type: owner`. Сводки модели в нём нет; обязательства не ведутся. Блок `facts` — только одобренные владельцем факты о нём, хронология — они же; блок владельца — его правила и постоянные указания ассистенту. Ассистент читает профиль как слова владельца, без рамки «чужой текст».

Четыре правила формата:

1. **Сводку ассистент переписывает, хронологию только дописывает.** Сводка собирается из хронологии и таблиц, а не из прежней сводки — так ошибка не закрепляется.
2. **Блок владельца неприкосновенен.**
3. **У каждого утверждения — ссылка на сообщение** и пометка происхождения: сказал владелец, сказал собеседник, вывела модель.
4. **Противоречие помечается, а не разрешается.** Старое утверждение получает дату окончания действия и остаётся в хронологии. Числовая «уверенность» не используется.

## Расписание прогонов

С Р-96 (не выпущено) обработка идёт не только ночью:

- **Днём — раз в `SHTURMAN_PROCESSING_EVERY` минут (по умолчанию 60) вне тихих часов уведомлений** (по поясу `SHTURMAN_TIMEZONE`; тихие часы — те же, что у уведомлений владельцу, по умолчанию 23:00–08:00). Берутся только новые сообщения после отметки и только **закрытые** эпизоды — после последнего сообщения прошло не меньше 45 минут (`EPISODE_GAP`); открытый разговор ждёт следующего прогона, отметка встаёт перед его первым сообщением. Там же — проверка «не сделано ли уже» и отложенная проверка быстрых обещаний. Поздно появившийся текст (расшифровка голосовых, разбор вложений) днём не разбирается — это делает ночной прогон.
- **Ночью в 03:30 — как раньше**, догоняет всё: то, что днём не поместилось в предел, поздний текст вложений и голосовых. Уже поставленное днём ночной прогон не повторяет: сообщения, по которым запрос на извлечение уже ставился, из окна вынимаются (`_already_planned`).
- **Пределы дневных прогонов**: не больше `SHTURMAN_PROCESSING_HOURLY_CAP` запросов к модели за час (по умолчанию 40) и `SHTURMAN_PROCESSING_DAILY_CAP` за сутки владельца (по умолчанию 300). Упёрлись — прогон откладывается (`capped` в итогах, `WARN processing` в `./ops/doctor.sh`), отметка не двигается, остаток разберёт ночной прогон; днём ничего не пропускается (эпизоды «только с фактом» не отбрасываются, как ночью при упоре в предел, а ждут). Ночной прогон ограничен, как прежде, 200 запросами на извлечение за прогон и 12 прогонами за ночь. В итогах каждого прогона — грубая оценка объёма запросов в токенах (`tokens_in_estimate`, по 3 знака на токен), в `./ops/doctor.sh` — сумма за сутки (строка `processing`).
- **Владельцу не спамить.** Новые предложения сразу видны в приложении «Штурман» («Согласования», «Договорённости»). Сводка с кнопками в бот уходит **не чаще часов сводки** `SHTURMAN_DIGEST_AT` (по умолчанию 13:00 и 19:00), плюс утренняя сводка ассистента; ночью и в тихие часы — ничего; пропущенная из-за простоя — в пределах трёх часов, две пропущенные — одним сообщением. Так же — предложения проектов и фактов профиля. Сразу после прогона сводку шлёт только прогон, запущенный вручную.

## Ночная сборка

1. Взять сообщения, пришедшие после прошлой сборки.
2. Нарезать на эпизоды; из эпизодов активных чатов извлечь кандидатов — факты, обязательства, решения — с идентификаторами сообщений.
3. Сопоставить людей с реестром; при вероятном совпадении новую запись не создавать.
4. Записать обязательства и факты в базу; дописать хронологию страниц.
5. Пересобрать сводку только затронутых страниц.
6. Перерисовать блоки из базы.
7. Проверки: страницы без ссылок на источники, битые ссылки, дубли по алиасам, слишком длинные страницы, страницы-сироты.
8. Коммит в git.
9. Переиндексировать изменённые страницы.
10. Отправить владельцу сводку изменений; рискованные правки — кнопками на одобрение.

Через одобрение идут новые обязательства, новые страницы для людей, которых владелец ещё не подтвердил, предложенные моделью проекты и любые факты о самом владельце; слияние людей — тоже только по решению владельца. Ниже — правило целиком, как задумано.

Автоматически проходят только дописывание датированных фактов и решений в уже существующие страницы (человек, которого владелец подтвердил; заведённый проект). Через одобрение владельца идут: создание и слияние страниц, смена роли человека, новые обязательства, любые правки профиля и правил.

Кто может что сказать — решает код по автору сообщения, а не модель:

- **Сменяемый факт о человеке** (должность, компания, телефон…) сменяет прежний, только если его сказал сам этот человек или владелец. Со слов третьего лица контактные данные — телефон, почта, адрес, реквизиты — не пишутся вовсе (иначе любой участник группы мог бы «поменять» человеку номер или счёт); остальное пишется как факт без ключа: ничего не сменяет, а в строке на странице видно, кто это сказал («сказал собеседник: Мария Сидорова»). У проекта говорят разные участники — имя сказавшего видно всегда.
- **Факт о владельце** берётся только из его собственных сообщений и попадает в профиль только с его «да»; на карточке и во вкладке «Согласования» указано «сказали вы».
- **Пароли, коды (в том числе от домофона, двери, сейфа), PIN и номера карт** не становятся фактами ни при каком ключе.

Если факт, сменивший прежний, исчез (стёрто сообщение, отмечен неверным), прежний снова действует, а строка «больше не действует» о нём убирается из хронологии; при новой смене она дописывается заново с новой датой.

Пределы правки через внутренний API (ассистент, карточка в боте): блок владельца — не длиннее 1800 знаков, ровно в том виде, в каком он показан на карточке целиком; длиннее — только на странице настройки, экран «Память» (до 20 000 знаков). Описание нового проекта — до 300 знаков, на карточке видны все его другие названия; другое название, занятое иным проектом, не принимается. Изменение чатов проекта хранится разницей («добавить … убрать …») и применяется к перечню на момент нажатия.

Срок в обязательстве модель копирует дословно («к среде»), а дату вычисляет код от времени сообщения. Оговорки вроде «постараюсь» обязательствами не считаются.

## Договорённости: что предлагается владельцу (Р-96)

Разбор первых двух прогонов пилота (219 договорённостей, модель gpt-6.1-sol, 30 дней истории; разбирал владелец вместе с разработчиком, данные в репозиторий не переносились) показал: 68% предложенного было старше недели на момент показа, у 82% в том же чате после обещания было не меньше 20 сообщений — и часто там прямо видно выполнение; 28% — быстрые обещания («сейчас гляну», «ща скину»), 27% — обещания между другими людьми, 9% — голое согласие («Ок», «Принял»), у которого «что обещано» додумывалось; 38% сроков не разбирались (из них 53 — «сейчас»). Отсюда правила версии 4 инструкции модели (`PROMPT_VERSION = "4"`):

- **Состояние на момент показа.** К эпизоду добавляется блок «После» — сообщения того же чата после эпизода до момента разбора: не больше 40 сообщений и 7 дней, только видимые ассистенту (скрытое защитой, удалённое, служебное и сообщения ботов не идут). Модель для каждого обещания говорит `open` / `fulfilled` / `cancelled` / `rescheduled` с номером сообщения-основания и дословной цитатой; код принимает это, только если основание — сообщение **позже** обещания, годное как источник, и цитата в нём есть (иначе — `open`, счётчик `dropped_ungrounded_status`). Сделанное или отменённое до показа владельцу **не предлагается**: записывается тихо — статус `expired`, причина `quiet_reason` (`done_before_shown`, `cancelled_before_shown`), событие `quiet_closed` с номером сообщения-основания в журнале, счётчик в итогах прогона. Перенос срока сразу становится новым сроком из сообщения-основания.
- **Проверка закрытия** идёт и по ещё не принятому (`proposed`), и по принятому (`open`); «В команде» отдельно не проверяется (только для сведения, а групповые чаты тратили бы запросы каждый час). Первая проверка — с момента обещания (не только новые сообщения прогона), дальше — с отметки `checked_until_*`. Принятое меняется **только нажатием владельца**: модель предлагает «похоже, выполнено» с цитатой (`commitment_changes`, как раньше). Ещё не принятое, сделанное до решения владельца, тихо снимается с показа (`done_before_decision`); пункт уже ушедшей сводки отвечает «Уже решено», а итог сводки — «— уже сделано».
- **Быстрые обещания** («сейчас», «ща», «сразу», «через N минут», «через N часов» не дальше 3 часов, «в течение часа») — срок сегодня, `due_reason = immediate`. Показ откладывается на сутки после обещания (`hold_until`); за это время проверка закрытия тихо снимает сделанное; не сделанное приходит строкой «Быстрое обещание («сейчас») · обещано 14.10 — похоже, так и не сделано». Обещание старше суток на момент разбора (первый прогон по истории) показывается сразу, если блок «После» не показал выполнения.
- **«В команде».** Обещания между другими людьми (`direction = others`) — новый статус `team`: не в сводке с кнопками, не в «Я обещал / Мне обещали», не в «Ждёт решения»; в приложении — третий список «В команде» только для сведения, с «Скрыть» (и «Вернуть» сразу после). Через 14 дней после обещания уходят сами (`team_stale`). Не «между другими», если владелец участвует: модель назвала его получателем (теперь и когда он сам в эпизоде не писал), обещание — согласие на его просьбу, ответ (reply) на его сообщение или называет его по имени или @адресу. Уже записанные «между другими» и не решённые владельцем миграция `0039` переводит в `team`.
- **Голое согласие** («Ок», «Принял», «Да, конечно», «Проверю», «Поправим», «Сейчас гляну») принимается, только если модель указала просьбу другого участника **раньше в блоке «Сообщения»** (не в «Ранее»), её цитата дословна, а «что обещано» опирается на неё (общее значимое слово); срок — тоже только из блока «Сообщения». Просьба хранится (`request_message_id`, `request_quote`); удалили или скрыли её — договорённость не видна. Полные сами по себе глаголы («подойду», «перезвоню») голым согласием не считаются.
- **Не обязательства** — инструкция с примерами пилота и правила кода: решение «как будет» («запускать всё же будем на …» — это решение для фактов), толкование («буду воспринимать как …»), процесс без результата («будем мониторить», «будем разбираться», «буду параллельно править»), условное («если …», «пусть сделает заявку, и мы …»). Счётчик `dropped_not_a_promise`.
- **Сроки.** «На конец (рабочего) дня» и «на конец дня рабочего», «конец дня», «к обеду», «вечером», «вечерком», «утром», «поутру», «к концу недели» разбираются; время с поясом («в 08:35 UTC», «к 15:00 по Москве») переводится в пояс владельца; срок-событие («к уикли», «как прилечу», «по готовности», «как закончит», «после созвона», «к ней») — `due_reason = event`, показывается словами («по событию: «к уикли»»), а не «срок не распознан».
- **Дубли в одном разговоре.** Модель отмечает `same_as` — то же дело, что раньше в её ответе; код склеивает и сам: близко по времени (30 минут), одно действие (созвон или встреча; прислать или найти; узнать или сообщить), общий предмет или у одного предмета нет, разные числа — разные дела. Остаётся то, где владелец сторона, иначе — раньше сказанное.
- **Ключи и токены** (`sk-…`, `ghp_…`, `xox…`, `AKIA…`, JWT и токены вида `eyJ…`, токен бота, `Bearer …`, пароль после «пароль:», длинная случайная строка рядом со словами «ключ», «токен», «key», «token», «secret») заменяются на «[ключ скрыт]» в одном месте — при постановке любого запроса к модели (`bridge.request_structured`, `bridge.request_text`): обработка переписки, разбор входящих, черновики, репетиция, разбор вложений, сводки страниц. Это не фильтр утечек: ключ без узнаваемого вида пройдёт.
- **Дата обещания** — «обещано 23.09» — в сводке, в «Согласованиях» и в «Договорённостях».
- **«Не так» с причиной**: «не обещание», «не тот человек», «неверно что», «неверный срок», «дубль», «уже сделано» — в боте кнопками под сводкой сразу после «не так» (по желанию), в приложении — выбор при «Не так». Причина пишется в журнал (`commitment_events.details.reason`) — для будущей оценки качества.

**Перепроверка уже найденного** — `./ops/commitments.sh recheck` (по решению владельца, тратит запросы к модели; сначала `--dry-run` с оценкой): ещё не решённые предложения прежних правил разбираются заново с блоком «После» и заменяются (прежние — `expired`, причина `recheck`), принятые проверяются «не сделано ли уже» с момента обещания — найденное приходит владельцу карточкой «похоже, выполнено». Один раз на версию правил.

**Измерение «было / стало»** — `./ops/commitments.sh stats` (`service/tools/commitments_stats.py`): только числа — по статусам и отдельно по версии правил, снятое без владельца по причинам, причины «Не так», доля причин срока, доля «между другими» и быстрых, часы от обещания до сводки и до записи.

**Честные оговорки.** Числа выше — одна выборка одного владельца (два прогона, одна модель); правила кода проверены тестами на синтетических примерах по мотивам этой выборки, а не на ней самой. Насколько модель верно говорит «сделано» по блоку «После» на настоящей переписке, не измерено: это покажет `stats` после перепроверки и недели работы. Ложное «сделано» до показа скрывает настоящее обещание от владельца без следа в сводке (след — в журнале и в `stats`); поэтому основание и цитату проверяет код, а принятое владельцем так не закрывается никогда.

## Как владелец читает и правит

- **Веб-кабинет** — основной способ: страницы открываются с телефона, блок владельца редактируется, очередь одобрений там же.
- **Фразой в управляющем чате:** «неверно, Петров теперь в другой компании» — ассистент вносит правку отдельным коммитом.
- **Obsidian — по желанию.** Страницы — обычные файлы Markdown, каталог открывается как хранилище Obsidian. Синхронизация с телефоном (Obsidian Sync с серверным клиентом или собственный сервер синхронизации) в базовую поставку не входит: это платная зависимость от стороннего сервиса.

## Удаление

Каждая производная запись хранит идентификаторы сообщений-источников. Удаление сообщения или чата каскадно удаляет выведенные из него факты, решения, обязательства, упоминания проектов и строки хронологии; исключённый чат перестаёт быть чатом проекта, а предложение проекта, выведенное из него, снимается; затронутые сводки пересобираются. Факт, который сменил удалённый, снова действует. Чаты из списка исключений не попадают в архив вообще.

## Проверка качества

Набор из 50–100 вопросов по переписке владельца с известными ответами четырёх типов: факт, время, изменение, отсутствие. Прогоняется после каждого изменения поиска, схемы извлечения или сборки страниц. Опубликованные бенчмарки систем памяти для выбора решений не используются: это почти всегда самооценка вендоров на диалогах, которые на порядки меньше архива переписки.

Этого набора ещё нет. Пока его заменяет синтетический набор для поиска (`service/tests/search/data/`, скрипт `service/tools/search_eval.py`): 165 вопросов к коротким сообщениям и 78 — к длинным текстам, один правильный ответ на вопрос. По нему выбирались модели поиска по смыслу; что он показал и чего по нему сказать нельзя — `docs/search.md`.

## Что рассмотрено и не взято

| Вариант | Почему нет |
|---|---|
| Notion и другие зарубежные облачные сервисы | Нельзя разместить у себя; данные и доступ зависят от сервиса и региона; ограничения API |
| Вики без поиска, только оглавление | Перестаёт работать на 100–200 страницах |
| Двусторонняя синхронизация страниц и базы | Нет данных, что она работает надёжно; у проектов с опытом — одно направление |
| Графовая память на весь архив | Вызов LLM на каждое сообщение: дорого на сотнях тысяч сообщений; решение — только после сравнения на собственном наборе вопросов |
| Извлечение фактов из каждого сообщения при записи | Дорого, факт отрывается от контекста |
| Отдельный поисковый движок для страниц | Гибридный индекс в Postgres уже есть |
| Готовая вики с собственной базой (Outline, AppFlowy, SiYuan, Trilium, Docmost) | Не файлы Markdown и/или лицензии AGPL, BSL |
