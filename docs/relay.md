# Посредник `sh.namre.app`: адрес для тех, у кого нет домена или белого IP

Статус: **реализовано, проверено на стенде; на настоящем посреднике не развёрнуто**, 2026-10-12. Сам посредник работает с 2026-10-12 как прототип (тестовый экземпляр получил сертификат Let's Encrypt через него). Теперь в репозитории есть подключение настоящего экземпляра: служба посредника с ограничением имён и кодами приглашения (`relay/`), `./ops/relay.sh` и контейнер frpc на экземпляре. Всё это проверено на стенде разработки с настоящими frp 0.71.0, Caddy 2.11.7 и тестовым центром сертификации Pebble («Что проверено» ниже); на посреднике в AWS новая служба ещё не поставлена, и настоящий экземпляр через неё не подключался. Решение — Р-69 в `docs/decisions.md`.

**Проверка имени до подключения** (`POST /api/check`, `./ops/relay.sh check`, служба 0.3.0, 2026-10-12) — проверена юнит-тестами и на стенде разработки (ниже, «Проверка имени»); на посреднике в AWS до обновления работает служба 0.2.0, которая проверять имя не умеет — тогда `./ops/relay.sh check` так и говорит, и подключаются сразу `join`. Обновление — `relay/README.md`, «Установка и обновление».

**Бот-менеджер** (служба 0.4.0, 2026-10-13; привязка кодом бота с изменённым адресом — 0.5.0, Р-78; ниже, «Бот-менеджер», и `docs/approvals-bot.md`) — создание бота согласований в одно нажатие для владельцев, которые доверяют держателю посредника. 0.4.0 проверена юнит-тестами, на стенде со службой целиком и подставным Bot API и через настоящий Caddy 2.11.7, первая живая проверка показала, что бот с изменённым в окне создания адресом не узнаётся; 0.5.0 — юнит-тестами и на стенде, на посредник в AWS не ставилась.

## Зачем

Дашборду Hermes и странице настройки переписки нужен адрес с HTTPS. Какой из способов взять, решает владелец по рекомендации агента — сравнение в `docs/address.md`. Варианты, которые уже есть:

- свой домен, направленный на сервер (`docs/runbooks/server-prepare.md`);
- без домена — HTTPS прямо на IP-адресе сервера (Р-67, `docs/deployment.md`, «Без домена»);
- без внешнего адреса — туннель SSH (режим без Hermes, запасной путь страницы настройки).

Посредник — для тех, кому всё это сложно или невозможно: нет своего домена и не хочется разбираться с DNS, или у сервера нет белого адреса (дома, в офисе, за общим NAT хостинга), и снаружи к нему не подключиться вовсе. Ассистент в Telegram и бот согласований посредника не используют: они сами ходят в Telegram исходящими запросами. Через посредника идут только две веб-страницы.

## Как устроено

```
браузер владельца ──https://ivan.sh.namre.app──▶ посредник (relay.sh.namre.app, :443)
                                                      │ читает только имя сайта (SNI)
                                                      ▼
                     сервер владельца ◀── исходящее соединение экземпляра (:7000, TLS)
                     (Caddy снимает TLS, сертификат и ключ — только здесь)
```

- **Имена.** У экземпляра два имени в зоне `sh.namre.app`: одно для дашборда, другое для страницы настройки переписки (например, `ivan.sh.namre.app` и `setup-ivan.sh.namre.app`). Два имени вместо одного имени с портом 8443: так страница настройки остаётся отдельным origin (`docs/setup.md`), а наружу посреднику нужен только порт 443.
- **Посредник** — frps из проекта frp (https://github.com/fatedier/frp, лицензия Apache-2.0, версия 0.71.0 от 2026-08-14). Тип пересылки `https`: посредник читает из первого пакета TLS только имя сайта (SNI, `pkg/util/vhost/https.go`) и передаёт поток экземпляру как есть. Расшифровать его посредник не может: сертификата и ключа у него нет. На порту 80 он так же по имени (заголовок `Host`) передаёт открытые запросы — они нужны только для перенаправления на https и проверки Let's Encrypt `http-01`.
- **Экземпляр** держит постоянное исходящее соединение к `relay.sh.namre.app:7000` (frpc, поверх TLS) и получает через него соединения браузеров. Белый адрес и открытые входящие порты ему не нужны.
- **Сертификат** экземпляр получает сам, обычным Caddy: Let's Encrypt проверяет имя через посредника (`tls-alpn-01` на 443 или `http-01` на 80), а ключ сертификата не покидает сервер владельца.
- **DNS.** Домен `namre.app` обслуживает Cloudflare (только DNS, трафик через Cloudflare не идёт). Поддомен `sh.namre.app` передан записями `NS` в зону Amazon Route 53. В зоне: `relay.sh.namre.app` и `*.sh.namre.app` → адрес посредника; `CAA` — выпуск только Let's Encrypt, сертификаты на `*` запрещены.
- **Размещение.** Amazon Lightsail, Франкфурт, самый маленький тариф (0,5 ГБ памяти, постоянный IPv4). frps работает службой systemd без прав root (`DynamicUser`, только право занимать порты ниже 1024); общий токен frps лежит в файле, читаемом только root.

## Кто какое имя может занять

Общий токен frps один на всех: он только пускает к посреднику и границей доверия не служит. Граница — **ключ экземпляра** и служба посредника `relayd` (`relay/relayd.py`, только стандартная библиотека Python 3.12). frps спрашивает её перед операциями (серверный плагин frp, `doc/server_plugin.md` в frp 0.71.0; формат запросов сверен с `pkg/plugin/server/types.go` и `server/service.go`):

| Операция frps | Что проверяет relayd |
|---|---|
| `Login` — подключение frpc | Имя пользователя frpc (`user`) — экземпляр из базы, не отключённый, и его ключ (`metadatas.key` у frpc, приходит как `metas.key`) совпадает с записанным. Хранится только sha256 ключа, сравнение — за постоянное время. Чужой `run_id` (номер подключения другого экземпляра) — отказ: frps заменил бы им чужое подключение |
| `NewProxy` — новая пересылка | Только типы `https` и `http`, без `customDomains` и групп; `subdomain` — ровно `<имя>` или `setup-<имя>` этого экземпляра. Служебному экземпляру посредника — только `relay` |
| `NewWorkConn` — рабочее соединение под браузер | Экземпляр не отключён: отключённому новых рабочих соединений frps не даёт. Уже открытые соединения рвёт только перезапуск frps (`relayctl revoke` делает его по умолчанию) |

Ключи, коды и токен в журнал не пишутся. Служба слушает только `127.0.0.1`: плагин — на 7400, `/api/*` — на 7401 за локальным Caddy посредника.

**TLS между экземпляром и посредником проверяется.** Без файла доверия frpc принимает любой сертификат посредника (`pkg/transport/tls.go`: `InsecureSkipVerify`, если `trustedCaFile` пуст) — перехвативший соединение узнал бы ключ экземпляра, занял бы его имена и получил бы на них сертификат. Поэтому у frps постоянный сертификат на `relay.sh.namre.app` (создаёт `relay/install.sh`, 10 лет, закрытый ключ — только root), экземпляр получает его при подключении по обычному HTTPS и проверяет им посредника (`transport.tls.trustedCaFile`, `serverName`).

## Подключение экземпляра

Только в режиме с Hermes: без Hermes экземпляр наружу ничего не публикует, страница настройки открывается через туннель SSH (`docs/standalone.md`).

1. **Решение владельца.** Агент пересказывает владельцу риск 1 ниже (держатель посредника может подменить имя) и получает явное «да» (`AGENTS.md`, стоп-точки).
2. **Код приглашения** выдаёт держатель посредника: `sudo relayctl invite --note 'кому'`. Код одноразовый, 20 знаков (100 бит), действует 7 дней; на посреднике хранится только его хеш.
3. **Выбор имени: `./ops/relay.sh check КОД ИМЯ`.** Агент спрашивает владельца, как назвать адрес, или предлагает 2–3 имени из того, что владелец о себе сказал, и проверяет каждое (`docs/runbooks/deploy.md`, шаг 5а). Запрос — `POST https://relay.sh.namre.app/api/check {code, name}`; ответ — свободно ли имя, а если нет — причина (`taken` — занято, `reserved` — служебное, `invalid` — не по правилам) и до трёх свободных вариантов от него: имя, приведённое к правилам, с цифрой 2–9, с двумя случайными буквами через дефис. Нужен действующий код — неиспользованный и неистёкший, — но проверка его не расходует и в базе ничего не меняет. С неверным, использованным или истёкшим кодом — тот же отказ 403, что у `join`, и ни слова об имени: без приглашения занятые имена по этому адресу не перебрать. Свободное при проверке имя может занять другой владелец до `join` — тогда `join` ответит 409 со свободными вариантами, и код останется.
4. **`./ops/relay.sh join КОД ИМЯ`** на сервере экземпляра. Имя — 3–30 знаков: латинские строчные, цифры, дефис внутри; служебные имена (`relay`, `www`, `api`, `admin`, `mail`, `test`, `setup`, `ns1` и подобные) и имена на `setup-` не выдаются. Ключ экземпляра (32 случайных байта) скрипт создаёт сам и записывает в `.env` до обращения к посреднику; на `https://relay.sh.namre.app/api/join` уходят код, имя и только sha256 ключа — сам ключ посредника не проходит ни в одну сторону. В ответ — два имени, адрес посредника, общий токен и сертификат frps. Если ответ потерялся в сети, повтор той же команды (тот же код, имя и ключ из `.env`) получает тот же успешный ответ; любой другой повтор израсходованным кодом — отказ. Токен скрипт пишет в `.env` и не печатает, сертификат — в `data/relay/ca.pem`; адреса экземпляра — через `./ops/set-public-url.sh https://ИМЯ.sh.namre.app` и `./ops/set-setup-url.sh https://setup-ИМЯ.sh.namre.app` (те же проверки, что адреса разные); включает профиль Compose `relay`. Неверное или занятое имя код не тратит; на занятое (409) посредник отвечает и свободными вариантами — их скрипт печатает. Служебное или неподходящее имя `join` отклоняет до проверки кода и поэтому без вариантов: по ним без кода было бы видно, какие имена заняты.
5. **Прокси — стоп-точка.** `./ops/relay.sh caddyfile` печатает готовую настройку Caddy — вариант «через посредника» из `config/Caddyfile.example`: те же два блока на двух именах (порт 443), в глобальном блоке чтение протокола PROXY от `127.0.0.1`, а в блоке дашборда — отказ изменяющим запросам, которые браузер пометил как пришедшие не с этого адреса (риск 9 ниже). Её показывают владельцу и после согласия кладут в `/etc/caddy/Caddyfile`.
6. **`./ops/up.sh`** собирает образ `frpc/` (официальный выпуск frp 0.71.0, sha256 сверяется при сборке) и запускает контейнер `shturman-relay` в сети хоста; `./ops/doctor.sh` — строки `relay`, `relay-proxies`, `relay-reach`, `relay-addresses`, затем прежние `setup-page-public` и `setup-isolation`.

Входящие порты на сервере открывать не нужно. Пока frpc не запущен, первая попытка Caddy получить сертификат не проходит — он повторяет сам (на стенде сертификаты пришли через несколько секунд после запуска frpc).

Другие команды: `./ops/relay.sh status` — имя, адреса и состояние четырёх пересылок; `off` — выключить (ключ остаётся, адреса — тоже, страницы по ним не откроются); `on` — включить снова (заново забирает сертификат посредника и возвращает адреса); `off --forget` — забыть ключ и имя (имя на посреднике остаётся занятым, пока держатель его не освободит).

**Адрес браузера.** frpc передаёт каждое соединение со своего `127.0.0.1`, а настоящий адрес браузера сообщает заголовком протокола PROXY v2 — только в пересылках https. Caddy читает его лишь от `127.0.0.1` и передаёт дальше как обычно, в `X-Forwarded-For`. На порт 80 заголовка нет: этот порт Caddy обслуживает своим сервером перенаправлений, к которому настройка `listener_wrappers` не применяется (Caddy 2.11.7, `modules/caddyhttp/autohttps.go`) — с заголовком он отвечал 400, и проверка `http-01` не проходила; найдено на стенде. Сервис переписки адресам клиентов не верит и решений по ним не принимает (`service/src/shturman/setup_page/shield.py`); для Hermes ничего не меняется: он и раньше получал запросы от Caddy с `127.0.0.1`.

## Держатель посредника

Установка и обновление — `relay/install.sh` (порядок — `relay/README.md`): frp 0.71.0 и Caddy 2.11.7 из официальных выпусков с проверкой сумм, служба `relayd`, frps с плагином и постоянным сертификатом, а для `https://relay.sh.namre.app/api/*` — свой Caddy на `127.0.0.1:9080/9443` и служебный frpc под именем `relay`: порты 80 и 443 посредника занимает frps, и служба выдачи имён подключена к нему так же, как экземпляр. Службы прототипа `relay-test-*` установщик убирает.

Команды: `relayctl invite [--days N] [--note …]`, `relayctl list`, `relayctl revoke ИМЯ [--no-restart]`, `relayctl release ИМЯ`; с 0.4.0 — `relayctl manager-link`, `manager-token [--remove]`, `manager-status` (бот-менеджер, ниже).

## Бот-менеджер: бот согласований в одно нажатие (relayd 0.4.0)

Необязательная часть посредника (Р-77, `docs/approvals-bot.md`). Держатель заводит у @BotFather бота-менеджера и включает ему Bot Management Mode, служба `relayd` опрашивает его (`getUpdates`, только обновления `managed_bot` и, с 0.5.0, личные сообщения с кодами привязки; без webhook) и по просьбе экземпляра помогает владельцу создать **его собственного** бота согласований одним нажатием: `POST /api/botpair/start` → ссылка `https://t.me/newbot/<менеджер>/<имя>?name=…` → владелец подтверждает в Telegram → служба сопоставляет бота по имени, закрывает к нему доступ для всех, кроме владельца, и один раз отдаёт экземпляру токен по секрету пары (`POST /api/botpair/<pair_id>/token`). Если владелец изменил адрес бота в окне создания, служба 0.5.0 запоминает бота без пары (без токена, в памяти, сутки) и привязывает его к паре, когда **создатель этого бота** присылает бот-менеджеру код пары (`/start <код>` по ссылке со страницы, Р-78). Подробно — `docs/approvals-bot.md`; операторские шаги — `relay/README.md`, «Бот-менеджер».

**Граница доверия — та же, что у посредника, но шире по последствиям.** Держатель бота-менеджера технически может в любой момент получить токен каждого бота, созданного через него (`getManagedBotToken`), — а с ним подделать вход в Mini App и нажатия в нём, через экран «Чаты» менять, какие чаты читает ассистент (Р-80), получать обновления бота, выпустить ему новый токен; если владелец подключит такого бота в бизнес-режиме — читать его личные переписки. Поэтому одно нажатие — только по выбору владельца, после текста о цене, и в любой момент заменяется ботом, созданным вручную. Токен бота-менеджера хранится в `/var/lib/shturman-relay/manager.token` (600, пользователь службы) и вводится держателем на странице посредника по одноразовой ссылке `relayctl manager-link` или из стандартного ввода — не через чат и не через агента.

Новые точки входа посредника: `POST /api/botpair/start` (пределы: 10 пар с адреса или сети /64 за 15 минут, 5 ожидающих пар с сети /24 или /48, 200 ожидающих пар; по выбору — только по коду приглашения), `POST /api/botpair/<pair_id>/token` (секрет 256 бит телом запроса; неверный — тот же ответ 404, что неизвестная пара; только предел на адрес; «ждём», пока не закончилось закрытие доступа к боту; создатель — номер, @имя и имя), `GET /api/manager/setup` и `POST /api/manager/setup` (страница ввода токена бота-менеджера: одноразовая ссылка, секрет — после «#», строгая политика содержимого), признак `botpair` в `GET /api/health`.

**Отключение.** `revoke` отмечает экземпляр отключённым и перезапускает frps (нужен root): управляющее соединение экземпляра и все его уже открытые соединения браузеров рвутся, остальные экземпляры переподключаются сами за несколько секунд. Закрыть одно подключение средствами frps нельзя — у панели frps 0.71.0 есть только списки клиентов и пересылок. С `--no-restart` frps не перезапускается: новых рабочих соединений экземпляр не получает (`NewWorkConn`), переподключиться не может (`Login`), но уже открытые соединения браузеров (keep-alive, HTTP/2) и заранее открытые рабочие соединения frpc продолжают работать до перезапуска frps — на стенде после такого отключения прошли ещё 2–3 запроса. `release` освобождает имя отключённого экземпляра и тоже всегда перезапускает frps: иначе прежнее подключение держало бы пересылку на это имя, и новый владелец её не занял бы. Выдавать освобождённое имя другому владельцу раньше чем через 90 дней не стоит: сертификаты, выпущенные на него прежнему владельцу, действуют до конца своего срока.

## Кто что видит

| Кто | Видит | Не видит |
|---|---|---|
| Посредник | какие имена открывают, когда, с каких адресов, сколько данных; адрес, с которого подключается экземпляр, и что frpc сообщает о себе при входе — имя компьютера (`hostname`), ОС и архитектуру; адреса, с которых подключаются по коду | содержимое страниц, пароли, ключи, QR-код входа в Telegram — всё зашифровано до сервера владельца |
| Держатель зоны `sh.namre.app` | то же, что посредник | то же — **но может подменить имя** (ниже, риск 1) |
| Cloudflare | запросы DNS к `namre.app` | трафик страниц |
| Let's Encrypt, журналы Certificate Transparency | имена экземпляров | — |
| Бот-менеджер посредника (с 0.4.0, если владелец создал бота в одно нажатие) | имя и номер созданного бота, номер и имя аккаунта владельца, создавшего его; **может получить токен бота в любой момент** | содержимое переписки — пока держатель не воспользовался токеном |

## Риски

1. **Держатель зоны может перехватить вход.** Тот, кто управляет зоной `sh.namre.app` или посредником, может направить имя владельца на свой сервер, получить на него настоящий сертификат и показать поддельную страницу настройки — а на ней вводят ключи Telegram и входят в аккаунт. Тем же способом он перехватит и приложение «Штурман» (Mini App бота согласований, `setup-<имя>/shturman-setup/app/`, `docs/miniapp.md`): Telegram откроет его подменённую страницу и передаст ей подписанные данные входа владельца, а с ними в течение 10 минут можно войти в настоящее приложение и нажимать кнопки согласований за владельца — принять обязательство, открыть скрытое сообщение, разрешить чтение источника; черновик — отправить, если отправка включена; на экране «Чаты» — включить чтение чатов, исключить чаты и увидеть список диалогов (Р-80; о каждом изменении владельцу приходит сообщение в бот). Полностью этот риск не убирается; сужают его:
   - запись `CAA` с `accounturi` (RFC 8657) для имён экземпляра — выпуск только учётной записи ACME самого экземпляра; держатель зоны может её поменять, но это отдельное действие;
   - проверка журналов Certificate Transparency экземпляром: чужой сертификат на его имя — сообщение в бот согласований (обнаружение, не защита);
   - прямо сказать владельцу в документах и при подключении: посредник — для тех, кто доверяет его держателю. Кто не доверяет — свой домен, адрес по IP (Р-67) или туннель SSH.
2. **Одна точка отказа.** Посредник недоступен — страницы не открываются ни у одного подключённого экземпляра. Ассистент в Telegram при этом работает.
3. **Посредник видит метаданные** (таблица выше).
4. **Ограничения Let's Encrypt.** Новые сертификаты считаются на зарегистрированный домен `namre.app` — порядка 50 в неделю (точные правила — https://letsencrypt.org/docs/rate-limits/, сверить перед открытием сервиса); продления не ограничиваются. Для десятков экземпляров достаточно; для сотен — внести `sh.namre.app` в Public Suffix List (процедура на недели).
5. **Злоупотребление именами.** Открытая регистрация — фишинговые страницы в зоне и блокировка её целиком. Поэтому имена — только по коду приглашения; попыток подключения с одного адреса (IPv6 — с одной сети /64) — не больше 10 за 15 минут; неудачных попыток со всех адресов вместе — не больше 60 в минуту (удачные не считаются: перебор с многих адресов задерживает законное подключение не дольше минуты после своего конца). У проверки имени (`/api/check`) свой счёт — не больше 30 проверок с адреса за 15 минут: агент владельца проверяет несколько имён подряд, и это не должно съедать попытки подключения; неверный код в проверке идёт в тот же общий предел неудачных попыток, что и у `join`, — перебирать коды через проверку не выгоднее, чем через подключение. Счёт — в памяти службы.
6. **Посредник открыт в интернет** — нагрузка, атаки, обновления ОС и frp на держателе. Служба `relayd` недоступна — frps отказывает в новых подключениях и пересылках (уже открытые продолжают работать, пока не понадобится новое рабочее соединение).
7. **Порт 7000** для исходящего соединения экземпляра в некоторых сетях закрыт; запасной путь — подключение экземпляра поверх 443 (в frp есть транспорт через WebSocket) — не проверялся. `./ops/doctor.sh` показывает это строкой `WARN relay-reach`.
8. **Общий токен frps и чужой `run_id` — захват имени.** Общий токен знает каждый подключённый экземпляр. frps принимает рабочее соединение по номеру подключения (`run_id`) и проверяет только токен (`RegisterWorkConn` в `server/service.go` frp 0.71.0); плагин в `NewWorkConn` видит пользователя этого подключения, а не того, кто открыл рабочее соединение. Значит, держатель другого экземпляра, узнавший чужой `run_id`, может забить запас рабочих соединений чужого экземпляра своими и получать соединения к его именам — в том числе проверочные соединения Let's Encrypt (`tls-alpn-01`). Так он получит настоящий сертификат на чужое имя и дальше сможет читать всё, что вводится на страницах чужого экземпляра. Это полный захват, а не только помеха. Защищает только тайна `run_id` (64 случайных бита, выдаёт frps): служба хранит лишь его sha256 и отклоняет вход с чужим `run_id`; frps пишет журнал только с уровня `warn` — в строках `info` номер есть у каждого подключения, а в предупреждениях остаётся только у неудачных рабочих соединений и их тайм-аутов (проверено на стенде); журнал systemd читают root и группа `adm` — посторонних в ней быть не должно; на экземпляре номер виден в журнале контейнера `shturman-relay` — только владельцу сервера. Что снимет риск: CAA с `accounturi` для имён экземпляров (сертификат выпустит только учётная запись ACME самого экземпляра) и проверка журналов Certificate Transparency — в планах (риск 1); надёжнее — свой токен frps у каждого экземпляра, чего frps 0.71.0 сам не умеет.
9. **Общий сайт для всех экземпляров.** Все экземпляры — имена одной зоны `sh.namre.app`, а `namre.app` нет в Public Suffix List, поэтому для браузера это один «сайт». Страница любого экземпляра — «своя» (same-site) для всех соседних:
   - cookie `SameSite=Lax` дашборда Hermes браузер отправляет и на запросы со страницы соседа, а проверки `Origin` или CSRF у изменяющих запросов дашборда нет (ниже — что найдено в Hermes). Изменяющий запрос с телом JSON закрыт предварительным запросом CORS, но запрос без тела или с телом формы прошёл бы. Поэтому в варианте прокси «через посредника» блок дашборда отвечает 403 на изменяющий запрос (не GET, HEAD, OPTIONS), если у него есть заголовок `Sec-Fetch-Site` и он не `same-origin`; запросы без этого заголовка (не браузер) проходят как раньше. Страница настройки переписки cookie не использует и сама сверяет `Sec-Fetch-Site` и `Origin` — ей это не грозит;
   - сосед может поставить cookie на всю зону (`Domain=sh.namre.app`): подбросить свои `__Secure-hermes_session_*` или `hermes_session_*` (Hermes читает их, когда своей `__Host-…` у браузера нет — до входа и после выхода), сбить вход через `hermes_session_pkce` или забить заголовок `Cookie` огромными cookie, чтобы страницы перестали открываться (cookie bomb). Действующий вход так не подделать — нужен токен, выпущенный этим же экземпляром, — но помешать войти можно. Прокси это не закрывает: отличить чужую cookie по заголовку `Cookie` нельзя;
   - **что снимает риск** — внесение `sh.namre.app` в Public Suffix List (задача держателя, `relay/README.md`, «Public Suffix List»): тогда каждое имя в зоне станет отдельным сайтом, а заодно лимиты Let's Encrypt будут считаться на каждый экземпляр отдельно (риск 4). Попадает в браузеры не сразу — с их обновлениями, через недели и месяцы после внесения. **До этого посредник — только для экземпляров, держателям которых доверяет держатель посредника:** любой подключённый владелец может мешать соседям и, зная их `run_id`, захватить их имя (риск 8).

**Что найдено в Hermes `v2026.9.24`** (коммит `f97608f`, `hermes_cli/dashboard_auth/cookies.py`, `middleware.py`, `web_server.py`): cookie сессии (`hermes_session_at`, `_rt`, `_provider`) — `HttpOnly`, `SameSite=Lax`, по HTTPS — с приставкой `__Host-` (только этот адрес, `Path=/`, без `Domain`), поэтому соседи их не перезапишут и не прочитают; `hermes_session_pkce` — `SameSite=None; Secure`, тоже `__Host-`. Но читатель перебирает имена `__Host-…`, затем `__Secure-…`, затем без приставки (`_read_with_fallback`) — отсюда подброс от соседа, когда своей cookie нет. Запросы к `/api/*` при опубликованном дашборде принимаются по одной cookie сессии (`gated_auth_middleware`), без проверки `Origin` и без CSRF-токена; CORS разрешён только для `localhost`/`127.0.0.1`; `Origin` сверяется только у WebSocket. Маршруты плагина «Штурмана» в дашборде (`dashboard/plugin_api.py`) `Origin` тоже не проверяют.

### Прототип — на посреднике

На посреднике поднят тестовый «экземпляр» — отдельные службы Caddy 2.11.7 и frpc под своими пользователями, подключённые к `relay.sh.namre.app:7000` как внешний клиент:

- frpc подключился, посредник принял имя `test.sh.namre.app` (поле `subdomain`; имя полностью в `customDomains` frp внутри `subDomainHost` не принимает);
- Caddy экземпляра получил сертификат Let's Encrypt на `test.sh.namre.app` через посредника (проверка `tls-alpn-01` прошла сквозь пересылку по SNI);
- с компьютера владельца в России `https://test.sh.namre.app/` открылся (ответ 200 от Caddy экземпляра), `http://` — перенаправление 308 на https;
- ключ сертификата лежит только в каталоге службы тестового экземпляра; у frps в `/etc/frp` — только его настройка и ключ доступа экземпляров.

Не проверено (прототип): экземпляр за настоящим NAT (тестовый стоял на самом посреднике — для исходящего соединения это не важно, но живой проверки нет), сеть с закрытым портом 7000, нагрузка, продление сертификата через посредника.
