# Сервис переписки

Единственная часть «Штурмана» вне Hermes: держит сессии Telegram, ведёт архив и отдаёт его агенту. Этот документ — что сервис делает, какие у него режимы, как им пользоваться без веб-интерфейса и что из написанного проверено. Устройство кода — в `service/README.md`.

Состояние на версию 0.0.3: код написан и покрыт тестами, часть запускалась на стенде разработки. **На эталонном сервере, с настоящим Telegram и с настоящей моделью не проверено ничего** — подробно в разделе «Что ещё не проверено».

## Что готово

Как читать столбец «Как проверено»: **тесты** — автоматические тесты, в которых Telegram, модель и сервер эмбеддингов заменены подставными объектами; **стенд** — запуск настоящего кода на стенде разработки (не на эталонном сервере); **нет** — не проверялось.

| Срез | Состояние | Как проверено |
|---|---|---|
| Схема архива, общий путь записи, импорт экспорта Telegram Desktop, команды `shturman` | Написано | Тесты; стенд: синтетический экспорт на 300 000 сообщений импортирован примерно за 30 секунд. Настоящий экспорт — нет |
| Сессии Telegram на Telethon: вход по QR, роль «только чтение» для основного аккаунта, роль помощника, выбор чатов, загрузка истории, приём новых, изменённых и удалённых сообщений, сверка | Написано | Только тесты, Telegram подставной. Настоящий Telegram — нет |
| MCP-сервер архива для агента Hermes, девять инструментов только на чтение | Написано | Тесты; стенд: стоковая команда `hermes mcp test shturman` (Hermes 0.21.5, MCP-клиент 2.0.0) подключилась с токеном из окружения и нашла 9 инструментов |
| Приём сообщений бизнес-бота из плагина Hermes | Написано | Тесты; стенд: настоящий исполнитель плагина с настоящим сервисом, бот подставной. Настоящий бизнес-поток — нет |
| Поиск: полнотекстовый с русской морфологией; гибридный (слова + смысл) при включённых эмбеддингах | Написано; эмбеддинги по умолчанию выключены | Тесты; стенд: настоящий сервер TEI 1.9.4 с настоящей моделью. Качество — только на маленьком синтетическом наборе (см. ниже) |
| Обработка: реестр людей, разбор сроков, извлечение обязательств с одобрением владельца, ночной прогон | Написано | Тесты, модель подставная. Качество извлечения на настоящей модели — нет |
| Страницы памяти о людях: файлы Markdown и история в git | Написано, первая версия | Тесты, модель подставная |
| Шлюз отправки: черновики с согласованием кнопкой, автоответ доверенным, наблюдатель групп | Написано; **отправка по умолчанию выключена** | Тесты; стенд: путь «черновик → карточка → нажатие владельца → отправка через бизнес-бота» с подставным ботом |
| Мост в плагине `shturman`: исполнитель заданий, пересылка бизнес-сообщений, кнопки, инструменты агента, два скилла, задачи по расписанию, проход дашборда к сервису | Написано | Тесты; стенд: 35 проверок настоящего исполнителя с настоящим сервисом (бот подставной, ответы модели заготовлены); настоящий адаптер Telegram из Hermes с подставным Telegram |
| Упаковка: образ сервиса, Compose с базой и эмбеддингами, скрипты оператора | Написано | **Под Docker не запускалось**: в среде разработки нет Docker. Образ собирает только CI. Первый запуск на эталонном сервере и есть проверка |
| Экраны во вкладке «Штурман» для всего перечисленного | **Не сделаны** | Серверные адреса для них есть (`/api/plugins/shturman/service/...`), страниц нет. Пока — команды из раздела «Как пользоваться без веб-интерфейса» |
| Скачивание вложений, распознавание голосовых, страницы проектов и решений, извлечение произвольных фактов, проверочный набор вопросов, отдельный бот согласований | **Не сделаны** | — |

Цифры проверок. Автоматические тесты сервиса: 1038, на Postgres 16 с pgvector 0.8.7; они же пройдены на Python 3.12 с зависимостями из списка с контрольными суммами (`service/requirements.lock`). Тесты плагина: 404 без Hermes (3 пропущены) и 504 в окружении Hermes 0.21.5 с python-telegram-bot 22.8.

Замеры на стенде разработки, не на эталонном сервере. Импорт: 300 000 сообщений примерно за 30 секунд. Эмбеддинги: около 155 коротких сообщений в секунду на 2 ядрах, 0,9–1,15 ГБ памяти. Качество гибридного поиска мерилось только на маленьком синтетическом русском наборе: полнота в первых пяти результатах 0,88 против 0,20 у поиска по словам. Это ориентир, а не оценка качества на настоящей переписке.

Код прошёл две независимые проверки — безопасности и стыков между частями. Замечания исправлены, кроме одного ограничения: оно описано в `docs/architecture.md`, раздел «Открытое ограничение», и из-за него отправка остаётся выключенной.

## Что где работает

Сервис — один процесс (`shturman serve`) в контейнере `shturman-service`. Он слушает порт 8765 на локальном адресе сервера; наружу порт не открыт.

| Путь | Кто обращается | Токен | Что можно |
|---|---|---|---|
| `/health` | Проверки | Нет | Только «жив» и версия |
| `/api/*` | Плагин `shturman` в Hermes; оператор командой `shturman call` | `SHTURMAN_API_TOKEN` | Внутренний API: приём бизнес-сообщений, очередь заданий, нажатия кнопок, аккаунты Telegram, импорт, правила отправки, обязательства, люди, страницы |
| `/mcp` | Агент Hermes | `SHTURMAN_MCP_TOKEN` (в Hermes переменная называется `MCP_SHTURMAN_API_KEY`) | Только чтение архива. Принимаются только запросы POST |

Токены разные и не взаимозаменяемы; сервис не запустится, если они совпали или короче 32 знаков. Оба генерирует `./ops/init-env.sh --auto`.

Инструменты архива для агента: `search_messages`, `get_context`, `list_chats`, `get_chat_history`, `find_person`, `list_commitments`, `get_commitment`, `get_person_page`, `search_pages`. Все только читают. Чужой текст в ответах стоит в рамке `[untrusted] … [/untrusted]`; исключённые чаты, удалённые сообщения и служебные чаты Telegram не отдаются.

**У сервиса нет ни модели, ни бота.** И то и другое есть только у Hermes. Всё, для чего нужна модель, сообщение владельцу или отправка через бизнес-бота, сервис ставит в очередь заданий; плагин забирает задание, выполняет и возвращает итог. Видов заданий пять:

| Задание | Что делает плагин |
|---|---|
| `llm.structured` | Спрашивает модель Hermes и возвращает ответ по заданной схеме |
| `llm.text` | Спрашивает модель Hermes и возвращает текст |
| `notify.owner` | Отправляет владельцу сообщение в управляющий чат, при необходимости с кнопками |
| `notify.edit` | Правит это сообщение: заменяет текст, убирает кнопки |
| `business.send` | Отправляет сообщение от имени владельца через бизнес-бота |

В обратную сторону плагин пересылает сервису нажатия кнопок владельца (их данные начинаются с `sh:`) и сообщения бизнес-режима. Содержимое выполненного задания стирается через десять минут после закрытия; задание, которое никто не забрал, закрывается как неудачное (уведомление и запрос к модели — через сутки, правка сообщения и запрос текста — через час).

Что плагин добавляет агенту поверх архива:

| Что | Имя | Назначение |
|---|---|---|
| Инструмент | `shturman_draft_message` | Создать черновик сообщения. Ничего не отправляет |
| Инструмент | `shturman_commitments` | Посмотреть обязательства |
| Инструмент | `shturman_commitment_update` | Закрыть, отменить, открыть заново, перенести срок. Принять или отклонить предложение агент не может — это кнопка владельца |
| Инструмент | `shturman_people` | Найти человека, посмотреть карточку, добавить алиас |
| Скилл | `shturman:morning-brief` | Утренняя сводка |
| Скилл | `shturman:weekly-review` | Обзор недели |

Задачи по расписанию для двух скиллов заводит адрес плагина `POST /api/plugins/shturman/cron/install` (по умолчанию сводка в 08:27 каждый день, обзор в 17:47 по пятницам). Кнопки для него в интерфейсе пока нет.

## Отправка выключена

| Переменная | По умолчанию | Что значит |
|---|---|---|
| `SHTURMAN_SENDING` | `off` | Главный выключатель отправки. Включено — значение `on` |
| `SHTURMAN_SEND_DAILY_CAP` | `50` | Потолок отправок на аккаунт в сутки, черновики и автоответы вместе |

Обе читаются **только из окружения сервиса** — на сервере это файл `.env`. Во внутреннем API нет вызова, который включает отправку или поднимает потолок: настройки шлюза могут потолок только уменьшить.

Пока выключатель в положении `off`:

- сервис не отправляет ничего и никому, ни одним каналом;
- черновики не создаются: инструмент агента получает отказ с объяснением;
- автоответ не начинается, модель не спрашивается;
- аккаунту-помощнику запрещены запросы отправки и «печатает…» на уровне клиента Telegram.

Работает при этом всё остальное: архив, поиск, обязательства, страницы памяти, наблюдатель групп (он пишет только владельцу).

Включать отправку сейчас не следует: в конструкции есть открытое ограничение (`docs/architecture.md`). Пока отправка выключена, в настройках Telegram Business у бота стоит оставить выключенным право отвечать на сообщения.

Включение — действие владельца и стоп-точка для агента (`AGENTS.md`): строка `SHTURMAN_SENDING=on` в `.env`, затем `./ops/up.sh`.

## Аккаунты и источники

«Аккаунт» в архиве — это точка зрения, с которой пронумерованы чаты и сообщения. У основного аккаунта владельца три возможных источника. Задумано, что они дают одни и те же идентификаторы и складываются в одни строки без дублей; для пары «бизнес-бот и экспорт» это на настоящих данных не проверено.

| Аккаунт | Источник | Что даёт | Может ли отправлять |
|---|---|---|---|
| Основной (владелец) | Экспорт Telegram Desktop | Прошлое: всё, что выгружено | — |
| Основной (владелец) | Бизнес-бот | Новые личные чаты по фильтру владельца | Да — ответ в личном чате в течение 24 часов после входящего, при включённой отправке |
| Основной (владелец) | Сессия Telethon **только на чтение** — необязательный режим | Группы и каналы основного аккаунта, история без выгрузки | **Нет.** Клиент этой роли пропускает к Telegram только перечень запросов на чтение |
| Дополнительный (помощник) | Сессия Telethon | Чаты и группы, где состоит помощник | Да — через шлюз отправки, при включённой отправке |

Режим «основной аккаунт на чтение» включается владельцем отдельно, с предупреждением: на сервере появляется сессия основного аккаунта, и риск ограничений со стороны Telegram ложится на него, а не на запасной номер. От имени владельца сервис пишет только через бизнес-бота — официальным путём.

Правила сессий:

- **Ничего не читается, пока владелец не выбрал чаты.** Вход в аккаунт сам по себе в архив ничего не приносит.
- **Глубина истории ограничена.** Для включаемого чата по умолчанию загружаются последние 12 месяцев; глубину можно изменить для аккаунта или задать дату для конкретного включения.
- **Помощником не может стать аккаунт владельца.** Вход помощника не начинается, пока сервис не знает владельца (бот не привязан в мастере и в архиве нет основного аккаунта). После входа и при каждом запуске аккаунт сверяется с владельцем; при совпадении сессия завершается.
- **Одна сессия — один процесс.** Перед подключением берутся блокировка файла и блокировка в базе; занято — сервис не подключается.
- **При ограничении со стороны Telegram** сервис ждёт названное время и не повторяет запрос раньше.
- **Прочитанным ничего не отмечается.**

Сообщения бизнес-режима приходят через бота только из личных чатов. Сообщения принимаются только по подключению, которое создал сам владелец.

## Уровни автономии

| Уровень | Что делает ассистент | Где | Состояние |
|---|---|---|---|
| 0. Наблюдатель | Читает, ищет, сводит | Любой источник | Написано |
| 1. Черновики | Готовит ответ, отправляет после нажатия владельца | Бизнес-бот, помощник | Написано, отправка выключена |
| 2. Шаблонные действия | Сам отправляет типовые сообщения людям из белого списка | Помощник | Не сделано |
| 2а. Автоответ доверенным | Сам отвечает людям из списка доверенных, без подтверждения | Бизнес-бот (голос владельца), помощник | Написано, по умолчанию выключен, отправка выключена |
| 3. Свободная переписка | Ведёт диалог в заданных рамках | Помощник | Не сделано |

Правила уровня 1:

- агент может только создать черновик; текст черновика после создания не меняется — владелец согласует ровно то, что уйдёт;
- **ассистент не пишет первым**: черновик возможен только в чат, где уже есть исходящее сообщение владельца или помощника, либо как ответ через бизнес-бота человеку, который только что написал сам. Через API это правило не выключается;
- в одном чате ждёт решения не больше одного черновика; новый заменяет прежний;
- нажатие сначала занимает черновик, потом идёт отправка — два нажатия не дают двух отправок;
- если ответ Telegram потерялся, исход помечается «неизвестно, дошёл ли» и сам не повторяется никогда.

Правила уровня 2а:

- доверенные задаются только числовыми идентификаторами Telegram;
- ответ готовится **без инструментов**: сервис сам собирает справку — последние сообщения этого чата и найденное в архиве — и просит у модели только текст. По умолчанию поиск идёт только в этом же чате; владелец может расширить его на другие чаты аккаунта, но оттуда берутся лишь собственные слова владельца или помощника. Чужие сообщения из других чатов в справку не попадают никогда;
- только личные чаты, только входящие, не от ботов и не через ботов, не на правки; свои исходящие отсекаются по флагу сообщения;
- пауза между ответами и дневной лимит на аккаунт (по умолчанию 5 секунд и 300 ответов); поверх него действует общий потолок `SHTURMAN_SEND_DAILY_CAP`;
- пока ответ готовится, аккаунт-помощник показывает «печатает…» с обновлением каждые 4 секунды;
- ответ одним сообщением, длинный режется по абзацам; запоздавший ответ не отправляется;
- всем, кто не в списке, сервис не отвечает вообще;
- о каждом включении автоответа, изменении списка доверенных и правил отправки владелец получает сообщение.

## Наблюдатель групп

Для выбранных групп и каналов: совпадение по словам и выражениям правила → проверка моделью со строгим форматом ответа → уведомление владельцу в управляющий чат. В самой группе сервис не пишет и прочитанным её не отмечает: в модуле нет ни одного обращения к Telegram. Свои лимиты проверок и уведомлений в час и в сутки, защита от повторов. Работает на любом аккаунте, который состоит в группе, и при выключенной отправке.

## Обязательства и страницы памяти

Ночной прогон (по умолчанию в 03:30 по часам владельца) берёт новые сообщения, режет их на эпизоды и отправляет модели только те, где есть похожее на обещание. Ответ модели проверяется текстом сообщений: цитата и формулировка срока обязаны в нём быть. Дату по формулировке считает код, а не модель; если формулировка не сводится к одной дате — обязательство помечается «нужно уточнение». Найденное записывается как предложение, владелец получает одну сводку с кнопками и принимает или отклоняет каждое. При первом прогоне разбираются последние 30 дней.

После прогона собираются страницы о людях. Что из устройства памяти сделано, а что нет — `docs/memory.md`.

## Как пользоваться без веб-интерфейса

Экранов во вкладке «Штурман» пока нет. Всё ниже делается в терминале сервера. Команды показывают названия чатов и имена людей, а часть из них меняет то, что хранится в архиве, поэтому выполняет их владелец либо агент по его явной просьбе в текущей сессии (`AGENTS.md`).

Сначала — `./ops/up.sh` и `./ops/doctor.sh` со строкой `PASS service`.

### Загрузить экспорт Telegram Desktop

Экспорт делается в Telegram Desktop в формате JSON. Файл `result.json` переносится на сервер.

```
./ops/import-export.sh scan /путь/к/result.json
./ops/import-export.sh import /путь/к/result.json --exclude user:123456789
```

`scan` ничего не записывает: показывает чаты с числом сообщений и периодом. Во втором столбце списка — вид и идентификатор чата (`user:…`, `chat:…`, `channel:…`); его и нужно передать в `--exclude`, чтобы чат не попал в архив. `--exclude` можно повторять. Исключение запоминается для всех источников. Для экспорта одного чата нужен `--owner-id` с числовым идентификатором владельца. Повторный импорт того же файла дублей не создаёт. Файл подключается контейнеру только для чтения и никуда не копируется; после импорта его стоит удалить с сервера — в нём вся переписка открытым текстом.

### Войти в аккаунт Telegram

Нужны `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` собственного приложения владельца (my.telegram.org → API development tools). Их вводит человек в своём терминале: `./ops/init-env.sh`, затем `./ops/up.sh` (`docs/setup.md`).

```
./ops/tg-login.sh assistant
./ops/tg-login.sh owner
```

Первая команда подключает аккаунт-помощник, вторая — основной аккаунт владельца, только на чтение. Скрипт запускает **человек**: в терминале появляется QR-код, его сканируют телефоном («Настройки → Устройства → Подключить устройство»). Если на аккаунте включён облачный пароль, он вводится скрыто и нигде не сохраняется. Агент этот скрипт не запускает и его вывод не читает.

### Выбрать чаты

```
docker exec shturman-service shturman call GET /api/tg/accounts
docker exec shturman-service shturman call GET '/api/tg/accounts/1/dialogs?limit=100'
docker exec shturman-service shturman call POST /api/tg/accounts/1/sync '{"enabled": true, "chats": [{"peer_class": "user", "tg_id": 123456789}]}'
docker exec shturman-service shturman call GET /api/tg/accounts/1/sync
```

Первая команда показывает подключённые аккаунты; число из поля `account_id` подставляется вместо `1` в остальных. Вторая — чаты аккаунта с полями `peer_class` и `tg_id`. Третья включает выбранные чаты; вместо списка можно включить все чаты одного вида: `{"enabled": true, "types": ["personal_chat"]}`. Значение `"enabled": false` чат выключает. Четвёртая показывает ход загрузки.

Глубина истории: по умолчанию 12 месяцев. Изменить для аккаунта — `PUT /api/tg/accounts/1/options` с телом `{"backfill_months": 6}`; для одного включения — поле `"since": "2026-01-01"` в запросе `sync` (`null` — вся история).

### Исключить чат из архива

```
docker exec shturman-service shturman call GET '/api/chats?query=название'
docker exec shturman-service shturman call PUT /api/chats/42/excluded '{"excluded": true, "purge": true}'
```

Первая команда находит чат и его номер в архиве (поле `id`); он подставляется вместо `42`. `"purge": true` стирает уже сохранённые сообщения чата — это необратимо. Вместе с чатом уходит всё, что из него выведено: обязательства, строки страниц, черновики, векторы. Вернуть чат — `{"excluded": false}`. Служебные чаты Telegram вернуть нельзя.

### Включить поиск по смыслу

```
./ops/embeddings.sh on
./ops/embeddings.sh status
./ops/embeddings.sh off
```

`on` скачивает модель (около 0,5 ГБ с huggingface.co, с проверкой контрольных сумм), добавляет контейнер с ней (около 1,2 ГБ памяти) и перезапускает стек. Это стоп-точка: нужна память и скачивание. Сам контейнер эмбеддингов в интернет не ходит. Без него поиск работает по словам: сначала «все слова сразу», затем, если нашлось мало, «любое из слов».

## Модель данных архива

| Таблицы | Что хранят |
|---|---|
| `accounts`, `peers`, `chats` | Точки зрения (основной аккаунт, помощник); люди, боты, группы, каналы по идентификаторам Telegram; чат с точки зрения аккаунта и признак «исключён» |
| `messages`, `message_versions` | Сообщения дословно: текст, разметка, ответ-на, пересылка, вид вложения, вектор; прежние формулировки отредактированных сообщений |
| `imports` | Журнал импортов с итогами |
| `settings`, `jobs`, `business_connections` | Настройки сервиса, очередь заданий, подключения бота в бизнес-режиме |
| `tg_sessions`, `tg_sync_chats` | Какой аккаунт занимает роль и какие чаты выбраны. Ключ сессии лежит в файле, не в базе |
| `people`, `person_*` | Реестр людей: учётные записи, алиасы, словоформы имён, предложения слияния |
| `processing_*`, `commitments`, `commitment_*` | Прогоны обработки, обязательства, журнал их изменений |
| `pages`, `page_*` | Указатель страниц памяти; сами страницы — файлы |
| `outbox_*`, `watch_*` | Черновики, правила отправки, доверенные, журнал автоответов; правила и совпадения наблюдателя |

Правила, зашитые в схему и проверенные тестами:

- **Без дублей.** Сообщение определяется парой «чат, идентификатор сообщения»; повторный приход из любого источника дополняет запись, а не создаёт новую.
- **Правки не теряются и не затираются.** Более свежая правка заменяет текст, прежний уходит в историю. Старый экспорт, загруженный после новой правки, текст не перезаписывает.
- **Исключённый чат не попадает в архив** ни из одного источника; запрет запоминается.
- **Служебные чаты Telegram исключены всегда**: уведомления Telegram (777000), @BotFather, @SpamBot и диалог экспорта «Коды подтверждения». В них лежат коды входа и токены ботов.
- **Время — из точной отметки экспорта**, а не из местного времени компьютера, на котором делали выгрузку.
- **Отправляется только строка черновика**, прошедшая путь «ждёт → принят → отправляется»; её текст после создания не меняется.

Вложения не скачиваются: в архиве остаётся только вид вложения.

## Команды

Внутри контейнера сервиса (`docker exec shturman-service shturman …`):

```
shturman serve                         запустить сервис (так стартует контейнер); схема базы обновляется при старте
shturman migrate                       привести схему базы к текущей версии
shturman scan result.json              показать чаты экспорта с объёмом и периодом, ничего не записывая
shturman import result.json            импортировать; --exclude user:123 — не принимать чат; --owner-id — для экспорта одного чата
shturman search "смета по фасадам"     поиск по словам с учётом русских словоформ; --limit N
shturman call GET /api/status          запрос к внутреннему API работающего сервиса; методы GET, POST, PUT, DELETE, тело — JSON третьим аргументом
shturman tg-login assistant|owner      вход в аккаунт по QR в терминале; выполняет человек
shturman bot-bind                      одноразовая ссылка привязки владельца к боту согласований
shturman bot-status                    состояние бота согласований и своей модели сервиса; без секретов
```

Для `scan` и `import` на сервере есть обёртка `./ops/import-export.sh`, для `tg-login` — `./ops/tg-login.sh`, для `bot-bind` — `./ops/bot-bind.sh` (кто её запускает и что делать со ссылкой — `docs/standalone.md`).

## Что ещё не проверено

- **Всё, что касается настоящего Telegram**: вход по QR, загрузка истории, удаления, ограничения частоты, бизнес-поток.
- **Совпадают ли идентификаторы сообщений в бизнес-потоке и в экспорте.** На этом держится обещание «без дублей» для пары «бизнес-бот и экспорт». Если не совпадают, одно сообщение ляжет в архив дважды.
- **Настоящая модель**: качество извлечения обязательств, сводки страниц, текст автоответа, два скилла.
- **Docker**: `service/Dockerfile`, сети Compose, `ops/up.sh`, `ops/doctor.sh` и `ops/backup.sh` под Docker, контейнер эмбеддингов с заранее скачанной моделью, подключённой только для чтения.
- **Настоящий экспорт Telegram Desktop**: проверено только на синтетических данных, составленных по официальной схеме.
- **Поведение на эталонном сервере с 4 ГБ памяти.**
- Какой идентификатор у диалога «Коды подтверждения» в живых источниках (бизнес-бот, сессия): сейчас он исключается по типу чата экспорта.
