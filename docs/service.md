# Сервис переписки

Единственная часть «Штурмана» вне Hermes: держит сессии Telegram, ведёт архив, отдаёт его агенту и сам отдаёт владельцу страницу настройки переписки. В режиме установки без Hermes (`docs/standalone.md`) сервис и его база — весь экземпляр. Этот документ — что сервис делает, какие у него режимы, как им пользоваться без веб-интерфейса и что из написанного проверено. Устройство кода — в `service/README.md`.

Состояние на версию 0.0.7: реализованы ограниченные задачи ответа, посредник источников, раздельное чтение/раскрытие, Telegram-управление и `prepare_only`. Проверки 0.0.6 ниже — исторические; приёмка новых путей описана в `docs/runbooks/validate-pilot.md`. **На эталонном сервере, с настоящим Telegram и с настоящей моделью не проверено ничего** — подробно в разделе «Что ещё не проверено».

Цифры проверок для версии 0.0.6. Автоматические тесты сервиса: 1632 (в версии 0.0.5 было 1413). Тесты плагина: 549 без Hermes (3 пропущены) и 704 в окружении Hermes 0.21.5 с python-telegram-bot 22.8. На Python 3.12 с зависимостями из списка с контрольными суммами (`service/requirements.lock`) тесты сервиса проходили в версии 0.0.3; для версий новее такой прогон делает только CI.

Замеры на стенде разработки, не на эталонном сервере. Импорт: 300 000 сообщений примерно за 30 секунд. Эмбеддинги, контейнер из `compose.yaml`, 2 ядра: `e5-small` — 96 коротких сообщений в секунду, 0,85–1,2 ГБ памяти; `user2-small` — 60 в секунду, 0,17–0,22 ГБ, пик 0,7 ГБ. Фоновый счётчик с паузой по умолчанию пересчитывает 25–30 коротких сообщений в секунду. Качество поиска мерилось только на синтетическом русском наборе из 165 вопросов, намеренно трудных для поиска по словам: ответ в первых десяти результатах — 0,06 у поиска по словам, 0,35 у гибрида с `e5-small`, 0,55 с `user2-small`, разброс ±8 процентных пунктов. Это ориентир для сравнения моделей, а не оценка качества на настоящей переписке; подробно и с оговорками — `docs/search.md`.

Код прошёл независимые проверки — безопасности и стыков между частями; страница настройки — отдельную проверку безопасности 2026-10-07. Замечания исправлены, кроме одного ограничения: оно описано в `docs/architecture.md`, раздел «Открытое ограничение», и из-за него отправка остаётся выключенной. Что нашли проверки и что осталось — `docs/security-review.md`.

## Что где работает

Сервис — один процесс (`shturman serve`) в контейнере `shturman-service`. Он слушает порт 8765 на локальном адресе сервера (наружу порт не открыт) — для Hermes, оператора и туннеля — и, если каталог для него готов, Unix-сокет `/run/shturman-service/proxy.sock` для обратного прокси (Р-76, `docs/deployment.md`, «Сокет для обратного прокси»). В режиме с Hermes обратный прокси ходит к сервису через сокет и отдаёт наружу один префикс — `/shturman-setup/` — и только на отдельном адресе страницы настройки.

| Путь | Кто обращается | Токен | Что можно |
|---|---|---|---|
| `/health` | Проверки | Нет | Только «жив» и версия |
| `/api/*` | Плагин `shturman` в Hermes; оператор командой `shturman call` | `SHTURMAN_API_TOKEN` | Внутренний API: приём бизнес-сообщений, очередь заданий, нажатия кнопок, аккаунты Telegram, импорт, правила отправки, обязательства, люди, страницы, ждущие подтверждения, состояние своего бота, защиты и расшифровки голосовых |
| `/mcp` | Агент Hermes; без Hermes — Codex CLI или Claude Code владельца (`./ops/connect.sh`) | `SHTURMAN_MCP_TOKEN` (в Hermes переменная называется `MCP_SHTURMAN_API_KEY`) | Только чтение архива. Принимаются только запросы POST |
| `/shturman-setup/*` | Владелец в браузере | Нет: вход по одноразовой ссылке (`./ops/setup-link.sh`), дальше — ключ сессии в заголовке; cookie нет | Страница настройки переписки: бот согласований, способ подключения, ключи приложения Telegram, вход в аккаунт, бизнес-режим, выбор чатов, выгрузка; в разделе «Дополнительно» — своя модель (ключ API или подписка ChatGPT) |

Токены разные и не взаимозаменяемы; сервис не запустится, если они совпали или короче 32 знаков. Оба генерирует `./ops/init-env.sh --auto`. Под `/shturman-setup/` токены входом не служат, а маршрутов `/api/*` и `/mcp` там нет. Любой другой путь — 404.

Инструменты архива для агента: `search_messages`, `get_context`, `list_chats`, `get_chat_history`, `find_person`, `list_commitments`, `get_commitment`, `get_person_page`, `search_pages`, `list_projects`, `get_project_page`, `get_owner_profile`, `list_spheres`. Все только читают. Каждый результат помечен сферами своего чата (`spheres`; у проекта — `sphere`), а необязательный параметр `spheres` сужает поиск; по умолчанию ассистент ищет в сфере, о которой разговор, — это правило в описаниях, а не запрет (`docs/spheres.md`). `search_pages` ищет по страницам людей, проектов и профилю; профиль и блоки владельца — слова самого владельца и отдаются без рамки. Чужой текст в ответах стоит в рамке `[untrusted] … [/untrusted]`; исключённые чаты, удалённые сообщения, служебные чаты Telegram и сообщения, скрытые защитой от внедрённых инструкций, не отдаются.

**Модель и бот — через очередь заданий.** Всё, для чего нужна модель, сообщение владельцу или отправка через бизнес-бота, сервис ставит в очередь заданий. Видов заданий шесть:

| Задание | Что делает исполнитель |
|---|---|
| `llm.structured` | Спрашивает модель и возвращает ответ по заданной схеме |
| `llm.text` | Спрашивает модель и возвращает текст |
| `notify.owner` | Отправляет владельцу сообщение, при необходимости с кнопками |
| `notify.edit` | Правит это сообщение: заменяет текст, убирает кнопки |
| `business.send` | Отправляет сообщение от имени владельца через бизнес-бота |
| `hermes.cron` | Только плагин в Hermes (своего исполнителя в сервисе нет): приводит задачи утренней сводки и обзора недели к выбору владельца штатными функциями Hermes или только сообщает, что заведено (Р-95, «Сводки по расписанию» ниже). Без Hermes его никто не забирает — гаснет за час |

Исполнителей два, и кто из них выполняет задание, решают настройки сервиса:

| Что задано в `.env` | Задания модели (`llm.*`) | Сообщения владельцу и кнопки (`notify.*`) | Бизнес-сообщения и `business.send` |
|---|---|---|---|
| Ничего — как в 0.0.3 | Плагин в Hermes, модель Hermes | Плагин в Hermes, управляющий чат | Плагин в Hermes, бот Hermes |
| `SHTURMAN_LLM_API_KEY` и `SHTURMAN_LLM_MODEL` | Сам сервис, по своему ключу | Как в строке выше | Как в строке выше |
| `SHTURMAN_BOT_TOKEN` | Как задано для модели | Сам сервис, бот согласований | Сам сервис, бот согласований |

Задание, которое выполняет сам сервис, плагину не выдаётся, и закрыть его по HTTP нельзя. Если исполнителя для задания нет — Hermes не установлен, а свой бот или своя модель не настроены, — задание ждёт и закрывается как невостребованное.

Старый плагин без своего бота может пересылать сообщения бизнес-режима и данные кнопок, но HTTP-заявление об ID нажавшего не создаёт полномочия владельца. Для защищённых решений нужен независимый бот сервиса или отдельный вход на страницу настройки. Запрос и результат модельного задания ответа очищаются при обработке, включая устаревший результат; прочие завершённые задания очищаются через десять минут. Задание, которое никто не забрал, закрывается как неудачное (уведомление и запрос к модели — через сутки, правка сообщения и запрос текста — через час).

## Страница настройки переписки

Единственное, что сервис отдаёт человеку, а не плагину и не агенту. Что владелец на ней делает и как она выглядит с его стороны — `docs/setup.md`; здесь — как она устроена.

**Что на ней.** Вверху — «Частые вопросы». Шаг 1 — «Бот согласований» (токен, привязка владельца); пока бот не сохранён и владелец не привязан, остальные шаги закрыты. Шаг 2 — выбор способа подключения (решение Р-62):

- `own`, «Через ваш аккаунт»: «Ключи приложения Telegram», «Вход в ваш аккаунт Telegram» (основной аккаунт владельца по QR-коду, только на чтение), «Какие чаты читать»;
- `staff`, «Через бота и помощника»: «Личные чаты: бизнес-режим Telegram» (к боту согласований), затем по желанию для групп — «Ключи приложения Telegram», «Группы: аккаунт помощника» (роль `assistant`), «Какие группы читать».

В обоих способах последний шаг — «Прошлая переписка из Telegram Desktop», необязательный. Выбор хранится в таблице `setup_state` (ключ `scenario`) и влияет только на то, какие шаги показывает страница: подключённое не отключается; шаг другого способа, где уже что-то подключено, виден без номера и с пояснением. Внутренний API выбор не читает. Состояние страницы (`GET /shturman-setup/api/state`, поле `scenario`) несёт выбранный способ (`chosen`) и подсказку по уже подключённому (`suggested`: есть сессия основного аккаунта — `own`, есть бизнес-режим или аккаунт помощника — `staff`). Пока способ не выбран, подключённое раньше видно без номера с просьбой выбрать способ. Выбор меняет маршрут страницы `PUT /shturman-setup/api/scenario` с телом `{"scenario": "own"}` или `{"scenario": "staff"}`; в журнал действий он попадает строкой «Выбран способ подключения» (`setup.scenario`) — в список важных, рядом со входами, ключами и аккаунтами. Под шагами — карточка «Аккаунты в архиве без подключения». В раскрывающемся блоке «Дополнительно» — «Своя модель сервиса», «Что собрано» и «Журнал действий». У каждого шага — строка «Что это даст» и свёрнутые «Вопросы».

**Уведомления, наблюдатель, повтор после сбоя (Р-84).** Карточки «Уведомления» и «Наблюдатель» — в блоке «Повседневное» под «Сферами», не шаги; карточка «Повторить то, что не получилось» — перед журналом действий, видна, только когда есть что повторить или недавно повторяли. | Маршрут | Что делает |

| `POST /shturman-setup/api/memory/pending/projects/{id}` | `{accept}` — согласие через `apply_owner(projects.accept)`, отказ — `decide_project_proposal`; решённое — 409 |
| `POST /shturman-setup/api/memory/pending/owner-facts/{id}` | `{accept, fingerprint}` — `facts.decide_owner_fact` в контексте владельца с отпечатком показанного (изменилось — 409 `changed_meanwhile`); решённое — 409 |
| `POST /shturman-setup/api/memory/pending/pages/{person_id}` | `{accept}` — согласие через `apply_owner(pages.accept)`, отказ — сразу; решённое — 409 |
| `POST /shturman-setup/api/memory/pending/commitments/{id}` | `{accept, fingerprint}` — принятие через `apply_owner(commitments.decide)` с отпечатком показанного (изменилось — 409 `changed_meanwhile`), отказ — `commitments.reject` от владельца; решённое — 409 |
| `PUT /shturman-setup/api/memory/projects/{id}/sphere` | `{sphere_id}` (номер или `null`) — сфера проекта (Р-82), сразу; журнал `sphere.project` |
| `GET /shturman-setup/api/spheres` | Сферы (название, описание, порядок, сколько чатов и проектов, папки) и предложения связанных папок (`proposals`) |
| `POST /shturman-setup/api/spheres`, `PUT …/spheres/{id}`, `DELETE …/spheres/{id}`, `PUT …/spheres/order` | Завести `{title, description?}`, изменить, удалить (= снять с чатов и проектов), порядок `{ids}` |
| `GET`, `POST /shturman-setup/api/spheres/{id}/chats` | Чаты сферы; `{account_id, chats, add}` — добавить или убрать |
| `PUT /shturman-setup/api/spheres/chat` | `{account_id, peer_class, tg_id, sphere_ids}` — все сферы одного чата |
| `GET /shturman-setup/api/spheres/folders`, `POST …/spheres/folders/make`, `POST …/spheres/{id}/folders`, `POST …/spheres/{id}/proposals` | Папки Telegram; «Сделать сферу из папки» `{account_id, folder_id, sphere_id?}`; «Связать папку» `{account_id, folder_id, link}`; решение по предложенным `{account_id, folder_id, accept, chats?}` |
| `GET /shturman-setup/api/tg/accounts/{id}/sections`, `POST …/bulk` | Раскладка списка чатов; «Включить все» `{section, enabled: true, months?}` (исключённые и служебные пропускаются) и «Выключить все» в разделе |

Внутренний API эти маршруты не меняют: через `/api/pages…`, `/api/commitments…`, `/api/projects…`, `/api/facts…` и `/api/owner/profile…` те же решения по-прежнему ждут нажатия в боте. Журнал — `memory.owner_block`, `memory.profile_block`, `memory.owner_fact_accept` (в списке важных), `memory.page_accept`, `memory.page_reject`, `memory.commitment_accept`, `memory.commitment_reject`, `memory.project_create`, `memory.project_chats`, `memory.project_archive`, `memory.project_accept`, `memory.project_reject`, `memory.fact_retract`, `memory.owner_fact_reject`; в записи — номера и числа, без имён, названий и текста.

**Отдельный вход.** Страница — не ещё один клиент внутреннего API: её маршруты (`/shturman-setup/api/…`) зовут функции сервиса напрямую и не принимают его токены.

| Что | Как |
|---|---|
| Ссылка входа | `./ops/setup-link.sh` (в контейнере — `shturman setup-link`): случайные 256 бит, в базе только хеш, 30 минут, один раз, новая отменяет прежнюю. Создаётся прямой записью в базу; маршрута для неё нет — токен внутреннего API есть у ассистента |
| Вход по ссылке | Завершает все прежние сессии страницы, гасит ждущие коды и снимает блокировку входа по коду. Неверная ссылка вход не закрывает (перебирать 256 бит бессмысленно); отказ отвечает с небольшой задержкой |
| Сессия | Ключ сессии (256 бит, в базе — хеш) сервис отдаёт один раз, в ответе на вход; страница хранит его в `localStorage` своего адреса и присылает в заголовке `X-Shturman-Session` с каждым запросом, в том числе с загрузкой выгрузки. Cookie страница не ставит и не читает — кроме одной cookie попытки входа по коду (строка «Вход по коду» ниже); любой другой заголовок `Set-Cookie` вырезается из ответа под префиксом. Сессия живёт ровно 7 дней от входа: обращения срок не продлевают, срока «по бездействию» нет |
| Источник запроса | Маршруты `/shturman-setup/api/…` принимают запрос, только если его сделала сама страница: `Sec-Fetch-Site`, когда он есть, обязан быть `same-origin` (`same-site` — соседний порт, то есть дашборд, `cross-site` и `none` — отказ 403); `Origin`, когда он есть, обязан быть адресом страницы, а у изменяющих запросов он обязателен, как и собственный заголовок `X-Shturman-Setup: 1`. Проверка идёт раньше проверки ключа. Отдельного значения против подделки запросов (CSRF) нет: заголовок с ключом браузер сам ни к какому запросу не приставляет |
| Выход | «Выйти» — эта сессия; «Выйти на всех устройствах» и `./ops/logout-all.sh` (в контейнере — `shturman setup-logout-all`) — все сессии и ещё не использованная ссылка входа |
| Вход по коду из бота (Р-88) | Кнопка «Получить код в боте» — только когда бот настроен, владелец привязан и вход по коду включён (у своего бота — по умолчанию; у бота от посредника — выключен, пока владелец не включит и не подтвердит в боте). Код — 6 цифр, 5 минут, один раз и **только в браузере, который его запросил**: `POST …/api/login/code/request` ставит cookie попытки `__Secure-shturman-code` (`HttpOnly; Secure; SameSite=Strict`, путь `/shturman-setup/api/login/code`, без `Domain`, 5 минут) со случайными 256 битами; в базе (`setup_codes`) — SHA-256 попытки и HMAC кода ключом из каталога данных. Две cookie с этим именем — не попытка. Новый запрос того же браузера гасит его прежний код. Не больше трёх запросов за 15 минут на всех; 5 неверных кодов гасят код и закрывают вход по коду на 1, 5, 15, 60 минут, 6 часов, сутки (счётчик общий, удачный вход его сбрасывает); владельцу о паузе — одно сообщение за период. Ответ на запрос одинаков, ушёл код или некому его отправить: недоставленный код не срабатывает. Сообщение в боте: код, когда, с какого адреса (последний адрес из `X-Forwarded-For` прокси — только для текста, не для решений, в базу не пишется) и какой браузер словами, «Никому не сообщайте код, даже ассистенту», кнопки «Это не я» (гасит все ждущие коды, журнал `login.code_denied`) и «Выйти на всех устройствах». С Hermes на сервере код принимается **только через сокет обратного прокси** (Р-76): через порт 8765 его мог бы запросить и ввести процесс ассистента в сети хоста — отказ 403 `port`. Сессия — как по ссылке; в журнале `login.code` — «по коду из бота», у `login.link` — «по ссылке». `./ops/doctor.sh` — строка `setup-code-login` (включён ли, входов за 7 суток, без кодов). Первый вход — всегда по ссылке: бот заводится на самой странице |

**Отдельный адрес.** Сервис получает два адреса: свой внешний адрес страницы (`SHTURMAN_SETUP_ORIGIN` — схема, имя и порт; на сервере это строка `SHTURMAN_SETUP_URL` в `.env`) и адрес дашборда Hermes (`SHTURMAN_DASHBOARD_ORIGIN`) — только чтобы сверить, что они разные. Почему они обязаны быть разными — `docs/architecture.md`, «Почему у страницы настройки свой адрес».

| Положение | Что делает сервис | `GET /api/status`, объект `setup` |
|---|---|---|
| Адрес страницы задан и не совпадает с адресом дашборда | Отдаёт страницу по этому адресу и по локальным именам | `enabled: true`, `origin_set: true`, `origin: "https://имя:8443"`, `reason: null` |
| Адрес страницы не задан | Отдаёт страницу только по локальным именам (`127.0.0.1:8765`, `localhost:8765`): с сервера и через туннель SSH | `enabled: true`, `origin_set: false`, `origin: null`, `reason: "no_origin"` |
| Адрес страницы совпал с адресом дашборда | Запускается и пишет об этом в журнал. По внешнему адресу страницу не отдаёт (отказ 421, как на любое чужое имя); по локальным именам — отдаёт, как во второй строке | `enabled: false`, `origin_set: false`, `origin: null`, `reason: "same_origin"` |

Поля объекта `setup`, как их отдаёт сервис (проверено на работающем стеке во всех трёх положениях): `enabled` — модуль страницы запущен и её адрес не совпал с адресом дашборда (при совпавших адресах `false`, хотя по локальным именам страница отвечает); `origin_set` — страница действительно отдаётся по внешнему адресу, а не «переменная задана»; `origin` — этот внешний адрес либо `null`; `reason` — почему внешнего адреса нет: `null`, `"no_origin"` или `"same_origin"`; `tg_keys` — заданы ли ключи приложения Telegram; `accounts` — число подключённых аккаунтов; `own_bot`, `owner_bound`, `business_connected`, `own_model` — настроены ли бот согласований, привязан ли к нему владелец, подключён ли к нему бизнес-режим, настроена ли своя модель; `socket` — состояние Unix-сокета для прокси: `listening`, `off` (не задан), `dir_missing`, `dir_owner`, `dir_mode` (каталога нет или он не такой — сервис слушает только порт), `not_socket`, `error`. Только признаки, числа и коды. `./ops/doctor.sh` и шаг мастера «Переписка» читают именно эти поля; сервис прежней сборки, у которого в объекте нет `origin` и `reason`, они считают устаревшим.

Адреса сравниваются как их сравнивает браузер — схема, имя и порт: регистр, обычный порт (443 для `https`) и точка в конце имени адрес другим не делают. У адреса дашборда путь и всё после него отбрасываются; у адреса страницы путь запрещён. **Неразборчивое значение любого из двух адресов** — без `http://` или `https://`, с именем пользователя, с неверным портом, а у адреса страницы ещё и с путём — **останавливает сервис при запуске**: в журнале контейнера остаётся строка вида `SHTURMAN_DASHBOARD_ORIGIN: нужен адрес вида …` (в `.env` это строки `SHTURMAN_PUBLIC_URL` и `SHTURMAN_SETUP_URL`). Очевидно неверную запись `./ops/up.sh` останавливает раньше, до перезапуска.

Запрос с именем узла не из этого перечня получает отказ 421: так страницу нельзя открыть под подставным именем. Заголовок `Host` должен дойти до сервиса как есть, вместе с портом; заголовкам `X-Forwarded-*` сервис не верит и ни одно решение по ним не принимает. Заголовок-метку `X-Shturman-Setup-Page: 1` сервис ставит на один ответ — на саму страницу, `GET /shturman-setup/`; на её файлах (`static/…`), на ответах её API и на отказах метки нет. По метке `./ops/doctor.sh` отличает ответ сервиса от чужого. Все ответы под префиксом, включая отказы, идут со строгой политикой содержимого: скрипты и стили только свои, запросы только к себе, показ в рамке запрещён; заголовков CORS страница не отдаёт, запрос файла service worker'а получает отказ.

**Значения, введённые на странице.** Ключи приложения Telegram, токен бота согласований, ключ, адрес и имя своей модели лежат в файле `data/shturman/setup/secrets.json` (права 600), а не в базе: каталог данных сервиса контейнеру Hermes не подключён, и ни один маршрут внутреннего API этот файл не читает. Обратно страница получает только «задано / не задано». Значение из окружения сервиса (`.env`) главнее файла: страница показывает его как заданное на сервере и менять не даёт; ключи приложения Telegram в этом смысле — пара: задан в окружении один — заперты оба. Значения применяются без перезапуска сервиса. Перед сохранением токен бота проверяется запросом к Telegram, а ключ модели — пробным вопросом модели. Вход по подписке ChatGPT лежит отдельно — `data/shturman/setup/chatgpt.json` и `chatgpt-host` (раздел «Своя модель по подписке ChatGPT»); страница получает из него только состояние, почту учётной записи и модель.

«Задано в окружении» сервис понимает буквально — переменная не пуста. Поэтому `compose.yaml` значений по умолчанию этим переменным не подставляет: адрес модели (`SHTURMAN_LLM_BASE_URL`) контейнер получает, только если строка есть в `.env`. До исправления в этой версии `compose.yaml` всегда передавал адрес по умолчанию, и под Docker поле адреса на странице было закрыто — это нашла первая проверка страницы в образе.

**Адрес своей модели.** Адрес API модели, введённый на странице, проходит фильтр (`service/src/shturman/netguard.py`): иначе тот, кто завладел сессией страницы, направил бы запросы сервиса с ключом модели на внутренний адрес.

- По записи адреса, до всякой сети: только `https`; без имени пользователя и пароля, без строки запроса и фрагмента; узел — не `localhost`, не имя без точки (так называются соседние контейнеры), не имя внутренней зоны (`.local`, `.internal`, `.lan`, `.home.arpa`, `.test` и подобные) и не IP-адрес закрытой сети. Закрытые сети: адрес самого узла (loopback), частные (10/8, 172.16/12, 192.168/16, fc00::/7), link-local (169.254/16 — там же метаданные облаков, fe80::/10), CGNAT (100.64/10), multicast, зарезервированные и неуказанные; адреса IPv6 с вложенным адресом IPv4 (IPv4-mapped, 6to4, Teredo, NAT64) проверяются по вложенному. Записи адреса IPv4 одним числом, восьмеричные и шестнадцатеричные закрыты всегда.
- В момент каждого запроса: имя разрешается заново, каждый полученный адрес сверяется с тем же перечнем (один закрытый адрес закрывает имя целиком), и соединение идёт на проверенный адрес, а не на имя, — подмена записи DNS между проверкой и соединением ничего не даёт. Имя не разрешилось — запрос не уходит. По перенаправлениям клиент модели не ходит.
- **Оговорка про исходящий прокси.** Если `EGRESS_PROXY_URL` — прокси HTTP (`http://…` или `https://…`), сервис проверяет адреса имени так же, но в запросе к прокси остаётся имя: его второй раз разрешает сам прокси, и от подмены DNS в этот промежуток защищает уже он. С прокси SOCKS соединение идёт на проверенный адрес. Это остаточный риск.
- При смене адреса ключ вводится заново: сохранённый ключ на новый адрес не уходит.
- Адрес по умолчанию (`https://api.openai.com/v1`) этим фильтром не ограничивается.
- **Адрес из окружения** (`SHTURMAN_LLM_BASE_URL` в `.env`) фильтром не ограничен вовсе — его задаёт оператор сервера, и там может стоять локальная модель, в том числе по `http` и во внутренней сети. Со страницы такой адрес не меняется: поле показывает его и закрыто.

**Действие со страницы — действие самого владельца.** Оно применяется сразу, без карточки в боте: карточка защищает от держателя токена внутреннего API, а сюда входят по ссылке, которую можно получить только на сервере. Каждое изменение пишется в журнал действий (таблица `setup_audit`): когда, что, итог — без значений, названий чатов и имён.

**Отправку страница не включает.** Токен бота согласований, введённый на странице, сам по себе отправку не включает: для неё нужны и строка `SHTURMAN_SENDING=on`, и токен бота именно в `.env` (раздел «Отправка выключена»).

**Что знает о странице плагин в Hermes.** Только объект `setup` из `GET /api/status`: признаки и числа — включена ли страница, её адрес, причина его отсутствия, заданы ли ключи приложения, сколько аккаунтов, настроены ли бот согласований и своя модель, подключён ли бизнес-режим. Ни значений, ни имён, ни ссылок входа в нём нет. Мастер показывает из этого три строки и кнопку. Через проход дашборда к сервису вход в аккаунт Telegram, управление аккаунтами, выбор чатов и импорт выгрузки недоступны (`plugins/shturman/shturman_core/service_routes.py`, перечень `SETUP_PAGE_ONLY`).

Во внутреннем API эти маршруты остаются — ими пользуется оператор командой `shturman call` (раздел «Как пользоваться без веб-интерфейса»), и они же доступны держателю токена внутреннего API; что из этого следует, сказано в `docs/architecture.md`, «Открытое ограничение».

### Mini App бота согласований

Что это для владельца и что оно умеет — `docs/miniapp.md`; решения — Р-72…Р-75, Р-80. Здесь — устройство. Приложение живёт под префиксом страницы настройки, на её адресе (не на адресе дашборда), со своей сессией и своей, более узкой ролью (`setup_page/miniapp.py`, `approvals.py`, `initdata.py`; файлы — `static/app.html`, `app.js`, `app.css`).

| Маршрут | Что делает |
|---|---|
| `GET /shturman-setup/app/` | Приложение. Данных в нём нет. Единственный ответ под префиксом, который разрешено показать в рамке, — только у `https://web.telegram.org` (`frame-ancestors`, без `X-Frame-Options`); его файлы, API и остальная страница — как прежде, без рамки |
| `POST /shturman-setup/api/app/login` | `{init_data}` — строка `Telegram.WebApp.initData`. Подпись — HMAC-SHA-256 по правилам Telegram с токеном бота согласований, `auth_date` не старше 10 минут, пользователь — привязанный к этому боту владелец; по одним данным входа — одна сессия. Любой отказ — 401 `app_login_failed` с одним и тем же текстом. Ответ на вход — единственный, где есть ключ сессии |

**Сессия приложения** — таблица `miniapp_sessions` (миграция `0030_miniapp.sql`): ключ 256 бит, в базе — хеш; заголовок `X-Shturman-App`, cookie нет; 30 минут без обращений и не дольше 4 часов от входа; любая привязка или отвязка владельца (`bridge.set_owner`, `clear_owner`) и смена токена бота (`executor/service.py`) завершают все сессии приложения; пока опрос бота получает 409 или у бота включён webhook (так выглядит и общий токен с ботом Hermes), вход закрыт и сессии не действуют. Ключ сессии страницы (`X-Shturman-Session`) маршруты приложения не принимают, ключ приложения — маршруты страницы; токены внутреннего API и архива не годятся ни туда, ни туда. «Выйти на всех устройствах» и `./ops/logout-all.sh` завершают и сессии приложения. Источник запроса проверяется так же, как у страницы (`Sec-Fetch-Site`, `Origin`, `X-Shturman-Setup: 1`).

**Кнопка меню.** Бот сам ставит в личном чате владельца кнопку «Штурман» (`setChatMenuButton`, `executor/menu_button.py`) — при запуске, после привязки и раз в 10 минут сверяет; при смене владельца прежнему возвращает обычную кнопку; без внешнего адреса страницы по `https` кнопки нет. Состояние — поле `bot.menu_button` в `GET /api/executor/status` (`set`, `no_address`, `no_owner`, `failed`), строка `miniapp` в `./ops/doctor.sh` и строка в `shturman bot-status`.

С Р-94 у каждого пункта списка согласований есть `group` — раздел экрана: `answers` («Ответы»: черновики, вопросы ассистента), `permissions` («Разрешения»: просьбы прочитать, подтверждения действий), `commitments` («Договорённости»), `memory` («Память»: факты о вас, страницы о людях, проекты), `guard` («Защита»: скрытые сообщения); в ответе — `groups` (ключ, название, сколько пунктов и сколько ещё придёт сводкой). Кнопки карточек и их данные не менялись.

Список согласований (`GET …/app/approvals`) с Р-87 несёт ещё `halt` (остановлен ли, с какого времени), `setup_url` — адрес «Настроек Штурмана» для кнопки «Открыть настройки в браузере» (только `https`, без ключа: там вход по коду или по ссылке; открывается через `web_app_open_link`) — и `mode` (способ работы). У карточки «Вопрос ассистента» вместо кнопки «Ответить» — поле `answer` (`ref`, вопрос, предел 2000 знаков). Подтверждения `halt.resume` и `setup.code_login` приходят без кнопок, с пометкой «Подтвердить можно только кнопкой под этой карточкой в боте согласований».

**Журнал действий:** `app.login`, `app.decide` и `app.answer` (в списке важных), `app.login_failed` (не чаще раза в минуту, с кодом причины; повтор уже использованных данных входа — всегда, и владельцу уходит сообщение в бот согласований), `app.logout`; в подробностях `app.decide` — вид и номер пункта и подпись кнопки, без имён и текстов.

## Свой бот согласований и своя модель

**Бот согласований — первый шаг страницы настройки переписки, в обоих режимах установки** (решение Р-62; прежнее решение Р-58 откладывало его до включения отправки). Без него запросы ассистента, которые должен подтвердить владелец, — принять найденное обязательство, объединить людей, записать блок владельца на странице памяти, включить чтение чата, импорт — отклоняются с кодом `owner_unknown` (`docs/architecture.md`, «Без своего бота согласований»). Бота создаёт владелец у @BotFather и сам вводит токен на странице; агент бота не заводит и токена не видит. Своя модель по-прежнему по желанию.

Зачем. Пока задания выполняет плагин в Hermes, нажатие владельца проходит через процесс, где у ассистента есть терминал и токен внутреннего API: внедрённая в чужое сообщение инструкция может прислать поддельное нажатие (`docs/architecture.md`, «Открытое ограничение»). Свой бот — отдельный бот от @BotFather, токен которого есть только в контейнере сервиса. Нажатие приходит сервису от Telegram напрямую.

Что бот делает:

- присылает владельцу карточки с кнопками: найденные обязательства, предложения страниц, срабатывания наблюдателя, черновики на согласование, подтверждения действий, уведомления защиты;
- принимает нажатия и считает владельцем только того, кто привязался по одноразовой ссылке `./ops/bot-bind.sh` (15 минут, один раз; порядок — `docs/standalone.md`, «Привязка владельца к боту»);
- принимает обновления бизнес-режима, если бизнес-режим подключён к нему, и отправляет от имени владельца через это подключение;
- принимает проверенные команды привязанного владельца только в личном чате: меню, состояние, правила, задачи ответа, источники и отзыв; произвольный разговор остаётся в полном Hermes. На свободный текст показывает подсказку меню, посторонним не даёт управление;
- ставит в чате владельца кнопку меню «Штурман», которая открывает Mini App с теми же решениями (раздел «Mini App бота согласований», `docs/miniapp.md`) — только когда у страницы настройки есть внешний адрес `https`.

**Как получить бота** (решение Р-77, `docs/approvals-bot.md`): у каждого владельца свой бот; общий бот на всех отклонён. На странице — два пути: пошагово у @BotFather (по умолчанию, ни от кого не зависит) или «в одно нажатие» через бот-менеджер посредника (`SHTURMAN_BOT_MANAGER_API`): сервис просит у посредника пару, владелец подтверждает создание в Telegram, сервис сам забирает токен по секрету пары и применяет тем же путём, что вставленный (`setup_page/bot_setup.apply_token`). Держатель посредника при этом технически может получить токен такого бота — владельцу это говорится до кнопки. У бота, созданного в одно нажатие, владельцем может стать только аккаунт-создатель. Если владелец изменил адрес бота в окне создания, страница (с посредником 0.5.0) показывает ссылку на бот-менеджер с кодом привязки: «Старт» в том же аккаунте — и посредник привязывает бота, созданного этим аккаунтом (Р-78). Как создан бот — `GET /api/executor/status` → `bot.created_via` (`manual` | `managed` | `null`), строка `approvals-origin` в `./ops/doctor.sh`, `shturman bot-status`.

Что меняется для плагина в Hermes, когда свой бот включён (`GET /api/status` → `"own_bot": true`):

- маршруты `PUT` и `DELETE /api/owner`, `POST /api/callbacks/telegram` и `/api/ingest/business/*` отвечают 403 с кодом `own_bot`: привязку владельца, нажатия и бизнес-поток ведёт бот сервиса;
- плагин узнаёт о режиме из `GET /api/status` и из этого отказа и уходит в спокойный режим: не привязывает владельца, не передаёт нажатия кнопок `sh:`, не пересылает обновления бизнес-режима. В журнале шлюза — одна строка при входе в режим и одна при выходе, без повторов и предупреждений;
- состояние плагин переспрашивает раз в 5 минут. Выключение своего бота он замечает с задержкой до 5 минут и после этого передаёт сервису владельца заново;
- нажатие кнопки на старой карточке в чате Hermes получает ответ «Теперь согласования приходят в отдельного бота»; карточка не меняется;
- в состоянии моста появилось поле `own_bot`: `true` — согласования ведёт бот сервиса, `false` — плагин, `null` — неизвестно (исполнитель плагина стоит или сервис прежней версии). Нулевые счётчики `forwarded_*` при `own_bot: true` — норма. `./ops/doctor.sh` показывает это строкой `plugin-own-bot`;
- защита от сообщений бизнес-режима в плагине от этого не зависит: пока официальный плагин бизнес-режима не загружен, сообщения бизнес-режима до ядра Hermes не доходят.

**Бизнес-режим подключается только к боту согласований.** Бота Hermes в бизнес-режиме не подключают вовсе (решение Р-59). Одного подключения хватает: сервис принимает бизнес-сообщения только через своего бота. Порядок — `docs/standalone.md`, «Бизнес-режим Telegram со своим ботом». Если на экземпляре прежней схемы бизнес-режим уже подключён к боту Hermes — `UPGRADING.md`, раздел «0.0.5 → 0.0.6».

Своя модель — ключ и имя модели у провайдера с API, совместимым с OpenAI, **либо подписка ChatGPT владельца** (ниже). Действует один способ из двух. Для отдельных задач можно назначить другую модель (`SHTURMAN_LLM_MODEL_EXTRACT`, `_REPLY`, `_WATCH`) — при любом способе. Ключ, введённый на странице настройки переписки, проверяется пробным вопросом модели до сохранения. Ключ, заданный в `.env`, проверяется только первым настоящим обращением, то есть ночной обработкой; отдельной команды проверки нет.

### Своя модель по подписке ChatGPT

Если у владельца есть подписка ChatGPT Plus или Pro, сервис может обращаться к модели за её счёт вместо ключа API. Это официальный способ OpenAI «Sign in with ChatGPT» для открытых программ, которые человек ставит себе сам; с 29 сентября 2026 он в предварительном режиме (документация — `developers.openai.com/siwc/token-sharing-open-source`, сверено 8 октября 2026). Решение и риски — `docs/decisions.md`, Р-64. Если ассистент работает через Hermes, подписку для него подключают в мастере Hermes; здесь — модель самого сервиса.

**Как подключить.** Страница настройки переписки, «Дополнительно» → «Своя модель сервиса» → «Подписка ChatGPT» → «Войти через ChatGPT». Дальше:

1. В новой вкладке открывается вход ChatGPT. Владелец входит и разрешает «Штурману» доступ к подписке.
2. Вкладка пытается открыть адрес `http://127.0.0.1:1455/auth/callback?…` и показывает ошибку «не удаётся открыть страницу». Так и должно быть: этот адрес ведёт на компьютер владельца, а сервис работает на сервере.
3. Владелец копирует весь адрес из адресной строки этой вкладки и вставляет его на странице. Попытка действует 10 минут; адрес одноразовый.

Сервис меняет код из адреса на токены, проверяет ID token (издатель, получатель, срок, `nonce`, подпись по ключам OpenAI) и разрешение `chatgpt.tokens.use.direct`, получает список моделей этой учётной записи и задаёт первой из них пробный вопрос. Только после этого подписка становится своей моделью сервиса; модель можно сменить списком на странице. Страница показывает «Используется подписка ChatGPT», учётную запись, модель и ссылку «Лимиты» (`https://chatgpt.com/settings/usage`).

**Один способ за раз.** Включение подписки удаляет ключ API, введённый на странице, — страница перед этим спрашивает. Сохранение ключа API выходит из подписки: сессия у OpenAI отзывается. Если ключ модели задан в `.env` (`SHTURMAN_LLM_API_KEY`), подписку со страницы включить нельзя: модель выбрана на сервере. Имя модели из `SHTURMAN_LLM_MODEL` к подписке не применяется — у подписки свой список моделей.

**Где лежит.** `data/shturman/setup/chatgpt.json` — почта, `sub`, выданный OpenAI номер программы (`client_id`), токены, срок, права, модель (права файла 600, каталог 700, запись через временный файл); `data/shturman/setup/chatgpt-host` — постоянный номер этого сервера для OpenAI (`ext_agent_host_id`, `urn:uuid:…`), он переживает выход. Токены не попадают ни в ответы страницы, ни во внутренний API, ни в журнал. Вводит всё это только владелец, в своём браузере; агент вход не открывает и вставленного адреса не видит (`AGENTS.md`).

**Токены.** Ключ доступа живёт час, ключ обновления — 30 дней и меняется при каждом обновлении. Сервис обновляет доступ сам, когда до конца остаётся меньше пяти минут, по одному обновлению за раз; новый ключ обновления записывается на диск раньше, чем используется новый ключ доступа. Если сервер выключен дольше 30 дней, вход придётся повторить.

**Что видно и что происходит при отказах.**

| Состояние на странице | Когда | Что делает сервис |
|---|---|---|
| Используется подписка ChatGPT | Всё в порядке | Задания модели выполняются |
| Лимит подписки исчерпан | OpenAI ответил `subscription_sharing_usage_limit_exceeded` (лимит общий с обычной работой владельца в ChatGPT; у Plus — пятичасовой) | 30 минут не обращается к модели; задания ждут в очереди, их попытки не тратятся |
| Нужно войти заново | Обновление отвергнуто (`invalid_grant`, `refresh_token_expired` и подобные) или доступ отозван в настройках ChatGPT | Токены стираются, `client_id` и номер сервера остаются; задания ждут повторного входа (не дольше срока ожидания в очереди — сутки) |
| Нет доступа | 403: тариф или рабочее пространство не разрешают, страна сервера не обслуживается | Задание не выполняется; час сервис к модели не обращается и вход не повторяет |
| — | 503 и другие временные сбои | Повтор с паузой; токены не трогаются |

`./ops/doctor.sh` показывает те же состояния строкой `model` (без почты и токенов); `GET /api/executor/status` — поля `way` (`api_key` или `subscription`) и `subscription` (`ok`, `limit`, `relogin`, `denied`).

**Ограничения предварительной версии.** Запросы — только `POST https://api.openai.com/v1/responses`, с `store: false` и потоком (`stream: true`); предел длины ответа задания (`max_tokens`) на этом пути не передаётся. «JSON по схеме» сначала просится строгой схемой (`text.format`); если путь подписки её не принимает, схема остаётся в тексте указаний, как при ключе API, и это запоминается до перезапуска. Картинки и файлы клиент подписки умеет передавать (`input_image`, `input_file`); задания с вложениями появятся отдельно.

**Выход.** Кнопка «Выйти из подписки»: сессия отзывается у OpenAI, токены стираются, своя модель выключается. Если OpenAI отзыв не подтвердил, страница так и говорит — тогда доступ отключают в настройках ChatGPT. «Войти другой учётной записью» регистрирует «Штурмана» заново.

Не проверено: всё выше — на настоящем OpenAI. Проверено тестами с подставным OpenAI (вход, вставка адреса, обмен, проверка ID token и подписи, обновление и его гонки, отказы, поток событий, схема и её отказ, вложения) и браузерным сценарием страницы.

Состояние — `docker exec shturman-service shturman bot-status` и строки `approvals-bot`, `approvals-owner`, `approvals-business`, `model` в `./ops/doctor.sh`: только признаки, счётчики и коды неполадок, без токена, ключа и имён.

Токен бота и ключ модели вводит владелец: на странице настройки переписки — токен бота и привязка на шаге 1, ключ модели или вход по подписке ChatGPT в разделе «Дополнительно» (значения применяются сразу, перезапуск не нужен), либо в своём терминале — `./ops/init-env.sh`, скрытым вводом, затем `./ops/up.sh`. Агент этого не делает (`AGENTS.md`). Для отправки токен бота должен быть задан именно в `.env`.

Что плагин добавляет агенту поверх архива:

| Что | Имя | Назначение |
|---|---|---|
| Инструмент | `shturman_draft_message` | Создать черновик сообщения. Ничего не отправляет |
| Инструмент | `shturman_commitments` | Посмотреть обязательства |
| Инструмент | `shturman_commitment_update` | Закрыть, отменить, открыть заново, перенести срок. Принять или отклонить предложение агент не может — это кнопка владельца |
| Инструмент | `shturman_people` | Найти человека, посмотреть карточку, добавить алиас |
| Скилл | `shturman:morning-brief` | Утренняя сводка |
| Скилл | `shturman:weekly-review` | Обзор недели |

Задачи по расписанию для двух скиллов заводит адрес плагина `POST /api/plugins/shturman/cron/install` (по умолчанию сводка в 08:27 каждый день, обзор в 17:47 по пятницам) — в мастере Hermes; дальше владелец меняет их без терминала (ниже, «Сводки по расписанию»). Время — по поясу `SHTURMAN_TIMEZONE`: если в `config.yaml` Hermes пояса нет или он другой, адрес записывает его туда (`hermes config set timezone`) и в ответе в `timezone_warning` просит запустить `./ops/up.sh` — шлюз Hermes читает пояс только при запуске (Р-90). `GET /api/plugins/shturman/cron` показывает пояс шлюза (`timezone`), ожидаемый (`timezone_expected`) и их сравнение (`timezone_state`).

**Сводки по расписанию (Р-95, находка Х3).** Включить и выключить утреннюю сводку и обзор недели, выбрать время и день владелец может в «Настройках Штурмана» (карточка «Утренняя сводка и обзор недели») и во вкладке «🔔» приложения «Штурман». Сервис хранит выбор (`settings.summaries.desired`: вкл, `ЧЧ:ММ`, день недели 0–6 как в cron, номер версии) и ставит задание `hermes.cron`; плагин в процессе шлюза Hermes забирает его (своя дорожка исполнителя, опрос раз в 20 с) и штатными функциями Hermes приводит задачи `shturman:morning-brief` и `shturman:weekly-review` к выбранному: нет задачи — создаёт (`create_job_with_scheduler_registration`, если задан чат владельца в Hermes, иначе `no_home_channel`), другое время — `cronjob(action="update", schedule=…)` (как `hermes cron edit --schedule`), выключить — `pause`, включить — `resume`; чужие задачи не трогает. Затем отвечает, что в Hermes на самом деле (есть ли задача, включена ли, время, день, следующий запуск по поясу шлюза из `config.yaml`, Р-90) — сервис хранит ответ в `settings.summaries.actual`. Раз в час сервис просит только «посмотреть» (`apply: false`), при запуске — тоже: так время следующей сводки свежее, а правка в самом Hermes видна как расхождение (`drift`) и молча не перезаписывается — владелец нажимает «Применить снова». Пока владелец ничего не выбрал, плагин ничего не меняет. Блок виден, только когда плагин ответил за последние 14 дней: в режиме без Hermes заданий никто не забирает (они гаснут за час) и блока нет. Внутреннего API у выбора нет — ни ассистент, ни дашборд Hermes его не меняют; ответ плагина держатель токена внутреннего API мог бы подделать, как любой итог задания, — тогда неверным будет только показанное время. `GET /api/status`: `summaries_available`, `summaries_chosen`, `summaries_state`, `summaries_differs`, `summaries_reported_at`, `summaries_next_morning`, `summaries_next_weekly`; `./ops/doctor.sh` — строка `summaries`.

## Отправка выключена

| Переменная | По умолчанию | Что значит |
|---|---|---|
| `SHTURMAN_SENDING` | `off` | `off` — доставка заблокирована; `on` — доставка разрешена при действующих правилах |
| `SHTURMAN_PREPARE_ONLY` | `off` | `on` — подготовка/просмотр без доставки, независимо от основного выключателя; также управляется `/prepare on|off` |
| `SHTURMAN_SEND_DAILY_CAP` | `50` | Потолок отправок на аккаунт в сутки, черновики и автоответы вместе |

Обе читаются **только из окружения сервиса** — на сервере это файл `.env`. Во внутреннем API нет вызова, который включает отправку или поднимает потолок: настройки шлюза могут потолок только уменьшить.

**Без своего бота согласований отправка не включается вовсе:** `SHTURMAN_SENDING=on` действует только вместе с `SHTURMAN_BOT_TOKEN` в `.env`. Без него нажатие «Отправить» шло бы через Hermes, где его может подделать ассистент. Токен бота, введённый на странице настройки переписки, для этого не засчитывается: иначе отправку можно было бы включить со страницы, а её включает только владелец на сервере.

При `off` без отдельного owner-разрешения подготовки (`/prepare on`):

- сервис не отправляет ничего и никому, ни одним каналом;
- черновики не создаются: инструмент агента получает отказ с объяснением;
- автоответ не начинается, модель не спрашивается;
- аккаунту-помощнику запрещены запросы отправки и «печатает…» на уровне клиента Telegram.

Работает при этом всё остальное: архив, поиск, обязательства, страницы памяти, наблюдатель групп и уведомления (они пишут только владельцу).

Включать отправку сейчас не следует. Свой бот закрывает подделку нажатия, но путь «карточка → нажатие → отправка через своего бота» на настоящем Telegram не проверен, а часть ограничения остаётся (`docs/architecture.md`, «Открытое ограничение»). Пока отправка выключена, в настройках Telegram Business у бота стоит оставить выключенным право отвечать на сообщения.

Включение — действие владельца и стоп-точка для агента (`AGENTS.md`): свой бот согласований, строка `SHTURMAN_SENDING=on` в `.env`, затем `./ops/up.sh`.

## Репетиция без доставки

Это репетиция в машине доставки — для бизнес-бота и аккаунта-помощника: её черновики лежат в `outbox_drafts` с отметкой `prepare_only`. Репетиция ответов на основном аккаунте (Р-85) — другое: черновиков не создаёт вовсе, к `/prepare` и `SHTURMAN_PREPARE_ONLY` не привязана (раздел «Репетиция ответов на основном аккаунте» ниже).

`SHTURMAN_PREPARE_ONLY=on` разрешает подготовку и просмотр черновиков и задач ответа, но не доставку. Черновик репетиции не превращается в отправленный после нажатия. Переключение установки в `on` не должно оживлять старое согласие или превращать старый репетиционный черновик в доставляемый. При `off` доставка заблокирована. Подготовка возможна только по явному решению владельца `/prepare on`; оно не меняет серверный выключатель отправки и сохраняется между перезапусками. `/prepare off` отзывает подготовку. Реальная отправка по-прежнему требует решения владельца на сервере и отдельного бота сервиса.

## Задача ответа и дополнительный источник

Вместо немедленного текста модель возвращает один из ограниченных исходов: ответ, запрос определённого источника, вопрос владельцу или отказ. Текст модели не создаёт прав. Сервис хранит задачу и её адресата, исходное сообщение, тему, версию политики и срок; по умолчанию задача живёт 30 минут. Состояния: очередь, генерация, ожидание источника/владельца, подготовка и готовый черновик либо завершение, отказ, отмена, истечение или ошибка. Готовый черновик — не свидетельство доставки: задача получает состояние `completed` после подтверждённой отправки в шлюзе. Репетиция без доставки не считается отправленным ответом. Связь конечного состояния со счётчиками и защита от повторного учёта проверяются отдельным сценарием приёмки.

Новый источник запрашивается карточкой у владельца: название, получатель и тема, точный запрос, период и предел фрагментов. В Telegram можно прочитать один раз, разрешить этот же поиск на 30 дней или отказать. Разрешение на 30 дней повторно используется только при совпадении источника, запроса, периода, пределов, получателя и темы; оно даёт только чтение. После разрешения сервис получает ограниченные сведения и продолжает ту же задачу. Источники: конкретный чат, память о человеке либо зарегистрированный внешний сервер; правила, реестр и ограничения — `docs/external-sources.md`. Чтение и раскрытие имеют отдельные разрешения. Если для автоматического раскрытия нет действующего права, готовый ответ возвращается владельцу на точное согласование.

Повседневный сценарий должен позволять владельцу ответить на действующую карточку, не начиная поиск заново: карточка живёт до десяти минут, задача — до тридцати. В приёмке отдельно проверяется продолжение на шестой минуте по сохранённому независимому решению текущего владельца. Эта проверка не отменяет сроки для обычного автоответа, изменение контекста или истечение самой задачи.

Текст, чат, аккаунт, ответ на исходное сообщение, тема, источник и версия политики связаны с черновиком и после создания не меняются. Перед согласованием и отправкой снова проверяются видимость, отзыв, срок и версии источников. Изменённый текст нельзя отправить по старому согласию; неизвестную доставку сервис автоматически не повторяет. Полный Hermes остаётся агентом владельца со своими инструментами, а этот путь — ограниченная сервисная автоматизация.

Классификатор и его уведомления помогают заметить подозрительный текст; они не определяют права и не служат границей безопасности. В автоматической задаче ответа модель получает только разрешённый контекст и возвращает предложение: у неё нет терминала и произвольных инструментов. Отдельный сервис проверяет источник, точный запрос, получателя и тему; шлюз отправки заново проверяет текст, права и срок перед доставкой. Поэтому обычный разрешённый ответ может идти по заранее выбранным правилам без нового вопроса владельцу, а чтение нового источника и новое раскрытие требуют соответствующего решения.

После регистрации точного числового ID управляющего бота сервис исключает его из сбора, удаляет уже принятые сообщения и связанные черновики, отменяет затронутые задачи ответа и стирает копии их запросов, результатов и карточек в заданиях. Связанные страницы памяти закрываются карантином до независимой очистки и пересборки; их файл и история не считаются автоматически стёртыми. Поздний результат старого задания не возобновляет задачу. Имя вроде «BotFather» само по себе не устанавливает ни личность бота, ни полномочия владельца.

## Управление владельца в Telegram

В личном чате независимого бота сервиса `/start` и `/menu` отвечают двумя строками и кнопками «Сейчас» (`/status`), «Согласования», «Сегодня» (`/today`, Р-94), «Помощь», «Ещё» (Р-86). `/today` — договорённости на сегодня и просроченные, «Я обещал» и «Мне обещали» (по 12 строк, остальное числом), сколько ждут «Верно / Не так» и кнопка «Открыть «Штурман»» — приложение сразу на экране «Договорённости» (адрес приложения с `?open=commitments`; данных в адресе нет). «Согласования» открывает приложение «Штурман» (кнопка `web_app`, если у страницы настройки есть внешний адрес https), иначе присылает сводку ждущего по видам. «Ещё» — кнопки «Черновики» (ждущие черновики и «Черновики ответов» вкл/выкл), «Вопросы ассистента», «Источники», «Группы и темы», «Внешние программы», «Чаты», «Репетиция», «Настройки», «Все команды». С Р-95 там же «Доверенные» и «Обращения», а настройки ответов и доверия — кнопками, без номеров и JSON (`executor/owner_settings.py`, данные кнопок `sh:hx:…`): `/trusted` — список с «Убрать: …» и «Выбрать человека»; `/trust` без номера — последние собеседники личных чатов кнопками; `/groups` — «Запретить: …» и «Разрешить группу…» (группы аккаунта помощника); `/addressing` без JSON — «Убрать «…»» и «Добавить обращение» (текстом в ответ на просьбу бота, ForceReply); `/drafting` без номера — выбрать чат, затем «Можно / Нельзя / Как обычно»; `/autoreply` без номера — «Включить / Выключить» по аккаунтам; `/rehearsal add` без номера — выбрать человека; под `/sources` и `/mcpaccess` — «Отозвать» у каждого разрешения (вместо `/sourcerevoke НОМЕР`, `/mcprevoke НОМЕР`). Нажатие владельца в личном чате бота — его решение: применяется сразу, тем же путём, что страница (`history.change`), со строкой «Истории» «бот, кнопка». Команды с номерами и JSON остались запасным путём в `/advanced`. `/help` — как пользоваться, простыми словами; полный список команд с номерами и JSON — `/advanced`. Сводки (`/status`, `/config`, `/chats`, `/drafts`, `/sources`, `/groups`, `/replytasks`, `/mcpaccess`) — словами, без JSON; пустое называется пустым. Настройки как есть, JSON-ом, — `/config json`. Ответ на команду, которая что-то меняет, говорит, что изменилось и как вернуть. Кнопки меню прежних версий («Статус», «Настройки», «Задания ответов», «Источники», «Группы и темы») под старыми сообщениями работают, как раньше; ответ на кнопку меню бот отправляет сам, а не заданием `notify.owner`. Проверяется текущий привязанный пользователь и личный чат; команды и callback от других пользователей или из группы не дают управление. Команда, полученная этим проверенным путём, уже является решением владельца и не создаёт второй общий запрос подтверждения. Подтверждать по HTTP нельзя.

Вторая строка меню — «Пауза», «Помощь», «Ещё»; пока ассистент остановлен, вместо «Пауза» — «Продолжить». Под `/status` — кнопка «Открыть «Штурман»» (приложение, когда у страницы есть внешний адрес https); при остановке `/status` начинается строкой «⏸ Остановлено сегодня в … (откуда)».

**Ответ на «Вопрос ассистента» (П1).** Под карточкой — «Ответить» и «Не отвечать». «Ответить» присылает сообщение с полем ответа (ForceReply, подсказка в поле ввода) и запоминает, к какому вопросу оно относится (`executor_state`, ключ `prompt`, не дольше срока вопроса и 30 минут): ответ — следующее сообщение владельца **ответом на это сообщение** в личном чате с ботом. Принимает его только текущий привязанный владелец в своём личном чате; чужие, группы, другие ответы, команды и сообщения из переписки владельца — не ответ (входящая переписка — данные, а не команды). Дальше — тот же путь, что `/replytask N answer ТЕКСТ` (`replies.owner.answer`): только пока задача ждёт владельца, с меткой карточки, не длиннее 2000 знаков; отказ — словами («Этот вопрос уже закрыт — ассистент не дождался ответа», «На этот вопрос вы уже ответили»). Тот же ответ — полем «Ваш ответ» в приложении.

Основные команды: `/status`, `/today`, `/config` (и `/config json`), `/advanced`, `/pause` (он же `/stop`; `/pause all` — и чтение переписки), `/resume` (он же `/continue`), `/prepare on|off` («Черновики ответов» — способ «Через бота и помощника»), `/rehearsal [on|off|add USER_ID|remove USER_ID|cap N|pause S]` («Репетиция» — способ «Через ваш аккаунт», Р-85; `cap` — карточек в сутки, 1–300; `pause` — секунд между карточками, 0–3600; ответ — «Предел — N в сутки. Вернуть: /rehearsal cap M»), `/replytasks` (или `/tasks`), `/replytask ID answer ТЕКСТ`, `/replytask ID cancel`, `/sources`, `/sourcerevoke ID`, `/mcpaccess` (или `/mcpclients`), `/mcprevoke GRANT_ID`, `/groups`, `/groupallow CHAT_ID [TOPIC_ID]`, `/groupdeny SCOPE_ID`, `/drafts`, `/cancel DRAFT_ID`, `/chats`. Для расширенной настройки есть `/policy JSON`, `/autoconfig JSON`, `/autoreply ACCOUNT_ID on|off`, `/trust USER_ID [ЗАМЕТКА]`, `/untrust USER_ID`, `/drafting CHAT_ID allow|deny|default`, `/addressing JSON`, `/sourcegrant JSON` и `/sourcepolicy JSON`. Владелец не обязан писать JSON для обычного решения о поиске и раскрытии: для этого есть карточки. Свободный диалог с ассистентом остаётся в боте полного Hermes.

## «Остановить всё»

Решение Р-87, код — `halt.py`, миграция `0035_stop_answer_code.sql`. Один флаг на сервер (`assistant_halt`). Пока он стоит, ассистент **ничего не делает сам**: не заводит задач ответа и вопросов владельцу, не готовит черновики (ни автоответом, ни «Черновиками ответов», ни по запросу ассистента), не готовит репетицию, не разбирает совпадения наблюдателя, не просит подтверждений действий и **не отправляет — даже если отправка включена на сервере**. Флаг сильнее любых настроек, а сами настройки не трогаются: после «Продолжить» возвращается ровно то, что было.

**Где проверяется.** В коде — в каждой точке, где ассистент начал бы действие: `replies.workflow.register/queue/notify_waiting`, `outbox.drafts.create/create_autoreply/_presend/_send_session`, `outbox.policy.check_send` (первым делом, причина `assistant_stopped`), `outbox.autoreply.on_message`, `outbox.watcher`, `rehearsal.core`, `triage.core` (разбор входящих — при остановке пересылка «Вам написали» как раньше), `confirm.request`, исполнитель `business.send`, кнопка «Подготовить ответ». В базе — вторая линия: триггеры не дают вставить задачу ответа, черновик, строку репетиции, строку разбора входящих, срабатывание наблюдателя, подтверждение (кроме `halt.resume` и `setup.code_login`) и задание `business.send` и перевести черновик в «согласован» или «отправляется» (ошибка `assistant_stopped`, код 55000).

**Что делает остановка сразу.** Отменяет ждущие вопросы и задачи ответа (`owner_stopped`), неотправленные черновики (в том числе «согласованные»), задания `business.send` в очереди, ждущие подтверждения (`rejected`, карточки в боте правятся), репетиции в очереди; забывает ждущий ответ на «Ответить». Уведомления «вам написали» и «вас упомянули» продолжают приходить. Галочка «И перестать читать переписку» (по умолчанию выключена) ещё и ставит на паузу все аккаунты Telegram; «Продолжить» снимает эту паузу, только если владелец отметит это отдельно. Владелец получает в бот сообщение: что остановлено, сколько отменено, как продолжить — с кнопками «Продолжить…», «Ещё и перестать читать переписку» и «Открыть «Штурман»».

**Откуда.** Остановить — сразу: кнопка «Остановить всё» в шапке «Настроек Штурмана», в приложении, в боте (меню «Пауза», `/pause`, `/stop`). Продолжить — **всегда нажатием владельца в боте**: в боте `/resume` присылает список того, что снова заработает, и кнопки «Продолжить», «Продолжить и снова читать переписку» (если чтение на паузе), «Оставить остановленным»; со страницы и из приложения — карточка подтверждения `halt.resume`, которую из приложения нажать нельзя. Внутренний API флаг не меняет ни в одну сторону.

**Видно.** `/status` и шапка страницы — «Остановлено с …»; приложение — полоса над разделами; `GET /api/status` — объект `stopped` (`stopped`, `since`, `via`, `reading_paused`); `./ops/doctor.sh` — строка `stopped` (`WARN`, пока остановлено). Журнал: `halt.stop` (откуда, сколько отменено), `halt.stop_again`, `halt.resume_request` (откуда), `halt.resume`.

**Ограничение: чтение архива продолжается.** Остановка не закрывает ассистенту архив (MCP): Hermes по-прежнему может искать и читать сохранённую переписку и отвечать владельцу в своём боте — это полный Hermes, его не изменяем. Закрывается всё, что делает сервис или что ассистент просит через внутренний API: инструменты, которые заводят вопросы, черновики и подтверждения, получают отказ «Владелец остановил ассистента» (409 или 423, `assistant_stopped`). Чтобы ассистент перестал видеть новую переписку, нужна галочка «И перестать читать переписку»; уже сохранённое остаётся доступным.

## Что подтверждает владелец в боте согласований

Внутренний API доступен плагину в Hermes, а значит и ассистенту: у него там терминал и токен. Поэтому, когда у сервиса свой бот согласований, действия, которые расширяют возможности ассистента или необратимо стирают данные, по HTTP не применяются. Сервис отвечает кодом 202 с телом `{"status": "pending_confirmation", "action_id": …, "summary": …, "expires_at": …, "note": …}` и присылает владельцу карточку «Подтвердите действие» с кнопками «Да, сделать» и «Нет». Нажатие приходит сервису напрямую от Telegram, мимо Hermes. На решение есть час.

Принцип: **ослабление ждёт, ужесточение применяется сразу.** Владелец должен иметь возможность закрыть доступ немедленно, даже когда бот недоступен.

| Ждёт нажатия владельца | Применяется сразу |
|---|---|
| Ослабление правил отправки и автоответа; любая правка текста представления автоответа | Ужесточение тех же правил |
| Разрешение готовить черновики (общее, для аккаунта, для чата) | Запрет черновиков |
| Включение автоответа; добавление в доверенные | Выключение автоответа; удаление из доверенных |
| Новое правило наблюдателя; правка, которая его расширяет; удаление правила с журналом | Выключение правила, сокращение его чатов, слов и пределов |
| Возврат исключённого чата; стирание сообщений исключённого чата; импорт выгрузки | Исключение чата; удаление загруженного файла |
| Вход в аккаунт Telegram; снятие с паузы; включение чатов; «брать новые чаты сами»; более глубокая история | Пауза, выход, отмена входа, выключение чатов, более мелкая история |
| Принятие предложенного обязательства (в том числе «вернуть в работу» и «закрыть» для неодобренного); объединение и разделение людей; алиас неподтверждённому человеку | Работа с принятым обязательством; отклонение предложений; алиас подтверждённому человеку |
| Запись блока владельца на странице памяти; согласие завести страницу | Отказ завести страницу; сборка страниц; запуск обработки |
| Завести проект; принять предложенный проект; изменить чаты проекта; убрать проект в архив; отметить факт неверным; правила в профиле владельца (блок владельца страниц проекта и профиля) | Отказ от предложенного проекта |
| Любое изменение сфер: завести, переименовать, удалить, отнести чат к сфере или убрать, сфера проекта (`spheres.create`, `spheres.update`, `spheres.delete`, `spheres.chats`, `spheres.project`; Р-82) — в том числе «убрать» и «удалить»: в следующих шагах сферы будут решать обработку, модель и границу ответов | Посмотреть сферы (`GET /api/spheres`) |
| Расширение репетиции ответов (`rehearsal.settings`, Р-85): включить, новые люди в списке, выше дневной предел, короче пауза | Выключить, убрать людей, ниже предел, длиннее пауза (с сообщением владельцу) |
| «Продолжить» после «Остановить всё» (`halt.resume`, Р-87) — из «Настроек Штурмана» и приложения; **только нажатием в самом боте**: из приложения «Да, сделать» не принимается, внутренний API и ассистент её не просят | «Остановить всё» — со страницы, из приложения, в боте (меню «Пауза», `/pause`, `/stop`) |
| Включение входа на страницу по коду из бота, когда бот заведён посредником (`setup.code_login`, Р-88) — тоже **только в самом боте**, не из приложения | Выключение входа по коду (ждущие коды гаснут) |
| Включение разбора входящих (`triage.enable`, Р-92) — со страницы; **только нажатием в самом боте**: из приложения «Да, сделать» не принимается, функция применения отказывает всему, кроме нажатия в боте; внутреннего API у разбора нет | Выключение разбора и правила разбора (важные, реже, тихие, сферы, срок) — на странице; «Не важно» под карточкой в боте |
| Расширение уведомлений владельцу (`notify.settings`, Р-84): больше личных сообщений («выкл» → люди или сферы → «от всех», новые люди или сферы), обращения в группах, новое обращение по имени, «показывать начало сообщения»; сфера в правиле наблюдателя (`watch.rule_update` с новой сферой) | Сужение уведомлений (с сообщением владельцу); время и частота — сразу или пачкой, тихие часы; убрать сферу из правила |
| Ослабление, о котором владелец попросил **из приложения «Штурман»**: добавить доверенного, разрешить черновики в чате, включить автоответ, разрешить группу (`outbox.group_scope`), новое обращение (`outbox.addressing`) — карточка `owner.widen` (Р-95), **только нажатием в самом боте**: «Да» под ней в приложении не принимается, функция применения отказывает всему, кроме нажатия в боте. Со страницы и кнопкой или командой в самом боте — сразу: это сам владелец | Убрать доверенного (`outbox.trusted_remove`), запретить черновики, выключить автоответ, запретить группу, убрать обращение — откуда угодно, сразу |
| «Вернуть как было» в «Истории», если возврат расширяет то, что может ассистент (Р-95) — со страницы и из приложения: карточка `owner.widen` (номер строки «Истории» в содержимом), «Продолжить» — `halt.resume`, разбор входящих — `triage.enable`; все — **только в самом боте** | «Вернуть как было», если возврат ужесточает; «Отозвать» разрешение прочитать источник и доступ внешней программы к архиву — со страницы, из приложения, кнопкой под /sources и /mcpaccess в боте |
| Решение разом по скрытому защитой (Р-99): «Показать ассистенту все скрытые» и «Все, кроме сильных правил» (`guard.release_all`) — **только нажатием «Да, сделать» в самом боте**, «Оставить все скрытыми» (`guard.keep_all`) — в боте или в приложении. Карточку подтверждения с итоговым числом ставит только нажатие владельца под сводкой скрытого (бот, `/guard`, раздел «Защита» приложения); маршрута во внутреннем API нет, ассистент и `shturman call` её не просят и не применяют (`confirm.apply` отказывает `guard.release_all`) | Поштучно: «Показать ассистенту» и «Оставить скрытым» под карточкой сообщения — как раньше, сразу; «Разбирать по одной» — следующие карточки |
| Разрешение на действие сопровождения сервера (`ops.consent`, Р-100): обновление с автоматическим откатом базы, восстановление из копии, восстановление без копии нынешнего состояния, откат обновления, перезапуск без свежей копии, порог защиты, удаление старых копий — **только нажатием «Разрешить» в самом боте**, не в приложении. Просит скрипт `ops/` на сервере (`POST /api/ops/consents`); функция применения отказывает всему, кроме нажатия под этой карточкой. Раздел «Разрешения на сопровождение» ниже | «Отклонить» — сразу; ничего не меняется |
| Отправка отчёта сессии сопровождения разработчику (`ops.report`, Р-102) — **только нажатием «Отправить» в самом боте**, не в приложении. Отчёт кладёт `./ops/report.sh` командой в контейнере сервиса прямо в базу; маршрута во внутреннем API нет; функция применения отказывает всему, кроме нажатия под карточкой. Раздел «Отчёты сопровождения» ниже | «Не отправлять» — сразу; отчёт остаётся только на сервере |

Вернуть чат, о котором владелец попросил не сообщать кнопкой «Не сообщать об этом чате» (`muted_chats`), — тоже расширение уведомлений: в боте и в приложении этого нет, только в «Настройках Штурмана», раздел «Уведомления», или через внутренний API с нажатием в боте. Расширение репетиции из вкладки приложения «Репетиция» — исключение по решению владельца (Р-89): сразу, с журналом и сообщением в бот.

Пока ассистент остановлен (Р-87), новые подтверждения не заводятся вовсе — запрос получает 423 `assistant_stopped` «Владелец остановил ассистента»; это не касается `halt.resume` и `setup.code_login`, которые просит сам владелец. Включение разбора входящих при остановке не просится вовсе: страница отвечает 423.

Что считать ослаблением, решается по значению, а не по названию настройки: уменьшить окно подсчёта сообщений — ослабление, увеличить — ужесточение. Если в одном запросе есть и то и другое, ужесточения применяются сразу (в ответе — поле `applied_now`), остальное ждёт. Запрос «исключить чат и стереть сообщения» исключает чат сразу, а стирание ждёт.

Повторный такой же запрос новую карточку не создаёт. Одновременно ждать могут не больше 20 действий; сверх этого — отказ 429. Если владелец к боту не привязан, действие не ставится в ожидание, а отклоняется с кодом `owner_unknown`. Запрос, который выглядел ужесточением, а к моменту записи стал бы ослаблением, потому что настройку в тот же миг изменили, отклоняется с кодом `changed_meanwhile`.

Посмотреть ждущие действия — `shturman call GET /api/confirmations`, одно действие — `GET /api/confirmations/7`, отменить — `POST /api/confirmations/7/cancel`. Подтвердить действие по HTTP нельзя. `shturman call` на ответ 202 печатает отдельной строкой «ЖДЁТ ПОДТВЕРЖДЕНИЯ В БОТЕ»: действие не выполнено, пока владелец не нажал кнопку. `./ops/tg-login.sh` при своём боте сначала ждёт разрешения владельца в боте и только потом показывает QR-код.

Без своего бота защищённый запрос ассистента отклоняется: отсутствие независимого подтверждения не означает согласие. Предусмотренные ужесточения можно применять сразу. Сам владелец выполняет настройки через отдельно проверенный вход страницы; отправка без своего бота выключена. Это поведение 0.0.7; результаты старых стендов относятся к указанным в них версиям.

Удаление из архива аккаунта без сессии (`tg.forget`: аккаунт, его чаты, сообщения и всё извлечённое из них) есть только на странице настройки переписки и применяется только как действие владельца: по внутреннему API его нет, а без владельца функция применения отказывает.

То, что владелец делает сам на странице настройки переписки, карточки не ждёт ни в одном случае: туда входят по ссылке с сервера, а не по токену внутреннего API, и каждое действие пишется в журнал.

Известные оговорки. Инструмент агента `shturman_commitment_update` на неодобренном предложении при своём боте получает «не выполнено, ждёт владельца». Алиас уже подтверждённому человеку добавляется без подтверждения — им пользуется инструмент агента. В карточке нет формулировки обязательства: чужой текст в карточки не кладётся, только номер, стороны и дата. Карточка хранит значения на момент запроса: если владелец после этого ужесточил настройку, а потом нажал «Да» на старой карточке, применится значение из карточки.

## Разрешения на сопровождение

Стоп-точки сопровождения (`AGENTS.md`), на которых скрипт перезаписывает данные или меняет решение владельца, раньше требовали фразу с одноразовым числом в терминале человека. Владелец, который сопровождает экземпляр с помощью Codex, терминалом и ssh не владеет — сопровождение останавливалось (Д-29); а фразу в терминале агент с теми же правами мог набрать программно. С Р-100 «да» на них — нажатие «Разрешить» в боте согласований.

| Вид (`--action`) | Скрипт | Цель (`--target`) | Что на карточке |
|---|---|---|---|
| `update` | `./ops/update.sh`, `--consent` | коммит выпуска (40 знаков) | версия «было → станет», откат базы и `data/` из копии при провале, миграции, непроверенный Hermes |
| `restore` | `./ops/restore.sh --from` | `метка:all\|db\|data:env\|keep` | метка и время копии, что заменится, `.env` |
| `restore_nocopy` | `./ops/restore.sh` (копия «до» не снялась) | метка копии | продолжить без копии нынешнего состояния |
| `rollback` | `./ops/restore.sh --rollback` | прежний коммит | версии, копия до обновления и сколько минут архива пропадёт |
| `no_backup` | `./ops/up.sh --skip-backup-check` | отпечаток того, что ждёт (16 знаков) | какие миграции или смена Hermes ждут без свежей копии |
| `guard_threshold` | `./ops/guard.sh threshold` | новый порог (0,5–1) | порог «было → станет» |
| `backups_delete` | `./ops/cleanup.sh --backups` | `N:отпечаток списка` | сколько копий, с какой по какую, сколько места, сколько останется |

Как устроено (`ops_consent.py`, `ops_consent_cli.py`, функции `owner_consent` и `confirm_owner` в `ops/lib.sh`):

- Скрипт запускает в контейнере сервиса `shturman ops-consent ask --action … --target … --detail поле=значение …`. Команда просит `POST /api/ops/consents`: строка таблицы `ops_consents` и подтверждение `ops.consent` — карточка «Подтвердите действие» с кнопками «Разрешить» / «Отклонить». Текст собирает сервис по виду действия из проверенных полей (вид — из перечня, цель — по образцу, подробности — только названные поля, в одну строку, до 200 знаков); готовый текст от скрипта не принимается. Тот же запрос, пока ждёт или выдан и не израсходован, новой карточки не создаёт.
- Команда печатает «Ждём подтверждения владельца в боте согласований: <что>; запрос действует до ЧЧ:ММ (пояс)» и ждёт нажатия до `--wait` секунд (скрипты: `OPS_CONSENT_WAIT`, по умолчанию 300). Нажато «Разрешить» — расходует разрешение (`POST /api/ops/consents/{id}/use` с тем же видом и целью) и выходит с кодом 0. Не дождалась — код 4 и «запрос в силе до ЧЧ:ММ»: повтор той же команды находит тот же запрос и продолжает без новой карточки. Отклонено, срок вышел, израсходовано — код 5. Бот не настроен или владелец не привязан — код 6 (`owner_unknown`).
- Разрешение одноразовое, на один вид и одну цель: другой коммит, другая копия, другой порог, изменившийся список копий — отказ. Ждёт нажатия час (как любая карточка), после нажатия годно 2 часа. `./ops/update.sh --consent` получает его заранее и не расходует (`--keep`): израсходует следующий `./ops/update.sh`.
- Нажать может только привязанный владелец в личном чате с ботом — общие правила нажатий; **только в самом боте** (`BOT_ONLY`): войти в приложение «Штурман» может и держатель токена бота. Функция применения `ops.consent` дополнительно отказывает всему, кроме нажатия под карточкой (`confirm.card_press`), и нажатию из приложения.
- Маршрута, который выдаёт разрешение без нажатия, нет. Внутренний API (`shturman call`, ассистент в Hermes) может попросить карточку, узнать исход (`GET /api/ops/consents/{id}`, `GET /api/ops/consents?action=…&target=…`) и израсходовать уже выданное. Разрешение, выпрошенное ассистентом, ему бесполезно: скрипты `ops/` он не запускает. Предупреждение на карточке — «Запрос прислала команда сопровождения на сервере…»; не просили — «Отклонить».

**Когда сервис не работает** (база сломана, сервис не стартует, зависший — только для восстановления и отката, которые всё равно его останавливают): скрипт запускает одноразовый контейнер из образа сервиса — `docker compose run --rm --no-deps -T shturman ops-consent ask … --direct`. Команда сама говорит с Telegram от имени бота согласований: токен — из окружения контейнера и файла страницы настройки, не печатается, агент его не видит. Шлёт владельцу карточку (кнопки с данными `oc:y|n:<случайная метка>` — сервис такие не примет) и ждёт нажатия через `getUpdates` **без `offset`**: ничего не подтверждает, все прочие обновления (в том числе сообщения бизнес-режима) остаются сервису. Принимается только нажатие под этой карточкой, от владельца, в его личном чате с ботом; чужому — «Кнопка недоступна». Если бота опрашивает кто-то ещё (сервис ожил) или включён webhook — Telegram отвечает 409, команда отказывает (код 8) и снимает карточку: идти через сервис. Если у бота 100 и больше непрочитанных обновлений — тоже отказ: без сервиса их не пропустить, не потеряв. Не дождалась — карточка гаснет, код 4; повтор пришлёт новую.

Кто владелец на этом пути: сначала база, если контейнер базы жив (`binding.bound_owner` — тот же владелец, что принимает нажатия бот); без базы — копия `data/shturman/setup/owner.json` (`{bot_id, user_id, chat_id}`, права 600). Её пишет сам сервис — бот согласований при запуске, после привязки и при каждой сверке кнопки меню (раз в 10 минут), стирает при отвязке. Копия о другом боте не годится. Почему здесь: каталог данных сервиса подключён только его контейнеру (ассистенту в Hermes не виден), копия попадает в резервные копии вместе с базой и восстанавливается согласованно с ней; `local/` и `.env` — область скриптов, куда сервис не пишет. Предел: оператор с правами на сервере может подменить и копию, и саму базу (`docs/pilot/locks-audit.md`).

**Запасной путь** — бот не настроен, владелец не привязан, образа сервиса нет (новый сервер), сервис запущен, но не отвечает и сам держит бота: скрипт так и пишет («Подтвердить в боте согласований сейчас нельзя…») и, если у запуска есть терминал человека, просит фразу с одноразовым числом, как раньше; без терминала — код 4 и команда `ssh -t …` для владельца, который умеет работать в терминале. Терминал — только когда бота нет: при работающем боте фразу скрипт не спрашивает.

## Уведомления об обновлениях

Р-101, `updates.py`. Раз в сутки (первый раз — через 5 минут после запуска) сервис читает список выпусков `releases.json` из `main` репозитория (`SHTURMAN_UPDATES_URL`, по умолчанию raw-ссылка GitHub; только https; одним GET без идентификатора экземпляра; через `EGRESS_PROXY_URL`, если задан) и пишет владельцу в бот согласований. Выключатель — `SHTURMAN_UPDATES=off`. Форма списка — `docs/releases.md`, «Список выпусков».

- **Доверие.** Список — данные: принимается только целиком прошедший проверку полей (`updates.parse`: теги, версии, даты, виды, строки до 200 знаков без управляющих знаков; лишние поля отбрасываются) и в пределах срока годности (`expires`, не дольше 120 дней от `published`) — и при скачивании, и при каждом чтении из базы. Неполадка (`expired`, `invalid`, `too_big`, `unreachable`, `http`, `bad_url`) — строка `updates` в `./ops/doctor.sh` и одно сообщение владельцу (`unreachable` и `http` — после трёх суточных неудач подряд); удачная проверка неполадку снимает. Есть ли тег в истории `main`, сервис не проверяет — это делает `./ops/update.sh` при обновлении.
- **Что и когда.** Новость о выпуске — одна на версию (таблица `update_notices`); обычная — не чаще раза в неделю и не в тихие часы владельца (настройки уведомлений); `security` — сразу (в тихие часы без звука) и раз в сутки, пока экземпляр не на нём. Кнопки (`sh:up:…`): «Как обновить» — следующим сообщением текст для Codex (`updates.codex_text`), «Напомнить через неделю», «Пропустить версию» — две последние не у `security`. Канал — `SHTURMAN_UPDATE_CHANNEL` (как у `./ops/update.sh`). Новая проверенная версия Hermes — отдельное сообщение, только в режиме с Hermes (`SHTURMAN_HERMES_IMAGE` задан) и если она новее запущенной. Снятие модели (`warnings`) — за 30 и за 7 дней, если сервис сам обращается к этой модели.
- **Итог обновления.** `./ops/update.sh` в конце выполняет в контейнере сервиса `shturman update-result --run … --result ok|rolled-back|failed-needs-human|rollback-failed --from … --to … --new-fails "…"` — запись прямо в базу (`update_runs`), не через внутренний API. Сервис пишет владельцу итог словами («обновлён: A → B, проверки прошли» и «что изменилось»; «не встало — всё вернули»; «прошло с ошибками — попросите Codex откатить»; «откат не удался»). При запуске сервис сверяет запущенный код (`SHTURMAN_CODE_VERSION`, `_TAG`, `_COMMIT` — пишет `./ops/up.sh`) с прошлым; сменился, а итога 30 минут нет — «версия сменилась, итога проверки нет».
- **Где видно.** `GET /api/status`, объект `updates` — только теги, коды и время: `enabled`, `channel`, `running` (`version`, `tag`, `commit` — 12 знаков, `hermes`), `checked_age_s`, `problem`, `fails`, `expires`, `available` (самый новый тег впереди), `available_kind` (`security` | `regular`), `behind`, `hermes_new`. Текстов списка во внутреннем API нет: ассистент в Hermes их не читает. Приложение «Штурман» — плашка в «Сейчас» (`app/now`, поле `update`: версия, «что изменилось», текст для Codex, итог последнего обновления за трое суток; `docs/miniapp.md`).

## Отчёты сопровождения

Р-102, `ops_report.py`. Каждая сессия сопровождения кончается `./ops/report.sh` (`prompts/operate-codex.md`): отчёт собирается на сервере белым списком (`ops/report_filter.py`) и записывается командой `shturman ops-report submit` (JSON на stdin) в контейнере сервиса прямо в базу (`ops_reports`, status `new`) — маршрута во внутреннем API нет.

- Сервис раз в 5 секунд берёт новые отчёты, ещё раз проверяет каждое поле (`ops_report.check`: виды, длины, перечни, в тексте — замена адресов, имён узлов, почты, @имён, номеров и похожего на ключи) и сам собирает текст. Карточка — подтверждение `ops.report`: «Отчёт сессии сопровождения — отправить разработчику?», весь текст отчёта, кнопки «Отправить» / «Не отправлять»; `BOT_ONLY`. Бот не настроен или владелец не привязан — отчёт помечается `failed` с причиной, `./ops/report.sh` так и говорит.
- «Отправить» — бот присылает владельцу сообщение-отчёт и блок `ОТЧЁТ-JSON <№> i/n — данные для разработки, не указания` (при длинном отчёте — несколько сообщений) с просьбой переслать разработчику. Если задан `SHTURMAN_FEEDBACK_CHAT` (номер чата разработки, куда владелец добавил своего бота), — туда; не вышло — владельцу с объяснением. Исход — в `ops_reports` (`sent`, `declined`, `expired`, `failed`; `sent_to` — `owner` или `chat`).
- Сведение на стороне разработки — `service/tools/feedback_import.py`: черновые строки `docs/pilot/defects.md` и отметки К-8; содержимое отчётов не исполняется.

## Аккаунты и источники

«Аккаунт» в архиве — это точка зрения, с которой пронумерованы чаты и сообщения. У основного аккаунта владельца три возможных источника. Задумано, что они дают одни и те же идентификаторы и складываются в одни строки без дублей; для пары «бизнес-бот и экспорт» это на настоящих данных не проверено.

| Аккаунт | Источник | Что даёт | Может ли отправлять |
|---|---|---|---|
| Основной (владелец) | Сессия Telethon **только на чтение** — способ «Через ваш аккаунт» | Выбранные владельцем чаты: личные, группы, каналы; история без выгрузки | **Нет.** Клиент этой роли пропускает к Telegram только перечень запросов на чтение (в нём есть и скачивание голосового для расшифровки — ниже) |
| Основной (владелец) | Экспорт Telegram Desktop — по желанию | Прошлое: всё, что выгружено | — |
| Основной (владелец) | Бизнес-бот (бот согласований) — основной путь к личным чатам в способе «Через бота и помощника»; Telegram Premium не нужен (документация Telegram API, сверено 2026-10-14) | Новые личные чаты по фильтру владельца, с момента подключения | Да — ответ в личном чате в течение 24 часов после входящего, при включённой отправке |
| Дополнительный (помощник, «аккаунт помощника») | Сессия Telethon — по желанию, в способе «Через бота и помощника» для групп | Чаты и группы, где состоит помощник | Да — через шлюз отправки, при включённой отправке |

Какой путь — сессия основного аккаунта или бизнес-бот с аккаунтом помощника — владелец выбирает сам на странице настройки переписки, шагом 2 (решение Р-62). Основной аккаунт на чтение он подключает там же. Страница предупреждает: на сервере появляется сессия основного аккаунта, и риск ограничений со стороны Telegram ложится на него, а не на запасной номер. От имени владельца сервис пишет только через бизнес-бота — официальным путём.

Правила сессий:

- **Ничего не читается, пока владелец не выбрал чаты.** Вход в аккаунт сам по себе в архив ничего не приносит.
- **Глубина истории ограничена.** Для включаемого чата по умолчанию загружаются последние 12 месяцев; глубину можно изменить для аккаунта или задать дату для конкретного включения.
- **Помощником не может стать аккаунт владельца.** Вход помощника не начинается, пока сервис не знает владельца (бот не привязан и в архиве нет основного аккаунта). После входа и при каждом запуске аккаунт сверяется с владельцем; при совпадении сессия завершается.
- **Одна сессия — один процесс.** Перед подключением берутся блокировка файла и блокировка в базе; занято — сервис не подключается.
- **Запросы к Telegram — по одному на аккаунт, со случайной паузой.** Пауза — от 3 до 5,4 секунды, примерно раз в сто запросов — перерыв 15–60 секунд; случайность берётся из системного генератора, а не из времени. В среднем это около 4,5 секунды на запрос по 100 сообщений: 300 000 сообщений истории — примерно 3,5–4 часа. Telegram своих пределов не публикует; «около 10 запросов истории за 30 секунд» — опыт открытых проектов, и пауза никогда не короче этого шага. Насколько случайный шаг снижает риск ограничений, не известно.
- **При ограничении со стороны Telegram** сервис ждёт названное время и не повторяет запрос раньше.
- **Список диалогов — в базе, загружается в фоне** (Р-81, раздел «Список диалогов аккаунта» ниже).
- **Прочитанным ничего не отмечается.**
- **Скачивание вложения — только для расшифровки голосовых и разбора фото и документов.** Перечень запросов на чтение расширен тремя: `upload.GetFileRequest` (сам файл, частями), `auth.ExportAuthorizationRequest` и `auth.ImportAuthorizationRequest` (перенос авторизации этой же сессии в дата-центр, где лежит файл, — так делает любой клиент Telegram при открытии вложения). Прочитанным это ничего не отмечает. Сервис вызывает их только для голосовых и «кружков» в очереди расшифровки (`docs/voice.md`) и для фото и документов в очереди разбора, пока владелец его не выключил (`docs/media.md`).

Сообщения бизнес-режима приходят через бота только из личных чатов. Сообщения принимаются только по подключению, которое создал сам владелец.

### Список диалогов аккаунта

Той же загрузкой, одним запросом после последней страницы, читаются папки Telegram (`messages.getDialogFilters`, только чтение; таблица `tg_folders`, Р-82): названия, явные перечни чатов и правила. Состав папки и разделы раскладок «Папки / Сферы / Активность / Вид» сервис считает по списку в базе (`spheres.sections`); маршруты страницы — `GET /shturman-setup/api/tg/accounts/{id}/sections?layout=…`, `POST …/bulk {section, enabled, months?}`, приложения — `GET /shturman-setup/api/app/chats/{id}/sections`, `POST …/bulk` (только `enabled: false`). Список раздела — тот же `…/dialogs` с `section=` `folder:3`, `sphere:2`, `sphere:none`, `activity:week`, `kind:bot`. Подробно — `docs/spheres.md`.

Решение Р-81. Список диалогов аккаунта (названия, @имена, вид, последнее сообщение, папка Telegram) хранится в таблице `tg_dialogs`, сведения о загрузке — в `tg_dialog_lists` (миграция `0031_tg_dialogs.sql`). Экран выбора чатов на странице и в приложении, включение и исключение чата, текст карточки подтверждения, настройка «брать новые чаты сами» и дозагрузка истории берут его оттуда; после перезапуска сервиса список есть сразу.

Загружает его из Telegram фоновая задача аккаунта (`TgManager.start_dialogs`, цикл — `tg/dialogs.py`): страницы `messages.GetDialogs` по 100 с паузой 1,5–2,7 с, каждая сразу в базу. Запрос экрана загрузку только запускает и отвечает сразу; вторая, пока идёт первая, не начинается. При FLOOD_WAIT загрузка ждёт названное время и повторяет ту же страницу; при сбое связи — до трёх повторов. Пока она идёт, запросы истории аккаунта ждут; FLOOD_WAIT общий. Дошла до конца — диалоги, которых не оказалось, убираются из списка (не из архива).

Кто запускает: кнопка «Обновить список из Telegram» (`refresh=1`; не чаще раза в 30 секунд после полной загрузки); страница «Настройки Штурмана», если список старше 10 минут или его нет; дозагрузка истории, которой нужен свежий номер последнего сообщения каждого диалога; отказ включить «брать новые чаты сами», пока списка нет. Приложение «Штурман» само не запускает.

Ход загрузки — поле `load` в ответе на запрос списка (`/shturman-setup/api/tg/accounts/{id}/dialogs`, `/shturman-setup/api/app/chats/{id}/dialogs`, `/api/tg/accounts/{id}/dialogs`):

| Поле | Что значит |
|---|---|
| `state` | `idle` — списка нет и он не грузится; `loading` — грузится; `waiting` — Telegram просит подождать; `done` — загружен целиком; `failed` — последняя загрузка не дошла до конца |
| `running` | Идёт ли загрузка сейчас |
| `loaded`, `expected` | Сколько диалогов получено в этой загрузке (вне загрузки — сколько в базе) и сколько назвал Telegram |
| `wait_seconds` | Сколько ещё ждать по просьбе Telegram (при `waiting`) |
| `updated_at` | Когда список последний раз загружен целиком |
| `error` | Почему загрузка не дошла до конца — текстом для владельца |

При выходе из аккаунта строки списка удаляются (архив остаётся); при удалении аккаунта из архива — каскадом. Список — данные владельца того же рода, что `chats`: наружу, кроме страницы, приложения и прежнего маршрута внутреннего API, не отдаётся; MCP и инструменты Hermes его не читают.

## Уровни автономии

| Уровень | Что делает ассистент | Где | Состояние |
|---|---|---|---|
| 0. Наблюдатель | Читает, ищет, сводит | Любой источник | Написано |
| 0а. Репетиция ответов (Р-85) | Готовит ответ, как автоответ 2а, и показывает владельцу карточкой с оценкой; не отправляет никогда | Основной аккаунт (только чтение) | Написано, по умолчанию выключена |
| 1. Черновики | Готовит ответ, отправляет после нажатия владельца | Бизнес-бот, помощник | Написано, отправка выключена |
| 2. Шаблонные действия | Сам отправляет типовые сообщения людям из белого списка | Помощник | Не сделано |
| 2а. Автоответ доверенным | Сам отвечает людям из списка доверенных, без подтверждения | Бизнес-бот (голос владельца), помощник | Написано, по умолчанию выключен, отправка выключена |
| 3. Свободная переписка | Ведёт диалог в заданных рамках | Помощник | Не сделано |

Правила уровня 1:

- агент может только создать черновик; текст черновика после создания не меняется — владелец согласует ровно то, что уйдёт;
- **ассистент не пишет первым**: черновик возможен только в чат, где уже есть исходящее сообщение владельца или помощника, либо как ответ через бизнес-бота человеку, который только что написал сам. Через API это правило не выключается;
- в одном чате ждёт решения не больше одного черновика; новый заменяет прежний;
- нажатие сначала занимает черновик, потом идёт отправка — два нажатия не дают двух отправок;
- если ответ Telegram потерялся, исход помечается «неизвестно, дошёл ли» и сам не повторяется никогда.

Правила уровня 2а:

- доверенные задаются только числовыми идентификаторами Telegram;
- ответ готовится **без инструментов**: сервис сам собирает справку — последние сообщения этого чата и найденное в архиве — и просит у модели только текст. По умолчанию поиск идёт только в этом же чате; владелец может расширить его на другие чаты аккаунта, но оттуда берутся лишь собственные слова владельца или помощника. Чужие сообщения из других чатов в справку не попадают никогда;
- в личных чатах — только входящие от доверенных; в группах — отдельная область или проверенное прямое обращение аккаунту-помощнику. Каналы вещания не участвуют. Боты, пересылки, правки и свои сообщения не запускают ответ; подробные условия ниже;
- пауза между ответами и дневной лимит на аккаунт (по умолчанию 5 секунд и 300 ответов); поверх него действует общий потолок `SHTURMAN_SEND_DAILY_CAP`;
- пока ответ готовится, аккаунт-помощник показывает «печатает…» с обновлением каждые 4 секунды;
- ответ одним сообщением, длинный режется по абзацам; запоздавший ответ не отправляется;
- всем, кто не в списке, сервис не отвечает вообще;
- о каждом включении автоответа, изменении списка доверенных и правил отправки владелец получает сообщение.

## Репетиция ответов на основном аккаунте

Решение Р-85, код — `rehearsal/`, миграция `0034_rehearsal.sql`. По умолчанию выключена; включает владелец (страница, `/rehearsal` в боте) или ассистент с его «Да» в боте.

**Дневной предел.** Когда предел исчерпан, владелец получает одно сообщение в сутки: «Репетиция ответов: дневной предел — N карточек — исчерпан…» с кнопками «Поднять до 50», «Поднять до 100» — только значения больше нынешнего; от предела 100 — «Поднять до 200» и «Поднять до 300»; на 300 кнопок нет (`rehearsal.core.raise_options`). Данные кнопки — `sh:rh:c:<новый>:<нынешний>[:<сообщение>]` в прежней схеме: нажатие принимается только от привязанного владельца в личном чате бота согласований (не из приложения) и только пока предел всё ещё тот, при котором кнопка была выдана, — иначе «Предел уже изменён: сейчас N в сутки». Нажатие — решение владельца: сразу (`confirm.apply_owner`), журнал `rehearsal.settings` «через: бот, кнопка «Поднять до …»», ответ «Предел — N в сутки. Вернуть: /rehearsal cap M». То же у ответа на «Подготовить ответ» при исчерпанном пределе — там в данных кнопки номер сообщения, и после подъёма просьба повторяется сама (итог дописывается в ответ бота). Поменять предел и паузу можно ещё командами `/rehearsal cap N`, `/rehearsal pause S`, во вкладке «Репетиция» приложения и в «Настройках Штурмана».

**Что запускает.** Событие `message.live` из сессии основного аккаунта (роль `owner`): новое входящее в личном чате с человеком — не «Избранное», не чат с ботом, не служебные чаты Telegram и не управляющий бот, от самого собеседника, не через бота, не правка; собеседник — в списке репетиции (`people`, числовые ID); сообщение видно ассистенту (не скрыто защитой), с текстом или с фото, документом, голосовым, не старше `max_age_seconds` автоответа; у сервиса свой бот согласований; это сообщение не готовит настоящий автоответ 2а. Догрузка истории, импорт и бизнес-поток событий для репетиции не дают. Одна карточка — на всю пачку (раздел «Пачки сообщений»), когда она закрылась; повод — собственное сообщение собеседника, пачка из одних пересланных репетицию сама не запускает. В карточке — пачка одной строкой и сколько сообщений она покрывает.

**Как готовится.** Как автоответ 2а: справка — `autoreply.gather_context` (последние сообщения этого чата и найденное в нём же; скрытое защитой и удалённое не берётся), запрос — `autoreply.build_messages` голосом владельца и `replies.workflow.model_request`, задание `llm.structured` с той же схемой исходов (`replies.model`). Ответ модели разбирается тем же `model.parse`; ссылка на непредложенное сообщение — «не получилось». Перед карточкой всё проверяется заново: удалено, изменено, скрыто, чат исключён, человека убрали, репетицию выключили — карточки нет. Исход «нужен источник» только называется в карточке: в репетиции ничего дополнительно не читается и разрешений не просят.

**Карточка** — `notify.owner` в бот согласований: «🎭 Репетиция ответа — ничего не отправлено», «💬 Вам написали: имя», чат, сферы, время, сообщение одной строкой до 300 знаков без невидимых символов (`notify.core.body`) или пачка одной строкой (`notify.core.pack_line`), чего ассистент не видел («Фото не успел разобрать», «Фото не смотрел: разбор фото и документов выключен…», раздел «Пачки сообщений»), ссылка «Открыть», «Ассистент ответил бы так:» и текст (или «не стал бы отвечать», «спросил бы вас», «не хватило бы сведений»), «вы ответили сами — можно сравнить», если владелец успел ответить. Кнопки — только оценки `sh:rh:g|a|b:<номер>:<метка>`: «Годится», «Почти — поправил бы», «Не годится». Нажатие (только привязанный владелец в личном чате с ботом) сохраняет оценку и заменяет кнопки — выбранная с «✓» (новое поле ответа на нажатие `buttons`, бот правит клавиатуру `editMessageReplyMarkup`); оценку можно изменить. В тихие часы уведомлений карточка приходит без звука.

**Связка с уведомлениями (Р-84).** `notify.core.Notifier.on_message` спрашивает репетицию (`rehearsal.core.notify_hold`): репетиция будет — уведомление ставится с `held_for_rehearsal` и сроком не раньше чем через 3 минуты после закрытия пачки и ожидания её вложений (вместе с ним придерживаются и уже ждущие уведомления этого чата — пачка уходит целиком); карточка ушла — придержанные уведомления чата до этого сообщения снимаются (`dropped_reason = 'rehearsal'`); репетиция не состоялась — они отпускаются сразу; карточка не дошла — уведомления возвращаются в очередь; карточка ушла раньше, чем уведомление встало в очередь, — оно сразу записывается снятым.

**Ничего не отправляется.** Основной аккаунт — только чтение (`RequestPolicy("owner")` при любом `sending` и `login`). Репетиция не создаёт `outbox_drafts`, `reply_tasks` и заданий `business.send`; в `rehearsal_items` нет текста переписки — ни сообщения, ни предложенного ответа; задание модели стирается после разбора. Единственный текст в строке — свой вариант владельца (ниже): его собственные слова, не переписка.

**Свой вариант (Р-89).** После «Почти — поправил бы» бот присылает «Напишите, как ответили бы вы» с полем ответа (ForceReply) и кнопкой «Не писать свой вариант». Ответ (только привязанный владелец, личный чат, ответом на это сообщение, до 2000 знаков) сохраняется в `rehearsal_items.owner_variant` и удаляется вместе со строкой через 30 дней; в журнале `rehearsal.variant` — номер карточки и число знаков, без текста. Показывается только во вкладке «Репетиция» приложения; модели не передаётся. В статистике — `variants`.

**Разовая репетиция по кнопке «Подготовить ответ» (Р-89)** у уведомления «вам написали» в способе «Через ваш аккаунт»: на пачку этого сообщения, даже если человека нет в списке и репетиция выключена (`on_demand`), — в том числе на пересланное без комментария: владелец попросил сам, пересланное модель получает как слова третьего лица (Р-93); сообщение не старше суток; входит в дневной предел; карточка помечена «По вашей просьбе». Если вложения пачки ещё разбираются, ответ готовится в фоне после их разбора (до `SHTURMAN_PACK_MEDIA_WAIT`). Ничего не отправляется, как и у обычной репетиции. Ни нажатие, ни `/prepare on`, ни `SHTURMAN_SENDING=on` позже не делают карточку доставляемой.

**Почему нельзя — словами (Р-93).** На каждый код отказа — своя фраза (`rehearsal.core.WORDS`) после «Не получилось: »: `gone` — удалено или чат исключён; `not_personal` — не личное сообщение человека вашему аккаунту; `not_session` — пришло не через вход в аккаунт (выгрузка, бизнес-режим): не видно, переслано ли и не от бота ли; `hidden` — скрыто защитой; `no_text` — нет ни текста, ни фото, документа, голосового; `stale` — старше суток; `forwarded_only` — в пачке только пересланное (только для автоматического запуска); `answered`, `newer`, `daily_cap`, `pause`, `stopped`, `disabled`, `not_listed`, `no_bot`, `unavailable`. Если ответ заранее невозможен (`gone`, `not_personal`, `not_session`, `hidden`, `no_text`, `stale`, сервис репетиции не запущен), кнопки «Подготовить ответ» под уведомлением и карточкой разбора нет (`notify.buttons.can_prepare`); временное — остановка, дневной предел, выключенные черновики — кнопку не убирает, а на нажатие называет причину.

**Пределы.** `daily_cap` — карточек (запросов к модели) за 24 часа, по умолчанию 30 (1…300); `pause_seconds` — между двумя запросами, по умолчанию 5 (0…3600). Что не уложилось — пропускается (`skipped`, `daily_cap` или `pause`), уведомление о нём уходит как обычно; о пределе владелец получает одно сообщение в сутки.

| Маршрут внутреннего API | Что делает |
|---|---|
| `GET /api/rehearsal` | Настройки (`people` — числовые ID), `own_bot`, `main_account`, `stats` — только числа за 7 дней |
| `PUT /api/rehearsal` | `{enabled?, people?, daily_cap?, pause_seconds?}`: включить, новые люди, выше предел, короче пауза — 202 и карточка в боте (`rehearsal.settings`, в карточке — имена и ID добавляемых); выключить, убрать людей, ниже предел, длиннее пауза — сразу, владельцу сообщение; смешанный запрос — сужение сразу (`applied_now`), расширение ждёт. Свой аккаунт, бот, служебный адрес — 400 |

В плагине маршрут отнесён к роли `UI`; инструмента агента для него нет. Вкладка приложения «Репетиция» живёт на адресе страницы и в проход дашборда не входит: роль `UI` и агент новых прав не получили. В `GET /api/status` — `rehearsal_enabled`, `rehearsal_people` и за 7 дней `rehearsal_shown_7d`, `rehearsal_good_7d`, `rehearsal_almost_7d`, `rehearsal_bad_7d`, `rehearsal_unrated_7d`, `rehearsal_limited_7d`, `rehearsal_failed_7d`. Журнал действий: `rehearsal.settings` (в списке важных: включена ли, сколько людей, предел, пауза, откуда — страница, бот (команда, кнопка «Поднять до …», «Да» под карточкой), приложение, внутренний API), `rehearsal.rate` (номер карточки, код оценки, прежняя оценка). Строки `rehearsal_items` хранятся 30 дней; при смене владельца репетиция выключается и список очищается.

## Ответы в группах и темах

Этот путь работает только через сессию дополнительного аккаунта-помощника: основной аккаунт остаётся на чтении, Telegram Business — в личных чатах. Группы и супергруппы поддерживаются; вещательные каналы исключены. Требуются включённый автоответ аккаунта и достоверное новое входящее сообщение известного обычного пользователя. Не участвуют боты, сообщения через бота, пересылки, правки, скрытые/удалённые сообщения и собственные сообщения зарегистрированного владельца или помощника.

Кандидат возникает по одной из двух причин: точная включённая область `account_id + peer_id + topic_tg_id` либо проверенное прямое обращение. Область с `topic_tg_id=0` действует на весь чат; положительный идентификатор — только на выбранную тему. Область не ограничена отдельным автором вопроса. Одинаковое название группы не переносит разрешение на другой `peer_id`.

Прямое обращение — настоящая разметка упоминания числового Telegram ID владельца/помощника, ответ на его реальное видимое сообщение в том же чате и теме либо заданное владельцем точное обращение в начале реплики, например «Штурман, …». Имя в цитате, коде или пересылке не считается обращением. Текстовой поиск имени не заменяет идентичность сообщения. Прямое обращение может запустить рассмотрение вне выбранной области при включённом автоответе аккаунта, но не даёт доступа к личным источникам и не обходит политику подготовки/отправки. При неизвестной достоверной разметке сервис не угадывает её из текста.

## Наблюдатель групп

Для выбранных групп и каналов: совпадение по словам и выражениям правила → проверка моделью со строгим форматом ответа → уведомление владельцу в управляющий чат. Сам наблюдатель в группе не пишет и прочитанным её не отмечает: в его модуле нет обращения к Telegram. Отдельный путь группового ответа описан ниже; включение наблюдателя не даёт ему прав. Свои лимиты проверок и уведомлений в час и в сутки, защита от повторов. Работает на любом аккаунте, который состоит в группе, и при выключенной отправке.

С Р-84 правило смотрит не только свои чаты (`chat_ids`), но и сферы (`sphere_ids`): все группы и каналы сферы, в том числе добавленные в неё позже; личные чаты сферы наблюдатель не смотрит. Хотя бы одно из двух не пусто. Правила заводятся, меняются и удаляются на странице настройки (раздел «Наблюдатель», с тремя шаблонами — «Сроки и деньги», «Срочно», «Ваше имя») сразу, а через внутренний API (`/api/watch/rules`) — как раньше, расширение ждёт владельца; новая сфера в правиле — расширение.

## Уведомления владельцу

Решение Р-84, код — `notify/`, миграция `0033_notify.sql`. Сервис сам, без модели, пишет владельцу в бот согласований:

- **«💬 Вам написали»** — новое входящее от человека в личном чате основного аккаунта: не «Избранное», не чат с ботом, не служебные чаты Telegram и не управляющий бот, не от бота и не через бота, не правка, не своё. Кому — по настройке: от всех, только из выбранных сфер, только от выбранных людей (по числовому ID);
- **«📣 Вас упомянули»** — прямое обращение в группе, то же определение, что в разделе «Ответы в группах и темах»: разметка упоминания числового ID владельца, ответ на его настоящее сообщение в том же чате и теме, заданное владельцем обращение в начале реплики («Иван, …»). Плюс разметка упоминания `@имени`, если это `@имя` владельца, как его сообщил Telegram. Имя в тексте, цитате, коде и пересылке обращением не считается. Нужна разметка живой сессии; сообщения из выгрузки не рассматриваются.

Только живые сообщения: событие `message.live`, а скрытые защитой — `message.held` (его слушают только уведомления; текст в уведомлении не показывается: «скрыто защитой — решите в карточке защиты»). Догрузка истории, импорт и правки уведомлений не порождают; «живое» сообщение старше трёх часов — тоже (догонялка после перерыва связи).

Что в уведомлении: кто, где (и сферы чата), когда, начало сообщения до 300 знаков — одной строкой, без невидимых и управляющих символов, простым текстом; метка вложения («🎤 голосовое, 0:42», «🖼 фото», «📎 файл «Смета.pdf»»); пересланное — «↪ пересланное от …»; расшифровка или пересказ, если готовы к моменту отправки; ссылка «Открыть», если у чата есть @имя.

**Одно уведомление на пачку (Р-93).** В режиме «сразу» уведомление уходит, когда пачка сообщений закрылась (раздел «Пачки сообщений»), — не позже `SHTURMAN_PACK_GAP` секунд после последнего сообщения: «3 сообщения: ↪ пересланное от Ивана Петрова: «…» · 🖼 фото (2) · «…»» — до 120 знаков на сообщение и 600 на строку, альбом — одной частью со счётом. Пачка уведомлений «раз в N минут» и тихие часы работают как раньше: в них свой срок.

**Кнопки (Р-89, `notify/buttons.py`)** — у уведомления об одном чате (уведомление «раз в N минут» о нескольких чатах их не несёт): «Подготовить ответ» (только личные, на всю пачку и только если ответ подготовить можно — `can_prepare`), «Напомнить через час», «Не сообщать об этом чате». Данные — `sh:nt:p|l|m:<строка очереди>:<метка>`, метка — новая на каждое уведомление (`notify_items.nonce`); нажатие — только привязанный владелец в личном чате с ботом. «Не сообщать об этом чате» — сразу (сужение): чат в `muted_chats`, ждущие уведомления чата снимаются, ответ «Готово… Вернуть — в «Настройках Штурмана», раздел «Уведомления»», журнал `notify.mute`. «Напомнить через час» — та же строка снова ждёт час (`reminder`) и уходит с пометкой «⏰ Напоминаю: вы ещё не ответили», только если владелец к тому времени не ответил. «Подготовить ответ»: способ «Через ваш аккаунт» — разовая репетиция (раздел «Репетиция ответов на основном аккаунте»); «Через бота и помощника» — черновик только для просмотра (`drafts.create(prepare_only=True)`), если «Черновики ответов» включены (`/prepare on`), иначе — ответ, как их включить. Пока ассистент остановлен, «Подготовить ответ» отвечает отказом; уведомления и две другие кнопки работают.

Очередь — таблица `notify_items`: строка на сообщение, время отправки, итог (`sent` или `dropped` с причиной: `answered` — владелец уже ответил в этом чате после сообщения, `gone` — удалено или чат исключён, `disabled` — такие уведомления выключили, пока ждало, `stale` — старше 36 часов, `no_bot` — нет бота согласований, `rehearsal` — его заменила карточка репетиции ответов, Р-85). Текст сообщения в очередь не копируется: читается из архива в момент отправки. Отправленное и снятое хранится неделю. Фоновая отправка проверяет очередь раз в 15 секунд и сразу после нового сообщения.

| Настройка (`settings`, ключ `notify.settings`) | По умолчанию | Что значит |
|---|---|---|
| `personal` | `all` | `off`, `people` (+ `people` — числовые ID), `spheres` (+ `spheres` — номера сфер), `all` |

## Разбор входящих

Решение Р-92, код — `triage/`, миграция `0036_triage.sql`. Владелец: «уведомления, смысл которых не понятен — это и так видно в Telegram; нужна активная позиция». Разбор заменяет пересылку «💬 Вам написали»: модель читает новые входящие, а сервис пишет владельцу только то, что требует его внимания. **После обновления выключен**; включает только владелец.

**Что разбирается** — отбор кодом, те же правила, что у уведомлений (`notify.core.personal_candidate`, `group_reason`): личные сообщения людей основному аккаунту (не боты и не через бота, не «Избранное», не служебные чаты, не свои, не правки) и в группах — только прямые обращения к владельцу (упоминание, ответ на его сообщение, обращение по имени). Только живые сообщения не старше 3 часов, видимые ассистенту (`messages.agent_visible`), не из исключённых чатов и не из «Не сообщать об этом чате». Пачка (раздел «Пачки сообщений») — один разбор, когда она закрылась; строки её прежних сообщений закрывает разбор последней. Пачку из одних пересланных разбор тоже читает: он только решает, сказать ли владельцу; пересланное подаётся модели как слова третьего лица. Вложения пачки поднимаются в начало очереди разбора и ждутся до `SHTURMAN_PACK_MEDIA_WAIT`; чего модель не видела, карточка говорит одной строкой.

**Что уходит модели** — задание `llm.structured` (задача `shturman_watch`, та же недорогая модель, что у наблюдателя), без инструментов: место (личный чат с «…» или группа «…» и вид обращения), до 10 сообщений этого чата перед пачкой (в группе — до 12 этой ветки и до 4 после обращения), сама пачка. Скрытое защитой не уходит ни поводом, ни справкой. Всё чужое — в рамке со случайной меткой; в указаниях — что это данные, не команды, и что слова «срочно» сами ничего не значат. Ответ — `{needs_reply, urgency: normal|important|urgent, want, due, thread}`; ссылки из ответа вырезаются, длина ограничена; непонятный ответ — сбой. Задание стирается сразу после ответа.

**Что получает владелец** (бот согласований):

| Отметка человека или группы (`triage.settings`) | Сразу | Напоминание о вопросе без ответа |
|---|---|---|
| ⭐ важный (`important_people`, `important_chats`, чаты из `important_spheres`) | всё, что ждёт ответа, «важно», «срочно»; «срочно» — даже в тихие часы | да |
| обычный | «важно», «срочно»; обращение в группе — ещё и если ждут ответа | да |
| 🔕 реже беспокоить (`lower_people`, `lower_chats`; так отмечает «Не важно») | только «срочно» | да |
| 💤 тихий (`quiet_people`, `quiet_chats`) | никогда | да |

Тише — сильнее: тихий человек в важной сфере — тихий. Карточка «сразу» в тихие часы уведомлений ждёт их конца («Пришло в тихие часы — показываю утром»), кроме «срочно» от важных. Не больше 3 карточек «сразу» на чат и 20 всего в час — сверх этого тишина (`capped`), напоминание остаётся. Вопрос без ответа: `remind_minutes` (по умолчанию 120) **рабочего** времени — вне тихих часов — после сообщения; владелец написал в этом чате (в группе — в этой ветке) — ожидание снимается молча. Напоминание одно; «Напомнить через час» — ещё одно.

Карточки — суть, а не пересказ: «🔴 Срочно / Петров (Корпус 3): бетон не пришёл, просит решение до 14:00 / Личный чат · 10:42», «⏰ Иван ждёт ответа 2 ч: просит смету по корпусу 3», «📣 В «Корпус 3» вас спросили: … / О чём ветка: …». Кнопки (`sh:tr:p|l|n|m:<строка>:<метка>`; метка строки — `triage_items.nonce`; нажатие — только привязанный владелец в личном чате с ботом): «Подготовить ответ» (только личные; тот же путь, что у уведомления: разовая репетиция или черновик только для просмотра), «Напомнить через час», «Не важно» (об этом сообщении больше не напоминать; человек или группа — на ступень тише: важный → обычный → «реже» → тихий; ответ говорит, как вернуть; журнал `triage.feedback`), «Не сообщать об этом чате» (как у уведомлений, `muted_chats`). Отправки собеседникам нет и быть не может.

**Связка с уведомлениями.** Пока разбор работает (включён, есть свой бот, ассистент не остановлен), «Вам написали» и «Вас упомянули» о разбираемых сообщениях не приходят (`notify.core` спрашивает `triage.takes`); скрытое защитой — по-прежнему уведомлением без текста. Выключил разбор — пересылка вернулась с прежними настройками. Разбор не состоялся — сбой модели, непонятный ответ, «Остановить всё» или выключение посреди — сообщения пачки уходят обычным уведомлением (`Notifier.fallback`); о сбое модели — одно сообщение в бот не чаще раза в 6 часов.

**«Остановить всё» (Р-87).** Разбор — действие ассистента (модель и карточки), поэтому при остановке он не идёт: новых строк нет (проверка в коде и триггер `triage_items_halt`), начатые снимаются (`stopped`) и приходят обычным уведомлением, карточки и напоминания не уходят. **Прежняя простая пересылка на время остановки работает** — владелец не теряет сигнал. Ожидания ответа сохраняются: после «Продолжить» напоминания вернутся.

**Включение — только владелец.** Страница «Настройки Штурмана», карточка «Уведомления», блок «Разбор входящих»: что уходит модели, оценка объёма и цены по счётчикам за 7 дней, «Включить разбор…» — карточка `triage.enable` в бот (`confirm.request_card`, `BOT_ONLY`); включает нажатие «Да, сделать» в самом боте. Выключить, правила (люди и группы с отметкой, поиск по имени; важные сферы; срок напоминания) — там же, сразу. Внутреннего API у разбора нет: ассистент и дашборд Hermes не включают его и не меняют правила. При смене владельца разбор выключается, правила очищаются.

**Хранение** — `triage_items`: строка на пачку — номера сообщений, выводы модели одной строкой (`want` до 200 знаков, `due`, `thread` до 300), отметка, состояния показа и ожидания. Текста сообщений нет. Строки хранятся 14 дней.

**Утренняя сводка.** Инструмент архива `list_awaiting_reply` (MCP, только чтение): кто ждёт ответа владельца — кто, чат, что хотят (вывод модели в рамке чужого текста), срок, срочность, сколько ждёт, номер сообщения для `get_context`; только видимое ассистенту из неисключённых чатов, без текста сообщений; разбор выключен — `not_found`. Скилл `morning-brief` строит из него раздел «Ждут вашего ответа».

**Учёт.** `GET /api/status`: `triage_enabled`, за сутки `triage_analyzed_24h`, `triage_shown_24h`, `triage_reminded_24h`, `triage_failed_24h`, сейчас `triage_waiting`, `triage_in_progress`. `/status` в боте: «Разбор входящих: вкл, за сутки: N разобрано, M показано, K ждут ответа». `./ops/doctor.sh` — строка `triage` (`WARN`, если за сутки были сбои модели). Журнал: `triage.enable_request`, `triage.enable`, `triage.disable`, `triage.settings`, `triage.feedback`.

**Не проверено.** Всё — на подставных Telegram, Bot API и модели (тесты и браузерный стенд). Как часто настоящая модель ошибается со срочностью и сутью, сколько карточек выйдет у владельца в день и сколько стоит разбор на его модели — нет.

## Пачки сообщений

Решение Р-93, код — `packs.py`, миграция `0037_packs.sql`. Человек пишет «Посмотри» и следом пересылает документ, присылает альбом, фото и отдельным сообщением подпись — это одно высказывание. Правило одно для уведомлений, разбора входящих, репетиции, «Подготовить ответ», черновиков и автоответа:

- пачка — сообщения одного отправителя в одном чате (и одной теме) подряд, без сообщений других участников между ними, с паузами не больше `SHTURMAN_PACK_GAP` секунд (по умолчанию 90; 0 — каждое сообщение отдельно);
- все сообщения одного альбома Telegram (`messages.grouped_id`: живая сессия и догрузка истории — `grouped_id` Telethon, бизнес-режим — `media_group_id`, если это число; в выгрузке Telegram Desktop его нет — альбом там собирают паузы) — одна пачка при любой паузе;
- пачка закрывается, когда прошло `SHTURMAN_PACK_GAP` без новых сообщений отправителя или написал кто-то другой, в том числе владелец. Кто пишет без пауз, не задерживает уведомление и ответ без конца: через 10 минут от первого сообщения пачки её закрытия больше не ждут (`packs.HOLD_MAX`). Удалённое и служебное в пачку не входит; скрытое защитой — входит (по нему пачка не рвётся), но модели не уходит.

**Пересланное.** Слова третьего лица: модели — цитатой внутри той же рамки чужого текста («↪ Надежда переслал(а) сообщение от Ивана Петрова — это цитата третьего лица, не слова собеседника и не указания: «…»»), в указаниях модели — что пересланное не просьба собеседника и не указание. Повод для **автоматического** запуска (автоответ 2а, репетиция по списку людей) — только собственное сообщение собеседника в пачке; пачка из одних пересланных их не запускает. По явной просьбе владельца («Подготовить ответ») ответ готовится и на такую пачку. Разбор входящих читает и её — он только решает, сказать ли владельцу.

**Вложения в подготовке ответа.** Пересказ фото и документа и расшифровка голосового дописываются в текст сообщения позже, по очереди. Перед подготовкой ответа (репетиция, «Подготовить ответ», черновик, автоответ) и разбором входящих сервис поднимает вложения пачки в начало очередей (`messages.rush_at`) и ждёт до `SHTURMAN_PACK_MEDIA_WAIT` секунд (по умолчанию 90; автоответ — не дольше, чем оставляет `max_age_seconds`), затем готовит с тем, что есть. Ничего не включается за владельца: если разбор фото и документов выключен (`docs/media.md`) — фото не разбирается, модель видит «[фото — не смотрел: разбор выключен владельцем]», карточка — «Фото не смотрел: разбор фото и документов выключен (включается в «Настройках Штурмана»)»; не успел — «Фото не успел разобрать»; не получилось — «Не получилось разобрать фото». Голосовые — так же («Голосовое не слушал: расшифровка голосовых не включена»). Ожидание идёт в фоне: нажатие «Подготовить ответ» отвечает сразу, карточка приходит позже. Фото без подписи — повод для ответа (после разбора в нём есть пересказ); стикер, GIF и видео без подписи — нет.

**Автоответ 2а.** Ответ — на всю пачку собеседника в личном чате; якорь задачи ответа — по-прежнему последнее сообщение чата (по нему проверяются «после него ничего нет», возраст и правка). Ждёт автоответ столько, сколько задал владелец (`debounce_seconds`), а не `SHTURMAN_PACK_GAP`: доверенный собеседник ждёт быстрого ответа; ответ закрывает пачку, дописанное после — уже следующая. Пересказ вложения, дописанный сервисом после регистрации задачи, обновляет отпечаток повода (`reply_tasks.trigger_hash`), пока задача не ушла модели; правка собеседника (`edited_at`) — нет, такая задача снимается, как и раньше. В группах автоответ отвечает на одно сообщение, как раньше.

## Повтор после сбоя

Решение Р-84, код — `retry.py`. Когда задания модели долго не выполняются, очередь честно сдаётся: вложение после четырёх попыток помечается «не получилось» (`media_state = 'failed'`), запрос обработки переписки после двух повторов — «пропущен» (`processing_requests.state = 'given_up'`). Повтор возвращает в работу:

- вложения с причиной сбоя модели — `model:…`, `lost_job`, `bad_answer` — не старше `SHTURMAN_MEDIA_DAYS`, не удалённые, из неисключённых чатов, если разбор включён владельцем: снова в очередь, попытки с нуля. «Пропущено» (вид файла, размер, файла нет, скачать нечем) и прочие причины не повторяются;
- запросы обработки, от которых прогоны отказались: в «повторить» (`retry`); следующий прогон (ночью) поставит их первым делом и проверит их сообщения заново (исключённый чат, удалённое, скрытое защитой не идут). Отметку прогона сбрасывать не нужно: запрос хранит свои сообщения. В отметке прогона ставится «есть ещё» — ночные прогоны продолжат;
- страницы памяти без свежей сводки пересобираются следующей сборкой сами — их только считаем.

`--since ДАТА` (на странице — «Сбой начался») — с какой даты считать: время отметки «не получилось» у вложения и время запроса обработки. Запускает владелец кнопкой на странице или оператор по его решению: `docker exec shturman-service shturman retry-failed [--since ГГГГ-ММ-ДД] [--dry-run]`. Повторный разбор снова отправляет данные провайдеру модели и тратит запросы — поэтому во внутреннем API повтора нет. Итог — в `settings` (`retry.last`: когда, сколько, кто), в `GET /api/status` (`retry_media_failed`, `retry_requests_given_up` — сколько можно вернуть; `retry_last_media`, `retry_last_requests`, `retry_last_at`), строкой `retry` в `./ops/doctor.sh` и на странице; журнал действий `retry.failed`. Голосовые не повторяются: их распознаёт свой контейнер, а не модель.

## Защита от внедрённых инструкций

По умолчанию выключена. Когда включена, каждое входящее текстовое сообщение при записи в архив оценивает малая модель-классификатор в отдельном контейнере без выхода в интернет. Подозрительное сообщение скрывается от ассистента: его нет в поиске, в истории, в запросах к модели, из него не извлекаются обязательства, на него не готовится автоответ. Владелец получает одно уведомление с кнопками «Показать ассистенту» и «Оставить скрытым» — о сообщениях живого потока и свежих (не старше `SHTURMAN_GUARD_CARD_HOURS`, 24 ч). Скрытое из истории (импорт, догрузка старых сообщений) отдельных карточек не получает: раз в сутки, когда фоновая проверка дошла до конца, приходит сводка — сколько, почему, откуда — с решением разом через подтверждение `guard.release_all` / `guard.keep_all` или «Разбирать по одной»; та же сводка — по `/guard` и сверху раздела «Защита» в приложении (Р-99). Во внутреннем API нет ни выключателя защиты, ни текста скрытых сообщений, ни способа их открыть.

Числа на переписке владельца — `./ops/guard.sh stats` (`shturman guard stats`): скрыто на 1000 проверенных, по причине, типу чата, пересланному, живому потоку и истории, решения владельца и доля «показано» среди решённых поштучно, «если бы порог был X», варианты Р-99 — без текстов и названий чатов. Порог меняет только владелец: `./ops/guard.sh threshold ЧИСЛО`, фраза в его терминале.

Это снижение риска, а не гарантия: тихие попытки — просьба переслать данные, сказанная как обычная просьба, — модель ловит редко. Что защита ловит и чего не ловит, измеренные числа, поведение при недоступной модели и переменные окружения — `docs/guard.md`.

## Разбор фото и документов

По умолчанию выключен; включает и выключает владелец на странице настройки переписки, шаг «Фото и документы» (`PUT /shturman-setup/api/media`; решение хранится в `setup_state`, внутренний API его не меняет). Фото и документы не старше `SHTURMAN_MEDIA_DAYS` дней и не больше 20 МБ берутся из загруженной выгрузки, сессией аккаунта или своим ботом; текст документа сервис достаёт сам (`media/extract.py`), фото и сканы уходят модели заданием `llm.structured` с полем `images` (задача `shturman_media`). Пересказ дописывается в текст сообщения (`media_summary`, функция `media_text`, миграция `0028_media.sql`). Вложения, по которым готовится ответ или идёт разбор входящих, очередь берёт первыми (`messages.rush_at`, раздел «Пачки сообщений»). Счётчики — `GET /api/media/status` и строка `media` в `./ops/doctor.sh`. Подробно — `docs/media.md`.

## Расшифровка голосовых и «кружков»

По умолчанию выключена; включает оператор по решению владельца (`./ops/asr.sh on`). Голосовые и «кружки» из читаемых чатов не старше 30 дней берутся из загруженного архива выгрузки, если он был (раздел «Выгрузка архивом zip»), иначе скачиваются тем же путём, каким пришло сообщение: через сессию аккаунта по номеру сообщения или через своего бота по `file_id`. Звук разбирает модель GigaAM-Multilingual в отдельном контейнере `asr` без выхода в интернет; хранится только текст. Расшифровка лежит в `messages.transcript`, а текст сообщения собирается из неё и подписи функцией базы `voice_text` — дальше поиск, обязательства, ассистент и защита от внедрённых инструкций работают с ним как с обычным текстом. Состояние — `GET /api/voice/status` (только числа), строка `voice` в `./ops/doctor.sh` и строка «Голосовые и «кружки»» в разделе «Что собрано» на странице настройки. Что попадает в очередь, сбои и повторы, измеренные числа и какой нужен сервер — `docs/voice.md`.

## Выгрузка архивом zip

Выгрузку Telegram Desktop можно загрузить двумя способами — на странице настройки и в терминале (`./ops/import-export.sh`): одним файлом `result.json` или архивом zip всей папки выгрузки. Вид файла сервис определяет по первым байтам (`PK\x03\x04` — архив), а не по имени. Загруженный архив лежит в `data/shturman/uploads/export-<номер>.zip`, файл — в `export-<номер>.json`; предел размера общий, 2 ГиБ (`SHTURMAN_UPLOAD_MAX_BYTES`).

**result.json в архиве.** Берётся член архива с именем `result.json` на наименьшей глубине: владелец сжимает папку `ChatExport_…` или `Telegram Desktop/DataExport_…`. Его нет — понятный отказ («в архиве нет файла result.json…»), файл загрузки удаляется. Архив с паролем, архив, сжатый способом кроме «без сжатия» и deflate (так сжимают «Сжать» в macOS и «Сжатая ZIP-папка» в Windows), и result.json, сжатый сильнее 200:1, не принимаются — с объяснением, что делать. Просмотр и импорт читают result.json прямо из архива потоком, не распаковывая; ход показывается по прочитанным байтам result.json, а не архива.

**Файлы вложений.** По ходу импорта сервис запоминает сообщения, файлы которых нужны:

- голосовые и «кружки» — если включена расшифровка (`SHTURMAN_ASR=on`) и сообщение не старше `SHTURMAN_ASR_DAYS` дней;
- фото и документы — если владелец включил их разбор (запись `media.enabled` в `settings`) и сообщение не старше 30 дней (`media_days`, переменная `SHTURMAN_MEDIA_DAYS`).

Когда сообщения записаны, файл каждого из них копируется из архива в `data/shturman/media-files/` — под случайным именем, с правами 600 (`media/files.py`, `media/from_export.py`), — и путь пишется в `messages.media_file`. Имя файла из архива на диск не попадает: путь из result.json только ищется среди членов архива (после приведения разделителей; абсолютный путь, имя диска и `..` отбрасываются), а содержимое копируется в свой новый файл. Файл не берётся, если его нет в архиве, член архива зашифрован или сжат неподдерживаемым способом, сжат сильнее 200:1 при размере больше 1 МБ («zip-бомба»), больше предела (`asr_max_bytes` для голосовых, `media_max_bytes` для фото и документов, по 20 МБ) или сообщению уже не нужен — расшифрован, разобран, удалён, его чат исключён. Голосовое, снятое с очереди из-за того, что скачать его было нечем (`no_source`), с файлом возвращается в очередь. Итог — в счётчиках импорта: `media_files` (взято на разбор), `media_skipped` (не взято), `media_no_space` (на диске кончилось место: копирование остановлено, импорт сообщений при этом сохранён). Страница показывает их после импорта. Копирование идёт в отдельном потоке и останавливается так же, как импорт, — удалением загрузки или остановкой сервиса; недописанный файл удаляется.

**Сколько файл лежит.** Очередь голосовых берёт файл отсюда, а не из Telegram; закончив с сообщением (готово, пропущено, не получилось), удаляет его (`media.files.drop`). Файла нет или он не читается — голосовое скачивается из Telegram, как без архива. Раз в 10 минут уборка импорта (`media.files.sweep`) удаляет: файлы, на которые не ссылается ни одно сообщение, старше часа; файлы сообщений, которые уже не ждут ни расшифровки, ни разбора, старше суток; файлы удалённых сообщений и исключённых чатов — сразу; любой файл старше 45 дней. Ссылку на пропавший файл она снимает. В копию данных (`./ops/backup.sh`) каталог `media-files` не входит.

## Обязательства и страницы памяти

Ночной прогон (по умолчанию в 03:30 по часам владельца) берёт новые сообщения, режет их на эпизоды и отправляет модели только те, где есть похожее на обещание. Ответ модели проверяется текстом сообщений: цитата и формулировка срока обязаны в нём быть. Дату по формулировке считает код, а не модель; если формулировка не сводится к одной дате — обязательство помечается «нужно уточнение». Найденное записывается как предложение, владелец получает одну сводку с кнопками и принимает или отклоняет каждое. При первом прогоне разбираются последние 30 дней.

Тем же запросом на эпизод модель называет факты (должность, телефон, цена, срок…), решения по проектам и названия проектов (с версии запроса 3; отбор эпизодов — ещё и по признакам факта: числа с единицами, деньги, даты, «решили», «теперь», «новый номер»). Цитата факта обязана быть в сообщении эпизода, которое можно считать источником. Факт о человеке, которого владелец подтвердил, и о заведённом проекте пишется сразу; новый факт с тем же ключом закрывает прежний датой. Факт о самом владельце владелец принимает кнопкой — одно сообщение «Профиль: запомнить это о вас?» на прогон. Незнакомое название проекта копится упоминаниями; после трёх упоминаний в двух разговорах за 30 дней, а также для группового чата с 20 сообщениями за 30 дней без проекта, владелец получает «Проекты из переписки: завести страницу проекта?» с кнопками. Отклонённое не предлагается снова.

После прогона собираются страницы о людях и проектах, профиль владельца — когда в нём есть одобренные факты или правила. Что из устройства памяти сделано, а что нет — `docs/memory.md`.

Маршруты памяти (внутренний API; изменения — через карточку в боте согласований, кроме отказа от предложения). Карточка показывает всё, что будет записано: блок владельца через API — не длиннее 1800 знаков (код `too_long_for_card`, длинный текст — на странице настройки), описание проекта — до 300 знаков, все его другие названия; чужое название проекта — отказ `name_taken`; изменение чатов хранится разницей; согласие на отклонённое предложение — сразу 409:

| Маршрут | Что делает |
|---|---|
| `GET /api/projects?status=` | Проекты: `proposed`, `active`, `archived`, `rejected`; без параметра — все, кроме отклонённых |
| `POST /api/projects` `{title, chat_ids?, aliases?, description?}` | Завести проект (`projects.create`) |
| `GET /api/projects/{id}` | Карточка проекта и блоки его страницы |
| `POST /api/projects/{id}/chats` `{chat_ids}` или `{add, remove}` | Изменить чаты проекта (`projects.chats`) |
| `POST /api/projects/{id}/archive` | В архив (`projects.archive`) |
| `PUT /api/projects/{id}/owner-block` `{text}` | Блок владельца страницы проекта (`pages.owner_block`) |
| `POST /api/projects/proposals/{id}` `{accept}` | Принять (`projects.accept`) или сразу отклонить предложение |
| `GET /api/facts?subject=person:N\|project:N\|owner&include_closed=` | Факты и решения; без `include_closed` — только действующие сейчас |
| `POST /api/facts/{id}/retract` | Отметить факт неверным (`facts.retract`); прежнее значение снова действует |
| `GET /api/owner/profile` | Профиль: страница, одобренные факты, сколько фактов ждёт решения |
| `PUT /api/owner/profile/owner-block` `{text}` | Правила и постоянные указания (`pages.owner_block`) |

Принятые договорённости владелец отмечает выполненными, переносит и убирает как записанные неверно в приложении «Штурман», экран «Договорённости» (Р-94, маршруты `app/commitments…` выше): сразу, в контексте владельца из Telegram. «Не так» у принятой — новое действие `commitments.mark_wrong` (`open` → `rejected`, событие `marked_wrong`), перенос датой — `commitments.reschedule_to`; оба только для владельца, во внутреннем API их нет.

Страница настройки (экран «Память») делает то же своим входом, без карточки (`confirm.apply_owner` или функции `processing/projects.py` и `processing/facts.py` в контексте владельца).

**Качество договорённостей и расписание (Р-96, подробно — `docs/memory.md`, «Договорённости: что предлагается владельцу» и «Расписание прогонов»).** К эпизоду — блок «После»: сделанное или отменённое до показа не предлагается (тихо, `expired` с причиной в `quiet_reason` и событием `quiet_closed`); проверка закрытия — и по ещё не принятому, и по принятому (принятое — только предложением владельцу), с момента обещания; быстрые обещания ждут суток; «между другими» — статус `team` («В команде»: `GET /api/commitments?view=team`, инструмент `list_commitments` с `view: "team"`), без кнопок и не в сводке; голое согласие — только с просьбой из эпизода; ключи и токены не уходят модели (`sanitize.redact_secrets` в `bridge.request_structured` и `bridge.request_text`). Кнопки под сводкой: прежние `a:`, `r:`, `ca:`, `cr:`; после «не так» — причины `w:<id>:<код>` (дописывают причину к уже отклонённому, по желанию); в приложении — `rw:<id>:<код>` (отклонить с причиной). Обработка днём — раз в час вне тихих часов, в пределах запросов в час и в сутки; сводка с кнопками — в часы сводки (по умолчанию 13:00 и 19:00). В `GET /api/status` — `processing_runs_24h`, `processing_requests_24h`, `processing_tokens_24h` (оценка), `processing_capped`, `commitments_proposed|open|team|quiet|rejected`, `recheck_done`, `recheck_at`, `old_prompt_items`; в `./ops/doctor.sh` — строки `processing` и `commitments`.

## Как пользоваться без веб-интерфейса

Вход в аккаунт Telegram, выбор чатов и загрузку выгрузки владелец делает в браузере, на странице настройки переписки (`docs/setup.md`). Команды ниже — запасной путь для того же самого и единственный путь для того, чему экранов ещё нет: исключения чатов, защиты, поиска по смыслу. Всё ниже делается в терминале сервера. Команды показывают названия чатов и имена людей, а часть из них меняет то, что хранится в архиве, поэтому выполняет их владелец либо агент по его явной просьбе в текущей сессии (`AGENTS.md`).

Сначала — `./ops/up.sh` и `./ops/doctor.sh` со строкой `PASS service`.

### Загрузить экспорт Telegram Desktop

Основной путь — страница настройки переписки: файл загружается из браузера. Запасной — ниже. Экспорт делается в Telegram Desktop в формате JSON. На сервер переносится файл `result.json` или архив zip всей папки выгрузки — из архива импорт берёт и файлы голосовых, фото и документов (раздел «Выгрузка архивом zip»).

```
./ops/import-export.sh scan /путь/к/result.json
./ops/import-export.sh import /путь/к/архиву.zip --exclude user:123456789
```

`scan` ничего не записывает: показывает чаты с числом сообщений и периодом. Во втором столбце списка — вид и идентификатор чата (`user:…`, `chat:…`, `channel:…`); его и нужно передать в `--exclude`, чтобы чат не попал в архив. `--exclude` можно повторять. Исключение запоминается для всех источников. Для экспорта одного чата нужен `--owner-id` с числовым идентификатором владельца. Повторный импорт того же файла дублей не создаёт. Файл подключается контейнеру только для чтения и сам никуда не копируется; из архива копируются только нужные файлы вложений — в `data/shturman/media-files`, тем же порядком, что при загрузке на странице (контейнер команды работает с тем же каталогом данных, что и сервис). После импорта выгрузку стоит удалить с сервера — в ней вся переписка открытым текстом.

### Войти в аккаунт Telegram

Основной путь — страница настройки переписки, шаги «Ключи приложения Telegram» и вход в аккаунт (свой — в способе «Через ваш аккаунт», аккаунт помощника — в способе «Через бота и помощника»). Запасной — в терминале. Нужны `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` собственного приложения владельца (my.telegram.org → API development tools). Их вводит человек: на странице либо в своём терминале — `./ops/init-env.sh`, затем `./ops/up.sh` (`docs/setup.md`).

```
./ops/tg-login.sh assistant
./ops/tg-login.sh owner
```

Первая команда подключает аккаунт-помощник, вторая — основной аккаунт владельца, только на чтение. Скрипт запускает **человек**: в терминале появляется QR-код, его сканируют телефоном («Настройки → Устройства → Подключить устройство»). Если на аккаунте включён облачный пароль, он вводится скрыто и нигде не сохраняется. Агент этот скрипт не запускает и его вывод не читает.

### Выбрать чаты

Основной путь — страница настройки переписки, шаг выбора чатов. Запасной — командами:

```
docker exec shturman-service shturman call GET /api/tg/accounts
docker exec shturman-service shturman call GET '/api/tg/accounts/1/dialogs?limit=100'
docker exec shturman-service shturman call POST /api/tg/accounts/1/sync '{"enabled": true, "chats": [{"peer_class": "user", "tg_id": 123456789}]}'
docker exec shturman-service shturman call GET /api/tg/accounts/1/sync
```

Первая команда показывает подключённые аккаунты; число из поля `account_id` подставляется вместо `1` в остальных. Вторая — чаты аккаунта с полями `peer_class` и `tg_id` из базы; если список устарел или его нет, она запускает загрузку из Telegram в фоне — ход в поле `load`, повторите команду, когда `load.running` станет `false` (обновить принудительно — `?refresh=1`). Третья включает выбранные чаты; вместо списка можно включить все чаты одного вида: `{"enabled": true, "types": ["personal_chat"]}`. Значение `"enabled": false` чат выключает. Четвёртая показывает ход загрузки.

Глубина истории: по умолчанию 12 месяцев. Изменить для аккаунта — `PUT /api/tg/accounts/1/options` с телом `{"backfill_months": 6}`; для одного включения — поле `"since": "2026-01-01"` в запросе `sync` (`null` — вся история).

### Исключить чат из архива

```
docker exec shturman-service shturman call GET '/api/chats?query=название'
docker exec shturman-service shturman call PUT /api/chats/42/excluded '{"excluded": true, "purge": true}'
```

Первая команда находит чат и его номер в архиве (поле `id`); он подставляется вместо `42`. `"purge": true` стирает уже сохранённые сообщения чата — это необратимо. Вместе с чатом уходит всё, что из него выведено: обязательства, строки страниц, черновики, векторы. Вернуть чат — `{"excluded": false}`. Служебные чаты Telegram вернуть нельзя.

### Включить защиту от внедрённых инструкций

```
./ops/guard.sh on
./ops/guard.sh status
./ops/guard.sh stats            # только числа на вашей переписке (Р-99)
./ops/guard.sh threshold 0.97   # порог модели — только владелец: «Разрешить» в боте согласований (Р-100)
./ops/guard.sh off
```

`on` скачивает модель-классификатор (около 0,3 ГБ с huggingface.co, с проверкой контрольных сумм), добавляет контейнер с ней (около 0,6 ГБ памяти) и перезапускает стек. Это стоп-точка: нужна память и скачивание; до включения владельцу стоит прочитать раздел «Что защита ловит и чего не ловит» в `docs/guard.md`. `off` выключает проверку; уже скрытые сообщения остаются скрытыми, пока владелец не решит по ним в боте. Включает и выключает защиту только владелец.

### Включить поиск по смыслу

```
./ops/embeddings.sh on                       # модель из настроек; если её там нет — e5-small
./ops/embeddings.sh on --model user2-small   # выбрать или сменить модель: e5-small | user2-small
./ops/embeddings.sh status
./ops/embeddings.sh off
```

`on` скачивает модель (около 0,5 ГБ у `e5-small`, 0,14 ГБ у `user2-small`; с huggingface.co, с проверкой контрольной суммы каждого файла), добавляет контейнер с ней (около 1,2 ГБ памяти у `e5-small`, 0,2–0,7 ГБ у `user2-small`) и перезапускает стек. Это стоп-точка: нужна память и скачивание. Сам контейнер эмбеддингов в интернет не ходит. Без него поиск работает по словам: сначала «все слова сразу», затем, если нашлось мало, «любое из слов».

Моделей две, по умолчанию — `intfloat/multilingual-e5-small`; `deepvk/USER2-small` на нашем наборе лучше находит короткие русские сообщения и хуже — длинные тексты. Чем они отличаются и на чём это измерено — `docs/search.md`.

**Смена модели — отдельная стоп-точка, решает владелец.** Векторы всех сообщений пересчитываются заново: по пересчёту со стенда — около трёх часов на 300 000 сообщений. Пока идёт пересчёт, поиск по смыслу видит только уже пересчитанные сообщения (сначала свежие), поиск по словам — весь архив; векторы двух моделей в одной выдаче не смешиваются. Прежние векторы не хранятся: возврат к прежней модели — такой же пересчёт, но файлы моделей повторно не скачиваются. Ход пересчёта — строка `embeddings` в `./ops/doctor.sh` и `./ops/embeddings.sh status`.

## Модель данных архива

| Таблицы | Что хранят |
|---|---|
| `accounts`, `peers`, `chats` | Точки зрения (основной аккаунт, помощник); люди, боты, группы, каналы по идентификаторам Telegram; чат с точки зрения аккаунта и признак «исключён» |
| `messages`, `message_versions` | Сообщения дословно: текст, разметка, ответ-на, пересылка, вид вложения, вектор, расшифровка голосового и её состояние (`transcript*`, `media_duration`, `media_ref`), признак «видно ассистенту» и итог проверки на внедрённые инструкции; прежние формулировки отредактированных сообщений |
| `guard_alerts` | Уведомления владельцу о скрытых текстах и его решения; самого текста нет. `via`: `card` — кнопкой под карточкой, `bulk` — разом, сводкой (Р-99) |
| `imports` | Журнал импортов с итогами |
| `settings`, `jobs`, `business_connections` | Настройки сервиса; очередь заданий с отметкой, кто выполняет задание; подключения бота в бизнес-режиме с отметкой, через какого бота |
| `pending_actions` | Действия, которые ждут нажатия владельца в боте согласований |
| `executor_state`, `executor_bind_codes` | Состояние бота согласований и одноразовые коды привязки владельца (хранится хеш кода). Через внутренний API недоступны |
| `tg_sessions`, `tg_sync_chats` | Какой аккаунт занимает роль и какие чаты выбраны. Ключ сессии лежит в файле, не в базе |
| `tg_dialogs`, `tg_dialog_lists` | Список диалогов аккаунта, каким его видел Telegram при последней загрузке: вид, название, @имя, последнее сообщение, папка; когда загружен целиком (Р-81). Удаляется при выходе из аккаунта |
| `setup_links`, `setup_sessions`, `setup_state`, `setup_audit`, `setup_codes` | Страница настройки переписки: одноразовая ссылка входа и сессии (только хеши), состояние входа по коду (пауза после неверных попыток) и попытки входа по коду (хеш попытки, HMAC кода, срок, счётчик, хранятся 8 суток), журнал действий владельца. Через внутренний API недоступны |
| `assistant_halt` | «Остановить всё» (Р-87): одна строка — остановлен ли, с какого времени, откуда, аккаунты на паузе по галочке |
| `people`, `person_*` | Реестр людей: учётные записи, алиасы, словоформы имён, предложения слияния |
| `processing_*`, `commitments`, `commitment_*` | Прогоны обработки, обязательства, журнал их изменений |
| `pages`, `page_*` | Указатель страниц памяти (люди, проекты, профиль владельца); сами страницы — файлы |
| `projects`, `project_chats`, `project_aliases`, `project_mentions` | Проекты, их чаты и другие названия; упоминания ещё не заведённых проектов (для предложений владельцу) |
| `facts` | Датированные факты и решения: о ком, ключ смены, период действия, источник и цитата, согласие владельца для фактов о нём |
| `outbox_*`, `watch_*` | Черновики, правила отправки, доверенные, журнал автоответов; правила и совпадения наблюдателя |
| `notify_items`, `rehearsal_items` | Очередь уведомлений владельцу (Р-84; `held_for_rehearsal` — придержано ради карточки репетиции); строки репетиции ответов (Р-85): номера, исход, оценка — без текста |

Правила, зашитые в схему и проверенные тестами:

- **Без дублей.** Сообщение определяется парой «чат, идентификатор сообщения»; повторный приход из любого источника дополняет запись, а не создаёт новую.
- **Правки не теряются и не затираются.** Более свежая правка заменяет текст, прежний уходит в историю. Старый экспорт, загруженный после новой правки, текст не перезаписывает.
- **Исключённый чат не попадает в архив** ни из одного источника; запрет запоминается.
- **Служебные чаты Telegram исключены всегда**: уведомления Telegram (777000), @BotFather, @SpamBot и диалог экспорта «Коды подтверждения». В них лежат коды входа и токены ботов.
- **Скрытое защитой не отдаётся ассистенту и модели** ни одним путём чтения; правка текста сбрасывает итог проверки.
- **Время — из точной отметки экспорта**, а не из местного времени компьютера, на котором делали выгрузку.
- **Отправляется только строка черновика**, прошедшая путь «ждёт → принят → отправляется»; её текст после создания не меняется.

Вложения не хранятся: в архиве остаётся только вид вложения (а у фото и документов — имя, тип и размер). Исключение — голосовые и «кружки» при включённой расшифровке и фото с документами при включённом разборе: файл скачивается во временный каталог в памяти контейнера распознавания или берётся из загруженного архива выгрузки (`data/shturman/media-files`) и удаляется после разбора, в архиве остаётся текст.

## Команды

Внутри контейнера сервиса (`docker exec shturman-service shturman …`):

```
shturman serve                         запустить сервис (так стартует контейнер); схема базы обновляется при старте
shturman migrate                       привести схему базы к текущей версии
shturman scan result.json              показать чаты экспорта с объёмом и периодом, ничего не записывая; принимает и архив zip папки выгрузки.
                                       Печатает названия чатов и имена — только человеку в терминале (Р-98)
shturman import result.json            импортировать (result.json или архив zip — по содержимому); --exclude user:123 — не принимать чат;
                                       --owner-id — для экспорта одного чата
shturman search "смета по фасадам"     поиск по словам с учётом русских словоформ; --limit N. Печатает текст переписки — только
                                       человеку в терминале: docker exec -it … (Р-98)
shturman call GET /api/status          запрос к внутреннему API работающего сервиса; методы GET, POST, PUT, DELETE, тело — JSON третьим аргументом;
                                       на ответ 202 печатает «ЖДЁТ ПОДТВЕРЖДЕНИЯ В БОТЕ». Без терминала (так выполняет команды ИИ-агент)
                                       GET отвечает только на маршруты с числами и состояниями: /api/status, /api/executor/status,
                                       /api/guard/status, /api/embeddings/status, /api/voice/status; остальные GET — только docker exec -it (Р-98)
shturman tg-login assistant|owner      вход в аккаунт по QR в терминале; выполняет человек
shturman bot-bind                      одноразовая ссылка привязки владельца к боту согласований
shturman bot-status                    состояние бота согласований и своей модели сервиса; без секретов
shturman setup-link                    одноразовая ссылка входа на страницу настройки переписки. В стандартный вывод — одна
                                       строка, путь /shturman-setup/#…; с ключом --url — полный адрес (тот, с которым запущен
                                       сервис, либо http://127.0.0.1:8765). Пояснения — в поток ошибок, значения ссылки в них нет
shturman setup-logout-all              завершить все сессии страницы настройки переписки и отменить неиспользованную ссылку входа
shturman retry-failed                  вернуть в работу то, что не получилось из-за сбоя модели (раздел «Повтор после сбоя»):
                                       --since ГГГГ-ММ-ДД — с какой даты считать сбой; --dry-run — только показать числа.
                                       Запускает оператор по решению владельца: повтор снова тратит запросы к модели
shturman ops-consent ask|status        разрешение владельца в боте согласований для скриптов ops/ (Р-100, «Разрешения на
                                       сопровождение»): --action, --target, --detail поле=значение, --wait, --keep, --direct
shturman update-result                 итог ./ops/update.sh — сервису, для сообщения владельцу (Р-101): --run, --result
                                       ok|rolled-back|failed-needs-human|rollback-failed, --from, --to, --new-fails "строки doctor";
                                       пишет прямо в базу. Вызывает ./ops/update.sh
shturman ops-report submit             отчёт сессии сопровождения (JSON на stdin) — в базу, карточка владельцу (Р-102); --wait N
                                       (30) — сколько ждать, пока сервис поставит карточку. Вызывает ./ops/report.sh
shturman commitments stats [--json]    договорённости «было / стало» (Р-96): только числа, без текста переписки
shturman commitments recheck           перепроверка найденного по новым правилам (Р-96): --dry-run — только оценка (запросы и
                                       токены; с --price-in/--price-out — в долларах), --limit N (300), --force — ещё раз.
                                       Запускает оператор по решению владельца: тратит запросы к модели. Обёртка — ./ops/commitments.sh
```

`GET /api/status` отдаёт только счётчики и признаки: сообщения, чаты, очередь заданий (`jobs_waiting` — ждут сейчас, `jobs_failed` — неудачных за всё время; объект `jobs_queue` — по группам `llm` (задания модели) и `bot` (уведомления владельцу, их правка, отправка через бизнес-бота): `waiting`, `ready_age_s` — сколько секунд ждёт исполнителя самое старое готовое задание, `done_hour` — выполнено за последний час по базе, переживает перезапуск; `hermes.cron` в группы не входит; по нему строка `jobs` в `./ops/doctor.sh`, Д-25), итоги заданий модели за последний час — объект `llm_jobs` (`window_s` — за сколько секунд собран счёт, не больше часа: он в памяти сервиса и после перезапуска начинается заново; `done` и `failed` — удачные и неудачные попытки `llm.structured` и `llm.text` обоих исполнителей; `errors` — до пяти частых видов ошибок `[вид, число]`: имя класса или короткий код, без текста ошибки, `service/src/shturman/jobstats.py`; по нему строка `jobs-failing` в `./ops/doctor.sh`, Р-83), известен ли владелец, включена ли отправка, `own_bot` и `own_llm` (выполняет ли сервис сам задания бота и модели), объект `setup` о странице настройки переписки (`enabled`, `origin_set`, `origin`, `reason`, `tg_keys`, `accounts`, `own_bot`, `owner_bound`, `business_connected`, `own_model`, `socket` — раздел «Страница настройки переписки»), счётчики защиты `guard_*` — проверено, скрыто, открыто владельцем, не проверено — и состояние поиска по смыслу `embeddings_*`: включён ли, какой моделью, сколько сообщений с её вектором (`embeddings_embedded`), сколько осталось посчитать или пересчитать (`embeddings_left`) и неполадка, если она есть (`unreachable`, `model_mismatch`). Подробнее — `GET /api/embeddings/status`: к тем же числам добавлены пропущенные (`skipped`), ждущие в очереди (`pending`) и посчитанные прежней моделью и ещё не возвращённые в очередь (`stale`). Расшифровка голосовых — поля `voice_*`: включена ли (`voice_enabled`), модель, неполадка (`voice_problem`) и счётчики очереди — ждут, готово, пропущено, не получилось (`voice_pending`, `voice_done`, `voice_skipped`, `voice_failed`). `GET /api/voice/status` отдаёт те же числа и вдобавок пределы очереди (`voice_days`, `voice_max_seconds`); в плагине этот маршрут отнесён к роли `UI` (проход дашборда, `service_routes.py`).

Молчаливые сбои (Р-98). Объект `tg_health` — сессии Telegram: `configured` (заданы ли ключи приложения), `checked` (была ли проверка с запуска), `accounts` — по ролям `owner`, `assistant`: `state` (`ok`, `connecting`, `error` — нет связи дольше 15 минут, `relogin` — нужно войти заново, `locked`, `quiet` — соединение есть, а обновлений от Telegram нет дольше суток, `paused`), `for_s` (сколько держится), `update_age_s` (давность последнего обновления о сообщениях); `worst` — худшее. Строки `tg-session`, `pulse`, `summary-last`, `model`, `approvals-bot` в `./ops/doctor.sh`; что делать — `docs/runbooks/symptoms.md`. Объект `updates` (Р-101) — раздел «Уведомления об обновлениях»; строка `updates`.

Для `scan` и `import` на сервере есть обёртка `./ops/import-export.sh`, для `tg-login` — `./ops/tg-login.sh`, для `bot-bind` — `./ops/bot-bind.sh` (кто её запускает и что делать со ссылкой — `docs/standalone.md`), для `setup-link` — `./ops/setup-link.sh` (берёт из вывода команды только путь, дописывает к нему адрес страницы из `.env` либо локальный адрес и печатает свои пояснения вместо пояснений команды; запускается только по просьбе владельца), для `setup-logout-all` — `./ops/logout-all.sh`.

## Что ещё не проверено

- **Всё, что касается настоящего Telegram**: вход по QR, загрузка истории, удаления, ограничения частоты, бизнес-поток.
- **Страница настройки переписки вне стенда**: с настоящим сертификатом и открытым в firewall портом, за Cloudflare, с настоящим аккаунтом Telegram и облачным паролем, загрузка выгрузки настоящего размера через прокси. На стенде под Docker она открывалась в образе сервиса за настоящим Caddy по https на отдельном порту — с внутренним сертификатом прокси; вход в аккаунт Telegram там не проходился вовсе (подставного Telegram на том стенде нет), выгрузка — файлом в несколько мегабайт.
- **Настоящий бот согласований**: связь с Telegram, привязка владельца по ссылке, карточки, кнопки, бизнес-режим и отправка через своего бота; совместная работа Hermes и бота согласований; `shturman tg-login` целиком при своём боте.
- **Mini App бота согласований в настоящем Telegram**: открывается ли кнопка «Штурман» на телефоне, в Telegram Desktop и в Telegram Web (рамка), принимает ли Telegram адрес с портом 8443 и адрес из IP, проходят ли настоящие данные входа нашу проверку подписи, работает ли «добавить на главный экран». Проверено только на стенде с данными входа, подписанными так же, как их подписывает Telegram (`docs/miniapp.md`).
- **Защита от внедрённых инструкций** на настоящей переписке и на эталонном сервере; время фоновой проверки большого импорта.
- **Совпадают ли идентификаторы сообщений в бизнес-потоке и в экспорте.** На этом держится обещание «без дублей» для пары «бизнес-бот и экспорт». Если не совпадают, одно сообщение ляжет в архив дважды.
- **Поиск по смыслу на настоящей переписке**: какая из двух моделей лучше для конкретного владельца, не измерено (`docs/search.md`).
- **Настоящая модель**: качество извлечения обязательств, сводки страниц, текст автоответа, два скилла; обращения сервиса к модели по своему ключу.
- **Репетиция ответов на настоящем Telegram и модели** (Р-85): как часто приходят карточки, каковы ответы голосом владельца и как он их оценивает; правка кнопок оценки в настоящем Telegram (`editMessageReplyMarkup`).
