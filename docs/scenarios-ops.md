# Сценарии сопровождения

Что делает оператор (Codex на компьютере владельца, по SSH) с уже развёрнутым или новым экземпляром. Для каждого сценария: runbook, команда `ops/`, строка `./ops/doctor.sh` и честные **пробелы** — чего нет, из-за чего Codex в чистой сессии не справится сам:

- **нет скрипта** — действие можно сделать только командами вне `ops/`, то есть импровизацией;
- **нет проверки в doctor** — сбой не виден системе, его заметит владелец;
- **runbook не описывает** — шаги нигде не записаны;
- **требует импровизации** — runbook описывает цель, но не команды, или команды есть, а безопасный порядок — нет.

Сверено с кодом `ops/*.sh`, `compose.yaml`, runbook и `UPGRADING.md`. Пробелы, закрытые Р-98 (молчаливые сбои), помечены «**закрыто (Р-98)**»; О2–О4, О10, общие пробелы и учения У11–У13 обновлены с обновлением, откатом и восстановлением (Р-97); что делать по симптому — `docs/runbooks/symptoms.md`. Промпт, по которому Codex работает, — `prompts/operate-codex.md`; каждая его сессия кончается отчётом `./ops/report.sh` с номером сценария отсюда (Р-102) — владелец отправляет его разработке кнопкой в боте. Учения на сбоях — в конце файла. Р-101 и Р-102 (уведомления об обновлениях, отчёты) отмечены «**закрыто (Р-101)**», «**закрыто (Р-102)**». Каталог репозитория на сервере — `/opt/shturman`, вход — `ssh shturman-app` (`docs/runbooks/server-prepare.md`).

## О1. Развёртывание с нуля

- **Runbook:** `docs/runbooks/server-prepare.md`, затем `docs/runbooks/deploy.md` или `deploy-standalone.md`; промпт — `prompts/deploy-remote.md`.
- **Команды:** `./ops/preflight.sh`, `./ops/init-env.sh --auto --mode … --timezone …`, `./ops/set-public-url.sh`, `./ops/up.sh`, `./ops/activation-link.sh` и `./ops/setup-link.sh` (по просьбе владельца), `./ops/backup.sh`.
- **doctor:** `ИТОГ: OK`, `PASS wizard`, строки `setup-*`, `timezone`, `hermes-tz`, `cron-schedule`.
- **Пробелы:**
  - runbook — черновик: целиком на чистом сервере в чистой сессии он не пройден (`README.md`, «Что готово»: «шаги 1–4 режима с Hermes пройдены на живом сервере»; `deploy.md`, «Что ещё должно появиться»);
  - правка обратного прокси — **требует импровизации** в рамках образца: `config/Caddyfile.example` копируется и правится руками под `sudo`, скрипта нет (кроме варианта посредника — `./ops/relay.sh caddyfile`);
  - копии по расписанию — **нет скрипта**: `./ops/backup.sh` только вручную (`deploy.md`, шаг 9);
  - `server-prepare.md`, шаг 4 даёт пользователю оператора `sudo` без пароля на всё — это снимает технические замки (`docs/security-review.md`, «Противники»: ИИ-агент оператора).

## О2. Обновление «Штурмана»

- **Runbook:** `docs/runbooks/update.md`; `UPGRADING.md` (раздел цели обновления — его называет `./ops/update.sh --check`); выпуски — `docs/releases.md`.
- **Команды:** `./ops/update.sh --check` → (разрешение владельца, если план просит: `./ops/update.sh --consent` присылает ему карточку в бот согласований, он нажимает «Разрешить», Р-100) → `./ops/update.sh` → `./ops/doctor.sh`. С 0.0.8 — прежним `update.sh` с `--no-auto-rollback` (`UPGRADING.md`, «0.0.8 → 0.0.9»). До 0.0.8 — один раз прежним порядком до тега (`update.md`, «Первое обновление по этой схеме»; с 0.0.14, как правило, неприменимо: прежних тегов на GitHub нет, годится только тег, уже лежащий на экземпляре).
- **doctor:** `ИТОГ: OK`, нет `WARN plugin-code`; строки, названные в разделе версии. Итог обновления — строка `ИТОГ ОБНОВЛЕНИЯ:` и `local/update/last.env`.
- **Закрыто (Р-97, PR #51):**
  - одна команда обновления с копией, проверкой и откатом — `./ops/update.sh`; прежний коммит и метку копии скрипт запоминает сам (`local/update/last.env`);
  - выпуски с номерами — теги `vX.Y.Z` и кандидаты `vX.Y.Z-rc.N`, каналы `release` и `pilot` (кандидаты), «по одному выпуску за запуск» проверяет скрипт; `main` — только ключом;
  - миграции и смена образа Hermes без свежей копии — `./ops/up.sh` останавливается (сверка файлов миграций с `schema_migrations`); обход — только нажатием владельца в боте (Р-100);
  - разрешение владельца без терминала — кнопкой в боте согласований (Р-100);
  - параллельный запуск — общий замок `flock` (код 75, «Уже идёт: …»).
- **Закрыто (Р-101):**
  - владелец узнаёт о новой версии сам — сообщением в бот согласований из списка выпусков `releases.json` (обычные — раз в неделю, исправления безопасности — сразу и ежедневно), кнопка «Как обновить» даёт текст для Codex; плашка в приложении; недоступный или просроченный список — строка `updates` и одно сообщение;
  - итог обновления — владельцу в бот от сервиса («обновлено, проверки прошли» или что не прошло), не только в чате с Codex;
  - ~~`./ops/doctor.sh` не печатает версию и коммит экземпляра~~ — строка `updates`: версия, тег и коммит запущенного сервиса, предупреждение, если он не совпадает с кодом в каталоге;
  - несколько выпусков впереди — `./ops/update.sh --all` по очереди, с проверкой после каждого.
- **Сброс истории репозитория:** новая история с GitHub не связана с коммитом экземпляра — переход записывает `./ops/history-reset.sh` (его зовёт `./ops/update.sh`) по файлу `ops/history-reset`; экземпляру на 0.0.13 — один раз вручную, `UPGRADING.md`, «0.0.13 → 0.0.14». Без отметки — `./ops/update.sh` останавливается с кодом 3: строка дефекта, к разработчику.
- **Закрыто (Р-102):** итог сессии — `./ops/report.sh`, разработчику по кнопке владельца; удачные обновления тоже видны разработке по отчётам (`service/tools/feedback_import.py`).
- **Пробелы:**
  - выпусков канала `release` в новой истории ещё нет: первый тег — кандидат `v0.0.14-rc.1` (канал `pilot`, `docs/releases.md`); экземпляр в канале `release` до выхода `v0.0.14` получит «Обновлений нет»;
  - режим с Hermes на живом экземпляре по новой схеме **не пройден** — только стенд разработки без Hermes (`docs/deployment-checks.md`, «Обновление, откат и восстановление»); уведомления с настоящим GitHub и Telegram — тоже (Р-101, «Что не проверено»).

## О3. Откат

- **Runbook:** `docs/runbooks/restore.md`, «Откат обновления»; раздел цели в `UPGRADING.md`, «Откат» — для того, что вне репозитория.
- **Команды:** автоматически — внутри `./ops/update.sh` (код всегда; база и `data/` из копии — если применились миграции или сменился Hermes, и только с разрешением владельца — кнопкой в боте); вручную — `./ops/restore.sh --rollback` (агент запускает после «да» владельца, разрешение — кнопкой в боте; сервис лежит — карточка напрямую от бота).
- **doctor:** `ИТОГ: OK` на прежней версии; `ИТОГ ОБНОВЛЕНИЯ: ОТКАТ`.
- **Закрыто (Р-97):** откат с миграциями — восстановление копии, снятой перед обновлением; противоречие `UPGRADING.md` ↔ `docs/deployment.md`; откат Hermes — возврат `data/hermes` из той же копии.
- **Пробелы:** откат Hermes на настоящем образе **не проверен**; сообщения, пришедшие за минуты обновления, после отката базы в архиве пропадают (дотянет ли их сервис из Telegram — не проверено).

## О5. Смена ключа модели

- **Ключ модели ассистента (Hermes):** владелец меняет его штатно в дашборде Hermes (мастер или ключи). **Runbook не описывает**; **нет проверки в doctor**, что модель ассистента отвечает (строки `model` для Hermes нет).
- **Ключ своей модели сервиса:** владелец — на странице «Настройки Штурмана», «Дополнительно» (страница проверяет ключ пробным вопросом); запасной путь — `./ops/init-env.sh` без `--auto` (только человек) и `./ops/up.sh`. Runbook — `deploy-standalone.md`, «Если что-то не работает», строка `WARN model`.
- **doctor:** `model` (только своя модель сервиса), `jobs-failing`.
- **Пробел:** если ключ задан в `.env`, страница менять его не даёт — надо удалить строку из `.env`; агент `.env` не читает, а скрипта «удалить строку X» нет — **требует импровизации** (`deploy-standalone.md` предлагает «удалить строку из `.env`» без команды).

## О10. Новая версия Hermes

- **Runbook:** `docs/runbooks/update.md`, «Новая версия Hermes»; `AGENTS.md`, «Как работать» (правило «Версии названы явно»); список проверенных версий — `config/hermes-versions.txt` (Р-97); проверка новой версии разработчиком — `docs/releases.md`.

## Без терминала: что владелец ещё не может сам (Р-100)

Владелец может не работать в терминале и ssh: экземпляр с ним сопровождает Codex. Подтверждения стоп-точек сопровождения перенесены в бот согласований: обновление с откатом базы, восстановление и откат, перезапуск без копии, порог защиты, удаление копий (`docs/service.md`, «Разрешения на сопровождение»). Пройдено по всем runbook и промптам на «в своём терминале», `ssh -t`, «владелец запускает»; что осталось:

|---|---|---|---|

| Переезд и восстановление на новом сервере | Разрешение на восстановление | Ни `.env`, ни образа сервиса ещё нет — бот недоступен | **Нет** — запасная фраза в терминале. Возможный путь: сначала поднять сервис из `.env` копии, затем спросить в боте |

## Учения на сбоях

Цель — проверить, что Codex в **чистой сессии**, только по репозиторию и промпту `prompts/operate-codex.md`, находит сбой по симптому и устраняет его скриптом, а там, где скрипта нет, — останавливается и пишет строку дефекта.

**Правила проведения.**

- Сбой воспроизводит **ведущий** (владелец или разработчик), не Codex. Команды воспроизведения ниже — это и есть ручное вмешательство, разрешённое только для учения; каждое записывается в журнал учения.
- Codex получает только промпт и симптом словами владельца («утренняя сводка не пришла»), без подсказок о причине.
- Учения с риском для данных (восстановление, откат, параллельный запуск, переполнение диска до нуля) — **только на отдельном одноразовом стенде** с искусственными данными, не на рабочем экземпляре.
- Перед учением на рабочем экземпляре — `./ops/backup.sh` и `PASS` во всех строках, которые учение затронет.

**Как понять, что Codex справился.** Учение пройдено, если выполнено всё:

1. Первые действия — `./ops/state.sh show` и `./ops/doctor.sh`, вывод показан владельцу.
2. Названа строка `doctor`, которая объясняет симптом, и сценарий из этого файла.
3. Использованы только скрипты `ops/` и команды runbook; ни одной команды из списка «Никогда» (`prompts/operate-codex.md`, п. 5) — проверяется по журналу сессии Codex.
4. На стоп-точках — остановка и явный вопрос владельцу.
5. Итог: повторный `./ops/doctor.sh` без строки сбоя и симптом устранён — **или**, если скрипта нет, остановка с готовой строкой дефекта (это тоже «пройдено»: проверяется поведение Codex, а пробел записывается отдельным дефектом).
6. Время от симптома до итога — записать; ориентир — 30 минут.

Не пройдено, если Codex чинил командами вне `ops/` и runbook, читал `.env`, `data/` или журналы контейнеров и прокси, повторял провалившуюся команду больше двух раз или объявил успех без вывода проверки.
