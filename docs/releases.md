# Выпуски

Экземпляр владельца обновляется не до `main`, а до **выпуска** — тега `vX.Y.Z` на коммите, где `VERSION` = `X.Y.Z` (Р-97). Так у обновления есть номер, раздел в `UPGRADING.md` и путь назад, а «по одной версии за раз» можно соблюсти. Обновляет `./ops/update.sh` (`docs/runbooks/update.md`).

## Каналы

| Канал | Что берёт `./ops/update.sh` | Для кого | Как задать |
|---|---|---|---|
| `release` (по умолчанию) | Следующий выпуск `vX.Y.Z` на пути к последнему | Экземпляры CEO и всех, кроме пилота | Ничего не задавать |
| `pilot` | Следующий выпуск или кандидат `vX.Y.Z-rc.N` | Экземпляр владельца пилота | `./ops/update.sh --set-channel pilot` (строка `SHTURMAN_UPDATE_CHANNEL` в `.env`) |
| `main` | Нынешний `origin/main`, мимо выпусков | Разработка, стенд | Только ключом `--channel main` при каждом запуске; в `.env` не записывается |

Правила, которые проверяет `./ops/update.sh`:

- только вперёд: цель должна содержать нынешний коммит (`git merge-base --is-ancestor`); назад — `./ops/restore.sh --rollback` или восстановление копии;
- по одному выпуску за запуск: без `--to` берётся **следующий** выпуск, а не последний; `--to` не может перескочить выпуск между нынешним кодом и целью (кандидаты перескакивать можно);
- тег, у которого `VERSION` не совпадает с номером, выпуском не считается: по умолчанию пропускается, по `--to` — отказ;
- тег на GitHub, который переставили на другой коммит, `git fetch` не примет (`would clobber existing tag`) — обновление остановится. Подписи тегов не проверяются: доверие к репозиторию и к тому, кто ставит теги, остаётся (`docs/pilot/decisions-options.md`, «а»).

## Как выпустить (разработчик)

1. В ветке выпуска: `VERSION` → `X.Y.Z`; в `CHANGELOG.md` раздел «Не выпущено» переименовать в `## X.Y.Z — ГГГГ-ММ-ДД` и открыть над ним новый пустой «Не выпущено»; в `UPGRADING.md` у раздела `## A.B.C → X.Y.Z (не выпущено)` убрать «(не выпущено)».
2. Раздел `UPGRADING.md` выпуска — форма из шапки файла. Всё, что `./ops/update.sh` не делает сам (правка прокси, `sudo`, перепроверка, решение владельца), — отдельным шагом со словами **«Стоп-точка»**: тогда `./ops/update.sh` без ключа `--upgrading-read` не запустится, и Codex обязан прочитать раздел и пересказать его владельцу. Новая миграция базы называется в разделе по имени файла.
3. Образ Hermes по умолчанию (`compose.yaml`) должен быть в `config/hermes-versions.txt`. Сменили версию по умолчанию — сначала проверка по разделу «Новая версия Hermes» ниже.
4. `bash ops/tests/release_check.sh vX.Y.Z` → «Выпуск vX.Y.Z готов к тегу». Та же проверка идёт в CI на теге.
5. После слияния в `main` — тег на коммите слияния:

   ```
   git tag -a vX.Y.Z -m "Штурман X.Y.Z" <коммит> && git push origin vX.Y.Z
   ```

   Кандидат для пилота — так же, `vX.Y.Z-rc.N` (`VERSION` тот же `X.Y.Z`). Теги не переставляются и не удаляются: ошибка исправляется следующим номером.
6. Выпуск на GitHub (Releases) — по желанию, с текстом из `CHANGELOG.md`; `./ops/update.sh` смотрит только на теги.

## Сколько выпуск живёт на пилоте, прежде чем уйти к другим

> **Предложение, утверждает владелец** (`docs/pilot/exit-criteria.md`, К-8).

Каждый выпуск сначала ставится на пилот кандидатом `vX.Y.Z-rc.N` (канал `pilot`). Тот же коммит получает тег `vX.Y.Z` (канал `release`), когда на пилоте выполнено всё:

- кандидат прожил на пилоте **не меньше 7 суток** — один еженедельный разбор (`docs/pilot/README.md`), ночные прогоны, выходные;
- обновление на него сделал Codex по `prompts/operate-codex.md` без ручного вмешательства: копия до, `ИТОГ ОБНОВЛЕНИЯ: OK`;
- за эти 7 суток нет новых дефектов тяжести «критично», а дефекты «мешает» с причиной «логика» или «сценарий», появившиеся с этим выпуском, исправлены или признаны владельцем допустимыми (`docs/pilot/defects.md`);
- если в выпуске миграция базы — на стенде пройдено учение У13 «обновление с откатом» на этом кандидате (`docs/pilot/scenarios-ops.md`).

Исправление в кандидате — новый кандидат `rc.N+1`, и отсчёт 7 суток начинается заново. Срочное исправление безопасности может пойти в `release` раньше — решением владельца, с записью в `docs/decisions.md`.

## Новая версия Hermes

Версию Hermes `./ops/update.sh` не поднимает никогда: `HERMES_VERSION` в `.env` — решение владельца (`AGENTS.md`). Список проверенных версий — `config/hermes-versions.txt` (тег образа, версия Hermes, дата, что проверено); его читают `./ops/doctor.sh` (строка `hermes-version`), `./ops/up.sh` и `./ops/update.sh`.

Чтобы добавить версию в список, разработчик на стенде:

1. снимает копию и пишет новую `HERMES_VERSION`, затем `./ops/up.sh --pull` (смена образа требует свежей копии — `up.sh` проверит сам);
2. проходит ручные сценарии `plugins/shturman/tests/e2e/` (мост, исполнитель, обработчики Telegram) и `./ops/doctor.sh` с `ИТОГ: OK`, в том числе строки `archive-mcp`, `hermes-tz`, `cron-schedule`;
3. записывает строку в `config/hermes-versions.txt` с датой и тем, что проверено; если версия по умолчанию меняется — и `compose.yaml`.

Откат Hermes после того, как новая версия записала свои данные, его документация не поддерживает; поэтому смена образа Hermes в `./ops/up.sh` и `./ops/update.sh` идёт только со свежей копией, а откат — восстановлением `data/hermes` из неё (`./ops/restore.sh --rollback` или `--from`).
