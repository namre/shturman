# Выпуски

Экземпляр владельца обновляется не до `main`, а до **выпуска** — тега `vX.Y.Z` на коммите, где `VERSION` = `X.Y.Z` (Р-97). Так у обновления есть номер, раздел в `UPGRADING.md` и путь назад, а «по одной версии за раз» можно соблюсти. Обновляет `./ops/update.sh` (`docs/runbooks/update.md`).

## Каналы

| Канал | Что берёт `./ops/update.sh` | Для кого | Как задать |
|---|---|---|---|
| `release` (по умолчанию) | Следующий выпуск `vX.Y.Z` на пути к последнему | Все экземпляры, кроме тех, что берут кандидаты | Ничего не задавать |
| `pilot` | Следующий выпуск или кандидат `vX.Y.Z-rc.N` | Экземпляр, на котором кандидат обкатывается до выпуска | `./ops/update.sh --set-channel pilot` (строка `SHTURMAN_UPDATE_CHANNEL` в `.env`) |
| `main` | Нынешний `origin/main`, мимо выпусков | Разработка, стенд | Только ключом `--channel main` при каждом запуске; в `.env` не записывается |

Правила, которые проверяет `./ops/update.sh`:

- только вперёд: цель должна содержать нынешний коммит (`git merge-base --is-ancestor`; после сброса истории — через записанный переход, раздел «Сброс истории и закрытый репозиторий» ниже); назад — `./ops/restore.sh --rollback` или восстановление копии;
- по одному выпуску за запуск: без `--to` берётся **следующий** выпуск, а не последний; `--to` не может перескочить выпуск между нынешним кодом и целью (кандидаты перескакивать можно); `--all` (Р-101) — по очереди до последнего выпуска канала, каждый шаг — отдельный обычный запуск со своей проверкой, копией и откатом, первая неудача останавливает цепочку;
- тег, у которого `VERSION` не совпадает с номером, выпуском не считается: по умолчанию пропускается, по `--to` — отказ;
- тег на GitHub, который переставили на другой коммит, `git fetch` не примет (`would clobber existing tag`) — обновление остановится. Подписи тегов не проверяются: доверие к репозиторию и к тому, кто ставит теги, остаётся (`docs/deferred.md`, О-13).

## Как выпустить (разработчик)

1. В ветке выпуска: `VERSION` → `X.Y.Z`; в `CHANGELOG.md` раздел «Не выпущено» переименовать в `## X.Y.Z — ГГГГ-ММ-ДД` и открыть над ним новый пустой «Не выпущено»; в `UPGRADING.md` у раздела `## A.B.C → X.Y.Z (не выпущено)` убрать «(не выпущено)».
2. Раздел `UPGRADING.md` выпуска — форма из шапки файла. Всё, что `./ops/update.sh` не делает сам (правка прокси, `sudo`, перепроверка, решение владельца), — отдельным шагом со словами **«Стоп-точка»**: тогда `./ops/update.sh` без ключа `--upgrading-read` не запустится, и Codex обязан прочитать раздел и пересказать его владельцу. Новая миграция базы называется в разделе по имени файла.
3. Образ Hermes по умолчанию (`compose.yaml`) должен быть в `config/hermes-versions.txt`. Сменили версию по умолчанию — сначала проверка по разделу «Новая версия Hermes» ниже.
4. **Запись в список выпусков** `releases.json` (Р-101, раздел «Список выпусков» ниже): запись тега — версия, дата, вид (`security` или `regular`), «что изменилось» 1–3 строки простыми словами для владельца, перерыв в работе, нужны ли его действия; `published` — сегодня, `expires` — через 45 дней. Без записи экземпляры о выпуске не узнают. Проверка формы — `python3 ops/release_manifest.py check releases.json --hermes-file config/hermes-versions.txt`.
5. `bash ops/tests/release_check.sh vX.Y.Z` → «Выпуск vX.Y.Z готов к тегу». Та же проверка идёт в CI на теге: кроме прежнего — запись тега в `releases.json` с версией `VERSION`, срок годности не вышел, образы Hermes в списке те же, что в `config/hermes-versions.txt`, версия пакета сервиса (`service/pyproject.toml`, `__version__`) — `VERSION`.
   Браузерные проверки прогнаны: задача CI `miniapp-e2e` (весь `service/tests/e2e/miniapp.mjs`) на последнем коммите ветки выпуска — зелёная; если выпуск менял страницу настройки или договорённости — вручную `setup_page.mjs` и `commitments_r96.mjs` (команды — `service/tests/e2e/README.md`), например:

   ```
   cd service
   PYTHONPATH=src SHTURMAN_TEST_DSN=postgresql://postgres@127.0.0.1:5432/shturman_e2e E2E_PORT=8775 \
     E2E_SETUP_ORIGIN=https://shturman.example.ru:8443 python tests/e2e/miniapp_stand.py &
   E2E_PORT=8775 E2E_SETUP_ORIGIN=https://shturman.example.ru:8443 node tests/e2e/miniapp.mjs   # ИТОГ: OK
   ```

   Итог — строкой в описании PR выпуска («браузерные проверки: miniapp-e2e зелёная; setup_page.mjs — ИТОГ: OK / не нужен»). Д-35: сценарий приложения на `main` падал незамеченным, пока шёл только вручную.
6. После слияния в `main` — тег на коммите слияния:

   ```
   git tag -a vX.Y.Z -m "Штурман X.Y.Z" <коммит> && git push origin vX.Y.Z
   ```

   Кандидат — так же, `vX.Y.Z-rc.N` (`VERSION` тот же `X.Y.Z`). Теги не переставляются и не удаляются: ошибка исправляется следующим номером.
7. Выпуск на GitHub (Releases) — по желанию, с текстом из `CHANGELOG.md`; `./ops/update.sh` смотрит только на теги, сервис — только на `releases.json` в `main`.

Тег кандидата ставится на коммит, где запись его в `releases.json` может ещё отсутствовать (например, `v0.0.9-rc.2` — на `97caaaa`, а запись добавлена следующим PR): экземпляры читают список из `main`, а не из тега, — запись должна быть в `main` к моменту, когда о выпуске пора сообщать.

## Список выпусков (`releases.json`, Р-101)

Файл в корне репозитория. Сервис каждого экземпляра раз в сутки читает его из `main` (raw-ссылка GitHub, без идентификатора экземпляра; выключается `SHTURMAN_UPDATES=off`) и пишет владельцу о новой версии: обычной — не чаще раза в неделю и не в тихие часы, исправлении безопасности — сразу и раз в сутки, пока не обновлено (`docs/deployment.md`, «Обновления»). Список — **данные**: сервис принимает его только целиком прошедшим проверку и только в пределах срока годности, текст сообщения собирает сам по шаблону; ничего исполняемого в сообщении нет, тег проверяет `./ops/update.sh` при обновлении.

```json
{
  "schema": 1,
  "published": "2026-10-17",
  "expires": "2026-12-01",
  "releases": [
    {"tag": "v0.0.9-rc.2", "version": "0.0.9", "date": "2026-10-17", "kind": "regular",
     "changes": ["Разрешения — кнопкой «Разрешить» в боте согласований, без терминала."],
     "downtime_minutes": 5, "owner_action": false, "owner_steps": [], "hermes": ["v2026.9.24"]}
  ],
  "hermes": [{"tag": "v2026.9.24", "version": "0.21.5", "verified": "2026-10-14"}],
  "warnings": [{"id": "gpt-x-retire", "model": "gpt-x", "provider": "OpenAI", "until": "2027-01-15",
                "text": "Замена — gpt-y: сменить в «Настройках Штурмана», «Дополнительно»."}]
}
```

| Поле | Что писать |
|---|---|
| `published`, `expires` | Дата правки и срок годности: не дольше 120 дней, по умолчанию +45. После `expires` экземпляры список не принимают: строка `updates` в `doctor` — `WARN`, владельцу — одно сообщение. Еженедельная задача CI (`.github/workflows/security.yml`) падает, если до конца срока меньше 14 дней, — продлите `published` и `expires` |
| `releases[]` | Каждый выпуск и кандидат. `kind` — `security` только для исправлений уязвимостей; `changes` — 1–3 строки для владельца, не для разработчика (не «рефакторинг X», а что он увидит), до 200 знаков каждая; `downtime_minutes` — перерыв в работе ассистента; `owner_action` — `true`, если владельцу самому что-то делать сверх нажатий в боте, и тогда `owner_steps` — что, простыми словами (то же, что «Стоп-точка» в `UPGRADING.md`) |
| `hermes[]` | Проверенные образы Hermes — тот же список, что `config/hermes-versions.txt` (CI сверяет). Новая запись — сообщение владельцам в режиме с Hermes «вышла версия Hermes X, с вашим „Штурманом“ проверена». Добавляет `./ops/hermes-check.sh X --record …` (файл) и разработчик (сюда) |
| `warnings[]` | Снятие моделей провайдером — ведётся вручную по объявлениям провайдеров. `model` — имя, как его пишут в настройках; владельцу пишем за 30 и за 7 дней, если сервис сам обращается к этой модели |

## Настройки GitHub (включает владелец репозитория)

Доверие к выпускам держится на том, что теги `v*` и ветку `main` (а значит и `releases.json`) меняет только владелец репозитория и только через PR. Это настройки GitHub, а не код — включаются руками:

1. **Учётная запись:** двухфакторная проверка (Settings → Password and authentication → Two-factor authentication; лучше ключ доступа — passkey или аппаратный ключ, а не SMS); резервные коды — в надёжном месте. Личные токены (Developer settings → Personal access tokens) — только fine-grained, на один репозиторий, со сроком; старые классические — отозвать.
2. **Защита `main`** (репозиторий → Settings → Rules → Rulesets → New branch ruleset, цель — `main`): Restrict deletions; Block force pushes; Require a pull request before merging; Require status checks to pass — задачи CI `service`, `plugin`, `miniapp-e2e`, `ops`, `relay`, `reply-regressions`. Bypass — никому (или только владельцу, осознанно).
3. **Защита тегов `v*`** (Rulesets → New tag ruleset, шаблон `v*`): Restrict deletions; Restrict updates (тег нельзя переставить); Block force pushes; Restrict creations — только владельцу. Тег, переставленный на GitHub, `./ops/update.sh` и так не примет (`git fetch` откажет), но удалённый и созданный заново тег — примет.
4. **Оповещения о уязвимостях:** Settings → Code security → Dependabot alerts — включить (без Dependabot security updates и version updates: PR с обновлениями зависимостей у нас не делаются автоматически); Private vulnerability reporting — включить, чтобы о дыре можно было сообщить не публично. Уведомления — на почту владельца (Settings → Notifications → Dependabot alerts).
5. **Действия CI:** Settings → Actions → General → Workflow permissions — Read repository contents (по умолчанию «только чтение»); Allow GitHub Actions to create and approve pull requests — выключить. Еженедельной задаче уязвимостей нужно `issues: write` — оно задано в самом файле задачи.

## Уязвимости зависимостей

Еженедельно (понедельник, 05:17 UTC) и вручную (Actions → security → Run workflow) задача `.github/workflows/security.yml` проверяет OSV-Scanner'ом закреплённые зависимости: `service/requirements.lock`, `asr/requirements.lock` (у плагина и посредника своих зависимостей нет: только стандартная библиотека Python и Hermes). Тревога — только на уязвимость высокой или критической тяжести (CVSS ≥ 7,0 или такая тяжесть у источника): задача падает (GitHub пишет владельцу о неудаче) и открывает issue «Уязвимость в зависимостях» с перечнем — без автоматических PR (Renovate и Dependabot updates не используются). Исправление — обычный PR: обновить строку в `requirements.lock` командой из его шапки, тесты, `THIRD_PARTY_NOTICES.md`, выпуск с `kind: "security"` в `releases.json`. Та же задача проверяет срок годности `releases.json`.

## Сколько кандидат обкатывается, прежде чем стать выпуском

> **Предложение, утверждает владелец.**

Каждый выпуск сначала ставится кандидатом `vX.Y.Z-rc.N` (канал `pilot`) на экземпляр, где он обкатывается. Тот же коммит получает тег `vX.Y.Z` (канал `release`), когда выполнено всё:

- кандидат проработал **не меньше 7 суток** — один еженедельный разбор, ночные прогоны, выходные;
- обновление на него сделал Codex по `prompts/operate-codex.md` без ручного вмешательства: копия до, `ИТОГ ОБНОВЛЕНИЯ: OK`;
- за эти 7 суток нет новых дефектов тяжести «критично», а дефекты «мешает» с причиной «логика» или «сценарий», появившиеся с этим выпуском, исправлены или признаны владельцем допустимыми (журнал дефектов — в закрытом репозитории проекта);
- если в выпуске миграция базы — на стенде пройдено учение У13 «обновление с откатом» на этом кандидате (`docs/scenarios-ops.md`).

Исправление в кандидате — новый кандидат `rc.N+1`, и отсчёт 7 суток начинается заново. Срочное исправление безопасности может пойти в `release` раньше — решением владельца, с записью в `docs/decisions.md`.

## Сброс истории и закрытый репозиторий

С 0.0.14 этот открытый репозиторий начат заново одним коммитом. Прежняя история (до 0.0.13 включительно) и закрытые записи пилота — журнал дефектов, варианты решений, условия выхода, аудит замков, ручные вмешательства, итоги проверок на экземпляре владельца — хранятся в **закрытом репозитории проекта**: история до переезда и закрытые записи пилота; код там не развивается. Код развивается только здесь. В открытом репозитории на закрытые записи ссылаются только номером (Д-…, Р-…, О-…), без адреса.

**Как экземпляр переходит через сброс.** Файл `ops/history-reset` называет прежний коммит, который продолжает новая история: `4f10f6e812a0aacb04c9557d30a98846298693d6` (`v0.0.13-rc.1`). `./ops/update.sh` после `git fetch` зовёт `./ops/history-reset.sh`: если ветка с GitHub (тег выпуска или `origin/main`) не связана с нынешним коммитом, а первый коммит её истории называет прежний коммит, до которого нынешний код доходит, — скрипт записывает переход локально (`git replace --graft <первый коммит новой истории> <прежний коммит>`). Дальше действуют прежние правила: только вперёд, по одному выпуску, `--to` не перескакивает, откат — на прежний коммит. Нет файла, нынешний коммит не ведёт к названному или его нет на экземпляре — переход не записывается, `./ops/update.sh` останавливается с кодом 3 и объяснением. Экземпляру на 0.0.13 (его `./ops/update.sh` ещё не знает этого шага) переход записывают один раз вручную — `UPGRADING.md`, «0.0.13 → 0.0.14».

Правила для разработчика:

- `ops/history-reset` не удалять и не править: по нему переходят экземпляры, которые обновляются позже. Новый сброс истории (если когда-нибудь понадобится) — новая строка с последним коммитом прежней истории в первом коммите новой.
- Теги с прежними именами (`v0.0.1`…`v0.0.13-rc.1`) в новой истории не ставить: на экземплярах они остаются, и `git fetch` откажет (`would clobber existing tag`). Первый тег новой истории — `v0.0.14-rc.1`.
- Ссылки на PR и коммиты прежней истории (номера PR в `CHANGELOG.md` и `docs/decisions.md`) ведут в закрытый репозиторий — оставлены как история.
- Записи `v0.0.8-rc.1`…`v0.0.13-rc.1` в `releases.json` остаются, хотя тегов в новой истории нет: `./ops/update.sh` списка не читает (только теги), а сервис по списку лишь сообщает и считает «выпусков впереди» — экземпляру на 0.0.13 и новее они позади; экземпляр старше дойдёт до них только по своим локальным тегам, иначе `./ops/history-reset.sh` остановит обновление с объяснением.

## Новая версия Hermes

Что проверить на стенде — `./ops/hermes-check.sh vГГГГ.М.Д` (по запросу, не по расписанию); после проверки — `./ops/hermes-check.sh vГГГГ.М.Д --record ВЕРСИЯ "что проверено"` в ветке разработки и та же версия в `releases.json` («hermes»): из него экземпляры узнают о проверенной версии.

Версию Hermes `./ops/update.sh` не поднимает никогда: `HERMES_VERSION` в `.env` — решение владельца (`AGENTS.md`). Список проверенных версий — `config/hermes-versions.txt` (тег образа, версия Hermes, дата, что проверено); его читают `./ops/doctor.sh` (строка `hermes-version`), `./ops/up.sh` и `./ops/update.sh`.

Чтобы добавить версию в список, разработчик на стенде:

1. снимает копию и пишет новую `HERMES_VERSION`, затем `./ops/up.sh --pull` (смена образа требует свежей копии — `up.sh` проверит сам);
2. проходит ручные сценарии `plugins/shturman/tests/e2e/` (мост, исполнитель, обработчики Telegram) и `./ops/doctor.sh` с `ИТОГ: OK`, в том числе строки `archive-mcp`, `hermes-tz`, `cron-schedule`;
3. записывает строку в `config/hermes-versions.txt` с датой и тем, что проверено; если версия по умолчанию меняется — и `compose.yaml`.

Откат Hermes после того, как новая версия записала свои данные, его документация не поддерживает; поэтому смена образа Hermes в `./ops/up.sh` и `./ops/update.sh` идёт только со свежей копией, а откат — восстановлением `data/hermes` из неё (`./ops/restore.sh --rollback` или `--from`).
