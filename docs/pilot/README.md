# Этап обкатки

Утверждён владельцем 2026-10-16. Продукт обкатывается на экземпляре владельца пилота. Конечный пользователь — руководитель (дальше — CEO), который **сам** разворачивает и сопровождает свой экземпляр с помощью Codex, без техподдержки. Цель этапа — довести «Штурман» до состояния, в котором это возможно, и доказать это числами, а не впечатлением.

Этот каталог — рабочие документы этапа. Они не меняют правил `AGENTS.md`: всё, что здесь названо предложением, становится правилом только после решения владельца (`decisions-options.md`) и записи в `docs/decisions.md`.

## Задание этапа

1. **Сценарии продукта.** Каталог того, что «Штурман» делает для владельца, с пограничными случаями: пересылка, альбом, фото, голосовое, правка, удаление, группа, ночь, ответ с другого устройства, длинная пауза, много сообщений подряд. → `scenarios-product.md`
2. **Сценарии сопровождения.** Развёртывание с нуля, обновление, откат, восстановление, смена ключа модели, повторный вход в Telegram, «сводка не пришла», «бот молчит», диск заполнен, новая версия Hermes и другие. Для каждого — runbook, команда `ops/`, строка `./ops/doctor.sh`. → `scenarios-ops.md`
3. **Пилот сопровождает Codex.** В чистой сессии, только по репозиторию. Claude руками не чинит; любое ручное вмешательство — дефект. Учения на сбоях. → `prompts/operate-codex.md`, `scenarios-ops.md` (раздел «Учения»), `manual-interventions.md`
4. **Замки вместо просьб.** Опасное должно быть защищено скриптом и правами, а не только текстом `AGENTS.md`. Отдельно — какие команды могут напечатать переписку: через Codex их вывод уходит в OpenAI. → `locks-audit.md`
5. **Журнал дефектов** с причиной и «кто заметил первым». → `defects.md`
6. **Разметка «Верно / Не так» как эталон.** Оценки владельца под карточками — это и есть мерило качества функций. → `scenarios-product.md` (столбец «как оценивается»), `exit-criteria.md`
7. **Сбои ловит система, а не владелец.** Внешний сторож, `doctor` с понятным следующим шагом, диагностический пакет без личных данных, выпуски с номерами, одна команда обновления с копией, проверкой и откатом. → пробелы в `scenarios-ops.md`, предложения в `locks-audit.md`
8. **Условия выхода с числами.** → `exit-criteria.md` (черновик, утверждает владелец)
9. **Решения на владельца.** → `decisions-options.md`

## Файлы

| Файл | Что в нём | Кто пользуется |
|---|---|---|
| `scenarios-product.md` | Функции, которые есть в коде: основной сценарий, ожидаемое поведение, пограничные случаи, как проверить, где смотреть результат, статус прохода | Владелец пилота — при проходах; разработчик — при правках |
| `scenarios-ops.md` | Сценарии сопровождения: runbook, команда, строка `doctor`, честные пробелы; учения на сбоях | Codex (оператор), разработчик |
| `defects.md` | Шаблон журнала и уже известные дефекты пилота | Все; запись — по еженедельному разбору |
| `manual-interventions.md` | Что на пилоте делалось руками в обход `ops/` и чем это закрыть | Разработчик |
| `locks-audit.md` | Что защищено технически, а что только текстом; команды, которые могут вывести переписку или секреты; предложения замков | Владелец, разработчик |
| `exit-criteria.md` | Условия выхода с числами — черновик; прогресс по каждому условию | Владелец |
| `decisions-options.md` | Четыре решения с вариантами, плюсами и минусами | Владелец |
| `../../prompts/operate-codex.md` | Промпт сопровождения уже развёрнутого экземпляра для Codex | Владелец пилота, позже CEO |

## Как пользоваться

- **Что-то сломалось или повело себя не так.** Открыть чистую сессию Codex с `prompts/operate-codex.md` и назвать симптом своими словами. Codex сам находит сценарий в `scenarios-ops.md`. Если скрипта нет — Codex останавливается и пишет строку для журнала дефектов. Чинить руками в обход нельзя: если всё же пришлось — это отдельный дефект с причиной «сопровождение» и строка в `manual-interventions.md`.
- **Проход сценария продукта.** Взять строку из `scenarios-product.md`, сделать то, что описано в «Как проверить», записать статус прохода (словарь — ниже). Плохой результат — строка в `defects.md`.
- **Учение.** По разделу «Учения на сбоях» в `scenarios-ops.md`: воспроизвести сбой, дать Codex только симптом, оценить по критериям из того же раздела.

Статусы прохода — те же, что в `docs/runbooks/validate-pilot.md`: «прошло локально», «прошло у владельца», «не проверено», «не поддерживается», «ошибка». В документах этапа нет текста переписки, названий чатов, имён людей, ссылок входа и секретов — и не должно появиться.

## Еженедельный разбор (30 минут)

Раз в неделю владелец пилота и разработчик (или Claude в режиме «разработчик») проходят три пункта.

1. **Журнал дефектов — 15 минут.** Новые строки за неделю: у каждой заполнены причина, тяжесть и «кто заметил первым». Для исправленных — есть ли проверка, которая не даст дефекту вернуться (тест, строка `doctor`, проверка в CI). Без проверки строка не закрывается.
2. **Повторы — 5 минут.** Что случилось второй раз (тот же симптом, та же функция, та же причина)? Повтор — признак, что исправлен симптом, а не причина. Что делалось руками (`manual-interventions.md`) — почему, и когда это станет скриптом.
3. **Условия выхода — 10 минут.** Пересчитать числа из `exit-criteria.md`: недели без критичных, доли «Верно» по функциям (`./ops/commitments.sh stats`, счётчики репетиции и разбора входящих в `./ops/doctor.sh` и в приложении), кто первым заметил сбои, обновления и учения Codex. Обновить таблицу «Прогресс условий выхода» в `exit-criteria.md` и записать одну строку итога недели в конец `defects.md`.

Решения, которые нельзя принять на разборе (меняют правила или инварианты), — в `decisions-options.md` и к владельцу.
