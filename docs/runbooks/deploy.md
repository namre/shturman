# Развёртывание базового экземпляра

**Версия runbook:** 0.0.9 · **Для `VERSION`:** 0.0.7 · **Состояние: черновик.** Шаги 1–5 версии 0.0.7 пройдены с нуля на сервере пилота 2026-10-08 (Ubuntu 24.04, Caddy 2.11.7, Cloudflare в режиме прокси перед адресом): `ИТОГ: OK`, `PASS setup-page-public`, `PASS setup-isolation`, `PASS proxy-admin-tcp`, `PASS proxy-admin-dir`. Этот проход нашёл пропуск в 5б — admin-сокет прокси (исправлено). Шаги 6 и 7 с настоящими ботом и аккаунтом ещё не пройдены. Шаги 1–4 пройдены на живом сервере 2026-10-06 (Ubuntu 24.04, Hermes 0.21.5). Шаги 3, 5 и 7б пройдены 2026-10-07 на стенде под Docker с выдуманными значениями: официальный образ Hermes, образ сервиса, настоящий Caddy 2.10.2 с двумя блоками по образцу и внутренним сертификатом — вывод шага 5г совпал с ожидаемым, страница «Переписка» открылась в браузере по адресу с портом. Шаг 6 в части входа и мастера проверен на стенде. В шаге 7 вход в аккаунт Telegram и выбор чатов проверены только на стенде сервиса с подставным Telegram. С настоящим сертификатом, открытым в firewall портом, настоящими ботом и аккаунтом runbook не пройден ни разу — первый проход на сервере и есть проверка. Шаг 8 — по желанию владельца; его пункты под Docker проходились на стенде разработки в прежних версиях. Вывод не совпал с ожидаемым — стоп.

Этот runbook — для режима с Hermes (`SHTURMAN_MODE=hermes`, по умолчанию). Установка без Hermes, «только архив и согласования», — `docs/runbooks/deploy-standalone.md`.

## Цель и критерий готовности

На чистом сервере работают стоковый Hermes из официального образа с ботом-ассистентом, который отвечает только владельцу, и сервис переписки, подключённый к Hermes; владелец настроил переписку на странице «Переписка» или сознательно отложил это. Критерий: владелец написал боту и получил ответ; сообщение с постороннего аккаунта осталось без ответа; `./ops/doctor.sh` показывает `ИТОГ: OK`, `PASS service`, `PASS setup-origin`, `PASS setup-page-public`, `PASS setup-isolation`.

Первая настройка у владельца — два места в браузере: мастер (помощник, модель, бот-ассистент) и страница «Переписка» (ключи приложения Telegram, вход в аккаунт по QR-коду, выбор чатов). **Бот согласований, бизнес-режим Telegram, защита от внедрённых инструкций и поиск по смыслу в первую настройку не входят** — это шаг 8, «позже, по желанию владельца». Отправка сообщений в этот runbook не входит и остаётся выключенной. Имя и характер ассистента владелец выбирает сам на первом шаге мастера.

## Предусловия

- Сервер Linux, доступ по SSH, пользователь с правом запускать Docker.
- У владельца готовы: адрес (домен), направленный на сервер; Telegram на телефоне или компьютере; ключ провайдера модели либо подписка ChatGPT. Бота он создаст по подсказке мастера, свой числовой Telegram ID ему знать не нужно. Ключи приложения Telegram он получит по подсказке страницы «Переписка».
- На сервере можно открыть порты 80, 443 и 8443. Если 8443 открыть нельзя — странице «Переписка» понадобится отдельное имя (шаг 5а).
- Репозиторий склонирован, агент запущен в его корне.

## Инварианты

Действуют все инварианты, стоп-точки и запреты из `AGENTS.md`. Дополнительно для этого runbook:

- Бота-ассистента (бота Hermes) в бизнес-режиме Telegram не подключать — ни на каком шаге. Бизнес-режим бывает только у бота согласований и только по решению владельца (шаг 8д).
- Ссылки из `./ops/activation-link.sh` и `./ops/setup-link.sh` передать владельцу как есть и больше нигде не сохранять. `./ops/setup-link.sh` — только по явной просьбе владельца.
- На страницу «Переписка» не заходить, её адреса не запрашивать, что владелец на ней ввёл — не спрашивать. О её состоянии судить по строкам `setup-*` в `./ops/doctor.sh`.
- Адрес страницы «Переписка» не должен совпадать с адресом дашборда; путь `/shturman-setup/` в блок дашборда обратного прокси не добавлять.
- На сервере не должно быть посторонних контейнеров. Нашлись — стоп.
- Отправку не включать: строку `SHTURMAN_SENDING` в `.env` не добавлять (`docs/architecture.md`, «Открытое ограничение»).
- `./ops/tg-login.sh` и `./ops/init-env.sh` без `--auto` — запасной путь, запускает только человек; их вывод не читать и не просить.
- Ссылку из `./ops/bot-bind.sh` выдавать только по явной просьбе владельца, передать как есть и нигде не сохранять — либо владелец запускает скрипт сам.
- Каталог `data/` и содержимое базы не читать; о состоянии архива судить по счётчикам `./ops/doctor.sh`.

## Шаги

Формат шага: действие → проверка → запись состояния. Провал проверки дважды — стоп.

### 1. Состояние и вариант установки
`./ops/state.sh show`. Если шаги уже отмечены — продолжить со следующего.
- Если шагов ещё нет — **до любого другого действия спросить владельца, какой из двух вариантов он ставит**, простыми словами:
  - **«Ассистент в Telegram (Hermes)»** — ассистент отвечает владельцу в Telegram, ведёт архив переписки, готовит ответы и сводки. Это этот runbook.
  - **«Только архив и согласования»** — без ассистента в Telegram: архив переписки с поиском и список обязательств; вопросы владелец задаёт из своего Codex CLI или Claude Code. Полного разговорного агента нет; ограниченные сервисные задачи ответа возможны при своём боте и модели. Тогда этот runbook закрыть и идти по `docs/runbooks/deploy-standalone.md`.
- Вариант выбирает владелец. Не выбирать за него и не считать выбором то, какой runbook или стартовый промпт получен: нужен явный ответ. Чем варианты отличаются — `docs/standalone.md`, «Что это».
- Развёртывание начато по runbook прежней версии (в состоянии есть шаг `business-plugin`): шаги до 6-го засчитываются, дальше идти по этому runbook с шага 7; что делать с уже подключённым бизнес-режимом — `UPGRADING.md`, «0.0.5 → 0.0.6».
- Запись: `./ops/state.sh done choice`

### 2. Проверка сервера
`./ops/preflight.sh`
- Ожидается: `ИТОГ: OK`. Строки `WARN` объяснить человеку простыми словами.
- `FAIL docker` — **стоп-точка**: установка Docker требует `sudo`. Получить согласие, ставить по официальной инструкции Docker для дистрибутива, после — повторить preflight.
- `WARN net:telegram` или `net:openai` — **стоп-точка**: без исходящего маршрута дальше идти бессмысленно. Объяснить, что нужен прокси (`EGRESS_PROXY_URL`), и что доступ к провайдеру модели из неподдерживаемого региона нарушает его условия и может стоить аккаунта. Решение принимает человек.
- `WARN setup-port: порт 8443 уже кто-то слушает` — выяснить, что это за программа. Посторонняя — сказать владельцу: странице «Переписка» понадобится другой порт или отдельное имя (шаг 5а).
- Запись: `./ops/state.sh done preflight`

### 3. Служебные значения
`./ops/init-env.sh --auto --mode hermes` — записывает выбранный владельцем вариант установки, генерирует пароль базы и два токена сервиса переписки, ничего не спрашивает и не печатает значений. Файл `.env` не читать.
- Проверка: `./ops/preflight.sh` показывает `PASS env: есть, права 600`.
- Токены и ключи владельца здесь не вводятся: их вводит владелец в браузере на шагах 6 и 7, порядок — `docs/setup.md`.
- Запись: `./ops/state.sh done env`

### 4. Версия Hermes
В `compose.yaml` указана версия официального образа, с которой расширения проверены. Показать её человеку. Если он хочет другую — записать `HERMES_VERSION=<версия>` в `.env` командой `echo` с добавлением в конец файла (сам файл не читать) и предупредить, что она не проверена. Образ не пересобирать и не менять. Теги `latest` и `main` не использовать.
- Проверка: после шага 5 `./ops/doctor.sh` показывает образ с явной версией.
- Запись: `./ops/state.sh set hermes.image <версия>` и `done pin`

### 5. Внешний адрес, прокси и запуск
5а. Спросить у владельца адрес, по которому он будет открывать ассистента, и записать его: `./ops/set-public-url.sh https://адрес`.
- Скрипт записывает два адреса и печатает оба: адрес дашборда и адрес страницы «Переписка» по умолчанию — то же имя, порт 8443. Владельцу этот порт ни знать, ни набирать не нужно: он переходит по кнопке и по ссылке.
- Если порт 8443 открыть нельзя или он занят — другой порт: `./ops/set-setup-url.sh https://адрес:порт`; либо отдельное имя, направленное на этот же сервер (запись DNS делает владелец): `./ops/set-setup-url.sh https://второе-имя`. Адрес, совпадающий с адресом дашборда, скрипт не примет и объяснит почему.
- Проверка: `./ops/set-setup-url.sh` без параметров показывает адрес страницы; он отличается от адреса дашборда.

5б. **Стоп-точка (`sudo`, TLS, порты).** Настроить обратный прокси на хосте по образцу `config/Caddyfile.example` — **два блока сайта**:
- блок дашборда на обычном порту: страницы входа из `plugins/shturman/public` по пути `/shturman-auth/`, отказ на `/shturman-setup*`, всё остальное — на `127.0.0.1:9119`;
- блок страницы «Переписка» на порту 8443 (или на отдельном имени): только пути под `/shturman-setup/` — на `127.0.0.1:8765`, остальное — отказ.

Заголовок `Host` не подменять ни в одном блоке. Блоки не объединять, путь `/shturman-setup/` в блок дашборда не переносить, второй путь на порт 8765 не добавлять. Почему страница на другом порту — простыми словами в шапке образца; пересказать владельцу. Перед выполнением показать человеку итоговую настройку и получить согласие.

В образце есть и глобальный блок `admin unix//run/caddy-admin/admin.sock`: admin API прокси уходит с `localhost:2019`, до которого достаёт контейнер Hermes (он в сети хоста), на Unix-сокет в закрытом каталоге. Каталог создаёт служба Caddy — **до** загрузки новой настройки:
1. `sudo install -D -m 644 config/caddy-admin-socket.conf /etc/systemd/system/caddy.service.d/admin-socket.conf` — каталог `/run/caddy-admin` (владелец — пользователь службы caddy, режим 0700) и перечитывание через сокет;
2. записать настройку прокси, `caddy validate`;
3. `sudo systemctl daemon-reload && sudo systemctl restart caddy` — **restart, не reload**: работающий Caddy слушает admin API по прежнему адресу, и `reload` в настройку с новым адресом admin не проходит (`dial unix /run/caddy-admin/admin.sock: … no such file or directory`). Прокси на несколько секунд недоступен.

Пользователь службы Caddy должен отличаться от пользователя Hermes; каталог сокета в контейнер Hermes не монтировать.
- Проверка: проверка синтаксиса настройки проходит (`caddy validate`); сертификат для адреса получен; `sudo systemctl reload caddy` проходит без ошибки; `sudo stat -c '%U %a' /run/caddy-admin` показывает `caddy 700`; `curl -s -m 3 http://127.0.0.1:2019/config/` не соединяется. После шага 5г `./ops/doctor.sh` покажет `PASS proxy-admin-tcp` и `PASS proxy-admin-dir`.
- Прокси перестал отвечать после правки — `systemctl status caddy` и `journalctl -u caddy -n 30`. Строка про `admin.sock` значит, что настройку перечитали `reload` раньше, чем служба создала каталог: выполнить пункт 1 и `restart`.

5в. **Стоп-точка (firewall).** Открыть порт страницы «Переписка» (по умолчанию 8443, TCP) в firewall сервера и, если есть, в правилах хостинга. Показать владельцу команду и получить согласие. Если перед сервером стоит Cloudflare в режиме прокси — HTTPS на порту 8443 он пропускает; что ещё проверить, сказано в шапке `config/Caddyfile.example`. Для отдельного имени на обычном порту этот пункт не нужен.

5г. `./ops/up.sh` — скачивает образы (Hermes — около 4 ГБ, несколько минут), собирает образ сервиса переписки (первая сборка — ещё несколько минут, нужен интернет для пакетов), запускает базу, сервис и Hermes, включает плагин `shturman`, подключает архив к Hermes и сам вызывает `./ops/doctor.sh`. Что скрипт делает по шагам — `docs/deployment.md`.
- Ожидается: `PASS mode: с Hermes`, `PASS hermes`, `PASS proxy-admin-tcp`, `PASS proxy-admin-dir`, `PASS dashboard`, `PASS dashboard-bind`, `PASS plugin`, `PASS public-url`, `PASS login`, `PASS login-page`, `PASS business-plugin`, `PASS service`, `PASS service-bind`, `PASS database`, `PASS archive-mcp`, `PASS archive` с нулями, `PASS jobs`, `PASS setup-page`, `PASS setup-origin`, `PASS setup-page-public`, `PASS setup-isolation`, `ИТОГ: OK`.
- Предупреждения про токен бота, владельца, мастер, `WARN service-owner`, `WARN setup-state: …Переписка ещё не настроена`, `WARN embeddings` и `WARN guard` на этом шаге нормальны. Строк `approvals-*` быть не должно: бота согласований в первой настройке нет.
- `FAIL login-page` — прокси не отдаёт страницы входа: вернуться к 5б.
- `FAIL proxy-admin` — из контейнера Hermes открыт admin API прокси на `localhost:2019`: **стоп**, вернуться к 5б (глобальный блок `admin` и `config/caddy-admin-socket.conf`). `FAIL proxy-admin-dir` — каталог сокета открыт шире 0700: тот же пункт. `WARN proxy-admin-dir` — каталога нет: прокси не по образцу или служба не перезапущена.
- `FAIL setup-origin` — адрес страницы совпал с адресом дашборда: **стоп**, вернуться к 5а.
- `FAIL setup-isolation` — прокси отдаёт страницу «Переписка» по адресу дашборда: **стоп**, вернуться к 5б; ссылку входа на страницу до исправления не выдавать.
- `WARN setup-page-public` — страница по своему адресу не открывается; причина названа в строке: порт закрыт (5в), у прокси нет блока (5б), нет сертификата, перед адресом внешняя защита. Если проверка с самого сервера упирается во внешнюю защиту или в правила хостинга, попросить владельца открыть адрес страницы из браузера: должна появиться страница входа «Штурмана».
- «`SHTURMAN_PUBLIC_URL` (или `SHTURMAN_SETUP_URL`) в .env записан не как адрес…» — скрипт остановился до запуска: строку вписали вручную или запасным путём `./ops/init-env.sh`. Записать адрес заново (5а) и повторить.
- «Сервис переписки не ответил за 90 секунд» или `FAIL service`, `FAIL database`, `FAIL archive-mcp`, `FAIL archive` — раздел «Сервис переписки не отвечает».
- `FAIL service-bind` — порт сервиса или базы открыт наружу: **стоп**, стек остановить не удаляя данных и разобраться с `compose.override.yaml`.
- `WARN dashboard-bind` и `WARN service-bind` со словами «нет программы ss» — на сервере нет пакета `iproute2`, и проверка, какие адреса слушают дашборд, сервис и база, не выполнена. Сказать владельцу; установка пакета — стоп-точка (`sudo`).
- Проверка: `docker ps` показывает только контейнеры этого стека: `shturman-hermes`, `shturman-service`, `shturman-postgres`.
- Запись: `done hermes-up`

### 6. Первый вход владельца и мастер — стоп-точка
6а. Убедиться, что владелец на связи и готов потратить десять минут. Выполнить `./ops/activation-link.sh` и передать ему ссылку как есть. Ссылка действует 30 минут и один раз; если не успел — выдать новую.

6б. Владелец в браузере проходит шаги мастера «Помощник», «Модель» и «Бот в Telegram». Агент в это время ничего не делает и значений не спрашивает. Дождаться слова «готово».
- Проверка: `./ops/doctor.sh` показывает `PASS bot-token`, `PASS bot-owner`, `PASS service-owner`. Если `service-owner` ещё `WARN` — повторить через минуту: плагин сообщает сервису владельца при запуске шлюза.
- Проверка (делает человек): написать боту «привет» — пришёл ответ. Написать с другого аккаунта — ответа нет. Выйти из дашборда и войти снова — по кнопке «Получить код в Telegram» бот прислал код, код подошёл.
- Запись: `done control-bot`

### 7. Переписка: страница настройки — стоп-точка
Четвёртый шаг мастера, «Переписка», сам ничего не настраивает: он коротко объясняет, зачем это нужно, и ведёт на отдельную страницу. На ней владелец делает три вещи: вводит ключи приложения Telegram, входит в свой аккаунт Telegram по QR-коду и выбирает чаты. Что именно он видит — `docs/setup.md`, «Страница „Переписка“».

7а. Сказать владельцу до выдачи ссылки простыми словами:
- на странице он подключит свой аккаунт Telegram **только на чтение**: сервис с этой сессией ничего не отправляет, но риск ограничений со стороны Telegram для такого подключения есть, и он его;
- читаться будут только те чаты, которые он сам отметит; их сообщения сохраняются на сервере, а раз в сутки ночью разбираются моделью у выбранного им провайдера;
- ключи приложения он возьмёт на my.telegram.org — страница подскажет где; ни агенту, ни в чат их присылать не нужно;
- шаг можно отложить: ассистент будет отвечать и без архива.

7б. **Стоп-точка: выдача ссылки входа.** Только по явной просьбе владельца в текущей сессии: `./ops/setup-link.sh`. Скрипт печатает одну строку со ссылкой вида `https://адрес:8443/shturman-setup/#…` и несколько строк пояснений. Передать ссылку как есть и нигде не сохранять — ни в состоянии, ни в журнале, ни в отчёте; самому не открывать. Ссылка действует 30 минут и один раз; новая отменяет прежнюю, а вход по новой ссылке завершает прежние входы на страницу. Открыв ссылку, владелец нажимает «Открыть настройку». Предпочтительно скрипт запускает сам владелец.
- «сервис переписки запущен без адреса страницы настройки или с прежним» — `./ops/up.sh` и повторить.
- «адрес страницы настройки совпадает с адресом дашборда» — **стоп**, шаг 5а.
- Страница по своему адресу ещё не открывается (`WARN setup-page-public`), а владелец готов сейчас — запасной путь через туннель SSH: `./ops/setup-link.sh --local`; скрипт сам подскажет команду туннеля.

7в. Владелец проходит три шага на странице. Агент в это время ничего не делает, на страницу не заходит и значений не спрашивает. Дождаться слова «готово».
- Проверка: `./ops/doctor.sh` показывает `PASS setup-state: ключи приложения Telegram: заданы, аккаунтов Telegram: 1, сообщений в архиве: N`. Пока история загружается, число сообщений растёт; ноль сразу после выбора чатов — повторить через несколько минут.
- Проверка (делает человек): в мастере на шаге «Переписка» три строки состояния стали зелёными; на итоговом шаге — одна строка «Переписка» с числом сообщений.
- `WARN setup-state: …аккаунтов Telegram: 0` после слова «готово» — вход в аккаунт не завершён: спросить владельца, на каком шаге он остановился; ссылку при необходимости выдать заново.
- Если владелец откладывает — `./ops/state.sh set setup-page skipped` и идти дальше.
- Запись: `done setup-page`

### 8. Позже, по желанию владельца
Ничего из этого для первой настройки не нужно. Каждый пункт предлагать отдельно, не как обязательный, и делать только после согласия. Если владелец не спрашивает — достаточно один раз перечислить, что есть.

8а. Выгрузка из Telegram Desktop — прошлое глубже, чем загружает сессия. Основной путь — та же страница «Переписка» (ссылка — шаг 7б). Запасной путь в терминале: `./ops/import-export.sh scan /путь/к/result.json`, затем `import`; вывод `scan` — названия чатов владельца, команду запускает владелец либо агент по его явной просьбе.
- Проверка: `./ops/doctor.sh` — в строке `PASS archive` число сообщений выросло.

8б. Поиск по смыслу — **стоп-точка** (скачивание около 0,5 ГБ, около 1,2 ГБ памяти): `./ops/embeddings.sh on`. Модель по умолчанию — `e5-small`. Вторую модель, `user2-small`, ставят только по решению владельца: `./ops/embeddings.sh on --model user2-small`; до этого пересказать ему, чем модели отличаются (`docs/search.md`). Смена модели на работающем экземпляре — отдельная стоп-точка: пересчёт всех векторов.
- Проверка: `PASS embeddings` с именем модели либо `WARN embeddings: …идёт подсчёт векторов` со счётчиками «готово» и «осталось» — пока архив считается, это нормально; `./ops/embeddings.sh status` показывает модель и счётчики.
- Сервер начал тормозить или появился `FAIL` — `./ops/embeddings.sh off`.

8в. Защита от внедрённых инструкций — **стоп-точка** (скачивание около 0,3 ГБ, около 0,6 ГБ памяти): `./ops/guard.sh on`. Перед включением пересказать владельцу раздел «Что защита ловит и чего не ловит» из `docs/guard.md`: это снижение риска, а не гарантия.
- Проверка: `PASS guard`; `./ops/guard.sh status` показывает счётчики и `"guard_problem": null`.
- `FAIL guard` — `docker logs --tail 50 shturman-guard`; не хватает памяти — `./ops/guard.sh off`. Выключение — только по явной просьбе владельца.
- Без бота согласований уведомления о скрытых сообщениях приходят в управляющий чат без текста сообщения.

8г. Аккаунт-помощник (дополнительный аккаунт Telegram) — на странице «Переписка», тем же входом по QR-коду. **Вход выполняет только человек.** Запасной путь в терминале: `./ops/tg-login.sh assistant`.

8д. Бот согласований — **только когда владелец сам решил готовиться к отправке.** Это отдельный бот от @BotFather, не бот-ассистент. Зачем он и что меняется — `docs/service.md`, «Свой бот согласований и своя модель».
- **Стоп-точка, вводит только владелец:** токен бота — на странице «Переписка», в разделе «Дополнительно» (ссылка — шаг 7б); там же привязка владельца к боту. Запасной путь в терминале: `./ops/init-env.sh`, `./ops/up.sh`, `./ops/bot-bind.sh` (ссылку привязки агент выдаёт только по явной просьбе).
- Ожидается: `PASS approvals-bot`, `PASS approvals-owner`; в течение 5 минут — `PASS plugin-own-bot`. `FAIL approvals-bot` — `docker exec shturman-service shturman bot-status`; разбор кодов — `docs/runbooks/deploy-standalone.md`, шаг 7.
- Сказать владельцу: карточки с кнопками теперь приходят в бота согласований; изменения, расширяющие права ассистента, ждут его нажатия там же.
- Бизнес-режим Telegram — **стоп-точка, подключает человек, и только к боту согласований**; бота-ассистента в бизнес-режиме не подключают. Порядок — `docs/standalone.md`, «Бизнес-режим Telegram со своим ботом». Сказать владельцу до подключения: с этого момента сообщения из выбранных личных чатов записываются в архив и раз в сутки разбираются моделью; право бота отвечать на сообщения не давать — отправка выключена.
- Сама отправка этим не включается и в runbook не входит.

- Запись: `done archive`; если владелец всё пропускает — `./ops/state.sh set archive skipped`.

### 9. Итог
- Проверка: все шаги отмечены в `./ops/state.sh show`; `./ops/doctor.sh` показывает `PASS wizard` и `ИТОГ: OK`.
- `./ops/backup.sh` — первая копия. Ожидаются строки «Копия готова» и «Копия базы готова».
- Сообщить человеку: версия Hermes и версия «Штурмана»; что работает; настроена ли переписка и сколько сообщений в архиве; что отправка сообщений выключена и почему; что бота согласований пока нет и чем это оборачивается (`docs/architecture.md`, «Открытое ограничение»: ассистент технически может менять настройки сервиса, отправить сообщение не может); что из шага 8 не сделано; где лежат данные (каталог `data/`) и копии (`local/backups`); что копии делаются вручную, по расписанию — пока нет.

## Если вход перестал работать

1. `./ops/doctor.sh`. `FAIL plugin` — запустить `./ops/up.sh`: он включит плагин и перезапустит Hermes.
2. Плагин включён, но дашборд не отвечает — посмотреть `docker logs --tail 50 shturman-hermes`. Если плагин не загружается, включить аварийный вход: `./ops/emergency-access.sh on` и объяснить владельцу, как открыть дашборд через SSH-туннель. Снаружи адрес в этом режиме закрыт.
3. После починки — `./ops/emergency-access.sh off` и снова `./ops/doctor.sh`.

Страница «Переписка» от входа в дашборд не зависит: у неё свой вход и свой адрес. Если не открывается она — таблица ниже, строки `setup-*`.

## Сервис переписки не отвечает

Вход, мастер и бот от сервиса не зависят: пока он не работает, ассистент отвечает владельцу, но архива не видит, новые сообщения выбранных чатов не принимаются, а страница «Переписка» не открывается.

| Строка `./ops/doctor.sh` | Что смотреть |
|---|---|
| `WARN service: сервис переписки не развёрнут` | Контейнера нет: `./ops/up.sh` |
| `FAIL service` | `docker logs --tail 50 shturman-service` — причина отказа запуска названа в последних строках. Строка `SHTURMAN_DASHBOARD_ORIGIN: нужен адрес вида…` значит, что в `.env` неразборчиво записан адрес дашборда (`SHTURMAN_PUBLIC_URL`), а `SHTURMAN_SETUP_ORIGIN: …` — адрес страницы (`SHTURMAN_SETUP_URL`): записать заново (`./ops/set-public-url.sh`, `./ops/set-setup-url.sh`) и `./ops/up.sh`. Если база не поднялась — следующая строка таблицы |
| `FAIL database` | `docker logs --tail 50 shturman-postgres`; свободное место — строка `disk` |
| `FAIL archive-mcp` | Запись в настройках Hermes пропала: `./ops/up.sh` запишет её и перезапустит Hermes |
| `FAIL archive: сервис не отдал состояние` | Сервис жив, но не отвечает на запрос состояния: `docker logs --tail 50 shturman-service` |
| `WARN jobs` | Задания копятся: Hermes их не забирает. Проверить `PASS hermes`, `PASS plugin`, `PASS bot-token`; журнал — `docker logs --tail 50 shturman-hermes`. Со своим ботом или своей моделью — ещё и строки `approvals-bot` и `model` |
| `WARN service-owner` | Бот не привязан в мастере или шлюз ещё не сообщил владельца: подождать минуту после запуска, затем шаг 6. Со своим ботом согласований этой строки нет — смотреть `approvals-owner` |
| `WARN setup-page: …сервис прежней версии` | Образ сервиса не обновился: `./ops/up.sh` |
| `FAIL setup-page`, `WARN setup-page: …не запущена` | Сервис не отдаёт страницу на локальном адресе: `docker logs --tail 50 shturman-service` |
| `FAIL setup-origin` | Адрес страницы совпал с адресом дашборда — по внешнему адресу сервис её не отдаёт (через туннель SSH она открывается): `./ops/set-setup-url.sh` (проще всего то же имя на другом порту), `./ops/up.sh`; затем прокси и firewall для нового адреса — стоп-точки |
| `WARN setup-origin` | Адрес не задан: `./ops/set-public-url.sh` или `./ops/set-setup-url.sh`; либо записан, а сервис не перезапущен: `./ops/up.sh` |
| `WARN setup-page-public` | Причина названа в строке. Порт закрыт — шаг 5в; у прокси нет блока — шаг 5б; сервис не узнаёт адрес — `./ops/up.sh`, заголовок `Host` в прокси не подменять. До починки — `./ops/setup-link.sh --local` |
| `FAIL setup-isolation` | Прокси отдаёт страницу по адресу дашборда: поправить блок дашборда по образцу (стоп-точка); до исправления ссылку входа на страницу не выдавать |
| `WARN plugin-code` | Файлы плагина изменились после последнего `./ops/up.sh` (репозиторий обновили), и Hermes исполняет прежний код плагина: `./ops/up.sh` перезапустит его |
| `WARN business-hermes` | Экземпляр прежней схемы: бот-ассистент подключён в бизнес-режиме. Ничего не трогать; решает владелец — `UPGRADING.md`, «0.0.5 → 0.0.6» |
| `WARN plugin-own-bot` | Плагин в Hermes и сервис расходятся в том, кто ведёт согласования. Плагин переспрашивает раз в 5 минут: повторить проверку; не прошло — `PASS hermes`, `PASS bot-token`, журнал `docker logs --tail 50 shturman-hermes` |
| `FAIL approvals-bot`, `WARN approvals-owner`, `WARN model` | Свой бот согласований и своя модель: `docs/runbooks/deploy-standalone.md`, раздел «Если что-то не работает» |
| `FAIL guard` | Модель защиты не отвечает, входящие видны ассистенту непроверенными: `docker logs --tail 50 shturman-guard`; `./ops/guard.sh on` запускает контейнер заново |
| `FAIL embeddings` | `docker logs --tail 50 shturman-embeddings`; не хватает памяти — `./ops/embeddings.sh off` |
| Сборка образа в `./ops/up.sh` завершилась ошибкой | Нет доступа в интернет к пакетам или не хватило места на диске. Повторить один раз; не помогло — стоп |

В журналах сервиса нет текста сообщений, но есть номера чатов и виды ошибок. Журнал показывать владельцу можно, пересылать куда-либо — нет. Две неудачи подряд — остановиться и описать проблему. Данные (`data/`) при разборе не трогать и не читать.

## Откат

Остановить стек без удаления данных. Если владелец входил в аккаунты Telegram, эти сессии он завершает сам в Telegram: «Настройки → Устройства». Если подключали бота согласований в бизнес-режиме — его в настройках Telegram Business отключает человек. Блок страницы «Переписка» в обратном прокси и открытый для неё порт можно убрать (стоп-точки). Всё, что удаляет данные (`data/`, тома, `down -v`), — стоп-точка. Возврат на прежнюю версию — `UPGRADING.md`, «Откат».

## Что ещё должно появиться

`ops/smoke.sh`, `ops/restore.sh`, копии по расписанию; этот runbook проходит проверку на чистом сервере целиком.

## После базовой установки: отдельная приёмка

Базовое здоровье стека не доказывает качество памяти, источников и доставки. Если владелец выбрал сценарий ответов, настроить собственный бот сервиса и выбранную модель, затем пройти `docs/runbooks/validate-pilot.md` сначала без доставки. Повседневные решения — `/menu` и карточки в Telegram. Начальные входы в Telegram и у провайдера остаются действиями владельца в браузере или по QR. Отправку, источники и публичный доступ не включать из факта успешного `doctor.sh`.
