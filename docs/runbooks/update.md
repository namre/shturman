# Обновление экземпляра

**Для кого:** оператор — ИИ-агент по `prompts/operate-codex.md`. **Состояние:** черновик — проверен тестами и на стенде разработки (режим без Hermes, обновление с миграцией и с откатом), на экземпляре с Hermes не пройден. Вывод не совпал с ожидаемым — стоп.

Обновляет один скрипт — `./ops/update.sh`: проверка до, копия, новая версия, `./ops/up.sh`, проверка после, откат при провале. О новой версии владелец узнаёт сам — сообщением в боте согласований (кнопка «Как обновить» даёт текст для агента); итог обновления скрипт передаёт сервису, и тот пишет владельцу. Выпуски и каналы — `docs/releases.md`; восстановление из копии и откат вручную — `docs/runbooks/restore.md`.

## Цель и критерий готовности

Экземпляр стоит на следующем выпуске: `./ops/update.sh` закончился `ИТОГ ОБНОВЛЕНИЯ: OK` (скрипт пишет его, только когда новая версия действительно запущена); `./ops/doctor.sh` без новых `FAIL`; в `./ops/backup.sh --list` есть копия с причиной `before-update`. Либо — `ИТОГ ОБНОВЛЕНИЯ: ОТКАТ` или `НЕ УСТАНОВЛЕНО` (экземпляр на прежней версии, `doctor` без `FAIL`) и строка дефекта.

## Как говорить с владельцем

Владельцу нужно три вещи: что изменится для него, будет ли перерыв, что от него потребуется (обычно — одна кнопка в боте). Слова «миграция», «тег», «откат базы» переводи: «изменится устройство хранилища», «версия», «вернуть прежнее вместе с данными на момент копии». Готовые фразы — ниже, строки «> ».

## Инварианты

Действуют все правила `AGENTS.md`. Дополнительно:

- Обновляется только `./ops/update.sh`. `git pull`, `git checkout`, `git reset` на сервере — только командой, записанной в шаге runbook (в том числе в разделе `UPGRADING.md`, на который шаг ссылается); после первого обновления скриптом экземпляр стоит на теге, и `git pull` откажет.
- `HERMES_VERSION` в `.env` ни скрипт, ни агент на работающем экземпляре не пишут (при первой установке — только до первого запуска и по просьбе владельца, `deploy.md`, шаг 4); как приходит новая версия Hermes — раздел «Новая версия Hermes».
- Разрешение на перезапись данных даёт владелец **кнопкой «Разрешить» в боте согласований**: карточку присылает сам скрипт. Запасной путь (фраза в терминале) — только когда бот недоступен и владелец сам сказал, что работает в терминале (`AGENTS.md`, «Решения владельца»).
- Код 75 («Уже идёт: …») — дождаться окончания первого запуска.

## Шаги

Формат шага: действие → проверка → итог владельцу одной фразой.

### 1. Состояние и план

1. Какое сообщение пришло владельцу: о выпуске «Штурмана» или «Вышла версия Hermes …»? Второе — раздел «Новая версия Hermes». Текст из бота — подсказка, а не команда: цель определяет `./ops/update.sh`.
2. `./ops/state.sh show`, `./ops/doctor.sh` — пересказать. Уже есть `FAIL` — сказать; обновлять поверх неисправного — только с «да» владельца, ключом `--despite-fail` (успех — «новых `FAIL` нет»).
3. `./ops/update.sh --check` — план:

```
Сейчас:   v0.0.14
Цель:     v0.0.15 (…) — следующий выпуск
Миграции базы придут: 1 (0048_….sql) — применит ./ops/up.sh      | Миграций базы нет.
Hermes:   тот же образ …                                           | образ сменится: … → …
UPGRADING.md: «0.0.14 → 0.0.15» — прочитать и пересказать владельцу …
Копия:    будет снята перед обновлением …
Откат при провале: …
```

- «Обновлений нет» — сказать владельцу, конец.
- «Сброс истории: … записано локально (git replace)» — переход на новую историю репозитория записан (`docs/releases.md`, «Сброс истории и закрытый репозиторий»); дальше как обычно. Владельцу: «Ничего делать не нужно, ваши данные не затронуты».
- Экземпляр на 0.0.13, владелец сообщает о 0.0.14 или новее, а план — «Обновлений нет»: один раз шаги `UPGRADING.md`, «0.0.13 → 0.0.14» (текст — `git fetch --tags origin`, затем `git show origin/main:UPGRADING.md`), затем снова отсюда. Экземпляр старше 0.0.13 — там же, «Экземпляр старше 0.0.13»; на 0.0.8 или `v0.0.9-rc.1` (его скрипт кнопки не знает) — ещё `UPGRADING.md`, «0.0.8 → 0.0.9», владельца в терминал не отправлять.
- «Выпусков … ещё нет» — тегов на экземпляре нет; так быть не должно: стоп, строка дефекта, разработчику.

4. **Пересказ раздела цели.** Текст — `git show <тег цели>:UPGRADING.md`, раздел, который назвал план (строка «раздела нет» — действий сверх скрипта не нужно). Пересказать блок «Для владельца» своими словами и добавить из плана: есть ли изменения хранилища (миграции), сменится ли Hermes, нужна ли кнопка, есть ли шаги «Вне скрипта». Образец:

> Вышла версия 0.0.15. Для вас изменится вот что: … Ассистент будет недоступен минут пять–пятнадцать, пока ставится новая версия; перед этим я сделаю копию данных. Обновляем?

План просит разрешения («Нужно разрешение владельца») — после «да» шаг 2 со своей фразой; не просит — сразу шаг 3.

Особые случаи — каждый с отдельным «да»:
- уже есть `FAIL` (`--despite-fail`):

> Сейчас у ассистента уже есть неполадка: … Могу обновить поверх неё — тогда успехом будет «новых неполадок не появилось», а старая останется. Или сначала разберёмся с ней. Как поступим?

- владелец не хочет давать разрешение на откат данных (`--no-auto-rollback`):

> Можно обновить без разрешения на автоматический возврат данных. Тогда, если новая версия встанет с ошибками и успеет изменить хранилище, я данные сам возвращать не буду: ассистент останется на новой версии с ошибками, пока вы не разрешите откат кнопкой в боте. Обновляем так?

- впереди несколько выпусков (`--all`, шаг 4):

> До последней версии — ещё N выпусков. Могу ставить их подряд: перед каждым — копия, после каждого — проверка; на первой неудаче остановлюсь, а если выпуск попросит разрешения — придёт кнопка в бот. Ассистент будет недоступен дольше — по 5–15 минут на выпуск. Ставим все подряд или по одному?

- Проверка: владелец сказал «да».
- Итог владельцу: что будет и сколько займёт.

### 2. Разрешение владельца в боте (если план его просит)

План говорит «Нужно разрешение владельца», когда в выпуске миграции базы или смена образа Hermes: при провале откат перезапишет базу и `data/` из копии, снятой перед обновлением, и всё, что придёт в архив за минуты обновления, может пропасть. Ещё — когда версия Hermes не из списка проверенных. При `--all` этот шаг пропустить: разрешение спросит сам каждый шаг цепочки, `--consent` с `--all` не сочетается.

> Если новая версия не встанет, я верну прежнюю вместе с данными на момент копии, снятой прямо перед обновлением: архивом переписки, памятью и настройками ассистента. Сообщения, пришедшие за минуты обновления, из архива пропадут; в Telegram ничего не изменится. Я отправлю запрос в бот согласований — откройте его и нажмите «Разрешить», если согласны.

1. `./ops/update.sh --consent` (с теми же `--to` / `--channel`, что в плане).
- Проверка: «Ждём подтверждения владельца в боте согласований: …; запрос действует до ЧЧ:ММ», после нажатия — «Разрешение получено: обновление до vX.Y.Z, один раз, 2 часа». Время в выводе — по часам сервера (обычно UTC): владельцу называть по его поясу (строка `timezone` в `doctor`).
2. Код 4, «Владелец ещё не ответил…» — запрос в силе (ждёт до 5 минут, `OPS_CONSENT_WAIT`): напомнить и после «нажал» повторить ту же команду; есть ли разрешение — `./ops/update.sh --check`.
3. «Владелец отклонил» или «срок вышел» (код 4) — ничего не изменено; заново — только если он передумал.
4. Сервис не работает — карточку пришлёт сам скрипт напрямую от бота («Сервис не отвечает: запрос владельцу — напрямую…»). «Подтвердить в боте согласований сейчас нельзя…» — сказать причину; лучший выход — вернуть бот (`docs/setup.md`); запасной путь — только для владельца, который сам работает в терминале.

Разрешение — на эту цель, один раз, 2 часа после нажатия. Владелец не хочет давать разрешение на откат базы — с его «да» обновить с `--no-auto-rollback`: при провале скрипт остановится (код 3) и назовёт команду отката (`restore.md`, «Откат обновления»).

- Итог владельцу: разрешение получено, начинаю.

### 3. Обновление

В фоне (сборка образов — до 15 минут), с кодом выхода в конце журнала:

```
nohup sh -c './ops/update.sh; echo "КОД ВЫХОДА: $?"' > /tmp/shturman-update.log 2>&1 &
```

Ключи — из плана: `--upgrading-read`, если в разделе цели есть «Стоп-точка» и её шаги пересказаны и одобрены; `--no-auto-rollback`, `--despite-fail` — только с «да» владельца (фразы — шаг 1). **Окончание — строка `КОД ВЫХОДА: N`** в конце файла: её пишет обёртка, когда `update.sh` завершился. Итог — по коду N и последней строке `ИТОГ ОБНОВЛЕНИЯ:` (с `--all` — `ИТОГ ЦЕПОЧКИ:`) перед ней, по таблице. Строка `ИТОГ:` раньше в журнале — это `./ops/doctor.sh` внутри `./ops/up.sh`, не итог обновления. Строки `ИТОГ ОБНОВЛЕНИЯ:` нет вовсе (коды 0 «Обновлений нет», 2, 3 «Копия не сделана», 4, 75) — итог в последних строках перед кодом. Тот же журнал — `local/update/<время>.log` (читать можно, `AGENTS.md`).

| Итог | Код | Что это | Что делать | Владельцу |
|---|---|---|---|---|
| `ИТОГ ОБНОВЛЕНИЯ: OK` | 0 | Новая версия запущена, новых `FAIL` нет | Шаг 4 | «Обновил, всё работает; итог придёт и в бот» |
| `ИТОГ ЦЕПОЧКИ: OK` (`--all`) | 0 | Все выпуски до последнего установлены и проверены | Шаг 4 | То же |
| `ИТОГ ЦЕПОЧКИ: остановка на шаге N (код K)` | K | Шаг N кончился как строка с кодом K; выпуски до него установлены | По строке кода K | Какие версии встали, на какой остановился |
| `ИТОГ ОБНОВЛЕНИЯ: ОТКАТ` | 1 | Проверка после не прошла; экземпляр на прежней версии | Строка дефекта (`prompts/operate-codex.md`, п. 8) с новыми `FAIL` | «Обновление не встало, всё как было» |

Код возвращён, данные не тронуты | Строка дефекта с причиной из вывода `./ops/up.sh` (выше итога или в `local/update/<время>.log`). Повторять — когда причина устранена | «Обновление не установлено, работает прежняя версия» |
| `ИТОГ ОБНОВЛЕНИЯ: FAIL — нужен человек` | 3 | Миграции применились, разрешения на откат базы не было; экземпляр на новой версии с ошибками | Предложить откат (`restore.md`, «Откат обновления»), строка дефекта | «Новая версия встала с ошибками. Могу вернуть прежнюю вместе с данными на момент перед обновлением — тогда пришедшее за эти минуты из архива пропадёт; придёт запрос в бот» |
| `ИТОГ ОБНОВЛЕНИЯ: FAIL — откат не удался` | 3 | Откат упал; при неполной копии («Откат не начат») экземпляр на новой версии | Стоп. Строка дефекта; цела ли копия — строки проверки выше и `./ops/backup.sh --verify <метка>`; что она «сохранена», не говорить, пока проверка не прошла | «Обновление не встало, и вернуть прежнее автоматически не вышло. Данные не удалены; нужен разработчик» |

### 4. После

- `./ops/doctor.sh` — показать; строки, которые называет раздел цели.
- `./ops/state.sh show` — запись `step.update-vX.Y.Z` поставил скрипт.
- Шаги раздела цели «Вне скрипта», назначенные «после», — по одному, каждый с «да» владельца.
- План говорил «последний — …, до него ещё запуски» — следующий выпуск только после того, как владелец посмотрел, что всё работает (снова с шага 1). **Или**, если он сразу разрешил «до последнего» (фраза — шаг 1; вставленный им текст кнопки «Как обновить» — тоже его разрешение), — `nohup sh -c './ops/update.sh --all; echo "КОД ВЫХОДА: $?"' > /tmp/shturman-update.log 2>&1 &`, итог — строка `ИТОГ ЦЕПОЧКИ:` перед `КОД ВЫХОДА:`. До запуска пересказать раздел каждого выпуска цепочки (теги между нынешним и последним — `git tag -l 'v*' --sort=v:refname` после `--check`; раздел — `git show <тег>:UPGRADING.md`); «Стоп-точка» в любом остановит цепочку (код 2) — тот выпуск отдельно, с `--upgrading-read`. `--all` не сочетается с `--to`, `--upgrading-read`, `--despite-fail`.
- Итог в бот от «Штурмана» («обновлён: A → B, проверки прошли») не пришёл за 30 минут — `./ops/doctor.sh`, строка `updates`.
- Конец сессии — `./ops/report.sh --scenario О2 --result clean|intervened|failed` (`prompts/operate-codex.md`, п. 9).

> Обновил до 0.0.15, проверки прошли. «Штурман» пришлёт вам итог в бот. Туда же придёт отчёт о сессии — что я делал, без вашей переписки, имён и ключей; если нажмёте «Отправить», он уйдёт разработчику. Прочитайте и решите.

## Первое обновление по этой схеме (только экземпляры до 0.0.8)

**Применимо, только если нужный тег уже есть на самом экземпляре.** После сброса истории прежних тегов на GitHub нет (`docs/releases.md`, «Сброс истории и закрытый репозиторий»); нет тега — стоп, строка дефекта, разработчику (`UPGRADING.md`, «0.0.13 → 0.0.14», «Экземпляр старше 0.0.13»).

Экземпляр до 0.0.8 стоит на ветке `main`, `./ops/update.sh` у него нет. Один раз — прежним порядком до тега выпуска; раздел `UPGRADING.md` «0.0.7 → 0.0.8» ссылается сюда.

1. `./ops/state.sh show`, `./ops/doctor.sh`; `git status --porcelain` — пусто.
2. `./ops/backup.sh` — «Копия готова», «Копия базы готова» (прежний скрипт: копия без описи).
3. `./ops/state.sh set prev_commit "$(git rev-parse HEAD)"`; проверка — `./ops/state.sh get prev_commit` печатает 40 знаков (пояснение 1).
4. `git fetch --tags origin` и `git checkout --detach vX.Y.Z` (тег, который назвал разработчик; что придёт — `git log --oneline HEAD..vX.Y.Z`).
5. `nohup ./ops/up.sh > /tmp/shturman-up.log 2>&1 &` — до `ИТОГ:`. «Ждут: миграции … Свежей проверенной копии нет» — `./ops/backup.sh` и снова `./ops/up.sh`.
6. `./ops/backup.sh` (уже с описью), `./ops/backup.sh --verify` → `ИТОГ ПРОВЕРКИ КОПИИ: OK`.
7. Экземпляр, который берёт кандидаты, — `./ops/update.sh --set-channel pilot`.
8. `./ops/update.sh --check` → «Обновлений нет»: дальше — шагами выше.

**Критерий.** `cat VERSION` — версия тега; `./ops/up.sh` — `ИТОГ: OK`; `doctor` без новых `FAIL`; `prev_commit` записан; в `./ops/backup.sh --list` — копия шага 2 («версия неизвестна…») и копия шага 6 (причина `manual`, «проверена»). Копии `before-update` здесь нет: её снимает только `./ops/update.sh`.

**Откат этого пути** (`./ops/restore.sh --rollback` здесь не работает): миграций не было — `git checkout --detach "$(./ops/state.sh get prev_commit)"` и `./ops/up.sh`; были — сначала база из копии шага 2: `./ops/restore.sh --from <метка> --only db --no-start` (кнопка владельца в боте, `restore.md`), затем тот же `git checkout --detach …` и `./ops/up.sh`.

## Новая версия Hermes

Версия образа Hermes: есть строка `HERMES_VERSION` в `.env` — из неё; нет — версия по умолчанию из `compose.yaml` той версии «Штурмана», что стоит на экземпляре. `./ops/update.sh` строку не меняет, а скрипта, который её пишет, нет (`./ops/init-env.sh` её не пишет).

**Без терминала владельца путь один: новая версия Hermes приходит с выпуском «Штурмана».** Разработчик проверяет её на стенде, вносит в `config/hermes-versions.txt` и `releases.json` и меняет версию по умолчанию в `compose.yaml` (`docs/releases.md`, «Новая версия Hermes»). Тогда план показывает `Hermes:   образ сменится: … → …`, и обновление идёт шагами выше (смена образа — повод для разрешения в боте). Так — только если строки `HERMES_VERSION` в `.env` нет: строка сильнее версии по умолчанию, и план покажет `Hermes:   тот же образ`. Строку пишет агент только при первой установке, до первого запуска и по просьбе владельца (`deploy.md`, шаг 4); на работающем экземпляре — нет (пояснение 2). Есть ли она, агент узнаёт не из `.env`, а из плана: строка «версия закреплена строкой HERMES_VERSION в .env».

**Сообщение «Вышла версия Hermes …»** (только в режиме с Hermes) — `./ops/update.sh --check`:
- план называет выпуск «Штурмана» и `Hermes:   образ сменится` на эту версию — обычное обновление, шаги выше;
- выпуска с ней нет, а строки «версия закреплена» в плане нет:

> Новая версия Hermes придёт вместе с обновлением «Штурмана», когда разработчик включит её в выпуск. Раньше её может поставить только человек, который сам работает в терминале сервера, — я этого за вас сделать не могу.

- в плане «версия закреплена строкой HERMES_VERSION в .env»:

> Версия Hermes у вас закреплена вручную, поэтому с обновлениями «Штурмана» она меняться не будет — ни эта, ни следующие. Снять закрепление может только человек, который сам работает в терминале сервера (порядок ниже, с копией перед этим); я этого за вас сделать не могу.

Владелец сам работает в терминале и хочет поставить сейчас — его порядок (сценарий О10, `docs/scenarios-ops.md`):
1. Сверить версию с `config/hermes-versions.txt`; нет в списке — сказать: плагин с ней не проверен, откат Hermes — только восстановлением `data/hermes` из копии.
2. `./ops/backup.sh` — копия с `data/hermes`.
3. Строку `HERMES_VERSION=<тег>` вписывает (или, чтобы снять закрепление, удаляет) сам владелец в своём терминале; агент её не пишет и `.env` не читает.
4. `./ops/up.sh --pull` — без свежей копии остановится («смена образа Hermes»); непроверенную версию назовёт.
5. `./ops/doctor.sh` — `hermes-version` (`PASS … в списке проверенных` или `WARN … нет в списке`), `archive-mcp`, `hermes-tz`, `cron-schedule`.
6. Не встало — прежнюю строку возвращает владелец, затем `./ops/restore.sh --from <метка копии шага 2>` (кнопка в боте).

При следующем `./ops/update.sh` с непроверенной версией план попросит разрешение и на неё.

## Если что-то не так

| Вывод | Что делать |
|---|---|
| «Отслеживаемые файлы на сервере изменены» | Кто-то правил файлы репозитория на сервере. Стоп: `git status` показать владельцу; ничего не сбрасывать (`git reset --hard` — стоп-точка) |
| «git fetch не прошёл … would clobber existing tag» | Тег на GitHub переставлен или в новой истории тег с прежним именем. Стоп, разработчику |
| «На GitHub ветка другой истории репозитория, а перейти на неё нельзя» (код 3), «… из другой истории репозитория, и перехода на неё нет» | Ничего не изменено. Стоп: пересказать причину владельцу и разработчику; `git reset`, `git pull`, `git replace` руками — нет |
| «Тег … указывает на код с VERSION=…» | Выпуск собран неверно. Стоп, разработчику |
| «Между нынешним кодом и … есть выпуски» | По одному: `./ops/update.sh` без `--to` |
| «Внешний каталог копий … недоступен» | Диск копий не подключён — сказать владельцу; подключение — стоп-точка (`sudo`). Без внешнего каталога — `./ops/backup.sh --unset-dir`, только по его решению |
| `up.sh`: «Ждут: … Свежей проверенной копии нет» | Обновление шло не через `update.sh`: `./ops/backup.sh`, затем снова. Копию сделать нельзя (место, база), а запуск нужен — `./ops/up.sh --skip-backup-check`, только с «да» владельца и его кнопкой в боте: «Копию данных сейчас сделать не получается, а ассистенту нужно применить изменения хранилища. Могу запустить без свежей копии: если что-то пойдёт не так, вернуть данные можно будет только из более старой копии — всё, что пришло после неё, пропадёт. Надёжнее сначала освободить место. Запускаю без копии?» |

## Пояснения

1. **Зачем `prev_commit`.** На пути без `./ops/update.sh` `./ops/restore.sh --rollback` не знает, куда возвращаться, а у копии шага 2 нет описи с коммитом; без записи прежний коммит остаётся только в `git reflog`, а его сдвигает любой следующий `checkout`.
2. **Почему агент не пишет `HERMES_VERSION` на работающем экземпляре.** Смена образа Hermes требует свежей копии, а откат после того, как новая версия записала свои данные, документация Hermes не поддерживает — только восстановление `data/hermes`; скрипта, который проводит это с кнопкой владельца, нет. До первого запуска данных Hermes ещё нет, поэтому там строку пишет агент по просьбе владельца.
