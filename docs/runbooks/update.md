# Обновление экземпляра

**Версия runbook:** 0.0.1 · **Для `VERSION`:** 0.0.8 и следующих (`ops/update.sh` появился в 0.0.8, Р-97) · **Состояние:** скрипт пройден на стенде разработки 2026-10-16 (Docker 29, режим без Hermes, настоящие сборка образа сервиса и Postgres 16, выпуски-теги в локальном репозитории): обновление с миграцией — `ИТОГ ОБНОВЛЕНИЯ: OK` за 31 с; обновление, после которого проверка упала, — автоматический откат кода и базы из копии за 113 с (из них 60 с — повторные проверки), число строк совпало. На экземпляре с Hermes и на пилоте не пройден — первое обновление пилота по этому runbook и есть проверка. Вывод не совпал с ожидаемым — стоп.

Обновляет один скрипт — `./ops/update.sh`: проверка до, копия, новая версия, `./ops/up.sh`, проверка после, откат при провале. Что такое выпуск и каналы — `docs/releases.md`. Восстановление из копии и откат вручную — `docs/runbooks/restore.md`.

## Цель и критерий готовности

Экземпляр стоит на следующем выпуске; `./ops/update.sh` закончился строкой `ИТОГ ОБНОВЛЕНИЯ: OK`; `./ops/doctor.sh` — без новых `FAIL`; в `./ops/backup.sh --list` есть копия с причиной `before-update`. Либо — `ИТОГ ОБНОВЛЕНИЯ: ОТКАТ` (экземпляр на прежней версии, `doctor` без `FAIL`) и строка дефекта.

## Инварианты

Действуют все инварианты, стоп-точки и запреты из `AGENTS.md`. Дополнительно:

- Обновляется только через `./ops/update.sh`. `git pull`, `git checkout`, `git reset` руками — нет: после первого обновления скриптом экземпляр стоит на теге (detached HEAD), и `git pull` просто откажет.
- `HERMES_VERSION` скрипт не меняет; его меняет владелец (раздел «Новая версия Hermes» ниже).
- Фразу подтверждения (`РАЗРЕШАЮ`, `ВОССТАНОВИТЬ`, `ОТКАТИТЬ`, `БЕЗ-КОПИИ`) набирает только человек в своём терминале. Агент её не набирает, терминалом за человека не управляет, файл разрешения сам не пишет.
- Второй запуск, пока идёт первый, скрипт не пустит (код 75, «Уже идёт: …»). Это не ошибка — дождаться окончания первого.

## Шаги

### 1. Состояние и план

`./ops/state.sh show`, `./ops/doctor.sh` — показать владельцу. Затем `./ops/update.sh --check`. Ожидается:

```
Сейчас:   v0.0.8
Цель:     v0.0.9 (…) — следующий выпуск
Миграции базы придут: 1 (0041_….sql) — применит ./ops/up.sh      | Миграций базы нет.
UPGRADING.md: «0.0.8 → 0.0.9» — прочитать и пересказать владельцу …
Копия:    будет снята перед обновлением …
Откат при провале: …
```

- «Обновлений нет» — конец, сказать владельцу.
- «Выпусков … ещё нет» — экземпляр до первого выпуска; раздел «Первое обновление по этой схеме» ниже.
- Прочитать раздел `UPGRADING.md` цели (`git show <тег>:UPGRADING.md`) и пересказать владельцу простыми словами: что изменится, есть ли миграции базы, стоп-точки вне скрипта, перезапустится ли ассистент. Ждать его «да».
- В `doctor` уже есть `FAIL` — сказать владельцу; обновлять поверх неисправного — только с его «да», ключом `--despite-fail` (успехом тогда считается «новых `FAIL` нет»).

### 2. Разрешение человека (если план его просит)

План говорит «Нужно разрешение человека», когда в обновлении миграции базы или смена образа Hermes: при провале откат перезапишет базу и `data/` из копии, снятой перед обновлением, а всё, что придёт в архив за минуты обновления, может пропасть. Ещё — когда версия Hermes не из списка проверенных.

Сказать владельцу ровно это и дать команду, которую он вставляет **в Терминал своего компьютера** (не в чат):

```
ssh -t shturman-app 'cd /opt/shturman && ./ops/update.sh --consent'
```

Скрипт покажет план и что разрешается, попросит набрать `РАЗРЕШАЮ <число>`. Ожидается: «Разрешение записано: обновление до vX.Y.Z, действует до ЧЧ:ММ, один раз». Разрешение — на эту цель, на 2 часа, одноразовое.

Если владелец не хочет открывать терминал — с его «да» в этой сессии можно обновить с `--no-auto-rollback`: при провале скрипт остановится (код 3) и назовёт команду отката, которую выполнит человек (`docs/runbooks/restore.md`, «Откат обновления»).

### 3. Обновление

Долго (сборка образов — до 15 минут), поэтому в фоне:

```
nohup ./ops/update.sh > /tmp/shturman-update.log 2>&1 &
```

(с ключами, которые назвал план: `--upgrading-read`, если в разделе `UPGRADING.md` есть «Стоп-точка» и владелец сказал «да»; `--no-auto-rollback`, `--despite-fail` — только с его «да»). Смотреть конец файла, пока не появится строка `ИТОГ ОБНОВЛЕНИЯ:`. Тот же журнал — в `local/update/<время>.log`.

| Итог | Код | Что это | Что делать |
|---|---|---|---|
| `ИТОГ ОБНОВЛЕНИЯ: OK` | 0 | Новая версия, новых `FAIL` нет | Шаг 4 |
| `ИТОГ ОБНОВЛЕНИЯ: ОТКАТ` | 1 | Проверка после не прошла; экземпляр на прежней версии, `doctor` без `FAIL` | Строка дефекта (`docs/pilot/defects.md`) с новыми `FAIL` из вывода; владельцу — «обновление не встало, всё как было» |
| `ИТОГ ОБНОВЛЕНИЯ: FAIL — нужен человек` | 3 | Миграции применились, разрешения на откат базы не было | Экземпляр на новой версии с ошибками. Владельцу — команда отката (`restore.md`, «Откат обновления») и строка дефекта |
| `ИТОГ ОБНОВЛЕНИЯ: FAIL — откат не удался` | 3 | Откат упал | Стоп. Строка дефекта, владельцу; копия до обновления названа в выводе |
| «Копия не сделана…» | 3 | `./ops/backup.sh` не прошёл или внешний каталог недоступен | Обновление не начато. Причина — строкой выше (место на диске, база, диск копий) |
| «Нужно подтверждение человека…» | 4 | Нет разрешения | Шаг 2 |
| «Уже идёт: …» | 75 | Идёт другая команда `ops/` | Дождаться, повторить |
| Остальное с кодом 2 | 2 | Цель не годится: назад, перескок через выпуск, тег собран неверно, стоп-точка без `--upgrading-read` | Прочитать сообщение; тег собран неверно — стоп, сказать разработчику |

### 4. После

- `./ops/doctor.sh` — показать владельцу; строки, которые называет раздел `UPGRADING.md`.
- `./ops/state.sh show` — запись `step.update-vX.Y.Z` поставил скрипт.
- Если план говорил «последний — …, до него ещё запуски» — следующий выпуск только после того, как владелец посмотрел, что всё работает. Повторить с шага 1.
- Шаги из раздела `UPGRADING.md` вне скрипта (стоп-точки) — по разделу, каждый с согласия владельца.

## Первое обновление по этой схеме

Экземпляр, развёрнутый до 0.0.8, стоит на ветке `main`, а `./ops/update.sh` у него ещё нет. Один раз — прежним порядком, но до тега выпуска, а не до `main`:

1. `./ops/state.sh show`, `./ops/doctor.sh`; `git status --porcelain` — пусто.
2. `./ops/backup.sh` — «Копия готова» и «Копия базы готова».
3. `git fetch --tags origin` и `git checkout --detach vX.Y.Z` (тег, который назвал разработчик; `git log --oneline HEAD..vX.Y.Z` — что придёт).
4. `nohup ./ops/up.sh > /tmp/shturman-up.log 2>&1 &` — дождаться `ИТОГ:`. Если `up.sh` скажет «Ждут: миграции … Свежей проверенной копии нет» — копия старше часа: `./ops/backup.sh` и снова `./ops/up.sh`.
5. `./ops/backup.sh` (уже новая: с описью), `./ops/backup.sh --verify` → `ИТОГ ПРОВЕРКИ КОПИИ: OK`.
6. Канал: на пилоте `./ops/update.sh --set-channel pilot`; на остальных ничего.
7. `./ops/update.sh --check` → «Обновлений нет» — с этого момента обновления идут шагами выше.

## Новая версия Hermes

`./ops/update.sh` образ Hermes не меняет; меняет владелец — строкой `HERMES_VERSION` в `.env` (сценарий О10, `docs/pilot/scenarios-ops.md`). Порядок:

1. Сверить целевую версию с `config/hermes-versions.txt`. Нет в списке — сказать владельцу: плагин с ней не проверен; откат Hermes после того, как новая версия записала свои данные, его документация не поддерживает — только восстановление `data/hermes` из копии.
2. `./ops/backup.sh` — копия, в ней `data/hermes`.
3. Строку `HERMES_VERSION` пишет владелец (запасной путь — `./ops/init-env.sh` без `--auto`, только человек).
4. `./ops/up.sh --pull` — без свежей копии он остановится («смена образа Hermes»); непроверенную версию он назовёт предупреждением.
5. `./ops/doctor.sh` — `hermes-version`: `PASS … в списке проверенных` или `WARN … нет в списке`; `archive-mcp`, `hermes-tz`, `cron-schedule`.
6. Не встало — откат: `HERMES_VERSION` прежняя (владелец) и `./ops/restore.sh --from <метка копии шага 2>` (человек; `restore.md`).

При следующем `./ops/update.sh` с непроверенной версией Hermes план попросит разрешение человека и на неё.

## Если что-то не так

| Вывод | Что делать |
|---|---|
| «Отслеживаемые файлы на сервере изменены» | Кто-то правил файлы репозитория на сервере. Стоп: `git status` показать владельцу; ничего не сбрасывать (`git reset --hard` — стоп-точка) |
| «git fetch не прошёл … would clobber existing tag» | Тег на GitHub переставлен — так быть не должно. Стоп, сказать разработчику |
| «Тег … указывает на код с VERSION=…» | Выпуск собран неверно. Стоп, сказать разработчику |
| «Между нынешним кодом и … есть выпуски» | Обновляться по одному: `./ops/update.sh` без `--to` |
| «Внешний каталог копий … недоступен» | Диск копий не подключён. Сказать владельцу; подключение — стоп-точка (`sudo`). Без внешнего каталога — `./ops/backup.sh --unset-dir`, только по его решению |
| `up.sh`: «Ждут: … Свежей проверенной копии нет» | Обновление шло не через `update.sh`: `./ops/backup.sh`, затем снова |
