# Восстановление из копии и откат обновления

**Версия runbook:** 0.0.1 · **Для `VERSION`:** 0.0.8 и следующих (`ops/restore.sh`, Р-97) · **Состояние:** скрипт пройден на стенде разработки 2026-10-16 на настоящей базе (Postgres 16 + pgvector, все миграции сервиса, синтетический архив 20 000 сообщений): копия → порча базы и `data/` → восстановление за 5 с, число строк и сумма длин текстов совпали; переезд на пустое место (ни базы, ни `data/`, ни `.env`) с «внешнего диска» — за 5 с, то же совпадение; откат обновления с миграцией — в составе `ops/update.sh` (`update.md`). Проверка в CI — `ops/tests/e2e_restore.sh`. На экземпляре с Hermes, с настоящими сессиями Telegram и на пилоте не пройден. Восстановление на пилоте — только по отдельному решению владельца; учение — на стенде (`docs/pilot/scenarios-ops.md`, У12, У13).

Восстановление поверх данных — стоп-точка `AGENTS.md`. Поэтому `./ops/restore.sh` **запускает человек** в своём терминале: скрипт показывает, что будет перезаписано, и просит набрать фразу с одноразовым числом. Агент готовит всё до этой точки: выбирает копию, показывает план (`--dry-run`), объясняет владельцу и даёт ему команду.

## Что есть в копии

`./ops/backup.sh` пишет в `local/backups` (и, если задан, во внешний каталог — `SHTURMAN_BACKUP_DIR`) три файла с одной меткой времени: архив `data/` с `.env`, выгрузку базы и опись `meta-<метка>.txt` — версия и коммит кода, режим, версия Hermes, применённые миграции, контрольные суммы, число строк ключевых таблиц. Агент читает только опись и `--list`; архив и выгрузку не открывает (`docs/deployment.md`, «Резервные копии»).

## Восстановление из копии

1. `./ops/state.sh show`, `./ops/doctor.sh` — показать владельцу, что сломано.
2. `./ops/restore.sh --list` — копии: метка, время, размер, версия кода, причина (`manual`, `before-update`, `before-restore`), где лежит, проверена ли. Выбрать с владельцем: обычно — последнюю до поломки.
3. `./ops/backup.sh --verify <метка>` → `ИТОГ ПРОВЕРКИ КОПИИ: OK`. Нет — взять другую.
4. `./ops/restore.sh --from <метка> --dry-run` — план. Пересказать владельцу:
   - база архива заменится копией: всё, что пришло после времени копии, из архива пропадёт;
   - каталоги `data/…` заменятся копией (сессии Telegram, страницы памяти, настройки Hermes);
   - `.env` остаётся нынешним (с `--with-env` — из копии);
   - если копия сделана более старой версией — `./ops/up.sh` применит недостающие миграции; если более новой — скрипт откажет: сначала код той версии;
   - перед восстановлением скрипт сам снимет копию нынешнего состояния (`before-restore`).
   Частично: `--only db` — только база; `--only data` — только каталоги. `--no-start` — стек после восстановления не запускается: когда следом нужен код другой версии (`git checkout --detach <коммит из описи>`, затем `./ops/up.sh`).
5. Владелец запускает в Терминале своего компьютера ту команду, что напечатал `--dry-run`:

   ```
   ssh -t shturman-app 'cd /opt/shturman && ./ops/restore.sh --from <метка>'
   ```

   и набирает `ВОССТАНОВИТЬ <число>`. Агент фразу не набирает.
6. Ожидается: «Число строк совпало с описью: …», «База восстановлена.», «Каталоги данных восстановлены: …», затем вывод `./ops/up.sh` и `ИТОГ ВОССТАНОВЛЕНИЯ: OK`. Агент проверяет: `./ops/doctor.sh` (`archive` — число сообщений как в описи), `./ops/state.sh show` (запись «восстановление из копии …: ИТОГ OK»).
7. Сессии Telegram восстановились из копии: если владелец с тех пор завершал сессию сервиса в Telegram («Устройства»), сбор не пойдёт — вход заново на странице «Настройки Штурмана» (`docs/setup.md`, «Если вход сломался»).

## Откат обновления

Когда `./ops/update.sh` остановился с «нужен человек» (код 3), или владелец решил вернуть прежнюю версию после удачного обновления.

1. `./ops/restore.sh --rollback --dry-run` — что будет: код — на прежний коммит; если применились миграции или сменился образ Hermes — ещё база и `data/` из копии, снятой перед обновлением (и сколько минут назад она снята — столько архива пропадёт).
2. Пересказать владельцу; он запускает `ssh -t shturman-app 'cd /opt/shturman && ./ops/restore.sh --rollback'` и набирает `ОТКАТИТЬ <число>`.
3. Ожидается `ИТОГ ОТКАТА: OK`. Агент: `./ops/doctor.sh`, `cat VERSION`, `./ops/state.sh show`; строка дефекта о неудавшемся обновлении.

## Переезд или новый сервер

1. Новый сервер готовится по `docs/runbooks/server-prepare.md` до шага 8 (репозиторий в `/opt/shturman`), `.env` **не** создаётся.
2. Код той версии, которой сделана копия: в описи — `version` и `commit`; `git checkout --detach <тег или коммит>`.
3. Файлы копии — на сервере, например на подключённом диске копий (подключение — стоп-точка, `sudo`).
4. `./ops/restore.sh --from <метка> --dir <каталог с копией> --dry-run`, затем владелец — без `--dry-run`. Без `.env` скрипт берёт `.env` из копии, запускает новую базу с её паролем и восстанавливает всё.
5. Адрес: если у нового сервера другой IP — `./ops/set-public-url.sh` и прокси по `deploy.md`, шаг 5 (стоп-точки). Посредник подключится под тем же именем сам (ключ — в `.env`, сертификат — в `data/relay`).
6. Старый сервер — остановить, чтобы два экземпляра не читали одну переписку: `docker compose stop` там (данные не удаляются), сессии Telegram старого сервера владелец завершает в «Устройствах» — **после** того, как новый собирает переписку.

## Если что-то не так

| Вывод | Что делать |
|---|---|
| «Копия не прошла проверку» | Файл повреждён (сумма не совпала) или не читается — взять другую копию; внешний каталог проверить `./ops/backup.sh --verify <метка>` |
| «Копия сделана более новой версией кода» | Сначала код той версии (`commit` из описи), затем снова |
| «Мало места на диске» | Нужно около втрое больше размера выгрузки и 1 ГБ запаса. Ничего не изменено. Место — сценарий О9; удалять ничего не сам |
| «Выгрузка не легла в базу … Живая база не тронута» | Подробности — в `local/restore/<время>/pg_restore.log`: **агенту не открывать** (может быть строка данных). Взять другую копию; не помогло — стоп, строка дефекта |
| «Число строк восстановленной базы не совпало с описью» | Копия неполная или повреждена. Живая база не тронута. Другая копия |
| «Копию нынешнего состояния сделать не удалось» | Человек решает в терминале: продолжить без неё (`БЕЗ-КОПИИ <число>`) или остановиться и разобраться (обычно — база не запущена или нет места) |
| `ИТОГ ВОССТАНОВЛЕНИЯ: FAIL` после `up.sh` | Данные на месте, стек не поднялся: строки `FAIL` в выводе — по сценариям `docs/pilot/scenarios-ops.md` |
| «Нужно подтверждение человека …» (код 4) | Команду запускает владелец сам, в своём терминале (`ssh -t`) |
