# Восстановление из копии и откат обновления

**Для кого:** оператор — ИИ-агент по `prompts/operate-codex.md`. **Состояние:** черновик — проверен тестами и на стенде разработки на настоящей базе, на экземпляре с Hermes и настоящими сессиями Telegram не пройден. Восстановление на рабочем экземпляре — только по отдельному решению владельца; учение — на стенде (`docs/scenarios-ops.md`, У12, У13).

Восстановление поверх данных — стоп-точка `AGENTS.md`. «Да» на неё — **нажатие владельца «Разрешить» в боте согласований** (Р-100): агент запускает `./ops/restore.sh`, скрипт показывает, что будет перезаписано, и шлёт владельцу карточку с тем же описанием; продолжает только после нажатия. Владельцу терминал и ssh не нужны. Агент готовит всё до этой точки: выбирает с владельцем копию, показывает план (`--dry-run`), пересказывает его простыми словами и предупреждает: «сейчас придёт запрос в бот — нажмите „Разрешить“, если согласны».

Если сервис переписки лежит (база сломана, сервис не стартует), карточку шлёт сам скрипт — одноразовый контейнер из образа сервиса говорит с Telegram от имени бота согласований (токен он берёт сам, агент его не видит); зависший сервис скрипт при этом останавливает (восстановление всё равно его останавливает). Владелец бота — из базы, а без базы — из копии, которую сервис ведёт в своём каталоге данных. Если бот недоступен вовсе (не настроен, владелец не привязан, новый сервер без `.env` и образа) — запасной путь: владелец, который умеет работать в терминале, сам запускает команду, названную скриптом (`ssh -t …`), и набирает фразу с одноразовым числом. Агент фразу не набирает.

## Что есть в копии

`./ops/backup.sh` пишет в `local/backups` (и, если задан, во внешний каталог — `SHTURMAN_BACKUP_DIR`) три файла с одной меткой времени: архив `data/` с `.env`, выгрузку базы и опись `meta-<метка>.txt` — версия и коммит работающего кода (и кода в каталоге), режим, версия Hermes, применённые миграции, контрольные суммы, число строк ключевых таблиц. Агент читает только опись и `--list`; архив и выгрузку не открывает (`docs/deployment.md`, «Резервные копии»).

## Восстановление из копии

1. `./ops/state.sh show`, `./ops/doctor.sh` — показать владельцу, что сломано.
2. `./ops/restore.sh --list` — копии: метка, время, размер, версия кода, причина (`manual`, `before-update`, `before-restore`), где лежит, проверена ли. Выбрать с владельцем: обычно — последнюю до поломки.
3. `./ops/backup.sh --verify <метка>` → `ИТОГ ПРОВЕРКИ КОПИИ: OK`. Нет — взять другую. Проверка требует каждый файл, записанный в опись: копия без выгрузки базы — `FAIL`, даже если архив цел.
4. `./ops/restore.sh --from <метка> --dry-run` — план. Пересказать владельцу:
   - база архива заменится копией: всё, что пришло после времени копии, из архива пропадёт;
   - каталоги `data/…` заменятся копией (сессии Telegram, страницы памяти, настройки Hermes);
   - `.env` остаётся нынешним (с `--with-env` — из копии);
   - если копия сделана более старой версией — `./ops/up.sh` применит недостающие миграции; если более новой — скрипт откажет: сначала код той версии;
   - перед восстановлением скрипт сам снимет копию нынешнего состояния (`before-restore`).
   Частично: `--only db` — только база; `--only data` — только каталоги. `--no-start` — стек после восстановления не запускается: когда следом нужен код другой версии (`git checkout --detach <коммит из описи>`, затем `./ops/up.sh`).
5. Владелец сказал «да» в разговоре — агент запускает ту же команду без `--dry-run`: `./ops/restore.sh --from <метка>`. Ожидается строка «Ждём подтверждения владельца в боте согласований: восстановление из резервной копии; запрос действует до ЧЧ:ММ». Владелец нажимает «Разрешить» под карточкой. Скрипт ждёт до 5 минут; не дождался (код 4) — запрос в силе, повторить ту же команду после нажатия. «Отклонил» — ничего не изменено.
6. Ожидается: «Число строк совпало с описью: …», «База восстановлена.», «Каталоги данных восстановлены: …», затем вывод `./ops/up.sh` и `ИТОГ ВОССТАНОВЛЕНИЯ: OK`. Агент проверяет: `./ops/doctor.sh` (`archive` — число сообщений как в описи), `./ops/state.sh show` (запись «восстановление из копии …: ИТОГ OK»).
7. Сессии Telegram восстановились из копии: если владелец с тех пор завершал сессию сервиса в Telegram («Устройства»), сбор не пойдёт — вход заново на странице «Настройки Штурмана» (`docs/setup.md`, «Если вход сломался»).

## Откат обновления

Когда `./ops/update.sh` остановился с «нужен человек» (код 3), или владелец решил вернуть прежнюю версию после удачного обновления.

1. `./ops/restore.sh --rollback --dry-run` — что будет: код — на прежний коммит; если применились миграции или сменился образ Hermes — ещё база и `data/` из копии, снятой перед обновлением (и сколько минут назад она снята — столько архива пропадёт).
2. Пересказать владельцу и предупредить о запросе в боте; с его «да» — `./ops/restore.sh --rollback`. Владелец нажимает «Разрешить» под карточкой «Откат последнего обновления: … → …» (в ней — что вернётся и сколько минут архива пропадёт). Не дождался — повторить после нажатия.
3. Ожидается `ИТОГ ОТКАТА: OK`. Агент: `./ops/doctor.sh`, `cat VERSION`, `./ops/state.sh show`; строка дефекта о неудавшемся обновлении.

Если откату нужны база и `data/`, скрипт сначала проверяет копию, снятую перед обновлением (все файлы из описи на месте, суммы совпали, есть выгрузка базы), — ещё до запроса владельцу. Неполная копия — отказ без изменений: откатить код, оставив в базе миграции новой версии, нельзя.

## Переезд или новый сервер

1. Новый сервер готовится по `docs/runbooks/server-prepare.md` до шага 8 (репозиторий в `/opt/shturman`), `.env` **не** создаётся.
2. Код той версии, которой сделана копия: в описи — `version` и `commit`; `git checkout --detach <тег или коммит>`.
3. Файлы копии — на сервере, например на подключённом диске копий (подключение — стоп-точка, `sudo`).
4. `./ops/restore.sh --from <метка> --dir <каталог с копией> --dry-run`, затем без `--dry-run`. Без `.env` скрипт берёт `.env` из копии, запускает новую базу с её паролем и восстанавливает всё. **Пробел:** на новом сервере ни `.env`, ни образа сервиса ещё нет — бот согласований недоступен, разрешение — только запасным путём (фраза владельца в терминале, `ssh -t`). Владелец, который не работает в терминале, здесь пока не обойдётся без помощи (`docs/scenarios-ops.md`, «Без терминала»).
5. Адрес: если у нового сервера другой IP — `./ops/set-public-url.sh` и прокси по `deploy.md`, шаг 5 (стоп-точки). Посредник подключится под тем же именем сам (ключ — в `.env`, сертификат — в `data/relay`).
6. Старый сервер — остановить, чтобы два экземпляра не читали одну переписку: `docker compose stop` там (данные не удаляются), сессии Telegram старого сервера владелец завершает в «Устройствах» — **после** того, как новый собирает переписку.

## Если что-то не так

| Вывод | Что делать |
|---|---|
| «Копия не прошла проверку» | Файл повреждён (сумма не совпала), не читается или его нет, хотя он записан в описи («выгрузки НЕТ, хотя она записана в описи — копия неполная») — взять другую копию; внешний каталог проверить `./ops/backup.sh --verify <метка>`. Вернуть из неполной копии только каталоги `data/` без базы — `--only data`, осознанно и с «да» владельца: база останется нынешней |
| «Копия … неполная или повреждена … Откат не начат» (`--rollback`) | Копии, снятой перед обновлением, не хватает файла или он испорчен. Ничего не остановлено и не изменено, владельцу запрос не приходил; код остаётся на новой версии — откатить его без базы нельзя (в базе её миграции). Стоп: строка дефекта и владельцу; другие копии — `--list` |
| «Копия сделана более новой версией кода» | Сначала код той версии (`commit` из описи), затем снова |
| «Мало места на диске» | Нужно около втрое больше размера выгрузки и 1 ГБ запаса. Ничего не изменено. Место — сценарий О9; удалять ничего не сам |
| «Выгрузка не легла в базу … Живая база не тронута» | Подробности — в `local/restore/<время>/pg_restore.log`: **агенту не открывать** (может быть строка данных). Взять другую копию; не помогло — стоп, строка дефекта |
| «Число строк восстановленной базы не совпало с описью» | Копия неполная или повреждена. Живая база не тронута. Другая копия |
| «Копию нынешнего состояния сделать не удалось» | Скрипт присылает владельцу второй запрос — «восстановление без копии нынешнего состояния»: он решает кнопкой, продолжить или нет. Лучше остановиться и разобраться (обычно — база не запущена или нет места) |
| `ИТОГ ВОССТАНОВЛЕНИЯ: FAIL` после `up.sh` | Данные на месте, стек не поднялся: строки `FAIL` в выводе — по сценариям `docs/scenarios-ops.md` |
| «Владелец ещё не ответил…» (код 4) | Запрос ждёт в боте до названного времени: напомнить владельцу, после нажатия повторить ту же команду |
| «Владелец отклонил…», «Срок запроса вышел…» (код 4) | Ничего не изменено. Повторять — только если владелец передумал: придёт новый запрос |
| «Подтвердить в боте согласований сейчас нельзя…», «Подтвердить нечем…» (код 4) | Бот недоступен — причина строкой выше. Лучше вернуть бот (`docs/setup.md`) и повторить; запасной путь — владелец сам в своём терминале (`ssh -t`, команда в выводе) |
| «Контейнер сервиса запущен, но не отвечает…» | Только у команд, которые не останавливают сервис сами. Починить сервис (`docs/runbooks/symptoms.md`) и повторить |
