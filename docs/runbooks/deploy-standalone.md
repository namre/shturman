# Развёртывание экземпляра без Hermes («только архив и согласования»)

**Версия runbook:** 0.0.3 · **Для `VERSION`:** 0.0.5 · **Состояние: черновик.** Шаги 3, 4 и 8а пройдены 2026-10-07 под Docker на стенде разработки с выдуманными значениями; шаг 7 — с настоящими Claude Code 2.1.292 и Codex CLI 0.160.1. **С настоящим ботом Telegram и настоящей моделью runbook не пройден ни разу**: шаги 5, 6 и 8г на живом сервере — первая проверка. Вывод не совпал с ожидаемым — стоп.

Что это за режим, чего в нём нет и что из написанного проверено — `docs/standalone.md`. Установка с Hermes — `docs/runbooks/deploy.md`.

## Цель и критерий готовности

На чистом сервере работают сервис переписки с пустым архивом и база; у сервиса есть свой бот согласований, привязанный к владельцу, и свой доступ к модели; Hermes не установлен. Критерий: `./ops/doctor.sh` показывает `ИТОГ: OK`, `PASS approvals-bot`, `PASS approvals-owner`, `PASS model`; `docker ps` показывает только `shturman-service` и `shturman-postgres`; владелец получил от бота сообщение о привязке.

Подключение архива к Codex CLI или Claude Code, загрузка истории, поиск по смыслу, сессии аккаунтов, бизнес-режим и защита от внедрённых инструкций — по желанию владельца, шаги 7 и 8. Отправка сообщений в этот runbook не входит и остаётся выключенной.

## Предусловия

- Сервер Linux, доступ по SSH, пользователь с правом запускать Docker.
- У владельца готовы: Telegram; ключ провайдера модели с API, совместимым с OpenAI, и точное имя модели у этого провайдера. Домен, обратный прокси и TLS не нужны: у экземпляра нет веб-адреса.
- Бота согласований владелец создаст у @BotFather на шаге 5. Это отдельный бот: он не должен использоваться ни одной другой программой.
- Репозиторий склонирован, агент запущен в его корне.

## Инварианты

Действуют все инварианты, стоп-точки и запреты из `AGENTS.md`. Дополнительно для этого runbook:

- Токен бота и ключ модели вводит только владелец в своём терминале: `./ops/init-env.sh` без `--auto` агент не запускает, значений не просит, файл `.env` не читает.
- `./ops/mcp-token.sh` запускает только владелец; его вывод не читать и не просить.
- Ссылку из `./ops/bot-bind.sh` передать владельцу как есть и нигде не сохранять — либо владелец запускает скрипт сам.
- Наружу ничего не публиковать: порт 8765 остаётся на `127.0.0.1`, обратный прокси перед ним не ставить.
- Отправку не включать: строку `SHTURMAN_SENDING` в `.env` не добавлять.
- `./ops/tg-login.sh` запускает только человек; его вывод не читать и не просить.
- Каталог `data/` и содержимое базы не читать; о состоянии архива судить по счётчикам `./ops/doctor.sh`.
- На сервере не должно быть посторонних контейнеров. Нашлись — стоп.

## Шаги

Формат шага: действие → проверка → запись состояния. Провал проверки дважды — стоп.

### 1. Состояние и вариант установки
`./ops/state.sh show`. Первая строка называет режим установки. Если шаги уже отмечены — продолжить со следующего.
- Если шагов ещё нет — **до любого другого действия спросить владельца, какой из двух вариантов он ставит**, простыми словами:
  - **«Ассистент в Telegram (Hermes)»** — ассистент отвечает владельцу в Telegram, ведёт архив переписки, готовит ответы и сводки. Тогда этот runbook закрыть и идти по `docs/runbooks/deploy.md`.
  - **«Только архив и согласования»** — без ассистента в Telegram: архив переписки с поиском и список обязательств; вопросы владелец задаёт из своего Codex CLI или Claude Code. Готовых черновиков ответов нет. Это этот runbook.
- Вариант выбирает владелец. Не выбирать за него и не считать выбором то, какой runbook или стартовый промпт получен: нужен явный ответ. Чем варианты отличаются — `docs/standalone.md`, «Что это».
- Запись: `./ops/state.sh done choice`

### 2. Проверка сервера
`./ops/preflight.sh`
- Ожидается: `ИТОГ: OK`. Строки `WARN` объяснить человеку простыми словами.
- `FAIL docker` — **стоп-точка**: установка Docker требует `sudo`. Получить согласие, ставить по официальной инструкции Docker для дистрибутива, после — повторить preflight.
- `WARN net:telegram` — **стоп-точка**: без маршрута к Telegram бот согласований работать не будет. Объяснить, что нужен прокси (`EGRESS_PROXY_URL`). Решение принимает человек.
- `WARN net:openai` важно, только если владелец берёт модель у OpenAI. Доступ к провайдеру модели из неподдерживаемого региона нарушает его условия и может стоить аккаунта: сказать об этом владельцу.
- Запись: `./ops/state.sh done preflight`

### 3. Режим и служебные значения
`./ops/init-env.sh --auto --mode standalone` — записывает режим без Hermes, генерирует пароль базы и два токена сервиса. Ничего не спрашивает и не печатает значений. Файл `.env` не читать.
- Ожидается: строка `[SHTURMAN_MODE] записан режим: standalone`.
- Сообщение «Режим уже выбран: hermes» значит, что на этом сервере уже начата установка с Hermes: **стоп**. Смена режима на работающем экземпляре — отдельная процедура (`docs/standalone.md`, «Переход между режимами»).
- Проверка: `./ops/mode.sh` показывает `Режим: standalone`; `./ops/preflight.sh` показывает `PASS env: есть, права 600`.
- Запись: `./ops/state.sh set mode standalone` и `done env`

### 4. Запуск
`./ops/up.sh` — скачивает образ базы, собирает образ сервиса переписки (первая сборка — несколько минут, нужен интернет для пакетов), запускает базу и сервис и сам вызывает `./ops/doctor.sh`. Образ Hermes не скачивается.
- Ожидается: три строки «пропущено: режим без Hermes — …», затем `PASS mode: без Hermes…`, `SKIP hermes`, `PASS service`, `PASS service-bind`, `PASS database`, `PASS archive-mcp`, `PASS archive` с нулями, `PASS jobs`, `ИТОГ: OK`.
- `WARN approvals-bot: …не настроен`, `WARN model: …не настроена`, `WARN embeddings` и `WARN guard` на этом шаге нормальны.
- «Сервис переписки не ответил за 90 секунд», `FAIL service`, `FAIL database`, `FAIL archive` — раздел «Если что-то не работает».
- `FAIL service-bind` или `FAIL archive-mcp: …ответил без токена` — **стоп**: стек остановить, не удаляя данных, и разобраться с `compose.override.yaml`.
- Проверка: `docker ps` показывает только `shturman-service` и `shturman-postgres`.
- Запись: `done stack-up`

### 5. Бот согласований и модель — стоп-точка, вводит только владелец
5а. Объяснить владельцу, что понадобится, и дождаться, пока он это подготовит:
- **новый бот** у @BotFather (команда `/newbot`); его токен владелец никому не показывает и в чат не вставляет;
- ключ провайдера модели и точное имя модели; если провайдер не OpenAI — ещё и адрес его API (для OpenRouter — `https://openrouter.ai/api/v1`).

5б. Владелец в своём терминале на сервере запускает `./ops/init-env.sh`. Скрипт спросит по очереди: токен бота согласований (ввод скрыт), ключ модели (ввод скрыт), имя модели, адрес API, ключи приложения Telegram, часовой пояс, исходящий прокси. На ненужный вопрос — Enter. Агент в это время ничего не делает и значений не спрашивает. Дождаться слова «готово».
- Если скрипт ответил «НЕ записано» — значение скопировано с лишним знаком; владелец запускает скрипт ещё раз.

5в. `./ops/up.sh` — сервис перезапускается с ботом и моделью.
- Ожидается: `PASS approvals-bot: бот согласований на связи с Telegram`, `PASS model: модель <имя> настроена, обращений ещё не было`, `WARN approvals-owner: владелец не привязан`.
- `WARN approvals-bot: …ещё не начал опрос` — повторить `./ops/doctor.sh` через минуту.
- `FAIL approvals-bot` с кодом неполадки — `docker exec shturman-service shturman bot-status` даёт расшифровку. `token_rejected`, `bad_token_format` — токен введён неверно: владелец удаляет строку `SHTURMAN_BOT_TOKEN` из `.env` и повторяет 5б. `other_poller`, `webhook`, `conflict` — этим ботом пользуется другая программа: нужен отдельный бот. `no_connection` — нет маршрута к Telegram: шаг 2.
- Ключ модели на этом шаге не проверяется: первое обращение к модели сервис делает при ночной обработке. Ошибку ключа покажет `WARN model: …последнее обращение не удалось` на следующий день.
- Запись: `done secrets`

### 6. Привязка владельца к боту — стоп-точка
Ссылка из `./ops/bot-bind.sh` — одноразовый пропуск во владельцы: кто первым откроет её в Telegram и нажмёт «Запустить», тот и получает карточки и право нажимать кнопки. Действует 15 минут, один раз.

- Предпочтительно: скрипт запускает **сам владелец** в своём терминале и открывает ссылку в Telegram.
- Допустимо по явной просьбе владельца: скрипт запускает агент, передаёт ссылку как есть и нигде её не сохраняет — ни в состоянии, ни в журнале, ни в отчёте.
- «сервис ещё не связался с Telegram от имени бота» — вернуться к 5в.
- Проверка (делает человек): бот ответил «Готово: вы привязаны как владелец».
- Проверка: `./ops/doctor.sh` показывает `PASS approvals-owner`.
- Запись: `done owner-bind`

### 7. Архив для Codex CLI или Claude Code — по желанию владельца
7а. Спросить у владельца, где работает его клиент: на этом сервере или на его компьютере, и по какому адресу он входит на сервер по SSH. `./ops/connect.sh --ssh пользователь@сервер` — показать ему вывод целиком. Скрипт токен не печатает.

7б. **Выполняет только владелец:** шаг 1 из вывода (токен в переменную окружения командой `./ops/mcp-token.sh --pipe`), для своего компьютера — ещё и туннель SSH, затем настройка клиента. Агент команду `./ops/mcp-token.sh` не запускает. Дождаться слова «готово».
- Проверка (делает человек): `claude mcp list` показывает `shturman … Connected` либо `codex mcp list` показывает строку `shturman`; на вопрос «какие чаты есть в архиве» клиент отвечает (пока архив пуст — что чатов нет).
- Если у клиента другая версия и команда не подошла — смотреть `claude mcp add --help`, `codex mcp add --help` и документацию клиента; флаги не выдумывать.
- Сказать владельцу: клиент отправляет прочитанное своему провайдеру модели; режим клиента без подтверждений действий включать не стоит (`docs/standalone.md`, «О чём помнить»).
- Запись: `done connect`; если владелец пропускает — `./ops/state.sh set connect skipped`.

### 8. Переписка — по желанию владельца
Команды и их параметры — `docs/service.md`, раздел «Как пользоваться без веб-интерфейса». Каждый пункт предлагать отдельно и делать только после согласия.

8а. Загрузка истории из экспорта Telegram Desktop: `./ops/import-export.sh scan /путь/к/result.json`, затем `import`. Вывод `scan` — названия чатов владельца: команду запускает владелец либо агент по его явной просьбе. Какие чаты исключить, решает владелец.
- Проверка: `./ops/doctor.sh` — в строке `PASS archive` число сообщений выросло.

8б. Поиск по смыслу — **стоп-точка** (скачивание около 0,5 ГБ, около 1,2 ГБ памяти): `./ops/embeddings.sh on`. Модель по умолчанию — `e5-small`. Вторую модель, `user2-small`, ставят только по решению владельца: `./ops/embeddings.sh on --model user2-small`; до этого пересказать ему, чем модели отличаются (`docs/search.md`). Смена модели на работающем экземпляре — отдельная стоп-точка: пересчёт всех векторов.
- Проверка: `PASS embeddings` с именем модели либо `WARN embeddings: …идёт подсчёт векторов` со счётчиками «готово» и «осталось» — пока архив считается, это нормально; `./ops/embeddings.sh status` показывает модель и счётчики.
- Сервер начал тормозить или появился `FAIL` — `./ops/embeddings.sh off`.

8в. Аккаунт Telegram — **стоп-точка, выполняет только человек.** Если ключи приложения Telegram на шаге 5б пропущены — владелец запускает `./ops/init-env.sh` ещё раз, затем `./ops/up.sh`. Вход: `./ops/tg-login.sh assistant` или `./ops/tg-login.sh owner`. Агент ждёт слова «готово».
- Проверка: `docker exec shturman-service shturman call GET /api/tg/accounts` показывает аккаунт со статусом без ошибки. Чаты для чтения выбирает владелец — `docs/service.md`.

8г. Бизнес-режим — **стоп-точка, подключает человек.** Бизнес-режим в этом режиме подключается к боту согласований (`docs/standalone.md`, «Бизнес-режим Telegram со своим ботом»).
- Владелец включает Business Mode у @BotFather для бота согласований. Проверка: после `./ops/doctor.sh` строки `WARN approvals-business` нет.
- Сказать владельцу до подключения: с этого момента сообщения из выбранных чатов записываются в архив на сервере, а раз в сутки ночью разбираются моделью у выбранного провайдера.
- Владелец подключает бота в настройках Telegram Business, выбрав для начала один тестовый чат. Право бота отвечать на сообщения не давать: отправка выключена.
- Проверка: собеседник из тестового чата пишет сообщение; `./ops/doctor.sh` показывает в строке `PASS archive` число сообщений больше нуля. Собеседнику при этом **ничего** не приходит.
- Если собеседник получил что-либо от имени владельца — немедленно отключить бота в настройках Telegram и остановиться.

8д. Защита от внедрённых инструкций — **стоп-точка** (скачивание около 0,3 ГБ, около 0,6 ГБ памяти): `./ops/guard.sh on`. Перед включением пересказать владельцу раздел «Что защита ловит и чего не ловит» из `docs/guard.md`. В этом режиме она прячет подозрительные сообщения от модели сервиса и от клиента владельца, который читает архив.
- Проверка: `PASS guard`; `./ops/guard.sh status` показывает счётчики и `"guard_problem": null`.
- `FAIL guard` — `docker logs --tail 50 shturman-guard`; не хватает памяти — `./ops/guard.sh off`. Выключение — только по явной просьбе владельца.
- Шаг не пройден нигде: `./ops/guard.sh` проверен только в песочнице с подставным `./ops/up.sh`.

- Запись: `done archive`; если владелец всё пропускает — `./ops/state.sh set archive skipped`.

### 9. Итог
- Проверка: все шаги отмечены в `./ops/state.sh show`; `./ops/doctor.sh` — `ИТОГ: OK`.
- `./ops/backup.sh` — первая копия. Ожидаются строки «Копия готова» и «Копия базы готова». В копии есть и файл `.env` с токеном бота и ключом модели: агент её не открывает.
- Сообщить человеку: версия «Штурмана» и режим; что работает; чего в этом режиме нет (`docs/standalone.md`, «Чего нет…»); что отправка выключена; что первое обращение к модели будет ночью (по умолчанию в 03:30 по его часам) и найденные обязательства придут в бота карточками; что из шагов 7 и 8 не сделано; где лежат данные (`data/`) и копии (`local/backups`); что копии делаются вручную.

## Если что-то не работает

| Строка `./ops/doctor.sh` | Что смотреть |
|---|---|
| `FAIL mode` | В `.env` неизвестное значение режима: `./ops/mode.sh set standalone` |
| `WARN hermes-leftover` | Остался контейнер Hermes от прежнего режима: `./ops/up.sh` его уберёт |
| `FAIL service: сервис переписки не развёрнут` | Контейнера нет: `./ops/up.sh` |
| `FAIL service` | `docker logs --tail 50 shturman-service` — причина отказа запуска названа в последних строках |
| `FAIL database` | `docker logs --tail 50 shturman-postgres`; свободное место — строка `disk` |
| `FAIL archive-mcp` | Сервис не отвечает на `/mcp` либо отвечает без токена. Второе — **стоп** |
| `FAIL archive: сервис не отдал состояние` | `docker logs --tail 50 shturman-service` |
| `FAIL approvals-bot` | `docker exec shturman-service shturman bot-status`; разбор кодов — шаг 5в |
| `WARN approvals-owner` | Шаг 6 |
| `WARN model: …последнее обращение не удалось` | Код `http_401` или `http_403` — ключ неверен или не действует; `http_404` — нет такой модели или неверный адрес API; `connect:…` — нет маршрута к провайдеру. Значения меняет владелец: удалить строку из `.env`, `./ops/init-env.sh`, `./ops/up.sh` |
| `WARN jobs` | Задания копятся: бот или модель не настроены либо не работают — строки `approvals-bot` и `model` |
| `FAIL embeddings` | `docker logs --tail 50 shturman-embeddings`; не хватает памяти — `./ops/embeddings.sh off` |
| `FAIL guard` | Модель защиты не отвечает, входящие видны модели и клиенту непроверенными: `docker logs --tail 50 shturman-guard`; `./ops/guard.sh on` запускает контейнер заново |
| `shturman call` напечатал «ЖДЁТ ПОДТВЕРЖДЕНИЯ В БОТЕ» | Это не ошибка: действие расширяет права и применится, когда владелец нажмёт «Да, сделать» в боте согласований (`docs/service.md`) |
| Сборка образа в `./ops/up.sh` завершилась ошибкой | Нет доступа в интернет к пакетам или не хватило места на диске. Повторить один раз; не помогло — стоп |
| Клиент пишет, что сервер отверг токен | В окружении клиента нет `SHTURMAN_MCP_TOKEN` или токен сменился: владелец повторяет шаг 7б |
| Клиент не соединяется с своего компьютера | Не открыт туннель SSH либо порт слева в команде туннеля не 8765 |

В журналах сервиса нет текста сообщений, токенов и ключей, но есть виды событий и коды ошибок. Журнал показывать владельцу можно, пересылать куда-либо — нет. Две неудачи подряд — остановиться и описать проблему. Данные (`data/`) при разборе не трогать и не читать.

## Откат

Остановить стек без удаления данных. Бота в настройках Telegram Business, если его подключали, отключает человек; сессии аккаунтов Telegram он завершает сам: «Настройки → Устройства». Подключение архива у клиента убирается командами из `docs/standalone.md`. Токен бота владелец может отозвать у @BotFather. Всё, что удаляет данные (`data/`, тома, `down -v`), — стоп-точка.

Переход на режим с Hermes — `docs/standalone.md`, «Переход между режимами».

## Что ещё должно появиться

Проход этого runbook на чистом сервере с настоящими ботом и моделью; проверка ключа модели сразу после ввода, а не ночью; `ops/restore.sh`, копии по расписанию.
