# Подготовка сервера агентом владельца

**Версия runbook:** 0.0.1 · **Для `VERSION`:** 0.0.7 · **Состояние: черновик, на чистом сервере не пройден.** Написан 2026-10-08 по итогам разбора: прежние runbook-и предполагали, что человек сам заходит на сервер по SSH, а Docker и Caddy уже стоят. Шаги 3–6 на сервере пилота выполнялись по отдельности в предыдущих установках; путь «пустой VPS → готовый сервер» целиком не пройден ни разу — первый проход и есть проверка. Вывод не совпал с ожидаемым — стоп.

Для кого: ИИ-агент (Claude Code, Codex), работающий **на компьютере владельца**, который сам не пользуется терминалом и SSH (стартовый промпт — `prompts/deploy-remote.md`). Результат: агент заходит на сервер по своему ключу, на сервере есть пользователь `shturman` с правом запускать Docker, установлены Docker и Caddy, включён firewall, домен указывает на сервер, репозиторий лежит в `/opt/shturman`. Дальше — `docs/runbooks/deploy.md` (или `deploy-standalone.md`), команды которого агент выполняет через SSH в `/opt/shturman`.

## Инварианты

Действуют все правила `AGENTS.md`. Дополнительно:

- **Паролей владельца ты не видишь.** Ни от хостинга, ни от сервера, ни от регистратора домена. Доступ к серверу — только по ключу, который ты создал на компьютере владельца; закрытая часть ключа остаётся на его компьютере и никуда не копируется и не выводится. Открытую часть (`.pub`) показывать можно.
- **В панелях хостинга и регистратора действует владелец.** Ты говоришь, куда нажать и что вставить; если у тебя есть браузер на его компьютере и он сам вошёл в панель — можешь сделать это в его браузере после его «да». Логин и пароль за него не вводишь.
- **Каждое действие под `root` — стоп-точка**: перед выполнением скажи, что делаешь и зачем, и дождись «да». Стек под `root` не запускается никогда (`AGENTS.md`, «Никогда»): он работает от пользователя `shturman`.
- **Чужое на сервере — стоп.** Если сервер не пустой (есть чужие сайты, контейнеры, базы, занятые порты 80, 443, 8443), не трогай ничего и опиши владельцу, что нашёл.

## Шаги

Формат шага: действие → проверка → итог владельцу одной фразой. Состояние до появления репозитория на сервере записывать некуда — веди его в своём отчёте; после шага 7 — `./ops/state.sh`.

### 1. Что знает владелец
Спроси только это:
- у какого хостинга сервер и есть ли у него вход в панель этого хостинга;
- адрес сервера (IP) — он есть в панели или в письме хостинга;
- какой адрес будет у ассистента: домен или поддомен, которым владелец управляет (например, `assistant.example.ru`), и где управляется его DNS (у регистратора, в Cloudflare, у хостинга).

Пароль от сервера, если хостинг его прислал, не нужен — так и скажи.

### 2. Ключ доступа
На компьютере владельца: `ssh-keygen -t ed25519 -f ~/.ssh/shturman_server -N "" -C shturman-agent` (если файла ещё нет). Закрытый ключ не выводить.
- Добавь запись в `~/.ssh/config` владельца: `Host shturman-server`, `HostName <IP>`, `User root`, `IdentityFile ~/.ssh/shturman_server`, `IdentitiesOnly yes`.
- Покажи владельцу **открытую** часть (`~/.ssh/shturman_server.pub`, одна строка) и проведи его: панель хостинга → раздел SSH-ключей (названия: «SSH-ключи», «Ключи доступа», «SSH keys») → добавить ключ → вставить строку → привязать к серверу. У многих хостингов ключ применяется только при переустановке сервера; если сервер пустой и владелец согласен — переустановка с этим ключом (стоп-точка: стирает сервер). Точные названия пунктов посмотри в документации его хостинга, не выдумывай.
- Если в панели нельзя добавить ключ к работающему серверу, а переустанавливать нельзя: веб-консоль сервера в панели хостинга. Владелец открывает её, входит как `root` с паролем хостинга (пароль он вводит сам, тебе не сообщает) и вставляет одну команду, которую ты ему дашь: добавить твою открытую строку в `/root/.ssh/authorized_keys` с правами 600 (каталог 700).
- Проверка: `ssh shturman-server 'id -un; lsb_release -ds'` → `root` и `Ubuntu 24.04…`. Другая система — стоп: runbook проверен только на Ubuntu 24.04.

### 3. Осмотр сервера
`ssh shturman-server` и посмотреть, без изменений: свободное место и память (`df -h /`, `free -m`), что слушает порты (`ss -ltnp`), есть ли Docker, Caddy, nginx, apache, чужие контейнеры, firewall (`ufw status`).
- Ожидается пустой сервер: занятых 80/443/8443 нет, контейнеров нет. Иначе — **стоп**, описать владельцу.
- Памяти меньше 4 ГБ — сказать владельцу: базовый набор поместится, поиск по смыслу и защита — нет.

### 4. Пользователь `shturman` — стоп-точка (`root`)
Создать пользователя без пароля для входа, со своим ключом и правом `sudo` без пароля (иначе агенту понадобился бы пароль, а пароли через агента не идут): `adduser --disabled-password --gecos "" shturman`; скопировать в его `~/.ssh/authorized_keys` ту же открытую строку (каталог 700, файл 600, владелец `shturman`); `/etc/sudoers.d/shturman` с `shturman ALL=(ALL) NOPASSWD:ALL` (права 440, проверить `visudo -cf`).
- Объяснить владельцу: этим пользователем ты дальше и работаешь; право `sudo` без пароля — то же, что `root`, поэтому ключ на его компьютере надо беречь как пароль от сервера.
- Добавь в `~/.ssh/config` владельца вторую запись: `Host shturman-app` — тот же адрес и ключ, `User shturman`.
- Проверка: `ssh shturman-app 'id -un; sudo -n true && echo sudo-ok'` → `shturman`, `sudo-ok`.

### 5. Docker и Caddy — стоп-точка (`sudo`, установка пакетов)
По официальным инструкциям, **не по памяти**: Docker Engine для Ubuntu — https://docs.docker.com/engine/install/ubuntu/ (способ через репозиторий apt), Caddy — https://caddyserver.com/docs/install (раздел для Debian/Ubuntu, официальный репозиторий). Перед выполнением показать владельцу список команд.
- `sudo usermod -aG docker shturman`; затем переподключиться.
- Проверка: `ssh shturman-app 'docker version --format {{.Server.Version}}; docker compose version; caddy version; systemctl is-active caddy'`.
- Сказать владельцу: членство в группе `docker` равно правам администратора — это обычно для такого сервера.

### 6. Firewall и домен — стоп-точки
6а. **Firewall (`sudo`).** `ufw`: разрешить SSH (порт, на котором сервер принимает SSH, — проверь до включения, иначе потеряешь доступ), 80 и 443; порт 8443 — позже, в `deploy.md`, шаг 5в. Показать владельцу правила, затем `sudo ufw enable`. Проверка: `ssh shturman-app 'sudo ufw status'` и новое подключение по SSH проходит.
- Если перед адресом будет Cloudflare в режиме прокси и владелец хочет закрыть сервер от прямых обращений — 443 и 8443 только для сетей Cloudflare (список — https://www.cloudflare.com/ips/). Это по желанию; по умолчанию — открыто всем.

6б. **Домен (делает владелец).** Сказать ровно, какую запись создать там, где управляется его DNS: тип `A`, имя — поддомен (например, `assistant`), значение — IP сервера; для Cloudflare — пока «DNS only» (серое облако), чтобы сертификат выпустился без лишних настроек. Если у сервера есть IPv6 — ещё запись `AAAA`.
- Проверка с компьютера владельца: `nslookup <адрес>` возвращает IP сервера. Пока не возвращает — подождать (обычно минуты, иногда до часа) и повторить; не идти дальше.

### 7. Репозиторий на сервере
`ssh shturman-app 'sudo install -d -o shturman -g shturman -m 755 /opt/shturman && git clone https://github.com/namre/shturman.git /opt/shturman'`.
- Каталог — именно `/opt/shturman`: образец прокси (`config/Caddyfile.example`) отдаёт страницы входа из `/opt/shturman/plugins/shturman/public`, а домашний каталог пользователя прокси прочитать не может.
- Если клонирование просит логин — репозиторий закрыт. Не вводи ничего: сказать владельцу, что для этого пути репозиторий должен быть открытым (или у сервера должен быть свой ключ доступа к нему — отдельная задача).
- Проверка: `ssh shturman-app 'cd /opt/shturman && cat VERSION && ./ops/state.sh show'` → версия и «развёртывание не начато». Записать: `./ops/state.sh done server-prepare`.

Дальше — `docs/runbooks/deploy.md` с шага 1. Каждую команду runbook выполнять как `ssh shturman-app 'cd /opt/shturman && …'`; долгие (`./ops/up.sh`, скачивание моделей) — в фоне: `nohup ./ops/up.sh > /tmp/shturman-up.log 2>&1 &`, затем проверять конец файла, пока не появится `ИТОГ:`. Шаги runbook с `sudo` (прокси, firewall) — от `shturman` через `sudo`, как стоп-точки.

## Если что-то не так

| Что | Что делать |
|---|---|
| `Permission denied (publickey)` | Ключ не добавлен к серверу или добавлен не тот: проверить строку в панели хостинга; у многих хостингов ключ применяется только при создании или переустановке сервера |
| `Connection timed out` | Неверный IP, сервер выключен или хостинг закрыл SSH своим firewall — смотреть в панели хостинга |
| После `ufw enable` SSH отвалился | Доступ — только через веб-консоль хостинга: владелец входит и выполняет `ufw allow <порт SSH>/tcp` (команду даёшь ты) |
| Сертификат не выпускается (в `deploy.md`, шаг 5б) | Запись DNS ещё не разошлась, порт 80 закрыт, или перед адресом стоит защита, перехватывающая `/.well-known/acme-challenge/` (Cloudflare Access и подобные) — нужен обход для этого пути |
