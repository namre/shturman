# Подготовка сервера агентом владельца

**Состояние:** черновик — путь «пустой VPS → готовый сервер» целиком не пройден ни разу. Вывод не совпал с ожидаемым — стоп.

Для кого: ИИ-агент (Claude Code, Codex), работающий **на компьютере владельца**, который сам не пользуется терминалом и SSH (стартовый промпт — `prompts/deploy-remote.md`). Результат: агент заходит на сервер по своему ключу, на сервере есть пользователь `shturman` с правом запускать Docker, установлены Docker и Caddy, включён firewall, владелец выбрал способ адреса — свой домен, IP-адрес сервера или посредник (`docs/address.md`) — и сервер подготовлен под него, репозиторий лежит в `/opt/shturman`. Дальше — `docs/runbooks/deploy.md` (или `deploy-standalone.md`), команды которого агент выполняет через SSH в `/opt/shturman`.

## Как говорить с владельцем

Владелец здесь делает три вещи: отвечает на вопросы о сервере, нажимает кнопки в панели хостинга (и, со своим доменом, — у регистратора) и говорит «да» на стоп-точках. Технические слова (SSH, firewall, DNS, `sudo`) переводи: «доступ к серверу», «защита сети», «запись у регистратора», «права администратора»; порт — «порт», при первом упоминании — «дверь, через которую к серверу обращаются из интернета». Слово «вход» — только про вход владельца в ассистента и в Telegram. Готовые фразы — строки «> »; адреса и числа в них — примеры.

## Инварианты

Действуют все правила `AGENTS.md`. Дополнительно:

- **Паролей владельца ты не видишь** — ни от хостинга, ни от сервера, ни от регистратора. Доступ к серверу — только по ключу, который ты создал на компьютере владельца; закрытая часть остаётся там, никуда не копируется и не выводится. Открытую (`.pub`) показывать можно.
- **В панелях хостинга и регистратора действует владелец.** Ты говоришь, куда нажать и что вставить; с браузером на его компьютере, куда он сам вошёл, — можешь сделать это сам после его «да». Логин и пароль за него не вводишь.
- **Каждое действие под `root` — стоп-точка**: скажи, что делаешь и зачем, дождись «да». Стек под `root` не запускается никогда — он работает от пользователя `shturman`; агента в режиме без подтверждений под `root` не запускают (`AGENTS.md`, «Как работать»).
- **Чужое на сервере — стоп.** Чужие сайты, контейнеры, базы, занятые порты 80, 443, 8443 — ничего не трогай, опиши владельцу.
- **Способ адреса выбирает владелец** (шаг 5): ты проверяешь и рекомендуешь, спрашиваешь явно и ждёшь ответа; когда-то упомянутый домен — не выбор. Посредник — по `docs/relay.md`, «Правила для агента». Выбор записывается `./ops/state.sh set address domain|ip|relay`.

## Шаги

Формат шага: действие → проверка → итог владельцу одной фразой. До репозитория на сервере состояние веди в своём отчёте; после шага 8 — `./ops/state.sh`.

В примерах `203.0.113.10` — адрес сервера, который назвал владелец.

### 1. Что знает владелец

Был шаг 0 (`docs/runbooks/hosting.md`) — хостинг, адрес, вход и размер уже известны; спроси только то, чего нет. Иначе — одним сообщением:

> Чтобы зайти на сервер, мне нужно три вещи из панели хостинга или из его письма: у какого хостинга сервер, его адрес (цифры вида 203.0.113.10) и под каким именем пользователя и на каком порту хостинг даёт доступ к серверу. Пароль от сервера мне не нужен.

- Имя пользователя обычно `root`, порт 22; некоторые хостинги дают своего пользователя (`ubuntu`) и закрывают вход под `root`. Не знает — бери `root` и 22, шаг 2 покажет.
- Сервер ещё не куплен и шага 0 не было — сначала `docs/runbooks/hosting.md`. Нужны ли дополнения (расшифровка голосовых, поиск по смыслу) — спроси, только если от этого зависит размер сервера: 8 ГБ и 4 ядра — помещается всё, 4 ГБ — тяжёлые дополнения по одному, голосовые — только x86-64 (`docs/voice.md`, «Какой сервер нужен»).
- **Город для часового пояса здесь не спрашивай**: его спрашивают один раз, на шаге 3а runbook развёртывания (если стартовый промпт или шаг 0 его ещё не дали). Владелец назвал сам — запомни.
- Способ адреса здесь не спрашивай — это шаг 5, после проверок. Сам сказал, что есть домен, — запомни.
- Итог владельцу: что дальше — ключ доступа.

Дальше «вход хостинга» — пользователь и порт, которые назвал владелец.

### 2. Ключ доступа

На компьютере владельца: `ssh-keygen -t ed25519 -f ~/.ssh/shturman_server -N "" -C shturman-agent` (если файла нет). Закрытый ключ не выводить.
- Запись в `~/.ssh/config` владельца: `Host shturman-server`, `HostName <IP>`, `Port <порт>`, `User <пользователь входа хостинга>`, `IdentityFile ~/.ssh/shturman_server`, `IdentitiesOnly yes`.
- Показать **открытую** строку (`~/.ssh/shturman_server.pub`) и провести владельца: панель хостинга → раздел ключей («SSH-ключи», «Ключи доступа», «SSH keys» — точные названия по документации его хостинга) → добавить → вставить строку → привязать к серверу.

> Вот строка-ключ, по которой сервер будет меня узнавать: она не секретная. Вставьте её в панели хостинга, в разделе ключей, и привяжите к серверу — я подскажу, куда нажать.

- Ключ применяется только при переустановке, а сервер пустой — переустановка с ключом (**стоп-точка**: стирает сервер):

> Хостинг добавляет ключ только при переустановке сервера. Сервер пустой, поэтому ничего не потеряется, но всё на нём будет стёрто. Переустанавливаем?

- Добавить к работающему нельзя, переустанавливать нельзя — веб-консоль сервера в панели: владелец входит пользователем хостинга с его паролем (пароль он вводит сам) и вставляет одну команду от тебя — открытая строка в `~/.ssh/authorized_keys` этого пользователя (файл 600, каталог 700).
- Есть другой человек со входом (администратор, другой агент) — ключ добавляет он; передай только открытую строку.
- Проверка: `ssh shturman-server 'id -un; lsb_release -ds; sudo -n true && echo sudo-ok'` → имя пользователя, `Ubuntu 24.04…` и, если не `root`, `sudo-ok`. Другая система — стоп: проверено только на Ubuntu 24.04.
- Пользователь не `root`, а `sudo-ok` нет (`sudo` просит пароль) — пароль через тебя не идёт: шаг 4 — **стоп-точка**, его команды выполняет в веб-консоли хостинга владелец или его технический специалист; ты даёшь их одним блоком и проверяешь входом `ssh shturman-app`.

> Для следующего шага нужны права администратора, а хостинг защищает их паролем, который мне знать нельзя. Один раз нужно вставить несколько строк в окно управления сервером в панели хостинга — вы сами или ваш технический специалист. Готовы?

- `Permission denied` при правильном ключе под `root` — вход под `root` может быть закрыт: спросить, нет ли другого пользователя; настройки SSH сам не меняй.
- Итог владельцу: «я захожу на сервер по своему ключу; пароль не понадобился».

Дальше «под `root`» — под `root` или от пользователя входа через `sudo`.

### 3. Осмотр сервера

`ssh shturman-server` и посмотреть, ничего не меняя: `df -h /`, `free -m`, `ss -ltnp`, есть ли Docker, Caddy, nginx, apache, контейнеры, `ufw status`.
- Проверка: сервер пустой — 80/443/8443 не заняты, контейнеров нет. Иначе — **стоп**, описать владельцу:

> На сервере уже работают программы, которые ставил не я, — сейчас назову, какие нашёл. Я ничего из этого не трогаю. Если это ваше и нужно — ассистента лучше поставить на отдельный сервер; если сервер должен был быть пустым — спросите хостинг или того, кто им пользовался. Как поступим?
- Docker или Caddy уже стоят, контейнеров нет, `/etc/caddy/Caddyfile` пустой или стоковый (только `:80` и `root * /usr/share/caddy`) — не чужое: сказать и на шаге 6 только проверить. Сайты в Caddyfile, работающие контейнеры, чужие базы — стоп.
- Пользователь `shturman` уже есть — стоп: спросить, откуда; не пересоздавать.
- Память (`free -m`, `Mem`, `total`): меньше 4 ГБ по тарифу — **стоп**, предложить сервер побольше (сервер на 4 ГБ показывает чуть меньше 4096 — это не «меньше»); около 4 ГБ — из тяжёлых дополнений одно (голосовые **или** поиск с защитой); 8 ГБ — всё.
- `uname -m` не `x86_64` — расшифровка голосовых здесь не включится.
- Диск свободен меньше 15 ГБ — **стоп**; меньше 40 ГБ — места мало для большого архива; голосовым — ещё около 4 ГБ.
- Доступ к адресам (`docs/deployment.md`, «Что откуда скачивается»):
  `ssh shturman-server 'for u in https://github.com https://registry-1.docker.io/v2/ https://deb.debian.org/debian/ https://pypi.org/simple/ https://download.docker.com https://api.telegram.org https://huggingface.co https://ghcr.io/v2/ https://download.pytorch.org/whl/cpu/; do printf "%s %s\n" "$(curl -sS -o /dev/null -m 12 -w "%{http_code}" "$u" 2>/dev/null || true)" "$u"; done'`
  Любой код, кроме `000`, — достижим. `000` у первых пяти — **стоп** (не поставить Docker и не собрать стек): другой хостинг или страна. `000` у Telegram — понадобится исходящий прокси (`EGRESS_PROXY_URL`). `000` у Hugging Face, `ghcr.io`, PyTorch — не включатся дополнения.
- Запомни для шага 5: состояние `ufw` и занят ли порт 80 стоковым Caddy.
- Итог владельцу: сервер подходит (или чем не подходит), что из дополнений на нём не поместится.

### 4. Пользователь `shturman` — стоп-точка (`root`)

> Заведу на сервере отдельного пользователя, от которого будет работать ассистент, и дам ему права администратора без пароля — иначе мне понадобился бы ваш пароль. Это значит: ключ на вашем компьютере — полный доступ к серверу с вашей перепиской. Не давайте компьютер посторонним и не пересылайте файлы из папки с ключами. Делаю?

После «да» (через `sudo`, если вход хостинга не `root`): `adduser --disabled-password --gecos "" shturman`; в его `~/.ssh/authorized_keys` — та же открытая строка (каталог 700, файл 600, владелец `shturman`); `/etc/sudoers.d/shturman` с `shturman ALL=(ALL) NOPASSWD:ALL` (права 440, `visudo -cf`).
- Вторая запись в `~/.ssh/config`: `Host shturman-app` — тот же адрес, порт и ключ, `User shturman`. Дальше — только через `shturman-app`; вход хостинга — для восстановления.
- Проверка: `ssh shturman-app 'id -un; sudo -n true && echo sudo-ok'` → `shturman`, `sudo-ok`.
- Итог владельцу: «пользователь для ассистента заведён».

### 5. Адрес ассистента — выбирает владелец

Только для режима с Hermes. **Режим без Hermes:** наружу ничего не публикуется, страница «Настройки Штурмана» и архив открываются с компьютера владельца через туннель (`docs/standalone.md`) — шаг пропустить, ничего не записывать; на шаге 6 Caddy не ставить, на шаге 7 открыть только SSH, 7б–7г пропустить. Владельцу: «домен вам не нужен».

Способов три: **свой домен**, **по IP-адресу сервера**, **через посредника** `sh.namre.app` (`docs/address.md`). Порядок: проверки 5а–5г, рекомендация 5д, вопрос 5е.

5а. **Внешний ли адрес сервера** (тот, по которому ты заходишь, — `HostName`).
- В клоне на компьютере владельца: `bash -c '. ops/lib.sh && ip_kind 203.0.113.10'` → `public` или `private`. Пусто — это имя, не IPv4: `nslookup <имя>` и повторить. Нет bash — сверь сам: закрытые — `10.…`, `172.16.…`–`172.31.…`, `192.168.…`, `100.64.…`–`100.127.…`, `127.…`, `169.254.…`, `0.…` и от `224.…`.
- `ssh shturman-app 'ip -4 -brief addr'` — есть ли адрес сервера среди строк вида `eth0  UP  203.0.113.10/24`.
- Итог: `public` и адрес в выводе — белый адрес; `public`, а в выводе только закрытые — NAT (у облаков обычно все порты, тогда 5б пройдёт; у роутера и общего NAT хостинга — обычно только SSH); `private` — ты заходишь по внутреннему адресу: есть внешний в панели — подставить в `HostName` и повторить 5а; нет — входящих из интернета нет, сразу 5в.

5б. **Доходят ли 80, 443 и 8443 из интернета — стоп-точка (`sudo`).**

> Проверю, доходят ли до сервера обращения из интернета: на полторы минуты сервер откроет три порта — двери, через которые к нему обращаются из интернета, — и будет отвечать пустой страницей, потом закроет их сам. Ничего не ставится и не меняется. Проверяю?

1. `ssh shturman-app 'd=$(mktemp -d); for p in 80 443 8443; do sudo -n timeout 90 python3 -m http.server "$p" --bind 0.0.0.0 --directory "$d" </dev/null >/dev/null 2>&1 & done; sleep 2; sudo ss -ltn "( sport = :80 or sport = :443 or sport = :8443 )"'` → `LISTEN … 0.0.0.0:80`, `:443`, `:8443`. Порт 80 занят стоковым Caddy — убрать `80` из списка (ответит Caddy). На самом сервере — без `ssh shturman-app '…'`; `sudo` просит пароль — сначала `sudo -v` (пароль вводит человек).
2. Пока приёмник работает — с компьютера владельца (PowerShell — `curl.exe`): `curl -sS -m 10 -o /dev/null -w '%{http_code}\n' http://203.0.113.10/`, затем `:443` и `:8443`.
   - `200` (у стокового Caddy на 80 — любой трёхзначный) — доходит.
   - `000` и `curl: (28)` — пакеты отбрасывает защита сети в панели хостинга, `ufw` сервера или NAT без проброса.
   - `000` и `curl: (7)` — отказал firewall самого сервера (`ufw`, `iptables` образа) или прошло больше 90 секунд — повторить 1 и 2.
   - Компьютер владельца в той же сети, что сервер, — проверяет владелец с телефона через мобильный интернет: `http://203.0.113.10/` — страница «Directory listing for /» значит «доходит».
3. Таймаут или отказ: `ufw` включён без 80/443 — с согласия открыть 80, 443, 8443 командами 7а (стоп-точка) и повторить 1–2; правила входящих в панели — открывает владелец, повторить; открыть нельзя, а 5а показал NAT или закрытый адрес — входящих нет.
4. Через 90 секунд `ssh shturman-app 'sudo ss -ltn "( sport = :80 or sport = :443 or sport = :8443 )"'` — строк приёмника нет.

5в. **Достижим ли посредник** — если входящие не доходят или владелец сам спросил: `ssh shturman-app 'curl -sS -m 10 https://relay.sh.namre.app/api/health; echo; timeout 5 bash -c "exec 3<>/dev/tcp/relay.sh.namre.app/7000" && echo port-7000-ok'` → `{"ok": true, "version": "0.3.0"}` (или новее) и `port-7000-ok`. `0.2.0` — работает, но имя заранее не проверить (не стоп). Нет ответа или `port-7000-ok` — посредник не подходит (`docs/relay.md`, риск 7).

5г. **Домен.**

> Есть ли у вас домен или поддомен, в котором вы сами можете добавить запись, — например, assistant.ваша-компания.ru? И где он настраивается: у регистратора, в Cloudflare, у хостинга?

Записи в домене добавляет кто-то другой — считай, что домена нет, пока владелец не договорится.

5д. **Рекомендация** по 5а–5г:

| Что показали проверки | Рекомендуй | Запасной вариант |
|---|---|---|
| Домен с доступом к записям; 80, 443, 8443 доходят или открываются | **Свой домен**: постоянный адрес, посторонних нет, можно поставить Cloudflare | По IP |
| Домена нет; адрес внешний, порты доходят или открываются | **По IP**: без посторонних и без записей | Через посредника |
| Входящие не доходят и не открываются; посредник достижим | **Через посредника**, если владелец доверяет держателю | Домен или IP — когда администратор сети пробросит 80, 443, 8443 |
| Входящие не доходят, посредник недостижим | **Стоп**: открыть входящие (хостинг, роутер), другой сервер или вариант «Только архив и согласования» | — |

«По IP» требует внешний адрес у сервера или NAT со всеми портами: Let's Encrypt проверяет адрес через 80 или 443.

5е. **Вопрос владельцу.** Один явный вопрос, три варианта по строке — что получает, что от него, чем рискует; рекомендованный отмечен с причиной. Невозможный по проверкам — назвать и сказать почему, не предлагать. Образец:

> Как вы будете открывать ассистента в браузере? Выберите один из трёх:
> 1. **Свой домен** — адрес вида `https://assistant.ваш-домен.ru`. От вас — добавить одну запись у регистратора, я подскажу куда. Постоянный адрес, никого постороннего.
> 2. **По IP-адресу сервера** — адрес вида `https://203.0.113.10`. От вас — ничего. Адрес из цифр; сменится, если сервер переедет; порт 80 нельзя будет закрыть никогда — через него раз в несколько дней продлевается сертификат защищённого соединения.
> 3. **Через посредника `sh.namre.app`** — адрес вида `https://ivan.sh.namre.app`. От вас — код приглашения от держателя посредника. Открывать порты на сервере не нужно, но держатель посредника — а при старании и другой владелец на нём — технически может перехватить ваш адрес и всё, что вы вводите на его страницах.
>
> Рекомендую **2**: домена у вас нет, а обращения из интернета до сервера доходят. Способ можно сменить позже.

Дождись ответа; следующий шаг — только после него.

Выбран посредник — **до окончательного «да»** риски из `docs/relay.md` (для агента: риск 1 — держатель посредника и зоны может направить имя на свой сервер и получить на него сертификат; риски 8 и 9 — пока `sh.namre.app` нет в Public Suffix List, все экземпляры для браузера — один сайт; посредник видит, какие имена открывают, когда и откуда, но не содержимое):

> Через посредника есть риск, который полностью не убирается. Его держатель технически может направить ваш адрес на свой сервер и показать поддельную страницу настроек — а на ней вы входите в Telegram; так же он может подменить приложение «Штурман» в боте и минут десять нажимать кнопки согласований за вас. Пока посредник не признан браузерами отдельной зоной, то же может сделать и другой владелец на этом посреднике, если узнает служебный номер вашего подключения. Поэтому подключайтесь, только если доверяете держателю посредника и тем, кому он раздаёт коды. Посредник видит, когда и откуда открывают ваш адрес, но не то, что на страницах; если он недоступен, страницы не откроются, а бот в Telegram будет работать. Подключаемся?

Ту же фразу — перед `./ops/relay.sh join` (`deploy.md`, шаг 5а) и перед `./ops/relay.sh on`.

Код приглашения — у держателя посредника, одноразовый; понадобится в `deploy.md`, шаг 5а; не записывать ни в отчёт, ни в состояние.

5ж. **Запись.** В отчёт: `адрес: domain <имя>`, `адрес: ip 203.0.113.10` или `адрес: relay`; на шаге 8 — в `./ops/state.sh`.
- Итог владельцу: какой способ выбран и что дальше (запись у регистратора, открыть входы, код приглашения).

### 6. Docker и Caddy — стоп-точка (`sudo`, пакеты)

По официальным инструкциям, **не по памяти**: Docker Engine для Ubuntu — https://docs.docker.com/engine/install/ubuntu/ (репозиторий apt), Caddy — https://caddyserver.com/docs/install (Debian/Ubuntu, официальный репозиторий). Режим без Hermes — только Docker. Список команд показать владельцу.

> Поставлю на сервер две служебные программы из их официальных источников: одна запускает части ассистента, другая принимает обращения из браузера и получает сертификат для защищённого соединения. Нужны права администратора. Пользователь ассистента получит право управлять первой из них, а это равно правам администратора сервера; для такого сервера это обычно. Ставлю?

- `sudo usermod -aG docker shturman`; переподключиться.
- Проверка: `ssh shturman-app 'docker version --format {{.Server.Version}}; docker compose version; caddy version; systemctl is-active caddy; id -nG caddy'`; в последней строке есть группа `caddy` (через неё Caddy получит доступ к сокету сервиса, `deploy.md`, шаг 5б; `shturman` в группу `caddy` не добавляется).
- Адрес по IP: `caddy version` 2.11 или новее (сертификат на IP проверен с 2.11.7); ниже — стоп, обновить из того же официального репозитория (стоп-точка); версия из репозитория Ubuntu не годится. Через посредника — проверено с 2.11.7, ниже обновить (стоп-точка).
- Итог владельцу: программы поставлены. Группа `docker` равна правам администратора — для такого сервера это обычно, сказать одной фразой.

### 7. Firewall и адрес — стоп-точки

7а. **Firewall (`sudo`).** `ufw`: разрешить порт SSH (тот, что в `~/.ssh/config`; сверить с `sudo ss -ltnp | grep sshd` **до** включения, иначе потеряешь доступ); для домена и IP — ещё 80 и 443; 8443 — позже (`deploy.md`, шаг 5в). Через посредника и без Hermes — только SSH; открытые на шаге 5б 80/443/8443 закрыть (`sudo ufw delete allow 80/tcp` и так же 443, 8443 — стоп-точка). Показать правила, затем `sudo ufw enable`.

Свой домен или адрес по IP:

> Включу на сервере защиту сети: снаружи останутся открыты только порт моего доступа к серверу и два порта для браузера, 80 и 443. Остальное закроется. С адресом по IP порт 80 нельзя будет закрыть и потом — через него продлевается сертификат. Включаю?

Через посредника или без Hermes:

> Включу на сервере защиту сети: снаружи останется открыт только порт моего доступа к серверу; порты, открытые для проверки, закроются. Включаю?

- Проверка: `ssh shturman-app 'sudo ufw status'` и новое подключение проходит.
- Адрес по IP: **порт 80 не закрывать и потом** — через него Let's Encrypt проверяет адрес при каждом продлении, а продление — раз в несколько дней. Своя защита сети в панели хостинга — те же порты открывает там владелец (ты говоришь куда).
- Cloudflare в режиме прокси и владелец хочет закрыть сервер от прямых обращений — 443 и 8443 только для сетей Cloudflare (https://www.cloudflare.com/ips/), по желанию; к адресу по IP не относится.
- Через посредника: исходящие на порт 7000 `ufw` не закрывает; правила исходящих у хостинга — 7000 разрешить.
- Итог владельцу: защита сети включена.

7б. **Свой домен (делает владелец).** Запись: тип `A`, имя — поддомен (например, `assistant`), значение — IP сервера; в Cloudflare — пока «DNS only» (серое облако). Есть IPv6 — ещё `AAAA`.

> Добавьте у регистратора одну запись: тип A, имя assistant, значение 203.0.113.10. Если пользуетесь Cloudflare — оставьте облачко серым. Обычно запись начинает работать за минуты, иногда за час.

- Проверка: `nslookup <адрес>` с компьютера владельца возвращает IP сервера; пока нет — ждать и повторять, дальше не идти.
- Итог владельцу: «адрес заработал».

7в. **Адрес по IP.** Записи не нужно. Адрес ассистента — `https://<IP>`, страницы — `https://<IP>:8443` (`<IP>` — внешний, проверенный в 5а; закрытый `./ops/set-public-url.sh` не примет).
- Сервер за NAT (5а) — не стоп: на это в варианте прокси без домена есть `default_sni` (`config/Caddyfile.example`; `deploy.md`, шаг 5б). Записать в отчёт.
- Есть IPv6 — по нему ассистент открываться не будет, это нормально.

> Адрес сервера будет виден в открытых журналах выдачи сертификатов — так же, как было бы видно имя домена.

7г. **Через посредника.** Записей не нужно: имена `ИМЯ.sh.namre.app` и `setup-ИМЯ.sh.namre.app` — по коду приглашения в `deploy.md`, шаг 5а. Доступ проверен в 5в.

### 8. Репозиторий на сервере

`ssh shturman-app 'sudo install -d -o shturman -g shturman -m 755 /opt/shturman && git clone https://github.com/namre/shturman.git /opt/shturman'`. Каталог — именно `/opt/shturman`: прокси отдаёт страницы входа из `/opt/shturman/plugins/shturman/public`, домашний каталог он прочитать не может. Клонирование просит логин — репозиторий закрыт: ничего не вводить, сказать владельцу.
- Проверка: `ssh shturman-app 'cd /opt/shturman && cat VERSION && ./ops/state.sh show && ./ops/preflight.sh'` → версия, «развёртывание не начато», в `preflight` нет `FAIL` (кроме `FAIL docker`, пока группа не применилась — переподключиться). `WARN memory`, `WARN cpu`, `WARN net:…` — пересказать, что из дополнений не включится; не стоп.
- Запись: выбор адреса — `ssh shturman-app 'cd /opt/shturman && ./ops/state.sh set address ip'` (`domain`, `ip`, `relay`; без Hermes — не записывать), затем `./ops/state.sh done server-prepare`. Был шаг 0 — `./ops/state.sh set hosting "<провайдер>/<страна>"`, `./ops/state.sh set backup-place snapshot` (копии у провайдера включены; `none` — нет), `./ops/state.sh done hosting`. Проверка: `./ops/state.sh get address`.
- Итог владельцу: «сервер готов, дальше ставлю самого ассистента».

Дальше — `docs/runbooks/deploy.md` с шага 1: команды — `ssh shturman-app 'cd /opt/shturman && …'`; долгие — в фоне (`nohup ./ops/up.sh > /tmp/shturman-up.log 2>&1 &`, ждать `ИТОГ:`); шаги с `sudo` — от `shturman`, как стоп-точки.

## Если что-то не так

| Что | Что делать |
|---|---|
| `Permission denied (publickey)` | Ключ не добавлен или не тот: строка в панели; у многих хостингов ключ применяется только при создании или переустановке. Или вход под этим пользователем закрыт (часто `root`): спросить, каким пользователем хостинг даёт вход |
| `Connection refused` | SSH на другом порту: спросить порт из панели или письма |
| `Connection timed out` | Неверный IP, сервер выключен или хостинг закрыл SSH своей защитой — смотреть в панели |
| Шаг 5б: в выводе `ss` нет строки приёмника | Порт занят (шаг 3) или `sudo -n` просит пароль (шаг 4 не завершён) |
| После `ufw enable` SSH отвалился | Только через веб-консоль хостинга: владелец входит и выполняет `ufw allow <порт SSH>/tcp` (команду даёшь ты) |
| Сертификат не выпускается (`deploy.md`, шаг 5б) | Запись у регистратора ещё не разошлась, порт 80 закрыт, или защита перед адресом перехватывает `/.well-known/acme-challenge/` (Cloudflare Access и подобные) — нужен обход для этого пути |
