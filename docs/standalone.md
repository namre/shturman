# Режим без Hermes: только архив и согласования

Актуализация 0.0.7 (2026-10-08): новые задачи ответа и решения владельца описаны в `docs/service.md`; проверка — `docs/runbooks/validate-pilot.md`. Стендовые результаты 0.0.6 ниже сохранены как исторические, без заявления о новом живом пилоте.

Состояние на 2026-10-07, версия 0.0.6. Режим собирается и запускается: стек поднимался под Docker на стенде разработки (версии 0.0.5 и 0.0.6), архив отвечал настоящему Claude Code (версия 0.0.5), страница «Переписка» открывалась в браузере по локальному адресу (версия 0.0.6). **С настоящим аккаунтом и ботом Telegram, настоящей моделью и на сервере владельца режим не проверялся.** Что именно проверено — в конце документа.

## Что это

У «Штурмана» два варианта установки: **«Ассистент в Telegram (Hermes)»** и **«Только архив и согласования»**. Выбирает владелец: агент-оператор до первого шага установки спрашивает его, какой из двух он ставит, и сам не выбирает (решение Р-53). Выбор записывается в `.env` строкой `SHTURMAN_MODE`. Третьего варианта — ассистента в Telegram на Codex CLI или Claude Code вместо Hermes — нет и не будет: почему, сказано в том же решении.

| | «Ассистент в Telegram (Hermes)» — `hermes` | «Только архив и согласования» — `standalone` |
|---|---|---|
| Что работает на сервере | Hermes Agent, сервис переписки, база | Только сервис переписки и база |
| Кто говорит с владельцем | Полный ассистент Hermes и отдельный бот решений сервиса | Бот сервиса: меню, команды и решения по задачам; полного разговорного агента нет |
| Кто обращается к модели | Hermes | Сам сервис, по ключу владельца, — когда ключ задан |
| Вопросы по архиву | Ассистенту в Telegram | Из своего Codex CLI или Claude Code: архив подключается как сервер MCP |
| Где настраивается переписка | На странице «Переписка» — по кнопке из мастера, на отдельном адресе | На той же странице «Переписка» — через туннель SSH: внешнего адреса у экземпляра нет |
| Где вводятся прочие токены и ключи | В мастере | На странице «Переписка», в разделе «Дополнительно», либо в терминале сервера скрытым вводом |

Режим без Hermes — для владельца, которому нужен архив переписки с поиском и список обязательств, а разговаривать с ассистентом он собирается из своих инструментов.

## Что есть

- **Страница «Переписка»** — та же, что в режиме с Hermes (`docs/setup.md`): ключи приложения Telegram, вход в аккаунт по QR-коду, выбор чатов, выгрузка из Telegram Desktop. Внешнего адреса у неё нет: она открывается с самого сервера или через туннель SSH, вход — по одноразовой ссылке из `./ops/setup-link.sh`.
- **Архив переписки**: чтение выбранных чатов аккаунта через сессию, импорт экспорта Telegram Desktop — всё, что описано в `docs/service.md`.
- **Поиск** по словам, а при включённых эмбеддингах — и по смыслу.
- **Архив для Codex CLI и Claude Code**: девять инструментов, все только читают.

С ключом модели и ботом согласований — их владелец заводит, когда захочет, на той же странице, в разделе «Дополнительно», — добавляются:

- **Ночная обработка**: сервис сам просит модель разобрать новые сообщения, находит обязательства и собирает страницы памяти о людях. Нужен ключ модели.
- **Бот согласований**: отдельный бот, которым владеет сервис. Присылает владельцу найденные обязательства, предложения новых страниц и срабатывания наблюдателя групп — карточками с кнопками. Нажатие приходит сервису от Telegram напрямую. Без него карточки доставлять некому.
- **Подтверждения владельца**: при боте согласований изменения, которые расширяют то, что сервис читает и делает, и приходят через внутренний API, — включить чаты аккаунта, вернуть исключённый чат, запустить импорт, добавить доверенного, завести правило наблюдателя — применяются только после нажатия в боте. Команда `shturman call` в ответ печатает «ЖДЁТ ПОДТВЕРЖДЕНИЯ В БОТЕ» (`docs/service.md`, «Что подтверждает владелец в боте согласований»). То, что владелец делает сам на странице «Переписка», применяется сразу.
- **Защита от внедрённых инструкций**, по желанию: `./ops/guard.sh on` (`docs/guard.md`).

## Чего нет по сравнению с режимом с Hermes

| Чего нет | Почему |
|---|---|
| Свободного разговора с полным ассистентом в Telegram | Бот сервиса принимает меню, команды и решения, но не заменяет разговор, инструменты и память Hermes |
| Утренней сводки и обзора недели | Это скиллы Hermes и его расписание |
| Памяти разговора | Её ведёт Hermes. Память о переписке — архив, обязательства, страницы о людях — остаётся |
| Веб-мастера и дашборда | Это вкладка дашборда Hermes. У экземпляра нет внешнего адреса; `./ops/activation-link.sh`, `./ops/set-public-url.sh`, `./ops/emergency-access.sh` в этом режиме отвечают, что неприменимы, а `./ops/set-setup-url.sh` адрес не записывает. Страница «Переписка» есть, но только через туннель SSH |
| Имени и характера ассистента | Это настройка Hermes |
| Изменений из Codex CLI и Claude Code | Архив для них только читается: закрыть обязательство, поправить человека, создать черновик оттуда нельзя |
| Полного агента, готовящего любые ответы по поручению владельца | Сервис поддерживает ограниченные задачи автоответа и их согласования при своём боте и модели; произвольный составитель ответов уровня полного Hermes не добавлен. Репетиция — `prepare_only` |
| Проверенной живой совместимости облачных клиентов | Необязательный OAuth-вход реализован, но конкретный облачный клиент проходит отдельный пилот (`docs/remote-mcp.md`) |

Выбор чатов и исключение чата аккаунта — на странице «Переписка». Повседневные решения по задачам, источникам, доверенным, отправке и группам — в меню и командах бота сервиса. Терминал остаётся запасным операторским путём: `docs/service.md`, «Как пользоваться без веб-интерфейса».

## Как устроено

| Контейнер | Что это | Сеть |
|---|---|---|
| `shturman-service` | Сервис переписки: архив, сессии Telegram, страница «Переписка», сервер MCP; по желанию — бот согласований и обращения к модели | `backend` и `egress`; порт 8765 только на `127.0.0.1` |
| `shturman-postgres` | База архива | Только `backend`, порт не публикуется |
| `shturman-embeddings` | Поиск по смыслу, по желанию | Только `backend` |
| `shturman-guard` | Модель защиты от внедрённых инструкций, по желанию | Только `backend` |

Контейнер Hermes не создаётся, его образ (около 4 ГБ) не скачивается. Сети и правило «сервис и база слушают только локальный адрес сервера» те же, что в режиме с Hermes. Наружу экземпляр не публикует ничего: обратного прокси нет, внешний адрес странице «Переписка» не задаётся (`SHTURMAN_SETUP_URL` в этом режиме пуст; `./ops/doctor.sh` предупредит, если он остался от режима с Hermes).

Наружу сервис ходит сам: к Telegram (сессии аккаунтов, бот) и, если задан ключ, к провайдеру модели. При ночной обработке фрагменты переписки уходят этому провайдеру — как и в режиме с Hermes.

## Страница «Переписка» через туннель SSH

```
./ops/setup-link.sh
```

Скрипт печатает одноразовую ссылку вида `http://127.0.0.1:8765/shturman-setup/#…` и подсказку про туннель. Ссылка действует 30 минут и срабатывает один раз. Со своего компьютера владелец сначала открывает туннель и оставляет его работать:

```
ssh -N -L 8765:127.0.0.1:8765 пользователь@сервер
```

а затем открывает ссылку в своём браузере. Порт слева обязан быть `8765`: сервис сверяет имя, под которым к нему обратились, с `127.0.0.1:8765` и `localhost:8765`. Это тот же туннель, что нужен клиенту архива (раздел «Подключить Codex CLI или Claude Code»).

- Лучше всего скрипт запускает сам владелец: тогда ссылку не видит никто, кроме него.
- Агент запускает его только по явной просьбе владельца, передаёт ссылку как есть и нигде не сохраняет; на страницу агент не заходит (`AGENTS.md`).
- По туннелю страница открывается по `http`: соединение до сервера шифрует сам SSH.

Дальше — три шага на странице, как в `docs/setup.md`: ключи приложения Telegram, вход в аккаунт по QR-коду, выбор чатов. В этом режиме Hermes нет, и отдельный адрес страницы не нужен: скрипту на адресе дашборда взяться неоткуда.

Требования к серверу не перемерялись: `./ops/preflight.sh` проверяет те же 4 ГБ памяти, хотя без Hermes нужно меньше.

## Где проходят секреты

| Секрет | Кто вводит | Куда попадает |
|---|---|---|
| Ссылка входа на страницу «Переписка» | Создаёт `./ops/setup-link.sh`; лучше, если его запускает сам владелец | В базе — только хеш; 30 минут, один раз |
| Ключи приложения Telegram (`api_id`, `api_hash`) | **Владелец** на странице «Переписка»; запасной путь — `./ops/init-env.sh` | Файл `data/shturman/setup/secrets.json` (права 600) либо `.env`; только у сервиса |
| QR-код входа в аккаунт, облачный пароль Telegram | **Владелец** на странице «Переписка» | QR нигде не сохраняется; пароль уходит в Telegram и не сохраняется |
| Токен бота согласований (`SHTURMAN_BOT_TOKEN`) — по желанию | **Владелец**: на странице «Переписка», раздел «Дополнительно», либо в своём терминале — `./ops/init-env.sh` | Тот же файл либо `.env` → только сервису |
| Ключ модели (`SHTURMAN_LLM_API_KEY`) — по желанию | **Владелец**, там же | То же |
| Имя модели и адрес API (`SHTURMAN_LLM_MODEL`, `SHTURMAN_LLM_BASE_URL`) | Владелец, там же; значения не секретные. Адрес, введённый на странице, — только https и не внутренний. Локальная модель (например, Ollama) — только строкой `SHTURMAN_LLM_BASE_URL` в `.env`: такой адрес не фильтруется и со страницы не меняется | То же |
| Пароль базы, токен внутреннего API, токен архива | Генерирует `./ops/init-env.sh --auto`, значения не печатаются | `.env` |
| Ссылка привязки владельца к боту | Создаёт страница «Переписка» либо `./ops/bot-bind.sh` | В базе — только хеш; действует 15 минут, один раз |
| Токен архива для Codex CLI или Claude Code | **Владелец** забирает командой `./ops/mcp-token.sh` | Переменная окружения на машине, где работает клиент |

Запасной путь в терминале: `./ops/init-env.sh` без `--auto` спрашивает значения по очереди. Секреты вводятся скрыто: набранное не показывается на экране и не попадает ни в историю команд, ни в журналы. На лишний вопрос — Enter. Значение с пробелом, кавычкой или знаками `$ # \` скрипт не запишет и скажет об этом; токен бота проверяется на вид `123456789:буквы-и-цифры`. Уже заданное значение скрипт не переспрашивает: чтобы его сменить, строку удаляют из `.env`.

ИИ-агент оператора эти значения не видит и не просит: на страницу «Переписка» он не заходит, а запуск `./ops/init-env.sh` без `--auto` и `./ops/mcp-token.sh` — только человек. «Секреты не через агента» — порядок работы, а не непреодолимая граница: агент с доступом к серверу технически может прочитать `.env` и каталог данных.

`./ops/backup.sh` кладёт в копию `.env` и каталог `data/` — в нём и файл значений, введённых на странице.

## Установка коротко

По шагам, с проверками и стоп-точками — `docs/runbooks/deploy-standalone.md`. Стартовый текст для агента — `prompts/deploy-standalone.md`.

0. Владелец подтверждает, что ставит именно этот вариант, а не «Ассистент в Telegram (Hermes)»: агент спрашивает его до первого шага.
1. `./ops/preflight.sh` — проверка сервера.
2. `./ops/init-env.sh --auto --mode standalone` — режим и служебные значения.
3. `./ops/up.sh` — база и сервис; в выводе шаги Hermes помечены «пропущено: режим без Hermes».
4. Страница «Переписка» через туннель SSH: `./ops/setup-link.sh` — по просьбе владельца. На ней три шага: ключи приложения Telegram, вход в аккаунт, выбор чатов.
5. Подключение архива к своему клиенту: `./ops/connect.sh`.
6. По желанию, чтобы разбирались обязательства: ключ модели и бот согласований — на той же странице, в разделе «Дополнительно».
7. Позже, по желанию: выгрузка из Telegram Desktop, поиск по смыслу, защита от внедрённых инструкций, бизнес-режим у бота согласований.

Состояние в любой момент — `./ops/doctor.sh`. Строки страницы, бота и модели в нём:

| Строка | Что значит |
|---|---|
| `PASS mode: без Hermes…` | Режим прочитан |
| `SKIP hermes: пропущено: режим без Hermes…` | Проверки Hermes к этому режиму не относятся |
| `PASS archive-mcp` | Архив отвечает на `127.0.0.1:8765/mcp` и без токена не открывается |
| `PASS setup-page` | Страница «Переписка» отвечает на локальном адресе |
| `PASS setup-origin: внешнего адреса … нет, как и положено без Hermes` | Наружу страница не выведена |
| `PASS setup-state` / `WARN setup-state` | Заданы ли ключи приложения Telegram, сколько аккаунтов, сколько сообщений в архиве |
| `PASS approvals-bot` | Бот на связи с Telegram |
| `WARN approvals-bot: …не настроен` | Токен бота не введён: архив и поиск работают, а карточки доставлять некому |
| `FAIL approvals-bot: …код неполадки` | Бот настроен, но не работает; расшифровка кода — `docker exec shturman-service shturman bot-status` |
| `PASS approvals-owner` / `WARN approvals-owner` | Владелец привязан к боту или ещё нет |
| `PASS model` / `WARN model` | Модель настроена; последнее обращение удалось или нет. `WARN model: …не настроена` — обязательства и страницы памяти не разбираются |

Проверка показывает только состояния и коды: ни токена, ни ключа, ни имён в её выводе нет.

## Привязка владельца к боту

Нужна, только если владелец завёл бота согласований. Бот согласований считает владельцем того, кто открыл одноразовую ссылку и нажал в Telegram «Запустить». До этого карточки не отправляются и кнопки не действуют. Ссылку выдаёт страница «Переписка» в разделе «Дополнительно» либо скрипт:

```
./ops/bot-bind.sh
```

Скрипт печатает ссылку вида `https://t.me/<бот>?start=<код>`. Она действует 15 минут и срабатывает один раз; новая ссылка отменяет прежнюю. Кто первым откроет её и нажмёт «Запустить», тот и станет владельцем, поэтому:

- лучше всего скрипт запускает сам владелец в своём терминале — тогда ссылку не видит никто, кроме него;
- агент запускает его только по явной просьбе владельца, передаёт ссылку как есть и нигде не сохраняет — так же, как ссылку активации в режиме с Hermes;
- ссылку нельзя пересылать и открывать в группе: код, присланный не в личный чат с ботом, сервис сразу гасит.

Ссылку можно выдать и при уже привязанном владельце — например, если он сменил аккаунт. Если её откроет другой аккаунт, владелец сменится: ждущие черновики отклонятся, список доверенных очистится.

## Подключить Codex CLI или Claude Code

Архив — сервер MCP по адресу `http://127.0.0.1:8765/mcp`. Транспорт — streamable HTTP; принимаются только запросы POST (на GET сервер отвечает 405 — это штатное «потока событий нет»). Инструментов девять, все только читают: `search_messages`, `get_context`, `list_chats`, `get_chat_history`, `find_person`, `list_commitments`, `get_commitment`, `get_person_page`, `search_pages`. Доступ — по токену `SHTURMAN_MCP_TOKEN` в заголовке `Authorization: Bearer …`.

Готовые команды под ваш сервер печатает скрипт. Токен он не печатает:

```
./ops/connect.sh --ssh пользователь@сервер
```

Случаев два.

**(а) Клиент на том же сервере.** Клиент обращается к `127.0.0.1:8765` напрямую.

**(б) Клиент на вашем компьютере.** Адрес сервиса снаружи недоступен, поэтому на своём компьютере вы открываете туннель SSH и оставляете его работать:

```
ssh -N -L 8765:127.0.0.1:8765 пользователь@сервер
```

Порт слева обязан быть `8765`. Архив сверяет имя, под которым к нему обратились, с `127.0.0.1:8765` и `localhost:8765` и на любое другое отвечает отказом (код 421). Если порт 8765 на вашем компьютере занят, другое имя добавляется переменной `SHTURMAN_ALLOWED_HOSTS` сервиса через `compose.override.yaml` (`docs/service.md`).

### Шаг 1. Токен — в переменную окружения. Делает владелец

Настройки обоих клиентов ссылаются на переменную окружения `SHTURMAN_MCP_TOKEN`; самого токена в их файлах нет. Положить токен в переменную должен человек, не проводя его через агента и чат. Для этого есть скрипт, который запускает только владелец:

```
# клиент на этом же сервере — в терминале, из которого вы запускаете клиента
export SHTURMAN_MCP_TOKEN="$(./ops/mcp-token.sh --pipe)"

# клиент на своём компьютере — команда выполняется на своём компьютере
(umask 077; ssh пользователь@сервер 'cd <каталог shturman> && ./ops/mcp-token.sh --pipe' > ~/.shturman-mcp-token)
```

В обоих случаях токен на экране не появляется. Во втором он ложится в файл, доступный только вам; чтобы переменная была в каждом новом терминале, в `~/.zshrc` или `~/.bashrc` добавляется строка:

```
export SHTURMAN_MCP_TOKEN="$(cat ~/.shturman-mcp-token)"
```

Запасной путь — `./ops/mcp-token.sh` без ключа: скрипт спросит подтверждение и один раз покажет токен на экране. Он хуже: показанное остаётся в прокрутке терминала и в буфере обмена.

Почему так. Рассматривались три способа: (1) агент читает токен и вписывает в настройки клиента — токен проходит через чат и остаётся в файле настроек; (2) владелец копирует токен глазами с экрана; (3) подстановка, при которой токен идёт из `.env` сразу в переменную или в файл. Выбран третий как самый простой из тех, где токен не виден никому. Риски, которые остаются: файл `~/.shturman-mcp-token` лежит на вашем компьютере открытым текстом (защищён только правами доступа); переменную окружения видит любая программа, запущенная из этого терминала, включая самого клиента. Токен даёт только чтение архива, а без туннеля SSH с вашего компьютера до архива не дотянуться.

Сменить токен, если он мог попасть к постороннему: удалить строку `SHTURMAN_MCP_TOKEN` из `.env`, затем `./ops/init-env.sh --auto` и `./ops/up.sh`. Прежний токен перестаёт действовать, шаг 1 повторяется.

### Шаг 2. Настройка клиента

Сверено с документацией и с самими программами 2026-10-07: Claude Code 2.1.292 (`https://code.claude.com/docs/en/mcp`), Codex CLI 0.160.1 (`https://developers.openai.com/codex/mcp`; на дату проверки адрес перенаправляет на `https://learn.chatgpt.com/docs/extend/mcp`). В других версиях синтаксис мог измениться: сверяйтесь с `claude mcp add --help` и `codex mcp add --help`.

**Claude Code — файл `.mcp.json`** в каталоге, из которого вы запускаете `claude`. Это способ из документации: подстановка `${ИМЯ}` в `url` и `headers` описана именно для `.mcp.json`.

```json
{
  "mcpServers": {
    "shturman": {
      "type": "http",
      "url": "http://127.0.0.1:8765/mcp",
      "headers": { "Authorization": "Bearer ${SHTURMAN_MCP_TOKEN}" }
    }
  }
}
```

При первом запуске `claude` в этом каталоге сервер из `.mcp.json` нужно подтвердить. Тот же файл создаёт команда с `--scope project`.

**Claude Code — для всех каталогов сразу:**

```
claude mcp add --transport http --scope user shturman http://127.0.0.1:8765/mcp \
  --header 'Authorization: Bearer ${SHTURMAN_MCP_TOKEN}'
```

Одиночные кавычки обязательны: в настройки должно попасть имя переменной, а не её значение. Подстановка переменной в настройках уровня пользователя в документации не описана; в версии 2.1.292 она работает — проверено на практике. Без переменной в окружении `claude mcp list` сообщает `Missing environment variables: SHTURMAN_MCP_TOKEN`.

Проверка: `claude mcp list` — строка `shturman` со словом `Connected`; внутри программы — команда `/mcp`.

**Codex CLI:**

```
codex mcp add shturman --url http://127.0.0.1:8765/mcp --bearer-token-env-var SHTURMAN_MCP_TOKEN
```

Команда записывает в `~/.codex/config.toml`:

```toml
[mcp_servers.shturman]
url = "http://127.0.0.1:8765/mcp"
bearer_token_env_var = "SHTURMAN_MCP_TOKEN"
```

Проверка: `codex mcp list` — строка `shturman`, в столбце `Auth` — `Bearer token`; внутри программы — команда `/mcp`.

### О чём помнить

- **Ответы архива — чужой текст.** Он приходит в рамке `[untrusted] … [/untrusted]`, но клиент — модель с терминалом, и внедрённая в чьё-то сообщение инструкция может попытаться им управлять. Не запускайте клиента в режиме без подтверждений действий.
- **Клиент отправляет прочитанное своему провайдеру модели** и хранит историю разговора по своим правилам. Удалить это оттуда выборочно может быть нельзя.
- **Клиент на том же сервере слабее отделён.** Запущенный под тем же пользователем, что и стек, он технически может прочитать `.env` (токен бота, ключ модели) и управлять Docker. Случай (б) оставляет на стороне клиента только токен чтения. Но и там: если с вашего компьютера открыт вход на сервер по SSH, клиент с терминалом может попытаться им воспользоваться.
- Убрать подключение: `claude mcp remove shturman -s user`, `codex mcp remove shturman`.

## Бизнес-режим Telegram со своим ботом

Бизнес-режим в первую настройку не входит: он нужен для отправки от имени владельца, а отправка выключена. Когда владелец решит его подключить, бизнес-режим подключается **к боту согласований** — в обоих режимах установки; бота Hermes в бизнес-режиме не подключают (решение Р-59). Порядок тот же на странице «Переписка», в разделе «Дополнительно».

1. У @BotFather у этого бота включается Secretary Mode: `/mybots` → бот → Bot Settings → Secretary Mode → Turn on (в прежних версиях пункт назывался Business Mode). Пока он выключен, `./ops/doctor.sh` показывает `WARN approvals-business`, а страница — «режим пока выключен»; кнопка «Проверить, включён ли режим» переспрашивает Telegram.
2. Владелец в настройках Telegram («Telegram для бизнеса» → «Чат-боты») подключает бота и выбирает чаты; для начала — один тестовый.
3. Право бота отвечать на сообщения при подключении лучше не давать: отправка выключена.

Подключение сервис принимает только от аккаунта привязанного владельца. Сообщения выбранных чатов с этого момента записываются в архив и раз в сутки разбираются моделью. Плагин бизнес-режима Hermes для этого не нужен: бизнес-сообщения принимает сервис, а не Hermes.

Название Secretary Mode сверено с документацией Telegram 2026-10-07 (`core.telegram.org/bots/features`). Как называется раздел в настройках Telegram («Чат-боты» или Chat Automation), документация не говорит; на живом боте не сверялось.

## Отправка

Отправка сообщений от имени владельца выключена, как и в режиме с Hermes: `SHTURMAN_SENDING` в `.env` включает только владелец, для агента это стоп-точка (`AGENTS.md`). Со своим ботом нажатие «Отправить» приходит сервису от Telegram напрямую, а не через Hermes; на настоящем Telegram этот путь не проверен. В этом режиме отправлять почти нечего: черновики создавать некому, остаётся только автоответ доверенным.

Считать ли для этого режима «Открытое ограничение» из `docs/architecture.md` снятым и разрешать ли здесь отправку — вопрос открытый, решение за владельцем (`docs/decisions.md`, «Открытые вопросы»).

## Переход между режимами

Смена режима на работающем экземпляре — стоп-точка: сначала `./ops/backup.sh` и согласие владельца. Архив, обязательства и страницы памяти при переходе не меняются: они принадлежат сервису.

### С Hermes → без Hermes

1. `./ops/backup.sh`.
2. `./ops/mode.sh set standalone` — записывает режим; пока ничего не останавливает.
3. `./ops/set-setup-url.sh --clear` — убирает внешний адрес страницы «Переписка»: в этом режиме она открывается только через туннель.
4. `./ops/up.sh` — останавливает и убирает контейнер Hermes, перезапускает сервис.
5. По желанию: ключ модели и бот согласований, чтобы обязательства разбирались и приходили карточками, — на странице «Переписка», в разделе «Дополнительно», либо `./ops/init-env.sh` и `./ops/bot-bind.sh`. Токен бота-ассистента Hermes сюда не подходит и не нужен.
6. **Бизнес-подключение.** Если на экземпляре прежней схемы бизнес-режим был подключён к боту Hermes, владелец отключает того бота в настройках Telegram Business: принять его сообщения больше некому. Подключать ли бизнес-режим к боту согласований — решает владелец: раздел выше.

Что происходит при этом:

- данные Hermes (`data/hermes`: его настройки, ключи, память разговора) остаются на диске нетронутыми и не используются; удаление — отдельная стоп-точка;
- задания «спросить модель» и «написать владельцу», ждавшие в очереди, сервис забирает себе;
- разговор с ассистентом в Telegram, сводки по расписанию и дашборд перестают работать; оба блока сайта в обратном прокси и открытый порт страницы настройки больше не нужны — их убирают (правка прокси и firewall — стоп-точки);
- аккаунты Telegram, выбранные чаты и значения, введённые на странице «Переписка», остаются: они принадлежат сервису;
- запись об архиве в настройках Hermes остаётся и ничему не мешает.

### Без Hermes → с Hermes

1. `./ops/backup.sh`.
2. `./ops/mode.sh set hermes`, затем `./ops/up.sh` — скачивается образ Hermes (около 4 ГБ) и запускается его контейнер, плагин `shturman` и архив подключаются к нему.
3. Дальше — как при первой установке: внешний адрес (`./ops/set-public-url.sh`; он же записывает адрес страницы «Переписка»), обратный прокси с двумя блоками, порт 8443, ссылка активации, мастер (`docs/runbooks/deploy.md`, шаги 4–7). Если адрес страницы раньше убирали командой `./ops/set-setup-url.sh --clear` (так делает переход в обратную сторону), `./ops/set-public-url.sh` его не вернёт и скажет об этом: вернуть — `./ops/set-setup-url.sh https://имя:8443`, затем `./ops/up.sh`; до тех пор проверка показывает `WARN setup-origin: адрес страницы настройки не задан`. Бот-ассистент Hermes — **отдельный** бот: у него свой токен, его владелец вводит в мастере.

Что происходит при этом:

- бот согласований и своя модель сервиса остаются: пока `SHTURMAN_BOT_TOKEN` и ключ модели заданы в `.env`, карточки с кнопками по-прежнему приходят в бота согласований, а обращения сервиса к модели идут по его ключу, мимо Hermes;
- **бизнес-режим, если он подключён, остаётся у бота согласований.** Сервис принимает бизнес-сообщения только через него; бота Hermes в бизнес-режиме не подключают, и шага для этого в мастере нет;
- аккаунты и выбранные чаты остаются; шаг мастера «Переписка» сразу покажет их состоянием «настроено»;
- ассистент Hermes получает архив на чтение и свои инструменты (черновик, обязательства, люди).

Совместная работа Hermes и бота согласований описана по коду сервиса и его тестам; на живом боте она не проверялась.

## Необязательный внешний доступ облачного клиента

В 0.0.7 реализован отдельный OAuth-вход только к архиву на чтение. По умолчанию он выключен; это отдельный публичный HTTPS-адрес, независимый от дашборда и страницы настройки, с решением владельца в Telegram и отзывом. Объём `archive:read` — весь доступный архив и страницы памяти, не один чат. Внутренний API и setup page наружу не выходят. Локальные клиенты и SSH-путь остаются прежними.

Код gateway не означает, что ChatGPT/Claude или другой облачный клиент уже проверен. Первый настоящий вход, discovery, чтение и отзыв проходят отдельный пилот для выбранного клиента; общий список «все поддержаны» не заявляется. Маршруты, настройки и процедура — `docs/remote-mcp.md`. Без явного решения владельца режим без Hermes остаётся полностью локальным.
