# Режим без Hermes: только архив и согласования

Состояние на 2026-10-07, версия 0.0.4. Режим собирается и запускается: стек поднимался под Docker на стенде разработки, архив отвечал настоящему Claude Code. **С настоящим ботом Telegram, настоящей моделью и на сервере владельца режим не проверялся.** Что именно проверено — в конце документа.

## Что это

У «Штурмана» два режима установки. Режим выбирается один раз и записывается в `.env` строкой `SHTURMAN_MODE`.

| | С Hermes (`hermes`, по умолчанию) | Без Hermes (`standalone`) |
|---|---|---|
| Что работает на сервере | Hermes Agent, сервис переписки, база | Только сервис переписки и база |
| Кто говорит с владельцем | Ассистент в Telegram (бот Hermes) | Никто. Бот согласований только присылает карточки с кнопками |
| Кто обращается к модели | Hermes | Сам сервис, по ключу владельца |
| Вопросы по архиву | Ассистенту в Telegram | Из своего Codex CLI или Claude Code: архив подключается как сервер MCP |
| Где вводятся токены и ключи | В веб-мастере | В терминале сервера, скрытым вводом |

Режим без Hermes — для владельца, которому нужен архив переписки с поиском и список обязательств, а разговаривать с ассистентом он собирается из своих инструментов.

## Что есть

- **Архив переписки**: импорт экспорта Telegram Desktop, чтение аккаунтов через сессию, бизнес-режим Telegram — всё, что описано в `docs/service.md`.
- **Поиск** по словам, а при включённых эмбеддингах — и по смыслу.
- **Ночная обработка**: сервис сам просит модель разобрать новые сообщения, находит обязательства и собирает страницы памяти о людях.
- **Бот согласований**: отдельный бот, которым владеет сервис. Присылает владельцу найденные обязательства, предложения новых страниц и срабатывания наблюдателя групп — карточками с кнопками. Нажатие приходит сервису от Telegram напрямую.
- **Подтверждения владельца**: изменения, которые расширяют то, что сервис читает и делает, — включить чаты аккаунта, вернуть исключённый чат, запустить импорт, добавить доверенного, завести правило наблюдателя — применяются только после нажатия в боте. Команда `shturman call` в ответ печатает «ЖДЁТ ПОДТВЕРЖДЕНИЯ В БОТЕ» (`docs/service.md`, «Что подтверждает владелец в боте согласований»).
- **Защита от внедрённых инструкций**, по желанию: `./ops/guard.sh on` (`docs/guard.md`).
- **Архив для Codex CLI и Claude Code**: девять инструментов, все только читают.

## Чего нет по сравнению с режимом с Hermes

| Чего нет | Почему |
|---|---|
| Разговора с ассистентом в Telegram | Отвечать некому: бот согласований на сообщения не отвечает, только раз в час напоминает владельцу, что писать ему не нужно |
| Утренней сводки и обзора недели | Это скиллы Hermes и его расписание |
| Памяти разговора | Её ведёт Hermes. Память о переписке — архив, обязательства, страницы о людях — остаётся |
| Веб-мастера и дашборда | Это вкладка дашборда Hermes. У экземпляра нет ни веб-адреса, ни входа; `./ops/activation-link.sh`, `./ops/set-public-url.sh`, `./ops/logout-all.sh`, `./ops/emergency-access.sh` в этом режиме отвечают, что неприменимы |
| Имени и характера ассистента | Это настройка Hermes |
| Изменений из Codex CLI и Claude Code | Архив для них только читается: закрыть обязательство, поправить человека, создать черновик оттуда нельзя |
| **Готовых черновиков ответов** | Черновик создаёт ассистент Hermes своим инструментом. Без Hermes создавать их некому; автоматически сервис пишет текст только для автоответа доверенным, а он выключен вместе с отправкой |
| ChatGPT в браузере и других облачных клиентов | Архив не опубликован наружу — см. «Что не поддержано» |

Управление правилами (выбор чатов, исключение чата, список доверенных, правила наблюдателя) — командами в терминале, как и в режиме с Hermes: `docs/service.md`, «Как пользоваться без веб-интерфейса».

## Как устроено

| Контейнер | Что это | Сеть |
|---|---|---|
| `shturman-service` | Сервис переписки: архив, сессии Telegram, бот согласований, обращения к модели, сервер MCP | `backend` и `egress`; порт 8765 только на `127.0.0.1` |
| `shturman-postgres` | База архива | Только `backend`, порт не публикуется |
| `shturman-embeddings` | Поиск по смыслу, по желанию | Только `backend` |
| `shturman-guard` | Модель защиты от внедрённых инструкций, по желанию | Только `backend` |

Контейнер Hermes не создаётся, его образ (около 4 ГБ) не скачивается. Сети и правило «сервис и база слушают только локальный адрес сервера» те же, что в режиме с Hermes. Наружу экземпляр не публикует ничего.

Наружу сервис ходит сам: к Telegram (бот, сессии аккаунтов) и к провайдеру модели. При ночной обработке фрагменты переписки уходят этому провайдеру — как и в режиме с Hermes.

Требования к серверу не перемерялись: `./ops/preflight.sh` проверяет те же 4 ГБ памяти, хотя без Hermes нужно меньше.

## Где проходят секреты

| Секрет | Кто вводит | Куда попадает |
|---|---|---|
| Токен бота согласований (`SHTURMAN_BOT_TOKEN`) | **Владелец** в своём терминале: `./ops/init-env.sh` | `.env` на сервере → окружение контейнера сервиса |
| Ключ модели (`SHTURMAN_LLM_API_KEY`) | **Владелец**, там же | То же |
| Имя модели и адрес API (`SHTURMAN_LLM_MODEL`, `SHTURMAN_LLM_BASE_URL`) | Владелец, там же; значения не секретные | То же |
| Пароль базы, токен внутреннего API, токен архива | Генерирует `./ops/init-env.sh --auto`, значения не печатаются | `.env` |
| Ссылка привязки владельца к боту | Создаёт `./ops/bot-bind.sh` | В базе — только хеш; действует 15 минут, один раз |
| Токен архива для Codex CLI или Claude Code | **Владелец** забирает командой `./ops/mcp-token.sh` | Переменная окружения на машине, где работает клиент |

`./ops/init-env.sh` без `--auto` спрашивает значения по очереди. Секреты вводятся скрыто: набранное не показывается на экране и не попадает ни в историю команд, ни в журналы. На лишний вопрос — Enter. Значение с пробелом, кавычкой или знаками `$ # \` скрипт не запишет и скажет об этом; токен бота проверяется на вид `123456789:буквы-и-цифры`. Уже заданное значение скрипт не переспрашивает: чтобы его сменить, строку удаляют из `.env`.

ИИ-агент оператора эти значения не видит и не просит: запуск `./ops/init-env.sh` без `--auto` и `./ops/mcp-token.sh` — только человек. «Секреты не через агента» — порядок работы, а не непреодолимая граница: агент с доступом к серверу технически может прочитать `.env`.

`./ops/backup.sh` кладёт `.env` в копию вместе с каталогом `data/`: без Hermes токен бота и ключ модели лежат именно там.

## Установка коротко

По шагам, с проверками и стоп-точками — `docs/runbooks/deploy-standalone.md`. Стартовый текст для агента — `prompts/deploy-standalone.md`.

1. `./ops/preflight.sh` — проверка сервера.
2. `./ops/init-env.sh --auto --mode standalone` — режим и служебные значения.
3. `./ops/up.sh` — база и сервис; в выводе шаги Hermes помечены «пропущено: режим без Hermes».
4. Владелец создаёт у @BotFather **нового** бота и получает ключ у провайдера модели; вводит их: `./ops/init-env.sh`, затем `./ops/up.sh`.
5. Привязка владельца к боту: `./ops/bot-bind.sh`.
6. Подключение архива к своему клиенту: `./ops/connect.sh`.
7. По желанию: импорт истории, поиск по смыслу, сессии аккаунтов, бизнес-режим.

Состояние в любой момент — `./ops/doctor.sh`. Строки бота и модели в нём:

| Строка | Что значит |
|---|---|
| `PASS mode: без Hermes…` | Режим прочитан |
| `SKIP hermes: пропущено: режим без Hermes…` | Проверки Hermes к этому режиму не относятся |
| `PASS archive-mcp` | Архив отвечает на `127.0.0.1:8765/mcp` и без токена не открывается |
| `PASS approvals-bot` | Бот на связи с Telegram |
| `WARN approvals-bot: …не настроен` | Токен бота не введён: карточки доставлять некому |
| `FAIL approvals-bot: …код неполадки` | Бот настроен, но не работает; расшифровка кода — `docker exec shturman-service shturman bot-status` |
| `PASS approvals-owner` / `WARN approvals-owner` | Владелец привязан к боту или ещё нет |
| `PASS model` / `WARN model` | Модель настроена; последнее обращение удалось или нет |

Проверка показывает только состояния и коды: ни токена, ни ключа, ни имён в её выводе нет.

## Привязка владельца к боту

Бот согласований считает владельцем того, кто открыл одноразовую ссылку и нажал в Telegram «Запустить». До этого карточки не отправляются и кнопки не действуют.

```
./ops/bot-bind.sh
```

Скрипт печатает ссылку вида `https://t.me/<бот>?start=<код>`. Она действует 15 минут и срабатывает один раз; новая ссылка отменяет прежнюю. Кто первым откроет её и нажмёт «Запустить», тот и станет владельцем, поэтому:

- лучше всего скрипт запускает сам владелец в своём терминале — тогда ссылку не видит никто, кроме него;
- агент запускает его только по явной просьбе владельца, передаёт ссылку как есть и нигде не сохраняет — так же, как ссылку активации в режиме с Hermes;
- ссылку нельзя пересылать и открывать в группе: код, присланный не в личный чат с ботом, сервис сразу гасит.

Ссылку можно выдать и при уже привязанном владельце — например, если он сменил аккаунт. Если её откроет другой аккаунт, владелец сменится: ждущие черновики отклонятся, список доверенных очистится.

## Подключить Codex CLI или Claude Code

Архив — сервер MCP по адресу `http://127.0.0.1:8765/mcp`. Транспорт — streamable HTTP; принимаются только запросы POST (на GET сервер отвечает 405 — это штатное «потока событий нет»). Инструментов девять, все только читают: `search_messages`, `get_context`, `list_chats`, `get_chat_history`, `find_person`, `list_commitments`, `get_commitment`, `get_person_page`, `search_pages`. Доступ — по токену `SHTURMAN_MCP_TOKEN` в заголовке `Authorization: Bearer …`.

Готовые команды под ваш сервер печатает скрипт. Токен он не печатает:

```
./ops/connect.sh --ssh пользователь@сервер
```

Случаев два.

**(а) Клиент на том же сервере.** Клиент обращается к `127.0.0.1:8765` напрямую.

**(б) Клиент на вашем компьютере.** Адрес сервиса снаружи недоступен, поэтому на своём компьютере вы открываете туннель SSH и оставляете его работать:

```
ssh -N -L 8765:127.0.0.1:8765 пользователь@сервер
```

Порт слева обязан быть `8765`. Архив сверяет имя, под которым к нему обратились, с `127.0.0.1:8765` и `localhost:8765` и на любое другое отвечает отказом (код 421). Если порт 8765 на вашем компьютере занят, другое имя добавляется переменной `SHTURMAN_ALLOWED_HOSTS` сервиса через `compose.override.yaml` (`docs/service.md`).

### Шаг 1. Токен — в переменную окружения. Делает владелец

Настройки обоих клиентов ссылаются на переменную окружения `SHTURMAN_MCP_TOKEN`; самого токена в их файлах нет. Положить токен в переменную должен человек, не проводя его через агента и чат. Для этого есть скрипт, который запускает только владелец:

```
# клиент на этом же сервере — в терминале, из которого вы запускаете клиента
export SHTURMAN_MCP_TOKEN="$(./ops/mcp-token.sh --pipe)"

# клиент на своём компьютере — команда выполняется на своём компьютере
(umask 077; ssh пользователь@сервер 'cd <каталог shturman> && ./ops/mcp-token.sh --pipe' > ~/.shturman-mcp-token)
```

В обоих случаях токен на экране не появляется. Во втором он ложится в файл, доступный только вам; чтобы переменная была в каждом новом терминале, в `~/.zshrc` или `~/.bashrc` добавляется строка:

```
export SHTURMAN_MCP_TOKEN="$(cat ~/.shturman-mcp-token)"
```

Запасной путь — `./ops/mcp-token.sh` без ключа: скрипт спросит подтверждение и один раз покажет токен на экране. Он хуже: показанное остаётся в прокрутке терминала и в буфере обмена.

Почему так. Рассматривались три способа: (1) агент читает токен и вписывает в настройки клиента — токен проходит через чат и остаётся в файле настроек; (2) владелец копирует токен глазами с экрана; (3) подстановка, при которой токен идёт из `.env` сразу в переменную или в файл. Выбран третий как самый простой из тех, где токен не виден никому. Риски, которые остаются: файл `~/.shturman-mcp-token` лежит на вашем компьютере открытым текстом (защищён только правами доступа); переменную окружения видит любая программа, запущенная из этого терминала, включая самого клиента. Токен даёт только чтение архива, а без туннеля SSH с вашего компьютера до архива не дотянуться.

Сменить токен, если он мог попасть к постороннему: удалить строку `SHTURMAN_MCP_TOKEN` из `.env`, затем `./ops/init-env.sh --auto` и `./ops/up.sh`. Прежний токен перестаёт действовать, шаг 1 повторяется.

### Шаг 2. Настройка клиента

Сверено с документацией и с самими программами 2026-10-07: Claude Code 2.1.292 (`https://code.claude.com/docs/en/mcp`), Codex CLI 0.160.1 (`https://developers.openai.com/codex/mcp`; на дату проверки адрес перенаправляет на `https://learn.chatgpt.com/docs/extend/mcp`). В других версиях синтаксис мог измениться: сверяйтесь с `claude mcp add --help` и `codex mcp add --help`.

**Claude Code — файл `.mcp.json`** в каталоге, из которого вы запускаете `claude`. Это способ из документации: подстановка `${ИМЯ}` в `url` и `headers` описана именно для `.mcp.json`.

```json
{
  "mcpServers": {
    "shturman": {
      "type": "http",
      "url": "http://127.0.0.1:8765/mcp",
      "headers": { "Authorization": "Bearer ${SHTURMAN_MCP_TOKEN}" }
    }
  }
}
```

При первом запуске `claude` в этом каталоге сервер из `.mcp.json` нужно подтвердить. Тот же файл создаёт команда с `--scope project`.

**Claude Code — для всех каталогов сразу:**

```
claude mcp add --transport http --scope user shturman http://127.0.0.1:8765/mcp \
  --header 'Authorization: Bearer ${SHTURMAN_MCP_TOKEN}'
```

Одиночные кавычки обязательны: в настройки должно попасть имя переменной, а не её значение. Подстановка переменной в настройках уровня пользователя в документации не описана; в версии 2.1.292 она работает — проверено на практике. Без переменной в окружении `claude mcp list` сообщает `Missing environment variables: SHTURMAN_MCP_TOKEN`.

Проверка: `claude mcp list` — строка `shturman` со словом `Connected`; внутри программы — команда `/mcp`.

**Codex CLI:**

```
codex mcp add shturman --url http://127.0.0.1:8765/mcp --bearer-token-env-var SHTURMAN_MCP_TOKEN
```

Команда записывает в `~/.codex/config.toml`:

```toml
[mcp_servers.shturman]
url = "http://127.0.0.1:8765/mcp"
bearer_token_env_var = "SHTURMAN_MCP_TOKEN"
```

Проверка: `codex mcp list` — строка `shturman`, в столбце `Auth` — `Bearer token`; внутри программы — команда `/mcp`.

### О чём помнить

- **Ответы архива — чужой текст.** Он приходит в рамке `[untrusted] … [/untrusted]`, но клиент — модель с терминалом, и внедрённая в чьё-то сообщение инструкция может попытаться им управлять. Не запускайте клиента в режиме без подтверждений действий.
- **Клиент отправляет прочитанное своему провайдеру модели** и хранит историю разговора по своим правилам. Удалить это оттуда выборочно может быть нельзя.
- **Клиент на том же сервере слабее отделён.** Запущенный под тем же пользователем, что и стек, он технически может прочитать `.env` (токен бота, ключ модели) и управлять Docker. Случай (б) оставляет на стороне клиента только токен чтения. Но и там: если с вашего компьютера открыт вход на сервер по SSH, клиент с терминалом может попытаться им воспользоваться.
- Убрать подключение: `claude mcp remove shturman -s user`, `codex mcp remove shturman`.

## Бизнес-режим Telegram со своим ботом

В режиме без Hermes бизнес-режим подключается **к боту согласований** — другого бота у экземпляра нет.

1. У @BotFather у этого бота включается Business Mode (Bot Settings → Business Mode). Пока он выключен, `./ops/doctor.sh` показывает `WARN approvals-business`.
2. Владелец в настройках Telegram (Telegram Business → чат-боты) подключает бота и выбирает чаты; для начала — один тестовый.
3. Право бота отвечать на сообщения при подключении лучше не давать: отправка выключена.

Подключение сервис принимает только от аккаунта привязанного владельца. Сообщения выбранных чатов с этого момента записываются в архив и раз в сутки разбираются моделью. Плагин бизнес-режима Hermes здесь не нужен: Hermes нет, и принять сообщения собеседников за команды некому.

Названия пунктов в Telegram в источниках расходятся (Business Mode или Secretary Mode, «Чат-боты» или Chat Automation); на живом боте не сверялось.

## Отправка

Отправка сообщений от имени владельца выключена, как и в режиме с Hermes: `SHTURMAN_SENDING` в `.env` включает только владелец, для агента это стоп-точка (`AGENTS.md`). Со своим ботом нажатие «Отправить» приходит сервису от Telegram напрямую, а не через Hermes; на настоящем Telegram этот путь не проверен. В этом режиме отправлять почти нечего: черновики создавать некому, остаётся только автоответ доверенным.

Считать ли для этого режима «Открытое ограничение» из `docs/architecture.md` снятым и разрешать ли здесь отправку — вопрос открытый, решение за владельцем (`docs/decisions.md`, «Открытые вопросы»).

## Переход между режимами

Смена режима на работающем экземпляре — стоп-точка: сначала `./ops/backup.sh` и согласие владельца. Архив, обязательства и страницы памяти при переходе не меняются: они принадлежат сервису.

### С Hermes → без Hermes

1. `./ops/backup.sh`.
2. `./ops/mode.sh set standalone` — записывает режим; пока ничего не останавливает.
3. Владелец создаёт у @BotFather нового бота для согласований и вводит его токен и ключ модели: `./ops/init-env.sh`. Токен управляющего бота Hermes сюда не подходит и не нужен.
4. `./ops/up.sh` — останавливает и убирает контейнер Hermes, перезапускает сервис с ботом и моделью.
5. `./ops/bot-bind.sh` — привязка владельца к боту согласований.
6. **Бизнес-подключение.** Если бизнес-режим был подключён к боту Hermes, владелец отключает того бота в настройках Telegram Business и подключает бота согласований: раздел выше. Пока этого не сделано, новые сообщения личных чатов в архив не попадают — принять их у бота Hermes некому.

Что происходит при этом:

- данные Hermes (`data/hermes`: его настройки, ключи, память разговора) остаются на диске нетронутыми и не используются; удаление — отдельная стоп-точка;
- задания «спросить модель» и «написать владельцу», ждавшие в очереди, сервис забирает себе;
- разговор с ассистентом в Telegram, сводки по расписанию и дашборд перестают работать; настройку обратного прокси и адрес можно убрать (правка прокси — стоп-точка);
- запись об архиве в настройках Hermes остаётся и ничему не мешает.

### Без Hermes → с Hermes

1. `./ops/backup.sh`.
2. `./ops/mode.sh set hermes`, затем `./ops/up.sh` — скачивается образ Hermes (около 4 ГБ) и запускается его контейнер, плагин `shturman` и архив подключаются к нему.
3. Дальше — как при первой установке: внешний адрес, обратный прокси, ссылка активации, мастер (`docs/runbooks/deploy.md`, шаги 4–7). Управляющий бот Hermes — **ещё один** бот: у него свой токен, его владелец вводит в мастере.

Что происходит при этом:

- бот согласований и своя модель сервиса остаются: пока `SHTURMAN_BOT_TOKEN` и ключ модели заданы в `.env`, карточки с кнопками по-прежнему приходят в бота согласований, а обращения сервиса к модели идут по его ключу, мимо Hermes;
- **бизнес-режим остаётся у бота согласований.** При своём боте сервис принимает бизнес-сообщения только через него; бота Hermes в бизнес-режиме подключать не нужно, и шаг мастера «Бизнес-режим» пропускается;
- ассистент Hermes получает архив на чтение и свои инструменты (черновик, обязательства, люди).

Совместная работа Hermes и бота согласований описана по коду сервиса и его тестам; на живом боте она не проверялась.

## Что не поддержано: ChatGPT в браузере и другие облачные клиенты

Облачному клиенту нужен адрес `/mcp`, доступный из интернета. Сейчас этого нет и скрипты этого не делают: публикация меняет правило «экземпляр ничего не публикует наружу» и ждёт решения владельца. Решение Р-11 (`docs/decisions.md`) допускает такой режим — необязательный, только чтение, по умолчанию выключенный, за OAuth, — но он не реализован.

Что для него потребуется:

- публичный адрес с TLS и обратный прокси перед `127.0.0.1:8765`, пропускающий только путь `/mcp`;
- внешнее имя в `SHTURMAN_ALLOWED_HOSTS` — иначе сервис отвергнет запрос с этим именем;
- способ входа, который принимает облачный клиент. Сейчас у архива один постоянный токен в заголовке; Р-11 требует OAuth, и его в сервисе нет. Что именно поддерживает ChatGPT, нужно сверять с его документацией на момент решения;
- защита открытого адреса от перебора и ограничение частоты запросов;
- согласие владельца с тем, что сторонний сервис запоминает прочитанное по своим правилам;
- запись решения в `docs/decisions.md` и правка инвариантов в `AGENTS.md`.

## Проверено и не проверено

Проверено 2026-10-07 на стенде разработки (Docker 29.8.2, Compose 5.5.1; образ сервиса собран из того же `Dockerfile` без пакета git и с сертификатом прокси стенда; у контейнеров не было выхода в интернет):

- `compose.yaml` без профилей поднимает только базу и сервис; образ Hermes не запрашивается; порт 8765 опубликован только на `127.0.0.1`, порт базы не опубликован;
- `./ops/init-env.sh --auto --mode standalone`, скрытый ввод токена и ключа в настоящем терминале, отказ на неверный вид токена;
- `./ops/up.sh`, `./ops/doctor.sh`, `./ops/backup.sh`, `./ops/import-export.sh` в режиме без Hermes; вывод «пропущено: режим без Hermes»;

- Claude Code 2.1.292: `claude mcp list` показывает `Connected` для архива в Docker с токеном из переменной окружения;
- Codex CLI 0.160.1: `codex mcp add` пишет ожидаемый `config.toml`; при запуске сеанса с верным токеном ошибок связи с архивом нет, с неверным — отказ в доступе;
- переход между режимами в обе стороны на работающем стеке (официальный образ Hermes `v2026.9.24`): контейнер Hermes убирается и возвращается, данные остаются;
- экземпляр с `.env` без строки режима после `./ops/up.sh` работает как раньше, в режиме с Hermes.

- настоящая модель: обращения сервиса по ключу владельца, качество разбора;
- туннель SSH с настоящего компьютера (проверена только сверка имени узла);
- вызов инструментов архива моделью из Codex CLI: на стенде нет доступа к модели;
- Windows на стороне клиента;
- чистый сервер: сборка образа из неизменённого `Dockerfile`, расход памяти без Hermes;
- `./ops/embeddings.sh on` и `./ops/guard.sh on` в этом режиме (проверен только расчёт профилей).
