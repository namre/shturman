# Архитектура

Состояние на версию 0.0.11 (раздел «Открытое ограничение» сверен с кодом 2026-10-19): целевая модель и различие между локальными проверками и проверками владельца — `docs/target-model.md` и `docs/runbooks/validate.md`. Описанное ниже реализовано, кроме помеченного «запланировано». Исторические проверки 0.0.6 не удостоверяют новые пути ответа. Что из написанного проверено и как — `docs/service.md` и `docs/deployment.md`. Версии сторонних компонентов и их поведение сверены с документацией на 2026-10-06, для добавленного в 0.0.4 и позже — на 2026-10-07. Короткая вводная для того, кто проверяет безопасность, — `docs/security-review.md`.

Документ описывает режим установки с Hermes. Второй режим — без Hermes, «только архив и согласования» — `docs/standalone.md`: в нём из схемы ниже остаются сервис переписки и база, а бот и модель у сервиса свои.

## Принципы

0. **Hermes — стоковый.** Его код и образ не меняются, возможности не урезаются. Продукт — расширения Hermes (плагины, скиллы, MCP, настройки) и один сервис рядом. Подробно — `docs/deployment.md`. Сервис работает и без Hermes (решение Р-47).
1. **Один экземпляр — один владелец.** Граница изоляции — сервер. Общей многопользовательской базы нет.
2. **Экземпляр — только клиент.** Наружу он ходит сам (Telegram, провайдер модели, MCP-серверы организации) и не принимает запросов извне, кроме трёх вещей: веб-кабинета за аутентификацией, статических страниц входа и страницы настройки переписки за собственным входом — на отдельном адресе (Р-55, Р-56). Из порта сервиса переписки наружу выходит один префикс, `/shturman-setup/`; внутренний API и архив наружу не выходят. По умолчанию в режиме без Hermes наружу не выходит ничего. Необязательное исключение — внешний архив на чтение на отдельном HTTPS-адресе за OAuth; код реализован в 0.0.7, по умолчанию выключен, живой облачный клиент не принят (`docs/remote-mcp.md`).
3. **Чужой текст — данные.** Входящие сообщения и ответы внешних серверов не исполняются как указания.
4. **Отправку решает не модель.** Агент может только создать черновик. Каждое сообщение, отправляемое сервисом, проходит его шлюз; ручной черновик требует точного подтверждения, разрешённый автоответ — действующей ограниченной политики. Новый источник и раскрытие проверяются независимо. Это правило не охватывает произвольные внешние инструменты полного Hermes. Отправка целиком выключена, пока владелец не включит её на сервере, и без своего бота согласований не включается вовсе (`docs/service.md`, «Отправка выключена»).
5. **Сырьё неизменяемо, знание пересобираемо.** Всё производное можно удалить и построить заново из архива.
6. **Никаких вшитых адресов.** Модель, эмбеддинги, распознавание голосовых и исходящий прокси — настройки экземпляра.

## Почему так разделено

**Настройка переписки — страница сервиса, а не вкладка дашборда.** Вход в аккаунт Telegram, ключи приложения и выбор чатов — то, что ассистенту видеть нельзя: кто видит QR-код входа или облачный пароль, тот получает аккаунт. Дашборд Hermes для этого не годится: он работает в процессе, которым управляет ассистент, и на адресе, где ассистент может исполнять свой код. Поэтому страницу `/shturman-setup/` отдаёт сам сервис переписки, со своим входом по одноразовой ссылке и на отдельном адресе; мастер в дашборде только ведёт на неё и показывает три строки состояния. Через проход дашборда к сервису эти действия недоступны (Р-55, Р-56).

**Первая настройка — бот согласований и один из двух способов подключения.** Бот согласований — первый шаг страницы: без него запросы ассистента на решения владельца отклоняются. Дальше владелец выбирает способ: «Через ваш аккаунт» — свой аккаунт на чтение и выбор чатов; «Через бота и помощника» — бизнес-режим у бота согласований для личных чатов и по желанию аккаунт помощника для групп. Отправка в обоих выключена (Р-62, изменяет Р-58).

**Бизнес-режим — у бота согласований, не у бота Hermes.** У бота один получатель обновлений. У бота Hermes это шлюз Hermes: без дополнительного плагина его ядро принимает сообщения собеседников владельца за команды, а сам бот находится в процессе, где у ассистента есть терминал. Поэтому бота Hermes в бизнес-режиме не подключают, и шага для этого в мастере нет (Р-59). Защита на случай, если его всё же подключили, остаётся: плагин `shturman` перехватывает сообщения бизнес-режима, и до ядра Hermes они не доходят, пока официальный плагин `NousResearch/hermes-telegram-business` не загружен. Экземпляр прежней схемы, где бот Hermes уже подключён и официальный плагин стоит, продолжает работать как работал: плагин `shturman` пересылает бизнес-сообщения в сервис, официальный плагин готовит свои черновики со своими кнопками мимо шлюза отправки сервиса. Скачивание медиа не сделано; голосовые и «кружки» из бизнес-режима для расшифровки сервис скачивает своим ботом согласований, по `file_id` (`docs/voice.md`). `file_id` принадлежит тому боту, который получил сообщение: на экземпляре прежней схемы бизнес-сообщения пришли к боту Hermes, и бот сервиса их файл не скачает — такое голосовое расшифруется, только если подключена сессия того же аккаунта, иначе помечается «пропущено».

**Аккаунты Telegram — отдельный сервис.** Плагины Hermes исполняются в процессе агента без изоляции, а у агента есть терминал. Сессия Telethon даёт полный доступ к аккаунту, поэтому хранится вне процесса агента, в каталоге, который контейнеру Hermes не подключён. Перезапуск и обновление Hermes не рвут сессию.

**Между Hermes и сервисом два пути, у каждого свой токен.** Агент читает архив по MCP (`/mcp`, только чтение). Плагин `shturman` ходит во внутренний API (`/api`): пересылает бизнес-сообщения и нажатия кнопок, забирает задания. Всё, для чего нужны модель или бот, сервис ставит в очередь заданий: спросить модель, написать владельцу, отправить через бизнес-бота. По умолчанию задания выполняет плагин — моделью и ботом Hermes. Перечень заданий — `docs/service.md`. Оба токена считаются известными ассистенту: сервис сам ограничивает, что по ним можно, — раздел «Граница „Штурмана“ вокруг Hermes» ниже (Р-104). У оператора (`shturman call`, скрипты `ops/`) — свой токен, в контейнер Hermes он не передаётся.

**Свой бот согласований — у сервиса, а не у Hermes.** Пока нажатие владельца идёт через плагин, оно проходит через процесс, где у ассистента есть терминал и токен внутреннего API. Поэтому сервису можно дать своего бота: его токен есть только у сервиса, карточки с кнопками уходят через него, нажатия приходят от Telegram напрямую. Тогда сервис перестаёт принимать от плагина привязку владельца, нажатия и бизнес-сообщения, а плагин уходит в спокойный режим. Бизнес-режим Telegram подключается к боту сервиса. Так же сервису можно дать свой доступ к модели. Бот согласований — первый шаг страницы настройки переписки, его заводит владелец; своя модель — по желанию (решения Р-44, Р-62).

**Архив — отдельная база, а не память Hermes.** Хранилище сессий Hermes ищет только по собственным диалогам агента и по умолчанию удаляет завершённые сессии через 90 дней.

## Уровни автономии

| Уровень | Что может ассистент |
|---|---|
| 0. Наблюдатель | Читает, ищет, сводит. Ничего не отправляет |
| 1. Черновики | Готовит сообщения; отправка после «да» владельца |
| 2. Шаблонные действия | Сам отправляет типовые сообщения людям из белого списка |
| 2а. Автоответ доверенным | Сам отвечает людям из списка доверенных; ответ готовится без инструментов |
| 3. Свободная переписка | Ведёт диалог в заданных рамках |

Написаны уровни 0, 1 и ограниченный путь 2а; произвольная свободная переписка уровня 3 не реализована. Для групп — отдельные условия прямого обращения и точной области аккаунта/чата/темы, с независимыми правилами источников и отправки. Без отправки ответы приходят владельцу «Черновиком ответа» (Р-105): отправить его можно только нажатием «Отправить», когда отправка включена и доступен бизнес-бот; режима `prepare_only` больше нет. Правила — `docs/service.md`.

Классификатор и его уведомления помогают заметить подозрительный текст; они не определяют права и не служат границей безопасности. В автоматической задаче ответа модель получает только разрешённый контекст и возвращает предложение: у неё нет терминала и произвольных инструментов. Отдельный сервис проверяет источник, точный запрос, получателя и тему; шлюз отправки заново проверяет текст, права и срок перед доставкой. Поэтому обычный разрешённый ответ может идти по заранее выбранным правилам без нового вопроса владельцу, а чтение нового источника и новое раскрытие требуют соответствующего решения.

Полный штатный Hermes остаётся свободным помощником владельца со своими инструментами и памятью. Его поведение задают правила владельца, настройки и инструкции оператора; сервисные согласования не изолируют эти инструменты автоматически. Чужое письмо или документ может попытаться управлять ими, и этот остаточный риск сохраняется. Владелец задаёт границы работы и расширяет их после проверки конкретного сценария; отключать все инструменты или спрашивать о каждом обычном действии для этого не требуется.

## Модель и вспомогательные сервисы

- По умолчанию модель одна — та, что настроена в Hermes. Все обращения к LLM, включая ночную обработку, идут через Hermes: сервис ставит задание, плагин спрашивает модель. Ключ модели сервису переписки не нужен.
- По желанию у сервиса свой доступ к модели: ключ и имя модели у провайдера с API, совместимым с OpenAI. Тогда свои задания сервис выполняет сам, мимо Hermes. В режиме без Hermes это единственный способ.
- Провайдера выбирает владелец через штатные настройки Hermes. Ключ API и поддерживаемый upstream вход по подписке — разные пути; настоящий вход по подписке, лимиты, обновление входа и фоновые задания проверяются в пилоте отдельно. Сервисный API-ключ не заменяется подпиской автоматически. Фактические версии и границы совместимости — `docs/target-model.md`.
- Эмбеддинги и распознавание речи подписка не покрывает: они считаются локально либо по отдельному ключу API.
- Эмбеддинги — только локальные: модель в отдельном контейнере без выхода в интернет — `intfloat/multilingual-e5-small` по умолчанию или, по выбору владельца, `deepvk/USER2-small` (`docs/search.md`). По умолчанию выключены, включаются командой `./ops/embeddings.sh on`; без них поиск идёт по словам. Наружу уходят только фрагменты, нужные для конкретного ответа, а не весь архив.
- Модель защиты от внедрённых инструкций — тоже локальная: `Horizon-Labs/prompt-injection-guard-small` во втором контейнере без выхода в интернет. По умолчанию выключена, включается командой `./ops/guard.sh on` (`docs/guard.md`).
- Разбор фото и документов — по решению владельца: текст документа сервис достаёт сам, на сервере; фото и сканы смотрит модель обработки (Hermes или своя модель сервиса), то есть они уходят её провайдеру, как и текст сообщений. Выключен по умолчанию, включается владельцем на странице настройки переписки (`docs/media.md`, Р-65).
- Распознавание речи для голосовых и «кружков» — тоже локальное: GigaAM-Multilingual в третьем контейнере (`asr`) без выхода в интернет; звук скачивает сервис тем же путём, каким пришло сообщение, хранится только текст. По умолчанию выключено, включается командой `./ops/asr.sh on` (`docs/voice.md`).
- Фоновые задачи сервиса зарегистрированы в Hermes как вспомогательные задачи: владелец может закрепить за ними дешёвую модель в настройках Hermes, отдельно от интерактивного агента. Со своей моделью сервиса то же делают переменные `SHTURMAN_LLM_MODEL_EXTRACT`, `_REPLY`, `_WATCH`.

## Связь с системами организации

Для задач ответа сервис подключается к заранее настроенному оператором MCP-источнику по публичному HTTPS и вызывает только определённые инструменты поиска/чтения. Авторизация — служебные заголовки в закрытом реестре, автоматического входа по OAuth для источника нет. Согласованный запрос, период и пределы задаются структурированно; credentials не получает модель. Это реализованный посредник, а не готовое подключение любой почты. Подробно — `docs/external-sources.md`. Уведомления в обратную сторону — опросом со стороны экземпляра. A2A не используется: во встроенной реализации Hermes входящая задача попадает в живую сессию со всеми инструментами и памятью.

## Угрозы и меры

| Угроза | Мера |
|---|---|
| Инъекция через входящее сообщение | Сообщения — данные: в ответах архива и инструментов чужой текст вычищен от невидимых символов и стоит в рамке; команды только из управляющего чата; автоответ готовится без инструментов. По желанию — защита от внедрённых инструкций: модель-классификатор скрывает подозрительное сообщение от ассистента до решения владельца; это снижение риска, тихие попытки она пропускает (`docs/guard.md`). Мера неполная — см. «Открытое ограничение» |

## Граница «Штурмана» вокруг Hermes

Решение Р-104 (2026-10-19). Hermes — полноценный личный ассистент владельца: терминал, интернет, память — его зона, их не урезаем. «Штурман» отвечает за свою границу: что он отдаёт ассистенту и что ассистент может изменить. Модель Hermes считается полностью захваченной, а токены из её окружения — доступными программе в её терминале; поэтому все ограничения — на сервере, по токену.

**Что «Штурман» гарантирует** (код — `service/src/shturman/access.py`, `archive_guard.py`; проверки — `tests/test_hermes_access.py`, `tests/test_archive_guard.py`, якоря в `tests/security_mutations.py`):

- по токену внутреннего API, который есть в Hermes, данные и настройки владельца не меняются без его нажатия в боте согласований — ни ослабление, ни ужесточение; управление владельца (уведомления, исключения чатов, согласования, память, правила) этому токену закрыто;
- архив выдаётся порциями: ответ — до 120 сообщений и 100 000 знаков, история — только страницами; на каждый токен — пределы в час и сутки, которые не обходятся параллельными запросами и пачками вызовов; ослабляет их только владелец;
- необычное чтение (объём, много чатов подряд, перебор страницами и датами, исчерпанный предел, ловушка) — одно сообщение владельцу и притормаживание или закрытие выдачи до его решения;
- в ответах ассистенту нет ключей и токенов из текста сообщений, номеров Telegram, служебных путей; нет исключённых чатов, удалённых, служебных и скрытых защитой сообщений; чужой текст — в рамке, которую текст сообщения закрыть не может;
- журнал выдачи без текста и названий; раз в неделю — сводка владельцу сервисом, мимо Hermes.

**Чего «Штурман» не гарантирует.** Hermes владеет всем, что ему уже выдано: с терминалом и интернетом он может переслать это куда угодно — граница ограничивает объём и скорость и сообщает владельцу, но не возвращает выданное. Произвольные инструменты Hermes, его память и бот Hermes сервису не подчинены. Без своего бота согласований сообщение о тревоге доставляет Hermes, кнопок нет, а запросы ассистента на изменения отклоняются. Оператор с правами на сервере (токен оператора, Docker, `.env`) — доверенная сторона; его токен не мерится.

## Почему у страницы настройки свой адрес

Находка независимой проверки безопасности 2026-10-07 (решение Р-56). В первой редакции страница `/shturman-setup/` отдавалась по тому же адресу, что и дашборд Hermes: один блок сайта в прокси, один адрес в настройках сервиса.

**В чём дыра.** Ассистент в Hermes может ставить расширения дашборда — это штатная возможность Hermes, и мы её не урезаем (Р-60). Расширение — это JavaScript, который исполняется в браузере владельца на адресе дашборда. Ассистент читает чужие сообщения; внедрённая в одно из них инструкция может заставить его поставить такое расширение. Браузер считает «своими» друг для друга все страницы с одинаковыми схемой, именем и портом. Поэтому на общем адресе скрипт ассистента мог:

- открыть страницу настройки в скрытой рамке или окне и нажимать на ней от имени вошедшего владельца — включить чтение всех чатов, выпустить ссылку привязки к боту согласований;
- поставить service worker на весь адрес и перехватывать запросы страницы — ключи приложения, облачный пароль Telegram, ссылку для QR-кода входа;
- прочитать cookie сессии страницы, если бы они были доступны скрипту, или просто слать запросы с ними.

Отдельный вход страницы от этого не защищал: вошедший владелец и был целью.

**Что сделано.**

- У страницы свой адрес. По умолчанию — то же имя, порт 8443: для браузера это другой адрес, и ни чтение, ни нажатия, ни service worker с адреса дашборда до неё не дотягиваются. Отдельное имя тоже годится; по умолчанию выбран порт, потому что владелец счёл отдельное имя слишком сложным. Порт владельцу знать не нужно: он переходит по кнопке и по ссылке.
- Сервис сверяет адрес страницы с адресом дашборда и на общем адресе страницу снаружи не отдаёт; `./ops/set-setup-url.sh` такой адрес не записывает; `./ops/doctor.sh` показывает `FAIL setup-origin`, а если прокси всё ещё отдаёт страницу по адресу дашборда — `FAIL setup-isolation`.
- В блоке дашборда образца прокси путь `/shturman-setup*` закрыт отказом.
- Сессия страницы — без cookie (Р-57). Cookie по портам не разделяются: поставленная страницей cookie уходила бы и на порт дашборда, в Hermes, а скрипт дашборда мог бы подложить свою. Ключ сессии лежит в хранилище браузера, которое разделено по адресу вместе с портом, и передаётся заголовком, который ставит только скрипт самой страницы. Сессия живёт ровно 7 дней от входа и продлением не сдвигается.
- Вторая линия — источник запроса. К своему API страница принимает только запросы, которые браузер пометил как её собственные (`Sec-Fetch-Site: same-origin`, `Origin` — её адрес): запрос с соседнего порта того же имени, с чужого сайта и адрес API, набранный в адресной строке, получают отказ даже с верным ключом. Файлы страницы чужому адресу тоже не отдаются, а запрос на установку service worker'а под её путём отклоняется.
- Мастер берёт адрес страницы у сервиса, проверяет его и никогда не строит ссылку на адрес дашборда.
- Из прохода дашборда к сервису убраны вход в аккаунт Telegram, управление аккаунтами, выбор чатов и импорт выгрузки.

**Что осталось.**

- **Подмена.** Скрипт на адресе дашборда не может тронуть настоящую страницу, но может показать владельцу поддельную — похожую страницу в самом дашборде или кнопку, ведущую не туда. Создать ссылку входа он не может, но может её получить, если владелец откроет её не там (следующий пункт); и владелец, который введёт ключи приложения или облачный пароль в поддельную форму, отдаст их. Защита здесь — привычка: настоящая страница открывается по ссылке из `./ops/setup-link.sh`, и её адрес — не адрес дашборда.
- **Ссылка входа, открытая на адресе дашборда.** Значение ссылки стоит в её адресе после знака «#». Если владелец откроет ссылку без порта страницы — то есть на адресе дашборда, — скрипт дашборда прочитает значение, а ассистент из своего терминала войдёт по нему на страницу раньше владельца: по локальному адресу он подделывает любые заголовки. Ссылка из `./ops/setup-link.sh` всегда содержит порт, так что для этого владелец должен набрать адрес сам или убрать порт. Найдено второй внутренней проверкой 2026-10-07, воспроизведено; не закрыто. Признак: настоящая страница при первом открытии отвечает, что ссылка уже использована, — тогда `./ops/logout-all.sh` и новая ссылка. Уведомления о входе владелец получает только при настроенном боте согласований — это первый шаг страницы, но до него уведомлять некому.
- **Общее имя.** Порт разделяет адреса для скриптов и хранилища, но не для всего: cookie у имени общие (поэтому страница ими не пользуется), а менеджер паролей браузера может предлагать сохранённое для этого имени на обоих портах. Паролей страница не заводит.
- **Локальный адрес.** Контейнер Hermes работает в сети хоста и достаёт до `127.0.0.1:8765`, то есть до страницы по локальному адресу. Чужие соединения на петле он не читает (права `CAP_NET_RAW` у него нет), а обратный прокси ходит к сервису не через этот порт, а через Unix-сокет, которого в файловой системе Hermes нет (Р-76). Создать ссылку входа ему нечем: она создаётся только в контейнере сервиса, к Docker у Hermes доступа нет. Но чужую ссылку, попавшую к нему, он по локальному адресу использует (предыдущий пункт). Подбирать ключ сессии в 256 бит бессмысленно.
- **Ассистент по-прежнему держит токен внутреннего API** — об этом следующий раздел. Отдельный адрес закрывает страницу настройки, а не внутренний API.
- **Не проверено на настоящем сервере**: прокси с двумя блоками и настоящим сертификатом, работа за Cloudflare. На стенде под Docker — настоящие Hermes, сервис и Caddy, сертификат прокси внутренний — пройдено: страница открывается по адресу с портом, по адресу дашборда её путь закрыт, скрипт на адресе дашборда не читает ни её API, ни её хранилище, мастер ведёт на адрес с портом, при совпавших адресах сервис страницу снаружи не отдаёт (`docs/deployment.md`). Установка service worker'а с адреса дашборда там не проверялась — она проверена на стенде сервиса без прокси (`service/tests/e2e/README.md`).

## Открытое ограничение: токен внутреннего API доступен агенту

Состояние на 2026-10-19 (версия 0.0.11 и изменения после неё). Плагин `shturman` работает внутри процесса Hermes и держит `SHTURMAN_API_TOKEN`. Hermes передаёт переменные окружения в терминал агента. Агент читает чужие сообщения и имеет терминал, поэтому внедрённая в сообщение инструкция может заставить его обратиться к внутреннему API напрямую, мимо инструментов плагина. Поэтому границу держит сам сервис — по тому, каким токеном пришёл запрос, а не перечни плагина (Р-104).

Токен внутреннего API и заявленный числовой ID пользователя не создают полномочия владельца. Решение устанавливает только проверенное личное сообщение в независимом боте сервиса либо вход на отдельную страницу настройки. Эти полномочия не наследуются фоновой работой. Первичная запись ID владельца старым плагином нужна для запуска и уведомлений; она не даёт права согласовывать действия, менять уже привязанного владельца или разрешать источники.

### Что закрыто кодом

- **Подделка нажатия «Отправить».** Закрыта с Р-44. Со своим ботом согласований сервис не принимает через плагин ни нажатия, ни привязку владельца, ни бизнес-сообщения (`api_core.only_without_own_bot`, отказ `own_bot`): нажатие приходит сервису прямо от Telegram, от привязанного владельца в его личном чате. Без своего бота отправки нет вовсе: она включена, только если в `.env` есть и `SHTURMAN_SENDING=on`, и `SHTURMAN_BOT_TOKEN` (`config.py`). Токен бота, введённый на странице настройки, отправку не включает; через API и со страницы она не включается.
- **Что может токен Hermes.** С Р-104 он открывает только перечень `access.HERMES_ROUTES`: чтение (с пределами выдачи) и изменения, которые всегда ждут нажатия владельца. Правила отправки, список доверенных, автоответ, черновики ответов (бывшая репетиция) и подготовка ответов этому токену закрыты (`403 hermes_forbidden`). `POST /api/outbox/drafts` только создаёт черновик: без нажатия владельца он никуда не уходит. Немедленных ужесточений по этому токену тоже нет — «закрыть», «отменить», «перенести» договорённость ждут карточки.
- **Бизнес-подключение бота Hermes (схема до 0.0.6).** С Д-45 сервис не выбирает его для отправки и задание `business.send` плагину не выдаёт; исполнитель плагина такое задание отклоняет. Отправляет только бот согласований, по своему подключению, проверив перед запросом к Telegram выключатель и «Остановить всё».

### Без своего бота согласований

Архив на чтение и уведомления могут работать без независимого бота. Однако запрос ассистента на расширение прав, принятие защищённого решения или защищённое стирание переписки не применяется: при отсутствии независимого пути подтверждения он отклоняется (`owner_unknown`). Отправка без своего бота выключена независимо от серверного выключателя. Действия самого владельца на странице настройки подтверждаются её отдельным входом.

### Со своим ботом согласований

Запрос ассистента на расширение прав или защищённое изменение создаёт карточку; нажатие приходит сервису непосредственно от текущего привязанного владельца в его личном чате. Команда, которую владелец сам дал этим проверенным путём, уже является решением и не требует второй общей карточки. Чтение и раскрытие источника остаются раздельными; разрешение поиска на 30 дней повторяется только для того же источника, запроса, периода, пределов, получателя и темы.

**Что проверено вживую.** Свой бот согласований работает вживую: владелец получает в нём уведомления (Р-84, Р-93), карточки репетиции и оценивает их, нажимает «Подготовить ответ» (Д-31), разрешает сопровождение кнопкой (Р-100). Вживую не проверен только путь доставки — задание `business.send` от нажатия до сообщения собеседнику: на рабочем экземпляре отправка выключена и бизнес-подключения нет.

### Что остаётся

1. **Без своей модели сервиса.** Задания модели (`llm.*`) выполняет плагин в Hermes — в том числе текст автоответа доверенным. Держатель токена Hermes может подменить итог такого задания. Если включены и автоответ без подготовки, и отправка, подменённый текст уйдёт доверенному собеседнику без нажатия владельца; права и получателя сервис проверяет вне модели, но текст — нет. Этот путь закрывает своя модель сервиса (`SHTURMAN_LLM_API_KEY`, Р-44): тогда задания модели выполняет сервис, и плагину они не выдаются.
2. **Владелец нажимает, не вчитавшись.** Карточку читает человек. Если ассистент попросил расширить свои права или подготовил ответ, а владелец нажал «Да» или «Отправить», не прочитав, действие применится.
3. **Бот Hermes в бизнес-режиме на экземпляре прежней схемы (Р-59).** Агент в Hermes держит токен бота Hermes. Если бизнес-режим подключён к этому боту и у него есть право отвечать, агент может писать через это подключение напрямую через Bot API Telegram, мимо сервиса. Д-45 закрыл путь, на котором сервис сам отдавал согласованный ответ этому боту; прямой путь ограничивает только право «может отвечать» в настройках Telegram Business и отключение бота владельцем. Новым экземплярам бота Hermes в бизнес-режиме не подключают вовсе.
4. **Закрытие выдачи архива и задания модели (Д-54).** Без своей модели сервиса тексты переписки уходят модели ассистента в Hermes заданиями `llm.*` (договорённости, разбор входящих, черновики, страницы памяти, фото, голосовые) — и тогда, когда владелец закрыл ассистенту выдачу архива: граница закрывает только то, что ассистент запрашивает сам. Владелец видит это в сообщении о закрытии и в `./ops/doctor.sh`; отделяет обработку только своя модель сервиса. Останавливать ли обработку при закрытии — решение владельца (`docs/deferred.md`, О-18).
5. **Кто держит токен бота согласований.** После того как владелец подключит этого бота в бизнес-режиме с правом отвечать, держатель токена может писать от имени владельца напрямую через Bot API — мимо сервиса, выключателя и «Остановить всё». Токен есть у сервиса, у администратора сервера (доверенная сторона) и в @BotFather у создателя бота. Если бот создан в одно нажатие через бот-менеджер посредника (Р-77), держатель посредника тоже может в любой момент получить его токен.

### Что из этого следует сейчас

- **отправка выключена** (`SHTURMAN_SENDING=off`). Включить её можно только в `.env` на сервере и только двумя строками вместе: `SHTURMAN_SENDING=on` и `SHTURMAN_BOT_TOKEN` (токен бота, введённый на странице настройки, отправку не включает). Через API и со страницы — нельзя;
- архив на чтение работает и без бота согласований, но бот — первый шаг страницы настройки переписки: независимые согласования и настоящая отправка требуют отдельного бота сервиса. Отсутствие бота не превращает запрос ассистента в согласие владельца;
- свой бот согласований работает вживую; не проверена вживую только доставка `business.send`. Считать ли ограничение снятым и разрешать ли отправку — решает владелец; условие возврата к этому решению — первая доставка, проверенная вживую одним ответом тестовому собеседнику (`docs/deferred.md`, О-7; `docs/runbooks/validate.md`, «Первая настоящая доставка»);
- без своей модели сервиса автоответ доверенным при включённой отправке — путь без нажатия владельца с текстом, который может подменить держатель токена Hermes (п. 1 выше);
- пока отправка выключена, право бота отвечать в Telegram Business стоит держать выключенным (п. 3 и 5 выше);
- перед включением любого уровня выше нулевого владелец должен знать об этом ограничении.

В режиме без Hermes ассистента с терминалом на сервере нет, и токен внутреннего API держит только сам сервис. Но если владелец запускает Codex CLI или Claude Code на том же сервере под тем же пользователем, такой клиент технически может прочитать `.env` — подробно в `docs/standalone.md`, «О чём помнить».
