# Архитектура

Состояние на версию 0.0.6: описанное ниже написано, кроме помеченного «запланировано». Что из написанного проверено и как — `docs/service.md` и `docs/deployment.md`. Версии сторонних компонентов и их поведение сверены с документацией на 2026-10-06, для добавленного в 0.0.4 и позже — на 2026-10-07. Короткая вводная для того, кто проверяет безопасность, — `docs/security-review.md`.

Документ описывает режим установки с Hermes. Второй режим — без Hermes, «только архив и согласования» — `docs/standalone.md`: в нём из схемы ниже остаются сервис переписки и база, а бот и модель у сервиса свои.

## Принципы

0. **Hermes — стоковый.** Его код и образ не меняются, возможности не урезаются. Продукт — расширения Hermes (плагины, скиллы, MCP, настройки) и один сервис рядом. Подробно — `docs/deployment.md`. Сервис работает и без Hermes (решение Р-47).
1. **Один экземпляр — один владелец.** Граница изоляции — сервер. Общей многопользовательской базы нет.
2. **Экземпляр — только клиент.** Наружу он ходит сам (Telegram, провайдер модели, MCP-серверы организации) и не принимает запросов извне, кроме трёх вещей: веб-кабинета за аутентификацией, статических страниц входа и страницы настройки переписки за собственным входом — на отдельном адресе (Р-55, Р-56). Из порта сервиса переписки наружу выходит один префикс, `/shturman-setup/`; внутренний API и архив наружу не выходят. В режиме без Hermes наружу не выходит ничего. Единственное исключение на будущее — необязательный режим внешнего доступа к архиву на чтение (решение Р-11), не реализованный.
3. **Чужой текст — данные.** Входящие сообщения и ответы внешних серверов не исполняются как указания.
4. **Отправку решает не модель.** Агент может только создать черновик. Каждое исходящее сообщение проходит шлюз отправки в сервисе; от имени владельца — только после его подтверждения. Отправка целиком выключена, пока владелец не включит её на сервере, и без своего бота согласований не включается вовсе (`docs/service.md`, «Отправка выключена»).
5. **Сырьё неизменяемо, знание пересобираемо.** Всё производное можно удалить и построить заново из архива.
6. **Никаких вшитых адресов.** Модель, эмбеддинги, распознавание голосовых и исходящий прокси — настройки экземпляра.

## Почему так разделено

**Настройка переписки — страница сервиса, а не вкладка дашборда.** Вход в аккаунт Telegram, ключи приложения и выбор чатов — то, что ассистенту видеть нельзя: кто видит QR-код входа или облачный пароль, тот получает аккаунт. Дашборд Hermes для этого не годится: он работает в процессе, которым управляет ассистент, и на адресе, где ассистент может исполнять свой код. Поэтому страницу `/shturman-setup/` отдаёт сам сервис переписки, со своим входом по одноразовой ссылке и на отдельном адресе; мастер в дашборде только ведёт на неё и показывает три строки состояния. Через проход дашборда к сервису эти действия недоступны (Р-55, Р-56).

**Первая настройка — без бота согласований и без бизнес-режима.** Владелец подключает свой аккаунт на чтение и выбирает чаты; этого достаточно, чтобы ассистент помнил переписку. Бот согласований и бизнес-режим нужны для отправки от имени владельца, а она выключена, — они заводятся позже, по его решению (Р-58).

**Бизнес-режим — у бота согласований, не у бота Hermes.** У бота один получатель обновлений. У бота Hermes это шлюз Hermes: без дополнительного плагина его ядро принимает сообщения собеседников владельца за команды, а сам бот находится в процессе, где у ассистента есть терминал. Поэтому бота Hermes в бизнес-режиме не подключают, и шага для этого в мастере нет (Р-59). Защита на случай, если его всё же подключили, остаётся: плагин `shturman` перехватывает сообщения бизнес-режима, и до ядра Hermes они не доходят, пока официальный плагин `NousResearch/hermes-telegram-business` не загружен. Экземпляр прежней схемы, где бот Hermes уже подключён и официальный плагин стоит, продолжает работать как работал: плагин `shturman` пересылает бизнес-сообщения в сервис, официальный плагин готовит свои черновики со своими кнопками мимо шлюза отправки сервиса. Скачивание медиа и голосовые не сделаны.

**Аккаунты Telegram — отдельный сервис.** Плагины Hermes исполняются в процессе агента без изоляции, а у агента есть терминал. Сессия Telethon даёт полный доступ к аккаунту, поэтому хранится вне процесса агента, в каталоге, который контейнеру Hermes не подключён. Перезапуск и обновление Hermes не рвут сессию.

**Между Hermes и сервисом два пути, у каждого свой токен.** Агент читает архив по MCP (`/mcp`, только чтение). Плагин `shturman` ходит во внутренний API (`/api`): пересылает бизнес-сообщения и нажатия кнопок, забирает задания. Всё, для чего нужны модель или бот, сервис ставит в очередь заданий: спросить модель, написать владельцу, отправить через бизнес-бота. По умолчанию задания выполняет плагин — моделью и ботом Hermes. Перечень заданий — `docs/service.md`.

**Свой бот согласований — у сервиса, а не у Hermes.** Пока нажатие владельца идёт через плагин, оно проходит через процесс, где у ассистента есть терминал и токен внутреннего API. Поэтому сервису можно дать своего бота: его токен есть только у сервиса, карточки с кнопками уходят через него, нажатия приходят от Telegram напрямую. Тогда сервис перестаёт принимать от плагина привязку владельца, нажатия и бизнес-сообщения, а плагин уходит в спокойный режим. Бизнес-режим Telegram подключается к боту сервиса. Так же сервису можно дать свой доступ к модели. Оба — по желанию, по умолчанию выключены и в первую настройку не входят (решения Р-44, Р-58).

**Архив — отдельная база, а не память Hermes.** Хранилище сессий Hermes ищет только по собственным диалогам агента и по умолчанию удаляет завершённые сессии через 90 дней.

## Уровни автономии

| Уровень | Что может ассистент |
|---|---|
| 0. Наблюдатель | Читает, ищет, сводит. Ничего не отправляет |
| 1. Черновики | Готовит сообщения; отправка после «да» владельца |
| 2. Шаблонные действия | Сам отправляет типовые сообщения людям из белого списка |
| 2а. Автоответ доверенным | Сам отвечает людям из списка доверенных; ответ готовится без инструментов |
| 3. Свободная переписка | Ведёт диалог в заданных рамках |

Написаны уровни 0, 1 и 2а; уровни 2 и 3 запланированы. Для бизнес-бота (голос владельца) потолок — уровень 1, а для доверенных — 2а. Правила уровней — `docs/service.md`.

## Модель и вспомогательные сервисы

- По умолчанию модель одна — та, что настроена в Hermes. Все обращения к LLM, включая ночную обработку, идут через Hermes: сервис ставит задание, плагин спрашивает модель. Ключ модели сервису переписки не нужен.
- По желанию у сервиса свой доступ к модели: ключ и имя модели у провайдера с API, совместимым с OpenAI. Тогда свои задания сервис выполняет сам, мимо Hermes. В режиме без Hermes это единственный способ.
- Провайдера выбирает владелец. Ключ API — самый устойчивый вариант для сервера без присмотра. Вход по подписке тоже работает, но у него оконные лимиты, которые фоновые задачи делят с самим владельцем, и при сбое обновления токена нужен ручной повторный вход.
- Эмбеддинги и распознавание речи подписка не покрывает: они считаются локально либо по отдельному ключу API.
- Эмбеддинги — только локальные: модель в отдельном контейнере без выхода в интернет — `intfloat/multilingual-e5-small` по умолчанию или, по выбору владельца, `deepvk/USER2-small` (`docs/search.md`). По умолчанию выключены, включаются командой `./ops/embeddings.sh on`; без них поиск идёт по словам. Наружу уходят только фрагменты, нужные для конкретного ответа, а не весь архив.
- Модель защиты от внедрённых инструкций — тоже локальная: `Horizon-Labs/prompt-injection-guard-small` во втором контейнере без выхода в интернет. По умолчанию выключена, включается командой `./ops/guard.sh on` (`docs/guard.md`).
- Распознавание речи не сделано.
- Фоновые задачи сервиса зарегистрированы в Hermes как вспомогательные задачи: владелец может закрепить за ними дешёвую модель в настройках Hermes, отдельно от интерактивного агента. Со своей моделью сервиса то же делают переменные `SHTURMAN_LLM_MODEL_EXTRACT`, `_REPLY`, `_WATCH`.

## Связь с системами организации

Организация публикует MCP-сервер с узким набором инструментов; экземпляр подключается к нему как клиент по OAuth с минимальными правами. В аргументы инструментов не попадает свободный текст из личной переписки — только структурированные поля. Уведомления в обратную сторону — опросом со стороны экземпляра. A2A не используется: во встроенной реализации Hermes входящая задача попадает в живую сессию со всеми инструментами и памятью.

## Угрозы и меры

| Угроза | Мера |
|---|---|
| Инъекция через входящее сообщение | Сообщения — данные: в ответах архива и инструментов чужой текст вычищен от невидимых символов и стоит в рамке; команды только из управляющего чата; автоответ готовится без инструментов. По желанию — защита от внедрённых инструкций: модель-классификатор скрывает подозрительное сообщение от ассистента до решения владельца; это снижение риска, тихие попытки она пропускает (`docs/guard.md`). Мера неполная — см. «Открытое ограничение» |
| Самовольная отправка | Главный выключатель отправки и суточный потолок задаются только окружением сервиса; агент может лишь создать черновик; ассистент не пишет первым; отправляется только строка черновика, занятая нажатием владельца; лимиты и защита от повторов |
| Подделка нажатия владельца | Плагин передаёт сервису нажатие только от привязанного владельца и только из управляющего чата; в кнопке — номер черновика и случайная метка, текст берётся из базы. Без своего бота мера неполная — см. «Открытое ограничение». Со своим ботом согласований нажатие приходит сервису от Telegram напрямую, маршрут нажатий для плагина закрыт; расширяющие изменения настроек, одобрение обязательств и страниц, запись блока владельца применяются только после нажатия в боте сервиса (`confirm.py`) |
| Отправка от основного аккаунта | Роль «только чтение»: клиент пропускает к Telegram только перечень запросов на чтение; остальные модули клиента не получают |
| Утечка сессии аккаунта | Сессия в каталоге сервиса, который контейнеру Hermes не подключён; сервис работает без лишних прав, база — в закрытой сети |
| Перехват входа в аккаунт Telegram ассистентом | QR-код входа, облачный пароль и ключи приложения вводятся на странице сервиса, а не в дашборде; через проход дашборда к сервису вход в аккаунт, управление аккаунтами и импорт недоступны |
| Скрипт ассистента на адресе дашборда действует на странице настройки | У страницы свой адрес (другой порт или имя): браузер не даёт скрипту с адреса дашборда ни читать её, ни нажимать на ней, ни перехватывать её запросы. Сервис сверяет адреса и на общем адресе страницу не отдаёт; на адресе дашборда прокси отвечает на её путь отказом; сессия страницы без cookie. См. «Почему у страницы настройки свой адрес» |
| Вход на страницу настройки постороннего или ассистента | Ссылку входа создаёт только команда в контейнере сервиса, прямой записью в базу; маршрута для неё во внутреннем API нет. Ссылка одноразовая, 30 минут; вход по ней завершает прежние сессии. Токены внутреннего API и архива входом не служат |
| Страница настройки под подставным именем | Сервис сверяет заголовок `Host` с адресом страницы и локальными именами; на другое имя — отказ |
| Утечка кодов входа и токенов через архив | Служебные чаты Telegram и диалог «Коды подтверждения» в архив не принимаются и агенту не отдаются |
| Утечка архива через эмбеддинги и модель защиты | Оба контейнера не имеют выхода в интернет; модели скачиваются заранее с проверкой контрольных сумм |
| Утечка токена бота согласований и ключа модели сервиса | Оба лежат только у сервиса — в файле значений страницы настройки (`data/shturman/setup/secrets.json`) либо в `.env`; контейнеру Hermes не передаются; вводит их владелец, не агент. Страница обратно значения не отдаёт. Адрес своей модели, введённый на странице, принимается только https и не из внутренних сетей |
| Утечка токена архива при подключении клиента владельца | Настройки клиента ссылаются на переменную окружения; значение владелец забирает сам (`./ops/mcp-token.sh`); архив наружу не публикуется (`docs/standalone.md`) |
| Копии переписки в служебных данных | Содержимое выполненных заданий стирается; текст завершённых черновиков стирается через 30 дней; загруженный экспорт удаляется после перезапуска сервиса и через сутки без использования |
| Отравление памяти | Ответ модели принимается, только если цитата и срок есть в тексте сообщения; новые обязательства и новые страницы — через одобрение владельца; блок владельца на странице код не меняет. Со своим ботом согласований одобрение обязательств и страниц и запись блока владельца через внутренний API применяются только после нажатия в боте сервиса; сообщение, скрытое защитой, в запросы к модели не попадает |
| Подмена зависимостей сервиса | Образ собирается из списка с точными версиями и контрольными суммами |
| Ошибка оператора-агента | Стоп-точки, резервная копия перед изменениями, закреплённые версии (`AGENTS.md`) |
| Блокировка аккаунта Telegram или провайдера | Провайдер сменный; риск описан владельцу до подключения |

## Почему у страницы настройки свой адрес

Находка независимой проверки безопасности 2026-10-07 (решение Р-56). В первой редакции страница `/shturman-setup/` отдавалась по тому же адресу, что и дашборд Hermes: один блок сайта в прокси, один адрес в настройках сервиса.

**В чём дыра.** Ассистент в Hermes может ставить расширения дашборда — это штатная возможность Hermes, и мы её не урезаем (Р-60). Расширение — это JavaScript, который исполняется в браузере владельца на адресе дашборда. Ассистент читает чужие сообщения; внедрённая в одно из них инструкция может заставить его поставить такое расширение. Браузер считает «своими» друг для друга все страницы с одинаковыми схемой, именем и портом. Поэтому на общем адресе скрипт ассистента мог:

- открыть страницу настройки в скрытой рамке или окне и нажимать на ней от имени вошедшего владельца — включить чтение всех чатов, выпустить ссылку привязки к боту согласований;
- поставить service worker на весь адрес и перехватывать запросы страницы — ключи приложения, облачный пароль Telegram, ссылку для QR-кода входа;
- прочитать cookie сессии страницы, если бы они были доступны скрипту, или просто слать запросы с ними.

Отдельный вход страницы от этого не защищал: вошедший владелец и был целью.

**Что сделано.**

- У страницы свой адрес. По умолчанию — то же имя, порт 8443: для браузера это другой адрес, и ни чтение, ни нажатия, ни service worker с адреса дашборда до неё не дотягиваются. Отдельное имя тоже годится; по умолчанию выбран порт, потому что владелец счёл отдельное имя слишком сложным. Порт владельцу знать не нужно: он переходит по кнопке и по ссылке.
- Сервис сверяет адрес страницы с адресом дашборда и на общем адресе страницу снаружи не отдаёт; `./ops/set-setup-url.sh` такой адрес не записывает; `./ops/doctor.sh` показывает `FAIL setup-origin`, а если прокси всё ещё отдаёт страницу по адресу дашборда — `FAIL setup-isolation`.
- В блоке дашборда образца прокси путь `/shturman-setup*` закрыт отказом.
- Сессия страницы — без cookie (Р-57). Cookie по портам не разделяются: поставленная страницей cookie уходила бы и на порт дашборда, в Hermes, а скрипт дашборда мог бы подложить свою. Ключ сессии лежит в хранилище браузера, которое разделено по адресу вместе с портом, и передаётся заголовком, который ставит только скрипт самой страницы. Сессия живёт ровно 7 дней от входа и продлением не сдвигается.
- Вторая линия — источник запроса. К своему API страница принимает только запросы, которые браузер пометил как её собственные (`Sec-Fetch-Site: same-origin`, `Origin` — её адрес): запрос с соседнего порта того же имени, с чужого сайта и адрес API, набранный в адресной строке, получают отказ даже с верным ключом. Файлы страницы чужому адресу тоже не отдаются, а запрос на установку service worker'а под её путём отклоняется.
- Мастер берёт адрес страницы у сервиса, проверяет его и никогда не строит ссылку на адрес дашборда.
- Из прохода дашборда к сервису убраны вход в аккаунт Telegram, управление аккаунтами, выбор чатов и импорт выгрузки.

**Что осталось.**

- **Подмена.** Скрипт на адресе дашборда не может тронуть настоящую страницу, но может показать владельцу поддельную — похожую страницу в самом дашборде или кнопку, ведущую не туда. Одноразовую ссылку входа он при этом не получит, а без неё на настоящую страницу не войти; но владелец, который введёт ключи приложения или облачный пароль в поддельную форму, отдаст их. Защита здесь — привычка: настоящая страница открывается по ссылке из `./ops/setup-link.sh`, и её адрес — не адрес дашборда.
- **Общее имя.** Порт разделяет адреса для скриптов и хранилища, но не для всего: cookie у имени общие (поэтому страница ими не пользуется), а менеджер паролей браузера может предлагать сохранённое для этого имени на обоих портах. Паролей страница не заводит.
- **Локальный адрес.** Контейнер Hermes работает в сети хоста и достаёт до `127.0.0.1:8765`, то есть до страницы по локальному адресу. Войти ему нечем: ссылка входа создаётся только в контейнере сервиса, к Docker у Hermes доступа нет. Подбирать ключ сессии в 256 бит бессмысленно.
- **Ассистент по-прежнему держит токен внутреннего API** — об этом следующий раздел. Отдельный адрес закрывает страницу настройки, а не внутренний API.
- **Не проверено на настоящем сервере**: прокси с двумя блоками и настоящим сертификатом, работа за Cloudflare. На стенде под Docker — настоящие Hermes, сервис и Caddy, сертификат прокси внутренний — пройдено: страница открывается по адресу с портом, по адресу дашборда её путь закрыт, скрипт на адресе дашборда не читает ни её API, ни её хранилище, мастер ведёт на адрес с портом, при совпавших адресах сервис страницу снаружи не отдаёт (`docs/deployment.md`). Установка service worker'а с адреса дашборда там не проверялась — она проверена на стенде сервиса без прокси (`service/tests/e2e/README.md`).

## Открытое ограничение: токен внутреннего API доступен агенту

Плагин `shturman` работает внутри процесса Hermes и держит `SHTURMAN_API_TOKEN`. Hermes передаёт переменные окружения в терминал агента. Агент читает чужие сообщения и имеет терминал, поэтому внедрённая в сообщение инструкция может заставить его обратиться к внутреннему API напрямую, мимо инструментов плагина и их перечня разрешённых адресов.

Что из этого возможно, зависит от того, есть ли у сервиса свой бот согласований. **После первой настройки его нет** — так решено ради простоты (Р-58): действует перечень «Без своего бота». Цена названа прямо: пока бота согласований нет, ассистент под внедрённой инструкцией технически может менять настройки сервиса и то, что лежит в архиве; отправить сообщение он не может.

### Без своего бота — так после первой настройки

Через внутренний API можно:

- прочитать всё, что отдаёт внутренний API;
- исключить чаты и стереть их сообщения;
- записать в архив поддельные сообщения;
- перепривязать владельца;
- изменить лимиты, список доверенных, правила автоответа и наблюдателя;
- включить чтение других чатов уже подключённого аккаунта, поставить аккаунт на паузу, выйти из него;
- подделать нажатие владельца под любой карточкой: принять обязательство, завести страницу, открыть сообщение, скрытое защитой.

Чего так сделать нельзя:

- отправить сообщение: без своего бота отправка не включается при любом значении `SHTURMAN_SENDING`;
- войти в аккаунт владельца без его участия: вход можно начать запросом и получить ссылку для QR-кода, но отсканировать его должен телефон владельца. Остаётся уговорить владельца отсканировать код под чужим предлогом — поэтому настоящий вход идёт только на странице настройки;
- войти на страницу настройки или выпустить ссылку входа на неё: маршрута для этого во внутреннем API нет;
- получить значения, введённые на странице настройки: ключи приложения, токен бота, ключ модели внутренний API не отдаёт.

### Со своим ботом согласований

Нажатие владельца приходит сервису от Telegram напрямую, а токена бота в контейнере Hermes нет. Перечень сокращается. Через внутренний API без нажатия владельца в боте нельзя:

- вернуть исключённый чат и стереть сообщения чата;
- записать в архив выгрузку Telegram (импорт), подключить аккаунт Telegram, снять его с паузы, включить чтение его чатов;
- ослабить правила отправки, разрешить черновики, включить автоответ, изменить его текст представления, добавить доверенного;
- завести или расширить правило наблюдателя;
- одобрить предложенное обязательство, объединить или разделить людей, завести страницу памяти, записать «заметки владельца» на странице;
- перепривязать владельца, подделать нажатие, подложить бизнес-сообщения: эти маршруты со своим ботом закрыты;
- закрыть задание, которое выполняет сам сервис, и тем самым подменить ответ модели или итог отправки;
- прочитать текст сообщения, скрытого защитой, открыть его или выключить защиту.

Что остаётся возможным и со своим ботом:

- прочитать всё, что отдаёт внутренний API: это вся переписка, кроме скрытого защитой;
- ужесточить любую настройку и закрыть доступ: исключить чат, выключить автоответ и правила наблюдателя, убрать доверенных, поставить аккаунт на паузу или выйти из него, отменить ждущее подтверждение, удалить загруженный файл. Это неудобство, а не утечка: владелец должен иметь возможность закрыть доступ сразу, и мы не делаем этот путь медленным;
- добавить алиас уже подтверждённому человеку и менять состояние уже принятых обязательств — этим пользуются инструменты агента;
- засыпать владельца карточками (не больше 20 одновременно) и занять этот предел;
- создать черновик — он уйдёт только после нажатия владельца в боте сервиса;
- если своей модели у сервиса нет — забрать из очереди задание для модели и вернуть вместо её ответа свой. Ответ проходит те же проверки, что и ответ модели, а обязательства и страницы всё равно ждут владельца; текст автоответа доверенным так подменить можно. Своя модель сервиса (`SHTURMAN_LLM_API_KEY`) это закрывает.

### Чего не закрывает ни один из вариантов

Независимо от нашего сервиса агент в Hermes держит токен бота Hermes. Если бизнес-режим подключён к боту Hermes и ему дано право отвечать, агент может пользоваться этим подключением напрямую через Bot API Telegram, мимо сервиса. Ограничивает это только право «может отвечать», которое владелец даёт боту в настройках Telegram Business. Поэтому бота Hermes в бизнес-режиме не подключают вовсе (Р-59): бизнес-режим — только у бота сервиса. На экземпляре прежней схемы, где бот Hermes уже подключён, этот риск остаётся, пока владелец его не отключит.

Карточку подтверждения читает человек. Если ассистент попросил расширить свои права, а владелец нажал «Да», не вчитавшись, действие применится.

### Что из этого следует сейчас

- **отправка остаётся выключенной** (`SHTURMAN_SENDING=off`). Включить её через API нельзя, только в `.env` на сервере, и только при своём боте согласований; токен бота, введённый на странице настройки, отправку не включает — нужна ещё строка в `.env`;
- первая настройка идёт без бота согласований: это осознанный выбор простоты ценой перечня «Без своего бота». Когда владелец решит включать отправку, первым шагом заводится бот согласований — и перечень сокращается до «Со своим ботом»;
- свой бот согласований написан и покрыт тестами с подставным Telegram, но с настоящим ботом не проверен. Считать ли ограничение снятым для экземпляра со своим ботом и для режима без Hermes и разрешать ли там отправку — решает владелец после проверки на живом боте (`docs/decisions.md`, «Открытые вопросы»);
- пока отправка выключена, право бота отвечать в Telegram Business стоит держать выключенным;
- перед включением любого уровня выше нулевого владелец должен знать об этом ограничении.

В режиме без Hermes ассистента с терминалом на сервере нет, и токен внутреннего API держит только сам сервис. Но если владелец запускает Codex CLI или Claude Code на том же сервере под тем же пользователем, такой клиент технически может прочитать `.env` — подробно в `docs/standalone.md`, «О чём помнить».
