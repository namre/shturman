# Решения

Запись добавляется при каждом решении, меняющем конструкцию. Формат: что решено, почему, что из этого следует. Отменённое решение не удаляется, а помечается.

## Р-01. Один экземпляр на владельца, отдельно от любых корпоративных платформ
2026-10-06. **Почему:** переписка владельца не должна зависеть от безопасности общей платформы; экземпляр должен быть пригоден людям вне одной организации. **Следствие:** общей многопользовательской базы нет; изоляция — граница сервера.

## Р-02. С системами организации экземпляр общается по MCP и только как клиент
2026-10-06. **Почему:** нужные операции узкие и типизированные; экземпляр без входящих интерфейсов нельзя опросить снаружи. **Следствие:** A2A и API-сервер Hermes выключены. Пересмотр — если организации понадобится принимать свободные поручения отдельным агентом.

## Р-03. Открытый код, MIT
2026-10-06. **Следствие:** компоненты под AGPL, LGPL, BSL в поставку не включаются без отдельного решения. Форк официального бизнес-плагина ведётся отдельным репозиторием, чтобы изменения можно было предлагать в исходный проект.

## Р-04. Поставка — «свой сервер»; развёртывание и сопровождение ведёт ИИ-агент
2026-10-06. **Почему:** владелец не обязан быть специалистом, но должен оставаться единственным, у кого есть доступ к данным. **Следствие:** правила для агента, runbook-и, скрипты и стартовые промпты — часть продукта и обновляются вместе с кодом. Поддерживаются два режима: агент исполняет на сервере; агент ведёт, человек вставляет команды.

## Р-05. Экземпляр ставится на новый чистый сервер
2026-10-06. **Следствие:** runbook не рассчитан на сосуществование с чужими сервисами; обнаружение посторонних контейнеров — стоп-точка.

## Р-06. Приложение Telegram (api_id) у каждого владельца своё
2026-10-06. **Почему:** блокировка общего приложения остановила бы все экземпляры сразу. **Следствие:** регистрация на my.telegram.org — шаг владельца в мастере подключения.

## Р-07. Модель по умолчанию — собственный доступ владельца к OpenAI
2026-10-06. **Следствие:** доступ настраивается в Hermes штатно — ключом API или входом по подписке (уточнено решением Р-15: все обращения к модели идут через Hermes). Ключ API устойчивее для сервера без присмотра. Провайдер остаётся сменным: OpenAI работает не во всех странах, и потеря аккаунта не должна останавливать экземпляр.

## Р-08. Telegram: бизнес-режим — плагином Hermes, дополнительный аккаунт — отдельным сервисом
2026-10-06. **Почему:** бизнес-обновления приходят в шлюз Hermes; сессия пользовательского аккаунта не должна лежать в процессе агента, где нет изоляции плагинов. Обоснование — `docs/architecture.md`.

## Р-09. Память: архив в Postgres + курируемые страницы Markdown в git
2026-10-06. **Почему:** два разных объёма требуют разных инструментов; файлы читаемы и правимы владельцем, история правок — в git; структурные данные требуют таблиц. **Следствие:** у каждого вида данных один источник истины, синхронизация односторонняя. Обоснование и отвергнутые варианты — `docs/memory.md`.

## Р-10. Эмбеддинги и распознавание голосовых по умолчанию локальные
2026-10-06, предварительно — подтверждается замером на спайке. **Почему:** иначе внешнему провайдеру уходит весь архив целиком. **Следствие:** полный локальный набор требует 8 ГБ памяти. Сервер на 4 ГБ — поддерживаемый вариант: распознавание голосовых остаётся локальным (лёгкий сервер GigaAM укладывается в 0,4–0,8 ГБ), а для эмбеддингов выбирается лёгкая локальная модель либо API — по замеру на проверочном наборе вопросов. Эталонный пилот работает именно на 4 ГБ. Уточнено решением Р-36: модель эмбеддингов выбрана, по умолчанию они выключены; распознавание голосовых ещё не сделано.

## Р-11. Внешний доступ к архиву по MCP — необязательный режим, только чтение, по умолчанию выключен
2026-10-06. **Почему:** владельцу может быть удобно спрашивать свою переписку из стороннего ассистента (например, OpenAI Dots в приложении ChatGPT), а слой данных от движка агента не зависит. **Следствие:** при включении у экземпляра появляется входящий интерфейс за OAuth — это осознанное отступление от Р-02, о котором владелец предупреждается: сторонний ассистент запоминает прочитанное по своим правилам, и удалить это из него выборочно может быть нельзя. Отправка сообщений и черновики через этот интерфейс недоступны.

## Р-12. Размещение сервера выбирает владелец; эталонный экземпляр стоит в стране, где доступны Telegram и провайдер модели
2026-10-06. **Следствие:** исходящий прокси — необязательная настройка, а не часть базовой поставки. Где хранится переписка и что об этом говорит закон страны владельца — его ответственность; README говорит об этом прямо.

## Р-13. Продукт называется «Штурман», репозиторий — `shturman`
2026-10-06. **Почему:** имя объясняет отношения владельца и ассистента — владелец ведёт и решает, ассистент читает дорогу и подсказывает. Это совпадает с главным ограничением продукта: отправку решает владелец. Первая аудитория — русскоязычные руководители, для которых Telegram основной рабочий канал.

## Р-14. Имя и характер ассистента владелец выбирает при первом запуске
2026-10-06. Предлагаются Штурман (по умолчанию), Нестор, Савельич, Бэрримор, Дживс и своё. **Следствие:** характер действует только в разговоре с владельцем; на сообщения третьим лицам, на подпись дополнительного аккаунта, на содержание и на правила не влияет. Подробности — `docs/personas.md`.

## Р-15. Hermes остаётся стоковым; продукт — расширения и один сервис рядом
2026-10-06. **Почему:** владелец не должен терять ничего из того, что умеет Hermes, и должен получать его обновления штатным путём; у кого Hermes уже есть — тот ставит «Штурман» поверх. **Следствие:** своего образа Hermes нет, самообновление не выключается, версия Hermes не привязана к нашему релизу. Совместимость — список проверенных версий и предупреждение перед обновлением. Все обращения к модели идут через Hermes. Кабинет владельца — плагин дашборда, а не отдельное приложение. Подробно — `docs/deployment.md`. Уточнено решениями Р-44 и Р-47: по желанию владельца у сервиса свой доступ к модели, а сервис можно поставить и без Hermes.

## Р-16. Эталонное развёртывание — Compose с официальным образом Hermes
2026-10-06. **Почему:** одна команда поднимает всё; состояние описано в одном файле, который ИИ-оператор может прочитать, применить повторно и откатить; терминал агента ограничен контейнером без наших правок. **Следствие:** установка Hermes прямо в систему поддерживается как вариант «пристройка», но эталоном не является.

## Р-17. Токены, ключи и базовая настройка — через веб-интерфейс, а не через терминал
2026-10-06. **Почему:** владелец далёк от ИТ; секреты не должны проходить через ИИ-агента. **Следствие:** ключ модели, вход по подписке и токен бота вводятся в стоковом дашборде Hermes; вход в дополнительный аккаунт, загрузка экспорта и правила — во вкладке «Штурман»; агент ставит несекретное и проверяет по статусам. Первый вход в дашборд — через единый вход перед прокси либо по одноразовой ссылке. Терминальный ввод остаётся запасным путём. Подробно — `docs/setup.md`. В версии 0.0.3 экранов для аккаунтов, экспорта и правил ещё нет: эти действия временно идут запасным путём. Уточнено решениями Р-44 и Р-47: токен бота согласований и ключ модели сервиса вводятся в терминале скрытым вводом — веб-интерфейса для них нет.

## Р-18. Готовое берём только под разрешительными лицензиями
2026-10-06. **Следствие:** проекты под AGPL, GPL и без лицензии — источник идей, не кода. Разбор по частям решения — `docs/reuse.md`.

## Р-19. Основной аккаунт можно подключить через сессию — только на чтение, необязательным режимом
2026-10-06. **Почему:** бизнес-бот не видит группы и прошлое; сессия основного аккаунта даёт и то и другое без выгрузки. **Следствие:** пути отправки для этой роли в сервисе нет вообще; от имени владельца пишет только бизнес-бот. Режим выключен по умолчанию и включается с предупреждением о риске для основного аккаунта.

## Р-20. Автоответ доверенным собеседникам — отдельный уровень автономии
2026-10-06. **Почему:** владельцу нужен ответ близкому кругу без подтверждения каждого сообщения. **Следствие:** уровень 2а: список доверенных по числовым идентификаторам, ограниченный набор инструментов без терминала и файлов, паузы и дневной лимит. Остальным сервис не отвечает. Подробно — `docs/service.md`. Уточнено решением Р-31: ответ готовится вообще без инструментов.

## Р-21. Наблюдатель групп — часть продукта
2026-10-06. Ключевые слова → дешёвая модель → уведомление владельцу; в группе сервис не пишет и прочитанным её не отмечает.

## Р-22. Сервис переписки пишется на Python с asyncpg
2026-10-06. **Почему:** Telethon работает на asyncio; `asyncpg` под Apache-2.0, тогда как `psycopg` — под LGPL. **Следствие:** работа с базой асинхронная, миграции — пронумерованные SQL-файлы без отдельного инструмента.

## Р-23. Вход в дашборд — свой способ входа Hermes: ссылка активации и код от собственного бота
2026-10-06. **Почему:** владелец далёк от ИТ, паролей и терминала у него быть не должно; при этом Hermes с внешним адресом обязан иметь вход, а его встроенный парольный вход требует задать хеш пароля на сервере. **Следствие:** плагин `shturman` регистрирует способ входа штатным механизмом Hermes. Первый вход — по одноразовой ссылке, которую выдаёт `ops/activation-link.sh`; дальше — по коду из восьми цифр, который бот владельца присылает по кнопке на странице входа. Почты в первой версии нет: для неё нужен почтовый сервер. Отдельной программы для входа нет; страницы входа — статические файлы, которые отдаёт обратный прокси. Подробно — `docs/setup.md`.

## Р-24. Ссылку активации агент видит и передаёт владельцу
2026-10-06. **Почему:** другого канала от сервера к владельцу до настройки бота нет. **Следствие:** это единственное исключение из правила «секреты не проходят через агента». Ссылка одноразовая, живёт 30 минут, отменяется выдачей новой; значение стоит после `#` и в журналы прокси не попадает; агенту запрещено её сохранять. Та же команда выдаёт ссылку восстановления, если Telegram владельца потерян или захвачен: доступ к серверу считается доказательством владения, вход по такой ссылке отвязывает прежний аккаунт и завершает все сессии.

## Р-25. Владелец привязывается к боту кнопкой «Запустить», а не вводом своего Telegram ID
2026-10-06. **Почему:** числовой идентификатор владелец не знает; стоковая привязка Hermes отвечает по-английски и просит выполнить команду в терминале. **Следствие:** мастер выдаёт ссылку `t.me/<бот>?start=<значение>`; обработчик плагина в процессе шлюза запоминает отправителя как кандидата; владельцем он становится только после подтверждения в мастере, то есть из уже выполненного входа. Затем мастер штатными вызовами задаёт `TELEGRAM_ALLOWED_USERS` и `TELEGRAM_HOME_CHANNEL`. Обработчик активен только пока мастер ждёт сообщения.

## Р-26. Мастер настройки — вкладка дашборда Hermes, секреты идут в штатные вызовы Hermes
2026-10-06. **Почему:** так ключ модели и токен бота не проходят через наш код и не хранятся у нас; у плагина нет способа скрыть меню дашборда, а отдельная страница потребовала бы своего сервера с доступом к секретам. **Следствие:** серверная часть плагина хранит только выбор помощника, отметки шагов и состояние привязки. Исключение: токен бота один раз проходит через плагин, чтобы спросить у Telegram имя бота до сохранения; плагин его не записывает.

## Р-27. Плагин `shturman` перехватывает сообщения бизнес-режима, пока не включён плагин бизнес-режима
2026-10-06. **Почему:** порядок «сначала плагин, потом подключение бота» зависит от действий человека в Telegram, которые мы не контролируем; без плагина ядро Hermes отвечает собеседникам владельца (issue NousResearch/hermes-agent #127430). **Следствие:** защита не зависит от того, в каком порядке владелец выполнил шаги, и от того, поднялся ли плагин бизнес-режима: она снимается только когда Hermes сообщает, что он загружен без ошибки. Плагин бизнес-режима ставится из официального репозитория по SHA `98c60afc00d36c885bb040ebe973b1aa908886c0` (вершина `main` на 2026-10-06, включает исправление безопасности от 2026-08-15).

## Р-28. Плагин не привозит своих зависимостей
2026-10-06. **Почему:** `python-telegram-bot` распространяется под LGPL-3.0, в поставку мы такие компоненты не включаем (Р-18). **Следствие:** плагин пользуется библиотеками, которые уже есть в окружении Hermes (FastAPI, python-telegram-bot), и импортирует их только там, где они нужны. Логика плагина (`shturman_core/`) написана на стандартной библиотеке Python и проверяется без Hermes.

## Р-29. У сервиса переписки нет доступа к модели и к боту: задания выполняет плагин
2026-10-06. **Почему:** модель и бот есть только у Hermes (Р-15); второй ключ модели и второй получатель обновлений бота сервису давать нельзя. **Следствие:** всё, для чего нужна модель, сообщение владельцу или отправка через бизнес-бота, сервис ставит в очередь заданий в базе. Плагин `shturman` забирает задание, выполняет и возвращает итог. Видов заданий пять: `llm.structured`, `llm.text`, `notify.owner`, `notify.edit`, `business.send`; зачем они нужны, плагин не знает. Отправка через бизнес-бота не повторяется никогда: исход либо «ушло», либо «точно не ушло», либо «неизвестно». Уточнено решением Р-44: это поведение по умолчанию; по желанию владельца задания бота и модели сервис выполняет сам.

## Р-30. Сервис — один процесс и один порт, два разных токена
2026-10-06. **Почему:** сессией Telegram может владеть только один процесс; один порт на локальном адресе проще закрыть и проверить. **Следствие:** `shturman serve` отдаёт `/health`, внутренний API `/api/*` для плагина (токен `SHTURMAN_API_TOKEN`) и архив `/mcp` для агента (токен `SHTURMAN_MCP_TOKEN`, только чтение). Токены не взаимозаменяемы; сервис не запускается, если они совпали. У внутреннего API токен один на всё, поэтому границу между «мостом», инструментами агента и страницами владельца держит плагин — перечнями разрешённых адресов. От агента с терминалом эта граница не защищает (Р-42).

## Р-31. Агент может только создать черновик; автоответ готовится без инструментов
2026-10-06. **Почему:** отправку решает не модель (принцип 4 архитектуры); сообщение собеседника, даже доверенного, — чужой текст. **Следствие:** инструмент агента создаёт черновик, сервис показывает его владельцу карточкой с кнопками, отправляется ровно согласованный текст. Правила отправки, список доверенных, автоответ, правила наблюдателя, исключения чатов и аккаунты через инструменты агента недоступны. Для автоответа доверенным сервис сам собирает справку из архива и просит у модели только текст; из других чатов в справку попадают лишь собственные слова владельца. Уточняет Р-20.

## Р-32. Отправка включается только из окружения сервиса; жёсткий суточный потолок; ассистент не пишет первым
2026-10-06. **Почему:** тот, кто завладел токеном внутреннего API, не должен иметь возможности включить отправку или снять лимиты. **Следствие:** `SHTURMAN_SENDING` (по умолчанию `off`) и `SHTURMAN_SEND_DAILY_CAP` (по умолчанию 50 на аккаунт в сутки) читаются только из окружения, на сервере — из `.env`; в API нет вызова, который их меняет. Пока отправка выключена, сервис не отправляет ничего ни одним каналом и не создаёт черновиков. Черновик возможен только в чат, где уже есть исходящее сообщение владельца или помощника, либо как ответ через бизнес-бота на свежее входящее; через API это правило не выключается.

## Р-33. Из аккаунта читаются только выбранные владельцем чаты; глубина истории по умолчанию — 12 месяцев
2026-10-06. **Почему:** вход в аккаунт не должен означать «забрать всё»; чем меньше запросов истории, тем меньше риск ограничений со стороны Telegram и тем меньше чужих данных на сервере. **Следствие:** после входа ничего не читается, пока владелец не включил чаты — поштучно или по видам. Для включаемого чата история загружается на 12 месяцев вглубь; глубину можно изменить для аккаунта или задать для отдельного включения, в том числе «вся история».

## Р-34. Аккаунт владельца не может быть помощником; вход помощника — только когда владелец известен
2026-10-06. **Почему:** помощнику разрешена отправка, основному аккаунту — нет (Р-19). Перепутать роли значит получить отправку с основного аккаунта. **Следствие:** вход помощника не начинается, пока бот не привязан к владельцу в мастере и в архиве нет основного аккаунта. После входа и при каждом запуске сессии аккаунт сверяется с владельцем; при совпадении сессия завершается. Если владельцем становится аккаунт, уже подключённый как помощник, сессия останавливается, владелец получает уведомление.

## Р-35. Служебные чаты Telegram и диалог «Коды подтверждения» исключены всегда
2026-10-06. **Почему:** в них лежат коды входа и токены ботов; попав в архив, они стали бы доступны агенту. **Следствие:** уведомления Telegram (777000), @BotFather и @SpamBot не принимаются в архив ни из одного источника, не отдаются агенту, и вернуть их в архив нельзя. Диалог «Коды подтверждения» исключается по типу чата экспорта. Каким идентификатором этот диалог представлен в живых источниках, проверить не удалось — открытый вопрос.

## Р-36. Эмбеддинги: `multilingual-e5-small`, по умолчанию выключены, контейнер без интернета
2026-10-06. **Почему:** эталонный сервер — 4 ГБ памяти; веса `bge-m3` занимают 2,27 ГБ и рядом с Hermes и базой не помещаются. **Следствие:** модель `intfloat/multilingual-e5-small` на сервере TEI; столбец вектора — `halfvec(384)`: вектор и индекс вдвое меньше. Модель другой размерности требует новой миграции. Эмбеддинги включает владелец командой `./ops/embeddings.sh on`; без них поиск идёт по словам. Через контейнер проходит текст всех сообщений, поэтому выхода в интернет у него нет: модель заранее скачивает и сверяет по контрольным суммам тот же скрипт. Переранжирования нет. Качество измерено только на маленьком синтетическом наборе. Уточняет Р-10. Подтверждено решением Р-50: замена на EmbeddingGemma 2 измерена и отклонена. Уточнено решением Р-51: появилась вторая поддерживаемая модель, `deepvk/USER2-small`; `multilingual-e5-small` остаётся моделью по умолчанию.

## Р-37. Дату срока считает код; обязательства становятся предложениями, которые принимает владелец
2026-10-06. **Почему:** модель ошибается в датах, а ошибка в сроке хуже его отсутствия. **Следствие:** модель копирует формулировку срока дословно, дату от времени сообщения в поясе владельца считает разборщик; формулировка, которой нет в исходном тексте, отбрасывается; если она не сводится к одной дате — «нужно уточнение». На нашей таблице из 38 формулировок разборщик даёт 38 верных ответов и ни одной неверной даты. Каждое найденное обязательство — предложение: владелец получает сводку с кнопками и принимает или отклоняет; оставленное без ответа предложение устаревает.

## Р-38. Страницы памяти — файлы и git в каталоге данных сервиса; первая версия — только люди
2026-10-06. **Почему:** страницы собираются из архива и обязательств, которыми владеет сервис; каталог сервиса контейнеру Hermes не подключён, и агент читает страницы только через инструменты архива. **Следствие:** страницы лежат в `data/shturman/pages`, история — локальный репозиторий git без внешних адресов. Первая версия ведёт только страницы людей. Страница заводится без вопроса только для человека, которого владелец подтвердил; об остальных владельцу уходит предложение с кнопками. Блок владельца код не меняет никогда. Встроенный скилл Hermes `llm-wiki` не используется. Уточняет Р-09.

## Р-39. Зависимости образа сервиса ставятся из списка с контрольными суммами
2026-10-06. **Почему:** сервис держит сессии Telegram и всю переписку; подменённый пакет при сборке получил бы всё это. **Следствие:** `service/requirements.lock` содержит точные версии и суммы всех пакетов, включая транзитивные; образ ставит их с проверкой сумм, а сам сервис — поверх, без подтягивания чего-либо ещё. Базовый образ назван по точной версии. Обновление списка — отдельным изменением.

## Р-40. Содержимое заданий стирается после выполнения; невостребованные задания закрываются
2026-10-06. **Почему:** в задании лежат копии текста сообщений; иначе они пережили бы удаление сообщения и исключение чата. **Следствие:** через десять минут после закрытия задания его содержимое и результат стираются; строка остаётся — она защищает от повторной постановки. Задание, которое исполнитель не забрал за отведённый срок (от часа до суток по виду), закрывается как неудачное. Текст завершённых черновиков стирается через 30 дней.

## Р-41. MCP-сервер архива — на официальном SDK 2.x, класс `MCPServer`
2026-10-06. **Почему:** в SDK 2.x класса FastMCP больше нет; Hermes 0.21.5 поставляется с клиентом 2.0.0. **Следствие:** транспорт — streamable HTTP без состояния, только запросы POST, ответы в JSON; заголовки `Host` и `Origin` сверяются всегда. Проверено с SDK 2.3.0 и клиентом 2.0.0.

## Р-42. Отправка остаётся выключенной, пока согласование идёт через плагин в Hermes
2026-10-06. **Почему:** плагин держит токен внутреннего API в процессе Hermes, а Hermes передаёт окружение в терминал агента. Агент, которому внедрили инструкцию, может обратиться к API напрямую и, если отправка включена, подделать нажатие владельца. **Следствие:** `SHTURMAN_SENDING` остаётся `off`; право бота отвечать в Telegram Business рекомендуется держать выключенным. Полное описание — `docs/architecture.md`, «Открытое ограничение». Исправление — отдельный бот согласований, которым владеет сервис; решение о нём за владельцем (открытые вопросы). Уточнено решением Р-44: бот согласований сделан; без него отправка не включается вовсе. Отправка остаётся выключенной и с ним — до проверки на настоящем боте и решения владельца.

## Р-43. В образе сервиса есть программа git
2026-10-06. История страниц памяти ведётся программой git (GPL-2.0), установленной в образ сервиса из пакетов Debian. **Почему это не нарушает Р-18:** git вызывается как отдельная программа, его код в поставку не включается и с кодом сервиса не связывается; в репозитории его нет. Без git страницы собираются, но без истории правок.

## Р-44. У сервиса может быть свой бот согласований и свой доступ к модели; при своём боте маршруты плагина закрыты
2026-10-07. **Почему:** пока нажатие владельца идёт через плагин, оно проходит через процесс, где у ассистента есть терминал и токен внутреннего API, и его можно подделать (Р-42). **Следствие:** `SHTURMAN_BOT_TOKEN` включает бота, токен которого есть только в контейнере сервиса: карточки уходят через него, нажатия приходят от Telegram напрямую, владелец привязывается одноразовой ссылкой (`./ops/bot-bind.sh`); код привязки пишется прямо в базу, маршрута для него в API нет. `SHTURMAN_LLM_API_KEY` и `SHTURMAN_LLM_MODEL` дают сервису свой доступ к модели. Со своим ботом сервис отказывает плагину кодом `own_bot` в привязке владельца, нажатиях и приёме бизнес-сообщений; задания своего исполнителя плагину не выдаются и по HTTP не закрываются; бизнес-режим подключается к боту сервиса. Плагин в ответ уходит в спокойный режим. Без своего бота `SHTURMAN_SENDING` не действует. Всё это по желанию и по умолчанию выключено. Клиент Bot API написан на httpx: `python-telegram-bot` под LGPL в образ сервиса не входит (Р-28). С настоящим ботом не проверено. Уточняет Р-15, Р-17, Р-29, Р-42.

## Р-45. Действия, расширяющие права ассистента, подтверждает владелец: ослабление ждёт, ужесточение применяется сразу
2026-10-07. **Почему:** токен внутреннего API доступен ассистенту в Hermes (Р-42); закрыть нажатия мало, если тем же токеном можно добавить доверенного или вернуть исключённый чат. **Следствие:** при своём боте (Р-44) изменения, которые расширяют то, что ассистент читает, помнит или может отправить, и необратимые стирания по HTTP не применяются: маршрут отвечает 202, владелец решает кнопкой в боте сервиса, на решение час. Что считать ослаблением, решается по значению, а не по названию настройки. Ужесточения — исключить чат, выключить автоответ, убрать доверенного, поставить аккаунт на паузу — применяются сразу: владелец должен мочь закрыть доступ немедленно, даже когда бот недоступен. Цена: держатель токена может ужесточать настройки и отменять ждущие карточки — это неудобство, а не утечка. Подтвердить действие по HTTP нельзя. Без своего бота всё применяется сразу, как раньше: подтверждение через Hermes было бы видимостью. Перечень — `docs/service.md`.

## Р-46. Защита от внедрённых инструкций — одна точка проверки на входе в архив; модель `Horizon-Labs/prompt-injection-guard-small`
2026-10-07. **Почему:** три рубежа (вход, перед обработкой, выход) и отдельный экран — три места, где можно ошибиться; одна проверка при записи сообщения и один признак видимости, который учитывают все пути чтения, проще проверить тестами. **Следствие:** столбец `messages.agent_visible`; сообщение живого потока пишется скрытым и проверяется до того, как о нём узнают остальные модули; импорт и догрузка истории проверяются фоном. Модель — `Horizon-Labs/prompt-injection-guard-small`, ревизия `3215a27` (Apache-2.0 по карточке), во втором экземпляре TEI, по образцу эмбеддингов (Р-36): torch и transformers в образ сервиса не добавляются. Выбрана измерением на синтетическом русском наборе: `protectai/deberta-v3-base-prompt-injection-v2` даёт на русском 21–24 % ложных срабатываний, модели Meta Prompt Guard закрыты условиями доступа и лицензией. Порог 0,9: ложно скрытое сообщение ассистент не видит до решения владельца, поэтому выбран осторожный порог ценой полноты. При недоступной модели сообщения видны и считаются непроверенными: остановка модели не должна останавливать ассистента. Правила — второй оценщик и запасной вариант; защитой не считаются (19 % полноты на независимом наборе). Текст скрытого сообщения через внутренний API не отдаётся, выключателя защиты в API нет. По умолчанию выключена. Это снижение риска, а не гарантия; числа — `docs/guard.md`.

## Р-47. Второй режим установки — без Hermes: «только архив и согласования»
2026-10-07. **Почему:** владельцу может быть нужен архив с поиском и обязательствами без ассистента в Telegram; вопросы он задаёт из своего Codex CLI или Claude Code. **Следствие:** режим — `SHTURMAN_MODE` в `.env`, по умолчанию `hermes`; контейнер Hermes — в профиле Compose. В режиме без Hermes у сервиса свой бот согласований и свой доступ к модели (Р-44); разговора с ассистентом, сводок, памяти разговора, веб-мастера и готовых черновиков нет. Секреты в этом режиме вводятся в терминале скрытым вводом. Экземпляр наружу не публикует ничего. Под Docker запускался на стенде; с настоящим ботом и моделью не проверен. Уточняет Р-15, Р-16, Р-17, Р-29. Уточнено решениями Р-52 (готовых черновиков в этом режиме нет и не будет) и Р-53 (вариант установки владелец выбирает явно, вариантов два).

Архив наружу не публикуется: с компьютера владельца — через туннель SSH на порт 8765. Облачные клиенты (Р-11) не поддержаны.

Копия и раньше содержала ключи, сессии и переписку: агент её не открывает и никуда не передаёт. Подтверждено владельцем 2026-10-07.

## Р-50. EmbeddingGemma 2 не берём; модель эмбеддингов по умолчанию остаётся `multilingual-e5-small`
2026-10-07. **Почему:** измерено в день после выхода модели (`google/embeddinggemma-2`, Apache-2.0). TEI 1.9.4, на котором стоит наша упаковка, её не запускает, а версии TEI новее нет: понадобился бы второй сервер (llama.cpp) и второй протокол в клиенте. На нашем синтетическом наборе коротких сообщений она заметно лучше `e5-small` (полнота в первых десяти 0,59 против 0,34), но не лучше `e5-base` (0,59) и хуже `deepvk/USER2-base` (0,66). Вернуться к вопросу, если TEI научится запускать эту модель или понадобится поиск по картинкам и голосовым. Найден кандидат на вторую поддерживаемую модель в рамках нынешней упаковки — `deepvk/USER2-small` (Apache-2.0, 384 измерения, работает в TEI 1.9.4 с ограничением размера пачки); на том же наборе полнота 0,55, на стандартных русских наборах он слабее `e5-small`. На дату записи это не было реализовано; сделано решением Р-51. Оговорка: набор синтетический и написан одним автором, 165 вопросов дают разброс около ±8 процентных пунктов; на настоящей переписке не измерялось.

## Р-51. Вторая поддерживаемая модель поиска по смыслу — `deepvk/USER2-small`; по умолчанию остаётся `multilingual-e5-small`
2026-10-07, решение владельца. **Почему:** на нашем синтетическом наборе коротких русских сообщений `USER2-small` находит заметно больше (полнота в первых десяти 0,55 против 0,35 у `e5-small`, разброс ±8 процентных пунктов), занимает впятеро меньше памяти и укладывается в ту же упаковку: TEI 1.9.4, 384 измерения, столбец `halfvec(384)` не меняется, лицензия Apache-2.0. По умолчанию её не ставим: на энциклопедических наборах она слабее (RuBQ 0,75 против 0,80, MIRACL-ru 0,83 против 0,91), длинный текст среди коротких сообщений находит заметно хуже (0,21 против 0,54), язык один, а на настоящей переписке не измерялась ни одна из двух. **Следствие:** модель выбирает владелец — `./ops/embeddings.sh on --model e5-small|user2-small`; включение и смена модели — стоп-точки. Скрипт скачивает модель по закреплённой ревизии с проверкой сумм всех файлов в отдельный каталог; экземпляру, развёрнутому раньше, править `.env` не нужно. Контейнер запускается с `--max-batch-tokens 2048` для обеих моделей: без этого `USER2-small` не запускается в отведённой памяти. Смена модели — полный пересчёт векторов (около трёх часов на 300 000 сообщений по пересчёту со стенда); прежние векторы рядом не хранятся, возврат — такой же пересчёт. Векторы двух моделей в выдаче не смешиваются: до конца пересчёта поиск по смыслу видит только уже пересчитанные сообщения, поиск по словам — весь архив. Прежние векторы не стираются, пока контейнер не подтвердил новую модель. Набор и скрипт измерения — в репозитории; числа, оговорки и то, чего не проверено, — `docs/search.md`. Уточняет Р-36 и Р-50.

## Р-52. Режим без Hermes остаётся «архив и обязательства»: черновики ответов сервис сам не готовит
2026-10-07, решение владельца. **Почему:** черновик ответа — работа ассистента, у которого есть разговор с владельцем, его правила и память; сервис без Hermes — архив с поиском, обязательствами и согласованиями. Отдельный «составитель ответов» внутри сервиса был бы вторым ассистентом без этих опор. **Следствие:** вопрос закрыт, функция не запланирована. Сервис сам пишет текст только для автоответа доверенным (Р-20, Р-31), как и раньше. Кому нужны черновики ответов — ставит вариант с Hermes. Уточняет Р-47.

## Р-53. При установке владелец выбирает из двух вариантов; ассистент на Codex CLI или Claude Code вместо Hermes — рассмотрено и отклонено
2026-10-07, решение владельца. Варианты: «Ассистент в Telegram (Hermes)» и «Только архив и согласования». **Следствие:** выбор задаётся владельцу простыми словами до первого шага установки: в стартовых промптах, в runbook-ах, в `README.md` и в самом `./ops/init-env.sh` — без ключа `--mode` на новой установке он спрашивает сам, а с `--auto` останавливается и просит назвать вариант. Агент не выбирает за владельца и не считает выбором то, какой промпт ему дали. **Третий вариант — ассистент в Telegram на Codex CLI или Claude Code — не делаем.** Почему: эти программы не рассчитаны на работу постоянным ассистентом — это сеансы за терминалом, а не служба, которая неделями принимает сообщения; вход в них по подписке на сервере без присмотра ненадёжен и требует провести учётные данные владельца через сервер; между ними и Telegram пришлось бы писать и сопровождать собственную прослойку — по сути второй Hermes. Обе программы остаются тем, чем они в продукте уже служат: оператором установки и клиентом архива в варианте без Hermes (Р-48). Уточняет Р-47.

## Открытые вопросы

- Язык документации: сейчас русский; нужен ли английский как основной для сообщества Hermes.
- **Считать ли «Открытое ограничение» снятым и разрешать ли отправку** — отдельно для режима без Hermes и для Hermes со своим ботом согласований (Р-42, Р-44, Р-45). Свой бот закрывает подделку нажатия; что остаётся — `docs/architecture.md`. До проверки на настоящем боте и решения владельца отправка выключена везде.
- **Публикация `/mcp` наружу для ChatGPT и других облачных клиентов** (Р-11). Нужны OAuth, которого в сервисе нет, публичный адрес с TLS и защита от перебора; меняет правило «экземпляр ничего не публикует наружу». Делать ли и когда — не решено. Что потребуется — `docs/standalone.md`.
- **Клиент владельца на том же сервере.** Запущенный под тем же пользователем, что и стек, он может прочитать `.env` и управлять Docker. Рекомендовать только вариант с компьютером владельца или заводить отдельного пользователя ОС — не решено.
- **Проверка ключа модели сервиса** сейчас происходит только при ночной обработке; нужна ли команда немедленной проверки.
- **Вопросы `./ops/init-env.sh` в режиме с Hermes.** Скрипт спрашивает токен бота согласований, ключ, имя и адрес модели сервиса и там, где они не обязательны. Оставить или скрыть — не решено.
- **Требования к серверу без Hermes.** `./ops/preflight.sh` проверяет те же 4 ГБ памяти; расход без Hermes не измерен.
- **Отложенная отвязка владельца при своём боте.** Если владелец вошёл в дашборд по ссылке восстановления, пока плагин в спокойном режиме, запрос «отвязать владельца» уйдёт сервису только после выключения своего бота — возможно, через недели — и тогда очистит доверенных и ждущие черновики.
- **Тихое уведомление владельцу об ужесточениях**, сделанных через внутренний API: выключение правила наблюдателя сейчас не сообщается никак.
- **Две системы черновиков.** Официальный плагин бизнес-режима готовит собственные черновики со своими кнопками, мимо шлюза отправки сервиса. Оставить обе, выключить черновики официального плагина или вести свой форк — не решено.
- **Совпадают ли идентификаторы сообщений в бизнес-потоке и в экспорте.** От этого зависит обещание «без дублей» для пары «бизнес-бот и экспорт». Проверяется только на настоящем аккаунте.
- **Идентификатор диалога «Коды подтверждения» в живых источниках** (Р-35).
- **Качество на настоящей модели**: извлечение обязательств, сводки страниц, текст автоответа, два скилла. Проверочного набора вопросов ещё нет.
- **Какая из двух моделей поиска по смыслу лучше на настоящей переписке** (Р-51). Измерено только на синтетическом наборе; менять ли модель по умолчанию — после проверки на вопросах владельца.
- Вход по почте: нужен ли, и чей почтовый сервер для него использовать.
- Как Telegram сейчас называет пункты бизнес-режима (Business Mode или Secretary Mode, «Чат-боты» или Chat Automation) — уточнить на живом боте и поправить подсказки мастера.
- Официальный поток «вход по подписке ChatGPT» в Hermes ещё не слит (PR NousResearch/hermes-agent #128926) — вернуться после слияния.
