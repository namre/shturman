# Решения

Запись добавляется при каждом решении, меняющем конструкцию. Формат: что решено, почему, что из этого следует. Отменённое решение не удаляется, а помечается.

## Р-01. Один экземпляр на владельца, отдельно от любых корпоративных платформ
2026-10-06. **Почему:** переписка владельца не должна зависеть от безопасности общей платформы; экземпляр должен быть пригоден людям вне одной организации. **Следствие:** общей многопользовательской базы нет; изоляция — граница сервера.

## Р-02. С системами организации экземпляр общается по MCP и только как клиент
2026-10-06. **Почему:** нужные операции узкие и типизированные; экземпляр без входящих интерфейсов нельзя опросить снаружи. **Следствие:** A2A и API-сервер Hermes выключены. Пересмотр — если организации понадобится принимать свободные поручения отдельным агентом.

## Р-03. Открытый код, MIT
2026-10-06. **Следствие:** компоненты под AGPL, LGPL, BSL в поставку не включаются без отдельного решения. Форк официального бизнес-плагина ведётся отдельным репозиторием, чтобы изменения можно было предлагать в исходный проект.

## Р-04. Поставка — «свой сервер»; развёртывание и сопровождение ведёт ИИ-агент
2026-10-06. **Почему:** владелец не обязан быть специалистом, но должен оставаться единственным, у кого есть доступ к данным. **Следствие:** правила для агента, runbook-и, скрипты и стартовые промпты — часть продукта и обновляются вместе с кодом. Поддерживаются два режима: агент исполняет на сервере; агент ведёт, человек вставляет команды.

## Р-05. Экземпляр ставится на новый чистый сервер
2026-10-06. **Следствие:** runbook не рассчитан на сосуществование с чужими сервисами; обнаружение посторонних контейнеров — стоп-точка.

## Р-06. Приложение Telegram (api_id) у каждого владельца своё
2026-10-06. **Почему:** блокировка общего приложения остановила бы все экземпляры сразу. **Следствие:** регистрация на my.telegram.org — шаг владельца в мастере подключения.

## Р-07. Модель по умолчанию — собственный доступ владельца к OpenAI
2026-10-06. **Следствие:** доступ настраивается в Hermes штатно — ключом API или входом по подписке (уточнено решением Р-15: все обращения к модели идут через Hermes). Ключ API устойчивее для сервера без присмотра. Провайдер остаётся сменным: OpenAI работает не во всех странах, и потеря аккаунта не должна останавливать экземпляр.

## Р-08. Telegram: бизнес-режим — плагином Hermes, дополнительный аккаунт — отдельным сервисом
2026-10-06. **Почему:** бизнес-обновления приходят в шлюз Hermes; сессия пользовательского аккаунта не должна лежать в процессе агента, где нет изоляции плагинов. Обоснование — `docs/architecture.md`. В части бизнес-режима отменено решениями Р-44 и Р-59: бизнес-режим подключается к боту согласований сервиса, бота Hermes в бизнес-режиме не подключают. Часть про аккаунты в силе.

## Р-09. Память: архив в Postgres + курируемые страницы Markdown в git
2026-10-06. **Почему:** два разных объёма требуют разных инструментов; файлы читаемы и правимы владельцем, история правок — в git; структурные данные требуют таблиц. **Следствие:** у каждого вида данных один источник истины, синхронизация односторонняя. Обоснование и отвергнутые варианты — `docs/memory.md`.

## Р-10. Эмбеддинги и распознавание голосовых по умолчанию локальные
2026-10-06, предварительно — подтверждается замером на спайке. **Почему:** иначе внешнему провайдеру уходит весь архив целиком. **Следствие:** полный локальный набор требует 8 ГБ памяти. Сервер на 4 ГБ — поддерживаемый вариант: распознавание голосовых остаётся локальным (лёгкий сервер GigaAM укладывается в 0,4–0,8 ГБ), а для эмбеддингов выбирается лёгкая локальная модель либо API — по замеру на проверочном наборе вопросов. Эталонный пилот работает именно на 4 ГБ. Уточнено решением Р-36: модель эмбеддингов выбрана, по умолчанию они выключены; распознавание голосовых ещё не сделано. Уточнено решением Р-63: распознавание сделано локальным, но модель запускается несжатой — около 1,4 ГБ памяти, а не 0,4–0,8 ГБ; на 4 ГБ помещается одно тяжёлое дополнение, рекомендуемый сервер — 8 ГБ.

## Р-11. Внешний доступ к архиву по MCP — необязательный режим, только чтение, по умолчанию выключен
2026-10-06. **Почему:** владельцу может быть удобно спрашивать свою переписку из стороннего ассистента (например, OpenAI Dots в приложении ChatGPT), а слой данных от движка агента не зависит. **Следствие:** при включении у экземпляра появляется входящий интерфейс за OAuth — это осознанное отступление от Р-02, о котором владелец предупреждается: сторонний ассистент запоминает прочитанное по своим правилам, и удалить это из него выборочно может быть нельзя. Отправка сообщений и черновики через этот интерфейс недоступны. В 0.0.7 код отдельного gateway реализован, но настоящий облачный клиент не удостоверен: `docs/remote-mcp.md`.

## Р-12. Размещение сервера выбирает владелец; эталонный экземпляр стоит в стране, где доступны Telegram и провайдер модели
2026-10-06. **Следствие:** исходящий прокси — необязательная настройка, а не часть базовой поставки. Где хранится переписка и что об этом говорит закон страны владельца — его ответственность; README говорит об этом прямо.

## Р-13. Продукт называется «Штурман», репозиторий — `shturman`
2026-10-06. **Почему:** имя объясняет отношения владельца и ассистента — владелец ведёт и решает, ассистент читает дорогу и подсказывает. Это совпадает с главным ограничением продукта: отправку решает владелец. Первая аудитория — русскоязычные руководители, для которых Telegram основной рабочий канал.

## Р-14. Имя и характер ассистента владелец выбирает при первом запуске
2026-10-06. Предлагаются Штурман (по умолчанию), Нестор, Савельич, Бэрримор, Дживс и своё. **Следствие:** характер действует только в разговоре с владельцем; на сообщения третьим лицам, на подпись дополнительного аккаунта, на содержание и на правила не влияет. Подробности — `docs/personas.md`.

## Р-15. Hermes остаётся стоковым; продукт — расширения и один сервис рядом
2026-10-06. **Почему:** владелец не должен терять ничего из того, что умеет Hermes, и должен получать его обновления штатным путём; у кого Hermes уже есть — тот ставит «Штурман» поверх. **Следствие:** своего образа Hermes нет, самообновление не выключается, версия Hermes не привязана к нашему релизу. Совместимость — список проверенных версий и предупреждение перед обновлением. Все обращения к модели идут через Hermes. Кабинет владельца — плагин дашборда, а не отдельное приложение. Подробно — `docs/deployment.md`. Уточнено решениями Р-44 и Р-47: по желанию владельца у сервиса свой доступ к модели, а сервис можно поставить и без Hermes.

## Р-16. Эталонное развёртывание — Compose с официальным образом Hermes
2026-10-06. **Почему:** одна команда поднимает всё; состояние описано в одном файле, который ИИ-оператор может прочитать, применить повторно и откатить; терминал агента ограничен контейнером без наших правок. **Следствие:** установка Hermes прямо в систему поддерживается как вариант «пристройка», но эталоном не является.

## Р-17. Токены, ключи и базовая настройка — через веб-интерфейс, а не через терминал
2026-10-06. **Почему:** владелец далёк от ИТ; секреты не должны проходить через ИИ-агента. **Следствие:** ключ модели, вход по подписке и токен бота вводятся в стоковом дашборде Hermes; вход в дополнительный аккаунт, загрузка экспорта и правила — во вкладке «Штурман»; агент ставит несекретное и проверяет по статусам. Первый вход в дашборд — через единый вход перед прокси либо по одноразовой ссылке. Терминальный ввод остаётся запасным путём. Подробно — `docs/setup.md`. В версии 0.0.3 экранов для аккаунтов, экспорта и правил ещё нет: эти действия временно идут запасным путём. Уточнено решениями Р-44 и Р-47: токен бота согласований и ключ модели сервиса вводятся в терминале скрытым вводом — веб-интерфейса для них нет. Уточнено решением Р-55: вход в аккаунт, выбор чатов, выгрузка, а также бот согласований и ключ модели сервиса вводятся в браузере — но не во вкладке «Штурман», а на странице, которую отдаёт сам сервис переписки; терминал остаётся запасным путём.

## Р-18. Готовое берём только под разрешительными лицензиями
2026-10-06. **Следствие:** проекты под AGPL, GPL и без лицензии — источник идей, не кода. Разбор по частям решения — `docs/reuse.md`.

## Р-19. Основной аккаунт можно подключить через сессию — только на чтение, необязательным режимом
2026-10-06. **Почему:** бизнес-бот не видит группы и прошлое; сессия основного аккаунта даёт и то и другое без выгрузки. **Следствие:** пути отправки для этой роли в сервисе нет вообще; от имени владельца пишет только бизнес-бот. Режим выключен по умолчанию и включается с предупреждением о риске для основного аккаунта. Уточнено решением Р-58: вход в основной аккаунт на чтение стал основным путём первой настройки; предупреждение о риске осталось, включает его по-прежнему сам владелец. Изменено решением Р-62.

## Р-20. Автоответ доверенным собеседникам — отдельный уровень автономии
2026-10-06. **Почему:** владельцу нужен ответ близкому кругу без подтверждения каждого сообщения. **Следствие:** уровень 2а: список доверенных по числовым идентификаторам, ограниченный набор инструментов без терминала и файлов, паузы и дневной лимит. Остальным сервис не отвечает. Подробно — `docs/service.md`. Уточнено решением Р-31: ответ готовится вообще без инструментов.

## Р-21. Наблюдатель групп — часть продукта
2026-10-06. Ключевые слова → дешёвая модель → уведомление владельцу; в группе сервис не пишет и прочитанным её не отмечает.

## Р-22. Сервис переписки пишется на Python с asyncpg
2026-10-06. **Почему:** Telethon работает на asyncio; `asyncpg` под Apache-2.0, тогда как `psycopg` — под LGPL. **Следствие:** работа с базой асинхронная, миграции — пронумерованные SQL-файлы без отдельного инструмента.

## Р-23. Вход в дашборд — свой способ входа Hermes: ссылка активации и код от собственного бота
2026-10-06. **Почему:** владелец далёк от ИТ, паролей и терминала у него быть не должно; при этом Hermes с внешним адресом обязан иметь вход, а его встроенный парольный вход требует задать хеш пароля на сервере. **Следствие:** плагин `shturman` регистрирует способ входа штатным механизмом Hermes. Первый вход — по одноразовой ссылке, которую выдаёт `ops/activation-link.sh`; дальше — по коду из восьми цифр, который бот владельца присылает по кнопке на странице входа. Почты в первой версии нет: для неё нужен почтовый сервер. Отдельной программы для входа нет; страницы входа — статические файлы, которые отдаёт обратный прокси. Подробно — `docs/setup.md`.

## Р-24. Ссылку активации агент видит и передаёт владельцу
2026-10-06. **Почему:** другого канала от сервера к владельцу до настройки бота нет. **Следствие:** это единственное исключение из правила «секреты не проходят через агента». Ссылка одноразовая, живёт 30 минут, отменяется выдачей новой; значение стоит после `#` и в журналы прокси не попадает; агенту запрещено её сохранять. Та же команда выдаёт ссылку восстановления, если Telegram владельца потерян или захвачен: доступ к серверу считается доказательством владения, вход по такой ссылке отвязывает прежний аккаунт и завершает все сессии.

## Р-25. Владелец привязывается к боту кнопкой «Запустить», а не вводом своего Telegram ID
2026-10-06. **Почему:** числовой идентификатор владелец не знает; стоковая привязка Hermes отвечает по-английски и просит выполнить команду в терминале. **Следствие:** мастер выдаёт ссылку `t.me/<бот>?start=<значение>`; обработчик плагина в процессе шлюза запоминает отправителя как кандидата; владельцем он становится только после подтверждения в мастере, то есть из уже выполненного входа. Затем мастер штатными вызовами задаёт `TELEGRAM_ALLOWED_USERS` и `TELEGRAM_HOME_CHANNEL`. Обработчик активен только пока мастер ждёт сообщения.

## Р-26. Мастер настройки — вкладка дашборда Hermes, секреты идут в штатные вызовы Hermes
2026-10-06. **Почему:** так ключ модели и токен бота не проходят через наш код и не хранятся у нас; у плагина нет способа скрыть меню дашборда, а отдельная страница потребовала бы своего сервера с доступом к секретам. **Следствие:** серверная часть плагина хранит только выбор помощника, отметки шагов и состояние привязки. Исключение: токен бота один раз проходит через плагин, чтобы спросить у Telegram имя бота до сохранения; плагин его не записывает.

## Р-27. Плагин `shturman` перехватывает сообщения бизнес-режима, пока не включён плагин бизнес-режима
2026-10-06. **Почему:** порядок «сначала плагин, потом подключение бота» зависит от действий человека в Telegram, которые мы не контролируем; без плагина ядро Hermes отвечает собеседникам владельца (issue NousResearch/hermes-agent #127430). **Следствие:** защита не зависит от того, в каком порядке владелец выполнил шаги, и от того, поднялся ли плагин бизнес-режима: она снимается только когда Hermes сообщает, что он загружен без ошибки. Плагин бизнес-режима ставится из официального репозитория по SHA `98c60afc00d36c885bb040ebe973b1aa908886c0` (вершина `main` на 2026-10-06, включает исправление безопасности от 2026-08-15). Уточнено решением Р-59: мастер этот плагин больше не ставит и бота Hermes в бизнес-режим не ведёт; перехват в плагине `shturman` остаётся как защита на случай, если бота всё же подключили.

## Р-28. Плагин не привозит своих зависимостей
2026-10-06. **Почему:** `python-telegram-bot` распространяется под LGPL-3.0, в поставку мы такие компоненты не включаем (Р-18). **Следствие:** плагин пользуется библиотеками, которые уже есть в окружении Hermes (FastAPI, python-telegram-bot), и импортирует их только там, где они нужны. Логика плагина (`shturman_core/`) написана на стандартной библиотеке Python и проверяется без Hermes.

## Р-29. У сервиса переписки нет доступа к модели и к боту: задания выполняет плагин
2026-10-06. **Почему:** модель и бот есть только у Hermes (Р-15); второй ключ модели и второй получатель обновлений бота сервису давать нельзя. **Следствие:** всё, для чего нужна модель, сообщение владельцу или отправка через бизнес-бота, сервис ставит в очередь заданий в базе. Плагин `shturman` забирает задание, выполняет и возвращает итог. Видов заданий пять: `llm.structured`, `llm.text`, `notify.owner`, `notify.edit`, `business.send`; зачем они нужны, плагин не знает. Отправка через бизнес-бота не повторяется никогда: исход либо «ушло», либо «точно не ушло», либо «неизвестно». Уточнено решением Р-44: это поведение по умолчанию; по желанию владельца задания бота и модели сервис выполняет сам.

## Р-30. Сервис — один процесс и один порт, два разных токена
2026-10-06. **Почему:** сессией Telegram может владеть только один процесс; один порт на локальном адресе проще закрыть и проверить. **Следствие:** `shturman serve` отдаёт `/health`, внутренний API `/api/*` для плагина (токен `SHTURMAN_API_TOKEN`) и архив `/mcp` для агента (токен `SHTURMAN_MCP_TOKEN`, только чтение). Токены не взаимозаменяемы; сервис не запускается, если они совпали. У внутреннего API токен один на всё, поэтому границу между «мостом», инструментами агента и страницами владельца держит плагин — перечнями разрешённых адресов. От агента с терминалом эта граница не защищает (Р-42). Уточнено решением Р-55: на том же порту появился третий вход — страница настройки `/shturman-setup/` со своим входом; токены внутреннего API и архива на ней входом не служат.

## Р-31. Агент может только создать черновик; автоответ готовится без инструментов
2026-10-06. **Почему:** отправку решает не модель (принцип 4 архитектуры); сообщение собеседника, даже доверенного, — чужой текст. **Следствие:** инструмент агента создаёт черновик, сервис показывает его владельцу карточкой с кнопками, отправляется ровно согласованный текст. Правила отправки, список доверенных, автоответ, правила наблюдателя, исключения чатов и аккаунты через инструменты агента недоступны. Для автоответа доверенным сервис сам собирает справку из архива и просит у модели только текст; из других чатов в справку попадают лишь собственные слова владельца. Уточняет Р-20.

## Р-32. Отправка включается только из окружения сервиса; жёсткий суточный потолок; ассистент не пишет первым
2026-10-06. **Почему:** тот, кто завладел токеном внутреннего API, не должен иметь возможности включить отправку или снять лимиты. **Следствие:** `SHTURMAN_SENDING` (по умолчанию `off`) и `SHTURMAN_SEND_DAILY_CAP` (по умолчанию 50 на аккаунт в сутки) читаются только из окружения, на сервере — из `.env`; в API нет вызова, который их меняет. Пока отправка выключена, сервис не отправляет ничего ни одним каналом и не создаёт черновиков. Черновик возможен только в чат, где уже есть исходящее сообщение владельца или помощника, либо как ответ через бизнес-бота на свежее входящее; через API это правило не выключается.

## Р-33. Из аккаунта читаются только выбранные владельцем чаты; глубина истории по умолчанию — 12 месяцев
2026-10-06. **Почему:** вход в аккаунт не должен означать «забрать всё»; чем меньше запросов истории, тем меньше риск ограничений со стороны Telegram и тем меньше чужих данных на сервере. **Следствие:** после входа ничего не читается, пока владелец не включил чаты — поштучно или по видам. Для включаемого чата история загружается на 12 месяцев вглубь; глубину можно изменить для аккаунта или задать для отдельного включения, в том числе «вся история».

## Р-34. Аккаунт владельца не может быть помощником; вход помощника — только когда владелец известен
2026-10-06. **Почему:** помощнику разрешена отправка, основному аккаунту — нет (Р-19). Перепутать роли значит получить отправку с основного аккаунта. **Следствие:** вход помощника не начинается, пока бот не привязан к владельцу в мастере и в архиве нет основного аккаунта. После входа и при каждом запуске сессии аккаунт сверяется с владельцем; при совпадении сессия завершается. Если владельцем становится аккаунт, уже подключённый как помощник, сессия останавливается, владелец получает уведомление.

## Р-35. Служебные чаты Telegram и диалог «Коды подтверждения» исключены всегда
2026-10-06. **Почему:** в них лежат коды входа и токены ботов; попав в архив, они стали бы доступны агенту. **Следствие:** уведомления Telegram (777000), @BotFather и @SpamBot не принимаются в архив ни из одного источника, не отдаются агенту, и вернуть их в архив нельзя. Диалог «Коды подтверждения» исключается по типу чата экспорта. Каким идентификатором этот диалог представлен в живых источниках, проверить не удалось — открытый вопрос.

## Р-36. Эмбеддинги: `multilingual-e5-small`, по умолчанию выключены, контейнер без интернета
2026-10-06. **Почему:** эталонный сервер — 4 ГБ памяти; веса `bge-m3` занимают 2,27 ГБ и рядом с Hermes и базой не помещаются. **Следствие:** модель `intfloat/multilingual-e5-small` на сервере TEI; столбец вектора — `halfvec(384)`: вектор и индекс вдвое меньше. Модель другой размерности требует новой миграции. Эмбеддинги включает владелец командой `./ops/embeddings.sh on`; без них поиск идёт по словам. Через контейнер проходит текст всех сообщений, поэтому выхода в интернет у него нет: модель заранее скачивает и сверяет по контрольным суммам тот же скрипт. Переранжирования нет. Качество измерено только на маленьком синтетическом наборе. Уточняет Р-10. Подтверждено решением Р-50: замена на EmbeddingGemma 2 измерена и отклонена. Уточнено решением Р-51: появилась вторая поддерживаемая модель, `deepvk/USER2-small`; `multilingual-e5-small` остаётся моделью по умолчанию.

## Р-37. Дату срока считает код; обязательства становятся предложениями, которые принимает владелец
2026-10-06. **Почему:** модель ошибается в датах, а ошибка в сроке хуже его отсутствия. **Следствие:** модель копирует формулировку срока дословно, дату от времени сообщения в поясе владельца считает разборщик; формулировка, которой нет в исходном тексте, отбрасывается; если она не сводится к одной дате — «нужно уточнение». На нашей таблице из 38 формулировок разборщик даёт 38 верных ответов и ни одной неверной даты. Каждое найденное обязательство — предложение: владелец получает сводку с кнопками и принимает или отклоняет; оставленное без ответа предложение устаревает.

## Р-38. Страницы памяти — файлы и git в каталоге данных сервиса; первая версия — только люди
2026-10-06. **Почему:** страницы собираются из архива и обязательств, которыми владеет сервис; каталог сервиса контейнеру Hermes не подключён, и агент читает страницы только через инструменты архива. **Следствие:** страницы лежат в `data/shturman/pages`, история — локальный репозиторий git без внешних адресов. Первая версия ведёт только страницы людей. Страница заводится без вопроса только для человека, которого владелец подтвердил; об остальных владельцу уходит предложение с кнопками. Блок владельца код не меняет никогда. Встроенный скилл Hermes `llm-wiki` не используется. Уточняет Р-09.

## Р-39. Зависимости образа сервиса ставятся из списка с контрольными суммами
2026-10-06. **Почему:** сервис держит сессии Telegram и всю переписку; подменённый пакет при сборке получил бы всё это. **Следствие:** `service/requirements.lock` содержит точные версии и суммы всех пакетов, включая транзитивные; образ ставит их с проверкой сумм, а сам сервис — поверх, без подтягивания чего-либо ещё. Базовый образ назван по точной версии. Обновление списка — отдельным изменением.

## Р-40. Содержимое заданий стирается после выполнения; невостребованные задания закрываются
2026-10-06. **Почему:** в задании лежат копии текста сообщений; иначе они пережили бы удаление сообщения и исключение чата. **Следствие:** через десять минут после закрытия задания его содержимое и результат стираются; строка остаётся — она защищает от повторной постановки. Задание, которое исполнитель не забрал за отведённый срок (от часа до суток по виду), закрывается как неудачное. Текст завершённых черновиков стирается через 30 дней.

## Р-41. MCP-сервер архива — на официальном SDK 2.x, класс `MCPServer`
2026-10-06. **Почему:** в SDK 2.x класса FastMCP больше нет; Hermes 0.21.5 поставляется с клиентом 2.0.0. **Следствие:** транспорт — streamable HTTP без состояния, только запросы POST, ответы в JSON; заголовки `Host` и `Origin` сверяются всегда. Проверено с SDK 2.3.0 и клиентом 2.0.0.

## Р-42. Отправка остаётся выключенной, пока согласование идёт через плагин в Hermes
2026-10-06. **Почему:** плагин держит токен внутреннего API в процессе Hermes, а Hermes передаёт окружение в терминал агента. Агент, которому внедрили инструкцию, может обратиться к API напрямую и, если отправка включена, подделать нажатие владельца. **Следствие:** `SHTURMAN_SENDING` остаётся `off`; право бота отвечать в Telegram Business рекомендуется держать выключенным. Полное описание — `docs/architecture.md`, «Открытое ограничение». Исправление — отдельный бот согласований, которым владеет сервис; решение о нём за владельцем (открытые вопросы). Уточнено решением Р-44: бот согласований сделан; без него отправка не включается вовсе. Отправка остаётся выключенной и с ним — до проверки на настоящем боте и решения владельца.

## Р-43. В образе сервиса есть программа git
2026-10-06. История страниц памяти ведётся программой git (GPL-2.0), установленной в образ сервиса из пакетов Debian. **Почему это не нарушает Р-18:** git вызывается как отдельная программа, его код в поставку не включается и с кодом сервиса не связывается; в репозитории его нет. Без git страницы собираются, но без истории правок.

## Р-44. У сервиса может быть свой бот согласований и свой доступ к модели; при своём боте маршруты плагина закрыты
2026-10-07. **Почему:** пока нажатие владельца идёт через плагин, оно проходит через процесс, где у ассистента есть терминал и токен внутреннего API, и его можно подделать (Р-42). **Следствие:** `SHTURMAN_BOT_TOKEN` включает бота, токен которого есть только в контейнере сервиса: карточки уходят через него, нажатия приходят от Telegram напрямую, владелец привязывается одноразовой ссылкой (`./ops/bot-bind.sh`); код привязки пишется прямо в базу, маршрута для него в API нет. `SHTURMAN_LLM_API_KEY` и `SHTURMAN_LLM_MODEL` дают сервису свой доступ к модели. Со своим ботом сервис отказывает плагину кодом `own_bot` в привязке владельца, нажатиях и приёме бизнес-сообщений; задания своего исполнителя плагину не выдаются и по HTTP не закрываются; бизнес-режим подключается к боту сервиса. Плагин в ответ уходит в спокойный режим. Без своего бота `SHTURMAN_SENDING` не действует. Всё это по желанию и по умолчанию выключено. Клиент Bot API написан на httpx: `python-telegram-bot` под LGPL в образ сервиса не входит (Р-28). С настоящим ботом не проверено. Уточняет Р-15, Р-17, Р-29, Р-42. Уточнено решением Р-58: в первую настройку бот согласований не входит. Изменено решением Р-62.

## Р-45. Действия, расширяющие права ассистента, подтверждает владелец: ослабление ждёт, ужесточение применяется сразу
2026-10-07. **Почему:** токен внутреннего API доступен ассистенту в Hermes (Р-42); закрыть нажатия мало, если тем же токеном можно добавить доверенного или вернуть исключённый чат. **Следствие:** при своём боте (Р-44) изменения, которые расширяют то, что ассистент читает, помнит или может отправить, и необратимые стирания по HTTP не применяются: маршрут отвечает 202, владелец решает кнопкой в боте сервиса, на решение час. Что считать ослаблением, решается по значению, а не по названию настройки. Ужесточения — исключить чат, выключить автоответ, убрать доверенного, поставить аккаунт на паузу — применяются сразу: владелец должен мочь закрыть доступ немедленно, даже когда бот недоступен. Цена: держатель токена может ужесточать настройки и отменять ждущие карточки — это неудобство, а не утечка. Подтвердить действие по HTTP нельзя. Без своего бота всё применяется сразу, как раньше: подтверждение через Hermes было бы видимостью. Перечень — `docs/service.md`.

## Р-46. Защита от внедрённых инструкций — одна точка проверки на входе в архив; модель `Horizon-Labs/prompt-injection-guard-small`
2026-10-07. **Почему:** три рубежа (вход, перед обработкой, выход) и отдельный экран — три места, где можно ошибиться; одна проверка при записи сообщения и один признак видимости, который учитывают все пути чтения, проще проверить тестами. **Следствие:** столбец `messages.agent_visible`; сообщение живого потока пишется скрытым и проверяется до того, как о нём узнают остальные модули; импорт и догрузка истории проверяются фоном. Модель — `Horizon-Labs/prompt-injection-guard-small`, ревизия `3215a27` (Apache-2.0 по карточке), во втором экземпляре TEI, по образцу эмбеддингов (Р-36): torch и transformers в образ сервиса не добавляются. Выбрана измерением на синтетическом русском наборе: `protectai/deberta-v3-base-prompt-injection-v2` даёт на русском 21–24 % ложных срабатываний, модели Meta Prompt Guard закрыты условиями доступа и лицензией. Порог 0,9: ложно скрытое сообщение ассистент не видит до решения владельца, поэтому выбран осторожный порог ценой полноты. При недоступной модели сообщения видны и считаются непроверенными: остановка модели не должна останавливать ассистента. Правила — второй оценщик и запасной вариант; защитой не считаются (19 % полноты на независимом наборе). Текст скрытого сообщения через внутренний API не отдаётся, выключателя защиты в API нет. По умолчанию выключена. Это снижение риска, а не гарантия; числа — `docs/guard.md`.

## Р-47. Второй режим установки — без Hermes: «только архив и согласования»
2026-10-07. **Почему:** владельцу может быть нужен архив с поиском и обязательствами без ассистента в Telegram; вопросы он задаёт из своего Codex CLI или Claude Code. **Следствие:** режим — `SHTURMAN_MODE` в `.env`, по умолчанию `hermes`; контейнер Hermes — в профиле Compose. В режиме без Hermes у сервиса свой бот согласований и свой доступ к модели (Р-44); разговора с ассистентом, сводок, памяти разговора, веб-мастера и готовых черновиков нет. Секреты в этом режиме вводятся в терминале скрытым вводом. Экземпляр наружу не публикует ничего. Под Docker запускался на стенде; с настоящим ботом и моделью не проверен. Уточняет Р-15, Р-16, Р-17, Р-29. Уточнено решениями Р-52 (готовых черновиков в этом режиме нет и не будет), Р-53 (вариант установки владелец выбирает явно, вариантов два), Р-55 (страница настройки есть и в этом режиме — через туннель SSH; терминал остался запасным путём) и Р-58 (бот согласований и ключ модели перестали быть обязательным шагом установки).

## Р-48. Токен архива для клиента владельца не проходит через агента
2026-10-07. **Почему:** токен открывает всю переписку на чтение. **Следствие:** настройки Codex CLI и Claude Code ссылаются на переменную окружения; значение владелец забирает сам командой `./ops/mcp-token.sh` — подстановкой, без показа на экране; `./ops/connect.sh` токен не печатает. Архив наружу не публикуется: с компьютера владельца — через туннель SSH на порт 8765. В 0.0.6 облачные клиенты (Р-11) не поддержаны. В 0.0.7 появился отдельный необязательный OAuth gateway; локальный токен для него не применяется, живая совместимость требует приёмки (`docs/remote-mcp.md`).

## Р-49. Файл `.env` входит в резервную копию
2026-10-07. **Почему:** токен бота согласований и ключ модели сервиса лежат только там; в режиме без Hermes без них экземпляр из копии не восстановить. **Следствие:** `./ops/backup.sh` кладёт `.env` в архив каталога данных, не читая его. Копия и раньше содержала ключи, сессии и переписку: агент её не открывает и никуда не передаёт. Подтверждено владельцем 2026-10-07.

## Р-50. EmbeddingGemma 2 не берём; модель эмбеддингов по умолчанию остаётся `multilingual-e5-small`
2026-10-07. **Почему:** измерено в день после выхода модели (`google/embeddinggemma-2`, Apache-2.0). TEI 1.9.4, на котором стоит наша упаковка, её не запускает, а версии TEI новее нет: понадобился бы второй сервер (llama.cpp) и второй протокол в клиенте. На нашем синтетическом наборе коротких сообщений она заметно лучше `e5-small` (полнота в первых десяти 0,59 против 0,34), но не лучше `e5-base` (0,59) и хуже `deepvk/USER2-base` (0,66). Она в шесть раз медленнее `e5-small`: 19 сообщений в секунду против 115 на стенде. Длинное окно, её настоящее отличие, на сервере с 4 ГБ недоступно: один текст в 6000 знаков поднимает память сервера модели до 3,8 ГБ. **Следствие:** Р-36 остаётся в силе. Вернуться к вопросу, если TEI научится запускать эту модель или понадобится поиск по картинкам и голосовым. На дату записи это не было реализовано; сделано решением Р-51. Оговорка: набор синтетический и написан одним автором, 165 вопросов дают разброс около ±8 процентных пунктов; на настоящей переписке не измерялось.

## Р-51. Вторая поддерживаемая модель поиска по смыслу — `deepvk/USER2-small`; по умолчанию остаётся `multilingual-e5-small`
2026-10-07, решение владельца. **Почему:** на нашем синтетическом наборе коротких русских сообщений `USER2-small` находит заметно больше (полнота в первых десяти 0,55 против 0,35 у `e5-small`, разброс ±8 процентных пунктов), занимает впятеро меньше памяти и укладывается в ту же упаковку: TEI 1.9.4, 384 измерения, столбец `halfvec(384)` не меняется, лицензия Apache-2.0. По умолчанию её не ставим: на энциклопедических наборах она слабее (RuBQ 0,75 против 0,80, MIRACL-ru 0,83 против 0,91), длинный текст среди коротких сообщений находит заметно хуже (0,21 против 0,54), язык один, а на настоящей переписке не измерялась ни одна из двух. **Следствие:** модель выбирает владелец — `./ops/embeddings.sh on --model e5-small|user2-small`; включение и смена модели — стоп-точки. Скрипт скачивает модель по закреплённой ревизии с проверкой сумм всех файлов в отдельный каталог; экземпляру, развёрнутому раньше, править `.env` не нужно. Контейнер запускается с `--max-batch-tokens 2048` для обеих моделей: без этого `USER2-small` не запускается в отведённой памяти. Смена модели — полный пересчёт векторов (около трёх часов на 300 000 сообщений по пересчёту со стенда); прежние векторы рядом не хранятся, возврат — такой же пересчёт. Векторы двух моделей в выдаче не смешиваются: до конца пересчёта поиск по смыслу видит только уже пересчитанные сообщения, поиск по словам — весь архив. Прежние векторы не стираются, пока контейнер не подтвердил новую модель. Набор и скрипт измерения — в репозитории; числа, оговорки и то, чего не проверено, — `docs/search.md`. Уточняет Р-36 и Р-50.

## Р-52. Историческое решение 0.0.6: без произвольного составителя ответов в сервисе

Отдельный «составитель ответов» внутри сервиса был бы вторым ассистентом без этих опор. **Следствие:** вопрос закрыт, функция не запланирована. Сервис сам пишет текст только для автоответа доверенным (Р-20, Р-31), как и раньше. Кому нужны черновики ответов — ставит вариант с Hermes. В 0.0.7 уточнено Р-61: ограниченные задачи ответа могут ожидать просмотра и источника, в том числе без Hermes; произвольный разговорный агент в сервис не добавлен. Уточняет Р-47.

## Р-53. При установке владелец выбирает из двух вариантов; ассистент на Codex CLI или Claude Code вместо Hermes — рассмотрено и отклонено

## Р-55. Переписка настраивается на странице, которую отдаёт сам сервис переписки, со своим входом
2026-10-07. **Почему:** вход в аккаунт Telegram, ключи приложения и выбор чатов — то, чего ассистент видеть не должен: кто видит QR-код входа или облачный пароль, тот получает аккаунт. Дашборд Hermes для этого не годится: он работает в процессе, которым управляет ассистент, а терминал владельцу, далёкому от ИТ, неудобен (Р-17). **Следствие:** сервис отдаёт страницу `/shturman-setup/`: её маршруты зовут функции сервиса напрямую, токены внутреннего API и архива на ней входом не служат. Вход — по одноразовой ссылке, которую создаёт только команда на сервере (`./ops/setup-link.sh`) прямой записью в базу; маршрута для неё нет, потому что токен внутреннего API есть у ассистента. Ссылку агент видит и передаёт владельцу — на тех же условиях, что ссылку активации (Р-24); на страницу агент не заходит. Действие со страницы — действие самого владельца: применяется сразу, без карточки в боте, и пишется в журнал действий. Введённые значения лежат в файле каталога данных сервиса, а не в базе, и обратно не отдаются. Мастер в дашборде о странице знает только признаки и числа и ведёт на неё обычной ссылкой. Вход в аккаунт, управление аккаунтами, выбор чатов и импорт выгрузки из прохода дашборда к сервису убраны. В режиме без Hermes страница та же, через туннель SSH. С настоящим аккаунтом Telegram не проверено. Уточняет Р-17, Р-26, Р-30, Р-47.

## Р-56. У страницы настройки отдельный адрес; по умолчанию — порт 8443 на том же имени
2026-10-07, находка независимой проверки безопасности и решение владельца. **Почему:** в первой редакции страница отдавалась с адреса дашборда Hermes. Ассистент в Hermes может ставить расширения дашборда, то есть исполнять свой JavaScript на этом адресе; на общем адресе такой скрипт действовал бы на странице от имени вошедшего владельца, а service worker'ом перехватывал бы вводимые секреты. Отдельный вход страницы от этого не защищал. **Следствие:** адрес страницы (схема, имя, порт) обязан отличаться от адреса дашборда. По умолчанию — то же имя на порту 8443: владелец счёл отдельное доменное имя слишком сложным, а порт ему ни знать, ни набирать не нужно — он переходит по кнопке и по ссылке. Отдельное имя остаётся допустимым вариантом. Проверок четыре, и каждая отказывает сама: `./ops/set-setup-url.sh` совпадающий адрес не записывает; сервис на общем адресе страницу снаружи не отдаёт и сообщает причину (`same_origin`); мастер ссылку на адрес дашборда не строит; `./ops/doctor.sh` показывает `FAIL setup-origin`, а если прокси отдаёт страницу по адресу дашборда — `FAIL setup-isolation`. В образце прокси страница — отдельный блок сайта, в блоке дашборда на её путь стоит отказ. Экземпляр, развёрнутый раньше, получает адрес по умолчанию при обычном обновлении (`./ops/up.sh`); прокси и firewall правятся вручную, это стоп-точки. Цена: ещё один открытый порт, второй блок в прокси; сервисы единого входа, которые не сохраняют номер порта, перед страницей на порту не работают — тогда отдельное имя. Что остаётся: подмена страницы в самом дашборде (`docs/architecture.md`, «Почему у страницы настройки свой адрес»). На настоящем сервере не проверено. Уточняет Р-55.

## Р-57. Сессия страницы настройки — без cookie
2026-10-07. **Почему:** страница стоит на том же имени, что и дашборд, а cookie по портам не разделяются: поставленная страницей cookie уходила бы и на порт дашборда — в Hermes, которым может управлять противник, — а скрипт дашборда мог бы подложить свою cookie на то же имя. **Следствие:** ключ сессии сервис отдаёт один раз, в ответе на вход; страница хранит его в хранилище браузера, которое разделено по адресу вместе с портом, и присылает в заголовке с каждым запросом. Заголовок браузер сам не приставляет ни к какому запросу, поэтому подделка запроса с чужого сайта невозможна по построению. Cookie страница не ставит и не читает; прокси ничего особенного для неё делать не должен. Цена: ключ доступен скрипту самой страницы — поэтому у неё строгая политика содержимого (только свои скрипты) — и расширениям браузера владельца; сессия живёт не дольше 7 дней и отзывается новой ссылкой входа. Уточняет Р-55, Р-56.

## Р-58. Бот согласований и бизнес-режим отложены до включения отправки; первая настройка — мастер и три шага на странице «Переписка»
2026-10-07, решение владельца. **Почему:** первая настройка с двумя ботами запутывала: бот-ассистент, бот согласований, бизнес-режим у одного из них, вход на страницу по коду от другого. Всё это нужно для отправки от имени владельца, а отправка выключена (Р-42). **Следствие:** обязательный путь — мастер Hermes (помощник, модель, бот-ассистент) и страница «Переписка» из трёх шагов: ключи приложения Telegram, вход в свой аккаунт по QR-коду — на чтение (Р-19), — выбор чатов; выгрузка из Telegram Desktop — по желанию. Вход на страницу — по одноразовой ссылке от того, кто ставил ассистента. Бот согласований, бизнес-режим и вход по коду от бота остаются в продукте, на той же странице в разделе «Дополнительно», и понадобятся, когда владелец решит включать отправку. В шаге мастера о боте согласований одна строка. `./ops/doctor.sh` показывает строки про бота согласований, только если он настроен. В режиме без Hermes бот согласований и ключ модели тоже перестали быть обязательным шагом: без них экземпляр — архив с поиском. **Цена, названа прямо:** пока бота согласований нет, действия через внутренний API не ждут подтверждения владельца (Р-45), и ассистент под внедрённой инструкцией технически может менять настройки сервиса — включить чтение другого чата подключённого аккаунта, исключить чат, принять обязательство за владельца. Отправить сообщение он не может: без бота согласований отправка не включается вовсе. Перечень — `docs/architecture.md`, «Открытое ограничение». Уточняет Р-17, Р-19, Р-44, Р-45, Р-47. Изменено решением Р-62.

## Р-59. Бота Hermes в бизнес-режиме Telegram не подключаем; шаг убран из мастера
2026-10-07. **Почему:** без дополнительного плагина ядро Hermes принимает сообщения собеседников владельца за команды (issue NousResearch/hermes-agent #127430); токен бота Hermes лежит в процессе, где у ассистента есть терминал, и бизнес-подключением этого бота ассистент может пользоваться напрямую через Bot API, мимо сервиса; официальный плагин бизнес-режима готовит собственные черновики мимо шлюза отправки сервиса. **Следствие:** бизнес-режим подключается только к боту согласований сервиса (Р-44) и только по решению владельца (Р-58). Шага «Бизнес-режим» в мастере нет, официальный плагин бизнес-режима мастер не ставит; `./ops/doctor.sh` его отсутствие считает нормой. Перехват сообщений бизнес-режима в плагине `shturman` остаётся (Р-27) — на случай, если владелец подключит бота Hermes сам. Экземпляр прежней схемы, где бот Hermes уже подключён и плагин стоит, обновление не трогает: мастер и `./ops/doctor.sh` спокойно сообщают об этом, решает владелец (`UPGRADING.md`). Вопрос «две системы черновиков» для новых экземпляров снят. Отменяет Р-08 в части бизнес-режима; уточняет Р-27.

## Р-60. Hermes не урезаем — подтверждено повторно
2026-10-07, решение владельца. Находку Р-56 можно было закрыть иначе: запретить ассистенту ставить расширения дашборда, убрать у него терминал или держать собственную сборку Hermes. Владелец отказался: Hermes остаётся стоковым, его возможности не урезаются (Р-15). **Почему записано отдельно:** именно это решение порождает остальную сложность — ассистент с терминалом и правом расширять дашборд считается возможным противником, и поэтому существуют отдельный адрес страницы настройки (Р-56), сессия без cookie (Р-57), бот согласований мимо Hermes (Р-44), подтверждения владельца (Р-45) и выключенная отправка (Р-42). **Следствие:** защищаемся границами вокруг Hermes — отдельный процесс, отдельный адрес, отдельный бот, — а не правками в нём. Каждая новая возможность, которая даёт ассистенту власть над данными владельца, проектируется из расчёта, что ассистент может действовать под чужой инструкцией. Пересмотр — если Hermes получит штатное разграничение прав для расширений дашборда и терминала.

## Р-61. Полный Hermes и ограниченная сервисная задача ответа
2026-10-08. По задаче владельца полный штатный Hermes сохраняется. Сервис получает отдельный сохраняемый путь: подготовить ответ, запросить определённый источник, спросить владельца или отказаться. Чтение и раскрытие различаются; недостающие разрешения поступают только от проверенного владельца. Повседневные решения — в независимом боте Telegram. `prepare_only` позволяет репетицию без доставки. Групповая область привязана к аккаунту/чату/теме; проверенное прямое обращение — повод рассмотреть вопрос, не право на источник или отправку. Уточняет Р-31, Р-32, Р-47 и Р-52, сохраняя отсутствие произвольного второго агента. Состояние приёмки — `docs/runbooks/validate-pilot.md`.

## Р-62. Два способа подключения к Telegram; бот согласований — первый шаг
2026-10-08, решение владельца. **Почему:** с версии 0.0.7 запрос ассистента на защищённое решение — принять найденное обязательство, объединить людей, записать блок владельца на странице памяти, включить чтение чата, импорт — без независимого бота отклоняется кодом `owner_unknown` (Р-45, `docs/architecture.md`, «Без своего бота согласований»). Значит, без бота согласований ассистент не готов к работе, и откладывать бота до включения отправки (Р-58) больше нельзя. Кроме того, у владельца два разных сценария: ассистент, который видит всё, как он сам, и ассистент — отдельный сотрудник со своим аккаунтом. Они по-разному устроены и несут разный риск, поэтому выбирает человек, один из двух. **Следствие:** страница «Переписка» в обоих режимах установки начинается с бота согласований: владелец создаёт его у @BotFather, вводит токен на странице и привязывает себя кнопкой; агент бота не заводит и токена не видит. Второй шаг — выбор способа: «Ассистент видит всё как вы» (`own`: ключи приложения Telegram, вход в основной аккаунт по QR на чтение, выбор чатов, по желанию выгрузка) или «Ассистент — отдельный сотрудник» (`staff`: бизнес-режим у бота согласований — нужен Telegram Premium, только новые личные сообщения; по желанию для групп — ключи приложения, аккаунт ассистента в роли «помощник» на втором номере, выбор его групп; по желанию выгрузка). Выбор хранится на сервере в `setup_state`, меняется в любой момент (`PUT /shturman-setup/api/scenario`, запись `setup.scenario` в журнале); собранное не теряется, подключённое не отключается, шаг другого способа, где что-то подключено, виден без номера с пояснением. В «Дополнительно» остались своя модель, «Что собрано» и журнал. Бизнес-режим подключается только к боту согласований и только человеком; бота Hermes в бизнес-режиме не подключают никогда (Р-59). Отправка по-прежнему выключена и со страницы не включается (Р-42). Когда владелец её включит, ответы идут так: в способе «как вы» — в личных чатах через бизнес-бота от имени владельца, в группах — черновик, который отправляет сам владелец; в способе «сотрудник» — в личных чатах через бизнес-бота, в группах — аккаунтом ассистента от своего имени. С основного аккаунта сервис не отправляет никогда (Р-19). `./ops/doctor.sh` в обоих режимах показывает `WARN approvals-bot`, пока бот не настроен; мастер Hermes на шаге «Переписка» называет бота согласований и два способа. У каждого шага страницы — «Что это даст» и свёрнутые вопросы, вверху — частые вопросы. **Уточняет / отменяет:** отменяет Р-58 в части бота согласований и бизнес-режима (они больше не отложены до включения отправки); уточняет Р-19 (сессия основного аккаунта — путь одного из двух способов, а не единственный основной путь); уточняет Р-44, Р-47.

## Р-63. Голосовые расшифровываются на сервере моделью GigaAM-Multilingual, несжатой
2026-10-08, решение владельца. **Почему:** голос — самое личное в переписке; на сервере расшифровка бесплатна и звук никуда не уходит. Модель — GigaAM-Multilingual от ai-sage (Сбер), вариант `ctc`, 220 млн параметров, лицензия MIT; по карточке производителя — лучшее среди открытых моделей качество для русского (не проверялось). Наш замер: 4,6 % ошибок в словах на 30 коротких фразах набора `golos` (чистая речь), минута речи — около 5 секунд на двух ядрах. Модели берём у производителя на Hugging Face и запускаем несжатыми, как он их выложил. Сжатая модель давала ту же точность при 0,4 ГБ памяти, но требовала либо около 3 ГБ памяти на разовую конвертацию на сервере владельца, либо публикации своей сборки модели — отклонено. **Следствие:** отдельный контейнер `asr` (каталог `asr/`, профиль Compose `asr`) в закрытой сети `backend`, файловая система только на чтение, без привилегий, предел памяти 2 ГБ; образ собирается на сервере по `asr/requirements.lock` с контрольными суммами, только для x86-64. Включает оператор по решению владельца — `./ops/asr.sh on` (стоп-точка): три файла модели скачиваются с huggingface.co по закреплённой ревизии с проверкой sha256. В работе около 1,4 ГБ памяти, поэтому рекомендуемый сервер — 8 ГБ и 4 ядра; на 4 ГБ помещается одно тяжёлое дополнение — голосовые или поиск по смыслу с защитой (`docs/voice.md`, «Какой сервер нужен»). Расшифровка хранится в `messages.transcript`, текст сообщения собирается из неё и подписи функцией базы `voice_text` (миграция `0026_voice.sql`); дальше поиск, обязательства и ассистент работают с ним как с текстом, а защита от внедрённых инструкций проверяет расшифровку чужого голосового так же, как текст (Р-46 не меняется). Перечень запросов Telethon для сессии на чтение расширен тремя: `upload.GetFileRequest`, `auth.ExportAuthorizationRequest`, `auth.ImportAuthorizationRequest` — скачивание вложения и перенос авторизации этой же сессии в дата-центр файла; прочитанным это ничего не отмечает. Хранится только текст: файл голосового живёт во временном каталоге в памяти контейнера и удаляется сразу после разбора. **Лицензии:** ffmpeg (LGPL/GPL) и libsndfile (LGPL) ставятся в контейнер `asr` из пакетов Debian при сборке на сервере владельца; ffmpeg вызывается отдельной программой, libsndfile подгружается как системная библиотека в контейнере распознавания. В репозитории их нет, с кодом сервиса они не связываются — по тому же основанию, что git в образе сервиса (Р-43), поэтому Р-18 не нарушается. Уточняет Р-10 и Р-36.

## Р-64. Своя модель сервиса по подписке ChatGPT: вход «вставкой адреса»
2026-10-08, по просьбе владельца. **Что:** вторым способом своей модели сервиса, наравне с ключом API, стала подписка ChatGPT владельца (Plus, Pro) — официальный путь OpenAI «Sign in with ChatGPT» для открытых программ, которые человек ставит себе сам (`developers.openai.com/siwc/token-sharing-open-source`, предварительная версия с 2026-09-29, сверено 2026-10-08). Вход — OAuth 2.0 с PKCE без секрета: первая регистрация с `client_id=dynamic_agent_client` и `agent_name_hint=Shturman`, дальше — с выданным `client_id`; постоянный номер сервера `ext_agent_host_id` (`urn:uuid:…`) создаётся до первого входа и переживает выход. Модель — `POST https://api.openai.com/v1/responses` потоком, `store: false`. Действует один способ: подписка убирает ключ, введённый на странице, ключ выходит из подписки; ключ в `.env` запирает подписку. Код — `service/src/shturman/executor/siwc.py`, `executor/subscription.py`, `setup_page/`.

**Почему «вставкой адреса».** Адрес возврата у OpenAI — только `http://127.0.0.1:<порт>/auth/callback`. Сервис работает на сервере, а браузер — на компьютере владельца, поэтому возврат на 127.0.0.1 до сервиса не доходит. Документация для удалённой машины предлагает войти на своём компьютере той же программой и перенести файл учётных данных по SSH — владельцу без терминала это не подходит, и «Штурмана» на компьютере владельца нет. Выбрано: страница настройки начинает вход (state, nonce, PKCE — в памяти сервиса, 10 минут, одна попытка), браузер владельца после разрешения показывает ошибку на 127.0.0.1, владелец копирует адрес из адресной строки и вставляет на страницу; сервис сверяет `state` и меняет код на токены с тем же адресом возврата и собственным номером сервера. Все правила документации соблюдены (тот же `redirect_uri` в запросе и обмене, проверка `state`, PKCE, проверка ID token и разрешения `chatgpt.tokens.use.direct`, свой номер у этого сервера), но сам путь в документации не описан.

**Риски.** (1) Предварительная версия: требования к запросам, коды ошибок и смысл `earliest_refresh_at` могут измениться; сервис сверялся с документацией на 2026-10-08, на настоящем OpenAI не запускался. (2) Путь «вставкой адреса» не описан: если OpenAI его закроет, запасной путь — туннель SSH `ssh -L 1455:127.0.0.1:1455 <сервер>` и слушатель на порту 1455 сервера, тогда возврат дойдёт до сервиса сам (слушатель не написан). (3) Лимиты подписки общие с обычной работой владельца в ChatGPT; у Plus — пятичасовой лимит на все программы. Ночной разбор может их расходовать; при исчерпании сервис ждёт и не тратит попыток заданий. (4) Если сервер выключен дольше 30 дней, ключ обновления истекает — вход повторяется. (5) Подписка недоступна в некоторых странах, тарифах и рабочих пространствах (ответ 403): сервис объясняет и вход не повторяет. (6) Вставленный адрес — одноразовый код входа, как код из SMS: агент его не видит и не просит (`AGENTS.md`).

**Следствие.** Новые исходящие адреса сервиса — `auth.openai.com` (обмен и обновление токенов, ключи подписи, отзыв) — `docs/deployment.md`. Новый файл секретов `data/shturman/setup/chatgpt.json` (600) и `chatgpt-host` — `docs/security-review.md`. Подпись ID token проверяется по JWKS OpenAI библиотекой PyJWT с `cryptography` (теперь прямые зависимости сервиса); если ключи получить не удалось, остаётся проверка по TLS (OIDC Core 3.1.3.7). Подписку для ассистента в Hermes это не касается: её подключают в мастере Hermes штатно (Р-15). Уточняет Р-44 в части своей модели сервиса.

## Р-66. Память, этап 2: проекты, датированные факты и решения, профиль владельца

2026-10-09, решение владельца (делать все четыре части: проекты и решения, датированные факты, профиль владельца, экран «Память»). **Что:** к страницам людей добавлены страницы проектов (`projects/<название>-<id>.md`, `project:<id>`) и профиль владельца (`owner/profile.md`, `owner:profile`); таблицы `projects`, `project_chats`, `project_aliases`, `project_mentions`, `facts` (миграция `0029_memory_projects.sql`); у обязательства появился проект. Ночной разбор тем же запросом на эпизод извлекает ещё факты, решения и названия проектов (`PROMPT_VERSION` 3). На странице — блоки `decisions` (только у проекта) и `facts` между обязательствами и хронологией; старые файлы читаются как раньше.

**Правила.** (1) Проект заводит владелец — сразу, со страницы настройки, или через ассистента — карточкой в боте согласований; модель только предлагает: не меньше трёх упоминаний в двух разных эпизодах за 30 дней или групповой чат с 20 сообщениями за 30 дней без проекта. Отклонённое не предлагается никогда; название проверяется по тексту сообщений эпизода — модель не может придумать проект, которого в переписке нет. (2) Факт о человеке со страницей и факт или решение о действующем проекте пишутся сразу; цитата обязана быть в сообщении эпизода, которое можно считать источником. Новый факт с тем же ключом (должность, телефон, цена…) закрывает прежний датой, прежний остаётся в хронологии («противоречие помечается»). Ключи — закрытый перечень: незнакомый ключ модели ничего не закрывает. (3) Факт о самом владельце попадает в профиль только с его согласия — кнопкой с отпечатком содержания (модуль `of`) или на экране «Память»; согласие пишет проверенный владелец (authority), как у обязательств. (4) У профиля нет сводки модели: только одобренные факты и блок владельца — правила и постоянные указания; ассистент читает их как слова владельца. Блок владельца любой страницы пишет только проверенный владелец. (5) Удаление и исключение чата каскадом убирают факты, решения, упоминания, место чата в проекте и предложения проектов, выведенные из него; страницы перерисовываются.

**Отступление от проекта.** У фактов о владельце и у страницы профиля нет `person_id`: владелец на экземпляре один, а его запись в реестре людей может появиться позже фактов или смениться при слиянии; так страница и факты от реестра не зависят.

**Цена.** Отбор эпизодов шире (числа с единицами, деньги, даты, «решили», «теперь», «новый номер»), поэтому запросов к модели больше в пределах прежнего предела на прогон. Страницы людей при первой сборке получают блок `facts`. Качество извлечения на настоящей модели не проверено. Hermes `USER.md` не синхронизируется: профиль доступен инструментом `get_owner_profile`. Развивает Р-09 и Р-38 (первая версия — только люди), опирается на Р-37 (предложения принимает владелец).

## Р-67. Без домена — HTTPS по IP-адресу (Let's Encrypt, профиль shortlived)

2026-10-09, решение владельца. **Что:** экземпляр можно поставить без домена. Дашборд и страница «Переписка» открываются по внешнему IPv4-адресу сервера — `https://203.0.113.10` и `https://203.0.113.10:8443`, — с сертификатом Let's Encrypt на IP-адрес. В образце прокси — вариант «без домена»: те же два блока на IP-адресе, в каждом `tls { issuer acme { profile shortlived } }`, в глобальном блоке `default_sni <IP>`. Скрипты адресов принимают внешний IPv4-адрес и печатают, что для него нужно; https-адрес с IP закрытой сети, самого сервера, служебным или в необычной записи не принимают ни скрипты, ни `./ops/up.sh`, ни плагин (одинаковый перечень, его совпадение проверяет тест); адрес `http://` принимается, как и раньше, кроме IP в необычной записи: с ней сервис теперь не запускается. `./ops/doctor.sh` для адреса из IP проверяет сертификат и версию Caddy (строки `proxy-cert`, `proxy-version`). Описание — `docs/deployment.md`, «Без домена».

**Почему.** У владельца может не быть домена, а покупка домена и запись DNS — лишний шаг, на котором установка останавливается. С 2026-01-15 Let's Encrypt выдаёт сертификаты на IP-адрес — на 160 часов и только с профилем `shortlived`; Caddy выбирает профиль и сам продлевает такие сертификаты. Рассмотрены:

- **Имя от сервиса вида sslip.io или nip.io** (`203-0-113-10.sslip.io`) — отказ. Сертификаты на такие имена считаются в общих для всех пользователей сервиса пределах Let's Encrypt и могут не выдаваться в нужный момент; главное — имя принадлежит стороннему оператору DNS: он может направить его на другой сервер и получить на него сертификат, то есть подменить страницу настройки, куда владелец вводит ключи Telegram.
- **Только туннель SSH** — оставлен как самый закрытый путь: он уже есть (`./ops/setup-link.sh --local`), наружу ничего не публикуется. Но открывать дашборд с телефона через туннель владелец не сможет.
- **Частная сеть** (Tailscale с собственным сервером Headscale) — интересна тем, что страницы не видны из интернета, но открытых вопросов много — Р-68, отложено.

**Следствия.** Разделение страницы настройки и дашборда остаётся прежним: origin — это схема, адрес и порт, и тот же IP на порту 8443 — другой адрес (Р-56). Стороннего оператора DNS нет. Порт 80 (и 443) должен быть открыт всегда: через него Let's Encrypt проверяет адрес при каждом продлении; сорвётся продление — через 6 дней страницы перестанут открываться (бот в Telegram продолжит работать). Нужен Caddy 2.11 или новее; только IPv4. Адрес сервера виден в журналах Certificate Transparency, HSTS на адрес из цифр не действует, Cloudflare и подобные защиты перед ним невозможны. При смене IP-адреса меняется адрес ассистента. Строка `default_sni` нужна серверу за NAT (облака, где внешний адрес не назначен самому серверу): без неё браузер, не присылающий имени, не получает сертификата — это найдено на стенде. Проверено настоящим Caddy 2.11.7 с тестовым центром Pebble; с настоящим Let's Encrypt, за настоящим NAT и при входе в дашборд Hermes по IP в браузере не проверено.

## Р-68. Частная сеть (Tailscale с собственным сервером Headscale) — на будущее, не сейчас

2026-10-09, решение владельца: **отложено**. **Что рассматривалось:** вместо публичного адреса — частная сеть между телефоном и компьютером владельца и сервером. Сервер управления — свой, Headscale (лицензия BSD-3), на этом же сервере; на устройствах — официальные приложения Tailscale с указанием своего сервера управления: в приложениях для iOS и Android — в настройках, для macOS — в настройках (если в приложении уже есть другая сеть) или командой `tailscale login --login-server=<адрес>`, в Windows — той же командой или значением `LoginURL` в реестре (документация Tailscale «Configure Tailscale clients to use a custom control server», https://tailscale.com/docs/how-to/set-up-custom-control-server, сверено 2026-10-09). Учётная запись у Tailscale не нужна.

**Чем привлекает.** Дашборд и страница настройки не видны из интернета вовсе: открыты только участникам сети.

**Что решить до того, как делать:**

- На телефоне одновременно работает только один VPN: если владелец уже пользуется VPN, частная сеть с ним не уживётся.
- WireGuard, на котором построен Tailscale, во многих сетях в России распознаётся и блокируется. Tailscale тогда пускает трафик через свои ретрансляторы DERP поверх HTTPS (у Headscale есть встроенный); как это работает из России, не проверено.
- Самому Headscale нужен адрес с HTTPS — подойдёт сертификат на IP-адрес из Р-67.
- Внутри сети страницы открывались бы по `http://100.x.y.z` — браузер не считает такую страницу защищённой, а наш код требует https для страницы настройки. Сертификаты, которые выдаёт сам Tailscale, с Headscale недоступны; остаётся свой центр сертификации, сертификат которого нужно ставить на каждое устройство.
- **NetBird** — отказ: его сервер под AGPL и требует отдельного поставщика входа (IdP).
- **AmneziaWG** — запасной вариант, если блокировка WireGuard окажется решающей.

**Статус:** отложено. В `README.md` — в списке не сделанного.

## Р-69. Посредник `sh.namre.app` — адрес для тех, у кого нет домена или белого IP

2026-10-12, решение владельца: делать как альтернативу «для тех, кто не хочет разбираться»; размещение — AWS. **Почему:** адрес по IP (Р-67) требует белого адреса и открытых портов, свой домен — умения работать с DNS; у сервера дома или за общим NAT хостинга нет ни того, ни другого. **Как:** экземпляр держит исходящее соединение к посреднику и получает по нему соединения браузеров; посредник пересылает их по имени сайта (SNI), не расшифровывая; сертификат и ключ — только на сервере владельца. Программа — frp (Apache-2.0). Зона `sh.namre.app` — Route 53, передана из `namre.app` (DNS у Cloudflare, без проксирования); посредник — Lightsail во Франкфурте. Подробно — `docs/relay.md`.

**Что рассматривалось и отклонено.** Cloudflare Tunnel — проще всего, но Cloudflare снимает TLS у себя и видел бы всё, что владелец вводит на странице настройки (ключи Telegram, вход в аккаунт); кроме того, с июня 2025 года крупные российские провайдеры замедляют сайты за Cloudflare. Имена от sslip.io и подобных — общие лимиты Let's Encrypt и посторонний держатель DNS (Р-67). Посредник у российского хостинга — возможен; выбран AWS, потому что аккаунт у владельца есть.

**Главный риск и что с ним делать.** Держатель зоны и посредника технически может подменить имя владельца и получить на него сертификат — то есть перехватить вход на страницу настройки. Сужают риск `CAA` с `accounturi` и проверка журналов Certificate Transparency экземпляром; владельцу это говорится прямо: посредник — для тех, кто доверяет его держателю. ## Р-70. Подключение экземпляра к посреднику: ключ экземпляра, коды приглашения, проверка сертификата посредника

2026-10-12, по заданию владельца. **Как.** Общий токен frps остаётся, но границей доверия не служит: у каждого экземпляра свой случайный ключ (32 байта), посредник хранит его sha256. Служба посредника `relayd` (Python 3.12, только стандартная библиотека — ставится системным python3 Ubuntu 24.04 без пакетов) — серверный плагин frps: пускает только известный экземпляр с верным ключом (`Login`), разрешает ему только типы `https`/`http` и только имена `<имя>` и `setup-<имя>` без `customDomains` и групп (`NewProxy`), отключённому не даёт рабочих соединений (`NewWorkConn`). Имена выдаются по одноразовому коду приглашения (`relayctl invite`, 100 бит, 7 дней) через `POST https://relay.sh.namre.app/api/join`; `/api/*` отдаёт свой Caddy посредника, подключённый к frps служебным frpc под именем `relay` — порты 80 и 443 занимает frps. На экземпляре — `./ops/relay.sh` и контейнер frpc (профиль Compose `relay`, образ из официального выпуска frp с проверкой sha256, сеть хоста), Caddy — вариант «через посредника» из `config/Caddyfile.example`.

**Почему так, а не иначе.**
- *Постоянный сертификат frps и его проверка экземпляром.* Без `trustedCaFile` frpc принимает любой сертификат (`pkg/transport/tls.go` frp 0.71.0), и перехвативший соединение экземпляра с посредником узнал бы ключ, занял бы имена и получил бы на них сертификат. Сертификат frps экземпляр получает при `join` по обычному HTTPS (Let's Encrypt) и проверяет им посредника.
- *Два имени, а не имя с портом.* Посреднику нужен только порт 443, а страница настройки остаётся отдельным origin (Р-56).
- *Только в режиме с Hermes.* Без Hermes экземпляр наружу ничего не публикует (Р-47, `AGENTS.md`); страница настройки там открывается через туннель SSH. Переход в режим без Hermes убирает профиль `relay`.
- *Протокол PROXY v2 только в пересылках https.* Caddy читает его лишь от `127.0.0.1`. На порт 80 его нет: этот порт Caddy обслуживает своим сервером перенаправлений, к которому `listener_wrappers` не применяется, и `http-01` с заголовком не проходила (найдено на стенде). Адрес клиента нужен посреднику для ограничения попыток `join`; сервис переписки адресам не верит, как и раньше.
- *Отключение с перезапуском frps.* Закрыть одно подключение у панели frps 0.71.0 нельзя, а отказ в `NewWorkConn` не трогает уже открытые соединения браузеров (keep-alive, HTTP/2) и запас рабочих соединений (2–3 запроса на стенде). Поэтому `revoke` по умолчанию перезапускает frps (`--no-restart` — отказаться), а `release` перезапускает всегда: иначе прежнее подключение держало бы пересылку на освобождённое имя.
- *Ключ создаёт экземпляр.* Посреднику уходит только sha256 ключа, сам ключ не передаётся ни в одну сторону; повтор `join` тем же кодом, именем и ключом получает тот же успех — потерянный ответ не стоит кода.
- *Общий сайт.* Пока `sh.namre.app` нет в Public Suffix List, все экземпляры для браузера — один сайт: cookie `SameSite` дашборда Hermes от соседа не защищают, а `Origin` Hermes не проверяет. Вариант прокси «через посредника» отвечает 403 на изменяющий запрос с `Sec-Fetch-Site`, отличным от `same-origin`; подброшенные на всю зону cookie прокси не закрыть. До внесения в список коды выдаются только владельцам, которым держатель доверяет; захват чужого имени через чужой `run_id` (риск 8 в `docs/relay.md`) закроют CAA с `accounturi` и проверка журналов CT.
- *Панель frpc на `127.0.0.1` — с паролем.* Hermes тоже в сети хоста; без пароля он мог бы остановить frpc или подменить его настройку (так же, как ради этого admin Caddy вынесен на Unix-сокет).

**Что остаётся.** CAA с `accounturi` и проверка журналов Certificate Transparency (риск 1 в `docs/relay.md`), подключение поверх 443 там, где закрыт порт 7000, установка на настоящий посредник и первый настоящий экземпляр.

## Р-71. Способ адреса выбирает владелец по проверкам агента; имя у посредника проверяется до подключения

2026-10-12, по заданию владельца. **Как.** В режиме с Hermes адрес ассистента — один из трёх способов: свой домен, IP-адрес сервера (Р-67), посредник (Р-69, Р-70); сравнение — `docs/address.md`. При подготовке сервера отдельный шаг (`docs/runbooks/server-prepare.md`, шаг 5): агент проверяет, внешний ли адрес у сервера и есть ли он среди адресов самого сервера, доходят ли из интернета порты 80, 443 и 8443 (временный приёмник на 90 секунд под `sudo` — стоп-точка) и достижим ли посредник; спрашивает, есть ли домен; затем задаёт владельцу один вопрос с тремя вариантами, отмечает рекомендованный и ждёт ответа — так же, как с вариантом установки (Р-53). Выбор записывается `./ops/state.sh set address domain|ip|relay`, и `deploy.md` идёт по этой ветке. У посредника — `POST /api/check {code, name}` и `./ops/relay.sh check КОД ИМЯ`: свободно ли имя и до трёх свободных вариантов; на занятое имя `join` тоже отвечает вариантами.

**Почему так, а не иначе.**
- *Выбор — за владельцем, рекомендация — по проверкам.* Способы различаются тем, кому владелец доверяет (держатель посредника может подменить имя) и что ему придётся делать (DNS, порты), — это его решение. Но без проверок он не знает, что из трёх вообще возможно на его сервере, а прежний вопрос «какой домен?» подталкивал к одному варианту.
- *Проверка портов приёмником, а не по документации хостинга.* Правила хостинга, NAT и firewall образа видно только по факту соединения. Стандартный `python3 -m http.server` есть в Ubuntu 24.04 без установки; отдаёт пустой временный каталог и закрывается сам через 90 секунд.
- *Проверка имени требует действующий код и не расходует его.* Без кода посторонний перебирал бы занятые имена (кто подключён). С кодом проверка не даёт больше, чем `join`, который и раньше отвечал «занято», не расходуя код. Неверный код в проверке — тот же отказ 403, что у `join`, без слова об имени. Вариантов `join` не даёт на служебное и неподходящее имя: их он отклоняет до проверки кода.
- *Свой счёт попыток у проверки, общий — у неудачных.* 30 проверок с адреса за 15 минут, отдельно от 10 попыток `join`: перебор вариантов имени не должен лишать владельца подключения. Неверный код в проверке идёт в общий предел неудачных попыток со всех адресов — перебирать коды через проверку не выгоднее, чем через `join`.
- *Свободное при проверке имя не бронируется.* Бронь потребовала бы расходовать или привязывать код, а гонка двух владельцев за одно имя в первые минуты маловероятна; проигравший получает 409 с вариантами и сохраняет код.

**Что остаётся.** Шаг 5 `server-prepare.md` и проверка имени на настоящем посреднике не пройдены; служба на посреднике обновляется до 0.3.0 держателем (`relay/README.md`).

## Р-74. Вход в Mini App — подпись Telegram; одна сессия на одни данные входа; своя узкая сессия

2026-10-12. **Как.** Данные входа (`initData`) проверяются по правилам Telegram «Validating data received via the Mini App» (core.telegram.org/bots/webapps, сверено 2026-10-12): HMAC-SHA-256 строки полей по алфавиту без `hash` (поле `signature` в строке остаётся — исключается только `hash`), ключ — HMAC-SHA-256 токена бота со строкой `WebAppData`, сравнение за постоянное время. Сверх документа: `auth_date` не старше 10 минут и не из будущего дальше минуты, каждый ключ один раз, строка не длиннее 8 КБ, пользователь — владелец, привязанный к работающему боту согласований. Проверка третьей стороной (Ed25519 по открытому ключу Telegram) не нужна: токен у сервиса свой. Любой отказ — один ответ без причины; причина — кодом в журнале действий, не чаще раза в минуту.

**Повтор.** Строку данных входа можно перехватить: она лежит в адресе страницы у Telegram. Поэтому по одной подписи Telegram (`hash` — один и тот же при любой перестановке полей) сессия выдаётся один раз, и запись об этом хранится сутки — дольше срока данных входа. Цена: обрыв связи во время входа требует закрыть и снова открыть приложение.

**Сессия.** Отдельная таблица `miniapp_sessions`, отдельный заголовок `X-Shturman-App`, без cookie (по тем же причинам, что Р-57); ключ — в памяти страницы и `sessionStorage`; 30 минут без обращений и не дольше 4 часов; любая привязка или отвязка владельца и смена токена бота завершают все сессии (а не усыпляют: возврат A → B → A или тот же токен их не оживит), как и «выйти везде» и `./ops/logout-all.sh`; срок без обращений сдвигается только после сверки бота и владельца. Повтор данных входа пишется в журнал всегда и сообщается владельцу в бот. Пока бот согласований в конфликте опроса (409, webhook — так выглядит и тот же токен у бота Hermes), вход закрыт и сессии не действуют. Роль уже, чем у страницы настройки: только список «Согласования» и нажатие кнопки из него; маршруты страницы сессию приложения не принимают, и наоборот (тест сверяет перечни). Решение принимается в контексте владельца с источником `telegram` (`authority.miniapp_context`, действие `telegram.miniapp`): как и у нажатия в боте, кто нажимает, удостоверяет Telegram подписью для бота сервиса. О каждом входе владельцу в бот не пишется (он сам только что открыл приложение); вход и решения — в журнале действий, в списке важных.

## Р-76. Hermes без CAP_NET_RAW; обратный прокси ходит к сервису через Unix-сокет, которого у Hermes нет

2026-10-13, по решению владельца от 2026-10-13. **Что нашли** (проверка на пилоте 2026-10-12). Контейнер Hermes работает в сети хоста, процесс в нём — под uid 0 контейнера (s6-overlay держит PID 1 и стадию подготовки под root) с правами Docker по умолчанию: `CapEff 00000000a80425fb`, в том числе `CAP_NET_RAW`; сырой сокет `AF_PACKET` в нём открылся. Прокси ходил к сервису открытым HTTP на `127.0.0.1:8765`. Значит, процесс root в Hermes мог читать всё, что владелец вводит на странице настройки: ключи приложения Telegram, токен бота согласований, ключ модели, код входа и облачный пароль Telegram, заголовки сессий страницы и приложения, данные входа Mini App. На стенде 2026-10-13 то же воспроизведено: в контейнере с сетью хоста и правами по умолчанию тело запроса к `127.0.0.1` читается из сырого сокета на `lo`; с `--cap-drop NET_RAW` — `CapBnd 00000000a80405fb`, `AF_PACKET` — «Operation not permitted», в том числе через `compose.yaml` этой версии. Второе — открытый пункт «Hermes может занять порт сервиса, пока сервис перезапускается» (`docs/security-review.md`): порт `127.0.0.1:8765` публикует процесс `docker-proxy`; пока сервис остановлен, порт свободен, и процесс из Hermes может занять его раньше Docker.

**Что делаем.**

1. **У контейнера Hermes нет `CAP_NET_RAW`** (`cap_drop: [NET_RAW]` в `compose.yaml`). Это настройка запуска, а не правка кода или образа; инвариант «Hermes не изменяем» в `AGENTS.md` уточнён ровно на это. Право убирается из ограничивающего набора (`CapBnd`): вернуть его не может ни процесс root, ни программа с file capabilities. Что Hermes от этого теряет — проверено по исходникам `v2026.9.24` (коммит `f97608f`): сырых сокетов, ICMP, `scapy`, `setcap` в коде нет. В образе есть `ping` (пакет `iputils-ping`, для терминала): у Debian 13 он без file capabilities и без `CAP_NET_RAW` работает через ICMP-сокеты, если их разрешает `net.ipv4.ping_group_range` (проверено на стенде: в сети с открытым диапазоном — работает от root и от uid 10000, с закрытым — нет). У Hermes этот параметр — хоста; на Ubuntu 24.04 по умолчанию он открыт (`/usr/lib/sysctl.d/50-default.conf` systemd) — на пилоте не проверено. Агенту `ping` не нужен.
   Остальные права по умолчанию (`CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `FSETID`, `KILL`, `SETGID`, `SETUID`, `SETPCAP`, `NET_BIND_SERVICE`, `SYS_CHROOT`, `MKNOD`, `AUDIT_WRITE`, `SETFCAP`) оставлены. Читать чужие соединения на петле позволяют `NET_RAW` (сырые сокеты) либо `NET_ADMIN` (перенаправление и копирование пакетов: `iptables`, `tc`, `nflog`) и `BPF`/`SYS_ADMIN` — последних по умолчанию нет. `SETUID`, `SETGID`, `CHOWN`, `DAC_OVERRIDE`, `FOWNER` нужны образу при запуске (смена uid пользователя `hermes`, `chown` каталога данных, `s6-setuidgid`). `NET_BIND_SERVICE` чужой трафик читать не даёт, но позволяет root в контейнере занять на хосте свободный порт ниже 1024 — 80 или 443, пока Caddy остановлен; это записано открытым риском, без решения.

2. **Прокси ходит к сервису через Unix-сокет.** Сервис слушает, кроме порта, `SHTURMAN_PROXY_SOCKET` — `/run/shturman-service/proxy.sock` (`service/src/shturman/listen.py`; один сервер uvicorn и одно приложение на оба адреса — фоновая работа запускается один раз). Блок страницы настройки во всех вариантах образца (с доменом, без домена, через посредника — `./ops/relay.sh caddyfile` берёт его из образца) и образец внешнего шлюза архива — `reverse_proxy unix//run/shturman-service/proxy.sock`. Защита — в файловой системе: каталог хоста подключён только контейнеру сервиса; у Hermes своё пространство имён файловой системы и процессов (до `/proc/<pid>/root` процессов сервиса и Caddy ему не дотянуться), доступа к Docker нет. Права каталога — второй рубеж на случай ошибки в подключениях: `config/shturman-service-socket.conf` для systemd-tmpfiles — `d /run/shturman-service 2710 <пользователь стека> caddy`; сокет — группы `caddy` (бит setgid каталога), режим 0660. Входят только пользователь стека и группа `caddy`, создать или подменить сокет может только пользователь стека; проверено с настоящим Caddy 2.11.7 под пользователем `caddy` (ответ 200) и под посторонним пользователем (502, permission denied). Пользователь стека — тот же uid, под которым работают процессы Hermes (`./ops/up.sh` подставляет `id -u` в `HERMES_UID`), поэтому права одни сокет от Hermes не закрыли бы: закрывает его то, что каталога в файловой системе Hermes нет. Это записано инвариантом в `AGENTS.md`.
   *Почему `/run` и systemd-tmpfiles.* `/run` очищается при перезагрузке; systemd-tmpfiles создаёт каталог заново при каждой загрузке (до Docker) и приводит к строке уже существующий каталог. Создать каталог с чужой группой без `sudo` нельзя, а `./ops/up.sh` работает без него — поэтому установка файла — разовая стоп-точка, как у `config/caddy-admin-socket.conf`. `RuntimeDirectory` службы Caddy не годится: владельцем каталога был бы `caddy`, а сокет создаёт сервис.
   *Почему не другое.* Абстрактный Unix-сокет (имя без файла) принадлежит сетевому пространству имён, а оно у Hermes общее с хостом. Порт ниже 1024 занял бы и root в Hermes (`NET_BIND_SERVICE`). Caddy не умеет проверять, кто слушает порт, а TLS между прокси и сервисом добавил бы ключи и сертификаты, которые сервису пришлось бы где-то держать.

3. **Порт 8765 остаётся** — для Hermes (плагин и архив), оператора (`./ops/doctor.sh`, `./ops/up.sh`) и туннеля SSH. Отказ маршрутам страницы настройки и приложения по TCP **не делаем**: как клиент Hermes и так достаёт страницу через прокси из интернета (выход наружу у него есть) с любыми заголовками, так что отказ по TCP не убрал бы ни одной его возможности; страницу защищают её вход и сверка `Host`/`Origin` (Р-56, Р-57), а не путь запроса. Сокет закрывает другое — Hermes в роли сервера (занятый порт) и в роли слушателя (сырой сокет). Туннель SSH к порту в режиме с Hermes остаётся уязвим для занятого порта, поэтому `./ops/setup-link.sh` при готовом сокете даёт команду туннеля к сокету (`ssh -L 8765:/run/shturman-service/proxy.sock`); в режиме без Hermes всё как раньше.

4. **Переход без поломки.** Сервис открывает сокет, только если каталог именно такой (владелец — он сам, setgid, группе — только вход, остальным — ничего); иначе работает на порту, как раньше, и сообщает причину в `GET /api/status` (`setup.socket`). Пока каталога нет, Docker создаёт пустой каталог от root — сервис им не пользуется. `./ops/doctor.sh`: строка `hermes-net-raw` (FAIL, если право есть) и `setup-socket` (WARN, пока каталога нет или прокси ещё ходит на порт; FAIL, если прокси уже на сокете, а сокет не работает, или каталог открыт другим). Порядок для работающего экземпляра — `UPGRADING.md`: каталог (sudo), `./ops/up.sh`, затем прокси (sudo).

**Что остаётся.** На пилоте не проверены: `cap_drop` на настоящем образе Hermes (проверено на стенде с другим образом через тот же `compose.yaml`), `ping_group_range` сервера, Caddy из пакета через сокет и туннель SSH к сокету. Процесс из Hermes по-прежнему может занять порт 8765, пока сервис перезапускается: тогда сервис не запустится («port is already allocated» — оператор это увидит), а к занявшему порт пойдут запросы самого Hermes (их токены у него и так есть) и проверки `./ops/doctor.sh` (без секретов). Уточняет Р-56 (что наружу выходит из сервиса) и инвариант «Hermes не изменяем».

## Р-77. Свой бот согласований у каждого владельца; общий бот отклонён; два способа получить своего — вручную и в одно нажатие через бот-менеджер посредника

2026-10-13, по решению владельца от 2026-10-13. **Что.** Каждый экземпляр держит своего бота согласований. Общий бот на всех отклонён: держатель его токена видел бы содержимое карточек всех владельцев, мог бы подделывать нажатия и вход в Mini App (данные входа подписываются токеном бота, Р-74) за любого из них, а бизнес-режим на общем боте отдавал бы ему личные переписки владельцев. Чтобы свой бот было легко получить, на странице «Переписка» два пути (`docs/approvals-bot.md`):

1. **Вручную у @BotFather — по умолчанию, ни от кого не зависит.** Пошаговые указания простыми словами: кнопка «Открыть @BotFather», что отправить (`/newbot`, название «Согласования», предложенный свободный на вид адрес `soglasovaniya_<6 знаков>_bot` — кнопки «Скопировать»), где в ответе токен. Проверка вставленного токена прежняя (`getMe`, «не опрашивает ли другая программа», webhook) и ошибки прежние. Картинок нет: текст и схема переписки.
2. **В одно нажатие — по желанию, для тех, кто доверяет держателю посредника.** Telegram Managed Bots (Bot API 9.6 от 2026-04-03 и 10.0 от 2026-05-08, сверено с документацией 2026-10-13; поля — `docs/approvals-bot.md`). Бот-менеджер живёт на посреднике (`relay/relayd.py` 0.4.0) — в той же границе доверия, что посредник (Р-69). Экземпляр просит пару (`POST /api/botpair/start`), страница показывает ссылку `https://t.me/newbot/<менеджер>/<префикс>_<номер пары>_bot?name=…` кнопкой и QR-кодом, владелец подтверждает в Telegram, служба получает `managed_bot`, сопоставляет бота по имени, сразу закрывает доступ к нему для всех, кроме владельца (`setManagedBotAccessSettings`), и один раз отдаёт экземпляру токен, номер бота и номер создателя (`POST /api/botpair/<pair_id>/token {secret}`). Сервис применяет токен тем же путём, что вставленный вручную (`setup_page/bot_setup.apply_token`).

**Почему так.**
- *Секрет пары отдельно от имени бота.* 256 бит, только в памяти сервиса, у посредника — sha256; ни в ссылке, ни в имени бота его нет. В предложении Hermes (NousResearch/hermes-agent #10591) ключом выдачи служит nonce из публичного имени бота — кто увидел имя, тот за 5 минут забирает токен; здесь так нельзя.
- *Токен у посредника не хранится.* Служба берёт его у Telegram (`getManagedBotToken`) в момент выдачи, отдаёт один раз и забывает пару; пары — в памяти, 15 минут (+3 минуты после создания бота). Перезапуск службы теряет начатые пары — дёшево: начать заново.
- *Аккаунт-создатель подтверждает владелец; без этого токен не сохраняется* (найдено независимой проверкой PR #28). Ссылку создания можно подсмотреть (QR на экране) и создать бота первым со своего аккаунта. Такой бот принадлежит постороннему: токен у него есть в @BotFather, снять закрытый доступ он, скорее всего, может, а с токеном подпишет данные входа Mini App за любой аккаунт, в том числе за владельца, — после сохранения такого токена сервис уже ничем не защищён. Поэтому полученный токен ждёт в памяти сервиса (10 минут, пока жива сессия страницы), страница показывает @имя, номер и имя создателя и просит «Да, это мой аккаунт»; «Нет, не мой» — токен выбрасывается, попытка помечается перехваченной.
- *Привязать можно только создателя.* Номер создателя записывается (`setup_state 'approvals_bot'` — пишет только страница), и бот согласований принимает привязку только от него (`binding.required_creator`). Другой аккаунт с действующей ссылкой получает объяснение, а все неиспользованные ссылки привязки отменяются; на странице — отметка. Это защищает только от ссылки привязки, попавшей к чужому аккаунту; от бота, созданного посторонним, не защищает (создатель — он) — от этого защищает подтверждение выше. Закрытый доступ к боту (`is_access_restricted`) — ещё один рубеж: посторонний до бота не доберётся; посредник выдаёт токен только после того, как попытка закрыть доступ закончилась.
- *Сопоставление только по имени бота.* Окно создания даёт владельцу изменить имя; тогда посредник получит бота без пары и (в 0.4.0) не тронет его; с 0.5.0 такой бот привязывается кодом — Р-78. Сопоставлять по «первому пришедшему боту» или по номеру создателя нельзя: номера владельца экземпляр до привязки не знает, а первый пришедший бот мог быть чужим. Владельцу — крупно «Не меняйте адрес бота» и объяснение после истечения пары.
- *Сервис забирает токен сам, не браузер.* Спрашивает посредника, пока тот не выдаст токен или не ответит «пары нет»; каждый запрос — с общим сроком и ответом не длиннее 64 КБ. «Выйти везде», выход сессии, «Отменить» и ручной ввод токена снимают попытку в любом незаконченном состоянии; прямо перед сохранением, под общей с ручным вводом блокировкой, ещё раз проверяются сессия и то, что токен вручную не меняли, — ручной ввод главнее. Ссылку для страницы сервис собирает сам из проверенных имён: посредник не может показать владельцу чужую ссылку. Токен принимается, только если бот — с тем именем, что сервис вписал в ссылку, и с номером, о котором сообщил посредник (`getMe`).
- *Адрес посредника — только из окружения* (`SHTURMAN_BOT_MANAGER_API`, по умолчанию `https://relay.sh.namre.app`, `off` — выключить). Подменённый посредник отдал бы сервису бота, токен которого у подменившего; поэтому ни страница, ни внутренний API адрес не меняют, а ассистент не может запустить создание (маршрута во внутреннем API нет).
- *Код приглашения — по выбору держателя, по умолчанию выключен* (`--botpair-require-invite` или `RELAY_BOTPAIR_REQUIRE_INVITE=1`). Без него пару может начать любой, кто дойдёт до API посредника; бот создаётся только после подтверждения человеком в Telegram и принадлежит ему. Пределы: 10 новых пар с адреса (IPv6 — с /64) за 15 минут, не больше 5 ожидающих пар с одной широкой сети (IPv4 /24, IPv6 /48 — одна сеть не займёт общий предел, перебирая подсети), 200 ожидающих пар всего. **Цена открытого режима — отказ в обслуживании:** у кого много разных сетей, тот может занять все 200 пар, и на 15 минут создание в одно нажатие перестанет работать у всех; ручной путь от этого не страдает, а экземпляр без пары просто получит «посредник занят». С кодом это закрыто, но каждому владельцу — в том числе со своим доменом, не подключённому к посреднику, — пришлось бы просить код у держателя. Выбрано: по умолчанию без кода; при злоупотреблении держатель включает код одной строкой. Код при этом не расходуется. У выдачи токена (`/api/botpair/<id>/token`) общего предела неудачных нет: секрет — 256 бит, перебирать его бессмысленно, а общий предел дал бы постороннему остановить выдачу всем; остаётся предел на адрес.
- *Цена говорится до кнопки.* Держатель посредника технически может в любой момент получить токен (`getManagedBotToken`), а с ним подделать вход в Mini App и нажатия в нём, получать обновления бота, заменить токен; при бизнес-режиме — читать личные переписки. Это в тексте на странице, в `./ops/doctor.sh` (`approvals-origin`), в `shturman bot-status` и в `GET /api/executor/status` (`created_via`). Перейти на своего бота можно в любой момент: «Сменить токен» и удалить прежнего у @BotFather.
- *Токен бота-менеджера не проходит через агента.* Держатель вводит его на странице посредника по ссылке `relayctl manager-link` (секрет — после «#», 15 минут; одноразовая — до первого успешного сохранения: неудачные попытки её не тратят, новая ссылка отменяет прежние; запрос к Telegram идёт без блокировки базы службы) или командой `relayctl manager-token` из стандартного ввода. Хранится в `/var/lib/shturman-relay/manager.token` (600, пользователь службы), а не в `/etc/shturman-relay` через `LoadCredential`, как задумывалось: служба работает без root и с `ProtectSystem=strict`, а токен со страницы записывает именно она; учётные данные systemd она записать не может. По защите это то же: читают root и пользователь службы.

**Что остаётся.** Ничего из этого не проверено с настоящим Telegram: окно создания, поля обновления, закрытый доступ у управляемого бота (и работают ли у него Mini App и бизнес-режим), может ли владелец убрать бот-менеджер у своего бота. Список живой проверки — `docs/approvals-bot.md`. Служба посредника 0.4.0 на посредник в AWS не ставилась.

## Р-78. Бот с изменённым адресом привязывается кодом, который присылает боту-менеджеру его создатель

2026-10-13, дополнение к Р-77 после живой проверки: владелец изменил адрес бота в окне создания, посредник 0.4.0 записал «бот без ожидающей пары — пропущен», а страница бесконечно показывала «Жду…». **Что.** Служба посредника 0.5.0:

1. Бота, созданного под менеджером без подходящей пары, не выбрасывает, а запоминает «сиротой»: номер и адрес бота, номер создателя (`ManagedBotUpdated.user`) и время. Токен не берёт и не хранит. Доступ к боту сразу закрывает так же, как к боту пары (`setManagedBotAccessSettings`, только создатель). Сироты живут в памяти службы сутки; не больше 5 от одного создателя и 1000 всего (вытесняются самые старые); бот, уже выданный экземпляру, сиротой не становится (обновление о смене его токена).
2. У каждой пары — код привязки: 16 знаков из 31 (≈79 бит, `secrets`), годен, пока жива пара; у посредника — только sha256. Он отдаётся экземпляру в ответе `start` (`claim_code`, `claim_link`); ссылку `https://t.me/<менеджер>?start=<код>` сервис собирает сам.
3. Служба опрашивает менеджера с `allowed_updates: ["managed_bot", "message"]`. Сообщение `/start <код>` (или просто код) в личном чате с менеджером от пользователя U: пара ищется по коду (сравнение хешей за постоянное время, без раннего выхода), к ней привязывается самый свежий сирота, **созданный U**, — из созданных после начала пары, а если таких нет, из прежних. Дальше — как в обычном пути: запас времени, выдача токена по секрету пары, «Это ваш аккаунт?» на странице. Ответ U в чате — коротко: «Бот @… привязан, вернитесь на страницу» или причина («код не подошёл», «ботов, созданных вами по ссылке, не видно»), без токенов и чужих данных. Пределы: 10 сообщений от пользователя за 15 минут (дальше — один раз «слишком много попыток», потом молчание) и 60 неверных кодов от всех за минуту. Код в журнал не пишется — только номер пары.
4. Сервис принимает бота с адресом не из ссылки, только если посредник пометил его `claimed: true` **и** эта попытка получала код привязки; номер бота по-прежнему сверяется с `getMe`. Посредник 0.4.0 кода не отдаёт — подсказки нет, а бот с другим адресом, как и раньше, не принимается.

**Почему так.**
- *Личность удостоверяет Telegram.* Номер отправителя сообщения и номер создателя бота даёт Telegram; подделать ни то, ни другое экземпляр или посторонний не могут. Бот достаётся паре, только если код прислал **сам создатель этого бота**. Чужой код без участия создателя ничего не даёт: посторонний, приславший подсмотренный код, получит «ботов, созданных вами, не видно» и ничего не узнает о чужом боте; бот владельца остаётся сиротой.
- *Код отдельно от секрета пары.* Код виден в браузере владельца и в ссылке; секрет пары (выдача токена) — нет. Знание кода не даёт токена: токен по-прежнему получает только экземпляр, знающий секрет пары.
- *Сироты — только в памяти.* На диске нечего красть и нечего чистить; перезапуск службы их теряет — дёшево: бота можно удалить и создать заново по ссылке или подключить вручную.
- *Отклонено: «первый пришедший бот» и «бот того же номера, что откроет страницу».* Первый пришедший мог быть чужим; номера владельца экземпляр до привязки не знает (Р-77).

**Остаточный риск.** Если владельца уговорят отправить менеджеру **чужой** код (например, прислав ему ссылку `t.me/<менеджер>?start=…` под видом «доделать настройку»), его бот-сирота достанется паре того, кто прислал ссылку, и тот получит токен этого бота. Сужают: нужен бот без пары, созданный владельцем за последние сутки, — то есть бот, который у владельца и так не подключён; ответ менеджера называет бота и говорит вернуться на свою страницу; страница чужого экземпляра покажет создателем аккаунт владельца, а привязать себя владельцем к такому боту в «Штурмане» может только создатель (Р-77). Ни данных экземпляра владельца, ни его переписки в этом боте нет. Что владельцу делать: такого бота удалить у @BotFather (`/deletebot`) и не открывать ссылок на бот-менеджер, которые прислал кто-то другой, — только со своей страницы настройки.

**Чего это не решает.** Бот, созданный с изменённым адресом **до** 0.5.0 или до перезапуска службы (служба его не запомнила), этим путём не привязывается: подключить его вручную (токен из @BotFather, «Сменить токен») или удалить и создать заново по ссылке со страницы (`docs/approvals-bot.md`).

## Р-79. Фоновые запросы Telethon по каналам — только по выбранным чатам и с паузами

2026-10-13, по решению владельца от 2026-10-13 (после проверки журнала пилота). **Что было.** На пилоте после входа в аккаунт Telegram просил подождать дважды за полчаса, и оба раза одинаково: 35 отказов (FLOOD_WAIT) почти за полсекунды. Запросы шли не от сервиса, а от самой библиотеки Telethon 1.45.0: список диалогов сообщает ей состояние каждого канала и супергруппы, и если по каналу 15 минут не было обновлений, она запрашивает разницу (`updates.GetChannelDifference`) — по всем таким каналам подряд, без пауз и мимо планировщика сервиса. Так шло бы круглые сутки, раз в 15 минут, в том числе по чатам, которые владелец читать не выбирал. Тот же отказ, вероятно, задевал и «Обновить список из Telegram» на странице настройки («подождите 24 с»).

**Что.** Запрос разницы по каналу проходит через `ChannelUpdatesThrottle` (`service/src/shturman/tg/client.py`):
- по каналу, которого нет среди включённых чатов аккаунта (`LiveIngest.wants_channel`), запрос в Telegram не уходит: Telethon получает ответ «разницы нет» (`ChannelDifferenceEmpty`) с прежним номером состояния и откладывает канал на свои 15 минут. До запуска приёма и во время входа не выбран никакой канал;
- по выбранному — не чаще одного в 2–3,6 с;
- пока Telegram велит ждать, по каналам в Telegram не уходит ничего, а ожидание записывается в журнал с числом секунд (одна строка вместо пачки).

Страницы списка диалогов (`messages.GetDialogs`, по 100 чатов) идут с паузой 1,5–2,7 с. Ожидание при обновлении списка на странице записывается в журнал; страница показывает отсчёт и повторяет запрос сама один раз (дольше двух минут не ждёт — пишет, через сколько попробовать). (С Р-81 список грузится в фоне и после ожидания продолжает с той же страницы; отсчёт с повтором заменён ходом загрузки.)

**Почему так.**
- *Ответ «разницы нет» вместо отказа.* Отказ «канал закрыт» заставил бы Telethon забыть канал и написать в журнал «аккаунт забанен в канале» — ложная тревога. Пустой ответ ничего не меняет: номер состояния прежний, канал не забыт, и когда владелец его выберет, Telethon запросит настоящую разницу с того же места.
- *Живые сообщения не теряются.* Новые сообщения Telegram присылает сам; запрос разницы нужен только чтобы добрать пропущенное. По выбранным чатам пропущенное дочитывает и загрузка истории (`sync.HistorySync`: после каждого переподключения и раз в 6 часов).
- *Цена.* Чат, который включится сам настройкой «брать новые группы», включается по первому живому сообщению, как и раньше; сообщения, пропущенные таким чатом до включения, Telethon больше не добирает по разнице.

**Что остаётся.** Проверено на тестах с настоящим `MessageBox` Telethon 1.45.0 (повтор пачки из 35 каналов: в Telegram уходят только выбранные). На пилоте — после обновления: в журнале не должно быть пачек `caused FloodWaitError`. Запрос разницы зовётся из приватного кода Telethon (`client/updates.py`, `self(get_diff)`); при смене версии Telethon проверить, что путь прежний (тест `test_telethon_update_loop_burst_sends_only_selected`).

## Р-80. Выбор чатов — и в приложении «Штурман»: экран «Чаты»; цена — у кого токен бота согласований, тот меняет, какие чаты читаются

2026-10-14, по решению владельца от 2026-10-14. **Что.** В приложении «Штурман» (Mini App бота согласований, Р-72) — второй экран, «Чаты»: то же, что шаг «Какие чаты читать» на странице «Переписка». Список диалогов аккаунта, поиск по названию и @имени, отбор по виду и «только выбранные», включение и выключение чтения чата, глубина истории для включаемого чата (те же варианты, по умолчанию — настройка аккаунта), «Обновить список из Telegram» (отсчёт и один повтор сам, если Telegram просит подождать), счётчик выбранных, выбор аккаунта, если их два. «Не сохранять» (исключение чата из архива) и «Вернуть в архив» — тоже, но без стирания уже сохранённого. Описание — `docs/miniapp.md`, раздел «Чаты».

**Решение владельца и его цена.** Владельцу были предложены три варианта: оставить выбор чатов только на странице, только просмотр в приложении, полный выбор в приложении. До ответа ему пересказан риск: войти в приложение может любой, у кого есть токен бота согласований (данные входа подписываются этим токеном, Р-74), а у бота, созданного «в одно нажатие» через бот-менеджер посредника, держатель посредника технически может получить этот токен (Р-77) — значит, такой человек сможет через приложение добавлять чаты к чтению ассистентом. Ответ владельца: «3. Риски я понимаю». Что это значит по существу: держатель токена бота согласований теперь может не только нажимать кнопки согласований за владельца (так было с Р-72), но и **расширять, что читает ассистент** — включать чтение любого чата аккаунта на любую глубину истории, — **видеть список всех диалогов аккаунта** (названия, @имена; текста переписки — нет) и **исключать чаты из архива** (новые сообщения из них перестают сохраняться). Сам текст переписки через приложение он не получит: экран показывает только список чатов, а читать включённое будет ассистент, к которому у держателя токена доступа нет. Тот же путь открыт держателю посредника и через подмену имени `setup-<имя>` (перехват данных входа, `docs/relay.md`, риск 1) — у владельцев, чей адрес идёт через посредника, даже с ботом, созданным вручную.

**Смягчения.**
1. **Каждое изменение из приложения — отдельным сообщением владельцу в бот согласований**: «Из приложения включено чтение чата «…» (глубина: …)» с подсказкой, что делать, если это были не вы; выключение, исключение и возврат — короче. Путь тот же, что у остальных служебных сообщений сервиса — очередь заданий (`bridge.notify_owner`) с повторами при сбое Telegram. Отказ (исключённый чат не включается) сообщением не сопровождается: ничего не изменилось.
2. **Журнал действий страницы**: `app.sync_on`, `app.sync_off`, `app.chat_exclude`, `app.chat_include` — с названием «Из приложения в Telegram: …», номером чата в Telegram и глубиной, без названий чатов; все четыре — в списке важных, потоком мелких действий их из вида не убрать.
3. **Список диалогов — из памяти сервиса** (с Р-81 — из базы, загрузка из Telegram в фоне). Открытие экрана, поиск и отбор в Telegram не ходят, как бы давно список ни загружался; включение и исключение тоже ищут чат только в загруженном списке. Запрос к Telegram — только кнопкой «Обновить список из Telegram» (не чаще раза в 30 секунд, как на странице). Так приложение не добавляет запросов к Telegram (Р-79) и не вызывает новую загрузку списка без нажатия.
4. **Только по одному чату**: «читать все группы или каналы разом» — только на странице.
5. **Без стирания**: «Не сохранять» в приложении не стирает уже сохранённое; стереть — только на странице.
6. **Цена сказана там, где её выбирают**: в тексте о цене рядом с кнопкой «Создать бота в одно нажатие», в «Чем «вручную» отличается от «в одно нажатие»?» на странице и в `docs/approvals-bot.md` дописано: через приложение держатель посредника сможет и менять, какие чаты читаются.

**Как.** Маршруты `GET /shturman-setup/api/app/chats`, `GET …/chats/{id}/dialogs`, `POST …/chats/{id}/sync`, `POST …/chats/{id}/exclude` — под той же сессией приложения и той же обёрткой (`miniapp.endpoint`: проверки `Sec-Fetch-Site`/`Origin` и своей метки, сессия только из `X-Shturman-App`). Применяются сразу, без карточки подтверждения: кто нажал, удостоверяет Telegram, как у нажатия в боте; изменения — в контексте владельца из Telegram (`authority.miniapp_context`). Логика общая со страницей — `setup_page/chats.py` (тот же список, те же проверки служебных чатов и исключённых, то же `confirm.apply_owner` для исключения); различия — только в том, что разрешено приложению. На адресе дашборда маршрутов нет: префикс отдаётся только на адресе страницы (421), а в проходе дашборда к сервису (`service_routes`) их нет ни в одной роли — тест это сверяет. Вход в приложение, проверка подписи `initData`, сессии и повтор не менялись.

**Что остаётся.**
- Держатель токена бота согласований может **удалять сообщения бота** в чате владельца (`deleteMessage` работает для своих сообщений бота) и так стереть оповещение о своём изменении, если угадает номер сообщения. Запись в журнале страницы он стереть не может — сверять с ним, если есть сомнения.
- Держатель токена видит список всех диалогов аккаунта (названия и @имена), а не только выбранных.
- Поток включений и выключений даёт поток сообщений владельцу; ограничения частоты нет (каждое изменение — одно сообщение, и это заметно само по себе).
- Отключить экран «Чаты» отдельно от приложения нельзя; защита от держателя токена — бот, созданный вручную у @BotFather («Сменить токен»), и адрес не через посредника.
- В настоящем Telegram экран не открывался; проверено тестами сервиса и в браузере на стенде.

## Р-81. Список диалогов аккаунта — в базе; загрузка в фоне и продолжение с той же страницы после «подождите»

2026-10-14, по решению владельца от 2026-10-14. **Что было.** Список диалогов аккаунта жил только в памяти сервиса и загружался библиотекой (`iter_dialogs` Telethon), пока ждал запрос страницы. Опыт (настоящий `iter_dialogs` Telethon 1.45.0 и `GuardedClient`, сеть подменена): страницы по 100 диалогов с паузой 1,5–2,7 с; 1 500 чатов — 16 запросов (около 30 с одних пауз), 4 000 — 41 запрос (около 83 с). Пилот стоит за Cloudflare, а он рвёт запрос через 100 с. Если Telegram на середине отвечал «подождите» (FLOOD_WAIT), всё загруженное выбрасывалось, и следующая попытка начинала с нуля — у большого аккаунта список мог не загрузиться никогда. После перезапуска сервиса списка не было, пока его не загрузят снова.

**Что.**
- **Загрузка в фоне.** «Обновить список из Telegram» (страница «Переписка» и экран «Чаты» приложения) только запускает загрузку и сразу отвечает; если она уже идёт, вторая не начинается. Экран показывает уже загруженное и ход: «Загружено N из ~M» (M — сколько диалогов назвал Telegram), «Telegram просит подождать — продолжу сам через S с», «Список не обновился: …». Пока загрузка идёт, экран раз в 2,5 с перечитывает список. Прежний отсчёт с одним повтором при 429 убран: ответа 429 для списка больше нет.
- **Продолжение с места.** Свой цикл по `messages.GetDialogs` (`service/src/shturman/tg/dialogs.py`) повторяет `_DialogsIter` Telethon 1.45.0: смещения `offset_date`, `offset_id`, `offset_peer` — по последнему диалогу страницы, у которого есть сообщение; закреплённые — только на первой странице; конец — неполная страница или ответ не «срез». При FLOOD_WAIT загрузка ждёт названное время и секунду сверху (ожидание прерывается остановкой аккаунта) и повторяет ту же страницу с теми же смещениями: ничего не теряется, полученные страницы снова не запрашиваются. Ожидание — одной строкой в журнале с числом секунд. Сбой связи — до трёх повторов той же страницы. То, что `iter_dialogs` делал попутно, делается так же: ключи доступа собеседников — в память Telethon (`_mb_entity_cache`; в файл сессии их пишет сам `_call` Telethon), состояние каналов — в поток обновлений (`try_set_channel_state`, см. Р-79).
- **Паузы и общая очередь.** Между страницами — прежние 1,5–2,7 с (`Spacer` в `GuardedClient`). Первая страница ждёт своей очереди в общем `Pacer` аккаунта, как запрос истории; каждая страница отодвигает следующий запрос истории, так что список и история не идут к Telegram вперемешку; FLOOD_WAIT, полученный одним, — ожидание и для другого.
- **Хранение в базе.** Таблица `tg_dialogs` (миграция `0031_tg_dialogs.sql`): класс и номер собеседника, вид чата, название, @имя, номер и время последнего сообщения, папка Telegram (`folder_id`: 1 — архив), закреплён ли, место в списке, когда обновлено; `tg_dialog_lists` — когда список загружен целиком и сколько диалогов назвал Telegram. Каждая страница пишется сразу. После полной загрузки диалоги, которых в ней не оказалось, убираются из списка — архив сообщений (`chats`, `messages`) это не трогает. Ключ таблицы тот же, что у `tg_sync_chats`, — на него сошлётся будущая группировка (папки Telegram, активность, свои группы); саму группировку это решение не делает.
- **Кто читает список.** Экран, поиск и отбор (в базе — подстрокой по названию и @имени в нижнем регистре), включение и исключение чата, текст карточки подтверждения, отметка «уже существующих» для настройки «брать новые чаты», дозагрузка истории — всё из базы. После перезапуска сервиса список есть сразу, в Telegram за ним не ходят.
- **Обновление по сроку.** Страница «Переписка» сама запускает обновление в фоне, когда список старше 10 минут (после неудачи — не чаще раза в 10 минут). Приложение само не обновляет (Р-80). «Обновить» не начинает загрузку, если список загружен целиком меньше 30 секунд назад.
- **Дозагрузка истории** (номер последнего сообщения каждого диалога, чтобы не опрашивать чаты без нового) по-прежнему нужен свежий список: она запускает загрузку или ждёт идущую и берёт номера из базы; если загрузка не дошла до конца — опрашивает чаты по одному, как раньше.
- **«Брать новые чаты сами»** включается, только если список хоть раз загружен целиком: иначе существующие чаты не отличить от новых (отказ 409 с объяснением; загрузка при этом запускается). Существующими считаются диалоги из базы; если список старше 30 секунд, свежая загрузка в фоне по окончании отметит и диалоги, появившиеся после прошлой.

**Числа** (опыт с подменённой сетью: тот же `GuardedClient` с настоящим `_call` Telethon, паузы с настоящими распределениями, время виртуальное; 20 прогонов). 4 000 диалогов, FLOOD_WAIT 25 с на 12-м запросе: 42 запроса к Telegram — 40 страниц, пустая 41-я (так Telethon узнаёт конец при ровной сотне) и один повтор 12-й; каждая полученная страница — один раз; 4 000 диалогов без потерь и дублей; до готового списка 106–114 с (медиана 110 с). Без отказа — 41 запрос, 80–88 с. Было на том же отказе: 12 запросов, загруженные 1 100 диалогов выброшены, список не готов.

**Цена.**
- В базе теперь хранятся названия и @имена **всех** диалогов аккаунта, а не только выбранных чатов (раньше — только в памяти процесса, пока он работает). Это данные владельца того же рода, что таблица `chats`; они попадают в резервные копии `./ops/backup.sh`. ## Р-82. Сферы: владелец разделяет работу и жизнь; шаг 1 — модель данных, папки Telegram, раскладки, мягкая граница для ассистента

2026-10-14, по решению владельца от 2026-10-14. **Что владелец хочет.** Разделять в «Штурмане» разную работу и жизнь — «Работа РАЗУМ», «Личное», «Преподавание», проекты по ЖК — не только для выбора чатов, но и для хранения и обработки. Ответы владельца на вопросы: сферу заводит он сам; **чат может быть в нескольких сферах** (или ни в одной); для ассистента — **мягкая граница**: по умолчанию ищет в сфере, о которой разговор, в другую — только если владелец её назвал или попросил искать везде, каждый результат помечен сферой; для ответов собеседникам — строго своя сфера. Своя обработка на сферу (при нескольких сферах — самая строгая настройка), своя модель (запрет внешней модели: такую сферу не видит и Hermes), сводки по сферам, удаление и выгрузка сферы — следующие шаги.

**Шаг 1 (это решение).**
- **Модель данных** (`0032_spheres.sql`): `spheres` (название, описание, порядок, `settings` — место под шаги 2–4, пока не используется), `sphere_chats` (многие-ко-многим), `projects.sphere_id` (проект — не больше чем в одной сфере), `tg_folders`, `sphere_folders`, `sphere_declined`. **Ключ чата — диалог аккаунта** `(account_id, peer_class, tg_id)`, общий с `tg_dialogs` и `tg_sync_chats`, а не `chats.id`: сферу назначают и чатам, которые ещё не читаются (всей папке сразу), а запись в `chats` для них сделала бы их видимыми ассистенту (`list_chats`) с названием без выбора владельца. С архивом ключ сходится через `chats.account_id` + `peers`. Внешнего ключа на `tg_dialogs` нет: строка списка исчезает при выходе из группы, решение владельца остаётся. Удаление сферы — только снятие её с чатов и проектов.
- **Папки Telegram**: `messages.getDialogFilters` — новый запрос в перечне разрешённых, только чтение, той же фоновой загрузкой и с теми же паузами, что список диалогов (Р-81); состав папки сервис вычисляет сам по правилу клиентов Telegram. Точно — явные перечни и правила по виду и архиву; приблизительно — «без звука» (общие настройки звука не видны), «прочитанные» и «контакты» (снимок на момент обновления списка). «Сделать сферу из папки» (повторно — дополнить) и «Связать папку со сферой» — новые чаты папки **предлагаются**, а не добавляются.
- **Раскладки списка чатов** на странице и в приложении: «Папки Telegram / Сферы / По активности / По виду» (и «Все»), разделы со счётчиком «читается X из Y», постранично внутри раздела. «Включить все» раздела — **только на странице** (с глубиной; исключённые и служебные пропускаются); в приложении — только «Выключить все», с одним сообщением владельцу в бот (Р-80 сохраняется: включение из приложения — по одному чату). Всё — в журнал действий.
- **Управление сферами** — на странице (раздел «Сферы», строка чата, проект) и в приложении (вкладка «Сферы», строка чата) сразу, с записью в журнал (`sphere.*`, `app.sphere_*` — среди важных). Через внутренний API (ассистент, держатель токена API) — **любое изменение ждёт нажатия владельца** в боте согласований (`spheres.create|update|delete|chats|project`), включая «убрать» и «удалить»: в шаге 3 снятие сферы ослабит строгую границу. Инструменты плагина не могут переименовать или удалить сферу.
- **Ассистент**: инструменты архива и плагина помечают результаты сферами и принимают `spheres`; новый инструмент `list_spheres` (внесён в перечень `include` в `ops/up.sh` вместе с `list_projects`, `get_project_page`, `get_owner_profile`, которых там не хватало). Правило мягкой границы — в описаниях инструментов, `instructions` сервера MCP и блоке `SOUL.md` мастера. **Это правило, а не принуждение в коде**: архив по-прежнему отдаёт любую сферу, если ассистент её попросит.

**Цена.**
- Ассистент может нарушить мягкую границу: модель может искать везде без просьбы. Пометки сфер в каждом результате делают это заметным, но не невозможным. Строгой граница станет только для ответов собеседникам (шаг 3).
- Держатель токена бота согласований (Р-80) теперь может через приложение и менять сферы — заводить, удалять, относить чаты. Это не расширяет чтения, но в шагах 2–4 сферы будут решать обработку и модель; к тому времени изменение сфер из приложения нужно будет пересмотреть (сообщение в бот или подтверждение). Сейчас — журнал, записи среди важных.
- В базе — описания папок Telegram (названия и перечни чатов) и три новых признака диалога (контакт, без звука, непрочитанное) — данные владельца того же рода, что `tg_dialogs`, наружу не отдаются; MCP их не читает.
- Ещё один запрос к Telegram на каждую загрузку списка.

**Что остаётся.** На настоящем аккаунте Telegram не проверено (разбор `getDialogFilters` — по схеме Telethon 1.45.0). Как настоящая модель соблюдает мягкую границу — проверит только пилот. Описание — `docs/spheres.md`.

## Р-83. Токен архива — в `.env` профиля Hermes; вызовы модели из исполнителя плагина — в области секретов профиля

2026-10-14, по находке оператора на пилоте 2026-10-14 (образ `nousresearch/hermes-agent:v2026.9.24`, Hermes 0.21.5). **Что сломалось.** Два признака сразу, с 2026-10-13 и 2026-10-14:
- архив (MCP-сервер `shturman`) отвечал шлюзу Hermes `401` на каждую попытку подключения (`Streamable HTTP rejected the initial connect (… HTTP 401 …) — retrying over SSE`, затем `parking`), хотя переменная `MCP_SHTURMAN_API_KEY` в окружении контейнера есть, а отдельный процесс в контейнере подставлял её и проходил проверку токена;
- все задания модели плагина (`llm.structured`, около 1 100 в час) падали, а чат с ассистентом при этом отвечал. Причину журнал не называл: исполнитель писал только вид задания.

**Почему (по коду Hermes тега `v2026.9.24`, коммит `f97608f`, сверено с исходниками того же тега).** В Hermes 0.21.5 секреты читаются через `agent.secret_scope.get_secret` (agent/secret_scope.py:200-228). Когда шлюз обслуживает несколько профилей (мультиплекс: `gateway.multiplex_profiles: true` в настройках, `GATEWAY_MULTIPLEX_PROFILES` или — по умолчанию — больше одного профиля, hermes_cli/gateway_multiplex_mode.py:228-258; флаг ставит gateway/run.py:3504), действуют два правила:
1. Внутри области секретов профиля промах по ключу даёт значение по умолчанию и **не** читает окружение процесса. Область для ходов, для подключения MCP при старте (`_discover_gateway_mcp_tools`, gateway/run.py:1882-1906, каждая — под `_profile_runtime_scope`, gateway/run.py:1810-1842) и для повторного разбора настроек MCP (`_owner_secret_scope`, tools/mcp_tool_discovery.py:102-120) строится только из `.env` профиля (`build_profile_secret_scope`). `_interpolate_env_vars` (tools/mcp_tool_config.py:284-298) при промахе оставляет `${MCP_SHTURMAN_API_KEY}` как есть — шлюз отправляет архиву буквально `Bearer ${MCP_SHTURMAN_API_KEY}`. Сама подстановка в `load_config` устроена так же (hermes_cli/config.py:1543-1559). В отдельном процессе мультиплекс выключен и области нет — поэтому там подстановка работала.
2. Вне области чтение ключа бросает `UnscopedSecretError`. Исполнитель плагина работает в фоновой задаче шлюза, вне хода ассистента, и `ctx.llm` (agent/plugin_llm.py — областью не занимается) падает на чтении ключа провайдера. Ход ассистента область ставит сам — поэтому чат отвечал.

Сам Hermes хранит токены MCP-серверов именно в `.env` профиля: `hermes mcp add` с токеном пишет `MCP_<ИМЯ>_API_KEY` через `save_env_value` (hermes_cli/mcp_config.py:304-341: «The secret lives in the profile's `.env`»). Наше `MCP_SHTURMAN_API_KEY` только в окружении контейнера — путь, который Hermes при мультиплексе намеренно не видит.

**Проверено вне Docker** на пакете Hermes, установленном в отдельный venv из исходников тега `v2026.9.24` (ключевые файлы сверены с тегом побайтно): при включённом мультиплексе и ключе только в окружении `_load_mcp_config()` в области профиля оставляет `${…}`, а `ctx.llm` из фоновой задачи падает с `agent.secret_scope.UnscopedSecretError`; при выключенном — оба работают. После записи ключа в `.env` профиля подстановка работает при любом режиме; исполнитель плагина с областью профиля запуска выполняет `llm.structured` и `llm.text` через настоящий `ctx.llm` (подставной провайдер на 127.0.0.1). **Что на пилоте включило мультиплекс** (второй профиль в `data/hermes/profiles` или явная настройка) — по коду не определить; подтвердит строка журнала шлюза при запуске (`Serving every profile on this host…` либо `Multi-profile hosting activated…`) и строка `archive-mcp` в `./ops/doctor.sh` («шлюз обслуживает профилей: N»).

**Решение.** Код и образ Hermes не меняются; только штатные механизмы.
- `./ops/up.sh` записывает значение `MCP_SHTURMAN_API_KEY` из окружения контейнера Hermes в `.env` профиля (`/opt/data/.env`) функцией самого Hermes `hermes_cli.config.save_env_value` — той же, что у `hermes mcp add`; сравнение и запись идут внутри контейнера, значение не печатается. Изменилось — Hermes перезапускается. Смена токена (`./ops/mcp-token.sh`, затем `./ops/up.sh`) доходит так же: Compose пересоздаёт контейнер с новым значением, функция обновляет `.env` профиля. Запись `mcp_servers.shturman` по-прежнему ссылается на имя переменной; сравнение «same/changed» не меняется. Отвергнуто: поле `env` у MCP-сервера (оно только для серверов stdio, а наш — по HTTP) и вписать токен прямо в `config.yaml` (секрет в настройках, которые показывает дашборд и которые попадают в выгрузки настроек).
- Исполнитель плагина вызывает модель внутри области профиля запуска — `tui_gateway.launch_profile_policy.async_launch_profile_scope_if_multiplexed`, той же, что Hermes ставит своим делам профиля запуска вне хода (gateway/run_turn.py:2296, gateway/run_notifications.py:1562). Без мультиплекса это пустой контекст. В другой версии Hermes без этой функции — пустой контекст и одна строка в журнале.
- Журнал исполнителя называет вид ошибки: имя класса или короткий код (`error_label`), без текста; одинаковые сбои — не чаще строки в минуту на пару «вид задания, вид ошибки», с числом свёрнутых.
- `./ops/doctor.sh`: `archive-mcp` в режиме с Hermes проверяет настоящее подключение — запись разворачивается штатной функцией Hermes в самом строгом виде (область профиля, мультиплекс) и идёт один запрос к архиву, смотрится только код; плюс отказы `401` архива в журнале ошибок Hermes за час (только число). Новая строка `jobs-failing` — доля неудачных попыток заданий модели за час и частые виды ошибок по счётчику сервиса (`llm_jobs` в `GET /api/status`, в памяти сервиса, только числа и виды ошибок).

**Цена.** Токен архива (только чтение) теперь лежит и в `data/hermes/.env` — рядом с ключом модели и токеном бота ассистента; дашборд Hermes показывает его среди ключей — скрытым, с кнопкой «показать» (`/api/env`, `/api/env/reveal`, hermes_cli/web_routers/config_env.py), за входом владельца. Ассистенту архив и так доступен через MCP, новых возможностей у него не появляется. Счётчик `llm_jobs` после перезапуска сервиса начинается заново.

**Проверенные версии Hermes.** Прежняя единственная — 0.21.5 (`v2026.9.24`); это решение проверено на ней же, вне Docker. В контейнере пилота — после `./ops/up.sh` (UPGRADING.md).

## Р-84. Реакция на сообщения: уведомления «вам написали» и «вас упомянули», наблюдатель на странице, повтор после сбоя

2026-10-14, по решению владельца от 2026-10-14 («делаем всё»). До этого на пилоте новое сообщение только сохранялось в архив; голосовые и фото разбирались, ночью — обязательства и факты; уведомлений не было, правил наблюдателя — ни одного (их можно было завести только через внутренний API), автоответ выключен. Отправку (`SHTURMAN_SENDING`) и автоответ это решение не трогает.

**1. Уведомления.** Сервис сам, без модели, пишет владельцу в бот согласований (`notify/`, миграция `0033_notify.sql`):
- **личное сообщение** — новое входящее от человека в личном чате основного аккаунта (не «Избранное», не чат с ботом, не служебные чаты Telegram и не управляющий бот, не от бота и не через бота, не правка, не своё); дальше — настройка «от всех / только из выбранных сфер / только от выбранных людей» (по числовому ID, выбор — из собеседников личных чатов архива);
- **прямое обращение в группе** — то же определение, что у ответов в группах: разметка упоминания числового ID владельца, ответ на его настоящее сообщение в том же чате и теме, заданное владельцем обращение в начале реплики. Без поиска имени по тексту. **Одно добавление:** разметка упоминания `@имени` (тип `mention`), если это `@имя` владельца, как его сообщил Telegram (`peers.username`). Telegram размечает упоминание человека с `@именем` именно так, без числового ID: без этого обращения к владельцу с `@именем` не находились бы почти никогда. Это всё ещё разметка Telegram, а не поиск по тексту; в цитате, коде и пересылке она не считается. Автоответу в группах (`is_direct_address`) это ничего не добавляет;
- **только живые сообщения** (`message.live`; загрузка истории, импорт, сверка и правки событий не порождают). Сообщение старше трёх часов, пришедшее «живым» после перерыва связи, — тоже не уведомление.

Текст: кто, где (и сфера чата), когда, начало сообщения до 300 знаков одной строкой — без невидимых и управляющих символов, простым текстом (как отрывок у наблюдателя). Голосовое — «🎤 голосовое, 0:42», фото — «📷 фото», документ — «📎 файл «имя»». Отдельное «досылать расшифровку» не делаем: лишнее сообщение; но текст берётся в момент отправки, и расшифровка, успевшая к этому времени (пачка, тихие часы, «ещё N»), попадает в уведомление. Скрытое защитой — без текста: «скрыто защитой — решите в карточке защиты»; для этого живой путь публикует скрытое отдельной темой `message.held`, которую слушают только уведомления, — остальные модули скрытого по-прежнему не видят. Кнопок нет.

Частота: «сразу, но не чаще раза на чат за N минут» (остальное — одним уведомлением «…и ещё 3 сообщения») или «пачкой раз в 15/30/60 минут»; тихие часы по часовому поясу владельца (`SHTURMAN_TIMEZONE`) — всё, что пришло или созрело в них, уходит одной пачкой в их конце. Срочное не выделяется: без модели «срочность» не определить. Перед отправкой каждое сообщение проверяется заново: удалено, чат исключён, такие уведомления выключили, **владелец уже ответил в этом чате после него** — тогда уведомление молча снимается. Без своего бота согласований уведомлений нет вовсе: через Hermes чужой текст попал бы в разговор ассистента.

**Что включено после обновления — решение.** Включено: личные «от всех», прямые обращения в группах, «сразу» не чаще раза на чат за 10 минут, начало сообщения показывается, тихие часы 23:00–08:00. Почему так: владелец просил «делаем всё»; новых получателей данных нет — текст уходит туда же, куда уже уходят карточки сервиса, в чат бота согласований самого владельца; частота и тихие часы ограничивают шум; выключить или сузить можно сразу на странице, в приложении и сказав ассистенту. Цена: если токен бота согласований есть ещё у кого-то (бот, созданный «в одно нажатие» через посредника, Р-77), этот кто-то технически может переслать себе сообщения бота владельцу — а в них теперь начала личных сообщений. Для такого случая — «не показывать начало сообщения». Это сказано владельцу на странице и в `UPGRADING.md`.

**Кто меняет настройки.** Со страницы — сразу (это сам владелец). Через внутренний API (ассистент) — расширение ждёт нажатия в боте (`notify.settings`): больше личных сообщений, новые люди или сферы, обращения в группах, новое обращение по имени, «показывать начало». Сужение — сразу, с сообщением владельцу. Время и частота — не про то, что и о ком уходит, а про то, когда: применяются сразу. **В приложении «Штурман» — только сужение и время.** Включать там тоже можно было бы — уведомления идут только владельцу, чтения они не расширяют, — но войти в приложение может держатель токена бота согласований (Р-80), а именно ему доступны сообщения этого бота. Поэтому расширение — только на странице; из приложения сервер его отвергает (`page_only`), а каждое изменение оттуда бот сообщает владельцу. Журнал — `notify.settings`, `app.notify` (в списке важных), коды и числа.

**2. Наблюдатель на странице.** Раздел «Наблюдатель»: правила (слова и выражения, чаты и сферы, вкл/выкл), создание, правка, удаление, последние срабатывания — правило, чат, время, итог, совпавшие слова, причина от модели и ссылка, **без текста сообщения**. Со страницы — сразу (`confirm.apply_owner` тех же действий `watch.rule_*`), журнал `watch.*`. Три шаблона кнопкой: «Сроки и деньги» (срок, дедлайн, аванс, оплата, счёт, договор), «Срочно» (срочно, горит, asap, немедленно, как можно скорее), «Ваше имя» (поле для имени и вариантов). **Сферы:** у правила появились сферы (`watch_rules.sphere_ids`) — правило смотрит группы и каналы своих чатов и своих сфер, в том числе добавленные в сферу позже; личные чаты сфер наблюдатель по-прежнему не смотрит. Добавить сферу правилу через внутренний API — расширение, ждёт владельца. Страница прямо говорит: сообщение с совпадением уходит модели — её провайдеру.

**3. Повтор после сбоя.** Из-за сбоя плагина (Р-83) на пилоте 688 вложений помечены «не получилось», а прогоны обработки отказались от части запросов. Повтор (`retry.py`): вложения с причиной сбоя модели (`model:…`, `lost_job`, `bad_answer`) не старше `SHTURMAN_MEDIA_DAYS`, не удалённые, из неисключённых чатов, при включённом разборе — снова в очередь, попытки с нуля; «пропущено» (вид файла, размер, нет файла, нечем скачать) и прочие причины не повторяются. Запросы обработки, от которых прогоны отказались (`given_up`), — в «повторить»: следующий прогон поставит их первым делом и проверит их сообщения заново; миграция `0027_late_content` для этого не нужна — отметка прогона не сбрасывается, у запроса свои сообщения. Страницы памяти без сводки пересобираются сами — их только считаем. `--since ДАТА` — с какой даты считать сбой (время отметки «не получилось» и время запроса). Запускает владелец: кнопкой на странице или оператор по его решению командой `shturman retry-failed` (`--dry-run` — только показать). Во внутреннем API повтора нет: повторный разбор снова отправляет данные провайдеру модели и тратит запросы, ассистент его не запускает. Итог — числа в `GET /api/status` (`retry_*`), `./ops/doctor.sh` (строка `retry`) и на странице; журнал `retry.failed`.

**Не проверено.** Всё — на подставных Telegram и модели: тесты и браузерный стенд. Настоящий Telegram (как часто приходит разметка `mention_name` и `mention`, ответы в темах), настоящий объём уведомлений на пилоте и повтор на настоящих 688 вложениях — нет.

## Открытые вопросы

- **Убирать ли у Hermes `NET_BIND_SERVICE`** (Р-76). С ним root в контейнере может занять свободный порт ниже 1024 на хосте — 80 или 443, пока Caddy остановлен (перезапуск, обновление), — и на это время подменить прокси, в том числе пройти проверку Let's Encrypt за это имя. Чужой трафик это право читать не даёт. Нужно ли оно образу Hermes `v2026.9.24`, не проверялось; убирать — отдельным решением владельца после проверки на стенде с настоящим образом.

- **Бот согласований в одно нажатие в настоящем Telegram** (Р-77): окно создания по ссылке `t.me/newbot/…`, поля `managed_bot`, закрытый доступ у управляемого бота и работают ли при нём Mini App и бизнес-режим; может ли владелец убрать бот-менеджер у своего бота (документация об этом молчит). Список проверки — `docs/approvals-bot.md`.
- **Mini App в режиме без Hermes** (Р-75). Нужен внешний адрес по `https` только для страницы настройки — а это и есть то, что режим без Hermes наружу не публикует. Публиковать ли его там по решению владельца (как необязательное исключение), или в этом режиме приложению не быть — не решено.
- **Mini App в настоящем Telegram** (Р-72…Р-74): открывается ли кнопка на телефоне, в Desktop и в Telegram Web; принимает ли Telegram адрес с портом 8443, адрес из IP и адрес у посредника; проходят ли настоящие данные входа нашу проверку подписи (в том числе с полем `signature`); работает ли «добавить на главный экран». Проверено только на стенде с данными, подписанными тем же способом.
- **Открывается ли Mini App у владельца в России** (дополнение 3): приложение идёт с телефона напрямую на адрес экземпляра, мимо Telegram; Cloudflare Access перед адресом страницы настройки приложение не пропустит (вопрос В13 дополнения 3).
- **Подтверждение отправки биометрией телефона** в Mini App (дополнение 3) — не сделано.
- **Кнопки под сводками после решения в приложении** остаются в боте (Р-72): хранить ли номера сообщений сводок, чтобы гасить и их.

- Язык документации: сейчас русский; нужен ли английский как основной для сообщества Hermes.
- **Считать ли «Открытое ограничение» снятым и разрешать ли отправку** — отдельно для режима без Hermes и для Hermes со своим ботом согласований (Р-42, Р-44, Р-45). Свой бот закрывает подделку нажатия; что остаётся — `docs/architecture.md`. До проверки на настоящем боте и решения владельца отправка выключена везде.
- **Живая совместимость внешнего MCP** (Р-11). В 0.0.7 реализован отдельный OAuth read-only gateway, по умолчанию выключенный. Конкретные облачные клиенты, публичный TLS, вход и отзыв проходят отдельную приёмку; `docs/remote-mcp.md`. Объём разрешения — весь доступный архив.
- **Клиент владельца на том же сервере.** Запущенный под тем же пользователем, что и стек, он может прочитать `.env` и управлять Docker. Рекомендовать только вариант с компьютером владельца или заводить отдельного пользователя ОС — не решено.
- **Проверка ключа модели сервиса.** Ключ, введённый на странице настройки, проверяется пробным вопросом модели до сохранения. Ключ, заданный в `.env`, проверяется только при ночной обработке; нужна ли для него команда немедленной проверки — не решено.
- **Вопросы `./ops/init-env.sh`.** Запасной терминальный путь спрашивает токен бота согласований, ключ, имя и адрес модели сервиса и ключи приложения Telegram подряд, хотя основной путь для них теперь страница настройки. Сократить ли список вопросов — не решено.
- **Порт 8443 на настоящих сетях** (Р-56). Не проверено, пускают ли на него сети, из которых владелец открывает страницу (корпоративные и гостевые сети иногда закрывают нестандартные порты), и как ведут себя хостинги и внешние защиты, кроме Cloudflare. Запасной путь — отдельное имя.
- **Как владельцу отличить настоящую страницу настройки от подделки в дашборде** (Р-56). Сейчас — только адрес и то, что вход идёт по ссылке с сервера. Нужен ли признак понадёжнее — не решено.
- **Режим без Hermes без модели** (Р-58, Р-62). Бот согласований стал первым шагом страницы и в этом режиме; модель осталась необязательным шагом runbook, экземпляр без неё — архив с поиском, без обязательств. Подтвердить, что это то, чего хочет владелец.
- **Адрес дашборда с путём.** `SHTURMAN_PUBLIC_URL` допускает путь после имени, а сервис получает его как `SHTURMAN_DASHBOARD_ORIGIN` и сверяет с адресом страницы. Проверено на стенде: сервис путь отбрасывает и сравнивает схему, имя и порт, с таким адресом он запускается; `./ops/doctor.sh` проверяет закрытость пути страницы в корне адреса дашборда. Работает ли с адресом с путём сам Hermes, не проверялось; запретить ли путь в `./ops/set-public-url.sh` — не решено.
- **Пустая переменная окружения — не «по умолчанию».** Сервис читает переменную, заданную пустой строкой, как пустое значение. Для адреса своей модели это обходит упаковка: `compose.yaml` передаёт `SHTURMAN_LLM_BASE_URL`, только если строка есть в `.env`, а пустую строку `./ops/up.sh` подменяет адресом по умолчанию. Перенести ли это правило в сам сервис — не решено.
- **Неразборчивый адрес останавливает сервис.** Значение `SHTURMAN_PUBLIC_URL` без `https://` (его можно вписать вручную или запасным путём `./ops/init-env.sh`) останавливает сервис переписки при запуске — проверено на стенде; как ведёт себя с ним Hermes, не проверялось. `./ops/up.sh` теперь останавливается на такой записи до перезапуска. Проверять ли адрес уже в `./ops/init-env.sh` — не решено.
- **Вход в дашборд Hermes по адресу из IP** (Р-67). По коду Hermes `v2026.9.24` адрес из IP допустим: `Host` сверяется с адресом из `dashboard.public_url` без учёта регистра (`docs/deployment.md`, «Без домена»). 2026-10-12 на сервере за NAT облака переход по адресу из IP дошёл до страницы входа «Штурмана» (Hermes принял адрес; `docs/address.md`, «Что проверено вживую»); вход до конца, со ссылкой активации, не проверялся.
- **Требования к серверу без Hermes.** `./ops/preflight.sh` проверяет те же 4 ГБ памяти; расход без Hermes не измерен.
- **Отложенная отвязка владельца при своём боте.** Если владелец вошёл в дашборд по ссылке восстановления, пока плагин в спокойном режиме, запрос «отвязать владельца» уйдёт сервису только после выключения своего бота — возможно, через недели — и тогда очистит доверенных и ждущие черновики.
- **Тихое уведомление владельцу об ужесточениях**, сделанных через внутренний API: выключение правила наблюдателя сейчас не сообщается никак.
- **Экземпляры прежней схемы с ботом Hermes в бизнес-режиме** (Р-59). Обновление их не трогает. Нужно ли со временем настойчивее вести владельца к отключению — не решено.
- **Совпадают ли идентификаторы сообщений в бизнес-потоке и в экспорте.** От этого зависит обещание «без дублей» для пары «бизнес-бот и экспорт». Проверяется только на настоящем аккаунте.
- **Идентификатор диалога «Коды подтверждения» в живых источниках** (Р-35).
- **Подписка ChatGPT для своей модели сервиса на настоящем OpenAI** (Р-64): принимает ли OpenAI код, полученный «вставкой адреса» на другом компьютере; что на деле значит `earliest_refresh_at`; принимает ли путь подписки строгую схему `text.format`; сколько лимита съедает ночной разбор. Проверяется только живым входом владельца.
- **Качество на настоящей модели**: извлечение обязательств, сводки страниц, текст автоответа, два скилла. Проверочного набора вопросов ещё нет.
- **Качество расшифровки на живых голосовых** (Р-63): измерено только на чистой речи; на голосовых с шумом и разговорной речью ошибок будет больше, насколько — не измерено. Скачивание через сессию и через Bot API проверено только с подставным Telegram.
- **Какая из двух моделей поиска по смыслу лучше на настоящей переписке** (Р-51). Измерено только на синтетическом наборе; менять ли модель по умолчанию — после проверки на вопросах владельца.
- Вход по почте: нужен ли, и чей почтовый сервер для него использовать.

Пункт у @BotFather — Secretary Mode: так он назван в документации Telegram (`core.telegram.org/bots/features`, раздел Business Bots, сверено 2026-10-07); прежнее название — Business Mode. Как называется раздел в настройках Telegram, где владелец подключает бота («Чат-боты» или Chat Automation), документация не говорит — уточнить на живом боте.
