# Обновление

Этот файл читает ИИ-агент перед обновлением экземпляра и пересказывает владельцу простыми словами. Само обновление делает `./ops/update.sh` (`docs/runbooks/update.md`); что такое выпуск и каналы — `docs/releases.md`. Обновление идёт по одной версии за раз, без перескоков.

**Какой раздел читать.** Раздел **цели** обновления — той версии, до которой обновляет `./ops/update.sh`. Её называет `./ops/update.sh --check` строкой «UPGRADING.md: «A → B» — прочитать и пересказать владельцу до обновления (git show <тег>:UPGRADING.md)». Текст брать с тега цели (`git show <тег>:UPGRADING.md`): в каталоге экземпляра лежит файл его нынешней версии, раздела цели в нём ещё нет. Строка «раздела для этой версии нет» значит: действий сверх `./ops/update.sh` не нужно. При `./ops/update.sh --all` — раздел каждого выпуска цепочки, до запуска. Два исключения:

- экземпляр на 0.0.13, а `--check` говорит «Обновлений нет», хотя есть 0.0.14 или новее, — его `./ops/update.sh` ещё не знает сброса истории: один раз раздел «0.0.13 → 0.0.14» (`git fetch --tags origin`, затем `git show origin/main:UPGRADING.md`);
- экземпляр старше 0.0.13 — там же, «Экземпляр старше 0.0.13»: его путь до 0.0.13 идёт по прежней истории, которой в этом репозитории нет.

**Форма раздела** (с 0.0.14; разделы до «0.0.12 → 0.0.13» — только история):

- **Для владельца** — что изменится для него, 1–3 строки простыми словами, готовые к пересказу; отдельно — что выключено и не включается само.
- **Вне скрипта** — что нужно сделать, кроме `./ops/update.sh`, и когда: до запуска или после. Шаг, на который нужно «да» владельца (правка прокси, `sudo`, его решение или нажатие), начинается словами «Стоп-точка» — тогда `./ops/update.sh` без ключа `--upgrading-read` не запустится. Ничего нет — «нет».
- **Шаги** — команда, ожидаемый вывод, проверка. Миграция базы называется по имени файла; её применяет `./ops/up.sh`.
- **Откат** — только то, что не покрывает общий порядок ниже: правки прокси, настройки вне репозитория, действия владельца в Telegram.

**Откат — общий порядок.** Если проверка после обновления не прошла, `./ops/update.sh` откатывает сам: код — всегда; базу и `data/` из копии, снятой перед обновлением, — если применились миграции или сменился образ Hermes, и только с разрешением владельца: он нажимает «Разрешить» в боте согласований, карточку присылает сам скрипт (запасной путь, когда бот недоступен, — фраза в терминале человека). Обновлён с `--no-auto-rollback` — при провале после миграций скрипт останавливается (код 3) и называет команду отката: `./ops/restore.sh --rollback`, тоже через бот. Вернуть прежнюю версию позже, после удачного обновления, — `./ops/restore.sh --rollback` (пока не было следующего обновления) или `./ops/restore.sh --from <метка копии>` вместе с кодом той версии (`docs/runbooks/restore.md`).

## 0.0.13 → 0.0.14

**Для владельца.** Репозиторий «Штурмана» на GitHub начат заново — один раз. Код — тот же 0.0.13 плюс изменения из `CHANGELOG.md` («0.0.14»); данные, `.env`, база и Hermes этим не затрагиваются, видимых изменений нет. Если план попросит, — обычная кнопка «Разрешить» в боте согласований. Терминал владельцу не нужен.

**Вне скрипта.** Экземпляру на 0.0.13 — один раз шаги 1–3 ниже, до `./ops/update.sh`: его скрипт сброса истории ещё не знает, и новых выпусков для него нет («Обновлений нет»). Начиная с 0.0.14 `./ops/update.sh` делает это сам после `git fetch`.

Зачем. Новые выпуски — не потомки прежнего коммита экземпляра, а `./ops/update.sh` идёт только вперёд по истории. Файл `ops/history-reset` новой истории называет прежний коммит, который она продолжает: `4f10f6e812a0aacb04c9557d30a98846298693d6` (`v0.0.13-rc.1`). `./ops/history-reset.sh` проверяет, что нынешний код экземпляра — этот коммит или раньше него в прежней истории, и записывает переход локально: `git replace --graft <первый коммит новой истории> 4f10f6e…`. Отслеживаемые файлы, `.env`, данные и Docker не меняются, в сеть скрипт не ходит. Дальше — обычный порядок: по одному выпуску, с копией, проверкой и откатом.

**Перед началом.** `./ops/state.sh show`, `./ops/doctor.sh`; `cat VERSION` — `0.0.13`, `git rev-parse HEAD` — `4f10f6e812a0aacb04c9557d30a98846298693d6`. Версия меньше 0.0.13 — «Экземпляр старше 0.0.13» ниже. Другой коммит той же версии — шаг 3 скажет, можно ли перейти.

**Шаги** (агент; владельцу — только кнопка в боте, если план её попросит).

1. `git fetch --quiet --tags origin` — без ошибок. `would clobber existing tag` — стоп, сказать разработчику: в новой истории не должно быть тегов с прежними именами.
2. `mkdir -p local && git show origin/main:ops/history-reset.sh > local/history-reset.sh` — скрипт перехода из новой истории; кладётся в `local/` (вне git), отслеживаемые файлы не меняются.
3. `bash local/history-reset.sh --dry-run`, затем `bash local/history-reset.sh`. Ожидается: «Сброс истории: первый коммит новой истории … продолжает прежний 4f10f6e812a0 (v0.0.13-rc.1) — записано локально (git replace)…». Код 3 и «…перейти на неё нельзя» — стоп: ничего не изменено; пересказать владельцу причину из вывода, сказать разработчику, ничего не сбрасывать.
4. Обычный порядок `docs/runbooks/update.md` с шага 1. `./ops/update.sh --check` покажет цель — первый выпуск новой истории (`v0.0.14-rc.1` в канале `pilot`; в канале `release` — `v0.0.14`, когда выйдет; до того — «Обновлений нет»), этот раздел, копию и откат. Обновляет прежний `./ops/update.sh` экземпляра — переход для него уже записан.
5. Проверка после: `ИТОГ ОБНОВЛЕНИЯ: OK`; `./ops/doctor.sh` без новых `FAIL`; `git replace -l` — один коммит (первый коммит новой истории). `local/history-reset.sh` больше не нужен; удалить его — с «да» владельца.

Записи прежних выпусков в `releases.json` остаются, хотя их тегов в новой истории нет: экземпляру на 0.0.13 они позади, и сервис сообщит владельцу только о новых; `./ops/update.sh` смотрит на теги, а не на список.

**Откат.** Общий порядок: `./ops/restore.sh --rollback` возвращает прежний коммит `4f10f6e…` (он остаётся на экземпляре); запись перехода не мешает ни ему, ни следующему обновлению. Снять сам переход (пока экземпляр на прежнем коде): `git replace -d <первый коммит новой истории>` — тогда новые выпуски снова «не впереди».

**Экземпляр старше 0.0.13.** Его путь до 0.0.13 — прежняя история, а её в открытом репозитории нет: она хранится в закрытом репозитории проекта (`docs/releases.md`, «Сброс истории и закрытый репозиторий»). От разделов тех версий ниже осталась только история. Проверка — `git tag -l 'v0.0.13-rc.1'`:

- **Тег есть** (экземпляр получил его `git fetch` до сброса) — прежние выпуски на экземпляре целы. Шаги 1–3 выше запишут переход и для него; дальше обновление идёт по прежним выпускам (кандидаты `v0.0.8-rc.1`…`v0.0.13-rc.1`) по одному, затем на новую историю. Раздел каждого прежнего выпуска читается с его тега, `git show <тег>:UPGRADING.md`, как обычно. Экземпляр без `./ops/update.sh` (старше 0.0.8) — сначала `docs/runbooks/update.md`, «Первое обновление по этой схеме».
- **Тега нет** — прежних выпусков на экземпляре нет, шаг 3 остановится («…которого на этом экземпляре нет»). Стоп: сказать владельцу простыми словами — «обновить сам не могу: нужной части истории нет в открытом репозитории, нужен разработчик» — и обратиться к разработчику; строка дефекта.
