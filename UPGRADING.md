# Обновление

Этот файл читает ИИ-агент перед обновлением экземпляра. На каждую версию, требующую действий, здесь будет раздел одной формы:

- **С какой версии на какую.**
- **Что меняется** для владельца.
- **Перед началом:** резервная копия и её проверка (стоп-точка).
- **Шаги** — каждый с командой, ожидаемым выводом и проверкой.
- **Откат** — как вернуться на прежнюю версию.

Обновление всегда идёт по одной версии за раз, без перескоков.

## 0.0.7 → 0.0.8 (не выпущено)

**Что меняется для владельца.** Страница «Переписка» начинается с бота согласований — первым шагом, в обоих режимах установки: без него запросы ассистента, которые должен подтвердить владелец, отклоняются (решение Р-62). Вторым шагом владелец выбирает один из двух способов подключения: «Ассистент видит всё как вы» (вход в свой аккаунт на чтение и выбор чатов) или «Ассистент — отдельный сотрудник» (бизнес-режим у бота согласований для личных чатов, по желанию аккаунт ассистента для групп). У шагов появились «Что это даст» и вопросы с ответами, вверху — частые вопросы. В «Дополнительно» остались своя модель, «Что собрано» и журнал. Паузы между запросами к Telegram стали случайными (`docs/service.md`, «Правила сессий»). **Отправка выключена и этим обновлением не включается.**

На обновлённом экземпляре ничего не отключается: аккаунты, чаты, бот согласований, бизнес-режим и выгрузки остаются как были. Способ подключения ещё не выбран: подключённое раньше страница показывает без номера с просьбой выбрать способ, а сервис в состоянии страницы подсказывает способ по уже подключённому. Выбрать его владелец должен один раз сам; сменить можно в любой момент. Если бот согласований уже настроен и владелец привязан, первый шаг сразу отмечен готовым.

`./ops/doctor.sh` теперь и в режиме с Hermes показывает `WARN approvals-bot`, пока бот согласований не настроен. Это не ошибка обновления: бот заводит владелец сам, первым шагом страницы. Строка `approvals-business` при выключенном бизнес-режиме теперь `PASS`, а не `WARN`.

**Перед началом.** `./ops/state.sh show`; `./ops/backup.sh` и проверка копии по статусу, как в разделе «0.0.6 → 0.0.7». Без свежей проверенной копии — стоп.

**Шаги.**

1. `git pull` — получить опубликованный release commit; `cat VERSION` показывает новую версию; прежний commit сохранить для отката.
2. `./ops/up.sh` — пересобирает образ сервиса и перезапускает Hermes, если изменился плагин. Новых миграций нет: выбор способа хранится в существующей таблице `setup_state`.
3. `./ops/doctor.sh`: ожидается `ИТОГ: OK`, без `FAIL setup-origin`, `FAIL setup-isolation` и `WARN plugin-code`. `WARN approvals-bot: …не настроен` допустим — сказать владельцу, что бот согласований теперь первый шаг страницы «Переписка» и заводит его он сам.
4. Сказать владельцу простыми словами: на странице «Переписка» нужно один раз выбрать способ подключения; ничего из подключённого при этом не пропадёт. Ссылку на страницу (`./ops/setup-link.sh`) — только по его явной просьбе.

Новых стоп-точек нет.

**Откат.** Схема базы не менялась: вернуть прежний commit и `./ops/up.sh`. Запись о выбранном способе в `setup_state` прежняя версия не читает и ей не мешает.

## 0.0.6 → 0.0.7

**Что меняется.** Добавляются ограниченные задачи ответа, продолжение после решения владельца, раздельные чтение/раскрытие, Telegram-управление источниками и группами и подготовка без доставки. Полный штатный Hermes сохраняется. Старые правила автоответа не должны превратиться в права на новые источники или все группы. Отправка, провайдер, публичный доступ и новые credentials автоматически не включаются.

**Перед началом.** Прочитать `AGENTS.md`, `docs/service.md` и `docs/runbooks/validate-pilot.md`; выполнить `./ops/state.sh show` и определить уже выбранный режим. Снять `./ops/backup.sh`, убедиться по статусу, что архив и выгрузка базы читаются. Не открывать копию: в ней личные данные и секреты. Эта проверка оглавления не заменяет восстановление копии на отдельном стенде. Без свежей проверенной копии обновление остановить.

**Шаги.**

1. Получить опубликованный release commit 0.0.7 штатным обновлением репозитория. `cat VERSION` должен показать `0.0.7`; сохранить прежний commit для отката. Не переключаться на произвольную незавершённую ветку.
2. Объяснить владельцу новые миграции и получить решение на их применение. Они добавляют служебные исключения, задачи и источники, достоверную Telegram-разметку, точные групповые области и защиту связанных черновиков. `./ops/up.sh` собирает сервис, применяет миграции при старте и перезапускает изменённый плагин Hermes. Старые миграции не переписываются; фактический порядок — `service/src/shturman/migrations/`.
3. **Стоп-точка (`sudo`, прокси).** В 0.0.7 образец прокси (`config/Caddyfile.example`) получил глобальный блок `admin unix//run/caddy-admin/admin.sock`, а `./ops/doctor.sh` — проверки `proxy-admin-tcp` и `proxy-admin-dir`: admin API Caddy на `localhost:2019` доступен контейнеру Hermes (сеть хоста), через него можно перенастроить прокси. С прежней настройкой прокси проверка покажет `FAIL proxy-admin`. Исправление — `docs/runbooks/deploy.md`, шаг 5б: положить `config/caddy-admin-socket.conf` в `/etc/systemd/system/caddy.service.d/admin-socket.conf`, добавить глобальный блок `admin` в начало настройки прокси, `caddy validate`, затем `sudo systemctl daemon-reload && sudo systemctl restart caddy` (не reload). Показать владельцу и получить согласие.
4. `./ops/doctor.sh`: ожидается здоровый сервис и архив, `PASS proxy-admin-tcp`, `PASS proxy-admin-dir`, сохранённый режим, без `FAIL setup-origin`, `FAIL setup-isolation` или предупреждения о старом коде плагина. Не печатать `.env`, полномасштабную конфигурацию Compose и личные сообщения. Если проверка не прошла — остановиться на причине.
5. Владелец сам открывает `/menu` в независимом боте сервиса, проверяет `/status`, `/config`, доверенных и правила. Если бота ещё нет, установка архива может работать без него, но сценарий независимых согласований не принят. Владелец заводит бота и входит в модель по прежнему защищённому пути; токены не проходят через агента.
6. При выбранном пилоте ответов владелец разрешает подготовку без доставки (`/prepare on` либо выбранный оператором режим `prepare_only`). Пройти отказ, разрешение источника, продолжение, просмотр и отзыв на искусственных данных. Сохранённый репетиционный черновик не разрешено доставлять после смены режима. Для настоящей доставки создаётся новая задача и выполняется отдельная приёмка владельца.
7. Только если владелец выбрал внешний источник, настроить закрытый реестр по `docs/external-sources.md` и проверить один источник. Секретный файл не попадёт в Hermes, git или отчёт. Если файла ещё нет, задачи не получают внешний источник автоматически. Обновление не публикует внутренний `/api/*` или setup page.
8. Пройти пилот из `docs/runbooks/validate-pilot.md`, отметить фактические результаты и непроверенное. `doctor.sh` и локальные unit-тесты не заменяют оценки реальных ответов владельцем. Решение включить доставку принимается отдельно после знакомства с остаточным риском.

**Откат.** Возврат только старого кода при новой схеме не считается проверенным откатом. Остановить обновлённые процессы; восстановить согласованную копию данных и базы вместе с прежним checkout/config по отдельной процедуре на изолированном стенде. Восстановление поверх личных данных — отдельное решение владельца. Не выполнять автоматический downgrade или удаление новых таблиц и томов. До успешной проверки восстановленного экземпляра доставка остаётся выключенной.

## 0.0.5 → 0.0.6

**Что меняется для владельца.** Появляется страница «Переписка» — отдельная страница в браузере, на которой он сам вводит ключи приложения Telegram, входит в свой аккаунт по QR-коду и выбирает чаты; терминал для этого больше не нужен. В мастере шаги «Бизнес-режим» и «Переписка и память» заменены одним шагом «Переписка»: он коротко объясняет, зачем это, и ведёт на страницу. Бот согласований и бизнес-режим из первой настройки убраны — они понадобятся, только когда владелец решит включать отправку. **Отправка сообщений выключена и этим обновлением не включается.** То, что уже настроено, — аккаунты, чаты, бот согласований, бизнес-режим, поиск по смыслу, защита — продолжает работать как работало.

Страница «Переписка» открывается по отдельному адресу: по умолчанию это то же имя, что у ассистента, но порт 8443. Владельцу порт ни знать, ни набирать не нужно — он переходит по кнопке и по ссылке. Почему адрес отдельный — `docs/architecture.md`, «Почему у страницы настройки свой адрес».

Что действует без включения:

- `./ops/up.sh` дописывает в `.env` одну несекретную строку — адрес страницы по умолчанию (`SHTURMAN_SETUP_URL`), если адрес дашборда задан, а этой строки ещё нет;
- схема базы меняется: одна миграция с новыми таблицами страницы настройки;
- через дашборд Hermes больше нельзя войти в аккаунт Telegram, управлять аккаунтами, выбирать их чаты и загружать выгрузку: эти действия из прохода дашборда к сервису убраны. Экранов для них в дашборде и не было; свои скрипты, которые ходили в `/api/plugins/shturman/service/tg/…` и `…/imports…`, перестанут работать (ответ 404);
- `./ops/doctor.sh` показывает новые строки `setup-*`, а строки про бота согласований — только когда он настроен.

Чтобы страница открывалась по кнопке, нужны две правки на сервере, обе — стоп-точки: второй блок сайта в обратном прокси и открытый порт 8443. Пока они не сделаны, ничего не ломается: страница открывается через туннель SSH.

Под Docker эта версия запускалась только на стенде разработки. Обновление по шагам 1–3 и 5 ниже (firewall на стенде нет) пройдено там один раз, 2026-10-07: экземпляр версии 0.0.5 с официальным образом Hermes, 20 000 импортированных сообщений и настоящим Caddy с прежним, одним блоком сайта; значения выдуманные, сертификат прокси внутренний, бот и аккаунт Telegram не подключались (`docs/deployment.md`). Этот проход нашёл, что Hermes после обновления продолжал исполнять прежний плагин, — теперь `./ops/up.sh` его перезапускает. На сервере с настоящими данными, ботом и сертификатом обновление не проходилось: первый проход и есть проверка. Если вывод шага не совпал с ожидаемым — остановиться и описать, что именно не так.

**Перед началом — стоп-точка.** `./ops/backup.sh`. Ожидаются строки «Копия готова» и «Копия базы готова». Без них дальше не идти: обновление меняет схему базы.

**Шаги (режим с Hermes).**

1. `git pull` — получить версию 0.0.6. Проверка: `cat VERSION` показывает `0.0.6`.
2. **Стоп-точка (миграции базы).** Объяснить владельцу, что сделает следующая команда, и получить согласие. `./ops/up.sh`:
   - дописывает в `.env` строку `SHTURMAN_SETUP_URL=https://<имя>:8443` и печатает её одной строкой: «Адрес страницы настройки переписки записан по умолчанию: …». Остальное в `.env` не меняется и не печатается. Если адрес дашборда не `https` или сам стоит на порту 8443, строка не появляется — см. «Другой адрес» ниже;
   - пересобирает образ сервиса переписки и перезапускает его; при старте сервис применяет миграцию `0016_setup_page.sql` — четыре новые пустые таблицы: ссылки входа, сессии, состояние входа и журнал действий страницы настройки. Существующие таблицы не меняются;
   - контейнер Hermes не пересоздаёт (его описание в `compose.yaml` не менялось), но **перезапускает**: печатает «Файлы плагина shturman изменились с прошлого запуска — перезапускаю Hermes…». Hermes держит плагин в памяти с запуска; без перезапуска он продолжал бы исполнять плагин версии 0.0.5 — мастер без шага «Переписка» и проход дашборда к сервису с маршрутами входа в Telegram и импорта, которые в 0.0.6 закрыты. Ассистент на время перезапуска (до минуты) не отвечает.

   Ожидается: строка про адрес страницы, строка про перезапуск Hermes, «Дашборд Hermes отвечает на локальном адресе.», затем вывод проверки с `ИТОГ: OK`. Строки `WARN plugin-code` в проверке быть не должно: она значит, что Hermes всё ещё исполняет прежний код плагина, — повторить `./ops/up.sh`. Новые строки на этом шаге:
   - `PASS setup-page: страница настройки переписки отвечает на локальном адресе…`;
   - `PASS setup-origin: у страницы настройки свой адрес: https://<имя>:8443…`;
   - `WARN setup-page-public: …соединение не принято…` или `…не ответил за 8 секунд…` — прокси и порт ещё не настроены, это шаги 3 и 4;
   - `PASS setup-isolation: по адресу дашборда страница настройки переписки не отдаётся…`;
   - `WARN setup-state: …Переписка ещё не настроена…` либо `PASS setup-state` с числами, если аккаунты и архив уже есть.

   Что не так:
   - «`SHTURMAN_PUBLIC_URL` в .env записан не как адрес вида https://имя[:порт]…» — скрипт остановился до перезапуска, прежняя версия сервиса продолжает работать. С версии 0.0.6 сервис переписки получает адрес дашборда и с неразборчивым значением (например, без `https://`) не запускается. **Стоп**: спросить у владельца адрес и записать заново — `./ops/set-public-url.sh https://адрес`, затем повторить шаг;
   - `FAIL service`, а в `docker logs --tail 50 shturman-service` строка `SHTURMAN_DASHBOARD_ORIGIN: …` или `SHTURMAN_SETUP_ORIGIN: …` — то же самое, но скрипт запись не распознал (например, неверный порт): первая переменная — это строка `SHTURMAN_PUBLIC_URL` в `.env`, вторая — `SHTURMAN_SETUP_URL`;
   - `FAIL setup-origin` — адрес страницы совпал с адресом дашборда (строку вписали вручную): **стоп**, `./ops/set-setup-url.sh` без параметров покажет значение; исправить — «Другой адрес» ниже;
   - `FAIL setup-isolation` — прокси уже отдаёт страницу по адресу дашборда (так было в промежуточной сборке этой версии): **стоп**, шаг 3 обязателен, ссылку входа на страницу до него не выдавать;
   - `WARN setup-page: …сервис прежней версии` — образ сервиса не пересобрался: повторить `./ops/up.sh`;
   - «Сервис переписки не ответил за 90 секунд» — `docker logs --tail 50 shturman-service`: если не прошла миграция, причина названа в последних строках. Данные не трогать; откат — ниже.
3. **Стоп-точка (`sudo`, правка прокси).** Показать владельцу, что изменится в настройке обратного прокси, и получить согласие. По образцу `config/Caddyfile.example`:
   - в блок дашборда добавить отказ на путь страницы, как в образце: условие `@no_setup_page path /shturman-setup*` и блок `handle @no_setup_page` с единственной строкой `respond 404`. Если в блоке дашборда есть проксирование `/shturman-setup/*` на `127.0.0.1:8765` — убрать его;
   - добавить второй блок сайта — то же имя с портом 8443 — целиком, как в образце: только пути под `/shturman-setup/` уходят на `127.0.0.1:8765`, остальное — отказ. Заголовок `Host` не подменять. Блоки не объединять.

   Проверка: `caddy validate` для новой настройки проходит; после перезагрузки прокси дашборд открывается как раньше (делает человек).
4. **Стоп-точка (`sudo`, firewall).** Открыть порт 8443 (TCP) в firewall сервера и, если есть, в правилах хостинга. Показать владельцу команду и получить согласие.
5. `./ops/doctor.sh` — проверка. Ожидается `ИТОГ: OK` и четыре строки:
   - `PASS setup-page`;
   - `PASS setup-origin: у страницы настройки свой адрес: https://<имя>:8443 (дашборд — https://<имя>)`;
   - `PASS setup-page-public: страница настройки переписки открывается по своему адресу`;
   - `PASS setup-isolation: по адресу дашборда страница настройки переписки не отдаётся (HTTP 404)`.

   `WARN setup-page-public` называет причину: порт закрыт — шаг 4; «прокси отвечает „не найдено“» — второй блок не тот или не загружен, шаг 3; «сервис переписки не узнаёт этот адрес» — прокси подменяет `Host` либо сервис не перезапущен (`./ops/up.sh`); «нет подходящего сертификата» — подождать минуту и повторить: Caddy отдаёт на порту 8443 тот же сертификат, что и на 443.
6. Сказать владельцу, что изменилось, и спросить, хочет ли он настроить переписку сейчас. **Стоп-точка: ссылку входа на страницу (`./ops/setup-link.sh`) выдавать только по его просьбе**, передать как есть и нигде не сохранять. Владелец, уже прошедший мастер, найдёт кнопку во вкладке «Штурман», шаг «Переписка»: шаг у него отмечен пройденным, но открыт. Что он увидит на странице — `docs/setup.md`.
   - Проверка (делает человек): кнопка «Открыть настройку переписки» открывает страницу входа; по ссылке вход проходит.
   - Проверка: после настройки `./ops/doctor.sh` показывает `PASS setup-state` с числом аккаунтов и сообщений.
7. `./ops/backup.sh` — копия после обновления. В каталоге данных теперь лежит и файл значений, введённых на странице (`data/shturman/setup/secrets.json`); он входит в копию. Агент копию не открывает.

**Другой адрес страницы.** Вместо порта 8443 можно взять другой порт или отдельное имя — это стоп-точка, решает владелец:

- другой порт: `./ops/set-setup-url.sh https://<имя>:<порт>`, во втором блоке прокси — тот же порт, открыть его в firewall;
- отдельное имя, если порт открыть нельзя: владелец заводит запись DNS для второго имени на этот же сервер; `./ops/set-setup-url.sh https://<второе имя>`; заголовок второго блока прокси — это имя; firewall править не нужно.

После смены адреса — `./ops/up.sh` и `./ops/doctor.sh`. Адрес, совпадающий с адресом дашборда, скрипт не запишет и объяснит почему.

**Если перед адресом стоит Cloudflare или другая внешняя защита.**

- Cloudflare в режиме прокси HTTPS на порту 8443 пропускает (документация Cloudflare «Network ports», сверено 2026-10-07). Если на платном тарифе включено правило WAF, блокирующее нестандартные порты, для 8443 нужно исключение. `WARN setup-page-public: внешняя защита … не достучалась до сервера (HTTP 52x)` значит, что сам сервер на порту 8443 ей не отвечает: шаги 3 и 4.
- Сервис единого входа перед адресом (Cloudflare Access и подобные) номер порта в защищаемом адресе может не сохранять. Перед страницей на порту его не ставят; нужен единый вход и там — странице дают отдельное имя.
- Если порт 443 сервера открыт только для адресов внешней защиты, так же ограничить и порт 8443.
- `./ops/doctor.sh` проверяет адреса с самого сервера; при внешней защите он может показать `WARN setup-page-public: перед адресом … стоит внешняя защита` — тогда страницу проверяет владелец из браузера: должна открыться страница входа «Штурмана».

**Если бот Hermes уже подключён в бизнес-режиме или установлен официальный плагин бизнес-режима.** Так настраивали экземпляр до этой версии. Обновление ничего из этого не отключает и не удаляет:

- `./ops/doctor.sh` показывает `PASS business-plugin: официальный плагин бизнес-режима на этом экземпляре установлен…` и `WARN business-hermes: бот-ассистент сейчас подключён в бизнес-режиме Telegram…`; мастер на шаге «Переписка» говорит то же самое спокойной строкой. Сообщения бизнес-режима по-прежнему записываются в архив;
- агент сам ничего не отключает и не переподключает. Он пересказывает владельцу, почему бота Hermes в бизнес-режиме больше не подключают: токен этого бота лежит там, где у ассистента есть терминал, и бизнес-подключением ассистент может пользоваться мимо сервиса (`docs/architecture.md`, «Чего не закрывает ни один из вариантов»);
- если владелец решил отключить — он сам отключает бота в Telegram: Настройки → «Telegram для бизнеса» → «Чат-боты». Новые сообщения личных чатов после этого приходят в архив через его аккаунт, подключённый на странице «Переписка», — для чатов, которые он там выбрал. Официальный плагин бизнес-режима после этого ничего не делает; удалять его не обязательно, удаление — на странице плагинов Hermes, решает владелец;
- если владелец оставляет как есть — оставить. Право бота отвечать на сообщения в настройках Telegram Business лучше держать выключенным;
- бизнес-режим у бота согласований (если его заводили в 0.0.4) обновление не затрагивает: это и есть нынешняя схема.

**Если бот согласований или своя модель уже настроены.** Они продолжают работать: значения из `.env` главнее введённых на странице, страница покажет их как заданные на сервере и менять не даст. Раздел «Дополнительно» на странице показывает их состояние. Адрес API модели сервис теперь получает из `.env`, только если строка `SHTURMAN_LLM_BASE_URL` там есть; без неё он, как и раньше, обращается к `https://api.openai.com/v1`.

**Режим без Hermes.** Шаги 1, 2 и 7; прокси и firewall не трогать, внешний адрес странице не задавать. В выводе шага 2 вместо четырёх строк — `PASS setup-page` и `PASS setup-origin: внешнего адреса … нет, как и положено без Hermes`. Страница «Переписка» открывается через туннель SSH: `./ops/setup-link.sh` — по просьбе владельца (`docs/standalone.md`).

**Откат.**

1. **Стоп-точка (`sudo`).** В обратном прокси убрать второй блок сайта; отказ на `/shturman-setup*` в блоке дашборда можно оставить — прежней версии он не мешает. Закрыть порт 8443 в firewall.
2. `git checkout` предыдущего тега, затем `./ops/up.sh`. Строка `SHTURMAN_SETUP_URL` в `.env` версии 0.0.5 не мешает: она её не читает.
3. Проверка: `./ops/doctor.sh` — `ИТОГ: OK`.

Схему базы откат не возвращает: четыре новые таблицы остаются, сервис версии 0.0.5 их не читает, а незнакомую запись о применённой миграции пропускает. Так рассчитано по коду — сама версия 0.0.5 на базе с миграцией 0016 не запускалась. Что из этого следует:

- значения, введённые на странице «Переписка» (ключи приложения Telegram, а если вводили — токен бота согласований и ключ модели), версия 0.0.5 не видит: они лежат в файле каталога данных, который она не читает. Сессии аккаунтов Telegram после отката не запустятся, пока владелец не введёт ключи приложения в терминале: `./ops/init-env.sh`, затем `./ops/up.sh`. Сами сессии и выбор чатов сохраняются;
- сессии и ссылки входа на страницу настройки перестают что-либо значить: страницы в версии 0.0.5 нет.

Если после отката сервис не запускается — восстановление базы из копии, сделанной перед обновлением. Это стоп-точка; отдельной процедуры для неё пока нет.

## 0.0.4 → 0.0.5

**Что меняется для владельца.** Сразу после обновления — ничего: схема базы не меняется, новых контейнеров нет, включённый поиск по смыслу продолжает работать с прежней моделью из прежнего каталога, строк в `.env` добавлять не нужно. Появляется выбор модели поиска по смыслу: к `multilingual-e5-small` добавлена русскоязычная `USER2-small` (`docs/search.md`). Модель по умолчанию прежняя; менять её или нет, решает владелец.

Два изменения действуют без включения:

Под Docker эта версия запускалась только на стенде разработки (`docs/deployment.md`). Если вывод шага не совпал с ожидаемым — остановиться и описать, что именно не так.

**Перед началом — стоп-точка.** `./ops/backup.sh`. Ожидаются строки «Копия готова» и «Копия базы готова».

**Шаги.**

1. `git pull` — получить версию 0.0.5. Проверка: `cat VERSION` показывает `0.0.5`.
2. `./ops/up.sh`. Образ сервиса пересобирается; если поиск по смыслу включён, контейнер `shturman-embeddings` пересоздаётся.

Число «осталось» должно быть нулём или быстро убывать: если оно равно всему архиву, векторы пересчитываются заново — **стоп**, этого при обновлении быть не должно.

Версия 0.0.4 умеет запускать только `e5-small` из каталога `data/embeddings/model`; векторы другой модели она сотрёт и пересчитает сама, а без файлов `e5-small` контейнер эмбеддингов не запустится.

## 0.0.3 → 0.0.4

**Что меняется для владельца.** Сразу после обновления — ничего: экземпляр остаётся в режиме с Hermes, свой бот согласований, своя модель сервиса и защита от внедрённых инструкций выключены, поведение прежнее. Появляются три возможности, каждую владелец включает отдельно: свой бот согласований, защита от внедрённых инструкций и второй режим установки — без Hermes. **Отправка сообщений выключена и этим обновлением не включается.**

Одно изменение действует без включения: `SHTURMAN_SENDING=on` теперь работает только вместе со своим ботом согласований. Если отправку вопреки рекомендации включали в 0.0.3, после обновления она выключена.

Под Docker эта версия запускалась только на стенде разработки (`docs/deployment.md`). Если вывод шага не совпал с ожидаемым — остановиться и описать, что именно не так.

**Перед началом — стоп-точка.** `./ops/backup.sh`. Ожидаются строки «Копия готова» и «Копия базы готова». Без них дальше не идти: обновление меняет схему базы.

**Шаги.**

1. `git pull` — получить версию 0.0.4. Проверка: `cat VERSION` показывает `0.0.4`.
2. **Стоп-точка (миграции базы).** Объяснить владельцу, что сделает следующая команда, и получить согласие. `./ops/up.sh`:
   - дописывает в `.env` строки `SHTURMAN_MODE=hermes` и `COMPOSE_PROFILES=hermes`, не печатая остального. Включённый поиск по смыслу сохраняется: `COMPOSE_PROFILES=hermes,embeddings`;
   - пересобирает образ сервиса переписки: добавился пакет `socksio`, первая сборка идёт несколько минут;
   - перезапускает сервис; при старте он сам применяет три миграции:

     - `0015_executor_bot.sql` — две новые таблицы: состояние бота согласований и одноразовые коды привязки;
   - может пересоздать контейнер Hermes: его описание в `compose.yaml` изменилось. Бот и дашборд на минуту-две недоступны. При следующих запусках скрипт Hermes не трогает, если плагин включён и запись об архиве на месте; скрипт версии 0.0.3 перезапускал его каждый раз.

**Важно.** Контейнер Hermes теперь описан профилем Compose. Команда `docker compose up` в обход `./ops/up.sh` запустит Hermes, только если в `.env` есть `COMPOSE_PROFILES=hermes`. После шага 2 строка есть.

**Что изменилось во внутреннем API.** Пока у сервиса нет своего бота, ответы прежние. Со своим ботом:

- маршруты, которые расширяют права ассистента или необратимо стирают данные, отвечают 202 с телом `{"status": "pending_confirmation", …}`: действие не выполнено, пока владелец не нажал кнопку в боте. Перечень — `docs/service.md`, «Что подтверждает владелец в боте согласований»;
- `PUT` и `DELETE /api/owner`, `POST /api/callbacks/telegram`, `/api/ingest/business/*` отвечают 403 с кодом `own_bot`;
- `/api/jobs/{id}/complete` и `/fail` не закрывают задания, которые выполняет сам сервис.

Плагин версии 0.0.4 всё это понимает. Свои скрипты, которые ходят во внутренний API, нужно проверить на код 202.

**По желанию владельца, каждый пункт отдельно.**

- **Защита от внедрённых инструкций — стоп-точка.** `./ops/guard.sh on`: скачивает около 0,3 ГБ и занимает около 0,6 ГБ памяти; скрипт сам перезапускает стек. До включения пересказать владельцу раздел «Что защита ловит и чего не ловит» из `docs/guard.md`. Ожидается `PASS guard`. Без своего бота уведомления о скрытых сообщениях приходят через Hermes и без текста сообщения.
- **Свой бот согласований — стоп-точка, вводит только владелец.**
  1. Владелец создаёт у @BotFather **нового** бота. Токен управляющего бота Hermes не подходит: одного бота не могут опрашивать две программы.
  2. Владелец в своём терминале: `./ops/init-env.sh` — токен бота согласований скрытым вводом; на остальные вопросы — Enter. Затем `./ops/up.sh`. Ожидается `PASS approvals-bot`, `WARN approvals-owner`.

  4. В течение 5 минут `./ops/doctor.sh` покажет `PASS plugin-own-bot`: плагин в Hermes узнал о своём боте и перестал передавать нажатия.

  С этого момента карточки с кнопками приходят в бота согласований, а не в чат Hermes; кнопки под старыми карточками в чате Hermes не действуют. Перечисленные выше маршруты начинают отвечать 202 и 403 `own_bot`.
- **Бизнес-режим при своём боте — стоп-точка, переподключает человек.** Со своим ботом сервис принимает бизнес-сообщения только через него. Если бизнес-режим уже подключён к боту Hermes, после включения своего бота новые сообщения личных чатов в архив не попадают, пока владелец не переподключит:
  1. В настройках Telegram Business владелец отключает бота Hermes.
  2. У @BotFather включает Business Mode для бота согласований. Проверка: в `./ops/doctor.sh` нет строки `WARN approvals-business`.
  3. В настройках Telegram Business подключает бота согласований, для начала с одним тестовым чатом. Право отвечать на сообщения не даёт: отправка выключена.
  4. Проверка: после сообщения из тестового чата число сообщений в строке `PASS archive` выросло.

Схему базы откат не возвращает: новые столбцы и таблицы остаются, сервис версии 0.0.3 их не читает, а незнакомые ему записи о применённых миграциях пропускает. Так рассчитано по коду — сама версия 0.0.3 на базе с миграциями 0013–0015 не запускалась. Что из этого следует:

- сообщения, скрытые защитой, для версии 0.0.3 снова видны ассистенту: признак видимости она не читает;
- действия, ждавшие подтверждения владельца, остаются неприменёнными;
- задания, ждавшие своего исполнителя сервиса, заберёт плагин в Hermes.

Если после отката сервис не запускается — восстановление базы из копии, сделанной перед обновлением. Это стоп-точка; отдельной процедуры для неё пока нет.
