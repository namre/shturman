# Сервис переписки — устройство для разработчика

Что сервис делает для владельца, описано в `docs/service.md`. Здесь — как устроен код и по каким правилам он расширяется.

## Один процесс, один порт

`shturman serve` поднимает на локальном адресе сервера:

| Путь | Кто обращается | Токен | Что можно |
|---|---|---|---|
| `/health` | проверки | нет | только «жив» |
| `/api/*` | плагин «Штурмана» в Hermes; оператор командой `shturman call` | `SHTURMAN_API_TOKEN` | запись сообщений бизнес-бота, очередь заданий, нажатия кнопок, аккаунты Telegram, загрузка выгрузки, правила отправки, обязательства, люди, страницы, ждущие подтверждения, состояние своего исполнителя и защиты |
| `/mcp` | агент Hermes; без Hermes — клиент владельца (Codex CLI, Claude Code) | `SHTURMAN_MCP_TOKEN` | только чтение архива; принимаются только запросы POST |
| `/shturman-setup/*` | владелец в браузере | нет: вход по одноразовой ссылке (`./ops/setup-link.sh`), дальше — ключ сессии в заголовке `X-Shturman-Session`; cookie нет | страница настройки: бот согласований, выбор способа подключения, ключи приложения Telegram, вход в аккаунт (свой или ассистента), бизнес-режим, выбор чатов, выгрузка; в блоке «Дополнительно» — своя модель |

Перечень путей не означает, что токен даёт полномочия владельца. Поля HTTP-запроса и модельный результат не подтверждают согласие: чувствительные изменения требуют независимого проверенного решения в Telegram либо разрешённого действия на странице настройки.

Токены разные и не взаимозаменяемы; сервис не запустится, если они совпали или короче 32 знаков. Под `/shturman-setup/` токены входом не служат, а маршрутов `/api/*` и `/mcp` там нет. Любой другой путь — 404, соединения WebSocket закрываются. В том же процессе живут сессии Telegram, свой бот согласований и фоновая работа: сессией и опросом бота владеет ровно один процесс.

## Границы, которые нельзя размывать

1. **Модель и бот — только через очередь заданий.** Всё, что требует модели, сообщения владельцу или отправки через бизнес-бота, ставится в очередь (`bridge.py`); модули сами к модели и к Bot API не ходят. Видов заданий пять: `llm.structured`, `llm.text`, `notify.owner`, `notify.edit`, `business.send`. Договор — в шапке `bridge.py`. Исполнителей два: плагин в Hermes (по умолчанию) и свой исполнитель сервиса (`executor/`) — бот согласований при `SHTURMAN_BOT_TOKEN`, клиент модели при `SHTURMAN_LLM_API_KEY` и `SHTURMAN_LLM_MODEL` либо при подписке ChatGPT, подключённой на странице настройки (`executor/siwc.py`, `executor/subscription.py`). Кто выполняет задание, записано в `jobs.executor`; задание своего исполнителя плагину не выдаётся и по HTTP не закрывается. Сервис не знает, установлен ли Hermes: тексты для владельца не должны утверждать, что он есть.
   **Со своим ботом плагину закрыты `/api/owner`, `/api/callbacks/telegram`, `/api/ingest/business/*`** (`api_core.only_without_own_bot`, отказ 403 `own_bot`): привязку владельца, нажатия и бизнес-поток ведёт только бот. Новый маршрут, через который можно выдать себя за владельца, обязан вызывать ту же проверку.
2. **Отправку решает не модель.** Модель и агент могут только создать черновик. Отправка происходит после нажатия кнопки владельцем либо по правилу автоответа доверенным, которое включил владелец. Главный выключатель `SHTURMAN_SENDING` (`off`, `on`) и потолок `SHTURMAN_SEND_DAILY_CAP` читаются только из окружения (`config.py`); маршрута, который их меняет, быть не должно. Без своего бота согласований реальная отправка не действует. `prepare_only` допускает подготовку без доставки; `off` запрещает доставку; подготовка при нём возможна только по отдельному owner-решению `/prepare on`.
3. **Основной аккаунт владельца — только чтение.** Клиент этой роли пропускает к Telegram только разрешённый перечень запросов на чтение; пути отправки для неё в коде нет.
4. **Остальные модули не трогают Telethon.** Они получают `state.extras["tg"]` с интерфейсом `tg/gateway.py`.
5. **Текст сообщений — данные.** В промпт он попадает только как помеченный чужой текст; из него ничего не исполняется. Всё, что отдаётся агенту, проходит чистку управляющих и невидимых символов. Сообщение, скрытое защитой (`agent_visible = false`), не отдаётся вовсе: любой новый запрос, который отдаёт текст переписки агенту или модели, обязан содержать `AND m.agent_visible`, а тест на него — лежать в `tests/guard/test_guard_visibility.py`.
6. **Служебные чаты Telegram исключены всегда** (`store.BLOCKED_USER_IDS`, `BLOCKED_USERNAMES`, `BLOCKED_CHAT_TYPES`): в них лежат коды входа и токены ботов.
7. **Дату считает код.** Модель копирует формулировку срока дословно; дату от времени сообщения вычисляет разборщик. Срок, которого нет в исходном тексте, отбрасывается.
8. **Секреты не пишутся в журнал и не возвращаются из API**: токены, в том числе токен бота согласований и ключ модели, пароль облачного хранения Telegram, содержимое сессии. Пароль 2FA не сохраняется нигде.
9. **Ослабление ждёт владельца, ужесточение применяется сразу.** Маршрут, который меняет решение владельца, идёт через `confirm` — см. «Как добавить модуль».
10. **У защиты нет ни выключателя, ни чтения скрытого через API.** `/api/guard/status` отдаёт только числа; открыть скрытое сообщение можно только кнопкой.
11. **Страница настройки — отдельный вход, а не ещё один клиент внутреннего API.** Её маршруты зовут функции сервиса напрямую и не пересылают запросы в `/api/*`. Действие со страницы — действие самого владельца: применяется сразу (`confirm.apply_owner`), без карточки в боте, и пишется в журнал действий (`setup_page/audit.py`). Ссылка входа создаётся только командой `shturman setup-link`, прямой записью в базу: маршрута для неё быть не должно — токен внутреннего API есть у ассистента. Таблицы `setup_*` внутренний API не читает и не меняет. Страница живёт на своём origin — другой порт того же имени, что у дашборда Hermes, или другое имя; при совпадении адресов (`SHTURMAN_SETUP_ORIGIN` и `SHTURMAN_DASHBOARD_ORIGIN`) снаружи она не обслуживается. Сессия не держится на cookie: они по портам не разделяются. Новый маршрут страницы идёт через обёртку `endpoint` (ключ сессии и проверка, что запрос `same-origin`) и не ставит cookie. Адрес, введённый на странице и по которому сервис сам ходит в сеть, проходит `netguard.py`: только https, только наружу, без перенаправлений.
12. **Значения, введённые на странице, обратно не отдаются.** Токен бота, ключи приложения Telegram и ключ модели лежат в файле `setup/secrets.json` каталога данных (права 600), а не в базе; страница получает только «задано / не задано». Значение из окружения главнее файла. Выключатель отправки к этим значениям не относится: `config.sending` требует и `SHTURMAN_SENDING=on`, и `SHTURMAN_BOT_TOKEN` именно в окружении — токен, введённый на странице, отправку не включает.

## Как добавить модуль

Модуль перечислен в `app.MODULES` и может определить (пути начинаются с `/api/`; `/mcp` отдаёт только `mcp_server.py`):

```python
def routes() -> list[BaseRoute]: ...          # пути начинаются с /api/
@asynccontextmanager
async def lifespan(state: AppState): ...      # запуск и остановка фоновой работы
```

Состояние в обработчике — `state_of(request)`: `config`, `pool` (чтение и запись), `ro_pool` (только чтение), `events`, `extras`, `spawn(coro, name=...)`. Разбор тела и ошибок — помощники из `api_core.py` (`handler`, `body`, `need_int`, `need_str`, `BadRequest`).

Маршрут, который меняет решение владельца, идёт через `confirm`: модуль регистрирует функцию применения (`@confirm.applier("модуль.действие")`), а обработчик зовёт `api_core.settle(conn, вид, payload, summary=…)`. `summary` — текст карточки простыми словами; `summary=None` значит «это ужесточение, применить сразу». Функция применения заново проверяет условия и вызывает `confirm.must_not_widen(…)` под своей блокировкой. Новый вид действия нужно дописать в `tests/test_confirm_kinds.py` и в таблицу `docs/service.md`.

## Общие части

| Файл | Что в нём |
|---|---|
| `app.py` | сборка приложения, проверка токенов по пути, перечень модулей `MODULES`, состояние `AppState` |
| `api_core.py` | общие маршруты: состояние, владелец, очередь заданий, нажатия кнопок, ждущие подтверждения; помощники разбора запроса, `settle()`, `only_without_own_bot()` |
| `confirm.py` | подтверждения владельца: действие ждёт нажатия в боте согласований, защита от повторов, предел ждущих карточек, стирание содержимого решённых; `apply_owner` — действие самого владельца со страницы настройки |
| `config.py` | настройки из переменных окружения; шесть значений страницы настройки подставляются из файла, где окружение молчит (`with_page_values`) |
| `cli.py` | команды `shturman`: `serve`, `migrate`, `scan`, `import`, `search`, `call`, `tg-login`, `bot-bind`, `bot-status`, `setup-link`, `setup-logout-all` |
| `records.py` | `MessageRecord`, `ChatRecord` — запись в словаре экспорта Telegram Desktop |
| `store.py` | единственный путь записи в архив: `ensure_account`, `ensure_chat`, `upsert_messages` (параметр `hold` — записать входящее скрытым до проверки защитой), `mark_deleted`, `mark_deleted_without_chat`; перечень всегда исключённых чатов |
| `jobs.py` | очередь заданий с арендой и защитой от повторов; у задания — исполнитель (`plugin` или `builtin`); закрытие невостребованных и стирание содержимого выполненных |
| `bridge.py` | постановка заданий (`notify_owner`, `edit_owner_message`, `request_structured`, `request_text`, `request_business_send`), разбор результатов (`on_result`, `on_failure`) и нажатий кнопок (`on_callback`, `button`, `dispatch_callback`); владелец; кто выполняет задания (`set_builtin`, `builtin_kinds`, `owns_bot`) |
| `events.py` | события внутри процесса: `message.live`, `messages.deleted`, `messages.hidden`, `chat.excluded` |
| `archive.py` | запросы чтения архива с правилами видимости — из них собираются ответы агенту |
| `sanitize.py` | чистка чужого текста и рамка `[untrusted]` перед выдачей агенту |
| `retrieval.py` | единая точка поиска для ответов агенту |
| `search.py` | полнотекстовый и гибридный поиск; вызывать через `retrieval.find` |

## Соглашения

- **База.** Только asyncpg, без ORM. Параметры `jsonb` передаются строкой (`json.dumps(..., ensure_ascii=False)`) с приведением `$n::jsonb`; при чтении — `json.loads`, если пришла строка. Время — `timestamptz`, в коде — `datetime` с часовым поясом.
- **Миграции** — файлы `migrations/NNNN_имя.sql`, применяются по порядку имён, каждая в своей транзакции. Применённую миграцию не правят — добавляют следующую. Версия 0.0.6 добавила одну: `0016_setup_page.sql` — четыре таблицы страницы настройки (`setup_links`, `setup_sessions`, `setup_state`, `setup_audit`). **Комментарий в ней устарел:** у таблицы `setup_sessions` сказано, что идентификатор сессии лежит «только в cookie». Сессия страницы — без cookie: ключ лежит в `localStorage` страницы и приходит в заголовке `X-Shturman-Session` (`setup_page/auth.py`), в таблице по-прежнему только его хеш. Схема от этого не менялась, поэтому новой миграции нет, а текст применённой не правится.
- **Сообщения в архив пишет только `store.py`.** Производные данные хранят идентификаторы сообщений-источников (`messages.id`) и удаляются вместе с ними.
- **Язык.** Комментарии, документация, тексты для владельца — на русском. Имена в коде — на английском.
- **Зависимости** — только под MIT, Apache-2.0, BSD, лицензией PostgreSQL. Заимствованный код — с указанием источника в шапке файла и записью в `THIRD_PARTY_NOTICES.md`.

## Тесты

```
cd service && pip install -e '.[dev]' && pytest
```

Нужен Postgres 16 с расширениями `pg_trgm` и `vector`; адрес — в `SHTURMAN_TEST_DSN`. Тесты пересоздают схему `public`, поэтому база должна быть отдельной тестовой. Тестам страниц памяти нужен установленный git. В сеть тесты не ходят: Telegram, модель, сервер эмбеддингов и классификатор защиты заменены подставными объектами. Тесты страницы настройки — `tests/setup_page/` (фикстура `stand`: сервис со страницей и «браузер» владельца) и `tests/test_setup_qr.py` (генератор QR сверяется с segno; нужен Node.js, без него пропускается). Браузерная проверка страницы — вручную, `tests/e2e/README.md`. Сервис в тесте поднимает фикстура `make_client` (см. `tests/conftest.py`); фикстуры `own_bot`, `either_mode` и `approvals` там же — для проверки режимов согласований и явного согласия владельца.

Если пакет установлен в режиме разработки из другого каталога (например, тесты запускаются из git worktree), без `PYTHONPATH=src` pytest проверит код того каталога, а не текущего:

```
cd service && PYTHONPATH=src pytest
```

Целевые мутационные проверки запускаются из каталога `service` с тем же `SHTURMAN_TEST_DSN`, указывающим на отдельную тестовую базу:

```bash
python tests/security_mutations.py --output-dir /tmp/security-mutations --include-db
```

Это 11 выбранных изменений границ безопасности, а не измерение мутационного покрытия всего проекта. Сначала проходят исходные тесты; каждая мутация затем проверяется на отдельной копии кода. В `security-mutations.json` сохраняются commit, чистота checkout, версии зависимостей, SHA256 файлов, результаты и журналы. Пойманное нарушение, выжившая мутация, ошибка исполнения, пропуск и таймаут учитываются отдельно. Ошибка сбора или подключения к базе не считается пойманной мутацией. В CI отчёт доступен в artifact `security-mutations`.

Тест, который проверяет итог фоновой работы, ждёт условия (помощник `until`), а не фиксированное время.

Измерение защиты — `tools/guard_eval.py` на наборе `tests/guard/data/`. Сменил модель защиты, порог или правила — повтори измерение и обнови числа в `docs/guard.md`.

Измерение поиска по смыслу — `tools/search_eval.py` на наборе `tests/search/data/`: и «только модель», и настоящий путь сервиса от записи в архив до гибридного поиска. Сменил модель эмбеддингов, приставки, единицу текста или слияние рангов — повтори измерение и обнови `docs/search.md`. Новое имя человека или название в наборе проходит вычитку: фамилий, настоящих марок, ссылок и адресов в нём быть не должно (`tests/search/test_search_eval.py`).

Образ для сервера собирается из `Dockerfile`: зависимости ставятся из `requirements.lock` с проверкой контрольных сумм. Список обновляется командой из его шапки. Файлы страницы настройки (`setup_page/static/*`) и миграции — данные пакета (`pyproject.toml`, `package-data`): в образ они попадают вместе с пакетом, и CI проверяет это в собранном образе. Новый каталог с файлами не на Python нужно дописать туда же.

Значение страницы настройки, пришедшее из окружения (переменная не пуста), сервис считает заданным на сервере, и страница менять его не даёт (`secrets_store.locked_by_env`). Поэтому `compose.yaml` не подставляет таким переменным значений по умолчанию: адрес модели контейнер получает, только если строка есть в `.env`. Оговорка: переменная, заданная пустой строкой, для `config._env` — пустое значение, а не «по умолчанию»; для адреса модели пустую строку `.env` подменяет адресом по умолчанию `./ops/up.sh`.

## Новые границы 0.0.7

Модель предлагает `reply`, `need_source`, `ask_owner` или `decline`; она не создаёт owner receipt, grant или новую область группы. `authority` применяется только на проверенном владельце в личном чате собственного бота, не по полям HTTP-запроса. Задача, источник, чат, тема, версия политики и текст черновика связаны; изменять их после создания нельзя. Перед доставкой заново проверяются действительность источников и разрешения. При `prepare_only` никакой бизнес- или Telethon-путь не доставляет сообщение. При неизвестной доставке повтора нет.

Реестр внешних источников — `SHTURMAN_SOURCES_FILE`, только у сервиса, права 0600, credentials не выдаются модели. Поддержан ограниченный контракт поиска/чтения MCP, а не любой почтовый провайдер (`docs/external-sources.md`). Миграции 0.0.7 добавляют служебные исключения, задачи/источники, групповые области и защиту связанных черновиков; порядок и имена сверяются с `src/shturman/migrations/`. Применённые миграции не переписываются.

Приёмка разработчика и отдельный пилот владельца — `docs/runbooks/validate-pilot.md`; текущие ограничения совместимости — `docs/target-model.md`. Широкие инструменты полного Hermes сохраняются и не становятся автоматически ограниченными этим workflow.

Внешний gateway — `SHTURMAN_REMOTE_MCP_ORIGIN`, отдельный HTTPS-origin, по умолчанию пусто. Scope `archive:read` читает весь доступный архив, не один чат; постоянные локальные токены на нём не принимаются. Живая совместимость облачных клиентов не подтверждена (`docs/remote-mcp.md`).
