# Посредник «Штурмана»: установка и сопровождение

Для держателя посредника `sh.namre.app` (docs/relay.md, решение Р-69). Это **не часть экземпляра**: всё здесь ставится на отдельный сервер посредника. Владельцу экземпляра этот файл не нужен — ему нужен только код приглашения и `./ops/relay.sh join` на его сервере.

**Версия:** 0.4.0 (`relay/relayd.py`, `VERSION`) · **Состояние:** 0.2.0 стоит на настоящем посреднике с 2026-10-12 (docs/relay.md, «Живая проверка»). В 0.3.0 добавлена проверка имени до подключения (`POST /api/check`) и свободные варианты в ответе на занятое имя; в 0.4.0 — бот-менеджер: создание бота согласований в одно нажатие (`/api/botpair/*`, страница `/api/manager/setup`, `relayctl manager-*`; ниже, «Бот-менеджер», и `docs/approvals-bot.md`). Обе проверены юнит-тестами и на стенде разработки (0.4.0 — с подставным Bot API Telegram); на посреднике не ставились — обновление ниже.

## Что получается на посреднике

| Служба | Что делает | Слушает |
|---|---|---|
| `frps` | Пересылка по имени сайта (SNI) без расшифровки; соединения экземпляров | `:7000` (TLS), `:443`, `:80` |
| `shturman-relayd` | Серверный плагин frps (кто какое имя может занять), проверка имени и выдача имён по коду приглашения; бот-менеджер (опрос `getUpdates` у `api.telegram.org`, только исходящие запросы) | `127.0.0.1:7400` (плагин), `127.0.0.1:7401` (`/api/*`) |
| `shturman-relay-caddy` | `https://relay.<зона>/api/*` → relayd; сертификат Let's Encrypt | `127.0.0.1:9080`, `127.0.0.1:9443` |
| `shturman-relay-frpc` | Служебный «экземпляр» `relay`: имя `relay.<зона>` через frps → Caddy посредника | — |

Файлы: программы — `/opt/shturman-relay`; настройки — `/etc/frp/frps.toml`, `/etc/shturman-relay/{Caddyfile,frpc.toml}`; секреты (только root, 600) — `/etc/frp/token.env` (общий токен frps), `/etc/frp/frps.key` (ключ сертификата frps), `/etc/shturman-relay/operator.env` (ключ служебного экземпляра); база экземпляров и приглашений — `/var/lib/shturman-relay/relay.db` (пользователь `shturman-relay`, 600; в ней хеши кодов и ключей, не сами значения); токен бота-менеджера — `/var/lib/shturman-relay/manager.token` (пользователь `shturman-relay`, 600; появляется после `relayctl manager-link` или `manager-token`). Публичный сертификат frps — `/etc/frp/frps.crt`: его получает каждый экземпляр.

## Перед установкой

- Ubuntu 24.04, `python3` 3.12 (есть по умолчанию), `curl`, `openssl`, systemd.
- DNS зоны: `relay.<зона>` и `*.<зона>` → адрес посредника; `CAA` — только `letsencrypt.org`, `issuewild ";"`.
- Открыты входящие 80, 443, 7000 (в Lightsail — правила сети инстанса).
- На посреднике прототипа: `/etc/frp/token.env` с `FRP_AUTH_TOKEN=` остаётся — установщик его не трогает.

## Установка и обновление

```bash
git clone https://github.com/namre/shturman.git && cd shturman   # или git pull в имеющемся клоне
sudo ./relay/install.sh
```

Повторный запуск безопасен: перезаписываются программы, настройки и службы из репозитория; токен, сертификат frps, ключ служебного экземпляра и база остаются. Прежняя `/etc/frp/frps.toml` и изменённые файлы служб сохраняются рядом с пометкой `.bak-ДАТА`. Службы прототипа `relay-test-*.service` установщик останавливает и удаляет.

**Обновление** (например, 0.2.0 → 0.3.0) — тот же установщик из нового коммита, на посреднике, в клоне, из которого ставили:

```bash
cd ~/shturman                                   # клон репозитория на посреднике
sudo cp -p /var/lib/shturman-relay/relay.db "/root/relay.db.bak-$(date -u +%Y%m%dT%H%M%SZ)"   # копия базы, на всякий случай
git pull                                        # или git fetch && git checkout <коммит из PR>
sudo ./relay/install.sh
curl -fsS https://relay.sh.namre.app/api/health  # {"ok": true, "version": "0.4.0", "botpair": false} — true, когда задан бот-менеджер
curl -sS -X POST -H 'Content-Type: application/json' -d '{"code": "AAAA-AAAA-AAAA-AAAA-AAAA", "name": "ivan"}' \
  https://relay.sh.namre.app/api/check          # {"error": "bad_code", "message": "Код приглашения не подошёл: …"}
sudo relayctl list                              # экземпляры и приглашения на месте
```

Что происходит при обновлении (по `relay/install.sh`): frp 0.71.0 и Caddy 2.11.7 скачиваются заново и сверяются по суммам; `relayd.py`, `relayctl`, настройки (`/etc/frp/frps.toml`, `/etc/shturman-relay/Caddyfile` — в 0.3.0 в нём появился путь `/api/check`, в 0.4.0 — `/api/botpair/*` и `/api/manager/setup*`, `frpc.toml`) и файлы служб перезаписываются; общий токен, сертификат frps и его ключ, ключ служебного экземпляра и база с экземплярами и приглашениями не трогаются (`relayctl init` только создаёт недостающие таблицы, `operator` берёт прежний ключ из файла); сертификат Let's Encrypt Caddy посредника лежит в его каталоге состояния и тоже остаётся. Затем службы перезапускаются: **перезапуск frps на несколько секунд рвёт подключения всех экземпляров** — их frpc переподключаются сами, открытые в этот момент страницы владельцев оборвутся; выбирайте спокойное время. Новый сертификат frps при обновлении не создаётся, поэтому экземплярам ничего делать не нужно. Ответ `bad_code` на проверку выше значит, что запрос дошёл до службы 0.3.0; до обновления Caddy посредника отвечал на этот путь 404. Счёт попыток в памяти службы после перезапуска начинается заново.

Что делает установщик по шагам: скачивает frp 0.71.0 и Caddy 2.11.7 с GitHub и сверяет суммы (не совпали — ничего не ставится); ставит программы и `relayctl`; создаёт пользователя `shturman-relay`; создаёт, если их нет, общий токен и постоянный сертификат frps (`relay.<зона>`, ECDSA P-256, 10 лет); кладёт настройки и службы; заводит базу и ключ служебного экземпляра; проверяет настройки (`caddy validate`, `frps verify`); перезапускает службы и ждёт `https://relay.<зона>/api/health`.

Ожидаемый конец вывода:

```
  shturman-relayd: работает
  frps: работает
  shturman-relay-caddy: работает
  shturman-relay-frpc: работает
ГОТОВО: https://relay.sh.namre.app/api/health отвечает.
```

**При первой установке на прототипе** frps получает постоянный сертификат вместо случайного, а вход без ключа экземпляра перестаёт работать — тестовый экземпляр `test` больше не подключится (поэтому его службы и убираются).

Только проверить без установки: `./relay/install.sh --download-only НОВЫЙ_КАТАЛОГ` (скачать и сверить), `./relay/install.sh --render НОВЫЙ_КАТАЛОГ` (собрать настройки для зоны). Другая зона — `RELAY_DOMAIN=sh.example.org`.

## Коды приглашения и экземпляры

```bash
sudo relayctl invite --note 'Иван, пилот'      # код печатается один раз; по умолчанию живёт 7 дней (--days 1..90)
sudo relayctl list                              # экземпляры и приглашения (сами коды не хранятся)
sudo relayctl revoke ИМЯ                        # отключить экземпляр и перезапустить frps (рвёт его подключения)
sudo relayctl revoke ИМЯ --no-restart           # отключить без перезапуска frps (открытые соединения живут до перезапуска)
sudo relayctl release ИМЯ                       # освободить имя отключённого экземпляра; всегда перезапускает frps
```

Код передайте владельцу экземпляра удобным ему способом; он одноразовый. Имя владелец выбирает сам: до подключения его агент проверяет `./ops/relay.sh check КОД ИМЯ` (код не расходуется; на занятое имя посредник предлагает до трёх свободных), затем `./ops/relay.sh join КОД ИМЯ`; неверное, служебное или занятое имя код не тратит. Ключ подключения создаёт сам экземпляр — посредник получает и хранит только его sha256; повтор того же подключения (ответ потерялся в сети) получает тот же успешный ответ.

**Кому выдавать коды.** Пока `sh.namre.app` нет в Public Suffix List (ниже), все экземпляры — один «сайт» для браузера: подключённый владелец может мешать входу в дашборды соседей (подброшенные cookie), а узнав чужой номер подключения frps — получить сертификат на чужое имя (`docs/relay.md`, риски 8 и 9). Поэтому до внесения в список коды — только тем, кому вы доверяете.

`revoke` отмечает экземпляр отключённым и перезапускает frps: рвутся управляющее соединение экземпляра и все уже открытые соединения браузеров к нему, остальные экземпляры переподключаются сами за несколько секунд. С `--no-restart` frps не перезапускается: новых рабочих соединений экземпляр не получает и переподключиться не может, но уже открытые соединения браузеров (keep-alive, HTTP/2) и заранее открытые рабочие соединения работают до перезапуска frps. `release` освобождает имя и всегда перезапускает frps — иначе прежнее подключение держало бы пересылку на это имя. Выдавать освобождённое имя другому владельцу раньше чем через 90 дней не стоит: сертификаты, выпущенные на него прежнему владельцу, действуют до конца срока. Обе команды требуют root.

## Бот-менеджер: бот согласований в одно нажатие (0.4.0)

Необязательная часть посредника (Р-77, `docs/approvals-bot.md`): владельцы экземпляров, которые доверяют держателю посредника, создают своего бота согласований одной кнопкой на странице «Переписка» вместо пяти шагов у @BotFather. **Держатель посредника при этом технически может получить токен каждого такого бота** — владельцам это говорится до кнопки. Пока токен бота-менеджера не задан, служба работает как 0.3.0, а `/api/health` отвечает `"botpair": false`.

Один раз:

1. **Создать бота-менеджера** у @BotFather: `/newbot`, название, например, «Штурман — создание ботов», адрес, например, `shturman_manager_bot` (любой свободный). Этот бот — только для посредника: не подключайте его к другим программам и не ставьте ему webhook (служба опрашивает его `getUpdates`; второй опрашивающий — ответ 409 у обоих).
2. **Включить Bot Management Mode**: в @BotFather откройте мини-приложение → настройки этого бота → **Bot Management Mode** — включить (`core.telegram.org/bots/features`, «Managed Bots», сверено 2026-10-13; как именно называется кнопка в мини-приложении — проверить вживую). Без этого `getMe` не вернёт `can_manage_bots: true`, и служба токен не примет.
3. **Обновить посредника до 0.4.0** — «Установка и обновление» выше. Caddy посредника начнёт пропускать `/api/botpair/*` и `/api/manager/setup*`.
4. **Передать токен службе — не через чат и не через агента:**
   ```bash
   sudo relayctl manager-link       # одноразовая ссылка на 15 минут: https://relay.sh.namre.app/api/manager/setup#…
   ```
   Откройте её в своём браузере и вставьте токен бота-менеджера из @BotFather. Служба спросит у Telegram `getMe`, проверит `can_manage_bots` и сохранит токен в `/var/lib/shturman-relay/manager.token` (600). Ссылка тратится только при успехе; новая ссылка отменяет прежнюю; секрет ссылки — после «#», в журналы Caddy и службы он не попадает. Запасной путь — из терминала: `sudo relayctl manager-token` (токен вводится без показа; из файла — `sudo relayctl manager-token < файл`).
5. **Проверить:**
   ```bash
   sudo relayctl manager-status     # токен задан, бот @…, Bot Management Mode: включён, служба: работает
   curl -fsS https://relay.sh.namre.app/api/health   # "botpair": true
   ```

Дальше:

- `sudo relayctl manager-token --remove` — выключить создание ботов (служба перестанет опрашивать бота-менеджера за несколько секунд). Если токен мог утечь — ещё и выпустить новый в @BotFather (`/revoke`): прежний перестанет действовать.
- **Только по коду приглашения** (по умолчанию — без кода, с пределами частоты): `sudo systemctl edit shturman-relayd`, в разделе `[Service]` — `Environment=RELAY_BOTPAIR_REQUIRE_INVITE=1`, затем `sudo systemctl restart shturman-relayd`. Код — обычный `relayctl invite`; создание бота его не расходует.
- **Пределы**: не больше 10 новых пар с адреса (IPv6 — с сети /64) за 15 минут, не больше 200 ожидающих пар всего, вопросов «бот создан?» — 600 с адреса за 15 минут (экземпляр спрашивает раз в 3 секунды); неверные секреты идут в общий предел неудачных попыток вместе с `join` и `check`. Пары живут в памяти 15 минут; перезапуск службы их теряет — владелец просто начинает заново.
- **Журнал** (`journalctl -u shturman-relayd`): «пара …», «бот для пары … создан», «бот выдан экземпляру», «бот без ожидающей пары» (владелец изменил имя бота или пара истекла) — с номерами пар и адресами, без токенов и секретов.
- **Агент держателя** токен бота-менеджера не видит и не спрашивает; ссылку `relayctl manager-link` выдаёт только по явной просьбе держателя и сам её не открывает (`AGENTS.md`).
- **Подставной Telegram для стенда:** `RELAY_TELEGRAM_API=http://127.0.0.1:ПОРТ` в окружении службы и `relayctl` — только для разработки (`relay/tests/fake_telegram.py`).

## Public Suffix List

Внести `sh.namre.app` в Public Suffix List (раздел частных доменов) — тогда каждое имя в зоне станет для браузеров отдельным сайтом (риск 9 в `docs/relay.md`), а лимиты Let's Encrypt будут считаться на каждый экземпляр (риск 4). Порядок — по правилам списка (`github.com/publicsuffix/list`, wiki «Guidelines», сверено 2026-10-12):

1. Подаёт только владелец домена `namre.app` (или его уполномоченный представитель) от своего имени; сторонние заявки на частные домены не принимаются.
2. Срок регистрации `namre.app` — больше двух лет на момент подачи; в описании заявки — обещание держать регистрацию продлённой больше чем на год вперёд (домен, у которого осталось меньше года, могут убрать из списка).
3. Форк `github.com/publicsuffix/list`, правка `public_suffix_list.dat`: блок — между строками `===BEGIN PRIVATE DOMAINS===` и `===END PRIVATE DOMAINS===`, по алфавиту названия организации (не в конец файла):
   ```
   // Namre : https://namre.app/
   // Submitted by Evgenii Erman <адрес, которым владеет держатель домена>
   sh.namre.app
   ```
4. Pull request в `publicsuffix/list` по его шаблону, заполненному полностью: зачем (у каждого экземпляра своё имя в зоне, владельцы экземпляров — разные люди; нужна изоляция cookie и отдельный учёт лимитов сертификатов), сколько доменов (один), что они для общего пользования; пример: `ivan.sh.namre.app` и `petr.sh.namre.app` — разные сайты.
5. TXT-запись в зоне Route 53: имя `_psl.sh.namre.app`, значение — адрес этого pull request (`https://github.com/publicsuffix/list/pull/НОМЕР`). Запись не убирать и после внесения — она подтверждает, что домен по-прежнему хочет быть в списке. Проверка: `dig +short TXT _psl.sh.namre.app`.
6. Отвечать на вопросы в pull request до его закрытия. Сроков рассмотрения нет («NO SERVICE LEVEL AGREEMENTS ON TIME»), полные и ясные заявки идут быстрее.
7. После слияния браузеры, Let's Encrypt и другие получают список со своими обновлениями, по своему расписанию — недели и месяцы; ускорить нельзя. До тех пор — правило «Кому выдавать коды» выше.

## Проверка и журналы

```bash
systemctl status frps shturman-relayd shturman-relay-caddy shturman-relay-frpc
curl -fsS https://relay.sh.namre.app/api/health
journalctl -u shturman-relayd -n 50     # решения плагина и выдача имён: имена и адреса, без ключей и кодов
journalctl -u frps -n 50
```

## Если что-то не так

- `api/health` не отвечает после установки — `journalctl -u shturman-relay-caddy -u shturman-relay-frpc -u frps -n 80`: обычно Let's Encrypt ещё не проверил имя (DNS, порты 80/443) или служебный frpc не вошёл (в журнале relayd — причина).
- Служба `shturman-relayd` остановлена — frps отказывает в новых подключениях и пересылках всем экземплярам. `systemctl restart shturman-relayd`.
- Сертификат frps пришлось заменить (удалить `/etc/frp/frps.crt` и `.key`, затем `install.sh`) — каждый подключённый экземпляр должен забрать новый: `./ops/relay.sh on` и `./ops/up.sh` на его сервере.
