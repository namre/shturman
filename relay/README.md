# Посредник «Штурмана»: установка и сопровождение

Для держателя посредника `sh.namre.app` (docs/relay.md, решение Р-69). Это **не часть экземпляра**: всё здесь ставится на отдельный сервер посредника. Владельцу экземпляра этот файл не нужен — ему нужен только код приглашения и `./ops/relay.sh join` на его сервере.

**Версия:** 0.2.0 (`relay/relayd.py`, `VERSION`) · **Состояние:** проверено на стенде разработки (docs/relay.md, «Что проверено»); на настоящем посреднике не ставилось.

## Что получается на посреднике

| Служба | Что делает | Слушает |
|---|---|---|
| `frps` | Пересылка по имени сайта (SNI) без расшифровки; соединения экземпляров | `:7000` (TLS), `:443`, `:80` |
| `shturman-relayd` | Серверный плагин frps (кто какое имя может занять) и выдача имён по коду приглашения | `127.0.0.1:7400` (плагин), `127.0.0.1:7401` (`/api/*`) |
| `shturman-relay-caddy` | `https://relay.<зона>/api/*` → relayd; сертификат Let's Encrypt | `127.0.0.1:9080`, `127.0.0.1:9443` |
| `shturman-relay-frpc` | Служебный «экземпляр» `relay`: имя `relay.<зона>` через frps → Caddy посредника | — |

Файлы: программы — `/opt/shturman-relay`; настройки — `/etc/frp/frps.toml`, `/etc/shturman-relay/{Caddyfile,frpc.toml}`; секреты (только root, 600) — `/etc/frp/token.env` (общий токен frps), `/etc/frp/frps.key` (ключ сертификата frps), `/etc/shturman-relay/operator.env` (ключ служебного экземпляра); база экземпляров и приглашений — `/var/lib/shturman-relay/relay.db` (пользователь `shturman-relay`, 600; в ней хеши кодов и ключей, не сами значения). Публичный сертификат frps — `/etc/frp/frps.crt`: его получает каждый экземпляр.

## Перед установкой

- Ubuntu 24.04, `python3` 3.12 (есть по умолчанию), `curl`, `openssl`, systemd.
- DNS зоны: `relay.<зона>` и `*.<зона>` → адрес посредника; `CAA` — только `letsencrypt.org`, `issuewild ";"`.
- Открыты входящие 80, 443, 7000 (в Lightsail — правила сети инстанса).
- На посреднике прототипа: `/etc/frp/token.env` с `FRP_AUTH_TOKEN=` остаётся — установщик его не трогает.

## Установка и обновление

```bash
git clone https://github.com/namre/shturman.git && cd shturman   # или git pull в имеющемся клоне
sudo ./relay/install.sh
```

Повторный запуск безопасен: перезаписываются программы, настройки и службы из репозитория; токен, сертификат frps, ключ служебного экземпляра и база остаются. Прежняя `/etc/frp/frps.toml` и изменённые файлы служб сохраняются рядом с пометкой `.bak-ДАТА`. Службы прототипа `relay-test-*.service` установщик останавливает и удаляет.

Что делает установщик по шагам: скачивает frp 0.71.0 и Caddy 2.11.7 с GitHub и сверяет суммы (не совпали — ничего не ставится); ставит программы и `relayctl`; создаёт пользователя `shturman-relay`; создаёт, если их нет, общий токен и постоянный сертификат frps (`relay.<зона>`, ECDSA P-256, 10 лет); кладёт настройки и службы; заводит базу и ключ служебного экземпляра; проверяет настройки (`caddy validate`, `frps verify`); перезапускает службы и ждёт `https://relay.<зона>/api/health`.

Ожидаемый конец вывода:

```
  shturman-relayd: работает
  frps: работает
  shturman-relay-caddy: работает
  shturman-relay-frpc: работает
ГОТОВО: https://relay.sh.namre.app/api/health отвечает.
```

**При первой установке на прототипе** frps получает постоянный сертификат вместо случайного, а вход без ключа экземпляра перестаёт работать — тестовый экземпляр `test` больше не подключится (поэтому его службы и убираются).

Только проверить без установки: `./relay/install.sh --download-only НОВЫЙ_КАТАЛОГ` (скачать и сверить), `./relay/install.sh --render НОВЫЙ_КАТАЛОГ` (собрать настройки для зоны). Другая зона — `RELAY_DOMAIN=sh.example.org`.

## Коды приглашения и экземпляры

```bash
sudo relayctl invite --note 'Иван, пилот'      # код печатается один раз; по умолчанию живёт 7 дней (--days 1..90)
sudo relayctl list                              # экземпляры и приглашения (сами коды не хранятся)
sudo relayctl revoke ИМЯ                        # отключить экземпляр и перезапустить frps (рвёт его подключения)
sudo relayctl revoke ИМЯ --no-restart           # отключить без перезапуска frps (открытые соединения живут до перезапуска)
sudo relayctl release ИМЯ                       # освободить имя отключённого экземпляра; всегда перезапускает frps
```

Код передайте владельцу экземпляра удобным ему способом; он одноразовый. Имя владелец выбирает сам при `./ops/relay.sh join КОД ИМЯ`; неверное, служебное или занятое имя код не тратит. Ключ подключения создаёт сам экземпляр — посредник получает и хранит только его sha256; повтор того же подключения (ответ потерялся в сети) получает тот же успешный ответ.

**Кому выдавать коды.** Пока `sh.namre.app` нет в Public Suffix List (ниже), все экземпляры — один «сайт» для браузера: подключённый владелец может мешать входу в дашборды соседей (подброшенные cookie), а узнав чужой номер подключения frps — получить сертификат на чужое имя (`docs/relay.md`, риски 8 и 9). Поэтому до внесения в список коды — только тем, кому вы доверяете.

`revoke` отмечает экземпляр отключённым и перезапускает frps: рвутся управляющее соединение экземпляра и все уже открытые соединения браузеров к нему, остальные экземпляры переподключаются сами за несколько секунд. С `--no-restart` frps не перезапускается: новых рабочих соединений экземпляр не получает и переподключиться не может, но уже открытые соединения браузеров (keep-alive, HTTP/2) и заранее открытые рабочие соединения работают до перезапуска frps. `release` освобождает имя и всегда перезапускает frps — иначе прежнее подключение держало бы пересылку на это имя. Выдавать освобождённое имя другому владельцу раньше чем через 90 дней не стоит: сертификаты, выпущенные на него прежнему владельцу, действуют до конца срока. Обе команды требуют root.

## Public Suffix List

Внести `sh.namre.app` в Public Suffix List (раздел частных доменов) — тогда каждое имя в зоне станет для браузеров отдельным сайтом (риск 9 в `docs/relay.md`), а лимиты Let's Encrypt будут считаться на каждый экземпляр (риск 4). Порядок — по правилам списка (`github.com/publicsuffix/list`, wiki «Guidelines», сверено 2026-10-12):

1. Подаёт только владелец домена `namre.app` (или его уполномоченный представитель) от своего имени; сторонние заявки на частные домены не принимаются.
2. Срок регистрации `namre.app` — больше двух лет на момент подачи; в описании заявки — обещание держать регистрацию продлённой больше чем на год вперёд (домен, у которого осталось меньше года, могут убрать из списка).
3. Форк `github.com/publicsuffix/list`, правка `public_suffix_list.dat`: блок — между строками `===BEGIN PRIVATE DOMAINS===` и `===END PRIVATE DOMAINS===`, по алфавиту названия организации (не в конец файла):
   ```
   // Namre : https://namre.app/
   // Submitted by Evgenii Erman <адрес, которым владеет держатель домена>
   sh.namre.app
   ```
4. Pull request в `publicsuffix/list` по его шаблону, заполненному полностью: зачем (у каждого экземпляра своё имя в зоне, владельцы экземпляров — разные люди; нужна изоляция cookie и отдельный учёт лимитов сертификатов), сколько доменов (один), что они для общего пользования; пример: `ivan.sh.namre.app` и `petr.sh.namre.app` — разные сайты.
5. TXT-запись в зоне Route 53: имя `_psl.sh.namre.app`, значение — адрес этого pull request (`https://github.com/publicsuffix/list/pull/НОМЕР`). Запись не убирать и после внесения — она подтверждает, что домен по-прежнему хочет быть в списке. Проверка: `dig +short TXT _psl.sh.namre.app`.
6. Отвечать на вопросы в pull request до его закрытия. Сроков рассмотрения нет («NO SERVICE LEVEL AGREEMENTS ON TIME»), полные и ясные заявки идут быстрее.
7. После слияния браузеры, Let's Encrypt и другие получают список со своими обновлениями, по своему расписанию — недели и месяцы; ускорить нельзя. До тех пор — правило «Кому выдавать коды» выше.

## Проверка и журналы

```bash
systemctl status frps shturman-relayd shturman-relay-caddy shturman-relay-frpc
curl -fsS https://relay.sh.namre.app/api/health
journalctl -u shturman-relayd -n 50     # решения плагина и выдача имён: имена и адреса, без ключей и кодов
journalctl -u frps -n 50
```

## Если что-то не так

- `api/health` не отвечает после установки — `journalctl -u shturman-relay-caddy -u shturman-relay-frpc -u frps -n 80`: обычно Let's Encrypt ещё не проверил имя (DNS, порты 80/443) или служебный frpc не вошёл (в журнале relayd — причина).
- Служба `shturman-relayd` остановлена — frps отказывает в новых подключениях и пересылках всем экземплярам. `systemctl restart shturman-relayd`.
- Сертификат frps пришлось заменить (удалить `/etc/frp/frps.crt` и `.key`, затем `install.sh`) — каждый подключённый экземпляр должен забрать новый: `./ops/relay.sh on` и `./ops/up.sh` на его сервере.
